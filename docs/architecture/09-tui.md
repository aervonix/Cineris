# The terminal UI

The interactive front end. It is written in Rust and lives in the main binary, in two crates: `cineris-term` (terminal layer and renderer, no knowledge of agents) and `cineris-tui` (the application). The language choice is [decision 0001](../decisions/0001-tui-language.md) and the rendering approach is [decision 0002](../decisions/0002-tui-rendering.md). The owner accepted both on 2026-11-12, and both were confirmed on 2026-11-13 by the Windows Terminal checklist.

The look described here is our own: its glyphs, colours and wording are ours, in the arrangement modern terminal agents share. Glyphs, wording, colours, commands and default keys are defaults. The owner accepted a first draft on 2026-11-12, reopened it, and chose this look on 2026-11-14 after three rounds of proposals ([decision 0033](../decisions/0033-tui-look.md)). The TUI build steps implement what this page says and do not need to invent more.

It follows the [vision](../vision.md)'s interface policy: a clean chat-style flow by default, panels that open when there is something to show and close again, and the logo's purple (`#7A3CFB`) as the accent colour.

## Rendering approach

### Inline by default

The transcript lives in the terminal's own scrollback. The harness owns only a small **live region** at the bottom of the screen.

```
 ┌───────────────────────────── terminal window ─────────────────────────────┐
 │  … earlier output, owned by the terminal: scroll, search, select, copy …   │
 │                                                                            │
 │  committed transcript lines (written once, never touched again)            │
 │                                                                            │
 ├──────────────────── live region (owned by the harness) ────────────────────┤
 │  the unfinished tail of what is streaming                                  │
 │  the running tool round, in its box                                        │
 │  task list, approval dialog or completion menu, when present               │
 │  ╭ ◆ the input box ───────────────────────────────────────────────────╮    │
 │  hint row: the keys and the status that matter now                         │
 └────────────────────────────────────────────────────────────────────────────┘
```

**Why.** The terminal's scrollback, search, selection and copy keep working, including over SSH and inside multiplexers. Nothing the harness has printed needs to be kept in memory or redrawn, so the cost of a frame depends on the size of the live region and not on the length of the session. The measurements behind this are in decision 0002.

**The rule that makes it flicker-free: commit as soon as stable.** Content moves from the live region to the scrollback the moment it can no longer change. The live region therefore stays a few lines tall however long the answer is.

| Content | Committed when |
|---|---|
| Paragraph text | A wrapped row is committed when the next row has begun and no mark is open before the end of that row's first word. Only the last, growing row stays live. |
| Inline markup still open at the end of a row (bold, code, a link) | The row is held for at most two more rows; when a third has begun, it is committed as it is, and its open marks stay literal from then on. |
| Code block | Line by line, as each line ends. With highlighting, a line waits for its colours for at most 50 ms. |
| List, quote | Their paragraphs row by row, as above; a list item's marker with its first row. |
| Heading, rule | When its line ends. |
| Table | When the table ends, because column widths depend on every row. A table of more than 16 body rows is committed in parts of 16, each with the widths and the layout decided for the first. |
| Reasoning | Not committed while streaming. Replaced by its summary (`∴ Reasoned for 6s` and the provider's summary) when it ends. |
| Tool round | Live while any of its calls runs. The round's box, with each call's line and any open detail, is committed when its last call completes ("Tool rounds", below). |
| User prompt | On submit. |

### The commit rule

What "can no longer change" means for markdown that arrives a token at a time. `cineris_tui::markdown` holds it, and its tests hold it to this.

- **Blocks are decided by whole lines.** A line is read when it ends, and it says whether the block before it goes on: a blank line, or a line that starts another block, ends it. A line still arriving is given to the paragraph in progress as soon as its first characters show it can start nothing else (a letter, `**bold`, but not `-`, `1.`, `#`, `>` or `|`, which wait for the line's end).
- **A finished block is never parsed again.** Its rows are committed and its text is dropped. Inside a paragraph, the text of committed rows is dropped too, at a break between rows that no construct spans, after which the text parses alone as it did with what came before (plain text, at white space or at a character that can neither open nor close anything), so a paragraph is parsed again only from its first row still live.
- **The text kept is bounded.** A paragraph with no such break for long (one long word of marks or entities, or rows that all start inside a code span) keeps at most 1 KB of committed text before the break is forced where a row starts outside every construct, and 4 KB before it is forced where any row starts; the text after a forced break is parsed alone, so a construct across it may show its marks. Past 1 KB the decisions are also spaced 64 bytes apart, and one decision parses the text once for every row it commits. Each byte is then parsed a bounded number of times, whatever the text, and a frame's live rows parse no more than the text kept.
- **A paragraph's rows are decided at the end of each word, from the text up to it,** and inside a run of text with no white space every 64 bytes, at the first place after them where the byte after the cut cannot change what ends there (the text up to a decision is parsed as if white space followed it): after a letter, a digit or most punctuation; after `!` unless `[` follows, `]` unless `(` does, `<` unless a letter does, `&` unless a letter, a digit or `#` does; after backslashes in pairs; and inside a stretch of `*`, `_` and backticks once it is longer than marks can be (below). Row k is final when row k+1 has begun and nothing before the end of row k+1's first word, or of row k+1 if that word goes on past it, can change: no mark that text still to come could close (an emphasis mark that can open, a backtick run with no closing run, a bracket that is not a link's, a backslash, an entity or an autolink at the very end), and no matched construct with such a mark inside it, whose closing mark a later code span or link could take in. Otherwise the row is held for two more rows, then committed as it is: its open marks are frozen as text, with every open mark inside a construct that starts before that point. Because the decisions depend on the text alone, the same text commits the same lines whether it arrives token by token or at once.
- **What the dialect leaves out, so that nothing committed is restyled:** a heading is written with `#` only, because a `---` or `===` under text would turn the whole paragraph above it into a heading (`---` is a rule, `===` is text); and a table's header row starts with `|`, so that a line is known to be a table candidate from its first character. Inline HTML and strikethrough are shown as the text they are, and reference links are not resolved. A stretch of more than 64 of the marks `*`, `_` and backticks with nothing between them is text: what a mark is depends on the runs around it, so a stretch could not otherwise be decided until it ends.
- **The parser is our own** (decision recorded in [01-workspace.md](01-workspace.md)): the commit rule needs every piece of text's place in the source and the marks still open, which a whole-document parser does not give. Its inline rules are CommonMark's for the constructs above, held by cases written from the specification's examples.

**The price.** Committed lines are wrapped for the width at the time. If the window is resized, earlier output is not re-wrapped by the harness. A paragraph resized while it streams keeps the breaks of its rows already committed, and what follows them is wrapped at the new width; a row queued behind a code line still waiting for its colours is wrapped to the new width when it commits. Collapsing or re-expanding old output in place is not possible either; long content is opened in the viewer (below) instead.

### Full screen as the alternative

A second presenter owns the whole screen (the terminal's alternate screen). It keeps the transcript itself, scrolls it, re-wraps on resize and restores the user's previous screen on exit.

- Selected with `--fullscreen` or `tui.presenter = "fullscreen"`.
- It exists for terminals and multiplexers where inline drawing misbehaves, and for people who prefer an application-style view.
- It is built after the inline presenter, on the same renderer, and shows the same components.

**The full-screen presenter as built (step 25, its first pull request).** The design, its review and the maintainers' answers are [steps/25/answered.md](../steps/25/answered.md); what the pull request built and measured is [steps/25/parts/pr1-full-screen.md](../steps/25/parts/pr1-full-screen.md).

- **What it keeps.** The application keeps the transcript's finished blocks, not their lines (`transcript::Kept`, from `Transcript::take_finished`), in both presenters; the viewer and the full-screen presenter draw them again at the width they have. An answer keeps its markdown and the colours its code lines were committed with (`markdown::Source`), drawn again by `Markdown::render_source`. A finished round keeps a command's output to its last 64 KiB ([outstanding](../outstanding/a-kept-box-holds-only-the-end-of-its-output.md)). The rows of the blocks near the window are made when it reaches them and dropped after (`app::scroll`), and all of them on a change of width or look.
- **A frame.** `cineris_term::Full` draws the whole screen in one write, inside a synchronized update, writing only the rows that changed, each placed by its number and erased to its end; nothing is cleared and drawn again. The rows, top to bottom, are the transcript's window (the kept blocks, the rows an answer still streaming has committed, and the live rows), the panels' block, and the bottom (the input box with its hint row or menu, or a dialog), the last two made by the same code as the inline presenter's. The same session draws the same rows, styles included, under both presenters, frame by frame.
- **Scrolling.** The window follows the end, from the start and after each prompt or dialog. `PageUp`, `PageDown`, `Shift+Up`, `Shift+Down` and the wheel move it (the `screen` context of the key map), and any move up stops it following: its last row then says `more below · pagedown goes to the end`. Reaching the end follows it again. The window is held by its top block and row, so what changes above or below it does not move it.
- **Re-wrapping.** A change of width draws every block again at the new width; an answer still streaming is made again from its text at the new width (`Transcript::rewrap_open`), as if it had streamed there all along. Code keeps its colours, and code committed plain because its colours were late is handed to the highlighter again, whole, and coloured when they come.
- **Search.** `Ctrl+F` opens a row in the hint row's place. Each kept block's text goes to a worker of its own as it is kept (`app::search`), which answers the latest query with the blocks that hold it; the newest match is brought into view, every match on the screen is drawn reversed and the current one bold too, `Up` and `Enter` go to the older and `Down` to the newer, going round, and `Esc` ends it where it is. A match inside a closed box opens the box while it is current, its border saying `opened by the search`, and leaves it open when the search ends there. What is still streaming is searched once it is kept.
- **Panels beside the transcript.** From 140 columns the panels sit in a column of their own on the right, 40 columns and one more for each two past 140, up to 56, from the top, with step 24's rules inside it; the transcript keeps the rest, two columns from it, and the bottom keeps the whole width. The column is kept whether or not a panel is open, so that the transcript is not laid out again as panels come and go: at 140 columns the transcript is 97 wide.
- **Committed boxes.** Drawn as the inline presenter committed them. A click opens or closes one; the viewer (`Ctrl+O`) is the way to them by keys, on the same alternate screen.
- **Leaving it.** Every way out (quitting, the core gone, a signal, a write that fails, a panic, the external editor, a suspension) turns the mouse off and leaves the alternate screen; the main screen comes back as the shell left it, and nothing of the session is printed on it.

### One renderer, two presenters

Every component renders to **styled lines** for a given width. A presenter decides where lines go.

```
items ─► components ─► styled lines ─┬─► inline presenter ─► commits + live region
                                     └─► full-screen presenter ─► viewport over all lines
```

The renderer is ours and line-based. The reasons for not using a cell-grid TUI framework's terminal are in decision 0002: the measured prototype built on one sent more bytes per frame than a line-based renderer needs to, its inline mode has a fixed height and relies on asking the terminal for the cursor position, and other Rust harnesses that started with it replaced that part.

### How a frame is drawn (inline)

1. Collect lines committed since the last frame, and the new live-region lines.
2. Build the frame in one buffer:
   1. begin a synchronized update;
   2. move the cursor to the first row of the live region;
   3. write each newly committed line, each followed by "erase to end of line" and a line break; the terminal scrolls by itself as needed;
   4. write the live region: if nothing was committed and its height is unchanged, only the lines that differ from the previous frame; otherwise all of it, then "erase below";
   5. place the cursor at the editor's insertion point;
   6. end the synchronized update.
3. Write the buffer with a single system call.

Properties this gives, each checked by tests ([../testing-and-ci.md](../testing-and-ci.md)):

- Nothing is ever cleared and then redrawn. Lines are overwritten in place.
- A frame is one write, wrapped in a synchronized update, so a terminal that supports the mode shows it atomically, and one that does not receives so little at once that tearing is rare.
- No scroll-region or cursor-position queries are needed, which avoids the terminals and multiplexers that mishandle them.
- Nothing above the live region is touched.

**Live region height.** At most half the window, and at least the input box and the hint row. Content that would exceed it is clipped with a marker (for example a tool's output tail shows fewer lines). The presenter itself only refuses a region taller than the screen: it keeps the region's bottom rows, because rows that had scrolled away could not be reached again.

**The last column stays empty.** A line may use every column but the last (`Inline::width`). A row that filled the last column would leave the terminal waiting to wrap, which terminals handle differently (some wrap at once, and the next line break then leaves a blank row), and the erase after it would take its last character. Lines are cut to that width by the renderer, between grapheme clusters, so a line is always one row.

**Resize.** On a width change the live region is redrawn at the new width, row over row, and whatever is left below it is erased. Because the terminal may have re-wrapped the old live region itself, a few stale lines can be left in the scrollback after a shrink. `Ctrl+L` redraws the live region. The full-screen presenter has no such limit.

### Frame scheduling

- The UI loop sleeps until something happens: a key, a core event, a resize, or an animation tick while something is running.
- **Stream-driven frames** are capped at 60 per second. Events that arrive between frames are merged.
- **Input-driven frames** are drawn immediately. A key press never waits for the frame timer.
- A frame is skipped when the lines to draw equal the lines on screen.
- When idle, nothing is scheduled.

The budgets for frame time, input latency and idle CPU are in [../performance-budgets.md](../performance-budgets.md).

### Rendering cost control

- Each transcript item caches its rendered lines by content version, width and theme.
- Streaming markdown is parsed incrementally: finished blocks are never parsed again, only the block in progress ("The commit rule", above).
- **Syntax highlighting runs on a worker thread of its own** (`cineris_tui::highlight`, [decision 0015](../decisions/0015-syntax-highlighting.md)), started when the first code block asks for it. The worker loads the grammars, keeps each block's parse state and colours its lines in order; the interface hands it each line as it ends and takes what it has finished, and never waits for it. A completed line waits for its colours for at most 50 ms on the caller's clock, and is committed plain after that, so a stuck worker never holds the transcript; while it waits it is drawn plain in the live region. A line over 1,000 bytes is never highlighted. The line still streaming is drawn plain until it ends. The colours are the theme's five syntax tokens, picked by the grammar's scope names (keyword, type, string, number, comment).
- In inline mode, committed lines are dropped from memory. In full-screen mode, rendered lines are kept only around the viewport and rebuilt from items on demand.

## Layout and look

The owner chose this look on 2026-11-14, after three rounds of proposals ([decision 0033](../decisions/0033-tui-look.md)). Its reference screens are in [tui-look/](tui-look/README.md): the same session drawn at 100 and 60 columns, on a dark and a light background, in 16 colours, with no colour and in ASCII. They were generated from one source and each was drawn through the inline presenter into the test kit's virtual terminal before the choice.

- **Prose** wraps at `tui.prose_width` (default 80) or the window's width, whichever is smaller.
- **Code, diffs and boxes** use the window's width, less the last column.
- **Two indent levels:** a block's text sits two columns in, after its glyph. A tool call's detail sits two columns in from its call line, inside the round's box.

### Tool rounds

**One box per round:** the calls the model asked for together. A round is what runs together, and a box for each call would add two border rows to every call.

**A call's line:** its state mark, then the tool as a bold imperative with its target (`Read lex.rs`, `Edit lex.rs`, `Run cargo test -p parser`, `Search scan_number`; an extension's tool by its own name), then two spaces and its measure, dim. An edit's measure is `+5 −1` in the diff colours, and a failure's measure (`exit 101 · 3.4s`) is in the error colour. A path is shortened to its file name; the whole path is in the viewer.

| Mark | Meaning | Measure |
|---|---|---|
| spinner (accent) | running | elapsed time |
| `?` (warning) | waiting for approval | "approval needed" |
| `✓` (success) | succeeded | lines, matches, `+4 −1`, duration |
| `✗` (error) | failed | exit code or a short reason, and the duration |
| `⊘` | denied | |
| `■` | interrupted | |

The spinner is an eight-frame braille cycle at 100 ms. `tui.reduced_motion = true` replaces it with a static mark.

**Open and closed.** Closed, a box shows only the call lines. Open, each call's detail sits under its line, two columns in. What starts open, with `tui.tool_output = "auto"` (the default):

| Detail | Starts |
|---|---|
| A failure's output | open, the last 3 lines |
| A diff of up to `tui.tool_detail` lines (default 12) | open |
| A longer diff | closed |
| A successful command's output, a read, a search | closed |
| A running command's output | closed; open, its last 4 lines |

`"always"` opens every detail, and `"never"` keeps every box closed.

**While a round runs, its box is in the live region.**
- `Ctrl+T` opens or closes it in place, and its bottom border says which (`ctrl+t expands`, `ctrl+t collapses`).
- With more than one live box, `Ctrl+P` moves focus to them as it does to panels, and `Enter` opens or closes the focused one.
- An open box in the live region shows at most `tui.tool_detail` rows of detail; the rest is in the viewer.

**Too much detail for the live region.** When the open details in a live box come to more than `tui.tool_detail` rows, the first rows are kept and a dim row says how many more there are (`… 8 more lines`); the box shows all of them once committed.

**When the round's last call ends,** the box and its detail commit together, as they are, and never change after. A closed box with detail behind it says `ctrl+o expands` in its bottom border, dim. Calls that finish early wait for the round: their detail appears when the round commits, and until then the open box shows it in the live region.

### The live region

```
          return Err(self.error("digit separator mu

╭────────────────────────────────────────────────────────────────────────────╮
│ ◆ also run clippy when that's done                                         │
╰────────────────────────────────────────────────────────────────────────────╯
  ⣾ 14s  esc stops · enter steers this turn · tab queues it      opus-5.5 high · fast
```

From top to bottom:

1. **Streaming tail.** The unfinished last line or lines of the current block, or the two reasoning rows.
2. **The running round.** Its box, with the calls' lines and any open detail.
3. **Panels.** Whatever currently has something to show ("Panels", below).
4. **Dialog.** An approval or question replaces the input box while it is open.
5. **Input box.** A rounded box with a dim border, holding `◆` and the text. It grows to 8 lines, then scrolls inside itself. When it is empty it shows a dim placeholder.
6. **Hint row.** One dim row under the input box, in place of a status line. Its left side holds the keys that matter now, and its right side the status that matters now.

The hint row's left side:

| When | Shows |
|---|---|
| A turn is running | The spinner and the turn's elapsed time, then `esc stops · enter steers this turn · tab queues it instead`. Steering and queueing are offered only while a turn runs. |
| A dialog, a menu or a focused panel | Its keys. |
| Idle, after a turn | The turn's cost and the session's, for a while. |
| Idle, in the first sessions | `/ commands · @ files · alt+enter new line`. |
| `Ctrl+C` pressed idle with nothing typed | `ctrl+c again quits`, until the next key. |

The hint row's right side:

| Segment | Shown |
|---|---|
| Model | Always: the short model name and the reasoning level. |
| Speed | When not `standard`: `fast` (or the tier's own name) in the accent's text colour, and while a cooldown runs `fast after 14:32`, dim: requests go at `standard` until then ([decision 0027](../decisions/0027-speed-tiers.md)). |
| Context | From 50% of the context window: the percentage, in the warning colour from 70% and the error colour from 90%. |
| Cost | When a budget is set: the spend against it ([14-adaptation.md](14-adaptation.md)). Otherwise on the left, for a while after each turn. When a provider reports a limit and less than a fifth of it is left: what remains and when it resets. |
| Access | When it is not the default: `sandbox off` or `unrestricted` in the warning colour, a command that ran outside the sandbox, and under a task lease (after the first release) what remains of its time and budget. |
| Extras | When relevant: the queued prompt count, MCP or extension problems, a rate-limit wait. |

- **Narrow windows.** Both sides sit two columns in from the edges, in line with the input box's text. When they do not fit, the left side is cut with `…`, down to 24 columns; then the right side's segments are dropped from its right, in the order of the table above, the model last. Under 50 columns the hint row shows the model and the context only.
- **While a turn runs with a pending message queued** (`Tab`), the keys read `esc stops · enter queues it · tab steers this turn instead`; with a dialog, a menu or a focused panel open, the spinner and time are followed by its keys.
- **Everything else is a key away:** `/usage` for cost and the cache hit rate, `/context` for what the window holds, `/status` for the rest.
- **Height.** While an answer streams, the live region is 6 rows: the tail, a blank row, the 3 rows of the input box, and the hint row. A running round adds its 2 border rows, one row per call, and any open detail. Rows that do not change (the box's borders) cost nothing on a frame that commits nothing.

### Panels

A panel is a bounded block in the live region that appears when it has something to show and disappears when it does not. The chat flow stays the default view; nothing is permanently split off.

| Panel | Opens when | Shows | Closes when |
|---|---|---|---|
| **Plan** | The `plan` tool has items. | `◇ Plan  1 of 4 done`. Collapsed: that line with the active item after it. Expanded: one item per line, two columns in, with `☐`, `◧` (active, in the accent), `☑` and `⊘` (skipped). | The plan is empty or all items are done and the turn has ended. |
| **Review** | A turn ended having changed files. | One line per changed file with `+` and `−` counts, and the verification result. | The next prompt is sent. The changes stay reachable through `/view` and `/undo`. |
| **Usage** | `/usage`, or a limit is near. | This session: tokens by class, cache hit rate, cost by model, speed. History: usage and cost per provider and model for today, the week, the month and all time, with a breakdown per project, and what is left of each provider's limits ([18-usage.md](18-usage.md)). Near a limit and not opened: one line in the warning colour. | Dismissed, or the limit is no longer near. |
| **Project** | Learned entries are waiting for review, or `/project`. | Proposed commands, conventions and facts with their sources. | Reviewed or dismissed. |
| **Attempts** (after the first release) | Parallel attempts are running. | One row per attempt: variant, state, cost, checks. | A winner is picked or the attempts are discarded. |
| **Employees** (after the first release) | A Coordinator team is running. | One row per Employee: task, state (working, waiting, needs approval, stuck, done), model, spend, last activity. `Enter` attaches to that Employee: the transcript view switches to its session, and a banner shows whose session it is and how to return. | The team has finished and its work is integrated or discarded. |
| **Escalations** (after the first release) | Something is waiting for the user's decision. | The queue: who is asking, what kind of decision, the question. `Enter` opens the detail (command, diff, plan) with the choices. A count shows in the hint row. | The queue is empty. |

- **Height.** Each panel is collapsed by default to one to three lines. The live region's overall limit still applies; when several panels compete, the oldest collapses first.
- **Focus.** `Ctrl+P` moves focus from the input to the live tool boxes and the panels, and back. In a focused panel, `Up` and `Down` move, `Enter` expands an item or opens it in the viewer, and `Esc` returns to the input. The focused item is drawn in the accent, in bold.
- **Editing the plan.** With the plan panel focused: `Space` skips or restores an item, `e` rewords it, `Alt+Up` and `Alt+Down` reorder, `a` adds, `d` deletes. Each change takes effect at once and is passed to the agent at its next safe boundary ([05-tools.md](05-tools.md)).
- **In the full-screen presenter**, on a wide window, panels may sit beside the transcript instead of above the input. The components are the same. The owner chose stacked panels as the default on 2026-11-12.

**The panels as built (step 24, its second pull request).** The design is step 24's; what this part built, measured and departed from is its record, [steps/24/parts/pr2-panels.md](../steps/24/parts/pr2-panels.md).

- **A kind of panel is one type and one registration:** `app::panels::Panel` (what it sees and whether that opens or closes it, its rows collapsed and focused, its items, its hint keys, what each of its keys does), registered once in the application. The mechanism (`app::panels::Panels`) keeps the open ones in the order they opened and draws them as one block under the transcript's live rows and above the input box, ending in a blank row, and beginning with one when no live row is above it to set it apart from the scrollback. A panel without the focus is drawn collapsed; the focused one whole.
- **The live region's limit.** The block has what the bottom (the input box and its hint row or menu) leaves of half the window, less up to four of the transcript's live rows and its blank rows. When the panels need more, the focused one scrolls its list to keep its focused item, a dim `… N more` row at a cut end when there is room for it, and the oldest collapsed panels fold into one dim row, `+2 panels · ctrl+p`. A window of eight rows or fewer, or a menu or the history search open, draws none, and so does a dialog, which takes the focus back to the input. The folded row names the key only when it reaches a panel folded there. The focus ring is given the panels that would be drawn focused in that room, so a panel that would not be cannot hold the focus, and one a command asks for (`/plan`) that the rows the last frame gave the panels cannot draw focused says the window has no room for it, in the command's own frame, and does not take the focus (nor does any while a dialog is up); the focused item is kept by its id when the list changes under it. The panel whose item is being edited in the input box stays drawn whole. Only the events of the session open here reach the panels.
- **The keys.** `focus.skip` (`space`), `focus.edit` (`e`), `focus.add` (`a`), `focus.delete` (`d`), `focus.move_up` and `focus.move_down` (`alt+up`, `alt+down`), `focus.accept` (`y`), `focus.disable` (`n`), `focus.promote` (`p`), `focus.refresh` (`r`), `focus.range` (`tab`), `focus.group` (`g`) and `focus.close` (`x`) come to the application as the input's `Outcome::Panel` while a panel has the focus (the application looks the key up only to tell moving from typing). Each that changes something (all but `focus.close`) is taken only when the panel is ready, by the dialog's rule (`app::ready::Readiness`, which the dialog uses too): 300 ms after the focused row was first drawn, and a second after input no panel took (typing, keys read together, a paste, `/plan`'s own `Enter`; moving the focus with `Ctrl+P` is not such input). Its grace starts again after the viewer, `fg`, the external editor, a dialog, a new key map (`App::set_keymap`), and a change of the focused row from outside, as the change is seen and not at the next frame, since the loop takes keys between what it drains. A key held down never acts: a marked repeat, or the same key again within a second of one the panel took, goes nowhere, even once the panel it acted on has closed; after a key that began an item edit, only a marked repeat, since what is typed then is the item's. While a change of a panel's is on its way to the core (an operation of the session open it waits for), a key's change computed from what the panel shows, which the first will change (a second reorder), is not sent: the hint row says the last change is still being made, and the key, pressed again once the answer has come, acts. Moving (`Up`, `Down`, `Ctrl+P`), `Enter` and `Esc` act at once. A key that types and is not taken, by a panel or a live box, goes to the editor, and the focus with it (`Input::pass_to_editor`).
- **Rewording and adding** use the prompt's own editor (`Input::begin_item_edit`): the draft is set aside whole, `Enter` gives `Outcome::ItemEdited` and `Esc` `Outcome::ItemEditCancelled`, and either brings the draft back. Nothing goes to the history, no completion menu opens, and an item is one line: the plan sends the line breaks, tabs and other control characters a paste or the external editor brought as spaces, and cuts an item to the 400 characters it holds, which it says. The focus goes back to the panel after.
- **The plan panel** opens when `plan.updated` (or `plan/get`, asked when a stored session is opened) gives a plan with something left to do, or while a turn runs; it closes when the plan is empty, or every item is done or skipped and no turn runs. A plan older than the one shown (by its `revision`) is not taken. `space` skips (on a pending or active item; restoring a skipped one waits for `PlanEdit::Restore`), `e` rewords, `a` adds after, `d` deletes, `alt+up` and `alt+down` reorder: each one `plan/update` in the session open, whose result replaces the plan shown, whose error is said, and which is dropped for a session left. `/plan` focuses it, and with no plan says the model makes one with its plan tool.
- **The review panel** gathers, from `turn.started`, the files the `edit` and `write` tools changed (their counts summed by path, and the viewer's box of the last call), whether a command succeeded, the verification notices and the turn's verdict. It opens when the turn's checks start, end or are offered, and when the turn ends having changed files; it closes when the next turn starts, when this client sends a prompt, and with `x`. `Enter` on a file opens the viewer at its box. The turn's verdict (passed, failed, incomplete) is also in the turn summary line, after its cost, as the summary's text.

**The project and usage panels as built (step 24, its third pull request).** What this part built, measured and departed from is its record, [steps/24/parts/pr3-usage-project.md](../steps/24/parts/pr3-usage-project.md). Both are kinds of the mechanism above, with three more of its hooks: what a panel asks of the core when a command opens it (`/project`, `/usage`), the focus taken or moved inside it (a question asked in a row is forgotten), and whether its focused item's rows were all drawn in the frame on screen (`Panel::shown_whole`), its readiness starting again when that is new.

- **The project panel** shows the entries in use and waiting for this person's review (`project/list`, asked as a session opens, a failure that says no project is kept there not said, and again by `/project`): those waiting first (a proposal, an observed entry that became active by itself, an entry of the repository's file not accepted here), then the rest in use. It opens by itself, collapsed (`◇ Project  2 entries wait for review · 3 in use`), when entries wait; `/project` opens it with the focus; it closes when nothing waits and `/project` did not open it, and with `x`. `project.updated` changes its rows, a deleted entry going when it says so. Each entry is a row (its mark, kind, text cut with `…`, and age), and the focused entry's detail follows it, wrapped at the width and never cut: the command whole, what it is for, its folder and whether it only reads; its text; where it came from; its standing as the engine will treat it (a command accepted in a project not trusted as it is still asks); what accepting it keeps it until (a learned entry its kind's lifetime from the acceptance); its check, `not run in this build`; its evidence. `y` accepts, `e` edits the text in the prompt's own editor, `n` turns the entry off, `d` deletes it after asking in its row (`delete this entry? y deletes · any other key keeps it`, a move of the focus included), `p` promotes it to the repository's file: each one `project/update` with one change. **`y` is taken only when the focused entry's whole detail was drawn in the frame on screen;** an entry whose detail does not fit offers no `y`, and the hint row says to make the window taller (`y` pressed says so). Keys are offered, and taken, only where the core would act: no edit or delete of an entry of the repository's file, no promote of one not in use and accepted, and beside `p`, while a turn of this session runs, `promotes after this turn` (the core refuses a promote then, with its sentence).
- **The usage panel** opens with `/usage`, focused, its history asked for at once (`usage/report`, beside the lane, and `usage.refresh` with `config/get`) and drawn `reading…` until it comes; or by itself as one line in the warning colour when a provider's limit has less than a fifth left (`anthropic fast tier: 18% of the output token limit left, resets 15:00`, screen 4); it closes with `x`, or by itself when that limit is no longer near. It shows the session (`usage.updated`: tokens by class per model, cost, cache hit rate, tokens a second, time to the first token, speed), the history for a range by a grouping (`tab`: today, this week, this month, all time; `g`: provider then model, project, speed, provider within project) with the turns' time and the zone its days are counted in, the report's notes (what `cineris stats` says of the statistics), and each provider's limits with their age, a reset passed said as `reset since; unknown until the next request`, a refreshed figure as `from the refresh`, balances in their currency, and `not available` for a provider that reports none. The table's columns drop as the window narrows (cache writes, then cache reads, then input); under 60 columns it is the name, the output and the cost. Each cost has its basis: metered plain, `est.` with the legend once, a total that mixes them shown apart, an unknown price `—`. `r` asks the providers in `usage.refresh` (`usage/refresh`), one request at a time; with none in it, `r` says so and sends nothing.

### Dialogs and menus

Dialogs appear in the live region, above the hint row, in place of the input box.

**Approval.**

```
? Edit .github/workflows/ci.yml?
  CI configuration is protected, so a change to it always asks.

     29         - uses: dtolnay/rust-toolchain@stable
     30 −         with: { components: rustfmt }
     30 +         with: { components: rustfmt, clippy }
     31         - run: cargo test --workspace
     32 +       - run: cargo clippy --workspace -- -D warnings

  y Allow once   s Allow this session   a Always allow here   n Deny   e Deny with a note

  esc denies · ctrl+o shows it whole                                  opus-5.5 high · fast
```

- **The question** is bold, after a `?` in the warning colour. A dim line says why it is asked.
- **The detail** shows exactly what will run, wrapped, never shortened, or the diff with the line-number and sign gutter. Control characters are drawn as visible symbols. Detail of any kind taller than the window allows is clipped, with a line that says how many more lines there are, and `Ctrl+O` opens it whole; the question above it is never cut. While some of it has not been seen, no lasting answer is offered.
- **The answers** are on one line, each key in the accent. Letters choose directly, and `Esc` denies. A choice is offered only where [06-permissions-and-sandbox.md](06-permissions-and-sandbox.md) offers it.
- **Leaving the sandbox,** in a session whose sandbox is enforcing, asks `Run outside the sandbox?`. It shows the command and its folder, and says in the warning colour that it would run with the user's full rights and that this is asked every time. It offers only `y Run once outside the sandbox` and `n Deny`.

**Menus** (slash commands, file completion, model and session pickers) open below the input box, in place of the hint row. They show up to 8 rows, filtered as the user types. The selected row is marked with `◆` and drawn in the accent, in bold. `Tab` or `Enter` accepts, and `Esc` closes. The `/effort` menu ends with its fast-mode row, `tab - fast mode` and its state, when the model offers a fast speed.

### The viewer

`Ctrl+O`, or `/view`, opens the session in a temporary full-screen view on the alternate screen.

- **Layout.** A title row (`Viewer`, the folder, the session and its turns, and `esc returns to the session`), then the transcript, then a key row.
- **Boxes.** Every tool box starts closed, and the latest is selected, with its border in the accent. `Up` and `Down` move between boxes. `Enter` opens or closes the selected one with all its detail: the whole diff and the whole output, not a tail.
- **Moving and searching.** `PageUp` and `PageDown` scroll, and `/` searches.
- **Returning.** `Esc` returns to the inline screen exactly as it was.
- **Other long content.** The viewer also opens the reasoning summary, a compaction summary, and an item named by `/view n`.

This is how inline mode offers "expand" without rewriting the scrollback.

### The mouse

**Not in inline mode.** A terminal reports the mouse for the whole window or not at all; no mode limits it to some rows.
- With reporting on, the wheel is sent to the program instead of scrolling the scrollback, and a drag no longer selects text (Windows Terminal and xterm then need `Shift`). That breaks the two things inline mode exists for.
- Reporting cannot be turned on only while the pointer is over the live region, because nothing is reported until it is on.
- tmux passes clicks only when its own mouse mode is on.
- The inline presenter never asks where the cursor is, so it does not know which screen row its live region starts on. Mapping a click to a box would need the cursor-position query that [decision 0002](../decisions/0002-tui-rendering.md) avoids.

Inline, the keys do the work: `Ctrl+T`, and `Ctrl+P` then `Enter`.

**In the viewer and the full-screen presenter,** which own the screen, mouse reporting is on while they are shown (modes 1000 and 1006):
- a click on a box opens or closes it;
- the wheel scrolls the transcript;
- `Shift` and a drag select text with the terminal's own selection.

**As built in step 25.** The decoder reads mode 1006's reports, and mode 1000's own form while the mouse is on (`Event::Mouse`, with `Mouse`, `MouseKind`, `Button` and `Wheel`). `Terminal::set_mouse` asks for the mouse; the terminal turns modes 1000 and 1006 on with the alternate screen and off before it, and every emergency restore with the alternate screen on turns them off. **On Windows, and wherever the win32 input mode is on, nothing asks for the mouse** (`Capabilities::vt_mouse`, and the terminal's own check of the mode; since step 25's follow-up). On a hosted runner's pseudo-console (step 25): modes 1000 and 1006 written by the program are passed on to the terminal, whose reports then reach the program as typed keys (the wheel typed `[<64;10;5M`); and the console's mouse input with QuickEdit off makes the pseudo-console itself ask the terminal for modes 1003 and 1006, whose reports would come the same way. A Linux build under WSL or over ssh in Windows Terminal is likely to meet the same, behind a pseudo-console in the same mode (inferred: neither WSL nor Windows Terminal's own ConPTY was measured), so the mode decides, not the system; a terminal that knows the mode itself, with no pseudo-console between, loses the mouse with it. So there the viewer and the full screen have no mouse, and the keys do what it does (`PageUp`, `PageDown`, `Shift+Up`, `Shift+Down`, the viewer's `Enter` on a box); the terminal keeps its own selection, and its wheel is its own to give: Windows Terminal's alternate scroll is likely to send it to the full screen as `Up` and `Down`, which reach the input (not measured). A console record of the mouse is still read as the report it stands for, though none is asked for. [Outstanding](../outstanding/the-mouse-under-windows-terminal.md). `terminal.mouse = false` turns it off. A click is a press and a release of the left button on the same cell; the wheel scrolls three rows a notch. The viewer's keys and the mouse's gestures are actions of the key map, in its `viewer` and `screen` contexts (`viewer.toggle` takes `enter` and `click`, `viewer.scroll_up` `wheel_up`, and so on); `click`, `wheel_up` and `wheel_down` can be bound only there.

### Colour and glyphs

**Colours are semantic tokens.** The default theme uses one brand colour, the accent, and maps every other token to the terminal's own 16 colours, so the UI follows the user's terminal theme, light or dark.

**The accent is the logo's purple, `#7A3CFB`.** It marks your `◆` (in the transcript and the input), the spinner, `fast`, the active plan item, the answer keys in a dialog, the selected menu row, and the viewer's selected box. Nothing else.

| Terminal | Accent shown as |
|---|---|
| True colour | `#7A3CFB`. |
| 256 colours | Index 99, the nearest. |
| 16 colours | Named by the theme: bright magenta (13) on a dark background, magenta (5) on a light one. |

**The theme names its 16-colour accent itself.** The automatic reduction (`Color::for_depth`) brings `#7A3CFB` to the nearest xterm colour, which is bright blue (12), not magenta.

**On a dark background at 16 colours, the accent marks but does not carry text.** No magenta reaches 4.5 to 1 there: on Windows Terminal's default scheme (Campbell, `#0C0C0C`), magenta is 2.4 to 1 and bright magenta 3.2 to 1. There, accent-coloured text (the selected menu row, the focused plan item) is drawn bold in the default colour, and only glyphs take the magenta. On a light background magenta reaches 5.9 to 1 (One Half Light) and is used as it is.

**The tint for text.** In true colour, on a dark background, that purple has a contrast of about 3.6 to 1, enough for marks and not for text. Text in the accent colour therefore uses a lighter tint (`accent.text`), chosen to reach at least 4.5 to 1 against the terminal's background, which is queried at start-up: `#8D57FC`, 4.6 to 1, on Campbell. On a light background the base colour already reaches 5.2 to 1 and is used as it is. When the background cannot be determined, the dark-background tint is used. At 256 colours the tint is the palette's colour nearest to it among those that reach 4.5 to 1 and keep the accent's hue (index 99 on Campbell, 93 on One Half Light): the purple's darker neighbours in the palette are blue.

| Token | Default | Used for |
|---|---|---|
| `text` | default foreground | Answers, and the answer's `◇`. |
| `muted` | bright black | Reasoning (italic), tool detail, notices, hints, line numbers, box borders and rules. |
| `accent` | the logo purple, as above | The marks listed above. |
| `accent.text` | a tint of the accent, as above | Accent-coloured text. |
| `user` | the accent | Your `◆`. Your message itself is bold, in the default colour. |
| `title` | bold default foreground | A tool call's imperative, a dialog's question. |
| `code` | bright cyan on a dark background; cyan and bold on a light one | Inline code. Bright cyan is 11.3 to 1 on Campbell. Cyan is 3.3 to 1 on One Half Light, under the target for text, so it is bold there. |
| `heading` | bold default foreground | Headings. |
| `success` | bright green on a dark background; green and bold on a light one | `✓`, an edit's `+` count (`+5`). |
| `warning` | bright yellow on a dark background; yellow and bold on a light one | `?`, warnings, the context from 70%. |
| `error` | bright red on a dark background; red and bold on a light one | `✗`, errors, a failure's measure, an edit's `−` count (`−1`), the context from 90%. |
| `diff.add`, `diff.del` | bright green and bright red on a dark background; green and red on a light one, the signs bold | The sign of an added or removed line, and the whole line where there is no background colour. |
| `diff.add.bg`, `diff.del.bg` | in true colour, 20% of green (`#2EA043`) or red (`#E03E3E`) mixed into the background the terminal reported on a dark one, 13% on a light one; none otherwise, and none when the terminal did not report its background | The tint of an added or removed line. The text on it keeps the default foreground: 9.1 to 10.2 to 1 on the two sample schemes. |
| `diff.emph` | bold | Changed words inside a changed line. |

- **The bright colours on a dark background.** The default theme takes success, warnings, errors and the diff signs from the bright half of the terminal's palette on a dark background, and from the normal half on a light one: Campbell's red is 3.2 to 1 on its background, and its bright red 5.1.
- **Status text in red, green or yellow is bold on a light background** (the owner's decision of 2026-11-15, [decision 0033](../decisions/0033-tui-look.md)'s amendment), as inline code is: on One Half Light, red is 3.5 to 1, green 3.1 and yellow 3.1, under the 4.5 to 1 target for text. That is success, warnings, errors and a failure's measure, and a diff's signs. **Highlighted code (strings in green, numbers in yellow) and a whole changed line drawn in its colour where there is no tint keep their weight, and stay under the target on a light scheme, by the owner's choice:** bold everywhere would make code and untinted diffs heavy. One flag of the palette (`warm_bold_code_and_lines`, off) would reach them. The tints behind a changed line are backgrounds, and its text keeps the default foreground. On a dark background the bright colours reach the target, and nothing changes there.
- **The syntax colours.** Keywords are bright blue on a dark background (5.0 to 1 on Campbell; bright magenta, used before the owner's decision of 2026-11-15, was 3.2) and magenta on a light one (5.9 to 1 on One Half Light); types are bright cyan and cyan, strings bright green and green, numbers bright yellow and yellow, comments `muted`. A background the terminal did not report is taken as dark.
- **Muted stays as it is.** Bright black, the `muted` token, is 4.3 to 1 on Campbell, under the target: it is quiet on purpose (reasoning, notices, tool detail and hints), and the marks beside it carry the meaning. The owner kept it on 2026-11-15.
- **Elements are tokens too.** Each element is drawn in one of the tokens above, or in one with an attribute: a box's border is `muted`, a key in a dialog is `accent.text` and bold, an added line's sign is `diff.add` on `diff.add.bg`. `cineris_tui::theme::Token` lists them, and the theme alone decides how each looks at each depth and on each background, so no view holds a rule for 16 colours or for none.
- **Blue on a dark background.** Plain blue is not used for text there: Campbell's blue (`#0037DA`) is 2.4 to 1 on its background, and its bright blue 5.0 to 1. A theme that wants blue on a dark background uses bright blue.
- **Themes** are TOML tables that assign a colour to each token: an ANSI colour name, a 256-colour index or a hex value. `tui.theme` selects a built-in or user theme.
- **Without colour.** `NO_COLOR` and `--no-color` turn colour off. Meaning is never carried by colour alone: every state has a glyph or a word, diff lines keep their sign, removed lines are dim, and your `◆`, the answer's `◇`, the answer keys and the selection are bold.
- **Colour depth** is detected, and hex values are reduced when the terminal cannot show them.

**Glyphs.** `tui.glyphs = "auto"` uses the Unicode set when the locale is UTF-8, and the ASCII set otherwise (and on the old console host).

Width is computed per grapheme, and characters of East Asian ambiguous width are counted narrow, as terminals draw them outside CJK locales. Fifteen glyphs of the Unicode set are ambiguous (`◆ ◇ ∴ ■ · ╭ ╮ ╰ ╯ ─ │ – … → ×`); a terminal set to draw them wide would widen every box row, and the ASCII set avoids them (left so by the owner on 2026-11-15, with `tui.glyphs = "ascii"` for such a terminal: [steps/23/answered.md](../steps/23/answered.md)). Whether each Unicode glyph is in Windows Terminal's default font is checked by eye with the reference screens in [tui-look/](tui-look/README.md).

**Density.** `tui.density = "comfortable"` (default) puts a blank line between blocks. `"compact"` puts one only between turns, and shows reasoning as its first line alone.

## Input

### The editor

A multi-line text editor of our own. A text-area crate was considered and not used: paste handling, attachments, completion menus and wrapping in a growing region are most of the work and are specific to this UI.

- **Text model.** UTF-8 with cursor movement, deletion and wrapping by grapheme cluster.
- **Movement and editing.** Characters, words, line ends, buffer ends. Delete word and line. One kill-and-yank slot. Undo and redo with typing grouped into words.
- **History.** Up and Down on the first and last line step through earlier prompts for this project. `Ctrl+R` searches them.
- **Paste.** Bracketed paste is enabled, so pasted text is inserted as text and never interpreted as keys. A paste of more than 12 lines or 2,000 characters is shown as a chip (`[pasted 148 lines]`) and expanded when the prompt is sent. `Ctrl+X` expands it in place.
- **Files.** Typing `@` opens file completion over the workspace, with fuzzy matching and the ignore rules. An accepted path is inserted as a token and sent as a reference the agent can read.
- **Commands.** `/` at the start of the prompt opens the command menu.
- **External editor.** `Ctrl+G` opens the prompt in `$EDITOR` and reads it back.
- **While a turn is running** the editor stays usable. `Enter` sends the text to the running turn (steer). `Tab` on an empty completion context switches the pending message between "steer" and "queue", shown on the hint row. See [03-agent-loop.md](03-agent-loop.md).

**The text model.**
- Every position is a grapheme cluster boundary, found by reading only the line it is in. A movement or a deletion takes a whole cluster, and an edit that joins two clusters (two halves of a flag, a combining mark pasted after a letter) leaves the cursor after the cluster it made.
- A chip is one U+FFFC in the text, with the chips kept in a list in the order of their marks. A chip's mark is a cluster of its own, so an accent typed after a chip never takes the chip with it. A U+FFFC that arrives as text becomes a chip that holds that character, so none is lost.
- Line breaks are `\n`: `\r\n` and a lone `\r` are taken as one. A tab is kept and drawn four columns wide. Other control characters are kept, and drawn as visible symbols by the renderer.
- Rows break after the last white space that fits, or between clusters when a word is wider than the row, and keep every byte, so the cursor has a place everywhere. The cursor after a full row that ends a line sits one column past the text: the input box keeps that column for it, and no row reaches the box's edge.
- Undo: characters typed one after another are one step until a word begins after something that is not a word (`fix the bug` undoes as `bug`, `the `, `fix `); deletes one at a time likewise. A paste, a yank, a kill, a completion, a line break, a history entry and the external editor's result are each a step of their own. A thousand steps are kept.
- The kill slot: `Ctrl+W`, `Ctrl+K`, `Ctrl+U` and `Alt+D` put what they delete in it, and kills one after another join in it in the text's order, whichever way each went (`Ctrl+U` then `Ctrl+K` gives the whole line back); anything else in between starts it again.

**Keys.** Each action belongs to one context: `editor`, `menu`, `picker`, `toggle`, `search`, `focus`, `dialog` (since step 23: an approval's answers, `y`, `s`, `a`, `n` and `Esc`, `e`, and `Ctrl+O`), `fork` (since step 25: `Tab` in the pickers that fork, above `picker`, as `toggle` is for `/effort`'s), or `global`, which is looked up last whatever has the keyboard. A menu is looked up before the editor under it; a picker's filter takes typed text, so the editor is not under it; the `/effort` picker with its fast-mode row is `toggle`, `picker`, `menu`, so there `Tab` toggles and only `Enter` accepts. A key bound to nothing that types a character is typed. `Ctrl` or `Alt` with an upper-case letter is read as `Shift` with the lower-case one, as some terminals report it. In `[keys]` an action is named by its context and its own name, `editor.new_line = ["shift+enter", "alt+enter", "ctrl+j"]`, and the list replaces the action's defaults (an empty list unbinds it); a key given to an action is taken from any other action of the same context, and a key given to a global action from every context (so `global.suspend = ["ctrl+z"]` takes `Ctrl+Z` from undo, whatever else the table lists). An entry that cannot be used is reported and the action keeps its defaults.

**Plain input merges two bindings.** Every default binding is tested through the terminal layer's decoder as plain virtual-terminal input, as win32 input records and, for the keys with modifiers, as the enhanced keyboard protocol. Plain input sends `Shift+Enter` as `Enter` (send) and `Ctrl+Shift+Z` as `Ctrl+Z` (undo); `Alt+Enter`, `Ctrl+J` and `Alt+Z` arrive as themselves everywhere. Win32 input records carry `Ctrl+/` and `Ctrl+_` as a layout's control code or nothing, so those two undo keys are not reached there; `Ctrl+Z` is.

**History.** `Up` on the editor's first row (by row, as wrapped) shows the prompt before, with the cursor at its start, so the next `Up` goes on; `Down` on the last row shows the next with the cursor at its end, and past the newest what was being typed. An entry edited and stepped away from keeps its edit until a prompt is sent. `Ctrl+R` finds the newest prompt that holds the search, ignoring case; `Ctrl+R` or `Up` again finds the one before, `Down` the one after, `Enter` takes it into the editor as one step of undo, and `Esc` (or `Ctrl+G`) leaves the editor as it was. A search with no match takes nothing. A prompt sent is pushed to the store as it was written, its chips chips, within history's bounds (since the follow-ups of step 23; it was pushed expanded), once, and not when it is the same as the newest.

**Completion.** `@` at the start of the prompt or after white space opens file completion; accepting puts `@path ` in place of what was typed, with the path in quotes when it holds white space. `/` at the start of the prompt opens the command menu; accepting puts `/name `. The best 64 matches are kept, 8 are shown, and the menu scrolls to keep the selected row in view and wraps at either end. As the filter changes the best match is selected. A menu with no row says why: nothing matches, or the paths have not been listed yet. `Esc` closes it until the text asks again somewhere else.

**The matcher** is our own (`complete::fuzzy`): the query's characters in order, ignoring case, scored for characters at the start of a part of a path, characters one after another, a match inside the file's own name, and a shorter path. ASCII paths are matched byte by byte with no allocation, and a query that extends the last one looks only at the last one's matches. On 100,000 generated paths it takes 1.2 ms a keystroke at the median and 4.0 ms at worst, optimised, on the reference machine ([../performance-budgets.md](../performance-budgets.md)).

**Steering and queueing.** While a turn runs, `Enter` sends the prompt to it (`Outcome::Submit` with `Delivery::Steer`), and `Tab` with nothing to complete switches between steering and queueing (`Delivery::Queue`). When the turn ends the input goes back to steering.

**`Ctrl+C`.** A turn running: interrupt it. A picker open: close it (`Outcome::PickerClosed`), keeping the text. Idle with text: clear it, as one step of undo. Idle and empty: the first press arms quitting (`Outcome::QuitArmed`, which the hint row shows), and a second press quits; any other key disarms it.

**The focus ring.** `Ctrl+P` moves along the input, each live tool box in the order drawn, each panel, then the input again. The caller says what is there with `Ring::update(boxes, panels)` whenever it changes; a target that goes away gives the focus back to the input. A new kind of target is its ids passed to `update`; the ring does not change. With a box or panel focused, `Enter`, `Esc`, `Up` and `Down` are the `focus` context's.

**The external editor.**
- **Which.** `$VISUAL`, then `$EDITOR`, then `vi` and `nano` on Linux, and Notepad by its absolute path in `%SystemRoot%\System32` on Windows. A value that is the absolute path of a program is taken whole, spaces and all; otherwise it is split into words without a shell, as a POSIX shell splits them on Linux and as a Windows program splits its command line on Windows (the program word as it is, then the usual quote and backslash rules), on spaces and tabs only. The program is an absolute path, or a name found by `cineris_base::program::find_outside` in the absolute folders of `PATH`, never inside the session's write roots, where a command could have put one (`external::Env::avoid`); a relative path is refused. On Windows a name with no extension is looked for as `.exe`, `.com`, `.cmd` and `.bat`, folder by folder, never as the file with no extension, and an absolute path with no extension is the first of those beside it.
- **The file.** `prompt.md` in a new folder of the system's temporary folder, both private to the user (`cineris_base::private`); the editor runs in that folder, not the workspace. A chip goes into the file as its label (with `#2` added when two have the same) and comes back as the chip where its label is still whole. The folder is removed afterwards, except when the editor left text that is not UTF-8: then it is kept, and the error names the file.
- **The terminal.** `TerminalHandoff` erases the live region and leaves the terminal, so the editor has the modes the user's shell had (on Windows the console's modes and code pages too); after the editor it enters the terminal again, turns off what a killed full-screen editor may have left on (the alternate screen, mouse reporting, application keys, keyboard flags), and the presenter draws afresh where the cursor is. The terminal is taken back whatever the editor did. From before the terminal is left to after it is taken back, the interrupt keys do nothing to the interface (`cineris_term::ignore_interrupts`; the editor keeps its own), so a `Ctrl+C` meant for the editor, or typed as it ends, ends at most the editor.
- **What comes back.** The file's text with `\r\n` as `\n`, a byte-order mark and the one line break an editor adds at the end taken off. An editor that could not start, failed, or was killed leaves the prompt as it was, with an error that says which. A file left empty also leaves the prompt as it was (emptying the prompt is `Ctrl+C`), and so does one left unchanged. A change replaces the prompt as one step of undo.

### Rewind and fork

Built in step 25 ([steps/25/answered.md](../steps/25/answered.md), point 4; [steps/25/parts/pr2-rewind.md](../steps/25/parts/pr2-rewind.md)). Every step is an operation through the application's `Link`, so `cineris attach` rewinds and forks as the in-process interface does, and the question about files edited since is the core's `question/ask`, which an attached interface answers.

- **The points.** `/rewind` reads the active branch with `session/read` (a read beside the lane), page by page, and opens a picker over the earlier prompts, newest first: `turn 12  14:32  fix the lexer so digit separators…`, the turn counted along the branch, the time of day local, the prompt on one line, sanitised and cut at the row. Each prompt that began a turn is a point; a steering message is not, and nor is the first prompt (going back before it is `/new`). The application keeps the points, the row's text and the prompt's id each, only while the picker is open. While a turn runs, `/rewind` says to wait for it or stop it, and reads nothing.
- **The plan, then the question.** A point chosen asks the core for its plan (`session/rewind_plan` with `before` the prompt's item: the state before the prompt's turn, as `/undo` has it, which keeps what the log holds between the turn before and that turn; since the review of step 25's second pull request, which found that the item before the prompt took the turn before's last checkpoint with it, and before the turn's first entry rather than the prompt's own since the review of that review's fixes) and reads the prompt whole, its own item and no other (a page of an earlier rewind's read, given up, does not take away the one read: since the review of the fixes of step 25's second pull request). The question takes the input box's place, a dialog of the application's own with the approval dialog's rules of keys (readiness, no repeat, no paste), and one more: **until it first takes keys, every key and paste is its own and answers nothing** (since the same review), for nothing typed then is on its way to the editor it hides, and what reached the editor would come back in front of the prompt given back, for an `Enter` to send; they hold its quiet, as typing does, and once it has taken keys a draft typed at it goes to the editor as at any dialog. It shows `? Rewind to before turn 12?`, the prompt's first line, how many turns the plan undoes (the core's count, which its mark holds: a turn run since the points were read is in it), and each file of the plan with what happens to it (goes back to what it was, is removed, was changed since and is asked about, stays as it is and why, is already as it was; for a status or a target this build does not know, that what happens cannot be told, whatever the other says). `1 Rewind it and put back the files listed`, `2 Rewind the conversation only; the files stay as they are`, by their digits; `Esc` cancels and sends nothing; nothing is preselected and `Enter` chooses nothing. **`1` is offered only once every file of the plan was drawn whole**, by the rule of a lasting answer: a list cut to the window says so, and `1` comes once every row of it was drawn in the viewer (`ctrl+o shows it whole`).
- **What is sent.** `1` sends `session/rewind` with `before` the prompt's item and `restore_files: true`, `2` with `false`, each with the plan's `mark`: a plan that moved since it was shown (a turn ran, a file was edited, another client edited the plan) is the core's to refuse (`plan_changed`), and the refusal is said with what to do (`/rewind` again). A file edited since is then the core's own question, which keeps it unless the person says to put it back. **A prompt sent from the answer on waits** for the rewind and for the read after it (since the review of step 25's second pull request: its events could come before the rewind's result, and be drawn and then read again); a rewind refused gives it back into the editor, as it was meant for the conversation rewound, and `Ctrl+C` gives back every prompt that waits and says so. Giving prompts back stops the spinner only when no turn runs, and `Ctrl+C` then interrupts a turn that runs (another client's, begun meanwhile), so that `Esc` and `Ctrl+C` still stop it (since the review of the fixes of step 25's second pull request, which found the input shown idle and `Ctrl+C` interrupting nothing).
- **After it.** The prompt of the turn rewound to goes back into the editor, after what was being written there. Inline, the scrollback cannot be taken back: a notice says `Rewound to before turn 12. The conversation goes on from there; what is above this line is no longer part of it.` The transcript the viewer and the full screen draw is read again from the active branch (`session/read`) and drawn from it, the turns undone gone; there the notice says `Rewound to before turn 12. The conversation goes on from there.` An item whose events came while it is read is drawn from them and not again from the read, and one the read says is in progress is left to its events. `/copy` then copies the branch's last answer, not the one undone (since the same review), unless an item came from events meanwhile. A prompt sent while it is read waits for the read, and then goes as `Enter` would have sent it, and goes too when the read fails, which is said: the history did change. `/new`, a switch, `/undo`, `/rewind` and a fork wait for it too, and a second `/undo` waits for the first; a switch and a fork from `/sessions` wait for a rewind still being chosen or asked about as well. A turn that ends under the question (another client's) closes it, and nothing is rewound. **`/undo`**'s result is drawn the same way: its notice, and the transcript read again; and a prompt sent between `/undo` and its result waits for it and for the read after it, as one sent after a rewind's answer does, and comes back into the editor when the undo fails (since the review of the fixes of step 25's second pull request).
- **Fork.** `Tab` in the `/rewind` picker forks from before the point (`session/fork` with `before` the prompt's item; a result that does not give `before` back is a fork of all of the session, by a core that does not know the field, and what is said says that, not that it forked from before the turn: since the review of the fixes of step 25's second pull request), and in `/sessions` forks the selected session at its end (the session open here directly; another is opened for it first, as `--fork` does). The fork is opened in this one's place, under its own header with its history, and the session it came from is closed here and kept as it was. Each picker's last row says it (`tab - fork from here`, `tab - fork it`), as `/effort`'s toggle row does. The key is the action `fork.fork`, in a key-map context of its own (`fork`, looked up before `picker` in the pickers that fork, so that there only `Enter` accepts); `[keys]` names it there. A fork of the session open here that fails leaves it open as it was, and the prompts sent while it was asked for, which were meant for the fork, come back into the editor (since the review of step 25's second pull request: they went to the session that stayed, the first as a new turn); a turn that began meanwhile (another client's) still runs there, and `Esc` stops it (since the review of its fixes). A fork of another session from `/sessions` closes the one open here first, as a switch does, so one that fails leaves no session open, closes the other (opened for it), and says why; `/sessions` or `/new` goes on from there.
- **A fork's place in `/sessions`:** in the list's order, its note saying whose fork it is: `fork of "fix the lexer…"`, the parent's title cut at a word, or `fork of s_4f2a…` when the parent is not in the list (`session/list`'s `parent`).

### Exporting a session

Built in step 25. `/export` writes the session to a file: Markdown to read, or JSON with the items as the protocol has them. Nothing of it is in-process, so `cineris attach` exports the same way.

- **What is read is masked twice.** The application reads every page of the session with `session/read`'s `redacted` ([11-rpc-protocol.md](11-rpc-protocol.md)): the core masks each item with the filter its log's writer has, the harness's credentials by their values (which a client over the wire never has) and every well-known key format, by the same walk (`cineris_session::redact::for_export`, so the two can never mask different sets); drops every provider block (`raw`), which the log keeps unmasked to replay; makes an assistant message its neutral projection; leaves out what is still running, and says so; does the same for a session kept only in memory (`--no-session`); and says in its result that it masked (`redacted`). **A page whose result does not say so is refused, and nothing is written:** a core that does not know the field (an older one) reads the items as they are, and the person is told so. Then the client's stricter pass (`cineris_tui::export`) runs every string of every item, and every key of every object, through `cineris_base::SecretFilter`'s formats again before anything is serialised, the title with them, so a key JSON's escapes would cut is still found; a key that holds a secret is renamed to what the filter makes of it (`[redacted]`, then `[redacted] 2` and so on when that name is taken). It drops the provider's blocks again too: every `raw` field outside the JSON that is somebody else's (a tool call's `arguments`, a tool result's `payload`, an error's `details`), and every `provider_block` part. It masks the same formats the core's filter does; what makes it stricter is the keys, the provider's blocks, and the Markdown's own pass below.
- **An export belongs to the session it was asked in.** The title written is the one the session had when `/export` was asked for, and an export still being read when the session is left (`/new`, a switch, a fork) ends, writes nothing and says so; one being written goes on (since the review of the fixes of step 25's second pull request: the last page took the title and the turn of whatever was open when it came).
- **The count is of the masks the export holds,** as the core counts its own: each mask in its items' strings and keys and in its title, and, in Markdown, each the last pass adds. A pass that changes nothing adds nothing (an address whose password is masked already is left alone by the filter). What is said after names the file and that count, one number (`3 values were masked`), not one for each kind: the masks the log wrote say nothing of what they took the place of.
- **What is written is safe to read.** In Markdown, control characters are left out and what acts unseen is escaped, as `/copy`'s text is (`export::readable`, which `/copy` shares); the text of each block as it is shown goes through the filter once more, since leaving a control character out, or joining the parts of a message, can make one key of two halves that no string held whole; each block of output is fenced with more backticks than any run in it; the title is escaped so that it stays one heading; and a tool's name is put on one line, with no backtick, inside its code span. **What it does not neutralise:** the text of a prompt, an answer, its reasoning, a notice or a summary is written as it is, to be read as Markdown, so its headings, emphasis, links, tables and HTML are its own, and a viewer that renders HTML or fetches images renders and fetches them. A JSON export is the items as the protocol has them, with nothing to neutralise.
- **The file is the program's to write,** on a thread of its own that wakes the loop (`Start::export`, an `export::Writer`), which also makes the client's pass and the text, so the interface's thread neither masks, renders nor waits on the disk. The text is written whole, and flushed, to a new file private to the user (`cineris_base::private`) under a name of its own in the same folder (`.cineris-export-….tmp`), then given the file's name by a hard link, which never replaces a file that exists (that one is named and left as it was) and never follows a link; the name of its own is then removed. So `/export` then `/quit` leaves no file cut short under the name: a write that fails removes what it wrote, and only a process that ends in the middle can leave the name of its own behind. Where the file system has no hard links (FAT, some network shares) the file is created new under its name and written there: never over one that exists, though a process that ends in the middle can leave it cut short. The default name is `cineris-session-<date>-<the session's first eight characters>.md` (or `.json`) in the folder the person started in, with `-2`, `-3` and so on for another the same day; a path given is taken from that folder. **On Windows** a device's name (`CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9`, `LPT0` to `LPT9`, and `COM` or `LPT` with a superscript `¹`, `²` or `³`, in any case and with any ending; the zeros and the superscripts since the review of the fixes of step 25's second pull request) and a `:` after the drive, which names a stream inside a file (`notes.txt:x.md`), are refused and nothing is written; elsewhere they are ordinary names.

### The first run

Built in step 25 ([08-configuration.md](08-configuration.md), "First run", says what it chooses and writes; screens F1a to F4 in [tui-look/](tui-look/README.md) are its golden screens). It runs when the program gives the application a `app::Setup`, which `cineris` does at a terminal when the user's configuration file does not exist, and `cineris attach` never does.

- **Each step takes the input box's place, as a dialog does,** under the set-up card: the program and its version and what is about to happen, in the live region until the session opens and never committed, so that once the session is open its header is the one card. A step is its title and count (`◇ Mode  3 of 4`), a sentence at the prose width, its rows (a mark, a label and what it means, wrapped, and never cut but in a window too small for one, below), and its keys in the hint row. A step answered commits one dim line of what it did (`· Provider: anthropic, its key from ANTHROPIC_API_KEY.`), so the steps already taken stay above the one being asked. The views are `view::setup` (`card`, `step`, `fitted`); every label and text from outside passes through `sanitize`.
- **A step is shown only when nothing else has the input box's place** (since the full review of the third pull request, `App::first_run_shown`): never under a dialog or the viewer, and a step not shown takes no key: the keys go where they would without it. **The last step**, which comes once the session is open, is asked for (`project/detect`) and shown only while the session is idle (`App::first_run_idle`): no turn running and no prompt on its way, no dialog, not under the viewer, the full screen's search or a rewind, no panel's item being edited, and the input box empty with no menu open. **Until then the input box is the input box:** a prompt typed is sent as any prompt is, and the command line's prompt (`cineris "fix the build"`) goes at the open; the step comes once its turn has ended and the input box is empty. A turn or a dialog that comes while the step is shown hides it, and it comes back as if new.
- **A step fits the window** (since the same review, `view::setup::fitted`): when the card and the step are taller than the window, the card goes first; then the step's rows are a window around the selected one, which is drawn whole, a dim row (`… 3 more above`, `… 2 more below`) in the place of the rest; the step's note, the blank above its rows and its sentence give way, in that order, only when the selected row would not fit beside them, and its title never does. A selected row taller than the window is cut, the hint row says `a taller window shows this row whole`, and `enter` or `space` on it does nothing: a provider, a mode, a server or a command is accepted only once it has been drawn whole.
- **The rule of keys is the dialog's** (`app::ready::Readiness`): a step shows its keys, and takes one, only 300 ms after its first frame, a second after input it did not take, and a key's repeat window after the key that answered the step before; a repeat, keys read together and a paste never answer one. Its keys appear at the end of its grace, when the loop is due to draw (`App::deadline`). *Since the full review of the third pull request:* a step is seeded on its first frame as a dialog is, with the input nothing took just before it and the key that answered what came before it, a dialog's included; a key a step takes holds the dialog after it the same way (the session's trust question after the mode's `enter`); rows that the worker's answer changes under a step (the providers, what other tools left, a file's servers) start its grace again, keeping its quiet; and the imports' selection is the row it is, not its place, so a file's servers that come while another row is selected do not move it. `s` skips a step, `x` the whole set-up; `Ctrl+C` twice leaves, `Ctrl+L` and `Ctrl+Z` do what they do anywhere; nothing else reaches the editor while a step is shown.
- **The key's input is not the editor** (`cineris_tui::secret`): a `cineris_base::SecretBuf` of 64 KiB, which never moves and is written over with zeros when a character is taken away, when it is emptied and when it is dropped. It answers typing, a paste, `Backspace`, `Ctrl+U` (which empties it), `Enter` and `Esc`; typing and a paste go in whenever the step is shown (typing into it is not an answer), and `Enter` waits for its keys. Its row is a rounded box holding `◆` and how many characters it has (`108 characters, hidden`), never one of them. A paste with a line break, or past the capacity, is refused whole with a sentence. `Enter` hands the key, trimmed, to the program's store as a `Secret`; where the store is Windows Credential Manager a key that is not printable ASCII is refused first. `cineris auth login` at a terminal uses the same input (`secret::read_key`), inline, and puts the terminal back whatever happens.
- **Nothing of it runs on the interface's thread.** `Setup`'s calls go to a worker of their own (`app::setup::Worker`), one at a time in the order asked, which wakes the loop when it answers; a step says `reading…` meanwhile. The steps that are a session's go through the `Link`: `config/reload` once the file is written, the session's open (and its own trust question, screen 2c), `project/detect` for the commands, and `project/update`'s `add` for those picked.
- **The test kit** has the program's stand-in (`testkit::FakeSetup`, and `app_first_run`), which the application's tests and the golden screens drive the steps with.

## Terminal layer (`cineris-term`)

- **No terminal library** ([decision 0002](../decisions/0002-tui-rendering.md), "Amended in step 20"). Raw mode, the window's size, waiting for input and the handlers that put the terminal back are a module for each system (`sys::unix` on `libc`, `sys::windows` on `windows-sys`), the only `unsafe` code in the crate, behind a small trait (`Device`) so that they can be replaced and so that the layer's own logic is tested without a terminal. Input is decoded by our own decoder, the same on both systems. Output is written by our renderer, one write a frame.
- **Start-up.** The first frame is drawn at once with conservative assumptions. Capability queries go out just before it, when the terminal is entered, and their replies upgrade behaviour in later frames. Start-up never waits for a terminal to answer.
- **Capabilities, each detected and each with an override in `[terminal]`:**

| Capability | Detection | Fallback |
|---|---|---|
| Synchronized updates | Mode report query. | Emit anyway unless the terminal is on a small deny-list; terminals ignore private modes they do not know. |
| Enhanced keyboard reporting | Protocol query. | `Alt+Enter` and `Ctrl+J` for new lines. |
| Colour depth | Environment variables. | 16 colours. |
| Hyperlinks | Known-terminal list; only for a web address. | Plain text with the URL. |
| Clipboard through the terminal | Cannot be told: a terminal does not answer the clipboard sequence (OSC 52), so `/copy` says it sent the text, never that the clipboard has it. Since step 25 it is guessed: not the old console host, tmux (whose default passes no program's sequence on) or GNU screen; `terminal.clipboard` says otherwise. | Where it is thought not taken, `/copy` still sends it, and opens the answer in the viewer too with the mouse not reported, so that a plain drag is the terminal's own selection. |
| Bracketed paste, focus events | Requested; harmless when unsupported. Since step 25 bracketed paste is asked about (DECRQM 2004) with the other queries; a terminal that says the mode is set (1 or 3) is trusted to bracket its pastes. The query follows the start's `CSI ? 2004 h` in one write, so a terminal that answers reset (2 or 4) will not bracket, and is weighed as one that does not know the mode (since the review of step 25's second pull request). `terminal.bracketed_paste = true` trusts the brackets everywhere; `false` asks for none. | Where the terminal has not said bracketed paste is set, keys that come many in one read with a line break that is not the last, or more than 64 with no line break at all, are a paste, and the keys that come within the next 50 ms of waiting for input its rest: a pasted line break never sends the prompt (`Terminal::pastes`). *Since the review of step 25's second pull request:* a line break is `Enter`, a line feed (read as `Ctrl+J`), or the two together (`\r\n`), which are one, and since the review of that review's fixes also when they are cut between two reads of the paste (the paste's last key an `Enter`, the next read's first a line feed); a focus report, a reply or the mouse in the same read is passed on beside the paste; a read whose only line break is its last key is keys however long it is, so that a line typed through a stall, or sent by `tmux send-keys`, sends; only the time spent waiting for input counts towards the 50 ms, so that a frame drawn between two reads of one paste does not end it; and on Windows one wait reads every console record waiting, up to the 4,096 bytes one read takes on Unix, so that a paste comes in one read rather than 64 records at a time. The eight keys and the 50 ms have not been measured. A bracketed paste given up on after `terminal.paste_wait` (2 s) with no end marker is given as a paste, and what follows of it to its end marker is its rest; a lone key after the give-up is a key, and so is what comes after more than the wait with no input. |
| Unicode | Locale. | ASCII glyphs. |

- **Restoring the terminal.** Raw mode, cursor visibility, keyboard mode, paste mode and the alternate screen are restored on normal exit, on a panic, and on termination signals.
- **Suspend and resume** (the `global.suspend` action, which has no key by default; `Ctrl+Z` is undo) restore the terminal on suspend; on resume, raw mode, bracketed paste, focus events, automatic wrap off and whichever keyboard protocol was on come back, and the live region is drawn again from where the cursor is.
- **After the terminal has been put back in an emergency** (a panic on another thread, a signal), the layer writes nothing more: a frame would turn modes on again in a terminal that is no longer the program's. The program's next write fails, and it should end. The signal handlers replace whatever was installed for those signals before.
- **A signal handed to the program** (since step 23, `Terminal::hand_signals_over`, which the interactive application calls): SIGTERM, SIGHUP, SIGINT and SIGQUIT, and on Windows `Ctrl+Break`, `Ctrl+C` as a console event and the console's close, log-off and shutdown, still put the terminal back at once; then, instead of ending the process, the handler records the exit code the signal's own end would give (143, 129, 130, 131), arms a watchdog and wakes the loop. The watchdog is `alarm(3)` on Unix, whose default action ends the process; on Windows the handler's thread waits up to 3 s for `signal_ended`, since Windows ends the process when the handler returns from a close. A second signal ends the process at once. *Since the review of step 23:* **the terminal going away under a read** (the window or tab closed, an SSH connection dropped: end of input or EIO on Unix, a failed console read on Windows) is SIGHUP's end, code 129, with the same watchdog, since the reader sees it before, or instead of, the hang-up's signal. A SIGHUP after a SIGHUP handed over, or after the terminal went away under a read, is that same end and not a second signal, also when the program was already ending for another signal when the terminal went (a SIGTERM's end, then the window closed: it ends as 143, its end not cut short), while a second signal a person sends (another SIGTERM, `Ctrl+C`) still ends it at once: the kernel and shells send it more than once (to the session's leader, then to its jobs), in either order with the reader's end of input, and on another thread than the reader's: the handler asks whether it is that end once it finds the hand-over taken, so a read that takes the hand-over while the handler puts the terminal back does not make the SIGHUP a second signal (since the third pull request of the review's fixes, which found it killing the process before its end). **The handlers stay installed after the terminal is left,** until `signal_ended`: a signal while the program ends (its history, its core) or while the external editor has the terminal is still handed over, not the default action's. `signalled()` asks for a signal once the terminal is left. **The restore erases the whole live region:** each frame tells the layer how many of the region's rows are above the cursor (`Sink::region`), and the restore moves up that many before it erases. On Windows a frame being written finishes before the restore (a lock the console handler's thread waits on for at most 250 ms), so none lands after it. The application stops a running turn at once (`turn/interrupt` with `now`), ends the core within 1.5 s (the history's last prompts having had at most 1 s, so that the whole end fits the watchdog), and exits with the code (`Exit::Signal`). SIGABRT is not handed over: the terminal is put back and the abort ends the process by its default action.
- **Automatic wrap is off while the program runs.** A character the terminal draws wider than it is counted (an emoji sequence, an ambiguous-width character in a CJK locale) cannot then push a row onto the next and throw the presenter's count of rows out; at worst the row is cut short by the terminal.
- **Sanitising.** All text from models, tools and files passes through one function (`cineris_term::sanitize`) that makes visible every control character except newline and tab, and, since step 23, writes as an escape (`\u{202e}`) every other character that acts unseen by `cineris_base::visible`'s rule: the bidirectional controls, the characters of no width, the tag characters, the line and paragraph separators. Text is escaped once, as it is drawn, and stays exact as data (the rules an approval would add, a path put in the prompt). The zero-width joiner and non-joiner are kept, by the owner's choice of 2026-11-15: they join emoji sequences and shape Persian and the Indic scripts ([steps/23/answered.md](../steps/23/answered.md)). Only the renderer emits control sequences, and it shows every control character that reaches it in a line, newline and tab included, as a symbol one column wide: C0 characters as their Control Pictures (`␛`), DEL as `␡`, and C1 characters (`U+0080` to `U+009F`, which some terminals obey like `ESC [`) as `�`. A link's address is used only when it is a web address (`http`, `https`) in printable ASCII. **Since the review of step 23:** what a component makes of content after sanitising it is sanitised too (the character a markdown entity such as `&#x202E;` stands for); text that arrives in pieces is sanitised piece by piece as the whole would be (`cineris_term::sanitize::sanitize_after`, given the character before the piece, so that an emoji's variation selector in the next piece is kept); the prompt editor lays a character out in the columns of what is drawn for it, its escape included (since step 25 a run of four or more escapes inside one cluster is one mark in its row: of one character its escape, `×` and the count, `\u{e0041}×12`; of several, the first's escape, `+` and how many more follow, `\u{e0068}+11`; `x` for `×` in the ASCII glyphs, as wide; everywhere else every escape is shown); and `/copy` drops control characters but line feeds and tabs and escapes what acts unseen before the text leaves for the clipboard.

What steps 21 to 25 build on. Its public items are documented in the crate.

**What the design round must respect.** The presenter draws rows of styled text, one row a line, and nothing else: no cell is addressed on its own, no region scrolls, and nothing above the live region can change once committed. What is cheap: a live region of a few rows, rewritten every frame; changing one row (only the changed rows are written when nothing was committed and the height is the same); colour, the five attributes and links on any span. What costs more: a tall live region (30 rows measured at 0.14 to 0.5 ms a frame and about 4 KB, the size at which a frame no longer fits one read of a pseudo-terminal), and anything that changes the region's height every frame, which redraws all of it. What it cannot do: draw in the last column, re-wrap or restyle anything already committed, place things side by side except as text laid out in a row, or keep a region taller than the screen.

### Windows

| Topic | Handling |
|---|---|
| Console set-up | UTF-8 code pages, virtual-terminal processing for output, and virtual-terminal input are turned on at start; line input, echo and Ctrl+C as a signal are turned off. The modes and code pages found are put back on a normal exit, a panic and a console control event (Ctrl+Break, closing the window, logging off, shutting down). A console that refuses virtual-terminal processing, as consoles before Windows 10 do, is refused with a message. |
| Key events | With virtual-terminal input, keys arrive as the same sequences a Linux terminal sends, and one decoder reads both. Key releases are not reported in that mode; a release that the enhanced keyboard protocol reports is dropped. A repeat it marks (its event types, asked for since the review of step 23), or a win32 input record of a key going down again before it went up, is `Event::Repeat`: it types as the key does, and a dialog never takes it as its answer. What the mode cannot tell apart is in the next row. |
| Keys the mode merges | Plain virtual-terminal input cannot tell `Shift+Enter` from `Enter`, `Ctrl+Enter` from `Ctrl+J`, `Ctrl+Tab` from `Tab`, or `Ctrl+Shift` with a letter from `Ctrl` with it, and a lone `Esc` waits 50 ms for the rest of a sequence before it is the Escape key. Two things win them back: the enhanced keyboard protocol, where the terminal has it, and Windows Terminal's **win32 input mode** (mode 9001), which reports every key as a console input record in a sequence of its own (`CSI Vk ; Sc ; Uc ; Kd ; Cs ; Rc _`). The layer asks for both as it starts and turns on whichever the terminal confirms; the same decoder reads them. Where neither is there (the old console host), a new line is `Alt+Enter` or `Ctrl+J`. A terminal library that read console records (crossterm) would have had `Shift+Enter` in every console host; that is the price of one decoder and no library ([decision 0002](../decisions/0002-tui-rendering.md), "Amended in step 20"). **What is checked, and how:** the decoder's unit tests check every key above by its sequences, plain and win32. The system tests check under a hosted runner's ConPTY that keys sent as Windows Terminal sends them, win32 input records, reach the demo with every modifier: `Shift+Enter`, `Ctrl+Enter`, `Ctrl+Tab`, `Ctrl+Shift+A`, `Alt+X`, `Ctrl+Space`, `Ctrl+Up` and `Escape`, and that a lone Escape waits and is the Escape key. None is checked in a real Windows Terminal window; that is for the owner, by eye, with the demo. |
| `Shift+Enter` | Not distinguishable in every Windows terminal. `Alt+Enter` (where the terminal does not reserve it) and `Ctrl+J` always work. |
| Ctrl+C | Read as a key in raw mode, not as a signal, so a turn can be interrupted without ending the process. |
| Legacy console host | Taken to be the terminal when none of `WT_SESSION`, `TERM_PROGRAM` and `TERM` is set: no synchronized updates, ASCII glyphs, 16 colours. The checklist found it printing every escape sequence as text because nothing turned virtual-terminal processing on; the terminal layer now does. The system tests run the demo with that mode turned off first, as the old console host has it, under ConPTY (which is the console host without its window), and the demo draws correctly. A real window of the old console host is not seen by CI: whether it draws correctly now is for the owner to check by eye. Windows Terminal is the supported target. |
| Inline drawing under the console layer | Confirmed in Windows Terminal 1.24 by the manual checklist in [../measurements/windows-terminal-checklist.md](../measurements/windows-terminal-checklist.md) ([decision 0002](../decisions/0002-tui-rendering.md), "Checked on Windows"). If inline drawing misbehaves in a terminal, the full-screen presenter is the fallback. |

## Structure of `cineris-tui`

```
events from core ─► state ─► view (pure: state → styled lines) ─► presenter ─► terminal
keys ─► key map ─► actions ─► state changes and Ops to core
```

- **State** is plain data: the items of the active branch (for the full-screen presenter and the viewer), the live item, editor state, dialog state, status values.
- **View functions are pure.** Given state, width and a `view::Look` (the theme, the glyph set and the `tui` settings) they return lines, no row wider than the width given, which is one less than the window's. They are what the snapshot tests cover.
- **The transcript's state** (step 22) is `transcript::Transcript`: blocks in order, each committed when it can no longer change, with `commit(width, look)` for the lines that became final and `live(width, look, tick)` for the rows still open. Step 23 maps the core's events onto it:

| Event (`cineris-protocol`) | What it becomes |
|---|---|
| The session's start | `Block::Header(Header)`: version, model, effort, folder, branch, the profile's sentence |
| A user message item, on submit | `Block::User(text)` |
| `item.delta` of kind `reasoning` | `Block::Reasoning(Reasoning { text, elapsed, summary: None, finished: false })`, the text appended; when the item completes, `finished` set, with the summary if the provider sent one (reasoning without one commits as its first line) |
| `item.delta` of kind `text` | `Block::Answer(Markdown)`: each delta `push`ed; `finish` when the item completes |
| `item.started` of a tool call, `tool_call` and `tool_args` deltas | a `view::Call` in the round's `Block::Round(Round)`: verb, target and state from the tool's name and arguments (`Run` for `shell`, a path for the file tools) |
| `item.delta` of kind `tool_output` | the call's `Detail::Output`, appended |
| A tool result item | the call's state (`ToolOutcome` to `Succeeded`, `Failed`, `Denied`, `Interrupted`), its measure from the payload (an edit's counts and diff, a read's lines, an exit code) and how long it took |
| A notice (`retry`, `compaction`, `sandbox`, `instructions`, `speed_fallback`, `info`) | `Block::Notice(sentence)`, the sentence from the notice's message and fields |
| A turn that failed | `Block::Error { message, hint }` |
| A turn's end, with `tui.turn_summary` | `Block::Summary { took, tokens, cost }` |
| The session's state, usage and speed | `view::HintRow`: the model, effort, speed and its cooldown, the context's share, a budget, a limit, the access |
| Step 21's input (not an event) | `Outcome::QuitArmed`: `Hint::QuitArmed` until the next key; `Input::send_mode()` while a turn runs: `RunningKeys::Steer` or `Queue`; a menu or the history search open (`view::menu` gives lines): its lines in the hint row's place |

  `Transcript::push` gives each block a `BlockId`, and `Transcript::get_mut(id)` reaches it while any of it is still to commit: a round's results and a reasoning item's end arrive after other blocks may have been pushed below them (a notice, a steering message), so step 23 keeps the id of each item's block. The clock (`Clock::monotonic`) goes to `Transcript::set_now` each frame, for the code lines' wait; the spinner's frame is the tick. An answer is created with `Markdown::answer().with_highlighter(…)`: one highlighter for the process, whose waker wakes the interface's loop.
- **Actions** are an enum. Keys and slash commands both produce actions, so everything is reachable both ways and testable without a terminal.
- The TUI holds no agent logic. It never decides what a tool may do, never touches files, and never talks to a provider. It displays events and sends operations.

### The application as built (step 23)

`cineris` with no `-p` opens the interface on a session. The application is `cineris_tui::app`; `cineris-cli`'s `interactive` makes the core, its thread and the link, and hands them in. Its design, reviewed before it was built, is recorded in [steps/23/answered.md](../steps/23/answered.md).

| Part | What it is |
|---|---|
| `app::Link` | The one way to the core: `send(Op) -> Ticket`, `respond(RequestId, ServerResponse)` and `next() -> Inbound` (an event, a request, an operation's result, or the core gone), none of which waits. Only `cineris-protocol`'s types cross it. The binary's in-process link runs `Core::handle` on the core thread; step 27's `attach` is a second link over RPC. |
| `app::App` | The state: the transcript, the input, the dialogs, the session and its usage. What each terminal event, arrival and result does to it, and each frame. Plain data, driven in its tests by a scripted link. |
| `app::run` | The interface's loop on the thread that entered the terminal: every terminal event already read, a key's frame drawn at once, then at most 1 ms of what arrived (in batches of 64, looking for keys between), then a frame when the scheduler says, or when the application asks for one at a time of its own (`App::deadline`: an open dialog's answers, at the end of its grace). Idle, nothing is scheduled. Its times are the terminal's (`Terminal::now`), so that its tests play a terminal back on a clock of their own. Once the application has ended it reads nothing more: what is typed after the last key it takes is the shell's. |
| `app::interactive` | Enters the terminal with the `[terminal]` overrides, makes the link and the `Start` with the terminal's waker, runs the loop, and puts the terminal back whatever happened. |
| `app::Start`, `Settings`, `Open` | What the application is started with: the `[tui]` settings, the key map from `[keys]` with each entry it could not use as a notice, the session to open (new, `--resume`, `--continue`, `--fork`), a prompt from the command line, the history and the highlighter. |
| `view::dialog` | The approval dialog and the leave-the-sandbox form, from screens 2a and 2b; the trust question (screen 2c) and a question's dialog (screen 2d, the undo's). |
| `view::viewer` | The viewer's title row and its row of keys, each with its rule (screens 8a and 8b). |
| `transcript::Committed` | What `Transcript::commit_parts` gives: lines, or a finished round with its lines, which the viewer draws again as a box. |

- **Start-up,** in the order 15-efficiency asks: the user's configuration (for `[terminal]`, `[tui]`, `[keys]` and `log.level`, all user-only), the log (its file alone: standard error is the terminal), the rules of `--allow` and `--deny` (one that cannot be read is refused with exit code 2, as headless refuses it), the core started on its thread with that configuration (`CoreOptions::loaded`) and waited for, the terminal, the first frame (the input box and the hint row), and only then the session. The session's own events are held until its open returns, so that its header is the first block. A prompt sent before then, or given on the command line, is held and sent when the session is open, **one at a time, each once the one before it was answered** (since step 27): the first as a new turn, or steering the turn the open says is running (`session/open`'s `running_turn`, which `cineris attach` meets on every attach to a running turn), as `Enter` would; the rest queued behind it. A prompt sent while they are on their way follows them, and `/new` and `/sessions` say so and do not leave the session until the last has been answered. A refused one comes back into the editor with those behind it, in the order they were written, so that none overtakes another, and the spinner they started stops unless the core has said a turn runs (the open, the history's read or `turn.started`). An interrupt sends those not yet sent at once, queued behind the one on its way and ahead of the interrupt, so that the core holds them in order, as it holds any queued prompt at an interrupt ([03-agent-loop.md](03-agent-loop.md), "Only a turn that completed starts the next prompt by itself"), and they follow the next prompt; the one on its way, if it is refused or comes back undelivered in the interrupt's answer, goes into the editor, and sent again it runs first, with them behind it. Given back instead, one of them sent again would run ahead of one the core holds. A prompt sent after the interrupt goes at once, as any prompt sent after an interrupt does. A command line's prompt that is a slash command is done as one when the session is open, as typing it would, and is never sent to the model. An open that fails says why and gives the held prompts back into the editor, as an interrupt before the open does; of the events held while it was being opened, only notices are shown. With no session open and none on its way, a prompt is given back with a line that says `/new` starts one. `/new` opens its session with the settings the command line gave the first, in memory only after `--no-session`. `--fork` opens the session it forks (a fork is made from its log), forks it, and closes it once the fork is open, or once the fork has failed; `--continue` whose list of sessions cannot be read says why.
- **The mapping of events** is 09's table above. One response may be several blocks, in the order their parts began: reasoning ends when the answer or a call begins (`∴ Reasoned for 6s` and its text), and an answer ends when a call begins, so that no block below is held back by one still open above. The notice of the repository map is shown folded, one line. A tool result's line takes its measure from the payload `cineris-tools` gives it; a running command keeps the last 64 KiB of its output. An item whose deltas stopped (`item.resync`) is completed from the whole item, and so is a response whose `item.started` this client never saw: what arrived of it may not be its start, so none of it is drawn until it completes, whole.
- **Running from the moment a prompt is sent,** so that `Esc` right after `Enter` interrupts the turn it started. A second interrupt within 2 s stops running commands at once (`turn/interrupt` with `now`). While a turn runs, `Enter` steers and `Tab` then `Enter` queues. **A prompt the core refuses `turn_running` is sent again once, queued** (since step 27): the application's view of whether a turn runs lags the core's, so a prompt sent with no delivery between one turn's `turn.completed` and the `turn.started` of the next the core takes from its queue (which can fall in two of the loop's batches), or onto a turn another client began, is refused; sent again with `queue`, it runs after the turn that took the gap, and nothing is said. A second refusal, or one that comes after an interrupt was sent, gives it back into the editor with why, as any refusal does. Steering not yet delivered when the turn is interrupted comes back into the editor, from the interrupt's answer; after a turn that failed, or sent while an interrupted turn is still ending, the core holds it with the queue, to follow the next prompt ([03-agent-loop.md](03-agent-loop.md), "Only a turn that completed starts the next prompt by itself").
- **The approval dialog** takes the input box's place, its keys a context of the key map. It takes no key until it is ready, and its answers are drawn only then (the loop is woken for it): what can be pressed is what was shown, and what is shown can be pressed. *As built after the review of step 23, the owner's rule:* it is ready 300 ms after its first frame was written, and only after a second with no input that no dialog took (a key or a paste that went to the editor, keys read together, a key the dialog did nothing with while not ready, or a search typed in the viewer), whether that came while it was up or just before it came; answers already shown are hidden again by such input. Typing that carries on past the dialog's arrival, at any pace, never answers it, and a person who stopped to read it presses one key. The dialog after one a key answered is ready no sooner than a second after that key, so that the key held a little long, or pressed twice, never answers one not seen yet, and an answer key pressed before its row is drawn does nothing (it is not typed into the hidden editor). A key held down never answers: a repeat the terminal marks (the enhanced keyboard protocol's event types, which the layer asks for, mark those of the keys with no text; win32 input's key-downs with no key-up between mark all) goes where its press went, and an unmarked repeat reaches the editor and holds the dialog a second more, longer than the gap to the next. Reading the request whole in the viewer (`Ctrl+O`) is not typing at it; back from the viewer, after the program is continued (`fg`) and after the external editor, the dialog starts its grace again. While it does not take keys, what types a character goes on to the editor, where it was going, its own other keys (`Esc`) do nothing, so that a key meant to deny never stops the turn instead, and `Ctrl+O` shows the request whole, which answers nothing. Once it takes keys, a key it has no use for that types a character goes on to the editor as typing (so typing that resumed after a pause is kept, and the answers hide again), and any other does nothing. Keys that come in one read were typed together, and none of them answers, however long the read before them took. A paste never answers it. Once "deny with a note" has been chosen, what is typed or pasted is the note's, at any pace, and the row shows the note's end. `Ctrl+T` opens and closes the round's box from the dialog. **In the full screen, `Tab` reads the transcript above the dialog, which stays up** (since step 25, `dialog.transcript`): once the dialog takes keys (before, `Tab` goes where it was going) and is not taking a note, its row offers `tab reads above`, after the key that refuses, in the frame that first draws its answers. Reading, the dialog shrinks to its question's first row followed by `tab goes back`, the row's first words are the way back, and `PageUp`, `PageDown`, `Shift+Up`, `Shift+Down`, the arrows and the wheel scroll the transcript; no other key or paste does anything (`Ctrl+C`, `Ctrl+L` and the suspension excepted), the dialog's own answers and the search included, and each holds the dialog as typing does. A pressed `Tab` or `Esc`, not a held one, goes back: the dialog's second of quiet starts again, and until it is ready keys and pastes go nowhere, never to the hidden editor, whose `Enter` would send; `Ctrl+C`, `Ctrl+L` and the suspension still act then, and hold nothing. A dialog the window has grown too small for takes no key until the window grows; just back at one, `Tab` reads the transcript again (since the review of step 25's second pull request). A request that comes while reading keeps the reader's place. Reading ends with its dialog however that goes (answered, resolved elsewhere, withdrawn at the turn's end), and the next dialog follows the end as any does. The inline screen offers none: the transcript is the terminal's own scrollback. `Esc` denies; `Ctrl+C` interrupts the turn, which withdraws the question; with no turn running (the trust question, the undo's) it leaves the hidden editor's text as it is, and the hint row says a second quits. A note being written when its request ends from outside (the turn's end, a time limit, another client's answer) goes into the editor as a draft, which a notice says, and an `Enter` before a pause of a second does not send it. Because of that, the core holds every later call with side effects while a question is open (`CoreOptions::answers_may_stop`).
- **The dialog fits the window,** with a blank row and the hint row under it when the window has six rows or more. The question and the answers wrap, and are never cut. What gives way first is the line of what a lasting answer would allow, so that the detail stays whole, then the detail (a command, a diff, a tool's arguments), cut with a line that says how many more lines there are. In a window too small even for that, the rows between the question and the answers are dropped; in one too small for those two, no answer is taken until it grows. Only an answer drawn whole can be pressed, and the deny key, which the hint row shows. A request any of whose rows did not fit, a diff's line cut at the window's edge among them, offers no lasting answer, as leaving the sandbox does: no lasting rule is added for what could not be read. The leave-the-sandbox form is for a session whose sandbox is enforcing; with the sandbox off every command runs outside it, and is asked as any other call. A dialog's sentences wrap at the prose width, as the transcript's do; what would run, a path and a diff take the whole width. `Ctrl+O` in an approval or the trust question opens the viewer on the request drawn whole, its detail uncut; `Esc` returns to the dialog, still waiting for its answer, and a request settled elsewhere closes the viewer with it. What a cut request offers is not changed by having been read whole there.
- **The input box** says `Type to steer this turn` while a turn runs, and holds only its `◆` while a box or a panel has the focus (screens 1b and 4).
- **Panics.** The terminal layer's hook puts the terminal back only for a panic on the thread that entered it; the core catches a tool's panic and goes on, and the interface with it. The binary's hook writes a report with a backtrace to the log directory for the interface's own panic, and sends any other thread's to the log only, never to the terminal. The interface's panic unwinds to the binary, which ends the core in order, prints the report's one-line pointer once the terminal is back, and exits with code 1. An abort is SIGABRT, which the layer's handler restores from. A core thread that ends is the link's `Gone`, and the application ends with exit code 1.

- **The trust question.** A session of a project that has something to trust it with asks when it opens, before it is put together (`trust/request`, to the client that opens it, when its `ClientInfo` says it answers trust questions). The dialog says `Trust this project?`, the folder as a person reads it, and what trusting it turns on, each line with its kind (`rule`, `setting`, `git` and so on) and, for a rule of a profile the project defines, the profile it is in; a project whose rules changed since it was trusted says so. `y` trusts it, which pins every rule its files hold, in their base and every profile, as one pin; `n` or `Esc` is not now, which nothing stores and this process does not ask again; `x` is never for this project, stored with the trust pins, which later starts do not ask about either and `cineris permissions trust` lifts (`permissions forget` forgets a project). A line under the answers says what each does (since the follow-ups of step 23). A project trusted already is asked only about what is new in it (its rules changed, or git now that it is a repository): the dialog says `Trust what is new in this project?`, and `x` is `Keep trusting it, without the new rules` (or `without git`, or `without these`), which keeps what was trusted before and does not ask again until what is new changes ([06-permissions-and-sandbox.md](06-permissions-and-sandbox.md), "Project trust"). A list too long for the window is cut with a line that names `cineris permissions trust`, and offers no `Trust it`. Until a project is trusted its first limit (a `[limits]` key the user's files leave unset) waits, as what needs trust does. `/status` says the project's standing (`SessionState.trust`), with the command that changes it.
- **A question's dialog** (a tool's question, the undo's and the rewind's about files edited since): each choice by its digit, `Esc` to leave it unanswered, which for the undo keeps the files; a question with no choices takes `y` to write the answer. The approval dialog's rule of keys holds for it and for the trust question alike, and since step 25 for the application's own question of `/rewind` ("Rewind and fork").
- **Slash commands:** `/compact`, `/config` (the values in effect, one a line), `/copy` (the last answer, through the terminal's clipboard sequence, OSC 52, its control characters dropped and what acts unseen escaped), `/effort`, `/help` (the commands, then every key bound), `/mode`, `/model`, `/new`, `/permissions`, `/quit`, `/sessions`, `/status`, `/theme`, `/undo` and `/view [n]`; since step 25 `/rewind` and `/export`. Each of the table's others says it is not in this build, and is not sent to the model; [build-plan.md](../build-plan.md), step 23, "What later steps inherit", names the step of each.
- **Pickers** over the input, as step 21's menu draws them: `/sessions` (the stored sessions of the workspace, the one used last first, to resume or switch to), `/model`, `/effort` with its fast-mode toggle when the model has a fast speed (`Tab` turns it), `/mode`, `/permissions` (the stored approvals; `Delete` revokes the selected one and lists them again) and `/theme`.
- **The viewer** (`Ctrl+O`, `/view`), on the alternate screen. A title row (`Viewer`, the folder, when the session began in the local time, the turns it holds) and a rule, the transcript, and a rule and a row of keys with `box N of M`. Every finished round is kept as a round (`Transcript::commit_parts`) and drawn again as a box, all closed, the latest selected with its border in the accent. `Up` and `Down` move between boxes and keep the selected one in view, `Enter` opens or closes it with all its detail, `PageUp`, `PageDown`, `Home` and `End` scroll, `/` searches from where the view is and `n` finds the next, going round, and says when nothing matches; a paste goes to the search being typed, and nowhere else (never to the hidden editor); `Esc` or `q` returns to the inline screen exactly as it was, and so does quitting from the viewer (the alternate screen is left before the live region is erased, since the review of step 23). `/view n` opens box `n`, open. What is still live is drawn under the kept transcript as it is. **Since step 25's second pull request** a reasoning and a compaction are stops too: `Up` and `Down` move to them as to boxes, the selected one's first row drawn as a selected border is, and the keys row says `reasoning` or `summary` and `enter shows it whole`. `Enter` on a reasoning shows its whole text (all of it, however much `tui.reasoning` shows in the transcript), made safe as a command's output is, but with a bare carriage return shown as its symbol (`␍`), not taking the line back, so that nothing of it is hidden; on a compaction it reads the summary item through the link (`session/read` with its `item_id`) and shows it, the same way. A click on either's row does what `Enter` does. While the summary is read the keys row says `reading the summary…`, and `the summary could not be read` when the read fails or finds none; an answer is shown only on the view that asked, at the stop it asked at, never over the viewer opened again on something else (since the review of step 25's second pull request); a view that a reasoning or a summary is shown over gives its read up, so that it does not say `reading the summary…` for good once back, and `Enter` there asks again (since the review of that review's fixes). `Esc` from either goes back to the transcript where it was, drawn again if the look changed meanwhile. `/view n` still counts boxes. **Since step 25** the viewer draws the kept blocks again at the width it has, through the same window as the full-screen presenter, so it re-wraps on a resize and costs the rows near what it shows; its keys are the key map's `viewer` context, with the same defaults, and the mouse's click and wheel.
- **History** is a file of the state directory, `history`, one JSON line for each prompt sent with the project it was sent in. A thread of its own reads it from the start of the application, beside the start-up, keeps the project's newest 1,000 prompts (`Input::set_history`), and appends each prompt sent; past 20,000 lines the file is written again with each project's newest 1,000, under its lock. It is private to the user, and the end of the program waits at most a second for the last prompts to reach it. **Since the follow-ups of step 23 a prompt is kept as it was written,** each chip a chip with its label and its text, so `Up` and `Ctrl+R` give back the chip, not its text spread out in the editor; a search looks in the text and the chips' labels. What one prompt keeps is bounded (`cineris_tui::history::kept`): a chip keeps the first 64 KiB of its text, and its label then says so (`[pasted 2,345 lines, first 64 KiB kept]`), sent as kept if it is sent again; a prompt's chips keep 256 KiB together, one past that its label alone; and a prompt's own text past 64 KiB (the external editor's) is cut there, with a line saying how many characters were left out. The file is written again past 20,000 lines or 8 MiB, with each project's newest within 1,000 prompts and 2 MiB, and every project's together within 4 MiB; a project holds at most 1,000 prompts and 2 MiB of lines in memory; and a start reads at most the file's last 16 MiB, so an older build's file of pasted logs costs one read of its end. The measurements are in [steps/23/after-review/followups.md](../steps/23/after-review/followups.md).
- **`@` files** come from `workspace/files`, asked once, on the first `@` typed with a session open (`Input::wants_files`; since the fixes of the review of step 23, an idle session holds no list of them), up to the core's 100,000 paths; a listing that fails says why, once, and its `@` menu says the files could not be listed and asks nothing more while it is open; the next `@` asks again. They are moved, not copied, to a thread of their own, which makes them into one compact list (`complete::Candidates`: every path's text in one buffer, and 8 bytes a path beside it; at the cap that takes longer than a key's budget) and matches them there, off the key's path (`app::files`): the input hands each query out with a generation (`Input::filter_files_elsewhere`, `take_file_query`), the worker matches the latest it has been given, and the input takes rows of its latest query only (`Input::file_rows`), so that an older answer is never shown over a newer one. Until they come the menu keeps the rows it had.
- **The external editor** (`Ctrl+G`) is found and started as step 21's `external` says, with the session's write roots among the places it is never taken from (`SessionState::write_roots`, in `Env::avoid`): a project cannot plant the editor that runs. The loop gives the terminal to it and takes the text back as one step of undo.
- **Resume** (`--resume`, `--continue`, `/sessions`) draws the stored session's history under its header, read in pages of 500 items (`session/read`). An item the read gives in progress is drawn as far as it had gone, live, and goes on. Of the events that came while it was read, those of an item it holds whole are dropped, and those of an item it holds in progress up to the read's `seq`; the others follow it. The binary's link gives a result only after the events and requests queued when it was ready, so that a read's events come while it is under way; for a link that does not (step 27's), the same holds for that session's events taken after the read's result, until a turn begins or ends after the read. A turn was running at the read when an item was in progress, or when that session's turn events held up to the read say so, and then `Enter` steers it; otherwise a call the history holds with no result was cut off. A page that fails part-way says why; the events of what the pages before it drew are dropped as a whole read's are, but those of an item they do not hold are shown, since it may be on the missing page, and no call is taken for cut off. While the history is read, only the last 500 items' ids are kept. Until the session is open and its history drawn, `/sessions` does not switch and `/new` does not start another: each says so. A result that comes back for a session left meanwhile (an undo, a change of settings, `/status`, a page of history), or its error, is not taken for the one open now, and with no session open only the notices of the one closed are shown. `--continue` and the picker take `session/list`'s order: the one used last first.
- **Undo** (`/undo`) undoes the last turn, files and conversation, after the question about any file edited since. Since step 25 the transcript the viewer and the full screen draw is read again after it, as after a rewind ("Rewind and fork").
- **Signals** end the application gracefully, through the terminal layer's hand-off ("The terminal layer as built (step 20)", above): the running turn is stopped at once, the core ends within 1.5 s, and the process exits 143, 129, 130 or 131. The terminal closing is SIGHUP's end. A signal that lands while a key is taken or a frame is drawn, or after the loop ended for another reason, ends it the same way (since the review of step 23), and one that comes while the core ends after a quit cuts the core's wait to 1.5 s and is the exit code. On Windows the console's close, log-off and shutdown, `Ctrl+Break` and `Ctrl+C` as an event are handed over the same way.
- **The end is never behind the core's lane.** The binary's core thread runs what changes a session on a task of its own, one at a time in the order sent, and reads beside it; a read sent while a write is under way runs after it, in the lane, so that it sees every write sent before it. Since step 27 the lane is `cineris_rpc::lane`, and the order of results among events `cineris_rpc::order`, which an RPC connection runs too, so a client over the wire is ordered as this one is. When the interface ends it first disconnects it (`Core::disconnect`), which withdraws what it was asked and never answered, so that an open waiting on the trust question, or an undo on its question, ends; then it gives the lane's last operation 1 s, and shuts the core down. Ending with `Ctrl+C` twice, SIGTERM or SIGHUP while such a question waits takes a few milliseconds. `/quit` cannot be given while a dialog has the keys.
