# The TUI's look: reference screens

These are the screens of the look the owner chose on 2026-11-14 ([decision 0033](../../decisions/0033-tui-look.md)), which [09-tui.md](../09-tui.md) specifies. They show one session: turn 3 in a Rust workspace, where the agent fixes digit separators in a lexer, runs the tests, sees one fail, and streams the fix while the user types a steering message.

- **Width.** Every screen is 100 columns, except screen 6 at 60. No row uses the last column.
- **The live region** is the last rows of each screen; the table says how many. In screens 8a and 8b the viewer owns the whole screen.
- **How they were checked.** The design round's script drew each screen through `cineris_term::Inline` into the test kit's virtual terminal and compared every cell. The script is not in the repository; these files are the record of what was chosen.
- **How they are checked now.** Since step 22 the real views draw the same session again and are compared with these files cell by cell, in every pull request: `cargo xtask tui-screens` ([testing-and-ci.md](../../testing-and-ci.md), "The golden screens"). Step 21's input box and menus are drawn by its views, and since step 23 the dialogs, the viewer's frame and the input box's placeholder while a turn runs or a box has the focus are drawn by its. Since step 24 the plan panel's rows of screen 4, the usage panel's line under them, and the blank row that ends the panels' block, are drawn by their views: no row of any screen is counted as not built. **Since the review of step 23 a dialog is the application's own frame:** `cineris_tui::app::App` is given the request by a scripted core, in a window of the screen's width and height, and the live region it draws once the dialog takes keys is compared, its answers, their order, its fitting to the window, its blank row and its hint row included. Screens 2c and 2d were added then, written from the application with `tui-screens --write`, for the owner to see. Step 23 rewrote style alone in three files, from the views, for the owner to see: in 2a the bold of line 30's change is `clippy`, the word added, where it was four columns to its left (the owner's rule of 2026-11-16: whole changed words, the punctuation and spaces around them plain); and in the light 2a and 2b the warning colour and the diff's signs are bold, as the light theme draws them and screen 1's light file already had them.
- **What step 24 changed in them** (the owner's word of 2026-11-16, that the screens show the application's real states): 2a and 2b are asked in the middle of a turn, so their hint row shows the spinner and the turn's time before the dialog's keys (`⢿ 12s`, `⣽ 7s`), where step 23's fixes had composed them with no turn running; and 2a's edit carries the rule a lasting answer would add, as the core offers it for a protected file (writing that one file, by its whole path), which the dialog says on a line of its own (`Allowing it for longer allows: …`), two rows more. 2b's leaving the sandbox offers no lasting answer, so it says none. Both were written from the application with `tui-screens --write`. And in style alone, by the same command: in the light 4, the done plan item's `☑` (row 33, column 2) is bold, as the light theme draws the success colour since the owner's colour decision of 2026-11-15; the panel's rows were not compared when that decision rewrote the other screens. **Screen 4's usage line** (row 37) is drawn by the usage panel since step 24's third pull request, from a limit as the protocol carries it, and written with `tui-screens --write`: it says `anthropic fast tier: 18% of the output token limit left, resets 15:00` where the drawing said `fast tier: 18% of the hourly output limit left, resets 15:00`. A limit carries what it counts and when it resets, not its period, so `hourly` is not something the panel can know; and with more than one provider, a line that names none would not say whose limit it is. Every cell from column 2 to the line's end changed, in both files, in the same warning colour (bold in the light theme, as it draws the warning colour); the two blank cells before it are unchanged.
- **What step 22 changed in them,** each by rewriting the row from the real views (`tui-screens --write`), as 09-tui says the row should be: a bottom border with a label is as wide as the box (it was one column short, its corner left of the border above: screens 1c, 1d, 2a, 4, 8a, 8b); the live reasoning row shows the latest words (1b); on a dark background at 16 colours, `fast` is bold in the default colour, not magenta (7a, 7c); the code line still streaming is plain until it ends (1, 6, 7a, 7c); and in the `/model` menu, `fast` in a row's note is muted, as the rest of the note, not in the accent's tint (3a; step 21's menu gives a note one style). Every changed cell is listed in [step 22's records](../../steps/22/answered.md).
- **What the owner's colour decision of 2026-11-15 changed** ([decision 0033](../../decisions/0033-tui-look.md)'s amendment), again by `tui-screens --write`, in styles alone: on the light screens, status text in red, green or yellow is bold (the error sentence and failure's measure, `✓` and `+5`, a diff's signs), while highlighted code and whole changed lines keep their weight; on the dark screens, keywords in code are bright blue (1, 6, 7a, 7c, 8a, 8b). The cells are counted in [the fifth tooling step's records](../../steps/tooling-5/answered.md).

- **What step 25 added** (its third pull request): the first run's screens, F1a to F4, composed as drafts in [the step's design](../../steps/25/design/screens.md), revised to the maintainers' answers of 2026-11-17 (the set-up card in the live region and never committed, the imports unpicked, no `unrestricted`), and written from the application with `tui-screens --write`: the real `App`, given a scripted core and the test kit's program (`FakeSetup`), driven through its steps, its committed rows and then the live region of the frame that shows the step's keys. Their rows are the application's, so they are what a person sees: the step's prose wraps at `tui.prose_width`, a mask is `[redacted]` as everywhere else the harness masks, and F4's header is the session's own, with no line about the project's profile.

**To see a screen as the terminal draws it,** print its ANSI file in a terminal whose background matches the file's name:
- Linux: `cat docs/architecture/tui-look/1-dark.ans`
- PowerShell: `Get-Content -Raw docs\architecture\tui-look\1-dark.ans`

The `.txt` file beside each one is the same screen without colour, to read here. A test holds each to the text of its dark screen, and `tui-screens --write` writes both.
