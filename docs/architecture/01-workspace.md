# Workspace and crate layout

One Cargo workspace. Crates are split so that an edit recompiles as little as possible, so that heavy dependencies sit in leaf crates, and so that each crate can be tested alone.

## Crates

All crates use the `cineris-` prefix, live under `crates/`, and set `publish = false`.

One package is in the repository and outside the workspace: `fuzz/`, the fuzz targets for the stream decoders, the outline extractors and the RPC server's decoder, with a lockfile of its own. It depends on `cineris-llm`, `cineris-index`, `cineris-protocol` and `cineris-base`, and compiles `cineris-rpc`'s `wire.rs` from its file rather than depending on `cineris-rpc` and so on the whole core, needs a nightly compiler, and is built only by the nightly workflow's `fuzz` job and by `cargo xtask fuzz` ([../testing-and-ci.md](../testing-and-ci.md), "Not blocking").

## Dependency direction

```
protocol ◄─ base ◄─┬─ llm ◄──────────────┐
                   ├─ sandbox ◄─ tools ◄─┤
                   ├─ sandbox ◄──────────┤
                   ├─ policy ◄───────────┼─ agent ◄─┐
                   ├─ session ◄──────────┤          │
                   ├─ stats, knowledge ◄─┘          ├─ core ◄─┬─ rpc ◄─┐
                   │    └─ usage (later) ◄──────────┤         │        │
                   ├─ config, index ◄───────────────┤         ├─ runs ◄─ coordinator
                   │                                │         │        ├─ cli
                   ├─ ext, mcp ◄────────────────────┘         │        │
                   └─ term ◄─ tui ◄───────────────────────────┴────────┘
```

Rules, enforced by a workspace test that reads `cargo metadata`:

1. `cineris-protocol` depends on no workspace crate. It is the contract, so it stays small and stable. Of third-party crates it links serde and serde_json and nothing else in a normal build; schemars is an optional dependency behind the `schema` feature, which only `xtask` and the schema test turn on.
2. `cineris-agent` depends on traits, not implementations. It never names reqwest, a concrete provider, or a concrete tool. That is what lets the loop be tested with a scripted provider and fake tools in microseconds.
3. `cineris-tui` and `cineris-term` never depend on `cineris-core`, `cineris-agent`, `cineris-llm` or `cineris-tools`. The TUI sees only `cineris-protocol` types. A UI edit therefore never rebuilds the core, and the UI cannot reach around the protocol.
4. `cineris-core` and `cineris-rpc` never depend on `cineris-tui` or `cineris-term`.
5. Only `cineris-llm` (feature `http`) links the HTTP and TLS stack. Only it and `cineris-policy` link `ring`, the stack's crypto, which since the signed approvals step also makes and checks the person's signatures; only `cineris-policy` links `argon2`, which makes the person's key from their password. Only `cineris-mcp` links the MCP SDK. Only `cineris-tools` links the search libraries. Only `cineris-ext` links the script engine. A change elsewhere does not rebuild them.
6. Test support lives in `cineris-testkit`, never behind `cfg(test)` exports of production crates. The fake clock and the seeded random-number generator are the one case that looks like an exception and is not: they are ordinary public types of `cineris-base`, beside the traits they implement, because `cineris-base` tests itself with them and cannot depend on the test kit, which depends on it. The test kit re-exports them.
7. `cineris-usage` depends only on `cineris-base` and `cineris-stats`, and links no network code. Reading other tools' files stays apart from everything that can send.
8. `cineris-tools` depends on `cineris-sandbox` for process trees, and must not link the sandbox backends through it. The backends (`landlock`, `seccompiler`) are behind the feature `backends` of `cineris-sandbox`, off by default, which `cineris-core`'s `sandbox` feature turns on (since step 26). Only `cineris-sandbox` may depend on them directly, and only `cineris-core` may turn the feature on (`cargo xtask rules`).

## Why this split

- **Incremental builds.** The measured cost of a no-change relink of a binary carrying the full dependency set is in [../measurements/dependency-costs.md](../measurements/dependency-costs.md). The binary crate is kept tiny, and the two crates that change most during UI work (`cineris-tui`, `cineris-term`) sit beside the core, not under it, so they rebuild alone.
- **Test isolation.** The loop, the session store, the policy engine and the renderer each have tests that need no network, no terminal and no child process. Slow process-level tests are confined to a few crates (see [../testing-and-ci.md](../testing-and-ci.md)).
- **Dependency containment.** Each heavy dependency has one owner crate. Replacing it later (a different HTTP client, a hand-written MCP client) touches one crate.
- **Not too many crates.** Twenty-four, including test and tooling crates and three that arrive after the first release (`cineris-runs`, `cineris-coordinator`, `cineris-usage`). Each extra crate adds link and metadata overhead, so a new crate needs a reason from the three points above.

## Workspace settings

- `resolver = "3"`, `edition = "2024"`, one `[workspace.dependencies]` table so each third-party crate has one version and one feature set.
- `rust-toolchain.toml` pins the stable toolchain. The project builds a binary and publishes no libraries, so it follows current stable and promises no minimum supported Rust version.
- `[workspace.lints]` sets the shared Clippy and rustc lints (see [../testing-and-ci.md](../testing-and-ci.md)). Async crates deny blocking calls (`std::fs`, `std::process`, `std::thread::sleep`) through Clippy's disallowed-methods list.
- Profiles:

| Profile | Use | Settings |
|---|---|---|
| `dev` | Local work | `debug = "line-tables-only"`, dependencies built with `opt-level = 1` and `debug = false` |
| `test` | Local tests | as `dev` |
| `ci` | The blocking CI test jobs, and `cargo xtask ci` | inherits `dev`, with dependencies at `opt-level = 0` and, since the CI-budgets fix, no debug info for any crate ([decision 0012](../decisions/0012-release-profile.md)). Added in step 2, when a clean build of the planned dependency set on a hosted Windows runner measured 259 s with optimised dependencies and 60 to 82 s without ([../testing-and-ci.md](../testing-and-ci.md)) |
| `release` | Local optimised builds, perf runs | `opt-level = "s"` (since step 33's size fix, so that a measurement runs code optimised as the shipped binary's is: [decision 0036](../decisions/0036-the-shipped-binary-is-optimised-for-size.md)), `lto = "thin"`, `codegen-units = 16`, `debug = 0` |
| `dist` | Published binaries | inherits `release` and its `opt-level = "s"`, `lto = "fat"`, `codegen-units = 1`, `strip = true`. Built through `cargo xtask size` (and step 34's `dist`), which takes the build machine's folders out of the paths it holds |

`panic = "unwind"` in every profile. A panic in a tool task or an extension call is caught at the task boundary and becomes an error result, and the terminal is always restored. The size cost and the reasons are in [decision 0012](../decisions/0012-release-profile.md).

## Third-party dependency policy

Each direct dependency must earn its place. The rules:

1. Prefer the standard library, then a small focused crate, then a framework.
2. Default features off. Opt in to what is used.
3. A dependency that compiles C or C++ needs a decision record that states its measured build cost on both OSes. A dependency that needs build tools beyond the platform's own compiler (CMake, NASM, Perl, Go) is not accepted. Today that rules out aws-lc-rs, and it has kept out bundled SQLite and parser grammars on cost. Two dependencies with C code are accepted: the script engine ([decision 0005](../decisions/0005-extension-mechanism.md)), and `ring`, the cryptography under TLS ([decision 0004](../decisions/0004-http-and-tls.md)), which has been in the build since step 5.
4. Licences must be compatible with the project's MIT licence. The allow-list is in [../testing-and-ci.md](../testing-and-ci.md).
5. No dependency that is a port or extract of Pi or Opencode code.
6. Every direct dependency is listed with its purpose and owner crate in `docs/dependencies.md`, which the repo skeleton step creates. CI fails if `Cargo.toml` and that list disagree.

The initial set and the measured cost of each candidate are in [../measurements/dependency-costs.md](../measurements/dependency-costs.md).
