# The extension system

Extensions let users add their own tools, slash commands and hooks without changing the harness. The [vision](../vision.md) gives the extension system a concrete job on top of that:

- **Self-written extensions.** The user asks for a new tool or command; the harness writes it, the user reviews it, and it loads at once.
- **Sandboxed**, for an audience that includes Windows users, where no OS sandbox exists in the first release.
- **Hot-reloaded**, like configuration, themes and key bindings.
- **For everyone.** It cannot assume that Python, Node or a compiler is installed.

This page compares the ways to build it, recommends one, and specifies it. The choice is recorded in [decision 0005](../decisions/0005-extension-mechanism.md). The owner accepted it on 2026-11-12.

## What an extension can add

| Contribution | What it is | Example |
|---|---|---|
| **Custom command** | A prompt template in a markdown file. No code. | `/review` expands to the team's review checklist. |
| **Skill** | A folder of instructions the model reads on demand. No code of ours. | "How we write database migrations." |
| **Hook** | Code that runs when something happens in the agent's lifecycle. It can observe, add context, or decide. | Refuse edits to generated files. Run the formatter after every edit. |
| **Tool** | A function the model can call. | Query the team's issue tracker. |
| **Command with code** | A slash command handled by code. | `/deploy-preview` runs a script and reports back. |

## The options

### Three mechanisms

The same tool (JSON in, JSON out) was built behind each mechanism and measured, together with the cost each adds to the host. Method and full tables: [../measurements/extension-mechanisms.md](../measurements/extension-mechanisms.md) and [../measurements/dependency-costs.md](../measurements/dependency-costs.md). Reference-machine figures.

| | WASM components | Subprocess speaking JSON | Embedded scripting |
|---|---|---|---|
| **What it is** | Extensions compiled to WebAssembly and run in-process by an embedded runtime. | Extensions are ordinary programs. The harness starts them and exchanges JSON over standard I/O. | An interpreter inside the harness runs extension scripts. |
| **Can the harness write one and load it at once, on any machine?** | No. The source must be compiled to WASM first, which needs a toolchain on the user's machine and about 13 s per build. | Only if the right runtime (Python, Node) happens to be installed. | **Yes.** The interpreter is in the binary. |
| **Sandbox when the OS cannot help** | Strongest. No access to anything the host does not hand over. | None. The process has the user's rights. | Strong. A script has only the host functions it is given. |
| **Start-up** | 0.14 ms precompiled, 10 ms when compiled at load | 0.34 ms native, 10 to 16 ms for a script runtime | 0.04 to 0.12 ms |
| **Per call (200 bytes)** | 1.4 µs | 27 to 35 µs | 4 to 20 µs |
| **Per call (64 KiB)** | 0.06 ms | 0.10 to 0.31 ms | 0.8 to 5.3 ms |
| **Memory** | 0.3 MB per extension; 17 MB transiently when compiling at load | A process each: 2 MB native, 11 MB Python, 23 MB Bun, 47 MB Node | 0.2 to 1.4 MB per extension |
| **Cost to the host** | The largest dependency measured: 10.2 MB of binary and 65 s of clean release build on 4 cores when added to the harness (10.5 MB and 86 s built alone), and a new major version about monthly. | Nothing beyond what the harness already has. | Small to moderate, depending on the language. See the next table. |
| **Linux and Windows** | Identical. | Script shims, no shebang lines, newline translation, code pages, signals. | Identical once built. |
| **Access to libraries** | Whatever compiles to WASM. | Everything. | Only what the host exposes. |

**What decides it.**

- Per-call speed decides nothing. Every option adds microseconds to a tool call that sits inside a model round trip of seconds.
- The vision's requirements decide it. Only embedded scripting lets the harness write an extension and load it immediately on a machine with nothing else installed, with a sandbox that works on Windows today.
- Subprocesses keep one job: tools that need a real ecosystem (an official client library, a native tool). That job already has a standard, MCP, which the harness supports anyway ([13-mcp.md](13-mcp.md)).

### Which language

With embedded scripting chosen, the candidates are the languages themselves, plus WASM as the target for code the harness writes.

| | JavaScript on QuickJS | JavaScript on a pure-Rust engine (Boa) | Lua 5.4 | Rhai | Rust compiled to WASM |
|---|---|---|---|---|---|
| **Familiar to extension authors** | Very widely known. The first language of most people who script their tools. | The same language. | Known from editors and games; a minority. | Almost unknown. | Known to few; hard to write casually. |
| **Models write it correctly on the first try** (19 tools, a strong and a small model, 38 attempts) | 38 of 38 | 38 of 38 (the same sources) | 38 of 38 | 34 of 38. All four failures were the small model calling functions that do not exist. | 38 of 38 compile and pass, given a compiler. |
| **Start a runtime** | 0.07 ms | 0.15 ms | 0.04 ms | 0.12 ms | 0.14 ms precompiled |
| **Per call, 200 bytes** | 20 µs | 120 µs | 4 µs | 8 µs | 1.4 µs |
| **Per call, 64 KiB of text processing** | 5.3 ms | 155 ms | 0.8 ms | 1.9 ms | 0.06 ms |
| **Memory per runtime** | 0.9 MB | 4.2 MB | 0.2 MB | 1.4 MB | 0.3 MB |
| **Added to the harness binary** | 1.1 MB | 6.7 MB | 0.4 MB | 2.4 MB | 10.2 MB |
| **Added to a clean release build of the harness (4 cores)** | 8.6 s | 55 s | 1.5 s | 11 s | 65 s |
| **Sandbox with no help from the OS** | Strong: no ambient access; memory limit and interrupt hook. The engine is C, so its own bugs are a risk. | Strong, and the engine is memory-safe Rust. | Strong: libraries are chosen by the host; memory limit and instruction hook. The engine is C, small and old. | Strong, memory-safe Rust, with built-in operation limits. | Strongest. |
| **Build needs** | A C compiler. Its Windows (MSVC) support in the Rust binding must be confirmed. | Rust only. | A C compiler. Well-trodden on Windows. | Rust only. Brings one MPL-licensed crate. | Rust only for the host. A full toolchain on the user's machine to write one. |

How the first-try experiment was run, and its limits, are in the measurement page: the code was written by subagents of the session that produced these docs, told to write each file once without running anything, and then executed in the real engines against fixed tests.

**Reading the table.**

- **Models do not separate JavaScript, Lua and Rust** at this size of tool. Rhai trails with a weaker model, because little Rhai exists to learn from.
- **People do separate them.** The audience is the broad public, and JavaScript is the language most of them already write.
- **The pure-Rust JavaScript engine is too slow for the job.** A tool that tidies a 64 KiB command output takes 155 ms in it on the reference machine and 296 ms on the second machine, about 30 times longer than in QuickJS, and it costs six times the binary.
- **WASM is the strongest sandbox and cannot do the job**: the harness cannot write and load one on a machine without a toolchain.

## Decision

1. **Extensions are JavaScript, run by an embedded QuickJS engine.** One runtime per extension, with memory and time limits, and no access to anything except host functions that are checked one by one.
2. **Tools that need an ecosystem are MCP servers.** There is no second, bespoke process protocol.
3. **The simplest hooks can be a command line** in configuration, with no script.
4. **Fallback: Lua.** If the QuickJS binding does not build cleanly on Windows in the extension step's first hour, the step switches to Lua 5.4, which is smaller, faster and proven on Windows. The host functions are defined once in Rust and are the same for either language, so the switch is contained.

**What is given up.** The script engine is a C library inside the harness. A memory-safety bug in it could, in principle, let a script escape. Against that: scripts are code the user approved, each has a manifest that bounds what it may ask for, and the engine is the one C dependency accepted. The alternative that removes this risk, a pure-Rust JavaScript engine, measured too slow today.

**When to revisit.**
- A pure-Rust JavaScript engine reaches within a few times of QuickJS: switch engines, same language, same extensions.
- A public registry of third-party extensions is wanted: reconsider a WASM tier for code the user has not read.
- Models' reliability in JavaScript and Lua diverges on larger tools.

## The tiers

Each is simpler than the next. Most needs are met by the first three.

### Tier 1: custom commands (files, no code)

A markdown file is a slash command.

```markdown
---
description: Review the staged changes
arguments: [focus]
---
Review the staged changes in this repository. Focus on {{focus | "correctness"}}.
Report problems as a list, most serious first.
```

- **Where.** `<workspace>/.cineris/commands/*.md` and `<config dir>/commands/*.md`. The file name is the command name, by the registry's rules. **The user's command is used over a project's of the same name** (since step 28; names compared with ASCII's case folded), and the project's is listed as not used, saying why. *Changed in step 28, settled by the maintainers with the early reviewer's agreement:* this page said that project commands override the user's; but a command's body is sent as the user's own prompt, so a repository could make the user's own `/review` send text it chose. Hooks and extensions follow the same rule: a project's hook may not take a name of the user's, and an extension's name is the user's. Every project command is labelled as the project's wherever commands are listed.
- **Front matter.** A description for the menu, named arguments with optional defaults, and optionally a settings profile, which the first release judges and does not apply: a command that names one is not sent ("As built in step 28: custom commands").
- **Body.** Sent as the user's prompt, with arguments substituted. `{{args}}` is everything typed after the command.
- **No execution.** A command file cannot run anything or include files by itself. It is text for the model, so it needs no trust.

**As built in step 28: custom commands** (`cineris_ext::commands`; the core's `commands`; [steps/28/parts/pr3a-commands.md](../steps/28/parts/pr3a-commands.md)).

- **Found when used.** The two folders are read each time the commands are listed or one is sent, on the blocking pool, so a file changed is seen at once and a session with none reads nothing until one is asked for. A project's are read whether or not it is trusted: they are text for the model. A file is `<name>.md` (`.md` in any case), its name by the registry's rules.
- **Bounds, as the skills' are:** at most 100 entries looked at in a folder, every entry counting, the rest said; a file of at most 64 KiB, one over it refused by its length, unread; UTF-8 only; no link followed inside a folder (a command file that is a link is left out); a root may be a link the user made, and a project's must lead inside the workspace. Within one folder, files whose names differ only in case are all left out, on every system. A file of the user's takes its name from a project's even when it is itself left out. What is left out is listed by `commands/list` with its reason. When the user's folder of commands cannot be read whole (it cannot be resolved or read, is not a folder, holds more than 100 entries, an entry cannot be read, or its path is not Unicode), no project's command is used: its name could not be checked against the user's. A folder that is not there holds no names. Linked command files stay refused, as skills' and extensions' links are. **A project's body, and its arguments' defaults, may hold no character that acts unseen** (a control character other than a line break, CRLF included, and a tab; a format character, the bidirectional overrides and tag characters among them), since a project's command is sent as the user's own prompt.
- **The front matter is read strictly:** only `description`, `arguments` and `profile`, each once, and every line a `key: value` field; a block never closed refuses the file. `description` is at most 2 KiB with nothing in it that acts unseen. `arguments` is a list of names, each with a default in double quotes if it has one, `[focus, depth = "shallow"]`: at most 16, none twice, and not `args`. `profile` is a profile's name.
- **The body.** `{{name}}`, `{{name | "default"}}` and `{{args}}` are put in; `\{{` is a `{{` of the text, and any other `{{` refuses the file, as does a placeholder naming no argument, or an empty body. What is typed after the name is read as words, a word in double quotes holding spaces, `name=value` giving an argument by its name, and the other words filling the arguments in order. A value given wins over the placeholder's default, which wins over the front matter's. More words than arguments are refused unless the body puts in `{{args}}`, as is an argument put in with no default anywhere. At most 16 KiB may be typed and 256 KiB sent. What is put in is not read again.
- **An extension's commands** are those its script registered, as the session loaded it (the registration cache's entry), named `<extension>:<command>`. Its function is given `{args, arguments}` and returns the text to send, a string of at most 256 KiB, which is sent under a line that names the command and the extension and says the text is its author's. Nothing, an empty string or anything else is refused (`command_failed`) and starts no turn.
  - **Its time** is 30 s from when it is asked, its wait for its runtime included, whatever its manifest gives its tools.
  - **Its host calls are a command's:** decided under `<extension>/command.<name>`; a question put where the engine asks ("allow once" or "deny"), which begins by naming the command and whose extension it is; `fs.write` refused. **Its programs have no write root,** as a hook's: it runs outside any round, so nothing they wrote would be recorded; where the sandbox does not enforce, a program the engine lets run still writes as the user, unrecorded, as a hook's does. A command that needs to change files sends a prompt, and the turn it starts makes the change with the session's tools; a change that must follow every edit is a hook command with `write = true`.
  - **Its questions name the run,** in the place of a turn's id, by `cmd_<n>`, unique in the process and never a turn's (`t_<n>`): a person's "allow once" for one run is not another's, nor a real turn's, and no stop is recorded by its number.
  - **Its stop** (a question answered with a stop, such as a call nobody can be asked about under `--fail-on-denial`) is told, refuses the next prompt once, as a hook's does, and stops the turn running, if one is; never turn 0. Its programs have no write root, so no look at the protected paths runs around them. A stop of the running turn made while its script runs, a question it put still open included, refuses its later host calls (`exec`, `fetch`, every `fs` call) with that stop, as a hook's are; it is the turn's stop, not the command's own, so it holds back no prompt.
  - **It does not run** while a stop waits for the next prompt (the stop is taken, and said), while a gate is held on `prompt.submit`, or while the running turn is stopped: its text would be refused.
  - **An interrupt stops it,** from any client that may drive the session, sent before its step began or while it waits or runs: its script, an open question (withdrawn, a late answer refused) and its program (killed at once by a second interrupt) at once; while the step still waits (for another turn's start, the extensions, `session.start`'s hooks, the looks at a turn's start) it ends when those are over, before its script runs, having sent nothing. An interrupt's own step stops only the commands sent before it. The session's close and the core's end stop it too.
  - **A command that is not sent** is refused `command_refused` with why: a file left out (its reason), a command that names a profile, a script command where its prompt would be refused (a stop waiting for the next prompt, taken; a gate held on `prompt.submit`; the running turn stopped), and an extension's command when the extension is found and not loaded (turned off, not approved, changed, unreadable, its name a folder of the user's, a store that cannot be read, its registration failed or refused, or its gate held). A command the session knows nothing of is `unknown_command`. Both front ends send any `/a:b` as a command, so that an extension not loaded is refused by the core with its reason; headless mode's second signal kills a command's programs at once.
- **A command's profile is judged and never applied in this release.** Each key it sets is judged as a project's file is, against the session's value in force, and only a preference passes: it names a profile of the user's layers or of a trusted project's; never raises the level above the session's own, the sandbox, its network or its write roots; adds no `allow` rule; changes no provider or model; and sets nothing that runs code or is the user's alone. A command that names a profile is not sent: with what the profile would widen, or, when it would widen nothing, because sending it without its profile could run it wider than its author meant ([a-commands-settings-profile-for-its-turn](../outstanding/a-commands-settings-profile-for-its-turn.md)).
- **In the lane.** A prompt that names a command (`turn/start`'s `command`) is expanded once the session's extensions are settled and looked at again, before the loop takes it: its `prompt.submit` hooks see the text it sends, and a gate they hold refuses it. The recorded prompt says which command it came from and whose (`UserMessageItem.command`). A command's run is put on the session as its `turn/start` is sent, queued or not, with tokens of its own, and looked at again just before the prompt goes. An interrupt from any client that may drive the session, sent while the command is queued, waits or runs, stops it: the run ends `command_failed` of kind `interrupted`, nothing is recorded and no turn starts. A prompt given back (`prompt_returned`, an interrupt's undelivered messages) carries its command, and the interface puts back `/name args`, as it does in a rewind. Headless mode takes a command only from the words after `-p`, never from piped input, and a name holding `/` is never one; it sends `/name …` as a command whenever the session lists the name, used or not, any `/a:b`, and when the list cannot be had. With piped input, the command's expanded text comes first and the piped text after it, as one prompt that `prompt.submit` sees, and an image beside a command is refused (`invalid_prompt`). It says on standard error whose command it is and its file.

### Tier 2: skills (folders, read on demand)

A skill is a folder with a `SKILL.md` that starts with a name and a description. This is the open Agent Skills layout, read as it is so that people's existing skills work.

- **Where.** `.cineris/skills/`, `.agents/skills/` and `.claude/skills/`, in the project and in the user's home.
- **In the prompt:** each skill's name, description and path, and nothing else. The model reads the file when a task calls for it.
- **Scripts inside a skill** are just files. If the model runs one, it runs through the shell tool under the normal permissions.
- Skills need no trust, for the same reason as instruction files.

**As built in step 28** (`cineris_ext::skills`; [steps/28/answered.md](../steps/28/answered.md), point 7). `skills::find` looks in `.cineris/skills/`, `.agents/skills/` and `.claude/skills/` in the workspace, then the same three in the home directory; with `compat.skills` off, only the two `.cineris/skills/`. It reads the folders and the `SKILL.md` files and nothing else, and blocks, so the caller runs it on the blocking pool.

- **A skill is `<root>/<folder>/SKILL.md`, one level down.** A `SKILL.md` in the root itself or deeper than one folder is not one, and a folder with none is passed over without a word.
- **Paths are judged where they lead.** Every root, folder and file is found through the session's path resolver (`~`, a relative path, `..`, links, the case Windows stores), and two places are compared by place (`cineris_base::location_within` and its friends), never by their text. A root may be a link the user made (`~/.claude/skills` often is), and is followed; **a project's root must lead to a place inside the workspace.** A skill's folder or its `SKILL.md` reached through a link is followed only where it stays below its root. **The file is read through handles,** after resolving (since step 28's third pull request): the root opened once, where it was resolved to (a project's from the workspace down, no name below the workspace followed; a user's by its path, its own name not followed), and listed through its handle; then each name below it opened relative to the folder before, none followed if it is a link now, and nothing but a regular file read at the last (`cineris_sandbox::unfollowed`), so that what is read is what was checked, in the root that was looked in, whatever was swapped since. Before, a folder swapped for a link between the look and the read led out of the root, and that file's name and description reached the system prompt; and until the narrow re-check of the managing part the root was opened again by its path for each read, the folders above it followed, so that a folder above a project's root swapped for a link (`.cineris` to `~/.claude`) sent the read into the user's own skills, listed as the project's past the consent to other tools' folders. The root is opened again after its skills are read, as it was opened, and compared with the folder held by its identity (device and inode; on Windows, volume serial number and file index): one whose place now leads through a link or to another folder has its skills left out, said ("it changed while it was read"), and so has one that meets a link on the way when it is first opened. On Windows a folder above a root held cannot be renamed while the root is read. A skill's body is read by the model's own `read` tool when a skill is used, under the engine's checks. A root that is the same folder as one looked at before it is looked at once.
- **The front matter** is a block between two `---` lines at the top of the file, read by a small reader of the plain YAML skills are written in (`FrontMatter`), with no YAML library: `key: value` lines, a value in either quote with its escapes, a value folded over lines, and a `>` or `|` block. A file with no front matter, or without a `name`, is left out with its reason; a missing description is an empty one.
- **For the system prompt** each name and description is one line (`cineris_base::one_line`, the rule the agent's index of tool sources is shown by too): white space becomes one space, and the control characters and Unicode's format characters (the bidirectional controls, the zero-width characters, U+FEFF) are taken out, and so is every variation selector, since one after each character can carry a byte unseen and a run of them any bytes, while none changes what the model reads (since the fixes to step 28). A name is cut to 64 bytes and a description to 300, between two characters, ending in `…`. The path shown is relative to the workspace for a project's skill and under `~` for the user's, never the home directory written out, with every character that acts unseen, and every variation selector, written as an escape (`cineris_base::visible_to_the_model`), so that it still names the file once the system prompt has taken the selectors out.
- **Caps:** at most 100 entries looked at in a root (every entry counts, a file too; 1,000 before a repository's crafted roots were measured on Windows, below); a `SKILL.md` of at most 64 KiB, one over it refused by its length, unread; at most 8 MiB of `SKILL.md` files read in a root, every byte read counting, the rest left out unread with the reason; at most 100 skills listed, the rest counted.
- **One name, one skill.** Of two skills with one name, the project's is taken over the user's, and `.cineris/` over `.agents/` over `.claude/`, whatever order the roots are given in; the other is left out with its reason. The list is by name.
- **What was left out** (a link out of its root or to nothing, a file that is no file, too large, no front matter, no name, a duplicate, a root past its cap) is returned with its reason, for the user; the model is told only how many skills it is not shown.
- **Section 6's part** (`skills::render`) is a heading line, one line a skill, `- name: description (path)` (`- name (path)` with no description), and a line that counts the skills not listed, within 8 KiB.
- **In a session** (the core's `ext::found`): the skills are found on the session's finding with its extensions, before it settles, so that the first turn's prompt holds them; the user's three roots always and the project's three whether or not it is trusted (they need no trust, above); with `compat.skills` off the two `.cineris/skills/`. A root that is not there costs a look at each name on the way to it, and is not resolved: six looks for a session with no skill. The skills' part is rendered within `cineris_agent::SKILLS_CAP`, and section 6 is built from it ([07-sessions-and-context.md](07-sessions-and-context.md), "As built in step 28"). **Without the `scripts` feature, which the finding needs, no skill is found:** the shipped build has it. The session does not say what was left out; `cineris ext list` finds the skills again and lists them, and those left out with why (since the step's third pull request, "As built in step 28: managing extensions").
- **Reading the user's own skill is not asked about, when the user chooses so** (`permissions.read_skill_folders`, the user's own setting, off by default: the owner's answer, [steps/28/answered.md](../steps/28/answered.md), "The owner's answers"; narrowed by the maintainers). While it is on, the folder of each skill found in the home directory's roots, apart from the workspace (neither within the other) and neither the home directory nor a folder that holds it, is given to the session as a session rule that allows reading it and everything below it, set when the skills are found, before the first turn may start ([06-permissions-and-sandbox.md](06-permissions-and-sandbox.md), "A user's own skill folder may be read unasked"). A project's skills, and a user's in or around the workspace, give none: the workspace's reads stay as they were. Reads only, and a `deny` still wins; **a file in the folder that looks like a secret is read unasked.** A folder that is a link out of its root is not found and has none, nor has a skill in a root `compat.skills` leaves out. At each turn's start that finds the skills again, the rules follow them: a skill removed, or moved into the workspace, loses its rule, one added gains one, and one the user revoked is not given again.

### Tier 3: hooks

A hook runs when an event matches. It is either a command line or a function in an extension script.

```toml
[hooks.format-after-edit]
event   = "tool.after"
tools   = ["edit", "write"]
command = ["cargo", "fmt", "--", "{path}"]
observe = true
```

**Events in the first release.**

| Event | When | A hook may |
|---|---|---|
| `session.start` | A session opens. | Add context. |
| `prompt.submit` | The user sends a prompt, before it reaches the model. | Add context. Refuse the prompt with a message. |
| `tool.before` | A tool call has been planned and passed policy, before approval and execution. | Allow, deny, ask the user, or change the arguments. |
| `tool.after` | A tool call finished. | Add a note to the result. |
| `turn.end` | A turn completed or was denied; a stopped turn's do not start. | Observe. Add a notice for the next turn. |
| `compaction.before` | Before a summary is requested. | Add instructions for the summary. |
| `session.end` | The session closes. | Observe. |

The set is small on purpose. Every event is a compatibility promise, and both reference harnesses show how large an event list grows when adding is free.

**Contract, the same for both forms.**

- **Input.** One JSON object: `event`, `session_id`, `turn_id`, `workspace`, and the event's own fields: for `prompt.submit`, `prompt` (its text) and `delivery` when it was sent while a turn ran; for `tool.before`, `tool`, `call_id`, `arguments` (as the model wrote them) and `plan` (the plan in one line); for `tool.after`, the same with `arguments` those it ran with, and `result`, `{outcome, content}`; for `turn.end`, `outcome` and `error` (a code) when it ended with one; for `compaction.before`, `trigger` (`manual`, `threshold`, `overflow` or `background`) and `focus` when the user gave one. A command receives it on standard input. A script function receives it as its argument.
- **Output.** Nothing, or one object.

| Field | Meaning |
|---|---|
| `decision` | For `tool.before`: `allow`, `deny` or `ask`; for `prompt.submit`: `allow` or `deny`. Absent means no opinion. |
| `reason` | Shown to the user, and to the model when the decision is `deny`. |
| `arguments` | For `tool.before`: replacement arguments. They are validated, re-planned and re-checked by policy, and the change is shown to the user. |
| `context` | Text appended to the conversation as a notice, labelled as coming from the hook, on every event but `tool.before` and `session.end`. Capped at 8 KiB. |

**The answer is read by its event's contract, strictly:** `tool.before` takes `decision` (`allow`, `deny`, `ask`), `reason` and `arguments`; `prompt.submit` takes `decision` (`allow`, `deny`), `reason` and `context`; `tool.after`, `turn.end`, `compaction.before` and `session.start` take `context` alone, and `session.end` nothing. Anything else is a failure, a field given twice at any depth included. An answer of `null`, or none, is no opinion. `reason` and `context` are cut at 8 KiB, and what acts unseen in them is written as escapes.

- **Failure and timeout.** A gating hook that fails or times out counts as `deny`, with the failure shown; on the events that only add (`tool.after`, `turn.end`, `compaction.before`) a hook that fails is shown to the user and adds nothing. **A hook's time starts when it is asked,** so a script hook that waits for its extension's runtime spends its own time. A hook marked `observe = true` cannot decide anything, and its failure is logged and ignored. Default timeouts: 5 s for a hook that is waited for, 60 s for observers.
- **A script hook's host calls put no question** (since step 28): a call the permission engine would ask about is refused, the script's error saying that a hook may not put a question and naming the rule that would allow it, so a hook runs only what the engine allows outright. At `supervised`, where a program is asked about unless a rule allows its line, a gating hook whose `cineris.exec("npm", ["test"])` is refused throws unless it catches the error, and a hook that throws fails, which refuses the call or prompt it gates: allow the line with a rule of the user's (`[[permissions.rules]]`, `effect = "exec"`, `match = "npm test"`, `action = "allow"`) for the hook to run it. **On Windows, and in a session whose shell is PowerShell or `cmd`, a hook cannot run a line the engine reads as only reading** (`git status`, `cat notes.txt`), and no rule changes that: there the line's first word may be the shell's own command or alias, or the program Windows' own lookup finds, so the program that runs may be another, and the engine marks the line as only reading whatever the rules say. The refusal says so and names no rule; a hook command can run it, the user's own running where the engine would ask ([a-hook-cannot-run-a-line-read-as-only-reading-where-another-program-may-run](../outstanding/a-hook-cannot-run-a-line-read-as-only-reading-where-another-program-may-run.md)). A line that names a protected path, or a file that looks like it holds secrets, is asked about whatever the rules say, so no hook runs it. `cineris.ask` is refused in a hook.
- **A script hook's program has no write root,** whatever the manifest's `write` lists: only a tool's call is given the manifest's write roots, a hook's and a command's none (a command's since the step's third pull request), and a hook's `cineris.fs.write` is refused. A hook that needs to write is a hook command with `write = true`.
- **Several hooks on one event** run concurrently. Decisions combine as `deny` over `ask` over `allow`. Argument changes apply only if exactly one hook proposes one; two that both propose one refuse the call. The outcome does not depend on order.
- **`{path}`-style placeholders** in a `command` are filled as separate arguments. They are never interpolated into a shell string. Hook commands run in the sandbox where it enforces ([06-permissions-and-sandbox.md](06-permissions-and-sandbox.md)), and as they are where it does not.

**As built in step 28: hook commands** (`cineris_ext::hook`, the core's `ext::hooks`, `ext::hook_command` and `ext::hook_points`; [steps/28/parts/pr2b1-hooks.md](../steps/28/parts/pr2b1-hooks.md)).

- **The entry.** `[hooks.<name>]` has `event`, `tools` (tool events only: a name, `source/name` or `source/*`, at most 64; a `tool_call` is matched by `tool_call` and by the `source/tool` it names), `command`, `observe`, `timeout`, `write`, `network` and `enabled`, each taking effect at the next session. The section is enforced: an unknown key, a wrong type, or a time past ten minutes refuses the file. The user's layers merge as any setting's do. A project's hooks (its shared file's keys under its local file's) are read apart and never merged with the user's; each waits for the project's trust and its own approval. One with the name of one of the user's (ASCII case aside) is refused and said, and a managed lock on a hook, or on any key of its entry, keeps the project's hook of that name out. A profile may not hold a hook. The name follows the registry's rules. The program is a bare name or an absolute path, as `cineris.exec`'s. Placeholders are whole arguments: `--file={path}`, a `{…}` that is none of the four, and `{path}` or `{tool}` on an event that is not a tool's each refuse the entry. There are at most 256 arguments. An entry that does not compile is refused with its reason and its event kept, so that a refused gate fails closed where it would have run.
- **`{path}`** is each file within the workspace (judged by place) that a `read` or `write` effect of the call's plan names, resolved, in the system's plain form (never `\\?\`), once each, at most 64; a folder, or a file outside the workspace, never fills it. **An entry that uses `{path}` does not run for a call with no such file, and counts as no opinion** (since the maintainers settled it: `find {path} -delete` must not become `find -delete`): an entry that wants to gate every call filters its `tools` and does not rely on `{path}`, and a gating entry that uses `{path}` with no `tools` filter is warned of once, as the session opens, since it will not see a shell command. `{tool}` has a tool name's shape and never begins with `-`.
- **The start** is `cineris.exec`'s own (`ext::exec::run`): the same lookup, Windows quoting and `cmd.exe` line, environment, launcher, looks at the protected paths, with the put-back of what a confined start changed, and runner. Its decision is the permission engine's, of an `exec` of the expanded line in the workspace (and `network` with `network = true`), taken once, and never a question. Allow runs it. Deny or stop refuses it. Ask runs the user's own hook and not a project's. A managed `ask` rule among the reasons refuses every hook (the owner's answer, [steps/28/answered.md](../steps/28/answered.md)). A line the engine reads as only reading counts as an ask where the program that runs may be another (PowerShell, `cmd`, Windows). **The hook runs with the user's environment, as the project's checks do:** the shell's, less the providers' keys and `shell.env_remove`, so any tokens in it (`GITHUB_TOKEN`, a cloud's keys) are a hook's too; it reads what the session's commands may read, and writes only the session's temporary folder unless its entry says `write = true` (the workspace), and never at `read-only`. Hooks with a write root run one at a time. At most 8 runs of hooks that are waited for run at once, and as many observers, in pools apart, so that observers never keep a gate from starting. The wait for any of these is within the hook's own time, and a run let go while it waits starts nothing. At `read-only` a hook has no write root, which binds only where the sandbox enforces: where nothing confines commands, a user's `write = true` hook that the engine lets run still writes as the user (the owner's answer lets a user's hook run where the engine would ask). Its time is on the session's clock, and its process tree is killed when the time is up or the loop drops it. It has failed when it is refused, does not start, runs past its time, exits with anything but 0, writes more than 1 MiB, or answers outside the contract (at most 64 KiB).
- **A hook's stop is never lost:** a protected change a hook made, on any event and from an observer too, is told to the user at once, and the next prompt is refused once and given back. One made by a hook of no turn (`session.start`'s) also stops the turn running then, if one is; one made late by an earlier turn's hook leaves the running turn going, and refuses the next prompt. **A hook of a turn already stopped does not start,** and is no stop of its own: it has failed, its turn stopped, so a stopped turn's `turn.end` hooks do not start.
- **What a `write = true` hook writes is not recorded in the round's checkpoint,** so undo does not put it back, and the model's view of a file a hook rewrote is stale until it reads it again.
- **The core's seam** is one snapshot, settled as the session opens: a refused entry of the user's, and a trusted project's hook changed since it was approved, each stay on their event as a hook whose run fails, so that `wants` is false only when no hook in any state would match. **A project's entry nobody approved holds no gate:** an untrusted project's entries are nothing to its session and none is told; a trusted project's refused entries, its hook that takes one of the user's names included, are told once and are on no event. Each run is a task the session keeps; a waited `turn.end` hook has at most four runs going. `session.start`'s hooks are waited for before the first turn, their context a notice labelled as the hook's; its observers run beside the session under its token. **No run outlives its session:** the close stops what still runs under the session's token and waits for every run, then gives the `session.end` hooks 5 s, then makes its look. One bounded exception, since the script hooks: an extension's runtime start that a run let go leaves to go on, which may outlive the close by its evaluation time and grace, evaluating only, answering no host call, and counting toward the cap of threads left running while it does; its thread is told to stop whenever the start is dropped before it ends, the core's runtime ending included ("As built in step 28: script hooks"). The core's shutdown closes its sessions together.

**As built in step 28: script hooks** (the core's `ext::script_hooks`; `cineris-ext`'s `engine`, `CallContext::asked`; [steps/28/parts/pr2b2-script-hooks.md](../steps/28/parts/pr2b2-script-hooks.md)).

- **On their events.** Each hook a loaded extension's script registered with `cineris.on`, on an event its manifest's `capabilities.hooks` lists (as the registration cache keeps what it registered), is one of the session's hooks beside the hook commands, from when the extension is loaded (as the session's finding settles, or at a turn's start) until it is withdrawn: an extension's hooks are its own, on their events only while it is loaded as it was approved, a project's only while the project is trusted and the extension pinned as it is. One whose `tools` cannot be read as a filter is on every call, and fails.
- **Its gates fail closed.** An extension's hooks leave their events with it only when the user turns it off (`cineris ext disable <name>`, which writes `[extensions.<name>] enabled = false`), the project is no longer trusted, its pin is taken away (`cineris ext remove <name>` for the user's own), or, for a project's, a folder of the user's takes its name, so that the project's is not used. One that stands approved and is changed, unreadable, removed from where it was approved, or cannot be loaded (its capabilities do not compile, the registry refuses it) keeps its `tool.before` and `prompt.submit` hooks on their events as failing gates, made from what it registered at the hash approved (the registration cache, or what the session saw it register when it loaded it, gating hooks or none, kept for the session, so that a gate at a hash the cache no longer keeps, one approved for the run, which the cache prunes, holds what it registered). Where that is known nowhere (not in the cache, a cache set aside, never loaded in the session), a changed extension holds both gates, `tool.before` and `prompt.submit`, on every call and prompt: its manifest as found is the change's, and says nothing of what was approved. One whose first registration failed holds a gate on each gating event its manifest lists: that manifest is the approved one. One removed from where it was approved, and still pinned, says that its folder is gone, and that if you removed it you take its approval away with `cineris ext remove <name>`, or turn it off with `cineris ext disable <name>`, which sets `[extensions.<name>] enabled = false` in your configuration, since a deletion may be an unconfined program's, taking a gate away; a project's says to trust the project again without it, or to take its trust away. The way out of the user's own names the commands that manage it (since the step's third pull request): `cineris ext add <folder>` (the folder under `~` where it is known), `cineris ext disable <name>` beside the table it writes, and, for one whose folder is gone, `cineris ext remove <name>`. Under `--trust-project` the way out names `cineris permissions trust`, not the trust question, which is not shown. The way out names an extension's table as TOML reads it, a name that is not a bare key quoted (`[extensions."acme.lint"]`). Each refusal names the extension, why, and the way out; the user is told once a session, in words. Its observers, and its hooks on the events that only add, leave with it. Withdrawn, an extension's runs still going are stopped. The core's own operations (approvals, `/permissions`, `session/new`, `config/reload`, the command line) are no hook points, so turning an extension off stays open while its gates hold; a prompt, a slash command sent as one included, is refused by a held `prompt.submit` gate.
- **A store of approvals that cannot be read keeps the gates of what the session loaded.** While `pins.toml` cannot be read, each of the user's extensions found is not loaded; while `trust.toml` cannot be read, so is each of a trusted project's, but one a yes of this session's own approved. An extension the session loaded keeps the gating hooks it saw it register, on their events, failing, whatever it is found as now, or if it is gone: what an extension registered is kept for the session by where it comes from and its name, not only by the hash it was loaded at. Of the user's, one the session never loaded holds the gates of its approved versions as the registration cache keeps them: pruned as it is to the hashes pinned when it was last written, the cache stands in for the store, and only ever adds: since an entry names its extension and does not say whose (a project's of the same name may be among them), such an extension holds the gating hooks of the cache's entries of its name, together, beside a gate on each gating event its manifest as found lists. An extension approved that could not be loaded, or whose first registration failed, is known by what it registered, or by the gating events its approved manifest lists, as one loaded is, and so is one whose gate the session held from the registration the cache keeps at its pin (one changed or removed before the session). What the session knows of an extension is the latest it knew, by where it comes from and its name; one whose pin, or its project's trust, is taken away is forgotten, so that a store that cannot be read later gives it no gate back. **Of a project's, one the session never loaded holds nothing: no repository gates a session by itself** (the owner's answer, as the first part settled for a project's hook entries). The user is told once, with the store's file under `~` and the fix: repair or remove it, then approve the extensions again (`cineris ext add <folder>`), or trust the project again (`cineris permissions trust`); for the trust store, that the project's extensions are not loaded until it is fixed, and that those the session had loaded keep their gates. A project not trusted as the session opened has nothing of it looked at, and its store is not read.
- **Its name** is the extension's, `hook.` and the event (`tracker/hook.tool.before`), the second and later of one extension on one event numbered from 2 (`tracker/hook.tool.before.2`), each part a name by the registry's rules. Its host calls are decided under it, so a rule about the extension (`deny ext tracker/*`) reaches them. No tool or command of an extension may take a name that begins with `hook.` or `command.`, in any case: those are the harness's own.
- **Its run** is a call of the extension's runtime, one of the runtime's own queue, its function given the event's object. `undefined` or `null` is no opinion; anything else, at most 64 KiB of JSON, is the answer, read by the event's contract: the loop's reading for its five events, and for `session.start` the core's, as for a hook command. The promises a hook settled run before its answer is taken, so none runs in the extension's next call, and a host call it left going is not made once its call has ended, unless it only tells (`log`, `notify`, `progress`). A hook's `cineris.state` is its extension's, keyed by where the extension comes from and its name, as its tool's is: a hook reads what the extension's tool kept, and a `session.end` hook may keep a `project` value as the session closes.
- **Its time starts when it is asked:** the engine's deadline of a hook's call runs from then, so a hook that waits for its turn behind the extension's tool or another of its hooks spends its own time; one still waiting when its time is up is withdrawn before it starts, and the runtime's other call goes on; one running is stopped as any call past its time is, its runtime with it. A waited-for `turn.end` hook has at most four runs going, as a hook command has. An extension's observers and its gates share its one runtime, so a long observer of an extension can make its own gate wait, and fail for the wait: the pools apart that keep observers from holding up a gate are the session's, not a runtime's. An extension that observes at length keeps its observers short, or its gates in an extension of their own.
- **Its run is a task the session keeps,** under a token of its extension's within the session's, cancelled when the extension is withdrawn: the engine's stop of a call past its time, with its grace for the thread, is made whatever became of the loop's wait, and no run outlives its session. Dropped, its future stops the run, polled or not: a call not started is withdrawn, and one let go before it got that far starts no runtime, nor waits for one that is starting. Its runtime's start is not: a run let go leaves the start to go on, and nothing waits for it, not the session's close nor the core's shutdown. It runs on, unawaited, up to its own evaluation time, and is left running and counted, its hash refused for the process, only past that time and its grace, as any start is; a start whose future is dropped before it ends (the core's runtime gone) tells its thread to stop, as a call's does, so that a main module in a loop is interrupted. A first evaluation answers no host call, so a start that outlives its session does nothing but evaluate. While it evaluates, a start let go counts toward the cap of four threads left running (below); a later session that starts the same extension meanwhile gets a runtime of its own.
- **Starts let go count toward the cap.** A start nobody waits for any more (its session closed while it evaluated) counts toward the cap of four threads left running for as long as it evaluates (only once its start has begun: a run let go before its extension's start began counts nothing unless that start then runs): released when it ends within its time, the one count of a thread left running if it is abandoned, never two. Past the cap no extension starts until one is released, which it is within the evaluation time: a hook of one that cannot start fails, its gates refusing what they are on, and the user is told once, with the reason and that it clears within the evaluation time.
- **A hook whose extension's runtime cannot start fails, a gate closed:** a folder changed since it was loaded, a folder on the way now a link, a thread of the extension left running, a runtime torn down or disabled. The failure says why and what approves the extension again or turns it off, and the call or prompt it gates is refused. One the engine refuses for the rest of the process (a thread of it was left running) says so whole, a tool's call as a hook: fix it and approve the fix, turn it off (`cineris ext disable <name>`, which sets `[extensions.<name>] enabled = false`), or start Cineris again; only a new hash or a new process starts it. Where too many extensions' threads were left running, this process starts none, and the way out is to turn it off, or start Cineris again.
- **A stopped turn's hooks do not start,** a script's as a hook command's: one asked after its turn stopped has failed, and is no stop of its own. A hook's host call in a stopped turn is refused with the stop before anything of it runs, and is no stop of its own: nothing says it was stopped by the look, and no prompt is held back. The policy keeps the latest sixteen stopped turns, so a hook still running for one is refused after a later turn is stopped. A hook's program has no write root, so no look is made of it; what it writes where the sandbox does not enforce is not recorded in the round's checkpoint, as a hook command's writes are not. A turn the loop's own stop ends (a call nobody can be asked about, with `fail_on_denial`) counts as stopped for its hooks too: a hook of it still running has its host calls refused with the stop, and its later hooks, a hook command's included, do not start. The round's own calls stay the loop's to stop: one written before the refused call, and allowed, still starts.
- **The session's own events:** the `session.start` hooks of the extensions a session loads as it opens are heard before its first turn, which waits for those that are waited for, each one's context a notice labelled as the hook's; its extensions' `session.end` hooks run as it closes, observed, within the same five seconds as its hook commands'. When the close's five seconds are up, every `session.end` run still going, a script's or a command's, is stopped at once, and all are waited for together. A `session.end` hook, a command's or a script's, is of no turn, so that a `session.start` hook's stop refuses none of them.


### Tier 4: script extensions

An extension is a folder with a manifest and JavaScript.

```
<config dir>/extensions/tracker/
    extension.toml
    main.js
```

**The manifest** says what the extension is and what it may ask the host to do.

```toml
api = 1                         # the version of this format and of the host functions
name = "tracker"
version = "0.1.0"
description = "Issue tracker tools"
main = "main.js"
prompt = "prompt.md"            # optional: text for the system prompt, 4 KiB

[capabilities]                  # each is empty unless given
exec  = ["gh"]                  # programs it may ask the host to run: bare names or absolute paths
exec_network = true             # whether those programs may reach the network
read  = ["**"]                  # workspace paths it may read
write = []                      # workspace paths it may write
net   = []                      # hosts it may contact through the host's fetch
hooks = ["tool.before"]         # the events its script may hook

[limits]                        # optional, within the hard caps
memory = 32                     # MiB, at most 64
time = 120                      # seconds a tool call, at most 600
```

**Read strictly** (since step 28): a key this build does not know, a value of the wrong type, or an `api` it does not know refuses the extension, with the reason. The capabilities are values the harness enforces ([decision 0028](../decisions/0028-enforced-values-fail-closed.md)). The folder holds only regular files and folders, at most 256 files of 1 MiB each and 4 MiB in all: a link of any kind anywhere in it refuses the extension. What the events a script may hook let it see is shown in words when it is approved ("every prompt you send"), since a hook sees the session's content. Since the step's second pull request the manifest also refuses a backtick in a program, a glob or the version, and a program or a glob of more than 256 bytes: each is shown as code in an approval, and a backtick would end the code and let what follows read as the harness's words.

**The script** registers what it contributes.

```js
cineris.tool({
  name: "find_issue",
  description: "Search issues by text",
  input: { type: "object", properties: { query: { type: "string" } },
           required: ["query"], additionalProperties: false },
  readOnly: true,
  async run(args) {
    const r = await cineris.exec("gh", ["issue", "list", "--search", args.query, "--json", "number,title"]);
    if (r.code !== 0) throw new Error(r.stderr);
    return { issues: JSON.parse(r.stdout) };
  },
});

cineris.on("tool.before", { tools: ["edit", "write"] }, (event) => {
  if (event.arguments.path.startsWith("generated/")) {
    return { decision: "deny", reason: "generated files are rebuilt from schema/" };
  }
});
```

**Host functions.** This is the whole surface a script has. There is no file, process, network, timer or module API other than these.

| `cineris.log(...)`, and `console.log`, `info`, `warn`, `error`, `debug` as its names | Writes to the log. | A hundred lines in one call (since step 28), each shown as `notify` is. |

There is no function that returns credentials, reads the session, changes configuration or grants permission. **The manifest is asked first**, in code (`cineris_ext::host::serve`): a call it refuses never reaches the session. Then each call is decided by the permission engine as a call of the extension's tool (`tracker/find_issue`) with the built-in tools' default and an `ext` effect beside its own, so a rule about the extension covers its host calls too, and a question it needs offers only "allow once" and "deny" and keeps no rule (since step 28: a rule kept from it would reach past the extension). A hook's host call puts no question at all: one the engine would ask about is refused ("Tier 3: hooks").

**The runtime.**

| Property | Design |
|---|---|
| Isolation | One runtime per extension. Extensions cannot see each other. |
| Limits | Memory per runtime (default 32 MB, hard cap 64 MB, the manifest's `[limits]` within them). The stack, 256 KiB. Time per call (2 minutes for tools, the hook timeouts for hooks), enforced by the engine's interrupt hook, so a tight loop is stopped, and by the host, which stops waiting. A native function that loops without looking at the interrupt cannot be stopped: its thread is left running when its grace is up, and its extension is not started again in the process (since step 28; past four such threads, none is). A result is at most 1 MiB of JSON. An extension's command is not held to `time`: it has 30 s from when it is asked, whatever the manifest says (since step 28, the maintainers after the early review of the commands). A tool's call runs inside a turn the user can interrupt; a command runs while the user waits at the prompt, inside `turn/start`'s step, before any turn exists. |
| Language | JavaScript modules. Imports resolve only inside the extension's own folder, and are served from the snapshot of it whose hash was approved, never from the disk. Types for the host functions ship as a declaration file for editors. |
| Threading | **One thread per runtime** (since step 28, in place of one thread for all: a script that computes until its time is up never holds up another extension's hook), made the first time something of the extension's is used. **A runtime runs one call at a time,** to its end, and a call's time starts when it starts running, a hook's when it is asked (its wait for its turn is within it, and one still waiting when its time is up is withdrawn before it starts): the interrupt check belongs to the runtime and cannot tell two calls apart. A call's settled promises run before its answer is returned, and a host call it left going is not made once it has ended, unless it only tells, so nothing of one call runs in the next, and a call that has ended no longer stops its runtime. Host functions are asynchronous: a script awaits them, and the core does the work. A thread that does not come back within a grace after its deadline is abandoned, and its runtime counts as torn down. |
| Start-up cost | None. What an extension registers is cached with its hash when it is approved. At start-up the harness reads the cache and knows the tools, commands and hooks without starting the engine. The engine starts the first time something of the extension's is used. |
| Failure | An exception is an error result for that call. A runtime that hits a limit is torn down and recreated on next use. The session is never affected. **A call that never ran** (queued under a runtime torn down before its turn, or stopped as its thread took it) runs nothing of its script and says so (`CallError::NotRun`; since step 28's third pull request, where it said its time ran out or the runtime was gone, or ran with its stop set until the engine's first look at the interrupt): a tool's call is taken once more to a fresh runtime, nothing of it having happened, and a hook's fails, its gate refusing what it gates. |

**Tools from extensions** are reached through `tool_search` and `tool_call` ([05-tools.md](05-tools.md)), so adding one never changes the declared tool list. **An extension's tool always runs alone** (since step 28), whatever its definition says: its script may make a link, and a call beside it would have been decided before the link was there. `readOnly` is shown to the user and decides nothing. Declaring an extension's tool directly from the next context epoch (`expose = "direct"`), and promoting frequently used ones, are left to step 30, which needs the same for MCP; the manifest has no such key until then.

**As built in step 28** (`cineris-ext`; the core's `ext` module; [steps/28/answered.md](../steps/28/answered.md)): the folder's snapshot and hash (`folder`), the manifest (`manifest`), the capabilities compiled for a workspace (`capability`), the host functions' contract and the order they are checked in (`host`), and the engine (`engine`, behind `scripts`). The core registers an approved extension's tools from what it registered when approved (since the step's second pull request, the extensions each session finds itself, below; `CoreOptions::extensions` stays as a test's seam, which hands an extension in with no pin and no registration cache) and serves their host calls. A host call's arguments are bounded by size before the harness takes them, and at most sixteen calls a script awaits wait for their answers at once: the memory they take is the harness's, which the runtime's limit does not count. A path the manifest refuses is refused by the script's own text, and without being resolved where the manifest grants no reading or writing, so a script learns nothing of where a path outside leads. A write or a walk acts only on the path the manifest judged, and a read decided while a person was asked opens its file only if the path still leads there. A host call's "allow once" allows that call alone. A host call that finds its turn stopped ends the script's call, and so does a program whose look at the protected paths stops the turn: a script that catches the error does not go on. A program decided after a person was asked is given only what is left of the call's time, and what it did is looked at whatever ended it (its own time, the call's cancellation or its deadline). The look at what a program changed in the workspace runs the harness's git inside the sandbox wherever the program's launcher confined it, `unrestricted` included: the program may have written the repository's configuration, which can name a program for git to run (since the third security fix every look's git does so, wherever the sandbox enforces). What a program with a write root changed among the protected paths is put back at once, never through a link, and its call and the turn stop (the third security fix).

**As built in step 28's second pull request: the extensions a session finds and loads** (`cineris-ext`'s `discover` and `cache`; `cineris-core`'s `ext::found`; [steps/28/parts/pr2a1-found.md](../steps/28/parts/pr2a1-found.md)).

- **Where extensions are found** (`cineris_ext::discover`).
  An extension is a folder directly under one of two roots, the user's `<config dir>/extensions/` and the project's `.cineris/extensions/`, whose manifest gives the folder's own name: one that gives another is left out with both names, and a file beside the folders, or a folder whose name begins with `.`, is passed over.
  Each folder is read whole into the snapshot whose hash is pinned, and looked at again, itself, after the read: one swapped for a link while it was read is left out (since the full review of step 28).
  Since the step's third pull request the read goes through handles below the folder (`Snapshot::read`): every name in it is opened relative to the handle of the folder it is in, and a folder in it swapped for a link while it is read is refused where it is met, never read through. A name Windows cannot hold, or holds as another, refuses the extension on every system (`folder::unportable`: one that ends in a dot or a space, one with a control character or any of `< > : " | ? * \`, and a device's name, `con`, `prn`, `aux`, `nul`, `conin$`, `conout$`, `com0` to `com9` and `lpt0` to `lpt9` with `¹`, `²` and `³` among the digits, with any extension), so that a folder read and written again is the same folder everywhere; and each folder's listing is taken to one name past what is left of the 1,024 entries, folders and files together, that an extension's folder may hold, so that a folder of a great many names is refused without its whole listing read.
  A root is found through the session's path resolver and judged where it leads, compared by place: the user's may be a link, and is followed; the project's must lead inside the workspace, so a `.cineris` or a `.cineris/extensions` that is a link out of it gives nothing and says so; an extension's folder reached through a link is refused, as a link inside one is; the same folder given as two roots is looked in once. **A root is held open where it was resolved to,** as a root of skills is (since the narrow re-check of the managing part): the project's opened from the workspace down, no name followed, the user's by its path, its own name not followed; it is listed through its handle, and each extension's folder is opened relative to it, its own name not followed, and read through handles below it, so that a folder above the root swapped for a link (a project's `.cineris` to the user's configuration directory) is never read through. The root is opened again after its folders are read and compared by its identity; one whose place now leads through a link or to another folder has its extensions left out, said, and is not listed whole, and so has one that meets a link on the way when it is first opened. The trust question shows, and pins, the snapshot discovery read, so it shows the folder in the root.
  **A root that is not there costs one look,** and the resolver is not asked: the user's, given as an absolute path, is looked at as it is, and the project's one name at a time from the workspace's real location, without following a link (two looks for a workspace whose `.cineris` has no `extensions`).
  That is 1.2 µs a session with no extension on the reference machine, against 21 µs for resolving both roots (a release build, on an otherwise idle machine).
  At most 1,024 entries of a root are listed, and the rest of it is not looked at, which is said; of those, at most 64 folders are read, the first by name, and none once 16 MiB have been read from the root (since the full review of step 28; every byte read counts, of a folder left out after its read too, and a file over its cap is refused by its length, unread, since the fresh review and its re-check); the rest are left out, counted.
  The user's `tracker` and the project's `tracker` are both found, two extensions kept apart by where they come from.
  Within one source, extensions whose names differ only in case (`Tracker` and `tracker`, in one root or in two roots of one source) are all refused, on every system, each left out naming the others: on Windows they are one name and would share what an extension keeps, and none is kept, so that nothing depends on which was listed first.
  Every refusal names the folder, the project's relative to the workspace and the user's under `~`, as code it cannot end, since a folder's name comes from a repository: every character that acts unseen is written as an escape, and a backtick or a `\` has a `\` before it (`cineris_base::in_code`, which every question and notice uses for a path or a name it shows as code, since the full review of step 28).
  Discovery reads folders, and runs on the blocking pool, off the start-up path.
- **The registration cache** (`cineris_ext::cache`) is `<state dir>/extensions/registered.json`, `{"version": 1, "entries": {"<content hash>": {"name", "api", "tools", "commands", "hooks", "prompt"}}}`: what each approved extension's script registered, under the hash of its folder, with the text of its prompt file, so that a session knows them without starting the engine.
  **It is read strictly** ([decision 0028](../decisions/0028-enforced-values-fail-closed.md)): a field this build does not know, a value of the wrong type, a key that is not a content hash or that is given twice, another `version`, more than 1,024 entries, an entry a live runtime could not have registered, or a file over 16 MiB or that is not a regular file sets the whole file aside.
  **An entry is checked by the code a script's registration meets** (`cineris_ext::registration`): each tool's and command's name (1 to 64 of ASCII letters, digits, `_`, `-` and `.`), description (2 KiB, nothing in it that acts unseen) and schema (an object of 16 KiB as JSON, every text of it shown as written); a command's arguments (16, each a name); a hook's event, its filter (64 entries, each a tool's name or `source/*` of at most 129 bytes) and its time (1 ms to 10 minutes); 64 tools, 32 commands and 32 hooks, and no tool or command name twice; and the entry's own name, an extension's, and its prompt, of 4 KiB.
  Whether its hooks are on events the manifest's `capabilities.hooks` lists cannot be asked as the file is read, since the file holds no manifest: `Entry::fits` asks it, with the entry's name, its `api` and its prompt's text, against the manifest and the snapshot of the extension it is taken for.
  A session takes an entry only when it fits; one that does not is missing, and the extension is registered again. A project's extension that the trust question read is held with no bytes of its folder but its prompt file, as the question read it, which the entry is checked against.
  A file set aside is read as an empty cache, and moved to `registered.json.set-aside` while it is still the file that was read, so that a cache another session has just written is not moved for what the one before it held; one written in the moment between the look and the move is seen to be another file, and put back.
  A link at the file's name, a folder, or anything else that is not a regular file, is moved aside as it is (a link is moved, never what it leads to): left there, no write could replace it, and every session would register every approved extension again.
  A missing file is an empty cache.
  A file that cannot be opened or read for a reason that is not what it holds (too many files open, an I/O error, on Windows a file being deleted) is set aside too, though it may be good: it fails closed, and every approved extension is registered again.
  The file is written owner-only and atomically, never through a link at its name and never past what it would read: a write that would make a file this build sets aside writes nothing.
  Two sessions that write it at once may lose one entry; that fails closed too, since the next session registers that extension again, and no entry can be wrong, since each is keyed by the hash of what registered it.
- **What a session looks in.**
  The user's folder, given as the configuration directory is (the session's path resolver takes `~`, a relative path, `..` and a link), and the project's, under the workspace's real location, only while the project is trusted (in the trust store, or for the run): a session of a project that is not trusted does not look in it.
  Each extension found has its definition (kind `extension`, its name, the hash of its folder) judged against its pin: the user's in `pins.toml`, a project's in the project's entry of `trust.toml`, or, after a yes the store could not keep, the hashes that question showed, for that session alone.

| Found | Its pin | In the session |
|---|---|---|
| The user's | with its hash | loaded |
| The user's | with another hash, or none | not loaded; the session says so, with `cineris ext add <folder>`, the folder under `~`; its gating hooks stay on their events, failing, while its pin stands ("As built in step 28: script hooks"), and `cineris ext remove <name>` takes the pin away |
| The user's, `pins.toml` unreadable | any | not loaded; the session says the store is why; one the session loaded keeps the gates it registered, one it never loaded holds those of the cache's entries of its name beside a gate on each gating event its manifest lists ("As built in step 28: script hooks") |
| The user's, `pins.toml` not counting with the session's key (no key open, of version 1 or reset, or not signed by the key) | any | as when `pins.toml` cannot be read; the session says why ("The user's own pins, signed", below) |
| The user's, `[extensions.<name>] enabled = false` (`cineris ext disable <name>` writes it) | any | not loaded, and nothing is said or asked |
| A project's | with its hash | loaded |
| A project's | with another hash, or none | not loaded; the session says so, with the trust question (`cineris permissions trust` under `--trust-project`); its gating hooks stay on their events, failing, while its pin stands ("As built in step 28: script hooks") |

- **`cineris ext add` pins a user's own extension** (since the step's third pull request, "As built in step 28: managing extensions" below): it is the one command that writes a pin into `pins.toml`, and `cineris ext remove` the one that takes one away.
- **The user's own pins, signed** (the signed approvals step; [06-permissions-and-sandbox.md](06-permissions-and-sandbox.md), "Project trust", "As built in the signed approvals step").
  `pins.toml` (version 2) is signed whole, a revision and every pin, by the key the person's password makes, and a session checks it with the key the person opened their approvals with in its core.
  Pins that do not count with it are taken as a pin store that cannot be read: the approvals are not open (a headless run, a server nobody opened, Esc at the password), the file is of version 1 or was reset, or it is not signed by that key (another key's set, a pin added or taken out by hand).
  Each of the user's extensions found is then not loaded, and holds the gates of the cache's entries of its name beside a gate on each gating event its manifest lists; the session says why, once ("your approvals are not open in this session"; "written by an older version of Cineris, or before your password was reset: asked again"; "not signed by your key: changed by something other than Cineris"). So a pin taken out by hand lifts no gate.
  A project's entry in `trust.toml` that does not count holds the gates of the extensions it pins, from the cache's entry at the hash pinned or both gates, though nothing of the project is looked at; a project with no entry holds nothing.
  `cineris ext add` and `cineris ext remove` of a pinned extension are the person's signed changes of the whole set: proposed against the pins as they stand with the person's key, signed at the yes, and committed only over the file as it was proposed against (`Core::add_extension` and `remove_extension` take the key). A removal is signed because a pin can hold a gate.
- **A gate is the person's own check, not a bound on the model.**
  Turning an extension off is a write of the user's configuration (`cineris ext disable`), which a program of the model's can make where nothing confines it, and which no signature covers until the user's configuration is pinned (the signed approvals step's third pull request). An extension's gate holds against what a session's model asks through the harness; it does not hold against what the model's unconfined programs write.
  A gate meant to bind the model belongs in a deny rule of the pinned configuration or the managed file.
- **A name is the user's** whenever the user's folder of extensions holds a folder of that name, compared with ASCII's case folded, whether that folder could be used or was left out (a link in it, a manifest refused): a user's extension left out does not free its name for a project's, to which the user's rules about it would apply.
  A user's folder that is there and could not be opened or listed whole (a file, a link to nothing, a folder closed to the user) takes every name.
- **Everything is decided before anything runs.**
  The folders, the pins, the trust store and the registration cache are read, and every standing decided, before any script is evaluated.
  An approved extension's tools, commands, hooks and prompt text are taken from the cache by its hash, with no engine started.
  One the cache misses fails closed: the snapshot whose hash was compared with the pin is evaluated once in a throwaway runtime, the session says so ("Registering the extension …"), what it registered is written to the cache, and it is loaded.
  A project's extension the trust question listed is read again to be evaluated, and evaluated only when its folder's hash is still the one approved; otherwise the session says it changed.
  An evaluation that fails is said once, what the script threw escaped, and the extension is not evaluated again in the session until its folder changes.
  No runtime is made for the session before an extension's first call.
  What discovery left out is said, with its reason.
  A cache set aside is said once, with its files under `~`, and every approved extension is registered again.
  A session that found an approved extension then prunes the cache of the hashes no pin names, the user's and every trusted project's, since projects share it, and of nothing when a store cannot be read.
- **Where it runs, and what waits.**
  On a task the core spawns once the session's loop runs, off the path that opens the session and so after the interactive application's first frame: the reads and writes on the blocking pool, each evaluation on a thread of its own.
  The first turn waits for the extensions' tools (`turn/start` waits before it hands its prompt to the loop, as it waits for the look at the configuration's files), not for the cache, which is written and pruned after.
  A wait of more than three seconds, on the session's timer, is said once, and goes on: no turn starts while an approved extension's registration is missing, and each evaluation is bounded by the engine's own time (since the full review of step 28).
  Once the extensions are found, a first turn that waits for the `session.start` hooks of the session's extensions says that instead: "This turn waits for the `session.start` hooks of the session's extensions, which are heard before its first turn. It starts once each has answered, or its time is up."
  **A finding that ends before it is done** (its task stopped by a panic) fails, and does not count as settled: the first turn's start, every later one, and a compaction's are refused with `extensions_not_settled` and the reason ([11-rpc-protocol.md](11-rpc-protocol.md)), so that none waits for ever, nor starts as if the extensions were found.
  A turn's start is one step with the look at what the extensions were found in, one at a time in a session, so a look never runs beside another client's turn; a prompt queued behind a running turn is not looked at again, since its turn starts from the loop.
  A session closed meanwhile ends the task, and so does the core's end.
- **Section 7** is each loaded extension's `prompt` text as the registration cache holds it, one a name and only of an extension the registry took; an extension withdrawn leaves the prompt's snapshot, its text with its source of tools, before its tools leave the registry ([07-sessions-and-context.md](07-sessions-and-context.md), "As built in step 28").
- **Measured** (release build, an otherwise idle reference machine, 40 runs): a cache miss holds the first turn for one evaluation, a median of 0.34 ms for an extension of one tool, 0.50 ms of 16 and 0.98 ms of 64 (95th: 0.41, 0.58, 1.04 ms); misses are registered one after another.
  With no extension nothing of one is read but the stores of the pins and of the trust, which a pinned extension that is gone, and one that cannot be judged, need: the session's finding costs 4.6 µs with both stores absent and 10.4 µs with both present (a release build, an otherwise idle reference machine, medians of 400; `ext::found::pipeline::tests::perf_the_finding_with_no_extension`, ignored), of which the read of each store costs 0.42 and 0.30 µs where it is absent (a failed look, no parse) and 3.2 and 2.7 µs where it is present: about 0.7 and 6 µs more than before step 28's script hooks, which read neither with no extension (an estimate, the two reads taken away). The first turn waits for it.
  Beside the stores, the finding makes one look at the user's folder, and the trust question's look costs, for a client that answers it, one at the project's, two with a `.cineris` and no `extensions` in it.
  With extensions, none is read on the path that opens the session but a project's, which the trust question reads once for a client that answers it, and which the session then takes on rather than reading it again; of the user's, only when the project has an extension, the question takes the folder's names, with the places within its extensions looked at (`read_dir` and `lstat`, up to 4,096, as the session's finding counts them) and none of their files read.
  A crafted folder of extensions of 64 folders of 1,023 empty folders each costs the trust question's look 25 ms, a trusted session's opening 26 ms, its first turn 16 ms and a later turn's look 2.6 ms (a release build, an otherwise idle reference machine; `extensions_review::perf_a_crafted_folder_of_extensions_is_looked_at_within_its_bounds`, which fails past a second each).
  With three typical extensions of a few KiB each (a release build, an otherwise idle reference machine, medians of 30; since the full review of step 28): opening a session costs what it does with none, 0.7 ms, with the user's, which are read after it; the trust question's look and read of three of a project's adds 0.14 ms (0.93 against 0.79 ms), and it keeps of each only its hash, manifest, shown text and prompt file; the first turn, 10 to 12 ms on that machine with them or without, shows no cost of finding and loading them.

- **`cineris ext inspect <name>`** shows each extension of the name (the user's and a project's may share one): its folder, or that it is gone; the hash of its folder read whole; its pin and when it was pinned; its standing; what it registered; and what its manifest lets it do, in the approval's words. - **`cineris ext add <path>`** is the user's own approval. A leading `~` (alone, or before a `/`, or a `\` on Windows) is the home directory: PowerShell and `cmd` do not expand it for a program.
  - **It reads the folder once into a snapshot through handles that follow no link** (`Snapshot::read_unfollowed`, on `cineris_sandbox::unfollowed`). The folder is opened as its path says: the names before its last followed as the system follows them (the person named the path), and its last, a trailing separator or `.` taken off first, not followed. Every name in it is opened relative to the handle of the folder it is in: on Linux with `openat` and `O_NOFOLLOW`, with `O_DIRECTORY` for a folder, and with `O_NONBLOCK` and `O_NOCTTY` for a file, so that a FIFO or a terminal opens at once and is refused as no file; on Windows with `NtCreateFile` relative to the folder's handle and `FILE_OPEN_REPARSE_POINT`, every handle held without sharing deletion, so that nothing held can be renamed or removed while the tree is read, and a placeholder (a cloud file, a file the system compressed) opened a second time in the ordinary way relative to the same folder, while the first handle keeps the name from being swapped, and checked to be the same file. Each folder is listed through its own handle (`fdopendir` on Linux, `GetFileInformationByHandleEx` on Windows). A name that is empty, `.`, `..`, or holds a separator or a NUL (on Windows a `:` too, which names a stream) is refused before the system is asked.
    A link at any name, the folder's own included, refuses it (one at its own name with "name the folder it leads to"), and nothing outside the folder is read through one. The caps and the names' rules are discovery's (above), and the manifest is read strictly.
  - **It is evaluated before the question** (the early review of the third pull request, M2): once, in a throwaway runtime on a thread of the command's own process, after `cineris_ext::engine::forget_abandoned`, so that an extension refused in a process for a thread left running would start again on this approval (in `cineris ext add`'s own process nothing of one has run before). A script that cannot be evaluated is refused, and nothing is asked, written or pinned.
  - **It shows that snapshot:** its name, where it was read from, and its hash; its manifest in the approval's words, its programs' confinement as a session in this workspace would have it, and, where they are confined here, that this holds where a session's sandbox is on, since a user's extension is loaded in every workspace and the user's configuration or a trusted project can turn the sandbox off (`found::CONFINED_WHERE_ON`; the early review's M3), and `net = ["*"]` as "any host on the internet, including addresses on your own network that have public addresses"; each tool and command its script registered, with its author's description, and the whole text it adds to the system prompt, each quoted and escaped as its author's words; every file with its path and size, and their count and total; where it is written, under `~`; what is there that a yes replaces; an earlier approval of another version, which this one takes the place of; a project's extension of the same name, which is then not used; and that the user's configuration turns it off, where it does.
  - **It asks at a terminal,** a yes being `y` or `yes` and anything else, an empty line included, no. **With no terminal to ask at** (standard input or standard output is not one), only `--hash H` approves, and only when `H` is the hash shown (its case and the blanks around it aside); at a terminal a `--hash` given must be the hash shown too, and the question is still asked. A bare yes named nothing, and the hash names what was shown: the owner's answer to the early review of the third pull request, which took `--yes` away ([06-permissions-and-sandbox.md](06-permissions-and-sandbox.md), "The harness's own approving commands"). An extension approved already, and held as shown, does nothing.
  - **On a yes it takes that snapshot, never a second read of the source,** which may be a folder the model or another program can write. What it registered when it was evaluated is kept. Its place is looked at again (the early review's L3): a folder that holds the snapshot is left as it is; anything else is replaced by the snapshot, written into `<config dir>/extensions/<name>` whole or not at all: into a new folder beside it, made exclusively and owner-only, whose name begins with `.` so that no session looks in it, each file created new and synced; then put in place, what was there set aside first and removed after, a link there unlinked and never written through. What an earlier write left beside it (a process stopped between making its folder and putting it in place) is removed first; what was set aside and cannot be removed is said, and left, the new folder in place (the early review's L4). Then it is pinned in `pins.toml`, and its registration kept in the cache: a folder written and not pinned says so, and is not loaded; a registration the cache could not keep is said, and the next session registers it again. Sessions opened after it load it, and a running session at its next turn's start.
  - **What a yes replaces is named in the question:** a folder of another hash at the name, one that cannot be read as an extension, a link or a file. A folder added from where it is kept (`<config dir>/extensions/<name>` itself) is approved in place, and put back as shown if it changed since the read.
- **The names' rules.** The folder is written under the manifest's name, which must be one a session finds on every system (`ext::manage::folder_name_refused`): an extension's name by the registry's rules (1 to 64 of ASCII letters, digits, `_`, `-` and `.`), not beginning with `.` (a folder a session never looks in), not ending with `.` (which Windows takes off), and not a Windows device's name (`con`, `prn`, `aux`, `nul`, `com0` to `com9`, `lpt0` to `lpt9`, with any extension). The registry's own check takes `..` and `.x`: without these rules `..` would have named the configuration directory itself. A name that differs only in case from a folder of the user's is refused, as discovery would refuse both, and so is any name while the user's folder of extensions cannot be listed whole.
- **`cineris ext disable <name>`** writes `[extensions.<name>] enabled = false` into the user's own configuration file (`CINERIS_CONFIG`, or `config.toml` in the configuration directory), for an extension of the user's own, found by its name or pinned.
  - **One that holds gates is asked about first** (the early review's M1): a pinned extension whose registration, as the cache keeps it at the hash found or its pin's, has hooks on a gating event (`tool.before`, `prompt.submit`), or whose registration is not known. The command names those hooks, says that turned off they no longer hold and that what they would refuse goes ahead, and asks; with no terminal to ask at, only `--hash` with its pinned version's hash does it, a hash given at a terminal being checked as `add` checks one. One that holds none (not pinned, or pinned and registered with no gating hook) is turned off unasked.
  - **The file is edited in place,** never written anew: its text kept, comments and order included, and one change made. With no entry for the extension, the table is added at the file's end as the TOML serialiser writes it, a name that is not a bare key quoted (`[extensions."acme.lint"]`); an entry that says `enabled = true` on a line of its own has that value made `false`; one that says `false` already writes nothing. Anything else (an entry written inline, one with no `enabled`, a file that does not read or is not valid) is refused with what to change by hand.
  - **What is written is checked before and after it is written:** the new text must read back, as the loader reads a user's file, as the old settings with that one value; the file is read again just before the write and must be as it was; the write is atomic, through a link at the name to where it leads, keeping the file's mode; and the file is read back from the disk after it. A file that is not there is made, owner-only, with the table alone, and the command says so, since the first run then does not start.
  - **It takes effect as the key is declared** (`next session`): the command says that running sessions keep the extension until their next session, and that `config/reload` (`/reload`) does not apply it to them. When the configuration in force does not turn it off (a managed file's lock), it says so.
  - For a project's extension it writes nothing and says how instead: `cineris permissions trust` shows the project's extensions and approves them, and `cineris permissions untrust` takes its trust away. A name that is neither the user's nor the project's is refused.
- **`cineris ext remove <name>`** takes the user's own extension's pin away and deletes its folder, on one yes that names both (the early review's M1).
  - A name that cannot be an extension's is refused first, by the names' rules (`..`, `a/b`, `.hidden`), and so is a removal while `pins.toml` cannot be read. The name is taken as the user's folder of extensions holds it, the exact name before another case of it, or else as it is pinned, case aside: names that differ only in case are one name on Windows.
  - It says what goes, its pin (its hash and when it was pinned) and its folder under `~` (or that a link there is unlinked and what it leads to left as it is, or that the folder is gone already), and for one not pinned its folder's hash; then it asks one question naming both ("Unpin `tracker` and delete `~/.config/cineris/extensions/tracker` and everything in it?"). **Without the yes nothing is changed.** With no terminal to ask at, only `--hash H` does it, `H` being its pin's hash, or, for one not pinned, its folder's, read through handles; a link that is not pinned has no hash to name it by, and only a yes at a terminal removes it.
  - **On the yes the pin is taken away first;** a pin that cannot be taken away deletes nothing. Then the folder is deleted, never through a link: a link at the name is unlinked, and what it leads to left as it is; a folder goes with everything in it through the standard library's `remove_dir_all`, which follows no link inside it. A path whose folder, resolved, is not the user's folder of extensions, resolved, is refused whatever its text (`ext::manage::within`): the extension is then unpinned and its folder left, and the command says so. The folders above the name are resolved by name when it is deleted: one swapped for a link between the check and the delete is followed ([a-folder-is-deleted-by-its-path-after-its-check](../outstanding/a-folder-is-deleted-by-its-path-after-its-check.md)).
  - A project's extension is refused, naming `cineris permissions trust` and `untrust`. An `enabled = false` entry of the user's configuration and the registration cache are left as they are; sessions prune the cache.
- **Under a session's command** `add`, `remove` and `disable` each refuse before anything is read, and the permission engine refuses a session's command line that runs them, at every level, whatever the rules ([06-permissions-and-sandbox.md](06-permissions-and-sandbox.md), "The harness's own approving commands").
- **In a build without the script engine** (`cineris-cli`'s `scripts` feature off; [decision 0005](../decisions/0005-extension-mechanism.md)) `cineris ext add` refuses before the extension's folder is read, and nothing is written or pinned, since an extension is approved only as it was evaluated: it says, on standard error, "This build of Cineris has no script engine, so `cineris ext add` cannot evaluate or approve an extension." (with the name it was run as), and exits with 2, as its other refusals do. `list`, `inspect`, `disable` and `remove` work as with the engine, `list` and `inspect` saying an approved extension is not loaded, and so does `cineris permissions trust`, which approves a project's extensions and hooks by their hashes and evaluates none ("A build without the script engine", below).
- **`extensions/status`** ([11-rpc-protocol.md](11-rpc-protocol.md)) gives the same standings: of a session the client has open, with what its finding loaded and could not load, and the gates it holds of each; for a session whose finding has not settled yet, or with no session, the user's own, as the core's own configuration finds them, with no project. It is judged at each call, on the blocking pool.

**As built in step 28: the examples** (`examples/`; [steps/28/answered.md](../steps/28/answered.md), point 10, "3c"). Three, each with a README that says what it shows, what its manifest asks for and why, and how to install it:

It reads through `cineris.fs.read`, and its manifest asks for `read = ["**/*.md"]` alone: a read of any other file is refused by the manifest, naming `capabilities.read`, before any rule is asked.
- `shell-gate`: a hook on `tool.before`, on the shell tool's calls alone (`hooks = ["tool.before"]`), that refuses `rm` given a recursive and a forced option, and `git push` with `--force`, `--mirror`, `-f`, a `+` refspec or a `+` `push` refspec set with `-c`, in the forms its README lists, and has no opinion on any other command, `--force-with-lease` included. It reads a line's words as a POSIX shell splits them, and the line given to `sh -c`, `bash -c` and `eval` again. Its README says that it is an illustration of a hook and not a safety boundary, and what it does not read.
- `release`: a command file, `/release-notes <version> [audience]`, beside an extension's command, `/changelog:draft [since]`, which reads `git log` through `exec = ["git"]`, `--no-show-signature` and `--end-of-options` before the revision, and returns the prompt to send. It is laid out as the configuration directory is (`commands/`, `extensions/`). Its README leads with allow once for that line, offers a rule for the line word for word and no more, and says that an `exec` rule covers the model's shell too, in every project, and names what a repository's configuration can still make git start: a partial clone's fetch from its promisor remote, and a pager, on a terminal only.

They run as one test on both systems (`cineris-cli`'s `examples::sys_the_examples_run_as_their_readmes_say`): each added with `cineris ext add` and the hash it shows, the command file copied into the user's `commands/`, a workspace that is a git repository with a tag, the rules the READMEs of `release` and `md-outline` offer in the user's configuration, as they are written there, and one release in two headless runs against the scripted model, each rule judged by its own name; no test reaches the network. The start-up test runs with them approved (`cineris-core`'s `extensions_reload::with_the_examples_approved_no_engine_starts_until_one_is_used`): opening a session, a turn whose call none of their hooks is on, and listing its commands make no runtime, and the first call of a tool makes one. **On Windows a `%` in an argument of `cineris.exec` keeps every rule from allowing its line** (as do `& | < > ^` and `"` in an argument, one ending in `\`, and an empty one), since the engine reads the line as PowerShell would run it: such a call is asked about every time, and refused in a hook and where nobody can be asked ([an-extensions-program-is-judged-by-the-sessions-shell](../outstanding/an-extensions-program-is-judged-by-the-sessions-shell.md)). `release` reads the log with `--oneline` for this reason. Their scripts are run on their own through the engine with a host that records what it is asked (`cineris-ext`'s `examples` tests: each form `shell-gate` refuses and those it lets through, and `release`'s line and the option it refuses for a revision), and the rule `release`'s README offers is asked about the lines it must not allow (`cineris-policy`'s `decide::the_release_examples_rule_allows_its_line_and_no_other_option`).

## Self-written extensions

"Write me a tool that…" is an ordinary request to the agent, or `/extend <request>`.

1. **The agent writes a proposal** with the `propose_extension` tool: a name, a manifest, and the files. It can include test cases (arguments and expected results).
2. **The harness checks it** before the user sees it:
   - the manifest is valid, and its capabilities are flagged if broad (any program, any host, write access to everything);
   - every file parses;
   - the script is loaded in a throwaway runtime with host functions stubbed, to list what it registers;
   - test cases run in the same throwaway runtime. Host calls made during tests are recorded and shown, not performed.
3. **The user reviews** in a dialog: what it adds, what it may ask the host to do in plain words, the test results, and the full source in the viewer. Choices: approve for me, approve for this project, edit, or reject with a note that goes back to the agent.
4. **On approval** the files are written, the hash is pinned, and the extension is live: its tools through `tool_search`, its commands in the menu, its hooks from the next event. Nothing is restarted.
5. **Later changes** by the agent are new proposals, shown as a diff. Changes the user makes by hand are picked up by hot-reload and ask for the same review.

The agent writes extensions with no more power than the user grants at review: the manifest shown in the dialog is exactly what the runtime enforces.

## Hot-reload

Covered with configuration in [08-configuration.md](08-configuration.md). For extensions: a changed file is noticed at the next check, the extension's hash is compared with the approved one, and either the runtime is recreated (hash unchanged or change approved) or the extension is disabled pending review.

**As built in step 28** (`cineris-core`'s `ext::watched` and `ext::found`; [steps/28/parts/pr2a1-found.md](../steps/28/parts/pr2a1-found.md)).

- **What is stamped:** what the extensions were found in.
  The stores of the pins (`pins.toml`, `trust.toml`), the user's folder where it really is, the names on the way to the project's as written (none past a link or a name that is not there) and, where it really is, each name from the workspace down to it, each extension's folder, every folder in it (an empty one too) and its files, and each extension folder left out.
  **Each place is stamped before it is read** (since the full review of step 28), so that a change made as it is read, or while the trust question that read it is open, is seen at the session's first look: the question's extensions are pinned as it read them, and withdrawn then.
  **At most 4,096 places are stamped within one root's extensions** (since the fresh review of step 28, which found a crafted folder of 64 folders of 1,023 empty folders each taking a minute to stamp, each place stamped after a look through all the others): past them the rest of the root is left out unread and said. The user's root then counts as not listed whole and takes every name; the trust question takes the user's names within the same bound, so that the two agree (`discover::names_seeing`). Nothing reads that of a project's root, whose extensions past the bound are not loaded. Each place is stamped once, kept in a set.
  Apart, what the skills were found in (`skills::find_seeing` names each place first): each name on the way to each root as written, where a root that is not there would be, and where a link to nothing leads, each stamped by its kind alone, so that a file another tool writes in `~/.claude` is no change; where each root really is (stamped whole, though a root is also a name on the way to itself, so that a skill added to a root that is there is seen), each entry of it, the folder a link in it leads to, and each `SKILL.md`, stamped before it is read; at most 5 + 3 × 100 places a root. **What it costs** (`perf_what_a_projects_skills_cost_each_turns_start`, ignored): a root of 5 skills, nothing measurable on the reference machine and 0.02 to 0.33 ms on a hosted Windows runner in two runs, within their spread; three roots at the cap of 100, each entry a skill, a repository's worst without trust, 0.33 ms a turn's start on the reference machine and 10.6 ms on a hosted Windows runner, whose first turn took 225 ms against 15.7 ms with none ([performance-budgets.md](../performance-budgets.md)). A change to them has the skills found again, told by the index's notice at that turn's start, and has no extension read again.
  No stamp follows a link: a place is looked at itself, so a link a repository puts where a folder was is a change, and is never looked through (on Windows a look through a link to a share would send the account's credentials).
- **When it is looked at:** at each turn's start and a compaction's, before the look at the configuration's files. A change made during a turn is seen at the next turn's start: a headless run, which is one turn, does not see one made while it runs.
  The places are looked at in order, a folder before what is in it, stopping at the first change; a place modified within two seconds of its stamp counts as changed until that has passed.
- **Before an extension's runtime starts,** at its first call, each name on the way to its folder is looked at itself: one that is no longer a folder of its own (a folder on the way swapped for a link, perhaps out of the workspace) refuses the start (since the full review of step 28). The look comes before the read. **Since the step's third pull request the read goes through handles below the folder** (`Snapshot::read`, the same `cineris_sandbox::unfollowed` reader as `cineris ext add`'s, "As built in step 28: managing extensions"; settled by the maintainers): the folder is opened by its path, the names on the way and its own followed as the system follows them, and every name in it is opened relative to the handle of the folder it is in, a link at any of them refused, never followed. A folder on the way swapped between the look and the open is still read through, and what is read is still checked against the approved hash, so that nothing but what was approved runs; the stamp's walk of a folder has the same window, since the stamps look at places by name and read no content. Discovery and the trust question read an extension's folder through handles too, from the root they listed, held open where it was resolved to ("Tier 4: script extensions" above), so that a folder above the root swapped for a link is never read through there; the start's own read, by the folder's path, is held to the hash they approved.
- **What a change does:** every folder is found and judged again.
  An extension that no longer stands approved as it was loaded (changed, unpinned, its project's trust taken away, its folder behind a link out) is withdrawn: its tools leave the registry, its text leaves section 7, its hooks on the events that only add leave their events, its runs still going are stopped, and the session is told.
  If it was changed, made unreadable or removed while its pin stands, its `tool.before` and `prompt.submit` hooks are held on their events as failing gates ("As built in step 28: script hooks"); if it was unpinned, or its project's trust was taken away, it holds nothing.
  One that now stands approved (pinned in another process, or changed back) is loaded before that turn starts, registered first if the cache misses it, and its hooks join their events in place of the gates it held.
  A finding that fails after a change is told ("The session's extensions were not found again after a change: …"), and what was loaded, and what holds its gates, stays as it was.
- **What it costs:** a look at each place.
  Three with no extension (the two stores and the user's folder), more with the project's way and each extension's files.
  A configuration directory given as a link is watched where it leads: a link pointed elsewhere is seen by the next session.

## Safety

| Measure | Detail |
|---|---|
| No ambient access | A script can do nothing except call host functions. This holds on every OS. |
| Declared capabilities | The manifest bounds what the extension may ask for. The runtime checks every host call against it. |
| Policy still applies | After the manifest check, each host call goes through the permission engine like a built-in tool's effects. An extension's tool asks by default. |
| The sandbox still applies | Programs run on an extension's behalf go through a sandbox launcher of the extension's own, with the manifest's write roots and no network unless `exec_network`, at every level, where the sandbox enforces. Where nothing confines programs (Windows in the first release), `write` and `exec_network = false` do not bind them, and the approval says so first: "Programs this extension runs are not confined on this system. They can do anything you can, including changing Cineris's own settings and approvals." (since the full review of step 28; [06-permissions-and-sandbox.md](06-permissions-and-sandbox.md), "As built in step 28's second pull request"). |
| Review before load | Nothing the agent or a repository supplies runs before the user has seen it. |
| Trust pinned by hash | Any change disables the extension until approved again. |
| Approval reads what it shows | `cineris ext add` reads the folder once through handles that follow no link, evaluates that snapshot before it asks, shows what it registered, and writes, pins and registers that snapshot, never a second read of the source; with no terminal it approves only the hash shown (since step 28's third pull request). |
| An approval is the person's | The permission engine refuses a session's command line that runs the harness's approving subcommands, at every level and whatever the rules; those subcommands refuse to run under a session's command; and the RPC server refuses a session's commands as clients, its own and any other harness's (since the review of step 28). None of these is a boundary against a command with the user's rights, which can write the stores itself ([06-permissions-and-sandbox.md](06-permissions-and-sandbox.md), "The harness's own approving commands"; [../security.md](../security.md), section 3). |
| Limits | Memory, time and output size, per call and per runtime. |
| Bounded, labelled output | Tool results pass the standard output policy and are labelled as coming from the extension. |

## A build without the script engine

The engine is behind `cineris-core`'s `scripts` feature, which the shipped build has and `cineris-cli` passes through as its own ([decision 0005](../decisions/0005-extension-mechanism.md); [01-workspace.md](01-workspace.md), "Cargo features"); `cargo xtask check`'s `no-scripts` step keeps a build of the binary without it possible. Such a build runs no script, so it loads no extension, and it lets no gate lapse because of that (since step 28's close, settled by the maintainers: it fails closed). Until then it gave the loop no hooks at all, and a configured gate on `tool.before` or `prompt.submit` let through what it would have refused.

- **Hook commands run as they do with the engine.** The user's own `[hooks.<name>]` and a trusted project's approved hooks are processes. They go through the same seam (`ext::hooks`, `ext::hook_command`, `ext::hook_points`) and the same start as `cineris.exec`'s (`ext::exec::run`), with the same decision, confinement, looks at the protected paths, times, pools and stops, and the `session.start` and `session.end` hooks run as the session opens and closes. Only an extension's script hooks are left out, with the extension.
- **An extension that stands approved holds its gates.** None of an extension's tools, commands, hooks or prompt text is in a session. Each extension that stands approved (the user's own, pinned and not turned off; a trusted project's, pinned or approved for the run; whether it is found as approved, changed, unreadable or gone) keeps its gating hooks (`tool.before`, `prompt.submit`, not observing) on their events as failing gates, as one that cannot be loaded does with the engine ("Its gates fail closed"):
  - those it registered at its pin's hash, as the registration cache keeps them, each on its tools;
  - where the cache does not keep them and it is found as approved, a gate on each gating event its manifest lists, on every call;
  - where neither is known (changed, unreadable, gone), both gates, on every call and every prompt.

  While the pin store cannot be read, each of the user's extensions found holds the gating hooks of the cache's entries of its name and a gate on each gating event its manifest lists; a project's, while the trust store cannot be read, holds nothing: no repository gates a session by itself. One approved for this session by a yes the store could not keep stands approved all the same, as the session's finding judges it with the engine, and holds its gates. Each refusal names the extension, says it is not loaded because this build of Cineris has no script engine, and gives the way out: turn it off (`cineris ext disable <name>`, which sets `[extensions.<name>] enabled = false`, from the next session), take the project's trust away (`cineris permissions untrust`), or use a build that has the engine. This build cannot approve an extension again: `cineris ext add` says it has no script engine. The user is told once, as the session opens, of each extension that stands approved: that it is not loaded, and the gates it holds. What is held is settled as the session opens and kept for it, as its hook commands are; a change takes effect at the next session.
- **Skills are not found** in such a build: they are found on the extensions' finding, which needs the engine (the maintainers' call, for now). Custom command files work as with it.
- **`extensions/status`** gives an extension approved as it is found as `failed`, its `error` "approved, and not loaded: this build of Cineris has no script engine, which runs it", never `ready`; its `standing` stays `approved`, and the gates the session holds of each extension are its `gates`. A session's status judges what that session judged as it opened: the user's folder, and the project's while it is trusted. `cineris ext list` and `inspect` say the same of the standing. The protocol is unchanged.
- **Where it is tested.** The decision (the core's `ext::without_engine`), the session's judging of it from what the session opened with (`without_engine::in_session`), the held gates put on the loop's points (`ext::hook_points`, whose list of them is kept in both builds and is empty with the engine) and what `extensions/status` lists of each are built in every build, and their tests run in the ordinary test run. What only a build without the engine compiles is a few lines of `assemble` that hand the session that judging's gates and its lines for the user, `PointHooks::of`'s handing of the held list to the failing hooks (the list is empty in the ordinary build), the finding's own start and view in such a build (`ext::found`), which settle the session's readiness and keep what `extensions/status` reads, the words a standing is said in there (`ExtensionStanding::words`), and the status's `not_loaded` in place of what the finding loaded: `cargo xtask check`'s `no-scripts` step lints them with warnings denied, and no test runs them. The seam that runs the hook commands is the same code in both builds, and its tests run in the ordinary one.

## Windows

- Extension scripts behave identically: the engine is in the binary and the host functions are the same code.
- `cineris.exec` names a program and its arguments as a list. Nothing passes through a shell. Script shims (`.cmd`, `.bat`) are resolved by the host and run with arguments it escapes itself; arguments that cannot be escaped safely are refused.
- **A `.exe` is given every argument in double quotes,** escaped by the C runtime's rules (a `"` as `\"`, the backslashes before a quote and before the closing quote doubled), and not by the standard library's quoting, which quotes only an argument that is empty or has a space or a tab. A program of the Cygwin family (MSYS2's, and Git for Windows' `usr\bin`) expands `* ? [` and braces in an argument that is not quoted, against the folder it runs in, and takes `'` as a quote: an argument `.en*` the permission engine judged as a file name read `.env`. Inside double quotes it does neither. **What such a program does not read exactly** is a run of two or more backslashes that is not before a quote: inside quotes it takes `\\` as one, where the C runtime takes it as two, so `\\server\share` reaches it as `\server\share` and `a\\b` as `a\b` (seen on a Windows runner with Git for Windows' `echo.exe`; a single backslash, one at the end, and `\"` reach it as written). No quoting is read exactly by both, and the C runtime's is the one nearly every program reads.
- **A batch script is never given `& | < > ^ ( )`,** as it is never given `"`, `%`, `!`, a carriage return, a line feed or a NUL: an argument that holds one is refused before anything is asked, naming the argument and the character. Inside the double quotes `cmd.exe` puts round each argument they are plain, but a script that takes the quotes off and reads the argument again (`set A=%~1`, then `echo %A%`; `call :x %~1`; `if "%~1"==… (…)`) runs what follows `&` or `|`, redirects at `<` or `>`, groups at a parenthesis, and joins a line that ends in `^` to its next. The shims package managers write are such scripts' callers, so an npm shim's argument such as `--x=(a)` is refused too: an accepted cost.
- **A shim whose path holds `(` or `)` is refused,** as an argument with one is: the script's path is one of the quoted items of `cmd.exe`'s line, and a parenthesis cannot be carried through `cmd.exe` safely. So a shim under `C:\Program Files (x86)\` does not run; one installed elsewhere, or the program it starts named by its own path, does.
- **On every system, no argument holds `＂` (U+FF02), `ʺ` (U+02BA), `＼` (U+FF3C), `∖` (U+2216), `¥` (U+00A5), `₩` (U+20A9), a soft hyphen (U+00AD) or `－` (U+FF0D):** the call is refused, naming the argument and the character. A program that reads its command line in a Windows code page (an "ANSI" program) is given it converted with a "best fit", which makes the first two `"`, the next two `\`, the yen sign `\` in code page 932 and the won sign `\` in code page 949, and the last two `-`: a quote that ends the quoting, an escape before one, or an option where the engine saw a word. These are the ones known; checking every argument as Windows converts it is open ([an-exec-argument-is-not-checked-against-the-code-pages-best-fit](../outstanding/an-exec-argument-is-not-checked-against-the-code-pages-best-fit.md)).
- Hook commands follow the same rules.

## Relation to MCP

| If you want to… | Use |
|---|---|
| Add a prompt you type often | A custom command. |
| Teach the agent a procedure | A skill. |
| Gate or observe what the agent does | A hook. |
| Add a tool that glues together things already on the machine | A script extension. The agent can write it for you. |
| Add a tool that needs a client library, a database driver or a long-running process | An MCP server ([13-mcp.md](13-mcp.md)). |

Script extensions and MCP servers share the dynamic-tool registry, the trust store, the permission check and the output policy.
