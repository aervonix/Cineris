# Testing and CI

The test suite and CI are designed for speed from the first commit. The rule that shapes everything here: **the blocking pull-request checks finish in under 5 minutes per OS on GitHub-hosted runners.** Anything slower runs in a tier that does not block.

## Test tiers

| Tier | What | Where it runs | Blocking? | Time budget |
|---|---|---|---|---|
| **0. Static** | Formatting, lints, licence and source checks, generated-file freshness, repo rules (no home-directory paths, dependency list in sync, crate dependency rules). | Every pull request. | Yes | Under 2 min on a warm cache. |
| **1. Unit** | Pure logic inside each crate: parsers, decoders, mappers, policy evaluation, text layout, view functions. Property tests. Snapshot tests. | Every pull request, both OSes. | Yes | The whole tier in under 20 s of test time above the start of its processes ("Budgets are enforced", below). |
| **2. Integration** | Several crates together, in-process, with the scripted provider, fake tools or real tools on a temporary workspace, the fake clock and the virtual terminal. The agent loop, sessions, context, permissions, the RPC conformance scenarios, the TUI against the virtual terminal. | Every pull request, both OSes. | Yes | Under 40 s of test time above the start of its processes. |
| **3. System** | The real binary as a process: headless runs against the scripted SSE server, the TUI under a pseudo-terminal, process-tree and sandbox behaviour, extension scripts and MCP fake servers. | Every pull request, both OSes. | Yes | Under 60 s of test time above the start of its processes on Linux, 90 s on Windows. |
| **4. Performance** | The budgets in [performance-budgets.md](performance-budgets.md). | Main branch after merge, nightly, and on request. | No | 10 min. |
| **5. Live** | Smoke tests against real providers. Fixture recording. One headless run of the real binary against Anthropic, and one against DeepSeek, since step 13b. | By hand: `cargo xtask live` and `cargo xtask record`, since step 14. No workflow runs them yet. Never on pull requests. | No | |
| **6. Soak** | Fuzzing of decoders and parsers, long scripted sessions for memory growth, release builds for every target. | Nightly. | No | |

Tiers 1 to 3 are separated by where the test lives and by nextest filters, not by cargo features:

- unit tests are `#[cfg(test)]` modules in the crate;
- integration tests are one test binary per crate, `tests/it/main.rs`, with modules inside it;
- system tests live in `cortex-cli/tests/system/` and in `cortex-testkit`-driven binaries, and their names start with `sys_`.

**One integration binary per crate.** Every extra test binary is another link step, and linking is the slow part on Windows. Doc tests are turned off (`doctest = false`); examples that must compile are ordinary tests.

**No real waiting in tests.** This is rule 12 of the [build plan](build-plan.md).

- Timeouts, retries, backoff, cooldowns, debouncing and anything else that depends on time passing are tested with time that is paused or simulated: the async runtime's test clock, which jumps to the next timer as soon as every task is idle, or the fake clock for code that takes time from the clock trait in `cortex-base`. A test of a 30-second timeout takes microseconds. The fake clock is defined in `cortex-base`, beside the trait, because that crate tests itself with it and cannot depend on the test kit; the test kit re-exports it. Its `sleep` returns at once, moves its time forward and records what was asked, so blocking code that waits and retries (the replace of a locked file) is tested for how long it would have waited.
- Production code never reads the system clock or sleeps directly. It goes through the runtime's timers or the clock trait, which is what makes the rule possible to follow.
- **Async code that also needs the date waits on a timer trait.** The retry layer of `cortex-llm` waits between attempts and also says when the next attempt is and when a cooldown ends, so it needs waits and dates from one clock. It takes its waits from a `Timer` trait and its dates from the clock trait. The harness gives it the runtime's timer. A test gives it the test kit's `FakeTimer`, made from the same `FakeClock`, in one of two kinds: **automatic**, where a wait finishes when it is first polled and moves the clock by its length, so code that waits and goes on runs straight through and the test reads back what it waited for; and **manual**, where a wait finishes only when the test moves the clock past its end, for a time limit that must not pass until the test says so. Neither needs an async runtime: the test kit's `block_on` runs such code on the test's own thread.
- **Two sides of a test take turns through a gate, not a pause.** Where things must happen in an order (the scripted server has seen the client hang up; a scripted response may go on), one side opens a `Gate` and the other waits for it. A blocking wait on a gate takes a bound, so that a mistake is a failed test and not a hung one. Where the library itself must stop at a place (between a read and a write), the library marks a point and the test holds it ([A point the library stops at](#a-point-the-library-stops-at)).
- **Wait for a gate. Do not assert that it is open,** unless your own thread is the one that opens it. Another thread opens its gate a moment after the thing the gate marks: the scripted server writes a piece and then marks it, so the piece can reach the test first. An assertion that the gate is already open passes almost every time and fails under load, which is how step 5 put a test on the main branch that the nightly run then failed. Asserting that a gate is still **closed** is sound only for a gate the test itself opens.
- **Never rely on closing a socket from one thread to wake a read that is waiting in another.** Linux wakes it. Windows does not promise to, and a test that joins the reading thread then hangs there, some of the time. A thread that reads a socket and must be stoppable gives its read a short timeout and asks, each time it runs out, whether it has been told to stop. That is how the scripted server stops (`crates/cortex-testkit/src/server.rs`): the interval bounds how long stopping can take, and no test waits on it.
- A test never calls `std::thread::sleep`. Clippy's disallowed-methods list bans it everywhere, tests included.
- Tier 3 cannot pause time, because the code under test is another process. It waits on a condition with a deadline (output seen, file present, process gone), never on a fixed delay, and the helper for that is in `cortex-testkit`.
- **A process test's children are the test binary itself, run again** (`cortex_testkit::children`, since step 11). A test binary has one entry test, which passes at once under the test runner, and becomes a child when a test starts the binary again with a child's specification: one that stays until it is killed, one that starts a grandchild, one that the polite interrupt does not stop, one that exits with a code, one that prints its arguments back. Each child connects to the test's `Roll` on the loopback interface and keeps the connection until it dies. So "the process is up" is a connection that arrives, and "the process is gone" is that connection closed by the system: neither is a guess at how long something takes. No helper program is built, so there is no second link step, and no test runs `sleep`.
- **A test in a process of its own** (`cortex_testkit::rerun`, since the third tooling step). How the harness finds a program depends on its process's `PATH` and working directory, which a test cannot change: the tests of one binary share them. Such a test runs itself again as a child, with `Rerun::this_test().path([…]).cwd(dir).env(name, value).run()`; in the child, `rerun::is_child()` holds, the test does the search the harness does and reports with `rerun::say(key, value)`, and the parent reads it back with `said(key)`. A rerun whose name matches no test, which would pass having run nothing, fails. Step 13a's tests of a relative `PATH` entry used to make a path relative to the test's own working directory by hand; two of them now run in a child whose working directory holds the planted program, and a third, of the session store's git, turned a break that could only survive into one a test catches.
- **A call that should end by itself is given a bound.** The shell tool's tests run such a call with nobody to end a wait for it. If the runner then waits for something that is not there (a grace for a process the command did not leave), the wait never ends on a hand-driven timer, and the test used to be stopped a minute later with nothing to read. The bench now lets every wait go after its limit and fails the test with the waits the runner was in.
- **The process runner waits on a timer trait,** like the retry layer. Its tests give it a timer whose waits end when the test ends them, by their length: the time limit of a call, the grace between two stages of stopping, the grace for what a command left running. A test of a two-minute time limit takes as long as the processes take to die. A call that does not end by itself runs on the test's thread while a director on a second thread waits for children and ends waits, and a director that fails lets every wait go, so that a failed assertion is a failed test and not a hung one.

**Budgets are enforced.** This is rule 13 of the build plan.

| Tier | A test is reported as slow at | A test is stopped, and fails, at | The tier's tests together |
|---|---|---|---|
| 1. Unit | 2 s | 10 s | 20 s |
| 2. Integration | 2 s | 10 s | 40 s |
| 3. System | 10 s | 60 s | 60 s on Linux, 90 s on Windows |

- The limits on one test are nextest's `slow-timeout` and `terminate-after`, set per tier in `.config/nextest.toml`. They hold in every profile, at a desk as in CI, except `properties`, the nightly run with fifty times the property cases, whose limits are scaled for it ("Property tests", below).
- The tier totals are the sum of the tests' own times, not the wall time of the run. `cargo xtask ci test` reads them from nextest's JUnit report after the run, prints them with the share of the budget used, and writes them to the CI job's summary page.
- **Each tier is measured under its own load** (the owner's decision of 2026-11-15). The blocking test job is two runs of nextest: tiers 1 and 2 first (`-E 'not test(/(^|::)sys_/)'`), and then the system tests alone, three at a time (the `ci` profile's `system` group). One run held the system tests two at a time beside the rest from the start, so the integration tier was measured under the processes, pseudo-terminals and children of tier 3: on one Windows runner `main`'s integration tier took 27.4 s in the job and 21.2 s alone. An experiment of the fifth tooling step (`try` run 43665893748, five rounds of each layout on one runner of each OS) gave Windows' integration tier 17.8 s split against 22.5 s, 21% less, and its unit tier 8.6 s against 10.3 s, with the system tier unchanged (54.5 s against 53.9 s) and the job 1.7 s longer; with four system tests at a time they slowed each other (12.5 s more of the system tier). The budgets were not changed.
  - **The two runs leave one report.** The first's JUnit report is set aside and merged with the second's (`xtask/src/junit.rs`, `merge`), at `target/nextest/ci/junit.xml`, where one run left its own, so the tier budgets, `ci --tiers`, `ci-times` and the kept artifact read one report as before. The log shows two steps, `run tiers 1 and 2` and `run the system tests`, each with its time; both run when the first fails.
  - **`ci --tiers` and `ab` run the job as it is,** in two. A filterset given to them (`-- -E 'package(cortex-tui)'`) narrows each run, joined with `and` to the run's own: nextest takes a test that matches any of its filtersets, so given beside it, it would run the other tier's tests too. `ab` runs each tree as that tree's own job does: a tree whose `.config/nextest.toml` has no `system` group is from before the split, and is run in one, so that an A/B of a change to the layout compares the two jobs.
  - **On Windows the system tests run two at a time** (the owner's decision, amended on 2026-11-15 in the sixth tooling step; [steps/tooling-6/answered.md](steps/tooling-6/answered.md)). Most of Windows' system tests start PowerShell, whose start cost 290 ms alone and 440 ms with three at once on one runner (`try` run 43713246255). The same tree read its system tier at 57.6 s with three at a time and 46.6 s with two, five rounds of each on one runner, with tiers 1 and 2 unchanged; the system run's wall time went from 20.1 to 24.2 s (`try` 43715198613). With the step's test changes (93.2 s on `main` against 80.4 s, on one runner, `try` 43715195861) that brings the tier near 65 s on a 10 ms runner, where a 12 ms runner had failed the budget. In `.config/nextest.toml` it is the group `system-windows`, chosen by an override for `cfg(windows)` before the `ci` profile's own; Linux stays at three, and the line `system = { max-threads = 3 }`, which `xtask` reads to know a tree's job is two runs, stays as it is.
  - **On Windows tiers 1 and 2 run three at a time** (the owner's decision of 2026-11-16, in the seventh tooling step; [steps/tooling-7/answered.md](steps/tooling-7/answered.md)). With four test processes at once on a 4-core runner, the tests slowed each other: on one 6 ms runner three at a time took `main`'s integration tier from 23.4 to 19.0 s and its unit tier from 11.3 to 7.9 s, for 1.5 s more of the run's wall time (`try` 43778700279, three rounds of each). Two at a time took off more (38.3 to 23.6 s on an 8 ms runner) for 8 s more of the wall time, and was not taken: the job's time is what people wait for. In `.config/nextest.toml` it is the group `tiers-windows`, chosen in the `ci` profile by an override for `cfg(windows)` and every test that is not a system test; Linux runs as many as it has cores.
  - **`cargo xtask test --profile ci` is one run,** with the system tests three at a time beside the rest (two on Windows). It has the job's settings, not its order: `cargo xtask ci test` is the job.
- **A tier is held to its budget above the start of its tests' processes** (the owner's decision of 2026-11-13). nextest runs each test in a process of its own, and starting one costs about 5 ms on a hosted Linux runner and 6 to 12 ms on a Windows one, by the runner's speed. For a thousand unit tests that was 6 to 12 s of the unit tier's 20 before any test did anything, so the raw total told which runner a run drew more than how its tests did: one tree gave 17.0 s on a fast runner and 22.7 s on a slow one.
  - **The start cost is measured by each run:** the time that 1% of its unit and integration tests were quicker than. The quickest tests of a run do next to nothing, so their time is the start of a process. Not the single quickest, which one lucky test moves by a millisecond and with it the whole tier: in one job that ran one tree twice with each of two settings, the unit tier's figure moved by 1.1 s between the two runs of one setting with the quickest test as the floor, where the 1st percentile and the raw totals did not move. System tests are left out of the measure: they start processes of their own. A dedicated empty test in each binary was weighed against it: it would be one sample where the percentile stands on about eighteen, and a test every binary must keep.
  - **A run of a few crates, or of a filter's tests, measures its own start,** and its quickest tests may do real work: the report says so when it has fewer than 500 unit and integration tests to measure on. CI runs the whole workspace.
  - **Each test's time above that cost is added up,** a test that took less counting as nothing, and the warning at the budget and the failure at one and a half times apply to that sum. The same on both OSes: on Linux it takes about 5 s off a unit tier of 13.
  - **A start cost above a ceiling is a warning** (since the seventh tooling step): above 8 ms a test on Linux and 15 ms on Windows, more than the slowest runner of each starts a test in, the report says so, as an annotation on the pull request in CI. A cost every test process shares (a larger test binary that loads more slowly, a global initialiser, a heavier harness) rises with the start and is taken off every test with it, so the budgets cannot see it; the warning is where it shows. A run of fewer than 500 tests says nothing: its quickest tests may do real work.
  - **The report prints both totals** and the cost it took off: `process start: 11 ms a test (the 1st percentile of the run's 1857 unit and integration tests' times)`, then for each tier its tests, its time, its time above the start, its budget and the share of it used.
  - **What it does not even out.** A slow runner is slower at the tests' work as well as at starting them. On the same tree the unit tier read 11.0 s above the start on a fast runner and 11.6 s on a slow one, within noise, where the raw totals were a third apart; the integration tier read 23.1 and 31.3 s, 28.2 and 40.6 s raw. Its tests do far more than start, and the budget is right to see that. The two runs are kept as fixtures, `xtask/fixtures/tiers/windows-fast-runner.xml` and `windows-slow-runner.xml`, and a test holds the figures.
- **A run whose disk stalled is not judged, at a desk** (since the eighth tooling step; `xtask/src/stall.rs`, `tiers.rs`). A tier's time is the sum of its tests' times, and when a shared machine's disk stalls every test that touches a file waits with it: in wave 11 a tier budget "failed" by a stall, and a person read the log to find that out. The two test runs of `cargo xtask ci` read `/proc/pressure/io` when they start and when they end, and leave what it said of each (how long the run was, and for how long every task waited on I/O: `full` of the kernel's file) in `target/nextest/ci/pressure.txt`, beside the report, which the build forgets with it, each line with the tiers its run measured (`tiers=1,2` for the first run, `tiers=3` for the system tests'; a re-run's line is its run's). The tier budgets step reads that file. When every task waited on I/O for **10% or more** of a run's time (a run and its re-run counted as one), it prints

  ```text
  not judged: the machine stalled. Every task waited on I/O for 41.3 s of the test runs' 120 s (34%, from /proc/pressure/io; a run is taken to have stalled at 10%), so the times of the tiers they ran (1, 2, 3) are the disk's as much as the tests', and those tiers are not held to their budgets; any other is. Run the tests again when the machine is quiet. CI's runners are always judged.
  ```

  above the same tables (each tier's time, by crate, its slowest tests), with no mark, warning or failure for the tiers of the run that stalled: those it neither passes nor fails. The tiers of a run that did not stall are judged as ever, so a stall of the system tests' run leaves tiers 1 and 2 held to their budgets (found by the step's review: summed over both runs, a stall of one excused the other's tiers). (The step list at the end of the run says `ok` for a step whose every tier was excused, since a step has two outcomes; the line above is what says it was not judged.) **On CI the check is what it always was,** whatever the pressure: when `GITHUB_ACTIONS` is set the file is not looked at. A hosted runner's disk is its own, and a verdict that moved with a reading nobody can check there would be a way round the budgets. **Where the pressure cannot be read** (Windows, a kernel without `/proc/pressure/io`, or no file written) the run is judged as it was before. **The threshold, 10%,** is the one `mutate` uses for a busy disk (`full avg60` of 10%, from which it starts with one job), taken over the runs' own time: a run that spent a tenth of its time with every task waiting on the disk lost 2 s of a tier's 20 to it. It was chosen, not fitted to a distribution of quiet runs, which nobody has measured: the stalled runs of wave 11 read 54% (the desk's disk in the sixth step's measurement, in "What a runner would say, from a desk") and 66% (`mutate`'s side slot), and a machine at rest reads 0%. A lower figure would take every busy afternoon of the desktop for a stall; a higher one would judge a run that lost a fifth of its time. It is one constant to move when the desk's runs say it is wrong. A re-run after a stall ("Running the tests many times over") is part of the runs: a run that stalled enough to be re-run is, in all likelihood, over the threshold, and is not judged. `ci --tiers`, a measurement, and `ci --tiers --from`, which reads a report from elsewhere, are not changed: they judge as before. What it cannot tell: a stall short enough, or shared with a build that stopped, to be under the threshold for the whole of two runs of five minutes, which slows tests a little and is judged.
- **The report lists each tier's slowest tests,** five of them in CI, with the share of the tier's time they are. A CI log shows no time for a test under two seconds, and a tier's total is made of hundreds of those: this is where to look when a tier grows. "A CI run's test times", below, has how to get the rest.
- **A tier over its budget is a warning; a tier over one and a half times its budget is a failure.** Both are annotations on the pull request. The gap is there because hosted runners vary by tens of percent from one run to the next, and more on Windows (the same build took 60 to 82 s on four Windows runners in step 2). A failure at exactly the budget would turn a tier that is near its limit into red builds at random, which teaches people to re-run instead of to fix. The warning is the signal to act; the failure is for a tier that is over on any runner. The limits on a single test stay hard failures: they are several times what a healthy test takes.
- **A tier over its budget says what its runner was** (since the sixth tooling step): the run's process start, and whether that is a usual runner or a slow one, with what a slow one implies (`runner: 12 ms runner, a slow runner: tiers likely about twice what a usual runner (6 to 10 ms a test) reads, with the same tests`). The figures are the fifth tooling step's: a 12 ms Windows runner read the system tier at 138.8 s where 10 ms runners read 77 to 90 s, every tier about twice, and a slow Linux runner 1.8 times a usual one's. A run of too few tests to measure its start says so instead. The line is printed only when a tier is over.
- A test over its slow mark needs a reason or moves to tier 6.

**Property tests** use no property-testing crate. The pattern was set in step 4 (`crates/cortex-base/src/cases.rs`), and steps 6, 10 and 12 follow it. Since step 5 the helper every crate uses is `cortex_testkit::cases`. `cortex-base` keeps its own private copy for its unit tests, because it cannot depend on the test kit, which depends on it; a change to one is a change to both. `cortex-tools` had a third copy while step 6 was built beside the test kit; step 7 removed it, and the crate's unit tests use the shared one.

- A property is a function from a generated input to "fine" or "what was wrong". A generator is a function from a random-number generator to an input. `check(name, cases, generate, property)` runs the property on that many inputs.
- **Every run is the same.** Each case draws from the seeded generator of `cortex-base` with a seed made from the property's name and the case number. There is no randomness between runs or machines, so a property test cannot be flaky.
- **A failure prints the property, the seed, the case number and the input.** `CORTEX_PROPERTY_SEED=<seed>` runs that one case again, alone.
- **`CORTEX_PROPERTY_SCALE=<n>` multiplies every property's number of cases.** Pull requests run at 1, which keeps the properties of one crate to well under a second of the unit tier's 20. The `nightly` workflow runs tiers 1 and 2 at 50. The first time this was tried it found a case the default count had not (a wrong expectation in a wrapping test), which is the point of it. At 50 a property takes fifty times as long, so the nightly run has a nextest profile of its own, `properties`, whose limits on one test are scaled for it: slow at 60 s, stopped at 300 s. The limits pull requests run with are not changed. A property of pure logic is far from either (the slowest of step 4 takes 1.8 s at 50 on the desktop); one that does real file work for each case is not: the rewind property of `cortex-session`, a session and a workspace per case, takes 0.75 s at 1 and 32 s at 50 on the desktop, and passed the 10 s limit in the nightly run of 2026-11-13 (issue #19).
- **There is no shrinking,** so generators prefer small inputs, and an input is printed whole. In exchange the helper is 60 lines, adds no dependency and nothing to the build.
- **Small spaces are checked exhaustively** in addition, where that is possible, in the nightly run and by a sample on a pull request (the next point): every sequence of up to six path steps from a small alphabet, every split of a byte stream into two and into three chunks.
- **An exhaustive test that takes a noticeable part of a second checks a sample on a pull request and all of it in the nightly run.** It asks `cases::exhaustive()`, which holds when `CORTEX_PROPERTY_SCALE` is above 1. Its own comment says what the sample is, and the sample must reach every kind of case: path sequences of up to five steps, the calendar's days from 1600 to 2399 with the two ends of the range, every third second cut of a stream. A property's number of cases is cut the same way when it takes a tenth of a second on a Windows runner. The nightly run multiplies whatever the number is by fifty, so a cut there is a cut of the nightly run too, by the same share: the properties cut on 2026-11-13 run 40 to 50% of the cases they did, in both.

**A comparison with the real thing is a property too.** Where the code models another program, the test asks that program. Step 12's command analysis says "this line is these commands with these arguments", and a rule is matched against that, so `crates/cortex-policy/tests/it/differential.rs` generates lines, keeps the ones the analysis models, and compares: bash and `sh` are run with each command replaced by a function that prints its arguments, and PowerShell is asked to parse each line with its own parser. They are system tests, because they start a shell, and `CORTEX_PROPERTY_SCALE` multiplies their lines like any property's cases. On its first run the comparison found that dash reads `20<file` as an argument and a redirection where bash reads a descriptor. A shell that is missing skips its half at a desk and fails it in CI.

What was weighed against it: proptest, which shrinks failing inputs and has a library of generators, and which would add about fifteen packages to every crate's test build, on both OSes, for the life of the project.

## Deterministic agent tests without a network

`cortex-testkit` provides three levels of fake, one for each kind of test.

| Fake | Replaces | Used for |
|---|---|---|
| **Scripted provider** | `ModelClient`. A script of model events with optional delays, errors, stalls and aborts, plus assertions on the requests it received. | Tier 2: every loop behaviour. Runs in microseconds. |
| **Scripted transport** | `Transport`. Returns recorded response bodies in chosen chunk sizes. | Tier 1: protocol adapters, from fixtures. Tier 2: the provider client and its retry layer. |
| **Scripted SSE server** | The provider's HTTP endpoint. A local listener that writes scripted chunks with controlled timing, stalls and disconnects. | The real HTTP client, timeouts, cancellation (tier 2, in-process, since step 5), and the real binary end to end (tier 3). |

All three were built in step 5, with two more pieces they need.

- **The scripted provider** builds a response from what a model does (text, reasoning, tool calls, usage, an end, a speed the provider served it at) and what goes wrong (an error part-way, a delay on a timer, a stall until cancelled, a wait for the test's gate, a stream that just stops). It hands over one event at a time and only when the reader asks, so the order a test sees is the order of the script.
- **The scripted SSE server** listens on the loopback interface only, on a port the system picks, with plain threads and no async runtime, so it can also serve another process. A reply is a script of steps: send these bytes, tell the test this point was reached, wait for the test, hold the connection until the client hangs up, drop it. That last-but-one step is how a test sees that a cancelled request really closed its connection. A client that hangs up while the script is still writing is seen too, by the write that fails: a process stopped by a signal in the instant after its request arrived does that. **A gate that a server thread opens only at the end of its script never opens if an earlier step fails** (a write to a client that hung up, a wait the test never lets go): a test waiting for it waits out its limit. That was the shape of step 13b's SIGINT flake. Mark the point the test needs as early as it is true, or wait for something that opens either way, as the gate of "hold the connection until the client hangs up" does.
- **A test protocol** (`TestProtocol`): a wire dialect small enough to write by hand in a test and complete enough to say everything a real one can, including the speed that served a request and a refusal that belongs to a speed tier. `cortex-llm` has no real protocol until the first provider step, and its client is tested with this one. It is not a model of any provider's API.
- **Fixture models** with every shape of speed tier: one that fails when it cannot be served and has a limit and a cache of its own, one the provider downgrades by itself, and a model with no tier.

**A request a real protocol could not build.** The scripted provider takes any request. `ScriptedProvider::built_as(protocol, provider)` (since the fourth tooling step) runs the real `Protocol::build` on each request first, for a catalog model given with `with_model`, and fails a request the protocol cannot build with the build's error, as the real client does, taking nothing from the script; its stable prefix is the protocol's, so the loop's debug-build check runs on real bytes. Step 15's review needed one to show that a summary's thinking budget was not below `max_tokens`. `cortex-agent`'s context tests use it for Anthropic and DeepSeek.

**A response is cut at the request's maximum output** (since the sixth tooling step). A real provider stops a response at `max_output`, ends it with the length stop reason and counts the output it wrote; a script that said more than the request allows used to pass the loop as if it had been written whole. `ScriptedProvider` now cuts it, and ends it as a provider does:

- **The limit** is the request's `max_output`, or the model's own most when the request sets none, and never more than the model's own most (as Anthropic's builder holds it). `test-model` writes 8,000 tokens at most.
- **Output is counted as the loop counts a request before a provider has counted it,** at three bytes to the token (`cortex_testkit::provider::BYTES_PER_OUTPUT_TOKEN`; a test of `cortex-agent` holds it to `cortex_agent::context::DEFAULT_RATIO`), over the text, the reasoning and the arguments of the tool calls. A response is cut when its output would be more than the limit's bytes, never at them.
- **What is cut:** the delta in which the limit falls is cut on a character boundary, and nothing of the script after it is played, errors, waits and an `abort` included. Every block that was open is closed with what had arrived of it, as the real decoders close an unfinished block (`BlockEnd` with the partial content); a tool call cut in its arguments has arguments that are not JSON, as a real one has. The response then ends with `StopReason::MaxOutput` and a usage whose `output` is the limit (the script's other counts are kept). The loop treats it as it treats a real one ("a response cut off in its text", "a response cut off inside a tool call", in `cortex-agent`'s `streaming.rs`).
- **It is the default.** Of the 2,812 tests of tiers 1 and 2 when it was made, two had a script longer than their request allowed (a 600 kB write in `cortex-core`'s approval test; a 20,000-byte summary in `cortex-agent`'s test of a summary too large for a new epoch), and no test cut by it passed unnoticed. Each says why it opts out with `provider.set_output_limit(false)`, which is shared by every clone, so it can be called on a world's provider after the rig is made; `ScriptedProvider::without_output_limit()` is the same at construction. A script that needs a response longer than its model may write is a script of a response that cannot happen: the opt-out is the exception to say so.

**A long text in an assertion's message** is `cortex_testkit::brief(&text)`: whole when it is short, its size and its two ends when it is long. A notice of ten kilobytes in a failure message once hid the result it was about.

**Sizing a context test by pressure.** A test of compaction needs a request at a given pressure, and step 15's bulk was counted by hand, then counted again three times as the prompt and the tools grew. `Rig::fill(Fill::…, prompt)` in `cortex-agent`'s rig (since the fourth tooling step) gives the session's first request the bulk that puts it below the threshold for a background summary (`Below`), between it and the trigger (`Preparing`), past the trigger (`Compacting`), or past the window (`PastWindow`). It measures the request without the bulk on a twin of the session (the same prompt, tools, instruction files, thresholds and model, at the same workspace path, in a world of its own with a window it cannot fill), and puts the estimate in the middle of the band, from the real limit (`cortex_agent::context::limit_of`) and thresholds, at the ratio the loop uses before a provider has counted. A band the window cannot reach is refused with the numbers. The fixture models it works from:

| Model | Window | Most output | Limit | Background summary past | Compaction past |
|---|---|---|---|---|---|
| `test-model` (`fixtures::model()`) | 200,000 | 8,000 | 188,000 | 131,600 | 159,800 |
| `test-model` with `rig.window(6_000)` | 6,000 | 8,000 | 4,380 | 3,066 | 3,723 |
| `test-model` with `rig.window(4_000)` | 4,000 | 8,000 | 2,920 | 2,044 | 2,482 |
| `test-plain` (`fixtures::plain_model()`) | 32,000 | 4,000 | 27,360 | 19,152 | 23,256 |

The limit is the window less the room kept for the answer (the most output, capped at 32,768 and at a quarter of the window) and a fiftieth of the window; the thresholds are `context.prepare_at` (0.70) and `context.compact_at` (0.85) of the limit, in tokens. Seven of step 15's tests use it; they still catch all 40 of step 15's breaks.

**A request after the first** (since the sixth tooling step). `Rig::fill` sizes a session's first request and refuses one with history. Two more methods size a later one, on a twin made the same way:

- **`Rig::fill_next(Fill::…, prompt)`** sizes the first request of the next turn of a session that has history, and gives the next turn its bulk, as `fill` does. The twin is resumed from a copy of the items the rig's store holds, so what the session has said is in the measure; `summaries::past_the_trigger` (the second turn's request between the trigger and the limit, which counted its bulk by hand from the first request's estimate) is its first user.
- **`Rig::fill_after(Fill::…, prompt, earlier)`** sizes a request inside a turn: the one that follows `earlier`, the responses of the turn `prompt` starts that come before it (the call of a tool round, whose result is in the request). The twin runs the turn on those responses and measures the request after them. It returns what it measured and **gives the session nothing**: bulk given before the turn is in the turn's first request too, so the test gives it with `rig.bulk(filled.bulk)` at a moment of its own, while the turn runs, and the notice reaches the turn at its next request. `earlier` is what the session will be given, without a wait (a `wait` in a response changes no byte of the request, so the test's script may have one where the twin's has none: the test builds both from one function), and its tools must answer as the twin's. The test of it holds a response at a gate, gives the bulk, opens the gate, and checks the second request's estimate against the one sized.
- **A few sizes are still counted by hand, on purpose** (the eighth tooling step moved the rest onto `fill` and `fill_next`: the over-budget notices of the transition, interrupt and session tests, the second turn of the compaction whose epoch was not recorded, and the summary with a reasoning budget). A notice given in the middle of a turn that runs in one `world.run` (`rig.bulk` after a summary finished, in `context.rs`) cannot be sized by `fill_next`, which runs between turns; a request whose provider reported tokens (`counted`) has no twin; twelve notices that are each a place to cut are not one bulk; and a test that holds a window against the system prompt's room (`context.rs`, "the test holds from about 5,050 tokens") is about the prompt's size and says so. A test that passes within 5% of a threshold is not warned about by CI: which number is the threshold, and how near is too near, is the test's meaning and not its result.
- **They refuse what the twin cannot know**, with the numbers or the reason: a band the window cannot reach with that history; a session that has no history (`fill_next`) or has some (`fill`); a request the twin's turn never makes (how many it made, and which was asked for); a session whose store the rig does not hold, or that has compacted already; and a session any of whose requests was counted by its provider (a response that reported tokens), where the loop estimates from the count and the twin has none. A twin is resumed from items alone, so its estimate and the session's can differ by the few tokens of a notice: the tests allow eight.

**A directory of a test's own** is `cortex_testkit::Scratch`, made with the `scratch!` macro: a new, empty directory under the one Cargo gives the crate's integration tests, with helpers to write files and to make a git repository whose configuration is the test's own and not the machine's. It is removed when the test ends, and left in place when the test fails. A test that needs "no repository above this directory" asks for `Scratch::outside`, in the system's temporary directory. The tests of `cortex-config`, `cortex-policy`, `cortex-session` and `cortex-agent` use it. The ones that still have their own are listed in [steps/tooling-w5/answered.md](steps/tooling-w5/answered.md).

**Hostile names** are one set, in `cortex_testkit::hostile`, that every test of how a name is shown, kept, refused or looked up takes its names from (since the seventh tooling step). A name from a workspace is text the harness did not write; each test used to keep its own few of them, and one kept a constant that was a line feed on Linux and U+2028 on Windows, so that what it checked depended on where it ran, and a bug in how a line feed is shown could stay hidden on the system where the constant was U+2028. The set has a kind for each way a name is hostile: control characters (C0, DEL, C1), bidirectional controls (the embeddings, overrides and isolates, the marks, and names that use them to spoof an extension), other format characters (`Cf`: zero-width, joiners, the byte-order mark, the soft hyphen, the tag characters), characters that render as nothing and are not `Cf`, line breaks (LF, CR, CRLF, NEL, U+2028, U+2029), escape sequences for a terminal (CSI, OSC closed by BEL and by ST, the C1 forms), long names (254, 255 and 256 bytes, 260 characters, 254 and 256 UTF-16 units, a few thousand, and runs of characters whose escape is longer than they are), the names Windows keeps for devices (with other case, an extension, trailing dots and spaces, the superscript digits), combining marks, wide and emoji characters, right-to-left letters, punctuation that a file system, a shell or a glob gives a meaning (`..`, a leading `-`, a backslash, a colon, a stream, a quote, a trailing dot, an escape written out as text) and the replacement character. An entry is a `Name`: a label a failure message can print, the `text`, the `shown` form that `cortex_base::visible` must give it (written by hand, so that the function is checked against something other than itself), and its `Kind`. `hostile::of(kind)` and `hostile::all()` give them; `hostile::character(c)` and `hostile::named(label)` pick one.

**The rule: no constant per system that changes what a test checks.** The set has no `cfg` (a unit test reads its source for one), so the same entries are there on Linux and on Windows: a name that is hostile is hostile on both. What differs is what a *file system* takes: Windows refuses `CON`, a line feed and a colon in a file name, and Linux a slash and a NUL. A test that makes files asks the system at run time: `hostile::takes_file_name(dir, name)` makes the file in a directory of its own inside `dir` and reads back whether the directory holds exactly that name, and `hostile::accepted(dir, kind)` gives the entries of a kind that it does. The test runs its case for each of those, and fails when there are none, so that it cannot check nothing and pass; a test that makes no file (a path asked for that is not there, a reason, a notice) takes every entry. A case about one system's rule (a device name is refused on Windows, an ordinary file name on Linux) is in a file for that system and takes the same entries of the set. `cortex-base`, which is below the test kit (rule 6 of [architecture/01-workspace.md](architecture/01-workspace.md)), keeps its own copies in its tests; the test kit's unit tests check the set against `cortex-base` (`visible` and `acts_unseen`) instead.

**A crate's own unit tests cannot use test-kit types that are made of that crate's types.** The test kit depends on `cortex-llm`, so in `cortex-llm`'s unit-test build there are two copies of the crate, the one under test and the one the test kit was built against, and a `ModelEvent` of one is not a `ModelEvent` of the other. So `cortex-llm` tests its pure parts (the parser, the retry rules, the catalog, cost) as unit tests, and its client, which needs the scripted transport and the fake timer, in its integration-test binary. The parts of the test kit that involve only `cortex-base` types, such as the property helper, work in unit tests too.

**Fixtures.** Recorded provider responses live in the repo under each protocol's `fixtures/` directory: the raw response stream, the request that produced it, and a note. `xtask record` captures them from a real provider by hand, scrubs credentials and identifiers, and is never run in CI. Each provider step adds fixtures for every case in its checklist ([build-plan.md](build-plan.md)).

As built in step 14, for the first protocol:

- **Where.** `crates/cortex-llm/fixtures/<protocol>/<name>/`, with four files: `request.json` (the body that was sent), `response.sse` (the response body, byte for byte), `response.json` (the status and the headers that were kept) and `note.md` (what it shows, the model, and how it was made). `.gitattributes` keeps every file under a `fixtures` directory exactly as it is, line endings included.
- **Recorded, or written by hand.** A case that the real API produces on request is recorded. A case that cannot be provoked (an overload in the middle of a response, a refusal, a server-side tool, a stop reason from a newer API) is written by hand from the provider's documented format, and its note says so. Of Anthropic's 33 fixtures, 17 are recorded. Of the 72 of `openai-chat`, 56 are recorded, from OpenRouter, DeepSeek and Venice.ai; the 16 written by hand are OpenAI's seven and the local servers' five, for which there was no key and no server, and four cases that cannot be provoked (two failures in the middle of a response, a stop reason, and a fast tier's refusal). A fixture written by hand because its server was not there says so in the first line of its note, so that a recording can replace it.
- **The requests are shared.** The recorder builds each request with the same function the offline tests use. So a fixture's `request.json` is a snapshot of a request the real API accepted, and a test fails when the builder stops writing it. A recorded conversation is rebuilt the same way: each later request from what the decoder made of the response before it, and compared, byte for byte, with what was sent.
- **Recording.** `cargo xtask record [--provider PROVIDER] [SCENARIO…]` runs an ignored test of `cortex-llm` (the `live` module of the protocol's tests), and `cargo xtask live [PROVIDER]` the smoke test beside it, and then, for `anthropic` and `deepseek`, one headless run of the real binary: an ignored system test of `cortex-cli` (`tests/system/live.rs`) that hands the key to the binary's environment and runs a one-line task with one tool call, `--output json`, with the whole built-in toolbox. The provider is `anthropic` when none is named, or `openrouter`, `deepseek` or `venice`. `cargo xtask live --headless [PROVIDER]` (since the fourth tooling step) runs every headless test of `tests/system/live.rs` against the provider (`--test NAME`, since the sixth, runs the one named: its whole name, its name in the module or the end of it, `--test compaction`; `--dry-run` prints the commands it would run and whether the key file's variable is set, and builds, reads and sends nothing), under `cargo test` and not nextest, so a long session (step 15's compaction run) is not stopped at a system test's limit; with the key file and the ledger as `live` has them, and stopping before anything is built or sent without the key file. A test holds every ignored test of that file to a command. What the live tests of every protocol share (the transport that keeps what passes through it, the key, the spend limit) is `tests/it/live.rs`. They are there and not in `xtask` because `xtask` is built before every CI job, and the HTTP and TLS stack is the largest dependency the project has. No CI job runs ignored tests.
- **The key.** Each provider has a variable that names a file holding its key and nothing else: `CORTEX_LIVE_ANTHROPIC_KEY_FILE`, `CORTEX_LIVE_OPENROUTER_KEY_FILE`, `CORTEX_LIVE_DEEPSEEK_KEY_FILE`, `CORTEX_LIVE_VENICE_KEY_FILE`. The key is never an argument and never in the environment. Without the variable both commands say so and stop: they do not pass, and they do not skip.
- **What is taken out** (`cortex_testkit::fixture::Scrubber`). No request header is kept at all. Of the response headers only a short list is kept: the content type, `retry-after`, the request id and the rate limits of the model and of the fast tier. **The size of each rate limit is made up:** every `…-limit` is replaced by a round number chosen by what the limit counts (1,000 requests, 1,000,000 tokens, 100,000 output tokens), and every `…-remaining` by the same share of it, so that "all of it", "none of it" and "one request used" still read as they did. The ids the provider makes up (`msg_…`, `req_…`, `toolu_…`) are replaced by stand-ins, the same stand-in wherever the id appears, so that a tool result still names its call. The opaque payloads of reasoning blocks are replaced the same way: they are bound to the account that produced them. Every value of such a member that is not empty is replaced, whatever it looks like, and the member is also found where a block is quoted inside a string.
- **The servers of `openai-chat` write identifiers every which way** (a prefix and a hyphen, a bare UUID, a call id with underscores in it), so a recording of one finds them by where they are: the value of every `id` and `tool_call_id` member is an identifier, and is replaced wherever it appears afterwards, in any later exchange too. Of their headers the six `x-ratelimit-…` ones and `x-request-id` are kept, with the sizes made up in the same way. A UUID is an identifier wherever it is: one provider quotes its request id inside the message of a failure, where no member names it. The value of a request-id header is one whatever it looks like. **A stand-in is never replaced again:** a recording that quotes an earlier fixture (the conversation a second provider is handed) keeps that fixture's stand-ins.
- **A fixture says nothing about the account that recorded it.** The sizes of its rate limits would show its usage tier, which is why they are made up. A test checks that every limit in every fixture is the value the scrubber writes.
- **A recording that holds the key is refused.** Everything that is about to be written, and every line that is about to be printed, is searched for the key and for any twelve characters in a row of it. If it is there, nothing is written and nothing is printed. The refusal is tested with a made-up key, in the request, in the response, in a header that is kept and in the note.
- **What a run costs.** Each call prints what it used and what that cost at the catalog's prices, and a run stops before it has spent half a dollar. **Each call is also a line in a spend ledger,** outside the repository: the user's state directory (`~/.local/state/cortex-live/spend.jsonl`, or `%LOCALAPPDATA%\cortex-live\spend.jsonl`), or the file `CORTEX_LIVE_LEDGER` names. A line holds the date, the provider, the model, the tokens, the cost and the test; it is checked for the key like everything else a live run writes. `cargo xtask live --spent [--since YYYY-MM-DD]` totals it by provider and model. Since step 15 the headless runs of the real binary are in it too: each adds a line from its `--output json` record's tokens and cost (`cortex-cli`'s `tests/system/live.rs`).
- **A dry run.** `cargo xtask record --provider PROVIDER --dry-run SCENARIO` builds the scenario's first request, prints its method, URL and body, and sends nothing. It reads no key, so it needs no key file, and it does not ask a provider's usage endpoint. It stops at the first request, because what a scenario sends after it is built from the response. Recording all of Anthropic's fixtures cost about one and a half cents. Where a response states its own cost (OpenRouter, Venice.ai), that is the figure counted, and a run ends by asking the provider's usage endpoint how far its own figure moved; only the difference is printed. Recording the `openai-chat` fixtures cost under a cent for all three providers together.

**The toolbox fixtures.** Step 13b's one live run found three refusals by Anthropic's strict mode of the real built-in toolbox, which no fixture could have shown: the fixtures declared one small tool. Since the second tooling step, the real toolbox is recorded too.

- **What the binary sends is kept.** A system test of `cortex-cli` (`tools::sys_the_toolbox_the_binary_sends_is_the_one_its_fixtures_were_recorded_with`) runs the binary against the scripted server for the cheapest catalog model of each recorded provider (Anthropic's `claude-haiku-5-5`, DeepSeek's `deepseek-flash`, OpenRouter's `z-ai/glm-5.3-flash`, Venice.ai's `deepseek-v4-flash-0731`) and reads the tools of its first request: the real toolbox, through the real request builder and the strict reduction where the model has strict tools (only Anthropic's of the four). They are kept in `crates/cortex-llm/fixtures/toolbox/<provider>.json`.
- **A request with them is recorded** from each provider, with a short system prompt and a one-line task that needs no tool: the fixture `toolbox` of `anthropic-messages`, and `<provider>-toolbox` of `openai-chat`. All four providers accepted it on 2026-11-13, for $0.0022 together.
- **Two tests in `cortex-llm` hold the builder to it** (`tests/it/toolbox.rs`): built from the kept tools, a request declares them exactly as the binary did (name, description, schema and `strict`); and its bytes are the recorded `request.json`, which the provider accepted. A change to the builder or to the strict reduction that changes what is sent fails there, until it is recorded again. The fixtures are replayed at every cut like the others.
- **A change to the toolbox is a warning,** not a failure: the system test compares the tools the binary sends now with the kept ones (all but the shell tool's description, which names the machine's shell; on Linux only, since the kept tools are a Linux machine's) and, when they differ, says so on the job's summary page. Whether a provider still accepts the new tools is known only from a recording.
- **Recording it again:** `cargo xtask record --toolbox [--provider PROVIDER]` keeps the tools the binary sends now to the provider named, or to every provider whose key file is named in the environment (the system test in its writing mode, `CORTEX_UPDATE_TOOLBOX=<providers>`), then records the toolbox scenario from each. A provider that is not recorded keeps the tools of its recording, so a change to its tools stays a warning. The command fails unless the capture test really ran. It refuses `--dry-run`: `record --provider P --dry-run toolbox` prints the request instead. Snapshots of the new streams are written with `CORTEX_UPDATE_SNAPSHOTS=1`, as for any fixture.

**Replays at every chunk boundary.** Stream decoders are tested by replaying each fixture split at every byte offset, which catches the bugs that only appear when a network read ends in the middle of a token.

- Each stream fixture is decoded whole, one byte at a time, in pieces of several fixed sizes, and cut in two. The events must be the same every time, and what they are is in a snapshot for each fixture.
- **The work is bounded, and divided between two places,** as step 4 learned it must be. Cutting a stream of `n` bytes in two at every byte decodes `n` bytes `n` times, in a build that does not optimise the JSON reader. For the 26 streams of step 14 that is 200 MB of decoding. On the step's first CI run it took 22 s of test time on Linux and about 40 s on Windows, and put the integration tier over its budget there (51.6 s of 40 s, a warning). So:
  - **on every pull request,** each stream is delivered one byte at a time, which puts a boundary at every byte of it, and in pieces of two other sizes; and it is cut in two at each of its first 64 bytes and at about fifty places spread over the rest (a hundred places and seven sizes until 2026-11-13, when the Windows integration tier was at its budget);
  - **in the nightly run,** which already multiplies the property cases and has time limits of its own, each stream is cut in two at every byte, and delivered in pieces of seven other sizes.
- **The streams of `openai-chat` are larger**: one records 104 kB for 385 tokens, because the server sends a chunk of 300 bytes for each token of reasoning. So for them the number of cuts goes down as a stream gets longer (between 8 and 50 on a pull request), a stream over 16,000 bytes is cut in two at about 4,000 places in the nightly run and not at every byte, and one test replays all of a server's streams: a process for each stream cost more than the decoding did. Measured in CI's own build profile on the build machine before the push, the sum of the protocol's test times was 2.8 s against 2.4 s for Anthropic's (3.8 s before the streams of a server shared a test).

**Golden transcripts.** Sequences of protocol messages from released versions are kept and replayed against current types, to catch accidental breaking changes to the RPC protocol. The first one, written by hand in step 3, is `crates/cortex-protocol/tests/golden/v1-session.jsonl`: every method, every event type and every kind of item, part, delta, notice and plan edit of protocol version 1. Three tests use it: each line must read into its typed form and write back as the same JSON; the same must hold after a field no version knows is added to every object; and each line must be valid against the generated schema ([architecture/11-rpc-protocol.md](architecture/11-rpc-protocol.md)). A transcript is not edited to make a test pass. The types that travel in no message have golden values in a second file beside it, and a test fails, naming the type, when a type in the schema has a value in neither. An addition to a released version gets a new golden file.

**No paid API in CI.** Pull-request jobs have no secrets. The scripted fakes and fixtures cover everything that blocks.

**Usage records from other tools.** The adapters in [architecture/18-usage.md](architecture/18-usage.md) are tested only against small, made-up example files written for the purpose: one set per format version an adapter supports, plus damaged and unknown-version examples. Real session data from any tool is never used as a fixture and never committed. The static check that rejects home-directory paths covers the fixture folders, and an adapter test asserts that no text from the input reaches the output.

### A month of statistics, made up

A test of the usage view, of the panel that shows it, of the readers of other tools' files or of a measurement of `cortex usage` needs a month of statistics that looks like a person's: working days and days off, many sessions, a spread of models, a cache that is mostly read. Real data is never a fixture (above), and a month by hand is a month of one kind. `cortex_stats::synthetic` (since the sixth tooling step, `crates/cortex-stats/src/synthetic.rs`) makes one.

- **Where it lives, and why.** In `cortex-stats`, behind its `test-hooks` feature, and not in the test kit: it makes the crate's own `Record`s and writes them through the crate's own `Recorder`, and the test kit may not depend on `cortex-stats` ([architecture/01-workspace.md](architecture/01-workspace.md), rule 6 and the table). The crate's own unit tests have it with no feature. Another crate's tests ask for it in `[dev-dependencies]`: `cortex-stats = { workspace = true, features = ["test-hooks"] }`. `cargo xtask rules` fails when anything else turns the feature on, as for `cortex-tools`.
- **Use.** `synthetic::write(&StatsDir::new(dir), &Spec::month(seed, Scale::HEAVY))` fills an empty directory with `events-2026-10.jsonl` and `aggregates.json`, and returns a `Summary`. `Spec::year(seed, scale)` is twelve months from January 2026, one file each, for "a year of generated history"; `Spec` has the first month, the number of months and `days` (only the first so many days of each month; `with_days(n)` and `with_months(n)` set them) as fields. A test that reads the directory sees exactly what a user's holds: the writer thread wrote it, and the aggregates were brought up to date by the real sync, with "today" at the end of the last month written (a year or less folds and prunes nothing).
- **The scales.** `Scale::LIGHT` (about 200 requests a month: two days in five, a session or two, short turns), `TYPICAL` (about 1,500: weekdays, two or three sessions of a dozen turns), `HEAVY` (about 5,000: nearly every day, weekends half of them, four or five long sessions a day, every provider, the fast tier, subscription billing and a judge) and `EXTREME` (some 90,000: the size step 16 measured disk use at; for a release build, not a debug test). A scale is a plain struct of ranges and percentages, so a test that needs another makes one.
- **What a month holds.** Per session: a project, a main model drawn from the catalog's own names (`claude-opus-5-5`, `gpt-6-luna`, `deepseek-v4-pro`, `openai/gpt-6-luna` through OpenRouter and the rest) with its catalog prices, billing (metered, or subscription with the cost as an estimate), a speed (the fast tier where the model offers one, with some requests falling back to standard and recording `speed_requested`), the variants and effort level. Per turn: two to four requests of the main model with the tool calls between them, in the ways a call ends (ok, failed, invalid arguments, unknown tool, denied, interrupted), the turn's own ending (completed, failed by a failed request, interrupted, limit, denied), the verification result where files were edited, the split of the wall time and each tool's share. Per request: tokens by class with the cache read on most requests and lost when the user was away more than five minutes, cache writes on the providers that report them, reasoning tokens, the cost at the model's price, time to first token, tokens a second, a few retries and a few failed requests with no tokens and no price, and a context record. The `fast` role writes a title at the start of a session and a summary when the context passes 160,000 tokens (which begins a new epoch); the `judge` role appears in the heavy scale. Nothing in it is taken from anyone's use.
- **Deterministic.** The seed is the whole of the randomness (`cortex_base::SeededRng`); nothing reads the clock, the time zone or the environment; days are UTC; and only integer arithmetic and exact divisions are used. One seed gives the same bytes on both operating systems, which a test holds by writing a month twice and comparing every file.
- **The summary is an independent count.** `Summary` is added up from each event as it is made (requests, failed requests, tool calls, turns, contexts, lines, active days and days off, usage by day and model, turns by outcome, calls by tool, wall time), by code that shares nothing with `Part::add_line`. A test compares it with what `Aggregates` and a reading of the files say, so it checks the crate's reader as much as the generator. The ordinary tests do that for a week of a light user and a day of a small mixed scale, and for two months; the measurements below do it for a whole light, typical and heavy month and a year.
- **What the blocking tests cost, and what they leave to a measurement.** The blocking tiers run seven tests of the generator, 60 ms in all at the desk in the `ci` build, one at a time (each is a day or two of a small month, 5 to 15 ms with the test's process start). They are: one seed gives the same bytes; another seed gives other figures; a week of a light user and a day of the mixed scale each read back as the summary says (and a light week has days off and days worked); two months are two files that add up; a two-day month of the mixed scale has its roles, speeds, billings, failed requests and cache reads and every cost is its tokens at the catalog's price; the scales' differences, from their parameters (no month made); and the models and prices against the catalog. `MIXED`, a scale of the tests' own, works every day at rates far above a real user's (failures, fast tier, subscriptions, judge), so that two days show kinds a real month shows in weeks. **No ordinary test asserts on a time.** What needs a whole month is `perf_` and ignored, as the repo's measurements are, and run by hand: `cargo xtask test -p cortex-stats --run-ignored only perf_ --no-capture` (nextest shows a passing test's output only with it), or on a runner `gh workflow run try --ref <branch> -f os=windows -f command="perf -p cortex-stats"` (or `try -f command="test -p cortex-stats --run-ignored only perf_"`): `perf_the_scales_made_and_timed` (a light, a typical and a heavy month, each read back and compared with its summary, with the table below printed), `perf_a_heavy_month_has_every_kind_priced` (every outcome, role, purpose, provider, difference and verification kind, the summaries on the `fast` role, and every cost) and `perf_a_year_is_twelve_files_and_adds_up`. They print their times and assert on none. Measured on the desktop, `ci` build: a light month (550 lines, 0.3 MB) 14 ms, a typical one (5,500 lines, 2.9 MB) 133 ms and a heavy one (19,400 lines, 5,400 requests, 10 MB) 465 ms, and a light year (7,500 lines) 196 ms, in the process that makes it. Most of it is the real writer serialising each line and the real sync reading it back, not the generator, and reading a month again (parsing every line) costs about as much as making it. On a hosted Windows runner the heavy month took 3.25 s, which is why it is not in a blocking tier.
- **Breaks.** `mutations/tooling-6.breaks`: the seed ignored, something besides the seed deciding, the summary missing a kind of event, days off that never come, a cache never read, a fast request priced as standard, a price that drifts from the catalog (the generator's prices are held to `catalog/models.toml` by a test that reads it), and a queue too small for the events made between two waits for the writer. Each names ordinary tests: `mutate` never runs an ignored one.

## Showing that the tests bite

A test that passes says little until it has been seen to fail. Two things are checked before a step is reported, with a command for each: that a test does not pass only because of the order things happened to run in, and that it fails when the rule it tests is broken.

### A seeded order of events

**Where the order came from.** The loop plans each tool call, and bounds each result, on the blocking pool (`cortex_tools::run_blocking`). Those are real threads, and they finish when the machine lets them: a call's plan arrives before or after the response's next event, and one call's plan before or after another's. The loop itself looks at what is ready in a fixed order and picks nothing at random. A test of step 12 failed three runs in ten for this reason, and a break of the code was once reported as caught by a test that had only lost that race.

**What a test of the loop does now.** `cortex-agent`'s rig (`crates/cortex-agent/tests/it/main.rs`, `World`) puts that work on the test's own thread, at moments a seeded generator decides. The session already runs on a single-threaded runtime on that thread, so with the blocking work there too, **one seed is one order of events, on every machine.** That holds for work that goes through `run_blocking`, which is all the loop has. A thread that a test or a tool starts by itself is still the machine's to schedule. And work given to `run_blocking` must not wait for another task of the same runtime (a gate, a channel): on the pool it would be let go, and on the test's only thread it never is.

- **The seam** is `cortex_tools::InlineBlocking`, behind the `test-hooks` feature of `cortex-tools`. While one is alive, `run_blocking` called on the thread that made it runs its work on that thread, after a number of turns of the runtime drawn from the seeded generator (none to eight, mostly few). Work whose token fires before its turn comes is not run, and the caller gets "cancelled", as it does from the pool.
- **Only tests have it.** A dev-dependency turns the feature on, and `cargo xtask rules` fails when anything else does. A build of the binary by itself (`cargo build -p cortex-cli`, the `dist` build) resolves `cortex-tools` with no feature, and the released binary has none of it. A build of the whole workspace with its tests (`cargo nextest run --workspace`) resolves it with the feature, for every crate in that build, so the binary the system tests start has the branch compiled in. It does nothing there: the switch is a thread-local that only an `InlineBlocking` sets, and only a test makes one.
- **The seed** comes from `cortex_testkit::seed::for_this_test()`. An ordinary run uses 0, every time. `CORTEX_TEST_SEED=<n>` fixes it. In a run of `cargo xtask stress`, repeat `n` uses the first seed plus `n`.
- **A failed test shows its seed.** The rig prints `test seed 17: run this test again in the same order with CORTEX_TEST_SEED=17`, and the test runner shows a test's output when it fails.
- **A test must pass under every seed.** It asserts on what the loop promises (the results are recorded in the model's order, a refused call stops the turn at that call), and where it needs one order it makes it, with a gate. It does not assert on an order the seed decides.

When the rig was seeded, every test of `cortex-agent` passed under seeds 0 to 299: none depended on an order.

**Other rigs.** A crate whose tests drive the loop or the tools on a single-threaded runtime (the core's, from step 13) takes the same two lines: `cortex-tools` with `test-hooks` in its dev-dependencies, and an `InlineBlocking::seeded(cortex_testkit::seed::for_this_test())` kept for the life of the test. A test whose order is the operating system's to decide (processes, sockets, threads of its own) cannot be seeded, and is repeated instead.

- **The core's own operations' blocking work goes through the same seam** (since the review of step 13a): putting a session together, a fork's and a rewind's work on the log, the end of a session. So a core test's seed orders it with the loop's. What the core does for the loop through its seams is still on real threads, in the machine's order: the session store's writes, recording an approval the user chose to keep, recording a round's changes, reading an image; and so are a command's process and the base state's capture.
- **A test that acts between two steps of an operation** uses `InlineBlocking::after(n)` in place of a seed: every piece of blocking work waits exactly `n` turns of the runtime. With `after(1)`, each piece is one `Pending` of the future waiting for it, so a test that polls the operation by hand knows what is under way when it acts. The core's rig has it as `World::one_turn_each`, and the tests of a client that leaves, and a shutdown that begins, while a session is being put together use it (`crates/cortex-core/tests/it/lifecycle.rs`). Before it, such a test held the runtime's one blocking thread itself (`max_blocking_threads(1)`), which can order the first piece of work and not the second.

### A point the library stops at

**Why.** A race test needs the library to stop at a precise place: between a read and the write that follows it, between a file's new content being complete and the rename that publishes it. Nothing from outside can make it stop there, so such tests relied on timing (a reader that spins until it sees the window), on a thread held by hand, on a FIFO or on a loop that tries until the race happens. Since the seventh tooling step the library marks the place, and the test holds it.

```text
library:   cortex_base::hook::point(cortex_base::atomic::BEFORE_THE_RENAME);
test:      let hold = Hold::new(cortex_base::atomic::BEFORE_THE_RENAME);
           let writer = std::thread::spawn(|| write_atomic(…));
           hold.reach();             // the writer is stopped there
           …                         // read the file, change it
           hold.let_one_go();        // or release()
           writer.join()
```

- **Where it lives.** `cortex_base::hook`, in the lowest crate every library depends on. `point(name)` is the library's side; `Hold` is the test's, behind the `test-hooks` feature of `cortex-base`. A point's name is a sentence a failure can print, and the module that marks it exports it as a constant (`atomic::BEFORE_THE_RENAME`), so that a test cannot misspell it. `cortex_testkit::Hold` is the base crate's `Hold` with what only the test kit can add: its waits are named in the timeout report, `reach()` fails with a message, and the same methods are reached through `Deref`. `cortex-base`'s own tests have no test kit (it depends on `cortex-base`), so they use `cortex_base::hook::Hold` and ask for the feature with a **dev-dependency on the crate itself**, which Cargo allows and which keeps `cargo xtask test -p cortex-base` building the tests that need it (the crate-alone run of a feature-gated test is otherwise dropped). The test kit turns the feature on for every crate that has it as a dev-dependency.
- **With the feature off a point is nothing.** `point` is an empty `const fn` marked `#[inline(always)]`: no code, no symbol, no data, not the load of a flag. Every build of the product has it off. Shown, not argued: the assembly of the whole of `cortex-base` (`cargo rustc -p cortex-base --release --lib -- --emit=asm -C codegen-units=1`) is **byte for byte the same with `write_atomic`'s point and without it** (2,670,711 bytes of assembly each), and holds neither the point's name nor a symbol of the module. Repeat it after a change of `point`.
- **With the feature on and nothing held a point is one load.** It reads a counter, the holds alive in the process, and returns when it is zero: 1.0 ns over an empty loop (1.8 ns against 0.7 ns an iteration, a release build on the laptop, a billion calls). While a test holds some *other* point, a miss takes the registry's lock and a search: 41 ns, and only in a test that holds something. A test build has the feature on for every test and for the binary the system tests start (features are unified across a build of the whole workspace's tests), so there the points do nothing, as `InlineBlocking` does ("A seeded order of events", above).
- **Only tests turn it on.** `cargo xtask rules` holds a `test-hooks` feature to dev-dependencies and the test kit, in any crate that has one (the rule reads the feature's name): a normal or build dependency that asks for it, `default` or another feature of the crate that lists it, and a feature of another crate that passes it on are refused. For `cortex-base` the rule was extended in one place: a dev-dependency of a crate on itself is no edge of the crate table ("Which crate may depend on which"), where a normal one still is refused. The checks of both are unit tests of `rules::crate_graph`.
- **What a hold does.** Every thread that arrives at the held point stops until the test lets it go or the hold's bound passes (5 s, `Hold::with_limit` for another). Past the bound the thread goes on, and the hold counts it (`timed_out`), so that a mistake is a failed test and never a hung one. **Every wait of the test's side has a bound too**: `wait_reached(limit)`, `wait_reached_times(n, limit)` and `wait_stopped(n, limit)` return whether the thing happened, and `reach()` fails the test with a message when the library does not arrive.
- **When no test holds a point it passes at once;** a point that nothing reached is a point that has no arrival, and the hold says so (`arrivals()`).
- **The n-th arrival.** `skipping(n)` lets the first `n` arrivals through and stops the next ones: the second write of two, the third read. `let_one_go()` lets one stopped thread go on (one of those stopped, in no order: whichever wakes first; or the next to arrive) and keeps the others; `release()` lets all of them go, and every later arrival pass; dropping the hold releases it, so a test that fails never leaves a thread stopped.
- **Two tests in one process.** `cargo test` runs tests as threads of one process, and a hold is the process's. Two holds of one point do not live together: the second waits, within its bound, for the first to end, and fails with a message that says why when it does not. But any thread of the process that arrives at a held point stops, whichever test it belongs to, because the library cannot know. nextest gives each test a process of its own, which is how the workspace runs its tests, and there a hold is the test's alone. A test that holds a point is written for that: it does not claim to be safe under `cargo test` beside tests that run the same library code.
- **A wrong name is found.** The points that threads reached while any hold was alive are remembered, and a test whose point never came says which they were: a name that differs by a character shows up beside the one the test gave.
- **The timeout report names it** ([When a test runs out of time](#when-a-test-runs-out-of-time)): the test's wait is `waits for the library to reach the hold of the point … made at crates/…:40:16`, and each library thread stopped at a point is `stopped at the library point …, held by a test until it lets the thread go`.
- **First use.** `write_atomic` has one point, `BEFORE_THE_RENAME`: the new content is complete in its temporary file and the target has not been touched. `cortex-base`'s `a_reader_sees_the_old_content_or_the_new_and_never_a_mixture` held a reader spinning on a file while a writer replaced it a hundred times, and saw the window by chance. It now stops the writer there, four times, reads the target three times each (exactly the old content, with the temporary file beside it), lets the writer go and reads the new content. Every assertion is kept (reads were made, none was neither version, the replaces happened, the last content is one of the two, nothing is left in the directory). A second test, `a_file_that_is_created_is_not_there_until_its_content_is_complete`, looks at the directory at the same stop: the name is not there yet, which a reader that looks at the end of a write cannot see, and which no test saw before (its break creates the empty file early). **A break that the spinning reader also catches was measured:** a write that truncates the target before the rename left the target empty for the whole of the content's write, and the old test failed it at once (326,359 of 326,839 reads saw neither version). The point does not find more of those; it finds the state at a place nobody could stop at, and makes the finding the same on every run, in 11 ms and 12 reads, where the old test made 100 replaces and about 300,000 reads.
- **How it is tested.** The hold's own behaviour in `cortex-base`'s unit tests (a thread stops and goes on after the release, the bound, the n-th arrival, one let go and the others kept, a second hold, a dropped hold, the points remembered); the test kit's in its own (the report names a stopped thread, a point that never came says what did, a hold is named by where it was made); breaks of each in `mutations/tooling-7.breaks`.

### Running the tests many times over

`cargo xtask stress -p <crate>… [--count N] [--first-seed S]` runs the crates' tests `N` times over (100 when not given), and reports each test that failed on some repeat:

```text
1 test(s), 40 time(s) each, with seeds 0 to 39.

FAILED 20 of 40 times: cortex-agent::it order::stress_fixture_expects_the_first_sessions_call_to_start_first
  seeds: 0, 1, 2, 6, 7, 8, 11, 14, 16, 17, 18, 22, and 8 more
  again: CORTEX_TEST_SEED=0 cargo xtask test -p cortex-agent -E 'test(=order::stress_fixture_expects_the_first_sessions_call_to_start_first)'
```

That is the command's own test case, a test that is wrong on purpose (below). Seed 0 fails it every time and seed 3 passes it every time.

- The repeating is nextest's (`--stress-count`, in a nextest profile of its own, `stress`). The command sets the first seed, reads which repeat of which test failed from the JUnit report, and says how to run one failure again. Anything it does not know goes to nextest: a filter, `-E`, `--run-ignored`.
- **Each failing test's message is printed** (since the fifth tooling step), read from the same report: under the test's seeds, its first failure's text, which is the panic's message for a test that panicked (the thread's name taken off, as the test is named) and, for a timeout, what the test wrote to its standard error, where the test kit's timeout report is. Six lines at most, each cut at 160 characters, with how many more there were; then the first line of up to two other failures of the test whose text differs (digits aside: a seed, a process id, a time), the count of the rest, and the report's path for all of it:

  ```text
  FAILED 2 of 3 times: jx tests::flaky
    seeds: 40, 42
    failure, under seed 40:
      | panicked at src/lib.rs:11:9:
      | assertion `left == right` failed: the repeat was even: 0
      | with a second line
      | and a third
      | and a fourth
      | and a fifth
      | … and 4 more line(s)
    all of it: target/nextest/stress/junit.xml
    again: CORTEX_TEST_SEED=40 cargo xtask test -p jx -E 'test(=tests::flaky)'
  ```

  A test that passed only on its retry shows the failure it needed the retry for. Its tests read a report nextest wrote for the purpose (`xtask/fixtures/stress/junit.xml`).
- **Timeouts that end together are taken for the machine** (since the sixth tooling step; `xtask/src/stall.rs`). A test that hangs by itself is stopped at its own limit, counted from its own start. When a shared machine's disk stalls, the test runner's timers are late too and fire together when it comes back, so a dozen tests of crates nobody changed are stopped within moments of each other whatever time each started. When three or more of a run's timeouts end (their start plus their time, from the JUnit report) within 250 ms of each other, `stress`, `ci` (each test run that fails) and `mutate` say so, with the evidence:

  ```text
  STALL: 8 tests timed out within 140 ms of each other: likely the machine, not the tests.
    cortex-session::it durability::…
    …
    I/O pressure (/proc/pressure/io) now: some task waited 40.0% of the last 10 s and 15.5% of the last 60 s; every task at once 30.0% and 10.0%.
    During this run's 312 s, some task waited on I/O for 41.3 s, and every task at once for 30.2 s.
    Run them again, alone or with fewer jobs, before reading anything into these timeouts.
  ```

  The pressure is read when the run starts and again at its end, so the stall time is the run's own. Where there is no `/proc/pressure/io` (Windows, or a kernel without it) the message says that it could not be read and why. One test's timeout, two together, or timeouts a second apart are not a stall, **and nor are tests stopped on time:** a test that hangs, by itself or on a bug it shares with others, is stopped at its own limit (10 s, 60 s for a system test, 300 s in the `properties` run, 1,800 s for a measurement; a test holds the list to `.config/nextest.toml`), and only a test stopped more than 250 ms past its limit counts. Two reviews of the step found the cases that rule is for: a break in `mutate` that hangs a crate's tests stops the first wave of them together, and stops system tests at 60 s in the same moment as a later wave of 10 s ones; taken for the machine's, such a break was never judged. What it cannot tell: a stall short enough that the runner's timers were not late. `rx` prints a line of its own when the desktop's disk stalled during a run; this is the commands' own, wherever they run.
- **`ci` runs a cluster of timeouts again, once, when the disk stalled** (since the eighth tooling step; `xtask/src/stall/rerun.rs`). In wave 11 six sessions of seven lost time to a stalled disk at the owner's desk: a person had to read the output, see that it was the machine, and run the tests again by hand. Each of the two test runs of `cargo xtask ci test` (`run tiers 1 and 2`, `run the system tests`) now does that when it fails, under rules that never let a failure through. **It runs tests again only when all three hold:**
  1. the run failed;
  2. its failures hold a cluster that the check above finds: three or more timeouts, each stopped late, ending within 250 ms of each other (a lone timeout, timeouts at their own limits, or timeouts apart are never one; a test that passed on its retry is not a failure of the run, so it is not counted);
  3. the pressure says the disk stalled during the run: every task waited on I/O for **10% or more of the run's time** (`full` of `/proc/pressure/io`, its counter after the run less its value when the run started, over the run's wall time; the threshold is `xtask/src/stall.rs`' `STALLED_SHARE` and is the one of the tier check, with the reasons, above).

  **What it runs again** is the cluster's tests, once, each named by its binary and its name exactly (`-E '(binary_id(=cortex-session::it) and test(=durability::…)) or …'`, in place of the run's own filter, with the run's other arguments), and no others. The run's other timeouts, a test that failed in any other way, and a timeout that is not in the cluster are not run again and still fail the step; a test whose name a filter cannot be trusted to name exactly (characters other than letters, digits, `_ : / . -`) is not run again either. **What it leaves in the report** is the run's own report with the cases of those tests replaced by the cases the re-run wrote (`xtask/src/junit.rs`, `replace_cases`; the failure counts of each suite and of the whole are made again from the cases), so that the tier check and `ci-times` read one report, with the times the tests really took. **The step passes only when,** after that, the report holds no failed case, the re-run's command succeeded, and every test run again is in the re-run's report and passed. A test that times out again, one that fails, one that is missing from the re-run's report, and everything else that failed, each fails the step, which says which. The output says what it did:

  ```text
  STALL: 8 tests timed out within 140 ms of each other: likely the machine, not the tests.
    …
  Running the 8 tests that timed out together again, once: the disk stalled during the run (every task waited on I/O for 41.3 s of its 312 s, 13.2%; …). A test that times out again, and every other failure, still fails this step.
    cortex-session::it durability::… passed on the re-run
    …
  All 8 tests passed on the re-run, and nothing else failed: the step passes. Their times in the report are the re-run's.
  ```

  and a cluster that is not run again says why (`Not running them again: the disk did not stall during the run: every task waited on I/O for 1.2% of its time, and a run is taken to have stalled at 10%.`, or that the pressure could not be read). The job's summary page lists the tests run again and how each did. **On CI and on Windows:** the same rules hold on CI (`cargo xtask ci` is what CI runs). Ubuntu's kernels give `/proc/pressure/io`, so on the Linux test job a cluster of late timeouts during a stall of a tenth of the run is run again there too, by the same rules, and says so in the log and on the summary page; the tier budgets are judged there whatever the pressure (above). Windows never gives the file, and where the pressure cannot be read a cluster is a failure that is not run again: so on Windows nothing changes. **`CORTEX_PRESSURE_FILE`** names a file, in the kernel's form (`some avg10=… total=…` and `full …` lines), to read in place of `/proc/pressure/io`, on any system: it is how the tests give the decisions a recorded pressure and never a real stall, and how a person tries one by hand (the commands read it once when a run starts and once when it ends, so a fixed file says no time stalled; `mutate`'s one-job rule reads it too). **How it is tested:** the decisions are functions of the failures, the pressures and the reports (`stall::rerun::decide`, `verdicts`, `run`, `stall::judge`, `junit::replace_cases`), and the tests of them (`stall::rerun::tests`, `stall::tests`, `junit::tests`, `tiers::tests`) give them pressures and reports written for the purpose: a cluster with a stall is run again; one with no stall, one with no pressure to read, a lone timeout, and a cluster of tests that passed on a retry are not; a timeout that recurs, a test missing from the re-run, a re-run whose command failed and a failure of another kind beside a re-run that passed each fail the step; the report left has the re-run's cases and true counts. Nothing runs nextest or stalls a disk. What it cannot tell: that a stall short enough to leave the pressure under 10% of the run made the timeouts (the step fails, and a person runs the tests again); that the first run's other tests, which ran in the stall too, were slowed (the report keeps their times, and the tier check does not judge such a run at a desk, above); and the Windows side, where it never re-runs, is untested there beyond the unit tests, which run on both systems. **Not changed:** `ci --tiers`, `ab` and `stress` do not re-run: they are measurements, and a stalled one is run again by a person.
- **A test that passed only on its retry counts as failed for that repeat.** nextest gives a test in a `timing_sensitive` module one retry, and reports it as passed when the retry passes. A test that needs its retry some of the time is what this command looks for.
- **For a seeded rig** each repeat is another order, and the seed brings a failure back exactly. **For process and thread tests** each repeat is another roll of the machine's own dice, and the seed means nothing: a test that fails one time in two hundred there is still a test with a race in it.
- **`--cores K --load N` squeezes the run:** the command pins itself, and with it cargo, nextest and every test process, to the first `K` cores it may use, and runs `N` busy loops beside them on the same cores. A race whose window is a few microseconds on an idle machine opens wide enough to be hit. The tests are built first, unpinned. On Linux the pin is `taskset`'s; on Windows PowerShell sets the process's affinity mask. The busy loops are threads of the command, so they end with it however it ends. The SIGINT flake of step 13b failed about once in a thousand runs on an idle desktop and was found only this way, by hand.
- **Run it before reporting a step,** for `cortex-agent` and for every crate whose tests start processes or cross threads: `cargo xtask stress -p cortex-agent --count 300` takes 17 s on the desktop. Stress first, then break the code: a test that fails by chance makes a break look caught.
- **How it is tested.** Its reading of a report, on reports written for the purpose (unit tests). And by hand on the test above, `order::stress_fixture_…` in `cortex-agent`: it expects the first of two sessions' calls to start first, which nothing promises, so it fails under about half the seeds. It is ignored in every ordinary run; `cargo xtask stress -p cortex-agent --count 40 --run-ignored only stress_fixture` runs it.

### When a test runs out of time

nextest stops a test at its tier's limit and says only that it timed out. Since the second tooling step, a test that uses the test kit's waits says what it was doing first (`cortex_testkit::watch`).

- **When.** The first time a test process uses a `Gate`'s blocking wait, the scripted server, a `Roll` or `children::until`, one thread starts that does nothing until the test has used four fifths of its limit: 8 s of 10 in tiers 1 and 2, 48 s of 60 for a system test, 240 s of 300 in the `properties` profile, read from the profile nextest names (`NEXTEST_PROFILE`) and the test's name. A test unit-tests that these agree with `.config/nextest.toml`. On Linux the time is counted from the process's start; elsewhere from the first wait ([outstanding](outstanding/timeout-report-timing-on-windows.md)). If the test is still running then, the report goes to its standard error, the waits first and then the process tree, which on Windows takes PowerShell a moment, which nextest shows with the failure and keeps in the JUnit report. A test that passes never reaches it, and pays for one thread that waits and a lock when a wait starts and ends.
- **What it says.** Each wait in progress, longest first, with the thread that waits: the gate, named by where the test made it (`the gate made at crates/…/x.rs:40:16`, from `#[track_caller]`); the scripted server's connection by number, method and path, and the step of its script (reading the request, holding the response until a gate opens, waiting for a gate before step 3 of 5, holding the connection until the client hangs up); a child of a roll by name and process id; a thread of the library that a test's `Hold` has stopped at a point of its code, by the point and for how long (since the seventh tooling step, [A point the library stops at](#a-point-the-library-stops-at)). Then the process tree under the test, each process with its state and command line. On Linux, each thread's name, state and wait channel (the kernel function it sleeps in), and its kernel stack where the system lets it be read (as root). On Windows, each thread's state and wait reason, asked of PowerShell; thread stacks are not read there.
- **Not covered.** A test that uses none of the test kit's waits gets no report, unless it calls `cortex_testkit::watch::doing("…")` or `watch::arm()` itself. Rust offers no way to read another thread's stack from inside the process, so the report says what each wait is, not where in the code each thread is.
- **The fake timer's waits are in it** (since the fifth tooling step): a wait of a manual `FakeTimer` is named while it runs, with its length and the fake time it was made at, and that it ends only when the test moves the clock. The core's rig hung on such a wait (the shell's grace for a process left running) for a minute with nothing printed; now the report at 8 s says so.
- **A question nobody answers fails a rig's test at once** (since the fifth tooling step). The core rig's `Front` waits for a turn's end in `turns()`; an approval request that arrives meanwhile, and that the test did not take up with `approval()`, is answered by the front's `Answering` (`allow_all()`, `deny_all()` or `with(…)`, set with `front.answering(…)`), and with none the test fails, naming the call, once what is already on its way has arrived. A turn that asked what the test did not expect used to wait for ever. The agent rig's `ScriptedPolicy` answered every unscripted question by allowing the call, which could hide a question that should not have been asked: it now refuses such a call, so nothing runs, and fails the test when its rig goes, naming the call, unless the test answers with `answer_for(tool, …)` or `answer_all(…)`. (A panic in the question would not do: the loop makes a question's panic an error for its call, and goes on.)
- **Outside nextest it does nothing,** and never in a child a test started from its own binary.
- **How it is tested.** Against a test that hangs on purpose (`watch::tests::hangs_on_purpose`, which does nothing unless started for this): a gate nobody opens, a scripted server holding its response, and a child process. A system test runs it with a limit of one second (`CORTEX_WATCH_LIMIT_MS`), reads the report, kills the tree and checks it names both gates, the connection and the child. It is ignored in the blocking checks, where it would cost a second of the system tier and more on Windows; the nightly workflow runs it on both OSes.

**Widening a race on purpose.** `CORTEX_TESTKIT_PAUSE_MS=<n>` makes the scripted server pause `n` milliseconds before each write and before opening each gate of its script. A race between what the server writes and what the test does next, which a loaded machine loses once in a thousand runs, then loses every time, so that a fix can be shown to hold under the same widening. It is read once per process, is off unless set, and nothing in the product reads it. A test in the nightly run checks that four writes take at least four pauses.

### Where a test's time goes

nextest says how long a test took. `CORTEX_TESTKIT_PROFILE=1` makes a test that uses the test kit say where the time went (`cortex_testkit::profile`, since the fourth tooling step):

```text
CORTEX_TESTKIT_PROFILE=1 cargo xtask test -p cortex-cli -E 'test(=commands::sys_x)' --no-capture
```

```text
time profile of `sys_trust` (CORTEX_TESTKIT_PROFILE): 218.9 ms from the process's start
         at        took  what
     0.0 ms      0.0 ms  process start, before the test kit was first used
     0.0 ms      0.7 ms  phase: set-up
     2.8 ms     27.7 ms  phase: the binary runs to its end
    28.2 ms      0.1 ms    wait: the scripted server's connection 1: reading the request [scripted-server-1]
    …
               211.2 ms  in phases and tear-down; 1.0 ms in the test kit's waits, on any thread; 7.7 ms in none of them (the test's own work)
```

- **What it shows:** the process's start before the test kit was first used (on Linux, from the system's record of when the process started, to its clock tick of 10 ms); the phases a rig marks (`set-up` in the agent, core and binary rigs, a core started, a session opened, a turn, the binary run to its end, tear-down from the rig's `Drop`) and any a test names with `profile::phase("…")`; and every wait of the test kit's own (a gate, each step of the scripted server's script, a roll's child, `until`), the same waits the timeout report names, with the thread that waited when it is not the test's.
- **When it is written:** when the test's [`Scratch`](../crates/cortex-testkit/src/scratch.rs) goes, which every rig holds, so a rig's tests need no change. nextest shows a passing test's output with `--no-capture`.
- **It costs nothing when it is off.** The variable is read once; after that each mark is one load of a flag. No clock is read, nothing is allocated and no lock is taken. A unit test holds that.
- **On a hosted runner** (since the fifth tooling step), where a passing test's output is not kept: `CORTEX_TESTKIT_PROFILE_DIR` names a directory that each test's report is also written to, a file a test, named for its binary, its name and its process. `try`'s input `-f testkit=profile` sets both variables and uploads the directory with the run's log: `gh workflow run try --ref <branch> -f os=windows -f command=test -f testkit=profile -f filter='kind(test) & !test(/(^|::)sys_/)'` is tier 2 profiled on a Windows runner.
- **Shown in the fourth tooling step** on the slowest test of each rig ([steps/tooling-4/answered.md](steps/tooling-4/answered.md)).

### Where a measurement's time goes

The profile is opt-in and is about the test kit's waits. A `perf_` test (a measurement, in its own file, in a release build: [performance-budgets.md](performance-budgets.md)) wants something else, and always: which of its stretches took the time, from its first run on any machine, without a `try` round trip to find out. step 18's needed three. `cortex_testkit::Phases` (since the sixth tooling step) names the stretches and prints a breakdown when the test is done:

```text
phases of `perf_a_cold_index_a_warm_one_and_a_warm_map`: 297.3 ms in all
  phase                             took   share  times
  generate the tree              24.0 ms    8.1%
  cold pass                      11.0 ms    3.7%
  change a file                   0.5 ms    0.2%  15
  warm pass                     139.9 ms   47.0%  15
  warm map                       18.9 ms    6.3%  15
  breakdown of a warm pass       82.3 ms   27.7%
  tear-down                      20.7 ms    7.0%
  outside every phase             0.1 ms    0.0%
```

That is the first test of `cortex-index`'s `perf.rs` on a tree of 3,000 files (`CORTEX_PERF_FILES=3000`, a release build on the desktop, a run of 0.3 s).

- **The calls:** `let phases = Phases::new("perf_…")`; `phases.measure("name", || work)` runs the work as a phase and returns its value; `let _p = phases.phase("name")` is a phase until the guard is dropped; `phases.mark("name")` ends the phase the last `mark` began and begins another, `phases.end()` ends it, for a test written as a run of stretches. `phases.took("name")` is a phase's time so far, for a test that holds one stretch to a bound of its own; `phases.report()` prints at once and returns the text.
- **Phases of one name are added up** and shown in the order their names first appeared, with the number of times when it is more than one. What is outside every phase is shown too, so a stretch nobody named is not lost, and the shares add up to the whole. A phase inside a phase is counted twice: use phases for stretches that follow one another.
- **It prints when it is dropped,** unless `report()` printed already, so a test that fails half-way still says where its time had gone. The text is on standard output: nextest shows it for a failing test, and for a passing one with `--no-capture`; `cargo test … -- --nocapture` for the release runs the perf tests are made for.
- **It is always on and costs two clock readings and a push for each phase.** With `CORTEX_TESTKIT_PROFILE=1` each phase is also a phase of the test's [time profile](#where-a-tests-time-goes), beside the waits, so the two reports agree on the names.
- **Used in** `cortex-index`'s `perf_a_cold_index_a_warm_one_and_a_warm_map` (tree, cold pass, each warm round's change, pass and map, the breakdown of a pass, tear-down). A new `perf_` test begins with `Phases::new`.
- **How it is tested:** on a fake clock (`Phases::with_clock`), so nothing waits: the times and shares, phases of one name, marks and ends, the shares adding to the whole, a report printed once, an empty test, and the grouping of thousands.

### A throwaway test

A review that confirms a finding writes a failing test for it. `cargo xtask scratch-test CRATE FILE [--cargo-profile P] [--ignored | --include-ignored] [--no-capture] [-- NEXTEST ARGS]` runs the tests of one file as a module of the crate's integration tests (`use crate::…` reaches the binary's helpers) with nothing registered by hand:

- **The worktree is only read.** The run is made in a copy of the tree under `target/scratch-test/tree`, with a build directory of its own: the copy is brought up to date with the worktree (what git tracks and does not ignore, as `mutate`'s copies), the file goes beside `tests/it/main.rs` as `scratch_<its name>.rs` with its `mod` line, nextest runs that module alone, and the copy is brought up to date again, which takes it out. A run that is killed leaves the module in the copy, which git ignores, and the next run takes it out.
- It fails when a test fails, and when no test ran.
- **Arguments after `--` go to nextest,** and a filterset among them narrows the file's tests: `cargo xtask scratch-test cortex-stats f.rs -- -E 'test(/stuck/)'` runs the tests of `f.rs` whose names match (since the sixth tooling step; before it, nextest took the given filterset beside the module's own and ran every test of the file). Without a `.git`, as in `rx`'s copy, the tree is read as `mutate` reads it: every file outside `.git` and any `target` directory.
- **The first run builds** the crate and what it needs in the copy's build directory (about 10 s for `cortex-base` on the desktop); later runs rebuild what changed. One run at a time.
- **A measurement is a throwaway test too** (since the seventh tooling step). A review's measurement is an ignored `perf_` test, and a number from a debug build says nothing about the optimised one, so the file can be built and run as one:
  - **`--cargo-profile P`** builds and runs the file in cargo profile `P` (`release`, `ci`, `dist`...): nextest's `--cargo-profile`. The profile has a build directory of its own inside the copy's, so the first run of a profile builds the crate and what it needs from cold (15.4 s for `cortex-base` in `release` on the desktop, 2.7 s for the next run, the measurement itself 0.02 s; a crate with a heavier tree is minutes). `cargo xtask try` and its `perf` command ("Running an experiment on the runners") are for a number from a hosted runner.
  - **`--ignored`** runs the file's ignored tests **alone**, the meaning the flag has in `cargo test`; **`--include-ignored`** runs them with the file's others (nextest's `--run-ignored only` and `all`). Both together are refused. A run of ignored tests is a measurement, so it also shows the tests' output (`--no-capture`, which runs one test at a time) and runs under nextest's `perf` profile, whose limit on a test is half an hour where the default stops one at 10 s. A nextest profile or `--no-capture` given after `--` is the caller's and is not given twice (nextest refuses a flag twice). `--no-capture` alone shows the output of an ordinary run.
  - **What it keeps:** the worktree is only read, the module is taken out of the copy again, and the run fails when no test ran. `cargo xtask scratch-test cortex-index f.rs --cargo-profile release --ignored -- -E 'test(/perf_/)'` is a review's measurement of one test.

### A reviewer's kit

A review that confirms a finding hands over three things: **the failing test's file, the command that runs it, and the break that shows the rule untested.** The first two are `cargo xtask scratch-test <crate> <file>` ("A throwaway test", above), which registers nothing and leaves the tree as it was; the third is a break kept in a file of the reviewer's own, `cargo xtask mutate --file <list>` ("Breaking the code on purpose"), or, for one break, `cargo xtask mutate --break <file> --find '<code>' --replace '<code>' --test <name>`, which needs no list. On the code as it is, the break must make the test fail; and the test must pass without the break. The kit is what a review needs to write such a test for the findings that are hard to provoke: a race, a second process, a disk that does not answer, a huge allocation. Each technique below is one that a test in the repository already uses, which passes in the blocking tiers and fails when its rule is broken; the test is named so that a review can start from it.

| To stand in for | Use | The test that holds it, and its break |
|---|---|---|
| The library stopping between two of its steps (a read and the write that follows, a file's content and its rename) | A point the library marks and a `Hold` ([A point the library stops at](#a-point-the-library-stops-at)). The reviewer may add a point to the finding's code in the throwaway tree: `cortex_base::hook::point("…")`, and `Hold::new("…")` in the test. | `cortex-base`'s `a_reader_sees_the_old_content_or_the_new_and_never_a_mixture`; `a-write-truncates-the-target-before-the-rename`. |
| **Two processes sharing a state folder** | Two cores of one `World`: `world.core()` twice, each with a front of its own. They share the world's configuration, state and data directories; each has its own recorder and its own sessions, as a process has. **A lock between them is the operating system's** (`flock` on Linux, `LockFileEx` on Windows, which keep two opens apart even in one process: `cortex_base::private::hold_lock`), so one core's writer excludes the other's. A lock that belongs to the process (POSIX `fcntl`) would not. And whatever is a process-wide static is shared by both cores, as it is not by two processes. | `cortex-core`'s `two_processes_together_hold_the_day_to_its_limit` (`tests/it/day.rs`): the first core's spending is read by the second, which is held to the day's limit by it; its breaks are in `mutations/step-16-fixes.breaks`. |
| **A disk that does not answer** | A FIFO with nobody at its other end, which stalls whoever opens it, in the kernel, with no timing: `cortex_testkit::stalled_file(path)` (Unix only) makes one, and `release()` or dropping it lets a *writer* that waits go on (it opens the other end for reading; a reader that waits is not let go, as two readers of a FIFO both wait for a writer). The code that opens it runs on a thread of its own, waited for with a bound, so that a mistake is a failed test and not a hung one. **On Windows nothing stands in:** an open of a file there fails or succeeds at once, and a test of what a stall does is `#[cfg(unix)]`. What stands in on both systems for a **writer that is stuck** (not a disk that is) is a lock another party holds, `cortex_base::private::hold_lock`. | The helper's own `stalled::tests::sys_a_stalled_file_is_a_fifo_and_holds_an_opener_until_it_is_released`; the break `a-stalled-file-is-an-ordinary-file`. Used in raw form (`mkfifo`) by `cortex-core`'s `a_stalled_disk_holds_a_days_request_at_most_a_second` and, for a file swapped for a FIFO, by `cortex-session`'s and `cortex-tools`' `sys_` tests; a stuck writer by a lock in `a_stuck_statistics_writer_holds_the_end_at_most_two_seconds`. |
| **A huge allocation that must not happen** | `setrlimit(RLIMIT_AS)` on the test's own process (Linux): an allocation over the limit fails, and Rust's allocator aborts, so that the test **fails every time** where on a machine with enough memory it would pass, or fail only by being killed. nextest gives each test a process of its own, so the limit holds for the test alone; under `cargo test` it would limit every test that runs after it in the process, so the test is Linux-only and written for nextest. It needs `unsafe`, which the workspace denies: the test file allows it with a reason (`#![allow(unsafe_code, reason = "a test that limits its own address space")]`), as the one that exists does. `libc` is a dependency of `cortex-base`, `cortex-sandbox` and `cortex-term`, so a test in one of them may use it; **the test kit has no `libc`**, and a helper there (`cortex_testkit::limit_memory(bytes)`) would add an edge and a change to the dependency's row ([dependencies.md](dependencies.md)), which this step did not make. On Windows a Job Object's process memory limit does the same, and no test uses it. | `cortex-base`'s `a_zone_file_that_lies_about_its_counts_is_refused_without_a_large_allocation` (`tests/it/zone.rs`); `the-zone-reader-allocates-before-it-checks` (`mutations/step-16-fixes.breaks`). |

**What a reviewer hands over, for a finding of this kind:**

1. The test, as a file that `scratch-test` runs: `cargo xtask scratch-test cortex-base review_atomic.rs`. It uses `crate::…` for the crate's own test helpers, and the library's `test-hooks` points (the test kit's `Hold`, or `cortex_base::hook::Hold` in `cortex-base`) where it needs the library to stop.
2. The command that runs it, and what it prints when the finding is true (the test's failure message, with the rule it says is broken).
3. The break that shows the rule untested, in a list of its own for `mutate --file`, with the test it must be caught by in `caught-by`; or the one-break form. The break names the code that does the rule's work: made, the test must fail (a break nothing fails is the finding). Before the fix the test fails without it.
4. If a point was needed, the line that marks it, in the finding's own change, so that the author keeps it.

**What the kit does not do.** A race in a library that is not behind a point still needs a point; one made by adding it to the code under review, in the throwaway tree, is what the first row is for. Two cores in one process share what is global to it. A FIFO has nothing to say about a disk that answers slowly. An address-space limit finds an allocation that a check should have prevented, not one that a machine with little memory would refuse for other reasons.

### An adversarial confined command

The sandbox reviews each built their own adversary. The core's tests have one now (`crates/cortex-core/tests/it/adversary.rs`, Linux only, since the fourth tooling step):

- **`Reach::run(test, script)`** runs one turn at `autonomous`, in a trusted repository, with the sandbox enforcing, whose one call is `sh adversary.sh`: the script is a file in the workspace, so the command analysis cannot see what it aims at and ask about it. It names its targets with `{outside}` (a folder outside the write roots), `{port}` (a listener on the loopback interface) and `{marker}`. Every question the turn asks is refused, and listed.
- **What it reports** (`Reached`): the protected paths whose content changed (under the workspace's `.git`, `.cortex` and `.cargo`); the files outside the write roots made, changed or removed (anything under the world's folder but the workspace and the harness's own configuration, state and data); the connections that reached the listener; and the processes still alive after the turn whose environment holds the marker, which the shell passes to all it starts, killed once counted.
- **A test with more turns** wraps them in `Reach::start(&world)` and `reach.reached(&world)`, and gives the shell `reach.env()`. The stopped-turn sandbox test does.
- **The shell's grace for a process left running is on the world's fake timer,** which moves only when a test moves it: `run` lets each wait shorter than a minute go while the turn runs, asking again at once each time, so it keeps a core busy while the command runs (milliseconds). The call's time limit is minutes, and is never reached.
- **What it does not see:** a process that clears its environment (`env -i setsid sleep 600 &`) loses the marker, and is neither reported nor killed by the fixture; the kill's own sweep is what holds it.

### Breaking the code on purpose

A done criterion of the form "X is tested" is evidence only if the test fails when X is broken. Every step since step 5 has broken its own rules on purpose, one at a time, and listed which tests failed. The breaks are now data in the repository, and one command runs them.

**The lists** are `mutations/<name>.breaks`, one file for each step or crate, so that two steps adding breaks at the same time do not touch the same file. A break is a small change that breaks one rule, with the tests that must fail when it is made:

```text
[break] cancellation-not-seen-in-wake
rule: Cancellation is an input: a wait for the response or the round is ended by the turn being cancelled.
file: crates/cortex-agent/src/turn.rs
in: wake
find: cancelled.as_mut().poll(context).is_ready()
replace: cancelled.as_mut().poll(context).is_ready() && false
caught-by:
    transitions::an_interruption_is_taken_in_every_state_that_waits
```

That one is from `mutations/step-07.breaks`.

| Key | What it is |
|---|---|
| `[break] <name>` | Begins a break. Lower-case letters, digits and `-`. It is shown, and chosen, as `<file>/<name>`: `step-12/deny-beats-allow`. |
| `rule` | The rule the break breaks, in a sentence. Required. |
| `file` | The file to change, relative to the repository. Required. |
| `in` | The item the code is in: names separated by `::`, such as `Round::spawn`. An `impl` block answers to every name in its header. Optional. |
| `find` | The code to replace. Required (or `in-string`). It must be there exactly once, in the item if one is named. |
| `in-string` | Instead of `find` (since the eighth tooling step): a text to change **inside a string literal**, with `replace` the text to put in its place ("A word of a string constant", below). |
| `replace` | What to put there. Required, and may be empty. |
| `occurrence` | Which match of `find` is meant, counted from 1, when there are several. Optional. |
| `packages` | The crates whose tests to run, separated by commas. Without it, the crate the file is in. |
| `caught-by` | The tests that must fail, one a line: a test's name as nextest prints it, or its binary and its name (`cortex-agent::it denials::…`). A `*` at the end stands for any ending. Without it, any failing test catches the break. |
| `expect: survives` | Marks a break that changes nothing a test can see, kept so that nobody tries it again. Its `rule` says why. |
| `os` | `windows` or `linux` (since the seventh tooling step): the break is of code only that system builds, and only that system runs it. `windows` is what `cfg!(windows)` decides and `linux` is every `cfg!(unix)` system; anything else is an error. On the other system the break is applied in memory by the pre-flight, as on every system, and then left alone ("Breaks of code one system builds", below). Optional: without it the break runs everywhere. |

A value is on the key's line, or on the indented lines after a key that ends its line. A line that begins with `#` is a comment. Anything else is an error with its line: an unknown key, a key given twice, a break without a required key.

**`find` is matched by token,** not as text. White space, comments and a comma before a closing bracket are not tokens, so however `rustfmt` lays the code out, the break still applies. An exact-text break stops applying the day a line is wrapped, and that is how breaks were lost in earlier steps.

**A word of a string constant: `in-string`** (since the eighth tooling step). A string literal is one token, so a `find` that changes one word of a message, a path or a name kept in a constant had to repeat the whole literal, and was one more line to keep in step with the code. `in-string` names the word alone:

An illustration:

```text
[break] overload-message-says-something-else
rule: The message for an overloaded provider tells the user to retry.
file: crates/cortex-llm/src/error.rs
in: Overload::message
in-string: retry later
replace: give up
caught-by:
    error::tests::an_overload_tells_the_user_to_retry
```

- **Where it is looked for:** only inside the string literals of the file, or of the item `in` names (ordinary, byte, C and raw strings, with any number of `#`). Code, comments and character literals are never searched, so `Budget` the type and `"Budget"` the word are not mixed up. The text is matched **as the literal is written in the source**: an escape is typed as it is (`\n`, `\"`), a raw string is what is between its quotes, and the quotes are not part of the text (a text that begins with `"` finds nothing). It may begin or end in the middle of a word, and it cannot run from one literal into the next.
- **It must be there exactly once**, like a `find`: a text that is in two literals, or twice in one, is refused with the lines, and `occurrence` (counted from 1, across the literals in source order) or a longer text or an `in` picks the one meant. `occurrence` and `in` work as they do for `find`.
- **`replace` is text, not code.** It goes over the text found and nothing else of the literal changes, so the literal must still be one string after it: a `"` that no backslash escapes, or a `\` at the end that escapes the closing quote, is refused ("makes a string literal that is not one string"). A quote is written `\"`.
- **One-line values are trimmed,** so an `in-string` or a `replace` cannot begin or end in a space: put the neighbouring characters in the text (`in-string: retry later` and `replace: give up`, not `later` and a space). A value on indented lines keeps its inner layout and loses the white space at the ends of its lines.
- **The pre-flight holds it as it holds a `find`:** the text must be found once; a `replace` that is the text is a break that changes nothing; and two breaks that make the same change are refused, **whichever key made it** (an `in-string` of one word and a `find` of the whole literal with that word changed are one break: the comparison is of the string token after the change). The checks that are about code do not apply: a comma at the end of an `in-string` is text, not a comma that `rustfmt` moves. `--check --fix-in` finds the item that holds an `in-string` text after the code moved, as it does for a `find`. `--merge` and the lists' other tools see a break whose `in-string` is its text, kept as written.
- **What a result is kept for** includes the key: an `in-string` and a `find` of the same words are two breaks.
- **For one break with no list:** `mutate --break FILE --in-string TEXT --replace TEXT`, in the place of `--find` (the two do not go together).

**A break that does not apply is an error, never a result.** `cargo xtask check` has a step, `breaks`, that applies every break of every list to the tree in memory and fails when one cannot be made: its code is gone, or is there twice, or its replacement is the same code. It reads the files the breaks name and runs nothing (0.2 s on the desktop for the 617 breaks there are, the pre-flight below included, which is what it took without it), so it is in the blocking checks: a change that moves code out from under a break updates the break in the same pull request, or deletes it if the rule is gone. The message names the list and the line, and says which.

**The pre-flight** (since the third tooling step) is the same step, and `cargo xtask mutate --check` runs it alone. Besides a break that cannot be made, it refuses one that will go wrong later, or that tests nothing another does not:

| It refuses | Why |
|---|---|
| A `replace` that is its `find` once both are read by token | The break changes nothing, and would be reported as one no test caught. |
| A `find` that is not there, or is there more than once | The break is not made, or is made in a place nobody chose. |
| A `find` that ends in a comma | `rustfmt` adds and removes the comma before a closing bracket, and the search passes over such a comma, so the day the line is wrapped or joined the break no longer applies. The comma after a match arm that is an expression (`503 => Signal::Overload,`) is the formatter's always, and passes. A `find` whose last comma comes before a closing bracket in the file cannot match at all (that comma is not a token there, and the `find`'s is), and the pre-flight says so, with the line, and to end `find` before the comma (since the fifth tooling step); `cargo xtask replace` says the same of a `--from`. |
| An `in` that names more than one item | Two `impl` blocks with a `new`: the break is made in whichever holds its code today. Not when each of them is under a `#[cfg(…)]` about the system (`unix`, `windows`, `target_os`, `target_family`, `target_arch`): a function for each system, of which a build has one. A `cfg` of a test or a feature does not count: whether two such items can be built together depends on what the `cfg`s say, and the pre-flight does not read them, so it refuses them and a more precise `in` (or none) is needed. |
| Two breaks, in any lists, that make the same change | Read by token, from the first token they change to the last: `a && b` made `a` is `&& b` made nothing. The second tests nothing more. |
| A `caught-by` that names no test (since the sixth tooling step) | A renamed or removed test would be found only when the break is run, after a build. Here it is found from a list of the tests that exist, which has to be built once and is then kept ("The tests a `caught-by` names", below). |

What it cannot see is **a break that a second guard in the code has made unable to fail.** Step 13a's fixes closed the Windows credentials file by name and then its whole folder: after that, the break that removed only the first could fail no test, because the second still refused the read. Only running the breaks shows it, and `mutate` then says NOT CAUGHT, and for a break that names its tests, that another guard may now cover it: break both in one break, or mark it `expect: survives` and name the other guard in its `rule`.

When the pre-flight was written it found 43 breaks whose `find` ended in a comma, in the lists of steps 9, 12, 13a, 20, 26 and 31 and both earlier tooling steps. 38 of them had a `replace` that ended in one too, and lost both; the five others were match arms, which is how the rule came to pass them. It found two `in`s of its own step's that named a trait and its `impl` in one file, and no two breaks that made the same change.

**The tests a `caught-by` names** (since the sixth tooling step). A name that no test has is a test that was renamed or removed, and `mutate` found it only when it ran the break (NAMES A TEST THAT DOES NOT EXIST, below), after a build. `mutate --check` finds it before, with the break's list and line and the name, and when the test only moved it names the tests of the same last name. To know which tests exist it needs the tests built, which `cargo xtask check` must not do (`lint-linux` builds no test binary, only clippy), so the list of tests is **kept, and read when it is fresh**:

| Command | What it does with the names |
|---|---|
| `cargo xtask mutate --check --tests [BREAK…]` | Builds and lists the tests (`cargo nextest list`, once for each set of crates that the breaks run, as `mutate` judges a break against the tests of exactly its build), keeps each list in `target/mutate/test-lists.json`, and checks every `caught-by` against them. With names, only those breaks' names are checked (the rest of the check is always the whole list). At the desk: `rx -- cargo xtask mutate --check --tests`. |
| `cargo xtask mutate --check` and the `breaks` step of `cargo xtask check` | Check against the lists that are kept **and fresh**, and build nothing. A set of crates with no list, or a stale one, is left unchecked, and the output says so and says how to check it. With no file at all the tree's files are not even read: the step costs what it did. |

- **A list is fresh** when the files of its crates are what they were when it was listed: the name and content of every file under `crates/<name>/` of each crate in the set (`xtask/` for `xtask`), the workspace's `Cargo.toml`, `Cargo.lock` and `.config/nextest.toml`, as one 64-bit FNV-1a hash (the one the results of `mutate` are kept by). A change to another crate leaves it fresh: a test's name is in its own crate's files. A test added or renamed in the crate makes it stale, so the check never calls a new test missing: it skips it until `--tests` lists again.
- **Why the list is kept, and not built by the check, and not read from the sources.** Building is minutes the first time and the blocking check must stay as cheap as today (rule 2). Reading the names from the sources would be a guess: `proptest!` and the test kit's macros make tests no `#[test]` names, and a module path comes from `mod` lines across files, so a wrong guess would fail the blocking check on a test that exists. A list from nextest is the names a run has. The price is that the blocking check finds a wrong name only where a fresh list is kept: at the desk, after `--tests`, which is the command to run after renaming or removing a test that a break names. `lint-linux` has no list, so there it prints one line saying the names were not checked. A job that has built the tests anyway (the test jobs) could run `--tests` at the cost of the listing; none does yet.
- **An `#[ignore]`d test cannot catch a break:** a run of `mutate` never runs one. A `caught-by` that names only an ignored test is refused, and says so.
- **What the list is of:** the build of exactly the crates the break runs, as `mutate` builds them. `-p cortex-sandbox` alone has no confinement tests (see "What it cannot tell"), so a break there names `cortex-core` in `packages` and is listed with it.
- **Measured** (the desktop, 28 threads, a debug build of `xtask` as `cargo xtask` runs it; this tree's 1,024 breaks, whose `caught-by` names are of 32 sets of crates and 780 KB of lists): `mutate --check` with no list kept 0.39 s, as before the step (a laptop, before and after the step on the same 1,010 breaks: 0.852 s and 0.852 s); with every list kept and fresh 0.56 s, the 0.17 s being the reading of each crate's files once and of the lists, and the matching of the names. `mutate --check --tests`: the first time, on a desktop with nothing built, 249 s, nearly all of it the build of the workspace's tests, which `cargo xtask test` then finds built; with the tests built and one crate changed, 17 s for all 32 sets, 6 s of it the build of `xtask`'s own tests, and a few seconds when only a few sets are stale.
- **Measured again with the seventh tooling step's `os:`, `--break`, `--flagged` and `--merge`** (a laptop under other builds, a debug build of `xtask`, `mutate --check` with no list of tests kept, the fastest of 8 runs each): 0.77 s before the step on its 1,277 breaks and 0.77 s after on 1,307. The pre-flight reads a break's `os` as it reads any key and does not look at it again.
- **The names of a break of the other system's code** (since the eighth tooling step). A list of tests is of what the build here builds, so a test that only Windows builds is in no list made on Linux, and the names of a break marked `os: windows` were checked nowhere until it ran on Windows (found by the seventh tooling step's review). The check now looks for each of them, on any system and with no list, **among the words of the source**: the name's last segment (or, for an entry that ends in `*`, its beginning) must be a name token of some Rust file of the crates the break runs (comments and strings do not count). A test that was renamed or removed is found by `mutate --check` and the `breaks` step of `check`, as a name that no test has is, with the break's list and line. A list of the tests of a Windows build, kept and read on Linux, would be exact, and is **not** what was done, for three reasons: such a list is produced only by a build on Windows (`try -f os=windows`, a runner), so it would be a file to commit, to bring back from an artifact, and to make again after every change to a crate that a Windows break runs (the check's own freshness rule: any change to the crate makes it stale); a list that is stale checks nothing, so it would check the names on the days nobody changed the crate; and it adds a generated file and a workflow step outside what `xtask/src/mutate` owns. **What the words cannot tell:** a test from a helper of the same name, a wrong module path, a test that is `#[ignore]`d, and a name a macro makes from pieces (it is no word of any file: name it by the beginning of a word that is there, with a `*`, or by the macro's argument). An entry that ends in `::*` is not looked for at all. The run on Windows still judges them exactly.
- **What it found when it was written:** four names of the lists of steps 13a's and 15's fixes that no test has (two of them a test renamed with `sys_` in front, one a name reworded at its end, one a test of another crate than the break runs). They are left for their steps to correct.

**`mutate --check --fix-in`** (since the sixth tooling step) is for the day a refactor renames an item or moves code into another: the break's `in:` then matches nothing, and the check says its `find` is not in the item, and nothing of where it went. With `--fix-in`, for each break whose `in:` no longer holds its `find`, it looks for the code in the whole file, and prints the `in:` that names the item that holds it now, with the code's line:

```text
mutations/step-07.breaks:41: break `step-07/cancellation-not-seen-in-wake`: its `in: wake` no longer holds its `find` in `crates/cortex-agent/src/turn.rs`.
  The code is now at line 212 of `crates/cortex-agent/src/turn.rs`. Use:
      in: Round::poll
```

- **It offers only what it is sure of.** The `find` must be in the file exactly once, and in an item (a module, an `impl` block, a function, as `in:` names them). The name is the innermost item's, with the one around it added until the name picks out that one item and that place (an `in:` that names two items is refused by the pre-flight, and `new` in two `impl` blocks is `A::new`). A `find` that is in several places (it names each one, with its line and its item), nowhere in the file (the code is gone or has moved to another file: change `file:` by hand), in no item, or that asks for an `occurrence` above 1, is **not guessed at**: the message says why, and the break is left to a person.
- **`--fix-in --write`** rewrites the `in:` lines in the lists, only those: other lines, comments and line endings stay, and a value written on indented lines becomes one on the key's line. It then checks the lists again. Without `--write` nothing is changed and the check fails as before.
- A break whose `in:` still holds its code, or that has none, or that fails for another reason (its `find` twice in the item), is not touched. Run `cargo xtask mutate BREAK` after, to see that the tests still catch it: the code is where it was meant, not necessarily doing what the rule says.

**`cargo xtask mutate [BREAK…]`** runs the breaks: all of them, or the ones named (a break, a whole list, or the end of a name). **`--file PATH`** (since the sixth tooling step) runs the breaks of a list kept anywhere, and no others: a review's throwaway breaks need no file in `mutations/`, where one forgotten fails `check`. The list is named for its file, and a name that is already a list's of `mutations/` is refused.

1. Every break is applied in memory, as `check` does. Nothing is built if one fails.
2. **The work is done on a copy** of the tree under `target/mutate/`, with a build directory of its own. The working tree is only read. The copy is brought up to date at the start of each run, which also undoes a break that a killed run left in it. The first build of the copy is a whole build; after that each break rebuilds one crate.
3. **The tests are run once with nothing broken,** for each set of packages that a break runs. A test that fails by itself stops the run: it is no evidence about anything. A break is judged against the tests of exactly the build it runs in, because which tests there are depends on what is built together.
4. **Each break is compiled** (`cargo check`) before any break's tests are run, and the ones that do not compile are named.
5. **Each break's tests are run,** and the tests that failed are read from nextest's JUnit report (profile `mutate`), not from its terminal output.

What it says of each break:

| Verdict | Meaning | What to do |
|---|---|---|
| caught by N test(s) | At least one test failed, and every test of `caught-by` did. | Nothing. |
| survived, as its list expects | A break marked `expect: survives`, and no test failed. | Nothing. |
| NOT CAUGHT | No test failed. | Write the test. If nothing a test can see changes, mark the break `expect: survives`. |
| NOT CAUGHT BY ITS OWN TESTS | Some test failed, and one that `caught-by` names passed. | A test that used to catch this no longer does: find out why. |
| NAMES A TEST THAT DOES NOT EXIST | A `caught-by` entry matches no test. | The test was renamed or removed: correct the list. `mutate --check --tests` finds this without running the breaks. |
| CAUGHT, AND EXPECTED TO SURVIVE | A break marked `expect: survives` made a test fail. | Take the mark off and name the test. |
| DOES NOT COMPILE | The code does not build with the break made. | Correct `replace`. |
| COULD NOT BE JUDGED | The run failed and named no failed test. | Read the log it names. |
| left to a Windows run (or a Linux one) | The break has an `os:` of the other system. It was applied by the pre-flight and not run here. | Nothing here: it is neither a pass nor a failure of the run. Run it where its code is built ("Breaks of code one system builds"). |

It exits 0 when every break did what its list expects, 1 when one did not, and 2 when its time ran out.

**It stops, and carries on.** Every result is written to `target/mutate/results.jsonl` as it is known, under a key made of the code (every file but the lists) and the break. A run does not start new work after its time budget (`--minutes N`, 5 when not given, 0 for none), and the next run starts where it stopped: run the same command until it exits 0 or 1.

- **The budget is on starting work, not on finishing it.** One piece of work, a break's build and tests, is seconds. The first build of the copy is a whole build of the crates named, and runs to its end whatever the budget. After it, a long list gives a shared build machine back every five minutes or so.
- A run that is killed loses at most the break it was in.
- **One run at a time on a copy.** A second run on the same copy is refused while the first holds it: it would bring the copy up to date under the first, which would then report a break as survived that was no longer made. The lock is the operating system's, so a killed run lets go of it. A copy that cannot be locked at all is not used.
- **A lock that is held is tried again for 200 ms** (20 times, 10 ms apart) before the copy is called busy (since the seventh tooling step). Under plain `cargo test`, where `xtask`'s tests are threads of one process, a test that runs `mutate` twice on one copy found the lock still held by the first run: a process another thread had forked held the lock's descriptor from its fork to its `exec`, after the first run had let go of it. The descriptor is not inherited by what runs (the standard library opens every file close-on-exec, and a Windows handle is not inheritable), so the moment is the fork's alone and the retry ends it; a run that really holds the copy is still refused, 200 ms later. The wait is a parameter, so that no test sleeps: the tests of the retry count the waits instead.
- A change to the code forgets every result. A change to a list forgets only the breaks it changed.
- **A run that ended without a verdict is tried again by the next run:** a break that did not compile, or a test run that failed and named no failed test. The cause may have been the machine's. A break that did not compile is reported with the compiler's first errors, never cargo's progress lines: cargo runs with `CARGO_TERM_COLOR=never` whatever the caller set, since an `error` in escape sequences is not found (CI sets `always`, which is how the nightly run of 2026-11-14 failed, issue #40). A test run that named no failed test keeps its whole output in a file of its own under `target/mutate/logs/`, which the message names.
- `--again` forgets the results of the breaks named, and runs them again. To carry on after the time ran out, leave it off: with it, the next run would forget what this one did. The command says so.
- `--report` prints what is known and runs nothing.

**`--jobs N` runs N breaks at a time,** two when it is not given (since the sixth tooling step: four at the desk stalled its disk in wave 9, and baselines were lost). Each job has a copy of the tree (`target/mutate/tree`, `tree-2`, …) and a build directory of its own (`target`, `target-2`, …), and takes the next piece of work when it is free. The three rounds stay in order, each finished before the next begins: the tests with nothing broken, every break compiled, every break's tests. The run's own thread alone writes the results and the report, in the order pieces finish. With one job nothing changes: the pieces are done in order, on the run's own thread.

- **A busy disk starts a run with one job.** When every task has waited on the disk 10% or more of the last minute (`full avg60` in `/proc/pressure/io`, Linux only), a run asked for several jobs starts with one and says so: a review's two jobs on the desk's side slot lost a baseline to a stall at 66%, where one job ran clean.
- **A stall is not a verdict.** A test run whose timeouts ended together ("Running the tests many times over", above) comes back as the machine's. A set of tests with nothing broken that stalled is run again, once the round's other pieces are done, with one job, and the run says so; if it stalls with one job too, the run stops and says the machine is too busy. A break's run that stalled is reported as COULD NOT BE JUDGED with the stall's message, and the next run tries it again: a test that failed because the disk stopped would otherwise make the break look caught.

- **The first build of each new copy is a whole build** of the crates named. On the desktop that was 57 s for four copies of `cortex-core` together, the first time.
- **Measured on the desktop** (28 threads), on the 24 breaks of `mutations/step-13a.breaks` in `cortex-core`'s `assemble.rs`, once every copy was built: 43.5 s with one job, 15.8 s with four, which also ran the tests with nothing broken again. 2.8 times as fast.
- **The shared test lock.** On the desktop every run goes through `rx`, which holds the shared test lock for the whole command (`rx busy` shows who holds it and who waits). The jobs are threads of one command under that one lock, and `--minutes` is the budget of all of them together: no new piece starts after it, so the lock is held no longer than a run of one job with the same budget holds it, and for less work done. What `--jobs` adds is cores while it holds it; `rx throttle` caps those as it caps any run.
- **A long run on the side:** `rx --side -- cargo xtask mutate …` (or `stress`) runs in a second copy of the worktree (`<worktree>-side`) under a side lock of its own, pinned to the upper half of the desktop's threads, so the ordinary test lock stays free for other sessions. One side run at a time; its first run builds from cold. It does not combine with `--exclusive`, which holds the side lock too. `rx busy` shows the side slot.
- **The time is asked before any job starts,** then as each piece finishes and a few times a second. **The answer "up" is binding** (since the eighth tooling step): a job takes its next piece under a lock that the run's thread holds while it asks the time and writes the answer down, so a job either took its piece before the question, or finds the answer. The seventh tooling step's stress found `no_job_starts_a_piece_once_the_time_is_up` failing once in 50 repeats: the test lets the pieces go from inside the question, a job that was let go looked for its next piece before the answer was written, and with the gate open it went through every piece. The test is the same with a few milliseconds' window given to a job to try (a bound on the clock of a few milliseconds, which a passing run spends in full, since with the lock no job can take a piece in it, and a failing one leaves early; whether a missing lock is caught depends on a thread that is let go being scheduled within it, which a loaded Windows runner may not do), and 200 repeats, alone and under load (`--cores 2 --load 6`), pass.

**Only the breaks a diff can affect: `mutate --changed REF`** (since the eighth tooling step). A full run of a big step's breaks is half an hour, and again after each fix of a review. `--changed REF` runs the breaks the working tree's diff from `REF` (a branch, a tag or a commit) can affect, and says how many it left and why:

```text
--changed origin/main: the diff touches 9 file(s). 44 of 1663 break(s) chosen (3 new or changed in their lists, 38 by their file, 1 by a test they name, 2 whose test names could not be placed in any file, chosen to be safe); 1619 skipped: the diff touches neither their file, nor a test they name, nor their text, nor the build's settings. A full run (no `--changed`) is what a report rests on.
```

A full run stays the default, and is what a step's report rests on; `--changed` is for the loop of fix and run (0.5 s to choose, on 1,663 breaks).

**The diff** is the working tree against `REF`: `git diff --name-only --no-renames REF` (a file that was moved or deleted counts under both names) and the files git does not know yet (`git ls-files --others --exclude-standard`). **A break is chosen when the diff**

1. touches the build's settings: the workspace's `Cargo.toml`, `Cargo.lock`, `.config/nextest.toml`, `rust-toolchain.toml` or `.cargo/config.toml` (every break's build reads them: all are chosen), **or any file outside `crates/`, `xtask/`, `docs/`, `mutations/` and `.github/` that is not Markdown** (a file a build script embeds, such as `catalog/models.toml`: what the rule does not know is taken to touch every break; found by the step's review), or the `Cargo.toml` or `build.rs` of a crate the break runs (`packages`, or its file's crate); or
2. **adds or changes the break itself:** no break of the lists at `REF` has the text that decides what it does (its file, item, `find` or `in-string`, `replace`, `occurrence`, crates, `caught-by`, `expect` and `os`: a reworded `rule` is not a change, and a break moved to another list, by `--merge` or otherwise, is the break it was). The lists the diff does not touch are the same as at `REF`; those it touches are read as they were (`git show REF:mutations/NAME.breaks`). A break read from `--file` is judged the same way: one that no list of `mutations/` at `REF` has is new; or
3. touches its `file`; or
4. touches a test its `caught-by` names.

**It never skips a break that rule says to choose.** What it chooses when it cannot tell is the part that takes care:

- **Which test a name is.** A test's module path comes from `mod` lines across files, macros make tests no `#[test]` names, and a `*` ends a name, so the name is not mapped to a file by its path. A `caught-by` is read by its **last segment** (`no_job_starts_a_piece_once_the_time_is_up` of `mutate::jobs::tests::…`; the binary of an entry, `cortex-llm::it`, is dropped). A test is touched when a file of the crates the break runs that the diff touches has that word among its tokens **anywhere**: in a definition, as a macro's argument, in a call. The file is read as it is, and as it was at `REF`, so a test that was removed or moved is found by where it was.
- **What that over-chooses:** a helper or a test of the same name in another module, and a call of a function of that name in a file the diff touches.
- **When no file of those crates has the word at all** (a test that a macro made from pieces, a name that is gone), **or the entry ends in `*`** (a pattern can end inside a module's name: `open*` is every test of `openai_chat`, and no word of a test's own says so; found by the step's review), the name cannot be placed, and the break is chosen when **any file of those crates** was touched. **A touched file of those crates that is not Rust** (a fixture, a snapshot, a file a test reads) chooses it too. The summary counts these ("chosen to be safe"), and `--list` says for each break why it was chosen.
- **Only the crates a break runs are read:** a crate with no touched file is not read at all, so a diff that leaves a crate alone costs the choice nothing there.

**What it does not see**, and a full run is for: a change to Rust code a test calls that is not the break's file and names no test the break names (a helper elsewhere in the crate, the test kit, a crate it depends on), and a break that names no test (`expect: survives`, or any failing test catches it): that one is chosen by its file, its own text and the settings only.

**It combines** with the break and list names given (it narrows them), `--file` (the lists' breaks, narrowed), `--flagged` (the breaks of the narrowed set that were left without a verdict), `--again` (forgets the results of the narrowed set only), `--list` (which breaks, each with why), `--report`, `--jobs` and `--minutes`. **It is refused** beside `--break` (one break of its own: nothing to choose among), `--merge`, and `--check` (a check reads every list whole, since a break that does not apply is wrong whether or not it is run today). A `REF` that is not a commit is an error that names it, never "nothing changed", and a `REF` that begins with `-` is refused as an option. A diff that touches nothing any break depends on says "Nothing to run" and exits 0.

**It needs git's history.** The desk's `rx` copies the worktree **without** a `.git`, so there `--changed` fails and says so; the owner's `rx --git -- cargo xtask mutate --changed main …` gives the copy a `.git` from a bundle of the local refs, with `HEAD` at the worktree's commit, so the diff is the worktree's. Name a local branch there (`main`, brought up to date with `git fetch` and a fast-forward first): a bundle may not carry `origin/*`, and a ref it lacks is an error, never "nothing changed". A tree whose `.git` is missing fails the same way (the message names `rx --git`).

**One break with no list entry: `mutate --break`** (since the seventh tooling step). A break to try once, or to show a reviewer, needs no line in a list:

```text
cargo xtask mutate --break crates/cortex-agent/src/turn.rs \
    --in wake --find 'cancelled.as_mut().poll(context).is_ready()' \
    --replace 'cancelled.as_mut().poll(context).is_ready() && false' \
    --test transitions::an_interruption_is_taken_in_every_state_that_waits
```

`--break FILE`, `--find CODE` and `--replace CODE` are the break; `--in ITEM`, `--occurrence N` and `--packages A,B` are the keys `in`, `occurrence` and `packages`, and `--test NAME` is a `caught-by` entry, given once for each (the same matching, a `*` at the end). With no `--test` any failing test catches it.

- **It is the same run as a list's break:** the same pre-flight (the `find` by token, exactly once; a `find` that ends in a comma, an `in` of several items, a `--test` that no test has where a fresh list of tests is kept), the same baseline of the crates' tests, the same compile, the same judging and the same verdicts. It reads no list and writes none: `mutations/` is not touched, so there is nothing to forget and `check` has nothing to fail on.
- **It is named `one-off/<file's name>-<eight hex digits>`,** the digits from the break's own text (every key given, `--test`s included), as in `[ 1/1] one-off/turn-3fa9c2d1  caught by 1 test(s): ...`.
- **Its result is kept** in `target/mutate/results.jsonl` like any other, under a key made of the code and the break's text with a mark that a list's break never has: so a second identical run is instant (nothing is built or run), and a one-off break of the code of a list's break neither takes that break's result nor gives it one. What they share is the tests with nothing broken, which are the same for the same crates and the same code, and are kept once.
- **It is refused beside break names, a list's name and `--file`** (a run is of the one or of the lists), beside `--flagged` and `--merge`, and without `--find` and `--replace`. `--check`, `--list` and `--report` work on it: the pre-flight alone, its name, and what is kept for it.

**Only the breaks a run left without a verdict: `mutate --flagged`** (since the seventh tooling step). A run that a stall or a failed build left unjudged used to be found by reading its output and naming the breaks again. `--flagged` reads `target/mutate/results.jsonl` for the code as it is and chooses, among the breaks the names given choose (all of them without names, or those of `--file`), exactly these:

- **A break whose test run failed without naming a failed test** (the result's status `broken`: COULD NOT BE JUDGED, which is also how a stall is kept: "the machine stalled"), and
- **a break that did not compile** (the result of the compile of every break holds an error, or the status of its test run is `does-not-compile`: DOES NOT COMPILE).

These are the results the next run forgets and tries again whichever breaks it runs, so `--flagged` runs the same pieces with nothing else to name them. It prints each break it chose and why (`step-12/deny-beats-allow  COULD NOT BE JUDGED: the machine stalled. STALL: 3 tests timed out ...`), and runs them. Not chosen: a break with a verdict of its tests, good or flagged (NOT CAUGHT, NOT CAUGHT BY ITS OWN TESTS, NAMES A TEST THAT DOES NOT EXIST, CAUGHT AND EXPECTED TO SURVIVE: asking again gives the same, and `--again NAME` runs one again if a test is suspected); a break not run yet (the same command, run again, carries on); and anything found for other code, which a change to a file forgot. With nothing to choose it says "Nothing is flagged" and exits 0. It works with `--list` (which breaks it would run) and `--report`; a one-off `--break` is not chosen by it, since its text is all it has: give it again.

**The parts of a step's list, put together: `mutate --merge STEP PART…`** (since the seventh tooling step). A session that hands its work to sub-agents gives each one a list of its own, `mutations/<step>-<part>.breaks`, so that no two of them write one file. At the end, `cargo xtask mutate --merge STEP PART…` makes the parts named `mutations/STEP.breaks`:

- **The parts are named,** each `PART` the file `mutations/STEP-PART.breaks`, and they are merged in name order. A list of its own can have a name of the same form (`step-12-fixes` beside `step-12`, `tooling-2` beside a step called `tooling`), and merging it would rename its breaks and delete it (found by the review of the step): with no `PART` the command names every list that looks like a part of `STEP` and merges nothing, and a `PART` with no file is refused. Each part's text is kept as it is, its comments with it, under a comment line that names it: `# From mutations/tooling-7-mutate.breaks (part `mutate`).`. A list `STEP.breaks` that is already there is kept, and the parts follow it.
- **All or nothing.** It refuses a part that is not a list, and two breaks of one name (it names both files and lines: in one list a name is one break). Then it runs the whole pre-flight on what the lists would be afterwards (the other lists as they are, and the merged one): a break that does not apply, one that makes the same change as another, a `find` that ends in a comma, an `in` of several items, and a `caught-by` against the kept lists of tests where a fresh one is kept (with none, the names are not checked, as in `check`: `mutate --check --tests` checks them). Only when that passes is the list written (beside its place, then moved over it) and each part deleted. Otherwise nothing is written, no part is deleted, and the problems are printed with the lines the merged list would have.
- **`--dry-run`** says which parts it found, how many breaks each has and what the pre-flight says, and does none of it.
- **What was kept for the parts' breaks is kept.** A result is stored by the code and the break's own text, never by the name of the list it is in, so a break that moves from `step-13a-fixes` to `step-13a` finds the result it had, and `mutate step-13a` after a merge is as quick as the runs of the parts were. Nothing is forgotten.

**Breaks of code one system builds (`os:`)** (since the seventh tooling step). A break is made in the text, so a break of code that only Windows builds applied on Linux changes code the build does not compile, and its tests pass because nothing changed: it used to be reported as not caught, which it was not. A break with `os: windows` (or `os: linux`) says so:

- **The pre-flight applies it on every system:** `mutate --check` and the `breaks` step of `check` read the file and make the break in memory whichever system they run on, so its code is held and a day's refactor that moves it is found where Linux CI runs, as for every other break. A `caught-by` of it is checked against the kept lists of tests only on its own system, whose tests are the ones built there; on the other system its names are looked for among the words of the source ("The names of a break of the other system's code", below).
- **`mutate` runs it only on that system.** On the other it names the breaks it left and why, in a block of its own before the run, and says how to run them on the system that builds them:

```text
1 break(s) are of code only Windows builds, applied here by the pre-flight and left to a Windows run, which is neither a pass nor a failure of this one:
  tooling-7/nofollow-windows-follows-a-reparse-point  (mutations/tooling-7.breaks:1245)
Run one on a hosted Windows runner: `gh workflow run try --ref <branch> -f os=windows -f command="mutate tooling-7/nofollow-windows-follows-a-reparse-point"`.
```

  It is neither a pass nor a failure: it is not counted among the breaks that did what the list expects or did not, and the run's status is as if the break were not there. A run whose every chosen break is of the other system runs nothing and **fails**, saying so (since the review of the step: an exit of 0 would read as every break caught). (A run on Windows, where `os: windows` is run, the same for a break marked `linux`.)
- **Where it is run, it is judged as any break is,** against the tests that system builds: the Windows-only tests of the crate (a `#[cfg(windows)]` module) are in the Windows build and not in the Linux one, so a break of Windows-only code is caught only by a test that is built and run there. `mutations/tooling-7.breaks` has one as the demonstration: `nofollow-windows-follows-a-reparse-point` makes `cortex-base`'s Windows-only open follow a symbolic link or a junction, and the three Windows-only tests of `nofollow` must fail.

**What it cannot tell.**

- **A break in code the build does not compile is reported as not caught,** unless it says which system builds it. A break is made in the text, so it can be made in code that is behind a feature that is off, and the tests then pass because nothing changed. Run such a break where the code is built, and name in `packages` a crate whose build turns the feature on. Code only Windows (or only Linux) builds has the `os:` key above.
- **A crate alone.** `cargo xtask test`, `stress` and `ci --tiers` of `cortex-sandbox` on Linux turn its `backends` feature on, and say so: without it a build of the crate alone compiles the confinement tests out, and passes having confined nothing (two sessions were misled by such a run). A build of the whole workspace turns it on through `cortex-core`. `mutate` does not add it: a break in the sandbox names `cortex-core` in `packages`, or runs where the workspace is built.
- **Which tests exist depends on what is built.** `cortex-tools` has tests of the seeded order that are only built when `cortex-agent`'s tests are in the same build, because that is what turns `test-hooks` on. A break that names them in `caught-by` names `packages: cortex-tools, cortex-agent`.
- **"Caught" with no `caught-by` is one failing test in one run.** A test that fails by chance would do. The tests with nothing broken are run once, not many times: stress the crate first, and name the tests a break should fail.
- **`find` passes over a trailing comma,** so `f(a)` also finds `f(a,)`, and `(x)` finds the tuple `(x,)`. Whether a break changes anything is judged with commas counted. A match never begins or ends inside an operator of two characters: `= 0` does not find the second half of `x == 0`.
- **A break's tests are run without the caller's test settings:** under seed 0, with the ordinary number of property cases, and writing no snapshot or generated file. A result is kept by the code and the break alone.

**Adding a step's breaks.** Write `mutations/step-NN.breaks` as the rules are built, run `cargo xtask mutate step-NN`, and put the verdicts in the step's report. A break that nothing catches is a missing test.

**The lists as seeded.** Wave 4's breaks were kept only in the reports of the sessions that made them. The lists of steps 7, 8, 9, 10, 12 and 14 were written again from the pull requests' descriptions, the code's own documentation and the tests: 101 breaks, 14 to 20 a step. Every one is caught, by the tests its list names. All 101 run in under five minutes on the desktop, about a second each once the copy is built. What running them showed is in [steps/tooling-w5/answered.md](steps/tooling-w5/answered.md). This step's own code has a list too, `mutations/tooling-w5.breaks`: 23 breaks of the seeded order, the scratch directory and the commands of `xtask`, written with the code. And `mutations/step-31.breaks` is the 87 breaks step 31's session kept, each as text before and after, converted by a script. All 87 apply and are caught. Six of them no longer applied in the session's own last run, which matched the text exactly: by token, they still find their code.

**How `--changed`, `in-string` and the jobs' answer are tested.** `--changed`: the rule as pure functions over a list of changed files, the breaks and the files' texts as they are and as they were (`mutate::changed::tests`: nothing changed, a file, a test in a file of its own and in a shared one, a test removed or moved, a name no file has, a name that ends in `*`, a break new or changed in its list, a list renamed, a reworded rule, the settings, `packages`, a break with no test), the summary's counts, the refusals of the options, and one test with a real small git repository in a temporary folder (`sys_a_real_repository_gives_the_files_a_diff_touches_with_both_names_of_a_move`: a changed file, a file moved and staged, a new file git has not been told of, a bad reference). `in-string`: the literals' text (`lex`), where a text is found (code and comments are not searched, once, `occurrence`, the item), the break as `apply` makes it, the refusals (changes nothing, not one string, the same change as another break), the lists' keys, `--break`'s options and `--fix-in`. The jobs: `mutate::jobs::tests::no_job_starts_a_piece_once_the_time_is_up`. Each has breaks in `mutations/tooling-8-mutate.breaks`.

**How the command is tested.** With a runner that reads the copy and says which tests "fail" for what it finds: three breaks, two that are caught and one that nothing catches, and each verdict in the table (unit tests, in the blocking checks). And against the real cargo and nextest, on a small workspace kept for it (`xtask/fixtures/mutate`), with five breaks: two caught, one not, one expected to survive and one that does not compile. That test builds a workspace ten times over (0.8 s in all on the desktop, several times that on a hosted Windows runner), so it is ignored in the blocking checks. The nightly workflow runs it on Linux, and so does anyone who changes the driver: `cargo xtask test -p xtask --run-ignored only sys_the_real`.

### Asking the permission engine

`cargo xtask decide [--level LEVEL] [--rule RULE]… [--shell posix|powershell|cmd] [--workspace PATH] [--cwd PATH] [--untrusted] [--] COMMAND…` prints what the permission engine decides of a `shell` call running the command: allow (and whether read-only), ask with each reason and the rule an approval would add, or deny with its reason, and the command analysis it stands on. The engine is the one the command table's tests use: workspace `/work/app`, home `/users/dev`, a trusted project, an enforcing sandbox, level `supervised`, no rules, POSIX syntax, unless the flags say otherwise. A rule is `user|project allow|ask|deny read|write|exec|network|ext PATTERN`, with the patterns of the configuration: `--rule 'user allow exec cargo build *'`.

```text
$ cargo xtask decide --rule 'project deny exec git push *' -- git push origin main
command   git push origin main
…
decision  DENY
  because The command is refused by the rule `deny exec git push *` from the project's configuration.
```

It runs the probe that is an ignored test of `cortex-policy`'s integration binary (`decide::probe`), with the case in its environment: `xtask` does not build the engine, which would add its crates to every CI job. A test holds the probe to rows of the command table.

### Invariants to test

An architecture page may end with a section **"Invariants to test"** (since the fourth tooling step): what a review should try to break, so that each review does not have to find the rules again. Pages 06 and 07 have one, seeded from what their reviews found.

- **One row an invariant,** in a table `| Invariant | How a review breaks it | Held by |`: the rule as a sentence that can be false; an attack or a mistake that would make it false (a command, a sequence, a file a repository could carry); and the tests or the break list that hold it today, or "nothing yet", which is a gap to fill.
- **Found by a review, said where:** a row that a review's finding taught names it (`step 26, finding 2`), so the next review knows it was broken once.
- **A row is added when a review finds a new way in,** and changed when the code moves; a row is never removed because a test now holds it.
- **The tools for it:** `cargo xtask scratch-test` for a failing test without registering it, the core's adversarial fixture (`Reach`) for a confined command, `Rig::fill`, `fill_next` and `fill_after` for a context test at a pressure, `cortex_testkit::Phases` for where a `perf_` test's time goes, `cargo xtask mutate` to see a test catch its break.

## Testing the TUI

Three levels, matching the tiers.

| Level | What is tested | How |
|---|---|---|
| **View functions** (tier 1) | That state renders to the right lines. | Pure functions from state, width and theme to styled lines. Snapshots as text with inline style markers, at 60, 80 and 120 columns, in both glyph sets, with and without colour. |
| **Presenters** (tier 2) | That frames reach the terminal correctly. | The presenter writes into a virtual terminal (a terminal-state parser from the test kit). Tests assert the resulting screen and scrollback, and the **no-flicker properties** for every frame: one write, inside a synchronized update, no clear-then-redraw, nothing above the live region touched, bytes per frame under a cap. |
| **The real binary** (tier 3) | That it all works in a terminal. | The binary runs under a pseudo-terminal (ConPTY on Windows), driven by scripted keys, with the scripted provider. Tests assert on the parsed screen, on terminal restoration after exit, panic and signals, on the first frame coming within a generous limit, and on input latency staying under one: each key of a word typed into the prompt (`KEY_ECHO` in `crates/cortex-cli/tests/system/tui.rs`, since the fixes of the review of step 23, which found no such limit on the real binary). |

The no-flicker properties and the latency checks use the method developed for the TUI language comparison ([measurements/tui-language-spike.md](measurements/tui-language-spike.md)).

**What step 20 built for them.**

- **The virtual terminal** (`cortex_testkit::VTerm`) is the test kit's own: an xterm-like screen and scrollback, with wide characters, automatic wrap, margins, the alternate screen, styles, the private modes the terminal layer uses, and the queries it sends. It does not re-wrap on resize. `watch()` and `report()` record what the bytes between them did, checked after every action and not only at the end: the rows touched, counted from the top of the scrollback so that a row keeps its number when the screen scrolls; the rows an erase left blank that had text before and after (a clear followed by a redraw); clears of the whole screen; and whether the bytes began and ended one synchronized update. `Report::problems(live_top, sync)` is the list of the properties a frame breaks. It takes `U+009B` as the start of a control sequence, as some terminals do, so a renderer that let one through is seen.
- **The presenter's tests** (`crates/cortex-term/tests/it/presenter.rs`, tier 2) check every frame of a generated script of commits, live regions, cursors, repeated frames and height changes (150 scripts on a pull request): one call to the sink, the properties above, and the right scrollback and screen after it, with the cursor where the frame put it. Others check a streaming frame's size (median under 1 KiB, none over 4 KiB), a narrower window, and content full of escape sequences.
- **The pseudo-terminal driver** (`cortex_testkit::pty::Session`) runs a program in a pseudo-terminal (ConPTY on Windows), records each piece of output with the time it arrived, parses it with a `VTerm`, types keys, answers queries as a modern terminal would when asked to, and waits on what the screen shows. The system's half (opening the pseudo-terminal, starting the program in it) is in `cortex-term` behind its `pty` feature, beside the crate's other `unsafe` code; `cargo xtask rules` lets only dev-dependencies and the test kit turn the feature on.
- **The system tests** (`crates/cortex-term/tests/it/system.rs`, tier 3) run the crate's own test binary as a small shell, which records the terminal's modes (on Windows it first turns virtual-terminal processing off, as the old console host has it), runs the demo as a child, and says whether the modes after are the ones before. The demo draws, echoes keys and is resized, and is ended by Ctrl+C, by a panic, and by SIGTERM or a Ctrl+Break event; each time the modes must be back, the cursor shown, and nothing left on. On Windows the virtual terminal sees ConPTY's own rendering, not the demo's bytes, so there the shell's comparison of the console's modes is the check that speaks for the demo. On Linux a further test stops the demo with Ctrl+Z and continues it, and checks that everything is put back while it is stopped and on again after. The first frame and a key's echo have coarse limits there: five times the runner's first-frame budget, and 250 ms.
- **`cargo xtask perf`** builds the demo optimised and runs the measurement (`crates/cortex-term/tests/it/perf.rs`, ignored in every ordinary run) against the TUI's budgets. It runs on Linux and on Windows; no workflow runs it yet ([outstanding/perf-in-the-main-workflow.md](outstanding/perf-in-the-main-workflow.md)). **On Unix it runs each demo twice** (since the fifth tooling step), in both glyph sets: under `LC_ALL=C.UTF-8` (Unicode) and under `LC_ALL=C` (ASCII), which is how the terminal layer chooses the set there; a `--json` path gets `.ascii` for the second. On Windows the console decides, and ConPTY gets the ASCII set, so it runs once.

**Answering a dialog in a system test** (since the eighth tooling step). The application reads keys that arrive in one read as typing, and a dialog takes none of them as an answer (`App::burst`), so a key typed before the dialog has taken the one before can make the answer go to the input box. `Session::answer_dialog(limit, answers, key, answered)` waits for the dialog's row of answers (drawn only once the dialog takes keys), types the key alone, and returns once the row has left the screen and `answered` holds: something only the answer brings (the header after trust, the tool's result after an approval), since a frame can reach the terminal in pieces and one piece can lack the row while the dialog is up. Every dialog answer in `cortex-cli`'s system tests goes through it. It reads only what the screen shows, so it holds whatever rule decides when a dialog takes keys, as long as its answers are drawn only when they can be pressed. The flake it ended (`sys_a_projects_first_limit_is_listed_and_in_force_once_trusted`, 2026-11-16) was a wait for the header that matched the text `Cortex-Harness` in a path on the screen (the trust question shows the workspace's path, under the temporary folder, which at the desk is inside the `rx` copy of the main checkout, named after the repository; a hosted runner's temporary folder is not): it passed at once, the test typed `go` and Enter a few microseconds after `y`, and on a fast build all four were read together. A wait for the header matches its title and version. And a command that needs the turn to have ended (`/undo`) waits for the idle input box first, not for the turn's last answer, which is drawn before the turn ends.

**What the eighth tooling step added.** Wave 11 found two kinds of Windows-only difference late, through `try`: the wording of how a process ended, and the ASCII stand-ins for the interface's glyphs. A test spells neither now, and the console's closing is driven.

- **How a process ended** (`cortex_testkit::exit`). `ExitStatus` says `exit status: 1` on Unix and `exit code: 1` on Windows, a signal as `signal: 6 (SIGABRT)`, and a fault as `exit code: 0xc0000005`. `Exit::parse` reads either system's wording into `Exit::Code(n)`, `Exit::Signal(n)` or `Exit::Fault(status)`, and `Exit::of(status)` makes the same from a status itself. `Verdict::parse(screen_text)` reads what a `ModeShell` printed (`restored: yes (exit status: 129)`) into whether the modes were put back and how the child ended, so a test compares one value: `assert_eq!(Verdict::parse(&shown), Some(Verdict { restored: true, exit: Exit::Code(129) }))`. A text that is not an ending, a stop, and a verdict cut short on the screen are `None`. Tested on both systems' texts, and, for each system, against the text of a real `ExitStatus` of that system. It cannot tell a Windows code with the high bit set from a signal: `Fault` is Windows' and `Signal` is Unix's, and a test that expects an abort writes the one its system has.
- **Either glyph set** (`cortex_testkit::glyphs`). The interface draws `◆` and `│`, or `>` and `|` where the console gets the ASCII set (every Windows console, and a Unix terminal under the `C` locale). A test spells a text once, as a function of the set, and `GlyphSets::shows`, `history_has_row` (with a `RowPattern` of a start and the texts a row holds) and `strip_prefix` and `strip_suffix` try each set. The sets are `cortex-tui`'s own (`Glyphs::UNICODE` and `Glyphs::ASCII`), which the test kit cannot depend on, so the test passes them: `GlyphSets::new(&[Glyphs::UNICODE, Glyphs::ASCII])`, and there is one copy of each glyph, the product's. It matches rows by text, not by style or cell, and a row that mixes the two sets does not match either.
- **The console closing under the program** (`Session::close_console`, below).
- **An application frame as a snapshot** (`cortex-tui`'s `testing::assert_app_frame`, crate-private). `assert_app_frame("app-<name>", &mut app, now, columns, rows)` resizes the `App` to a window of that size, draws its real frame (`App::frame`) and compares it with `snapshots/app-<name>.txt`: the lines the frame committed to the scrollback, the live region, and where the cursor goes, each line with its styles in the view snapshots' markup. `CORTEX_UPDATE_SNAPSHOTS=1` writes it, as for every snapshot of the crate (`rx --back --` at the desk). It is for a test of what the application shows as a whole (a dialog, the header and the hint row); a test of one fact still asserts the fact. One call draws one frame and consumes what it committed, so a test that wants three sizes makes three snapshots. The dialog tests in `app/tests.rs` that checked three rows of a frame with `contains` check the frame.

**The console closing** (`Session::close_console`, since the eighth tooling step). A closed terminal window is a way the application ends that no key or signal of the test's makes: on Windows the console closes under it (`CTRL_CLOSE_EVENT`), on Unix the terminal hangs up (SIGHUP). `Session::close_console` does that to the program in the session and returns when it did; the program's end is read with `wait_exit`.

- **On Windows** it calls `ClosePseudoConsole` while the program runs, which is what closing a Windows Terminal tab does: the console host sends every process on it the event and ends it when its handler returns. The call may wait for the program's handler, so it runs on a thread of its own and `close_console` does not wait for it. The console is gone with its screen: the output ends, nothing can be typed, and a shell of the test's goes with it, so its verdict is never on the screen. A test of the application reads what it leaves outside the terminal.
- **On Unix** it sends SIGHUP and then SIGCONT to the program's process group, as the kernel does when the terminal's master closes. The master itself cannot be closed under the driver's reader, which holds it open in a read, so a write to the terminal still succeeds afterwards where after a real hang-up it fails; that case (a failed write) is the application's own test of step 23. A `ModeShell` that should live through it to say how its child ended asks `surviving_hangup()`: a handler that does nothing, which, unlike "ignore", the child does not inherit.
- **The application's answer** is `sys_the_console_closing_ends_the_application_and_stops_its_turn` and `sys_the_console_closing_stops_a_running_command` (`crates/cortex-cli/tests/system/tui.rs`), beside the SIGHUP test they mirror. The real binary runs under its shell, a turn is streaming or a command is running, and the console is closed; the request is dropped or the command is gone, within 2 s, under the 3 s of the watchdog that would end an application that did not (an end the watchdog made fails). On Unix the shell's verdict then says the terminal was put back and the code is 129, as for SIGHUP. The tests close the console just after a whole frame (the spinner has turned, and the hint row, the frame's last, shows it): a signal that lands while the application writes a frame makes that write fail, and the application ends with exit code 1 and "the terminal failed: the terminal has been put back", not with the signal's code. That is a finding about the application, not a flake of the test, and is open (the eighth tooling step reported it); it shows in 1 of 600 runs on a desk held to two cores with six busy threads beside it, and in none of 1,000 on an idle one, and the SIGHUP test beside these has the same window. On Windows the only evidence is what the application leaves outside the console, and whether the handler ran in order, with the terminal put back, is not seen: nothing is on a screen that has gone.

### The test binary in roles

A terminal's system tests run their crate's test binary again, as a small shell, as the program under test, and as what that program runs in turn (an editor). `cortex_testkit::role` (since the fifth tooling step) holds what `cortex-term` and `cortex-tui` each had a copy of:

- **`Role`:** a mark such as `cxterm-demo=`. `Role::command(options)` starts this binary with the entry test alone (`child_entry`) and the mark with the options after it; in the child, `Role::options()` gives them back, so the entry test knows which part to play. `arguments` gives the same for the pseudo-terminal driver, and `command_line` for a variable such as `$EDITOR`.
- **`Report`:** a file of `name: value` lines in the test's scratch directory, which a child writes and the test reads once it is gone. A child's standard output is the terminal, which ConPTY re-renders.
- **`ModeShell`:** records the terminal's modes, runs a child, and prints `restored: yes (<how it ended>)` when the modes after it are the ones before, or `restored: NO (<how it ended>)` with both, read back by `exit::Verdict::parse`. It can start the child as the old console host would (virtual-terminal processing off), pass the interrupt keys over while the child runs, and say a line first. It gives its children the modes it saw, so that a grandchild can ask `same_modes_as_the_shell()`.

**Signals made to order** (Unix). Step 21's hand-off of `Ctrl+C` to a child (`cortex_term::ignore_interrupts`) has three parts: a do-nothing handler while the guard lives, a drain of an interrupt still pending as it ends, and a grace of a second after, for one another thread took from the queue as the guard was ending. The race they close needs the kernel to hand a signal to a thread at the wrong moment, so they were reasoned and not tested. `cortex_term::pty::interrupt_pending_here()` leaves an interrupt pending on the calling thread, blocked and sent to it, as the kernel leaves one it has not handed over; `raise_interrupt()` runs its handler at a known point. With them `crates/cortex-term/tests/it/signals.rs` tests all three, each in a child of its own and each against a control with no guard, which must end the child with SIGINT. On Windows there is no pending interrupt to drain: a console control event runs its handler on a thread the system starts for it.

Snapshot changes are reviewed like code. A change in a view snapshot is a change in what users see.

**The view snapshots (step 22)** are text with inline style markers, in `crates/cortex-tui/snapshots/`: a style is written where it changes, as `{fg=a13 bg=#132A17 b d i u r link=…}` (`a` a palette colour, `i` an indexed one, `#` an exact one, then bold, dim, italic, underline, reverse), `{}` is the plain style, and each row ends in `|` so that its trailing spaces are seen. One test an element writes one file with a section a variant: 60, 80 and 120 columns in both glyph sets in true colour on a dark background, then at 80 columns true colour on a light one, 16 colours on both, 256 colours and no colour. Width and glyph set change the layout and touch no style; depth and background change styles and touch no layout, so each is covered against the other without the whole product, and the golden screens below cover the product for the reference session. `CORTEX_UPDATE_SNAPSHOTS=1` writes them (`rx --back --` at the desk).

### The golden screens

The reference screens of the chosen look ([architecture/tui-look/](architecture/tui-look/README.md)) are drawn again by `cortex-tui`'s real views, through the inline presenter, into the test kit's virtual terminal, and compared cell by cell with the reference files fed into another (`crates/cortex-tui/tests/it/screens/`). The session they show is Rust test data there, composed as the interactive application will compose it.

- **It is a tier-2 test, so every pull request runs it.** It draws 38 screens (19 on two backgrounds) in about 0.2 s in CI's build on the desktop, with one highlighter for them all as the application has, the views and the highlighter included, so it is cheap enough for the blocking tier; it needs the build, so it could not be part of `cargo xtask check`, which builds nothing it does not lint.
- **Every row the views built so far draw is compared** (step 22's, and step 21's input box and menus), text, style and wide cells alike, as a cell is seen: a space is compared by its background and by whether it is reversed or underlined, which is all of a space that shows.
- **A row another step draws is counted as not built**, with the step that builds it: since step 23 composed its dialogs, the viewer's frame and the input box's placeholder into the screens, only the panels (step 24). It is never counted as compared. **A dialog is the application's own frame** (screens 2a to 2d, since the review of step 23): the real `App` is given the request by a scripted core, in a window of the screen's size, and the live region of the frame it draws once the dialog takes keys is compared, so that its answers, their order, their fitting to the window and its blank and hint rows are held, not a list the test wrote. The test holds each screen's count of compared rows, so a row skipped by mistake fails it, and a self-check gives the comparison a screen with one changed cell and one row marked not built, and requires the first found and the second left alone. When a step builds the rows it owns, it composes them into the screens and raises the counts.
- **Style is compared as well as text:** a cell is the same when its text and its style are, a space by what of it shows. A self-check gives the comparison a cell in another colour, one made bold and a space with another background, and requires each found, and a space whose foreground alone changed not (since the fifth tooling step). The report counts, for each screen, how many of the cells that differ do so in style alone: the owner's colour decision of 2026-11-15 showed as 320 such cells.
- **`cargo xtask tui-screens`** prints the report: each screen's rows, the rows compared, the rows not built by whom, and every cell that differs. **`--write`** rewrites the reference rows that differ from the real views, in the reference files' own form, and lists every changed cell, writes each screen's `.txt` copy from the dark one (a test holds the two together), then compares again writing nothing and fails unless that passes. That is the only way a reference screen changes, and the cells it changed go in the step's report for the owner to see.

## CI layout

### Blocking, on every pull request

Four jobs in parallel, in `.github/workflows/ci.yml`. Wall time is the slowest job.

| Job | Runner | Runs |
|---|---|---|
| `lint-linux` | `ubuntu-latest` | `cargo xtask check`, and the owner guard ("The owner guard", below): `cargo fmt --all --check`; the repo rules; the break lists, each break of which must still apply ("Breaking the code on purpose"); the generated files (the protocol's schema and TypeScript declarations are what the types generate); `cargo clippy --workspace --all-targets --locked -- -D warnings`; `cargo deny check licenses bans sources`. |
| `lint-windows` | `windows-latest` | `cargo xtask check clippy`. Formatting, the repo rules and cargo-deny give the same answer on every OS and run once. Clippy runs on both, because code compiled only for Windows is otherwise never linted. |
| `test-linux` | `ubuntu-latest` | `cargo xtask ci test`: build the tests, run tiers 1 and 2 and then tier 3 (`cargo nextest run --workspace --locked --cargo-profile ci --profile ci`, with `-E 'not test(/(^|::)sys_/)'` and then `-E 'test(/(^|::)sys_/)'`), check the tier budgets and list each tier's slowest tests. Then the JUnit report of both runs is kept as an artifact. |
| `test-windows` | `windows-latest` | The same. |

The first draft of this page had three jobs. `lint-windows` was added in step 2: it runs beside the others, so it adds nothing to the wall time, and it closes a gap that would have opened as soon as the first Windows-only module was written.

**The jobs call `cargo xtask`.** What a job runs is defined in the `xtask` crate and nowhere else, so `cargo xtask ci` at a desk runs what CI runs. Every step of a command runs even when an earlier one failed, so one CI round trip reports everything that is wrong. Each step is timed, and the timings go to the log and to the job's summary page.

Settings common to all jobs:

- `--locked` and `CARGO_INCREMENTAL=0`.
- Each job has `timeout-minutes: 5`. That makes the budget a fact: a job that takes longer fails.
- The toolchain version comes from `rust-toolchain.toml` and is installed with `rustup toolchain install`. The version is pinned exactly, so a new stable release never changes the lints under a pull request. Installing it costs 8 to 9 s in every job, cache or no cache (11 to 13 s on Windows before `RUSTUP_HOME` was moved off the system disk).
- **Tests build in cargo's `ci` profile:** `dev`, with third-party crates unoptimised. The reason is in "Where the five minutes go". Our own crates keep line tables, so a failing test's backtrace has line numbers. A few third-party crates are optimised all the same: `serde_json` and `sha2`, because the decoder replays and the session log's tests spend their time in the first, and every file a tool reads is hashed by the second; and since step 22 `syntect` with the crates it loads its grammars with (`fancy-regex`, `regex-automata`, `regex-syntax`, `flate2`, `miniz_oxide`, `bincode`), because every highlighter test and the golden screens load the grammars once a process, 0.09 s a test unoptimised and 0.02 s optimised on the desktop. A third-party crate is built once and then served from the cache, so the exception costs a cold run a few seconds and a warm one nothing. Our own crates are not optimised there, though `cortex-llm` at `opt-level = 1` ran its tests four times as fast on the desktop: it is rebuilt by most pull requests, and the build is where a Windows job's time already goes. Measured again in the fifth tooling step, at four jobs and without incremental builds as CI builds: `cortex-llm` at `opt-level = 1` took 1.6 s more to rebuild at the desk for 0.3 s less of its tests' time. **Measured on the runners in the seventh tooling step, and declined by the owner on 2026-11-16:** every job builds every workspace crate, the cache holding only third-party ones, so `cortex-llm` at `opt-level = 1` would cost every pull request 5.7 s of build on Linux and 9.3 s on Windows (11.5 s cold), for 4.3 s less of Windows' integration tier and 1.7 s of its unit tier, summed over the test threads, under 2 s of the run's wall time ([steps/tooling-7/answered.md](steps/tooling-7/answered.md)). **An optimised crate's generic code is not optimised:** a generic function is compiled in the crate that calls it, at that crate's level, so `serde_json::to_vec::<Value>` called from `cortex-session` runs unoptimised whatever `serde_json`'s entry here says. The entries help a crate's own non-generic work (escaping, number formatting, `sha2`'s rounds), not a caller's serialisation.
- Dependency caching with `Swatinem/rust-cache`. The key is made of the job, the OS, the toolchain version, the `CARGO_*` and `RUST*` environment, and a hash of `Cargo.lock`, every `Cargo.toml`, `rust-toolchain.toml` and `.cargo/config.toml`. When that hash has no exact match, the newest cache for the same job, OS and toolchain is restored instead, so **a lockfile change rebuilds the changed crates and what depends on them, not everything**. Only a toolchain bump, or caches that have expired, give a truly cold run.
- Only the main branch writes the cache, so pull requests read a cache that is always consistent and never push each other's out of the repository's 10 GB. A scheduled run of the same workflow, twice a week, keeps the caches from expiring.
- On Windows, `CARGO_HOME` and `RUSTUP_HOME` point at a folder on the workspace's disk, not at their default place on the system disk, which is several times slower at unpacking files (measured below).
- **The Windows test job's temporary directory is on the workspace's disk too** (`TEMP` and `TMP`, since 2026-11-13). A test that needs a directory with no repository above it makes it in the system's temporary directory, which is on `C:` by default. Measured in one job, alternating twice: the 53 integration tests of `cortex-core` took 6.3 and 6.2 s with it on `C:` and 3.3 and 3.5 s on `D:`, and the three tiers together about 8 s less ([steps/11/ci.md](steps/11/ci.md)).
- `cargo-nextest` and `cargo-deny` are installed as prebuilt, checksummed binaries, not compiled.
- A new push to a pull request cancels the run in progress.
- Actions are pinned by commit hash. The workflow token has read-only permissions. No secret is used except the owner's protected terms, which the owner guard reads ("The owner guard", below). `cargo xtask rules` checks all three: the one secret is allowed only as the line `OWNER_TERMS: ${{ secrets.OWNER_TERMS }}`.

**Documentation-only pull requests skip the Rust build and tests.** Each job starts with a step (`.github/actions/changes`) that lists what the pull request changes. If every changed file is under `docs/` or ends in `.md`, the job's remaining steps are skipped and the job still reports success under its own name.

- The decision is made inside each job, not in a separate job that the others wait for. All four checks therefore always report, so they can be required by branch protection as they are, with no gate job, and a pull request that does touch code pays about a second for the question.
- **The owner guard runs on every pull request,** documentation-only or not, and whatever the steps before it did.
- **The repo rules still run on a documentation-only pull request, deliberately.** The check for home-directory paths, the check of `docs/dependencies.md`, the check that every link inside the repository leads somewhere and the check of where the step records are exist mostly for documentation, and skipping them on exactly the pull requests that write prose would open the hole they close. This compiles `xtask`, which is five small crates, and nothing else.
- Anything else in the change set (a manifest, a workflow, an asset, a source file) runs everything. So does every push to the main branch and every scheduled or manual run.
- **The generated files under `docs/protocol/` and `docs/configuration/` count as code.** They are checked against the Rust types by tests, so a pull request that touches them runs the tests, wherever else its changes are.

**nextest configuration** (`.config/nextest.toml`):

- the per-test limits of each tier, from the table under "Test tiers", in every profile;
- profile `ci`: fail fast off, quiet on success, JUnit output for the tier budgets;
- profiles `mutate` and `stress`, for the two commands of "Showing that the tests bite": fail fast off, only failures printed, JUnit output;
- a test group that limits pseudo-terminal and process tests (everything named `sys_…`) to two at a time, so they do not starve each other on a 4-core runner, and in profile `ci` a group of its own for them, `system`, three at a time (`system-windows`, two at a time, on Windows), for the blocking job's second run, where they run alone ("Each tier is measured under its own load", above); and on Windows a group for tiers 1 and 2, `tiers-windows`, three at a time, for its first run;
- no retries, except tests in a module named `timing_sensitive`, which get one retry and are reported as flaky when it is used;
- profile `fast` for local use: tiers 1 and 2 only.

Before it, only the `main` workflow checked the size, after the merge, which is how step 23's second pull request took the Windows binary over its budget unseen (issue #61).

|---|---|

### The owner guard

The owner's name, email and home path never appear in the repository (rule 3). Since 2026-11-13 CI checks for them, in the `lint-linux` job, on every pull request and every push to the main branch: `cargo xtask owner-guard --base REV --head REV`.

- **What it looks at:** every line the change adds, the path of every file it adds or changes, and every commit's message and its author's and committer's names and emails. A line it removes is not looked at. For a pull request the change is what its head adds since it left the base branch; for a push, what the push adds (the head commit alone on a first push). The repository's existing content is not scanned.
- **The terms are a secret, `OWNER_TERMS`,** which only the owner sets, so that they are not in a public repository. Its format: one term a line; white space around a term and empty lines are ignored; case is ignored. A term that contains `@` or `/` (an email, a home path) matches anywhere in the text; any other term (a name, a phrase of several words) matches only as a whole word, with no letter, digit or `_` against either end. The owner sets it with `gh secret set OWNER_TERMS < file`, from a file with one term a line.
- **A term is never printed.** A finding names the file and the line, or the commit and the field, and says that it "matches a protected term"; a file whose path matches is named by its number in the diff. GitHub masks a secret's value in a log as well, which is not relied on.
- **Without the secret it passes, with a warning** in the log and on the job's summary page: a pull request from a fork is not given the repository's secrets, and the secret may not have been set yet. A fork's pull request is therefore not checked until it is merged, when the push to the main branch is.
- **Which terms to list.** Each part of the name as a word of its own, as well as the whole name: a phrase is matched across any white space, line breaks included, but not across two lines of a diff. The account names, the email addresses, and the home directory's folder name as a word: a Windows path such as `C:\Users\<name>` has no `/`, would be matched as written, and would miss its escaped forms (`C:\\Users\\…`, `C:/Users/…`). Text is lowered and nothing more: a name written in decomposed Unicode, or `ß` against `SS`, does not match.
- **What it is not.**
  - **It stops a merge, not a leak.** A pull request's diff and commits are public as soon as it is opened, before the guard has run, and a commit stays reachable by its hash after it is rewritten. What stops a term before it leaves the desk is the guard before a push, below.
  - **It catches an accident, not someone set on leaking the terms.** Anyone who can push a branch to this repository can change the workflow or the guard on that branch, and with it read the secret.
  - **The workflow rule checks the line's form, not its place.** Only `ci.yml`'s guard step is given the secret today, and nothing enforces that.
  - **GitHub masks the secret's lines in the whole job's log,** so a term that appears in another step's output shows as `***`, in a public log; the guard fails on the same change.
- **Who commits on the main branch.** A pull request merged on GitHub by rebase has, as its committer on the main branch, the account that merged it. That is the project's public handle, which rule 3 allows, so it must not be among the terms: the guard looks at committers on a push to the main branch as on a pull request, and would fail every merge.
- **Before a push: the git hook** (since the fourth tooling step, after wave 7, when a fix session copied the owner's name from a message into a commit and a doc, and pushed). `xtask/hooks/pre-push` runs `cargo xtask owner-guard --pre-push`, with what git gives a pre-push hook:
  - **The terms** are read from `~/.config/cortex-harness/owner-terms` (the home folder is `HOME`, or `USERPROFILE` on Windows), or from the file `CORTEX_OWNER_TERMS_FILE` names. One term a line, matched as CI matches `OWNER_TERMS`. The owner keeps the file; nobody else needs one.
  - **What it checks** is every commit the push sends that the remote's branches, as the repository last fetched them, do not have: **each commit's own** added lines and paths (a term one commit adds and a later one takes out is still public in the first), its message, author and committer; the names of the refs it writes and sends; and an annotated tag's text. A merge is read against its first parent, and a root commit against nothing, whatever `log.showRoot` says. A push to a URL, which names no remote, is held only against what git says the URL has: another remote's branches may be private. `git replace` refs are not followed: the push sends the object itself.
  - **The terms are read as CI reads them,** but for a byte-order mark at the start of a line, which some editors write and which is taken off (in CI's guard too); a term that holds a character that cannot be seen (a control character, a zero-width one) refuses the push.
  - **A term is never printed:** a finding names the commit and the field, or the file and the line. Every line it prints is held against the terms first, and one that would show a term (git's own error text can name a path under the home folder) is withheld. A path to the terms file is shown as `~/.config/…` or as "the file `CORTEX_OWNER_TERMS_FILE` names", never spelled out.
  - **Without the default file it warns and lets the push go,** as CI does without the secret, so a contributor without it is not blocked; **unless the repository requires the file** (`git config cortex.ownerTermsRequired true`, which the owner sets when installing the hook), when it refuses: a push from a process with another home folder, or with the file moved, is then not waved through. **When there is a file and the check cannot run** it refuses the push and says why: a file the variable names that is not there, a file that cannot be read, is not UTF-8 or holds no term, a file inside the repository (where a commit could take it), what git gave the hook unreadable, or git failing.
  - **Speed:** a warm run takes 0.07 s on the laptop for a push of nothing new, and stays under a second for a branch of a few dozen commits: one `git config`, then five to seven git commands a ref, whatever the number of commits. The first push from a new worktree builds `xtask` first.
  - **cargo** is found as the one that started the push (`CARGO`), on `PATH`, or in `${CARGO_HOME:-~/.cargo}/bin`. Without it the push is refused.
  - **Installing it,** once, by the owner, for every worktree of the repository: `cp xtask/hooks/pre-push "$(git rev-parse --git-common-dir)/hooks/pre-push"` and `git config cortex.ownerTermsRequired true`. The copy is in the repository's own hooks folder, outside every branch, so a branch cannot turn it off by changing its own copy; `core.hooksPath` pointed at `xtask/hooks` would have run each branch's. **Install it once the change that adds `--pre-push` is on the main branch, and rebase the open branches:** a branch made before it has a guard without `--pre-push`, so its push is refused (closed, not open) until it is rebased.
  - **What it does not stop:** the guard it runs is the branch's own `xtask` and `.cargo/config.toml` alias, as CI's is, so a branch that changes them changes the check. It catches an accident, as CI's guard does, not someone set on pushing a term.
  - **Never push with `--no-verify`:** it skips the hook. [AGENTS.md](../AGENTS.md) says so.
  - **By hand:** `cargo xtask owner-guard --unpushed [REMOTE]` checks what a push of `HEAD` would send.
  - **How it is tested:** with made-up terms, in a repository with a remote that the test makes (`xtask/src/owner_guard/local/tests.rs`): a term in an added line that a later commit removes, a path, an author, a committer, a message, a remote ref's name and a tag, each found and named without the term; a clean push and what the remote has already find nothing; a git that fails is an error. And end to end: a real `git push` through the hook script, with a stand-in cargo in a `CARGO_HOME` of the test's own that runs the guard from the test binary: a push with a term is refused, one without the file warns and goes, a clean one goes.
- **How it is tested:** with made-up terms (`xtask/src/owner_guard.rs`): whole words and case, an occurrence inside one that is not a word, a phrase across white space and a line break, an email and a path anywhere, letters beyond ASCII, an added line against a deleted one, a line that looks like a diff header, a path (an empty file's and one with a tab included), a commit's author, its committer and its message, and a message that holds the separators. And on a real repository the test makes: a range, a first push, a base that is not there (a force push: the head commit alone is checked, and the log says so), a binary file and an empty file. Its breaks are in `mutations/owner-guard.breaks`.

### A CI run's test times

Each test job keeps nextest's JUnit report as an artifact, `junit-linux` or `junit-windows`, for 14 days, whether the tests passed or not. It has the time of every test, which the log does not.

```text
gh run download <run id> --name junit-windows --dir junit
cargo xtask ci --tiers --from junit/junit.xml --os windows --top 20
```

prints the tier totals of that run against the Windows budgets, each tier split by crate, and its twenty slowest tests in each tier.

**Two runs compared.** `cargo xtask ci --tiers --compare NEW [--against OLD] [--os linux|windows|both] [--top N]` prints each tier's time above the process start on both sides, with the change and the budget; each crate's change in each tier; and each tier's tests that moved most, with a test on one side only counted whole. Each side is held against its own start cost, so a slower runner alone moves nothing. `NEW` and `OLD` are each a JUnit report, a run id of the `ci` workflow (or of a `try` run of `test`, below), or `main`, the main branch's latest successful `ci` run that kept the report asked for (a run of a documentation change alone succeeds and keeps none, and is passed over; the command prints which run `main` was, and its commit); `OLD` is `main` when it is not given. A run's report is fetched through `gh` (`gh run download`) once, into `target/xtask-runs/<run>/`, and read from there afterwards. `--os` picks which test job's report: `linux` or `windows`, each held to its own OS's budgets (tier 3 is 60 s on Linux and 90 s on Windows), and `--os both` (since the seventh tooling step) prints Linux's comparison and then Windows', each under its name, from runs that kept both reports. `main` is one run for both (the latest that kept both reports), so the two OSes are of one commit; a report on disk is of one OS and is refused with `both`; and one OS whose report cannot be read is named in its place, without hiding the other's table, and the command fails after the last. Without `--os` it is the OS the command runs on. A run of the `try` workflow is a source too, since the seventh tooling step: a plain `test` run keeps its report in `try-<os>` (as `target/nextest/ci/junit.xml`, wherever the artifact puts the runner's folders), and it is read from there when the run kept no `junit-<os>`. A `try` A/B run is refused, with the commands that read it: it holds two trees' rounds and no one report. **A side that is no measurement fails the command** (since the review of the seventh tooling step): a test that failed on either side (a timeout reads as a test of its limit's length), or a tier with tests on one side and none on the other (a run that did not happen reads as a tier that got faster), is named under the table, and the command exits as a failure. A `try` run, now a source, fails far more often than `main`'s green `ci` runs.

**A step's tables.** `cargo xtask ci-times RUN [--against RUN|main] [--pr N] [--write FILE]` fetches a run's jobs and both test jobs' reports through `gh` and prints the two tables the steps' `ci.md` files have, in their form: which pull request and which `main`, each job's time under "Main, `sha`" and "The PR at `sha`" (the jobs a merge waits for first; then the ones that block nothing, the pull request's size jobs, marked `(blocks nothing)`, so that their four minutes are never read as a five-minute job's: since the eighth tooling step, and a test fails when `ci.yml` has a job of neither kind), and each tier's time above the process start against its budget, a column for each OS and run, with each run's start cost. `--write docs/steps/<NN>/ci.md` puts them in the file's section "On the pull request" (since the fifth tooling step): what it writes goes between two HTML-comment marks, and writing again replaces only that, so a note written after the end mark stays; a section of that name it did not write is refused, and nothing is written. `cargo xtask ci-times --ab TRY-RUN [--write FILE]` does the same for each OS's section "Windows, both trees on one runner" and "Linux, both trees on one runner", as the records name them, from a `try` run made with `-f against=…`: each OS's tiers on both sides, the median of the rounds, the tests counted and the change, read from the run's kept reports, written all or none; and it prints the pull request's CI section, each tier's change and its share of the budget by OS, ready to paste. Sessions used to grep these out of `gh run view --log`. A report with a failed test is named with a warning, and `--write` then writes nothing (since the review of the seventh tooling step): a step's record holds the times of runs whose tests passed.

**What moved, by crate and by test** (since the seventh tooling step). After those tables `ci-times --ab` prints, for each OS, each round's tier times (the spread of one side is the noise a change has to stand out of), the rounds left out and why, and then, tier by tier above the one start cost both sides were held to, the crates that moved (the time on each side to the hundredth of a second and the change; those that moved by 0.05 s or more, the ten that moved most named and the rest counted) and the `--top N` tests that moved most (8 when not given; a test on one side only counts whole). It is the comparison `ci --tiers --compare` makes of two CI runs, from the A/B's medians. `--top 0` prints neither the rounds' table nor the detail. It is printed and not written: a `ci.md` keeps the tiers. **The rounds are read as `ab` read them** (the review of the step): a round in which a side's run broke (`ab` keeps that run's report as `<side>-round-<n>-broke.xml`, which is not a round's), in which a test failed on one side only or not the same tests failed on both, or for which a side kept no report, is left out of both sides' medians with the numbers of the others kept, and named; a round in which the same tests failed on both sides, and nothing else went wrong, is compared, and those tests are left out of every round on both sides (before this, a failed round's partial report was counted as a finished one, and a run that broke after tiers 1 and 2 read as a faster tier 3).

**Several sections in one page** (since the seventh tooling step). A step that is measured again after a review's fixes writes each measurement under a name of its own. `--write FILE --section NAME` makes the tables **one section called NAME**, with marks that carry the name (`<!-- written by cargo xtask ci-times, section "NAME": it replaces this up to the end mark -->` and `<!-- end of what cargo xtask ci-times wrote, section "NAME" -->`): writing it again replaces what is between them and nothing else, whichever other sections the page has, wherever the section has been moved to, and whatever its heading has been edited to. An A/B's two OSes are `###` parts of that one section. `--heading TEXT` is the heading a **new** section is added with, when it should not be its name: a dated one, as an older step's page has (`--section fixes --heading "After the review: the fixes' pull request (#56), 2026-11-16"`). Alone, it is the name as well, which is how a page written before the marks existed gets a section of its own. The rules, which refuse every case that could lose a line:

- A section is **added at the end of the page** under `## <heading>`, never inside another, and never after a heading chosen by the tool; move it by hand and the marks go with it.
- The name and the heading are one line, with no white space at either end, no `-->`, and, for the name, no double quote; a heading is the text and not the `## ` before it.
- A **heading of that text already on the page that the tool did not write** (an older page's section by hand, with no marks) is refused, and so is a section under the plain marks of the unnamed form: choose another `--heading`. Nothing is written, in any of the page's sections, when one is refused.
- Marks that are not one opening and one closing, in that order, are refused, naming what was found; a mark or a heading inside a fenced block is text.
- `--section` and `--heading` say where `--write` puts the tables, and mean nothing without it.
- Without either, nothing changes: the sections `On the pull request` and `<OS>, both trees on one runner`, between the plain marks.
 **Through `rx`,** whose copy of the tree has no `.git`, `gh` cannot tell which repository it is in: name it, `rx -- env GH_REPO=<owner>/<repo> cargo xtask ci-times RUN --against main`, and the same for `ci --tiers --compare`. **A report is missing from a table only when the run made none** (its tests did not run), and the command says so; whether it did is read from the run's list of artifacts. An expired report, a download that fails and a question GitHub does not answer are errors that name the run, never a column left out (since the third tooling step). The upload is the one step these tools add to a blocking job. What they add in all (that step, three static checks and their own tests) is measured in [steps/tooling-w5/ci.md](steps/tooling-w5/ci.md).

**A `try` run's result.** `cargo xtask try-result RUN [--os linux|windows|linux-22.04] [--top N] [--tail N]` (since the seventh tooling step) reads a finished run of the `try` workflow in one step: it lists the run's jobs through `gh run view`, downloads each `try-<os>` artifact once (into `target/xtask-runs/<run>/`, as the other commands do) and prints, for each OS the run had, what the run's command found:

- **an A/B run** (`-f against=…`): each tier on both sides as `ci-times --ab` prints it, each round, the crates and tests that moved, the rounds left out and why, and `ab`'s block of the tests that failed on both sides (its line `N TEST(S) FAILED ON BOTH SIDES` and the indented lines after it), which are not counted as failures of the run;
- **a `test` run:** the tier report against that OS's budgets, whatever the verdict, with its crates and slowest tests;
- **a stress run:** the summary the run printed, rebuilt from its report (the seeds from the log's command line);
- **a `perf` run:** each test and its time, and where its own tables are (`ci-log RUN --grep 'perf_'`);
- and then **every failed test** with the first lines of its message, read from the JUnit reports as `stress` reads them (a test that passed on its retry is not one; one that failed in several rounds is listed once, with where). For a job that failed with **no failed test in a report**, the last `--tail N` lines of its log (30 when not given): from the artifact's own, or, for a job that kept no artifact (cancelled, or ended before the upload), from GitHub's log of the job.

It ends as a failure, naming what failed (`try run 123 failed: `try-windows` ended as failure; `try-windows`: 2 test(s) failed (…)`), and says `nothing failed` when the run did not. A run that is not finished, is of another workflow, or has no job for `--os` is an error that says so. Through `rx`, name the repository as for `ci-times`: `rx -- env GH_REPO=<owner>/<repo> cargo xtask try-result RUN`. It reads `try`'s artifacts as they are kept ("A run on the runners without a pull request"); it asks GitHub for the run's jobs and downloads, and nothing else. A `mutate` run is not a `try` command, so there is no mutation summary to read.

**A job's log.** `cargo xtask ci-log RUN|JOB [--job NAME] [--all] [--grep RE] [--context N] [--tail N]` (since the sixth tooling step) prints a CI job's log through GitHub's jobs-logs API (`gh api repos/{owner}/{repo}/actions/jobs/{id}/logs`) with its escape codes taken out. `gh run view --log-failed` prints nothing for the nightly workflow's runs, which this reads. A run's id lists its jobs (`actions/runs/{id}/jobs`) and prints the log of each one that failed or timed out, of the jobs whose names contain `--job NAME` (in any case, given again for more), or of all with `--all`; a job's id prints that job's log. Which an id is, is told by asking GitHub: for a run's jobs first, and for a job's log when GitHub says it knows no such run. `--grep RE` prints the matching lines only, each as `N:line` with `--context N` (2 when not given) lines either side as `N-line` and `--` between groups, as `grep -n -C` does; `--tail N` prints the last N lines of what would be printed. The pattern is read by a small matcher of `xtask`'s own (`xtask/src/pattern.rs`: literals, `.`, classes, `\d \w \s`, groups, `|`, `* + ? {n,m}`, `^ $` and a leading `(?i)`), because a regular-expression crate would be built before every CI job for a search through a log; a pattern it cannot read is an error before GitHub is asked. A log keeps its timestamps. Through `rx`, whose copy has no `.git`, name the repository as for `ci-times`: `rx -- env GH_REPO=<owner>/<repo> cargo xtask ci-log RUN --grep 'FAIL|panicked'`. A job's log is kept by GitHub for 90 days; an expired one is the error `gh` gives.

**The same report at a desk.** `cargo xtask ci --tiers [-p CRATE]… [--top N] [-- NEXTEST ARGUMENT…]` builds and runs the tests as the blocking job does, in cargo's `ci` profile, and prints the same report with ten tests a tier. The profile is the point: a desk's own build optimises third-party crates and CI's does not, so a test that spends its time in one (a JSON reader, a regular-expression engine) is several times slower in CI than it looks. Steps 12 and 14 each put a Windows tier over its budget that way. A desk is still faster than a hosted runner, and Windows about twice as slow as Linux there: read the report for which tests the time is in, and for the tier's share of its budget with room to spare. `--like-runner` adds an estimate of what a runner would say (below).

### What a runner would say, from a desk

`cargo xtask ci --tiers --like-runner [-p CRATE]…` (since the fifth tooling step) runs the tests as `ci --tiers` does, at a hosted runner's four test threads (`--test-threads 4`), and after the report prints, for each OS, each tier's time at the desk, its estimate on a runner, its estimate on a slow runner, and the budget, with the three crates that make most of it; a tier a slow runner would put over its budget says so. `--from REPORT --like-runner` estimates from a report already made.

- **How it estimates.** Each crate's time in each tier, above the start of its processes, times a factor measured for that crate and tier on each OS. A crate the table does not know (a new one) takes its tier's factor. A slow runner is the measured runner times a measured ratio.
- **Why a factor a crate.** The kind of work decides it. Code of our own that is unoptimised in CI's build is two to four times as slow on a runner: `cortex-llm`'s replays 1.7 times on Linux and 3.2 on Windows, `cortex-tui`'s markdown 2.2 and 3.5. Work that waits on the disk can be slower at the desk than on a Linux runner, because the desktop's Linux flushes to a virtual disk (`cortex-config`'s integration tests 0.07, `cortex-core`'s 0.69). And Windows-only work is not done at a Linux desk at all: `cortex-tools`' system tests run PowerShell on Windows, 84 times their desk time. Whole tiers, as measured in the sixth tooling step with Windows' system tests two at a time: on Linux 1.4, 1.0 and 1.4; on Windows 2.6, 1.8 and 6.4 (the fifth's, with three: 4.4, 1.7 and 12.4 on Windows).
- **Optimised crates and generics.** A crate optimised in CI's build (`[profile.ci.package.*]`) is optimised in its own code only: a generic function of it is compiled in the crate that calls it, at that crate's level. `serde_json::to_vec::<Value>` in `cortex-session`, or `from_slice::<T>` in `cortex-llm`, runs unoptimised in CI's build whatever `serde_json`'s entry says. A session's line of 66 MiB took 400 ms to write at the desk in that build. The factors count it as the crate's own work.
- **How it was measured, and how to measure it again.** The same tree (the fifth tooling step's branch at `ef5009d`, the job in its two runs) at the desk with `cargo xtask ci --tiers --like-runner`, on a quiet machine (`rx --exclusive`), and on both runners as the head of an A/B, `try` with `-f command=test -f against=main -f count=5` (run 43691692866: start 3 ms on Linux, 10 ms on Windows), each test the median of its rounds. Then `cargo xtask ci --tiers --from DESK.xml --factors-from TRY-RUN` prints the table, by crate and tier, to paste into `xtask/src/like_runner.rs`; it reads the A/B's head, the tree whose job this `xtask` runs (an A/A run's two sides are one tree). The slow runner's ratio is tier 2 of the same tree in its pull request's CI run (43691685559, start 4 and 10 ms) over the measured runner's: 1.44 on Linux, 1.22 on Windows. **Measured again in the sixth tooling step,** after Windows' system tests went to two at a time: the step's branch at `5e2866b` at the desk (`rx --exclusive`, though the desk's disk stalled 54% of the run, which makes its file-heavy crates slow there and their factors low) against the branch's side of `try` run 43718003767 (start 4 ms on Linux, 6 ms on Windows). The fifth step's table read Windows' system tier of that tree at 84 s, where the runners read 39 to 71 s. **The first table,** measured on `main` at `9ddbf67` when the job was one run, read Windows' tier 2 of the split job 51% high (37.4 s against 24.8 s): a table is of one layout of the job, and is measured again when the layout changes.
- **How far off it is.** From the desk's report it was measured on, it gives the runner's figures by construction. From a second quiet run of the same tree at the desk, an hour later, it came within 15% on every tier of both OSes: tier 2 8.8 s against the runner's 9.7 s on Linux (9% low) and 21.1 s against 24.8 s on Windows (15% low); tiers 1 and 3 4 to 8% high. The desk itself moved more than that between the two runs: its own tier 2 was 14.2 s the first time and 9.7 s the second, mostly the flushing tests of `cortex-session` and `cortex-config` on the desktop's virtual disk. The estimate is as steady as the desk's disk. On another tree it is right where a change does more of what a crate's tests already did, and wrong where it adds another kind of work: a first Windows-only test, or a test that waits on the disk in a crate whose tests did not. Runners themselves differ by a factor of up to two, and the estimate is of two particular ones. Read it for "is this crate's tier near its budget on a runner", and measure a change with `try -f against=main`, which takes about two minutes for one crate ("Running an experiment on the runners").

### A run on the runners without a pull request

The `try` workflow (`.github/workflows/try.yml`) runs one `cargo xtask` command on Linux, Windows or both, for any branch that has been pushed. It blocks nothing and opens no issue.

```text
git push origin <branch>
gh workflow run try --ref <branch> -f command=startup -f profile=dist
gh workflow run try --ref <branch> -f os=windows -f command="test -p cortex-tools shell::"
gh workflow run try --ref <branch> -f command="stress -p cortex-testkit" -f count=200 -f load=6 -f cores=2
ci-wait --workflow try
```

| Input | What it is |
|---|---|
| `os` | `both` (the default), `linux`, `windows`, or `linux-22.04`: Ubuntu 22.04, whose kernel has Landlock ABI 4, the partial case of the sandbox ([architecture/06-permissions-and-sandbox.md](architecture/06-permissions-and-sandbox.md)). It builds without the cache: the cache's key names the OS and not its version, and build scripts built on the newer image do not run on the older one. |
| `command` | `test [-p CRATE]… [--dependents] [WORD]…`, `stress -p CRATE… [ARGS]`, `startup`, `perf [ARGS]` (step 20's), `perf -p CRATE… [NAME]` (a crate's ignored `perf_` tests, below), `size [OPTION]…` (the binary's size, below), `ci [ARGS]` or `mutate BREAK… [--jobs N]` (the breaks of a list, run on the runner, below); or one of the nightly workflow's jobs, as the nightly runs it and with nothing added: `partial-landlock` (on `os=linux-22.04`, the one runner whose kernel has the partial case), `advisories` or `unused`. Words are separated by spaces and may hold letters, digits and `_-:./=,()\|&!~*+@#`; nothing else is passed on. A crate is `-p x`, `--package x`, `-px` or `--package=x`; every other word of `test` goes to nextest, a test's name or an option (`--run-ignored only`). |
| `profile` | `ci` (the default: the blocking jobs' build), `release` or `dist`. For `size` it is the build's profile: `ci`, the default, is the command's own, the shipped `dist` build. |
| `count` | For `test` or `stress`, the repeats of a stress run (`test` becomes `stress`); for `startup`, its runs. |
| `load`, `cores` | For a stress run: busy loops beside it, and the cores to pin it to ("Running the tests many times over"). |
| `filter` | For `test` or `stress`: nextest filter expressions, separated by `;`, each passed to nextest as one `-E` argument, spaces and all. A test any of them matches is run: `-f filter="test(/shell::/) & !test(=slow); package(cortex-agent)"`. |
| `against` | For `test` in the `ci` profile: a ref to compare the branch with, on the same runner ("Two trees on one runner", below). `count` is then the number of rounds, 5 when not given. For `perf -p CRATE…`: the same, of the crates' `perf_` tests and the numbers they print ("Two trees' performance tests on one runner", below), 3 rounds when `count` is not given. |
| `commit` | A full commit hash (40 hexadecimal digits, lower case): the branch's side of the run is that commit and not the head of `--ref`, so that a variant needs no branch of its own ("A variant without a branch", below). Empty: the head of the ref. The commit's own `xtask` runs the command, so the workflow passes it `--commit` and `--capture` only when they are set (`capture=no`): a commit from before an input was added runs as long as that input is left at its default (a commit of the step's own branch from before `capture` failed as "unknown flag" until this). |
| `capture` | `yes` (the default: nextest keeps a passing test's output, as in CI) or `no`: a passing test's output is shown in the log (nextest's `--no-capture`, which runs the tests one at a time), for `test` or `stress`; refused with `against`, whose comparison is of runs made as the job makes them (since the seventh tooling step). |
| `testkit` | `none` (the default) or `profile`: a test-kit switch for the tests, from a list. `profile` sets `CORTEX_TESTKIT_PROFILE` and a directory each test's time profile is written to, which the run uploads ("Where a test's time goes"). The value reaches the job through `env:`, as the other inputs do. |

- **The tools a command needs are installed for it:** cargo-deny for `ci` (its `check` ends with it) and `advisories`, cargo-machete for `unused`, at the versions the other workflows pin. The workflow's condition reads the command's words with spaces round them, so `test -p x-ci` installs nothing. `command=ci` failed on a missing cargo-deny before the fourth tooling step.
- **What each command becomes** is decided by `cargo xtask try`, under unit tests, not by the workflow's script: `test` is the blocking job's build and run with the tier report (`ci --tiers --top 20`) in the `ci` profile, and `test --cargo-profile P --profile ci` in another; `startup` builds `cortex` in the profile (release or dist, refused for `ci`) and measures it (`startup --profile P`); `perf` and `ci` take their words as they are, except `perf` with a crate (`-p`, in any of cargo's spellings), which is `test --cargo-profile release --profile perf -p CRATE… --run-ignored only -E 'test(/(^|::)perf_/)' --no-capture --test-threads 1` and any words after the crates: the crates' ignored `perf_` tests in a release build (`--profile dist` for a dist build), one at a time, their output shown, and nothing else, in nextest's `perf` profile, which reports a test as slow at 60 s and stops it at 30 minutes (tier 2's limit of 10 s stopped step 18's tree of 100,000 files, a measurement, while it made its files). A word narrows them (nextest takes a test that matches the word and the filter), so `perf -p cortex-index warm` is the one warm-map test; `--filter`, `--load`, `--cores`, `--count` and `--against` are refused with it. `against` runs pass `--keep-going` to `ab`. **With `against`, `perf -p CRATE…` is** `perf-ab --base ../ab-base --label REF --cargo-profile release -p CRATE… [--count N] [NAME]…` (`dist` with `--profile dist`; a count below 2 is 2; a word that is an option is refused, and so are `--load` and `--cores`; `perf` without `-p` is refused with `against`). **`size [OPTION]…` is** `size [OPTION]… [--profile P] [--target x86_64-unknown-linux-musl]`: the options of `cargo xtask size` as they are, the `profile` input as `--profile` (nothing for `ci`), and on a Linux runner the static target the budgets are of when the words name none (a runner's own default would be the gnu build). It is refused before anything is built when a word is `--profile` (the input chooses), `--at` (a runner's checkout is one commit deep: use the `commit` input, which checks out and measures any commit), a `--target` of another system than the runner's, `--breakdown` on Windows, `--check` or `--against-main` in a profile other than `dist`, or an input that does not go with it (`against`, `count`, `load`, `cores`, `filter`, `capture`).
- **`mutate`** (since the seventh tooling step) is `cargo xtask mutate --minutes 0 BREAK… [--jobs N] [--again] [--no-compile-check] [--file PATH]`: the breaks of the lists named ("Breaking the code on purpose") on the runner, to the end in one job, as `--minutes 0` says (its time budget is for the shared test lock of a desk, which a runner has no one to share). It builds its copies of the tree from cold, so the job's time limit is 90 minutes for a `mutate` command and 40 for the others. At least one break, list or `--file` must be named: the whole of every list is more than one job. `--check`, `--list`, `--report`, `--tests`, `--fix-in` and `--write` run no break and are refused, and so are `--minutes` (`try` gives it), `--count`, `--filter`, `--load`, `--cores` and `--against`, and a profile other than `ci`. The run's results (`target/mutate/results.jsonl`) and the logs of the runs that named no failed test (`target/mutate/logs/`) are kept in the artifact with the log. The exit code is `mutate`'s: 0 when every break did what its list expects, 1 when one did not.
- **`--dependents`** (since the seventh tooling step): a `test`, `stress` or `perf -p` command that has `--dependents` beside `-p CRATE` is resolved by `try` as `cargo xtask test --dependents -p CRATE` resolves it (the same code, `dependents::expand_in`): the crates whose tests can see a change to the ones named are added, and the job runs `ci --tiers -p A -p B …`. The crates it added are printed, first, in the log and the summary. Before this step the word went on to nextest as a test name's neighbour (`ci --tiers -p cortex-config -- --dependents`), which rejected it after the build, and the job failed with no test run. The workspace is read from the checked-out tree, so with `commit` it is that commit's.
- **A word `try` cannot pass on is refused before anything is built,** with the word and the reason, by `try` at the start of the job. Two kinds. A word of `test`, `stress` or `perf -p` that nextest would not take: an option of `ci --tiers` (`--tiers`, `--top`, `--from`, `--compare`, `--like-runner`, `--factors-from`), what `try` sets itself (`--profile`, `-P`, `--cargo-profile`), an input (`--count`, `--load`, `--cores`, `--filter`, `--against`, `--commit`; a stress run's own `--count`, `--load`, `--cores` and `--first-seed` pass), and the options of `ab` (`--keep-going`, `--base`, `--label`); a word after a `--` of the command's own is the test binaries' and is not looked at. And the command that `try` makes from the rest, read by the parser of that command: `ci`, `stress`, `ab`, `perf`, `mutate` take their arguments as `cargo xtask` takes them, and `startup` its profile, `--runs`, `--budget`, `--check` and `--workspace`, so that `ci --nope` or `stress -p x --stress-count 3` is refused here and not by the command after the build. The words nextest itself takes (its options and filters, a test's name) cannot be checked without running it, and go through.
- **`cargo xtask try --dry-run --command "…" [--profile P] [--count N] [--load N] [--cores K] [--filter F] [--against REF] [--commit SHA] [--os OS] [--testkit T]`** does only that, at a desk: it reads the inputs as the job does, resolves `--dependents` against this tree, prints the notes and `$ cargo xtask …`, the command the job would run, and exits 1 with the job's own message where the job would refuse. Nothing is built. `--os` and `--testkit` are the workflow's inputs that `xtask` is not given; a dry run checks their values and says what they would change (`partial-landlock` off `linux-22.04`; `testkit=profile` with `against`, which the workflow leaves unset). Use it before dispatching: a refused dispatch costs a job's start and the toolchain's install.
- **`commit`:** the workflow checks the given commit out in place of the ref's head (`actions/checkout`'s `ref`, empty for none, which is the ref the run was dispatched on), after a step that reads the input from the environment and refuses anything but 40 lower-case hexadecimal digits; `cargo xtask try` checks the form again and that `HEAD` is that commit. The workflow file stays the one of `--ref`. The checked-out commit's own `xtask` runs the command, so **the commit must contain this `try`**: a commit from before the seventh tooling step has no `--commit`, and the job fails at its start with "unknown flag". A commit that no pushed branch reaches cannot be fetched by hash: push it first.
- **The inputs reach the command as arguments, through the environment, never as text in the script.** `cargo xtask rules` refuses any workflow whose `run:` script has an input or a part of the event pasted into it.
- **The output** goes to the log, its last 80 lines to the run's summary page, and the log and any JUnit report are kept as the artifact `try-linux` or `try-windows`, for 14 days.
- **The cache.** The job's id and environment are the blocking test job's, so a run in the `ci` profile restores the main branch's cache and builds only what the branch changed. It writes no cache. A release or dist build builds from scratch: up to 40 minutes on Windows, which is the job's limit.
- **A dispatched workflow must be on the main branch** before it can be started on another; a branch made before it was merged has to be rebased first.
- **It replaced `windows-try`** in the third tooling step, which deleted that workflow: `-f os=windows -f command="test -p CRATE FILTER"` is what it ran, and `-f count=N` its repeats. **A test that passes every repeat of one crate may still fail in the blocking job:** the repeats do not have the rest of the workspace's tests running beside them.

### Running an experiment on the runners

A question a desk cannot answer (does it pass on Windows, on the kernel with Landlock 4, is it faster on a hosted runner) is a `try` run of a pushed branch. A branch whose pull request is not open yet is fine; so is a scratch branch named for the worktree (`<worktree>-try`), deleted afterwards.

- **One OS, one crate, a few tests:** `gh workflow run try --ref <branch> -f os=windows -f command="test -p cortex-base" -f filter="test(/location/); test(=paths::x)"`. Each `;`-separated filter is one `-E`; a test any of them matches runs. A test's name as a word of `command` works too, but a filter is exact.
- **The partial Landlock:** `-f os=linux-22.04 -f command=partial-landlock` is the nightly's job; `-f os=linux-22.04 -f command="test -p cortex-sandbox"` is the crate's tests there, with `backends` turned on ("A crate alone", below).
- **Many times over:** `-f count=200` makes `test` a stress run; `-f load=6 -f cores=2` squeezes it onto two cores beside six busy loops. A race that shows once in a thousand runs at a desk often shows in a few hundred there.
- **A change's cost, apart from the runner:** `-f against=main -f count=5` builds both refs and runs them in turn on one runner ("Two trees on one runner", below).
- **A variant without a branch of its own** (since the seventh tooling step). Wave 10 made twelve throwaway branches to try variants, because a force-push to one is refused. Commit each variant on one branch instead, each on top of the last (a commit that reverts the previous variant and makes the next), push normally, and dispatch each commit by its hash:

  ```text
  git commit -am "Variant A"; git push origin <branch>
  gh workflow run try --ref <branch> -f os=windows -f command="test -p cortex-llm" -f against=main -f commit=$(git rev-parse HEAD)
  git commit -am "Revert A, make B"; git push origin <branch>
  gh workflow run try --ref <branch> -f os=windows -f command="test -p cortex-llm" -f against=main -f commit=$(git rev-parse HEAD)
  ```

  Every commit reachable from a pushed branch can be fetched by its hash, so the earlier ones stay runnable after the branch has moved on. `--ref` stays the workflow file, so the workflow of the branch's head runs whatever commit is chosen, and `against` still names the other side. The commit's own `xtask` runs the command, and must contain `try`'s `commit` flag: a variant is a commit on top of this step's. `ci-wait --runs ID…` waits for runs by id; with several dispatched on one branch, note which run id each hash got.
- **Which crates a change reaches:** `-f command="test --dependents -p cortex-config"`, resolved as `cargo xtask test --dependents` resolves it, the crates it added named at the top of the log; `cargo xtask try --dry-run --command "test --dependents -p cortex-config"` shows them at a desk.
- **Breaks on a runner:** `-f os=windows -f command="mutate tooling-7 --jobs 2"` runs the list's breaks there, for a break whose code is built only on Windows or whose tests behave differently there ("Breaking the code on purpose": `mutate` cannot tell a break in code the build does not compile). `cargo xtask ci-log RUN --grep 'caught|NOT CAUGHT|COULD NOT'` reads the verdicts.
- **Is my change slower on the runner, for one crate:** `gh workflow run try --ref <branch> -f os=windows -f command="test -p <crate>" -f against=main -f count=5`, the A/B of that crate's tests alone, five rounds on one runner. For `cortex-llm` it took 2 min 24 s on Windows and 1 min 20 s on Linux from start to end of the job (run 43667663980), the base's build included. `cargo xtask ci-times --ab RUN` prints its tables, the crates and the tests that moved, and `cargo xtask try-result RUN` everything the run found, for each OS, in one step.
- **A passing test's output, on a runner:** `-f capture=no` passes `--no-capture` to nextest, so what a passing test prints (a `Phases` breakdown, a measurement's own table) is in the log, which `cargo xtask ci-log RUN --grep …` reads from a desk: `gh workflow run try --ref <branch> -f os=windows -f command="test -p cortex-tui" -f filter="test(/first_frame/)" -f capture=no`. nextest then runs the tests one at a time, so the tier report's times are of a serial run and do not compare with the job's; it is refused with `against`. A count makes it a stress run, each repeat's output shown (since the seventh tooling step, for step 23's start-to-first-frame figures).
- **A crate's performance tests, in release, on a runner:** `gh workflow run try --ref <branch> -f os=windows -f command="perf -p cortex-index"` builds the crate's tests in release and runs only its ignored `perf_` tests, one at a time, with their output (`-f command="perf -p cortex-index warm"` for one of them). It is the command step 18's records give by hand (`test -p cortex-index --run-ignored only --no-capture --test-threads 1` with `-f profile=release`). It first fetches the corpus of real code that a measurement of real code reads, and checks it against its pin ("A tree of real code to measure"). `perf` without `-p` is still step 20's terminal measurement. The tests' own tables are in the log; `cargo xtask ci-log RUN --grep 'perf_'` reads them from a desk.
- **Two trees' performance tests:** `gh workflow run try --ref <branch> -f os=windows -f command="perf -p cortex-index" -f against=main` builds the crate's `perf_` tests of both refs in release, runs them in turn three times each on one runner, and compares the numbers they print ("Two trees' performance tests on one runner", below). `try-result RUN` shows the comparison.
- **The binary's size on a runner:** `gh workflow run try --ref <branch> -f os=both -f command="size --check --against-main"` builds the shipped binary on both systems as the pull-request job does (the musl target on Linux), `-f profile=release` the thin-LTO build in a fraction of the time (no budget, no `main` to compare with), `-f command="size --breakdown --top 40"` the bytes by crate (Linux only), and `-f commit=<hash>` the size of any commit. The cost is the pull-request job's: three to five minutes a system, and twice that with `--breakdown`.
- **What a run found, in one step:** `cargo xtask try-result RUN` (`--os windows` for one runner) prints, for each OS the run had, the A/B's tables and what moved, or the tiers, or the stress summary; every failed test with its message's first lines; and, for a job that failed with no report, the end of its log. It fails when the run did, naming what failed. `ci-wait --runs RUN` first, then this. The details are in "A CI run's test times".
- **A run's tiers against another's, both OSes:** `cargo xtask ci --tiers --compare RUN --against main --os both` (a `try` run of `test` is a source as a `ci` run is). For an A/B, `ci-times --ab RUN` or `try-result RUN`.
- **Why a run failed, from a desk:** `cargo xtask ci-log RUN` prints the logs of the run's failed jobs, the nightly's and a `try` run's included, and `--job windows --grep 'FAIL|panicked|timed out'` the lines that matter ("A CI run's test times").
- **What CI would say, before a pull request:** `-f command=ci` runs `cargo xtask ci`, the static checks and the tests; `-f command="ci lint"` the checks alone.
- **Waiting:** `ci-wait --branch <branch> --workflow try` waits for the branch's head commit, so a failing nightly is not waited on. With several runs dispatched at once, look at each: `gh run list --workflow try --branch <branch>`, or wait for them by id with `ci-wait --runs ID…`. `ci-wait` passes over a dispatched or scheduled run created more than `--fresh` minutes (2 when not given) before it started, and a run already cancelled when it first sees it, and names each one it skips; each dispatched run on a commit is watched on its own. `--any-age` turns the age rule off, for a run dispatched earlier.
- **An A/B at the desk:** `rx ab [--against REF] [AB ARGUMENTS]` copies `REF` (`origin/main` when not given) to `<worktree>-base` on the desktop and runs `cargo xtask ab --base` against it ("Two trees on one runner", below): one machine, both trees, without a hosted runner.
- **Reading it:** the log's last 80 lines are on the run's summary page; the whole log and any JUnit report are the artifact `try-<os>`. A `test` in the `ci` profile ends with the tier report, whose first line gives the run's start cost: a test's time means something only beside it.
- **The traps sessions fell into:**
  - **Comparing two runs on two runners.** Hosted Windows runners differ in speed by a factor of two. Two runs are compared only on runners of the same speed, told by the start cost the tier report prints, or in one A/B run.
  - **Git Bash as the shell** (before the third tooling step): `try` ran the command from Git Bash on Windows, whose `mkdir` of `target/try` made a Windows test of a file held with no sharing fail that passed in the blocking job. It now runs from PowerShell, as the blocking job does.
  - **A crate's repeats alone are not the workspace.** A test that passes every repeat of one crate may fail in the blocking job, with other crates' tests beside it.
  - **A crate built alone builds what the crate turns on.** `cortex-sandbox` alone compiled its confinement tests out until the fourth tooling step turned `backends` on for it.
  - **A workflow is the branch's.** A dispatched run uses the workflow file of the ref it runs on, so a change to `try.yml` is tried by dispatching on the branch that has it.

### A tree of real code to measure

Step 18's review found its generated tree about ten times lighter than real code, and measured real code from whatever the cargo registry of the machine held: a desk's registry and a hosted runner's are different crates, so a desk's number and a runner's for "real code" did not compare. The corpus is one pinned set of real Rust, the same bytes on every machine:

- **What it is:** 20,162 `.rs` files of 670 crates from crates.io (324 MB; the median file is 4.5 KB, six are over 1 MB, 551 have CRLF line endings, one a byte-order mark; the longest path is 119 characters, which fits Windows' limit with the places it is kept at). The list is `corpus/dependencies.toml`: tokio, syn, wasmtime, boa, reqwest, tantivy and thirty more, which between them need the 670. It is what a harness meets, tests, generated tables and bindings included.
- **How it is pinned,** in three layers. `corpus/Cargo.lock` holds the version and SHA-256 checksum of every crate, and cargo checks each download against it. `cargo xtask corpus fetch` has cargo fetch them (`cargo fetch --locked`, in a manifest it makes for the purpose, in a folder outside the repository: no workspace, no code, nothing built), and copies every `.rs` file out of cargo's registry, byte for byte, into a folder named for its hash, each file dated 1 January 2021 so that a fresh fetch is not "modified a moment ago" to an index that reads it. `corpus/PIN` holds the number of files, the bytes and a **hash of the paths, lengths and contents** (64-bit FNV-1a, the hash `mutate` keeps its results by: it is here to see that the folder is what was pinned, which a single changed byte always breaks, and not to resist anyone, which cargo's SHA-256 does). The folder is checked against the pin **after every fetch, before it is put in place**, and **every time a test asks for it** (`cortex_testkit::corpus::real_code`). A folder that is not whole is removed and made again by `fetch`, and refused by a test with the command to run.
- **Line endings** are whatever the crates were published with. Nothing in the path touches them: cargo's registry sources are unpacked from the crate's tarball, not checked out of git, so `autocrlf` and `.gitattributes` do not apply; the corpus is never in the repository; and the copy reads and writes bytes. A test holds that a changed line ending is refused ("a line ending that changed").
- **Where it is kept:** outside the repository and outside `target`, so that `cargo clean` and a new worktree leave it be and one fetch serves every worktree: `$XDG_CACHE_HOME/cortex-harness/corpus/<hash>` (`~/.cache/…` when it is not set) on Linux, `%LOCALAPPDATA%\cortex-harness\corpus\<hash>` on Windows. `CORTEX_CORPUS_DIR` names another folder to keep them in: `try` sets it to a folder in the runner's temporary directory, on the disk the workspace is on, so that a measured tree can hard-link the files (on Windows the user's cache folder is on the system disk). **Its size:** 324 MB of content, 373 MB of disk with 4 KB blocks, in 4,769 folders. A corpus of an earlier pin is not removed by a new one: delete its folder. A folder `.work-<process id>` beside them is a fetch that was killed: delete it.
- **How long it takes,** measured at the desk (through `rx`, Linux on the desktop) and on the laptop, the dev build of `xtask` (tooling 7): a **cold fetch** with an empty cargo registry and an empty cache, 6.2 s at the desk (5.1 s of it cargo downloading the 670 crates, 0.6 s copying, 0.6 s hashing) and, on the laptop with the crates already in its registry, 4.9 s (0.6 s of cargo, 1.5 s copying, 2.8 s hashing, the hash loop being unoptimised there); a fetch at the desk while its disk was stalled by other sessions' builds, 14.9 s (6.6 s copying). A **warm check**, which reads and hashes the whole corpus: 0.5 s at the desk and 2.7 s on the laptop in `xtask`'s dev build, and 0.9 s (884 ms) in a release build of the perf test at the desk, with the disk busy. The same bytes came out at the desk and on the laptop: hash `285100c9ac0c85f0`. What a hosted runner takes is in the `try` run's log (`cargo fetch:`, `copied …`, `hashed in …`, `fetched in …` lines), which step records quote.
- **How a test asks for it:** `cortex_testkit::corpus::real_code()` returns the folder after checking it, and fails with the command to run when it is not there or not whole. Nothing blocking asks for it: a `perf_` test is ignored in the blocking checks. `cargo xtask corpus path` prints the folder, for a shell (`CORTEX_PERF_SOURCE=$(cargo xtask corpus path)`); `corpus check` verifies and prints its size and hash. `cortex-index`'s `perf_a_tree_of_real_code` reads it and, since the eighth tooling step, `cortex-tools`' `perf_search_real_code` and `perf_diffing_a_reread_of_real_code` and `cortex-llm`'s `perf_decoding_a_large_tool_call_of_real_code` read it too. `CORTEX_PERF_SOURCE` names another directory for the index's test to read in its place (a measurement of that, not of the corpus: do not compare the two).
- **How `try` has it:** `perf -p CRATE` runs `corpus fetch` before it builds anything, on Linux and Windows, and so does it with `against` ("Two trees' performance tests on one runner"). It is fetched each time and not cached by the workflow: a cold fetch costs seconds where a cache of twenty thousand files would need a key, a pinned action and a restore, and the time is in the run's log (`fetched in … s`). No other `try` command fetches it.
- **To change it:** edit `corpus/dependencies.toml`, run `cargo xtask corpus pin` (`--update` to take the newest versions the list allows, which changes more than the list does), and commit `corpus/`. `pin` writes `Cargo.lock` and `PIN` and keeps the new corpus where it is looked for. A figure measured on the corpus is of its hash: a new pin is a new baseline, and the page that holds the figure says which hash it was.
- **What it is not:** the crates are read as test input, kept outside the repository and never committed, built or shipped. They are under their own licences (the corpus's are almost all MIT or Apache-2.0, some of them with Unicode-3.0, BSD, Zlib or MPL-2.0 terms, and a few offer GPL-2.0 or LGPL beside a permissive one); nothing is copied into the harness. `cargo deny` does not read it: it is not a dependency of anything.
- **What was weighed instead.** A tarball as a release asset: a copy of third-party source on our account, a step to upload and refresh it, and bytes that cargo's checksums do not vouch for. A git repository at a commit: a clone with its history, and the checkout's `autocrlf` setting, which differs between a desk and a hosted Windows runner, changing the bytes it was to fix. The corpus in the repository: 324 MB of other people's code in every clone. The crates' own checksums, cargo's fetch and a hash of the copy need no host, no account and no new dependency.

### Two trees on one runner

Hosted Windows runners differ in speed by a factor of two, so a branch's run and the main branch's land on runners that cannot be compared, and a change's cost to a tier is lost in the difference. `cargo xtask ab --base DIR [--label NAME] [--count N] [-p CRATE]… [-- NEXTEST ARGS]` takes the runner out of it:

- **Both trees are built once,** this one and the one at `DIR`, as the blocking test job builds them, each in a build directory of its own (`<tree>/target`), so that building one never rebuilds the other. **Each is run as its own job runs it:** in two runs, or in one for a tree from before the split ("Each tier is measured under its own load", above).
- **Then they are run in turn on the same machine,** `N` rounds (5 when not given), the first round base then head, the next head then base, so that whatever drifts during the job falls on both alike.
- **Each test's time is the median of its runs,** and the two sides are compared as `ci --tiers --compare` compares two CI runs, by tier above the start of the processes, by crate, and the tests that moved most, **with one start cost for both:** the 1st percentile of both sides' tests together. They ran on one machine, and each side's own would differ by the noise of a millisecond, which over the unit tier's thousand tests is a second: the first A/A run of a tree against itself, so held, showed its unit tier 0.8 s slower than itself. Each round's tier totals are printed first: their spread on one side is the noise a difference has to stand out of.
- **On a hosted runner,** `try` runs it with `-f against=REF`: the workflow checks `REF` out and moves it beside the branch's checkout, to `../ab-base` (inside it, the branch's `.cargo/config.toml` would apply to the base's build too, and `ab` refuses a base inside its tree), and `cargo xtask try` turns `test` into `ab --base ../ab-base`. The base builds without the cache, which takes a few minutes more on Windows. Neither checkout keeps the job's token: the base may be any ref's code. Each round's two reports are kept in the head's `target/ab/`, and uploaded with the run's log.
- **A test that fails ends the run,** after both builds, unless `--keep-going` is given (since the sixth tooling step; `try` gives it for every `against` run). With it, a round in which a side's run fails (a test failed, or the run could not be made) is recorded as failed for that side and the run goes on to the next round. The comparison is of the rounds **both** sides finished: a round in which either side failed is left out of both sides' medians and of the rounds table, which keeps the other rounds' numbers. After the comparison the failed rounds are listed, each with the tests its report names (or what the run said when it wrote no report), and the command exits as a failure, so that the job is red and the measurement is still in its summary; with no round finished on both sides it says so and compares nothing. A failed round's report is kept in `target/ab/` with the others. Without `--keep-going` nothing changes: the first failing run is the error.
- **A test that failed on both sides is skipped, not a failure** (since the seventh tooling step, with `--keep-going`). Wave 10 lost three whole A/B runs, twenty minutes each on Windows, to one test that failed on both trees. Now a round in which both sides' runs failed **only by tests failing, and the same tests on both sides**, is compared, without those tests. Such a test is left out of both sides' medians and of the comparison **in every round**, not only the one it failed in: a time taken in a round where it passed is no more a measurement than one taken where it failed. The summary, at the head of the table in the job summary and again at the end of the log, says `N TEST(S) FAILED ON BOTH SIDES`, and names each test with the rounds it failed in and the first line of each side's failure message; the command exits 0 when that is all that went wrong. What it will not take for one:
  - **A test that failed on one side only,** in any round: the other side passed it, did not run it (a filter, a test the tree does not have) or has no report. That round is failed for that side as before, and the command exits as a failure. A test that is missing on one side is never read as failed there.
  - **A run that failed otherwise too:** a run counts as failing by its tests only when nextest's exit code says that (100) **and** its report names a failed test, in each of the job's two runs that failed. A build that broke, a run killed by a signal, a report that lists nothing, a failure no report names, or two runs of which one failed by its tests and the other broke, is not that, and the round is failed.
  - **A report that could not be read or put together.**
  - **The job's two runs.** A job is two runs (tiers 1 and 2, then the system tests), and with `--keep-going` the second is made even when the first failed, so that a failing tier-2 test does not leave tier 3 unmeasured; their reports are brought together after. Without it the first failing run still ends the job, as it always did.
  Tested on JUnit reports written for the purpose (`xtask/src/ab.rs`): a test failing on both sides in some rounds, on one side only, missing from one side, with a run that broke too, with no report, and with two failing tests of which only one is shared; the job's two runs with the first failing; and nextest's exit codes. Its breaks are in `mutations/tooling-7.breaks`.

```text
gh workflow run try --ref <branch> -f os=windows -f command=test -f against=main -f count=5
```

### Two trees' performance tests on one runner

`cargo xtask ab` takes the runner out of a comparison of tests' times. `cargo xtask perf-ab --base DIR [--label NAME] [--count N] [--cargo-profile release|dist] -p CRATE… [NAME]…` (since the eighth tooling step) does the same for the numbers a performance test prints. A figure measured on one hosted runner and the main branch's figure, measured on another, do not compare: runners differ by a factor of two, and the two runs land on different ones.

```text
gh workflow run try --ref <branch> -f os=windows -f command="perf -p cortex-index" -f against=main
gh workflow run try --ref <branch> -f command="perf -p cortex-tools -p cortex-llm real_code" -f against=main -f count=5
ci-wait --runs RUN
cargo xtask try-result RUN
```

- **What it does.** Both trees' ignored `perf_` tests of the crates named are built once each, in a release build as `perf -p CRATE` builds them (`--cargo-profile dist` for a dist build), each in a build directory of its own. Then they are run in turn on this machine, `--count` rounds (3 when not given, 3 to 20: with two, two runs of one tree read `apart` a third of the time, and with three a tenth, so use 5 for a decision): the first round the base then the head, the next the head then the base, so that what drifts during the job falls on both alike. Each run is one `cargo nextest run` in the `perf` profile, one test at a time with its output shown, and a word narrows the tests as it does for `perf -p`. A run that fails ends the command, with its output in the log: a perf test fails by an assertion on what it measured or by a corpus that is not there, and neither is a number to average.
- **How a test's numbers are read.** A test that wants its numbers compared prints each with `cortex_testkit::numbers::report("subject.what", value, "unit")`: the line `perf: subject.what 28.9 ms`. The name is one word of letters, digits and `._-`, starting with what is measured (`search.literal_rare_real_code`); the unit is one word and is only shown. Any other line the test prints is for a person and is not read. A name printed twice in a run is the median of its values, and a name with two units is two measurements. The line is the whole convention: the existing tables and what they measure are as they were. **The tests that print them** (a test that prints none is unaffected, and an A/B shows nothing of it): `cortex-index`'s `perf_a_tree_of_real_code` (`index.cold_index_real_code`, `index.warm_pass_and_map_real_code.nothing_changed` and `.one_file_changed`); `cortex-tools`' `perf_search_real_code` (`search.literal_rare_real_code`, `.literal_common_`, `.regex_`, `.no_match_`) and `perf_diffing_a_reread_of_real_code` (`diff.reread_changed_median_real_code`, `.reread_unchanged_median_`, `.reread_changed_95th_`); `cortex-llm`'s `perf_decoding_a_long_answer_and_a_large_tool_call` (`llm.decode_long_answer_and_large_call`) and `perf_decoding_a_large_tool_call_of_real_code` (`llm.decode_large_call_real_code`). The tests of real code read the pinned corpus ("A tree of real code to measure"), which `try` fetches first for `perf -p` with or without `against`; both trees must pin the same corpus, or the base's test fails with the command to run.
- **What the report says.** For each measurement: each side's median over the rounds with its least and most beside it, the head's median less the base's, with its percentage, and whether the two sides' ranges are `apart` (they do not overlap: the difference is more than this run's own spread) or `within noise` (they do, and the run cannot tell the difference from the machine's). A measurement that only one side printed (a new test, or one the head dropped) says so. Nothing judges which way is better: a time is better lower and a rate higher, and the unit is shown for the reader. The table is in the log, in the job's summary and, as JSON (`target/perf-ab/results.json`), in the run's artifact, from which `cargo xtask try-result RUN` prints it for each OS.
- **What it cannot tell.** With three rounds a range is two or three points: `apart` is a sign and not a test, and a difference near the spread wants more rounds (`count`). The very first run, the base's, reads files the machine may not have cached (the head's first run finds them in the cache, if the tests read the same files): that is one round of three, which each side's median discards. It compares the numbers a test prints, not the time of the test, and not a test that prints none.
- **What it costs.** Two release builds of the crates named, from scratch (the runner's cache is for the `ci` profile), and then the tests' own time six times over for three rounds; the job's limit is 60 minutes for it. A crate whose tests take a minute costs six minutes of runs.
- **How it is tested.** `xtask`'s unit tests (`xtask/src/perf_ab.rs`): the request and what it refuses; the nextest commands that build and run; the numbers read out of an output with noise, carriage returns, broken lines, a repeated name and two units; the order of the sides over the rounds with a runner that fails in the third run; a measurement on one side only; `apart` and `within noise` at the edges (overlap, a faster head, one run a side, a base of nothing); the report's row; the record read back; and in `try_run.rs`, `perf -p … --against` become `perf-ab` with their words, rounds, profile and refusals, and fetch the corpus. In `try_result.rs`, a run's artifact with a record prints the comparison and not the last run's test times. The test kit's `numbers` module has unit tests of the line, and the same line is held on `xtask`'s side. The workflow is not run by a pull request that changes only it ("A run on the runners without a pull request"): the first run of `perf-ab` on a runner is the one dispatched on the branch that adds it. Its breaks are in `mutations/tooling-8-measure.breaks`.

### The binary's size by crate and at a commit

`cargo xtask size` (since the eighth tooling step) takes more than it did:

```text
cargo xtask size [--check] [--target TRIPLE] [--against-main]
                 [--profile release|dist] [--breakdown [--top N]] [--at COMMIT]
```

- **`--profile release`** builds the thin-LTO `release` profile instead of the shipped `dist`, stripped as `dist` is (`release` is not stripped by default, and its size would be mostly its symbol table's: `size` sets `CARGO_PROFILE_RELEASE_STRIP`): a fraction of the build time, and not the shipped size (fat LTO is about 7% smaller), so it has no budget and no `main` to compare with: `--check` and `--against-main` are refused with it. For a look at what a change does to the size when a minute matters more than the byte.
- **`--at COMMIT`** builds the size of another commit: the commit's tree is read from this repository's history with `git archive`, extracted with `tar -m` into `target/size-at/<hash>` and built there with a build directory of its own (the build machine's folders are taken out of its paths as for any `size`), measured and removed. `-m` makes every file as new as the extraction: `git archive` dates each file as its commit, and a build directory that holds artifacts newer than that takes the file for unchanged. A copy with no `.git`, which the desk's `rx` makes, cannot do it; neither can a runner's checkout, which is one commit deep (`try` refuses `--at`: its `commit` input checks out any commit and measures it). The record `size` keeps for the workflow is not written for a commit but this tree's.
- **`--breakdown`** prints the binary's bytes by crate. It builds the same code a second time with the profile's `strip` turned off, in a build directory of its own (`target/size-breakdown`, so neither build rebuilds the other; the build costs as much again), reads the symbols with `nm --print-size --demangle` (binutils: on the runners and on a Linux desk) and adds each symbol's size to the crate its name starts with: the type's crate for a method of a trait (`<serde_json::Value as Debug>::fmt` is `serde_json`'s), the generic's own for generic code (`core::ptr::drop_in_place<cortex_core::X>` is the standard library's), and the standard library's `core`, `alloc` and `std` as one row. Symbols of no Rust crate are one row (C, assembly and libc), and data with no name of its own (strings, tables) another. The last row is what is in no symbol: the headers, the unwind tables and padding, as the stripped binary's size less the symbols'. The shares are of the stripped binary, the one that is measured. `--top N` lists the N largest crates (25 when not given) and the rest in one row. The table is printed and added to the job's summary, after the verdict, so that a failure of the breakdown does not hide it.
- **What it cannot tell.** A symbol is the code that is left: what the linker folded into another or threw away is not in it, and two names at one address count once. A generic function is the crate that owns the generic, as for `cargo bloat`, so `std` holds code instantiated for our types. **On Windows it does nothing:** an MSVC binary keeps its symbols in a PDB, which `nm` does not read, and the command says so before it builds anything (`try` refuses it too). The same code is about 1.15 to 1.2 times the Linux binary's size on Windows, so the Linux breakdown is the one to read. On macOS and other targets it is refused for the same reason.
- **How it is tested.** `xtask`'s unit tests (`xtask/src/nonblocking.rs`): the request and its refusals (a profile that has no budget, a commit's name with an option, a space or a revision's syntax in it); a runner's target and the breakdown on Windows; the report of a profile that is not shipped; `nm`'s output read (a symbol in `bss`, with no size or at an address already seen is left out); the crate of each kind of name (a function, a method of a trait, a reference, a slice, a primitive's impl, the standard library, C, an anonymous constant); the sums and their order; the table's rows, shares and remainder; and a real repository that the test makes, with a commit dated in 2001, extracted so that its files are dated now. The builds themselves are not run by the tests: `size` was run at the desk, and its first run on the runners is the dispatch of this step's branch. Its breaks are in `mutations/tooling-8-measure.breaks`.

### This branch on top of others

A clean rebase can hide a conflict of meaning: in wave 6 a pull request added a trait method with a default body, a parallel one wrapped the trait without forwarding it, and each passed alone. `cargo xtask combine PR…` checks a branch on top of the pull requests that will merge before it, before either merges:

- **It makes a clone** of the repository under the build directory (`target/combine/tree`) with `git clone --shared`, which reads the repository's objects and writes nothing to it: no branch, no ref, no worktree entry, no `FETCH_HEAD`. The session's worktree, its branch and its repository are not touched, and a test holds that, reading the repository's branch, head, refs, worktrees and status before and after.
- **It puts together** the main branch as GitHub has it now, then each pull request's commits since it left the main branch, in the order named, then this branch's commits since it left the main branch: what a rebase merge of each would make. Uncommitted changes are not in it, and it says so.
- **A commit that does not apply stops it,** naming the pull request, the commit and the files in conflict. Otherwise it runs `cargo xtask ci` in the clone, with a build directory of its own (`target/combine/target`), kept between runs so that the next builds only what changed.
- **It cleans up after itself:** the clone is removed when the run ends, pass or fail, and any clone a killed run left is removed when the next one starts. `--keep` leaves it to be looked at; `--no-ci` combines and runs nothing.
- **It runs git from inside `xtask`,** so the worktree shell guard does not see it ([shell-guard.md](shell-guard.md)). It asks `gh` whether each pull request is open, and says so when `gh` cannot answer.
- **Through `rx`,** whose copy of the tree has no `.git`, the branch is taken from GitHub: push it, then `rx -- cargo xtask combine --repo https://github.com/<owner>/<repo> --head <branch> 41 42`. Or, for commits not pushed yet, `rx --git -- cargo xtask combine 41 42`: `--git` gives the copy a real `.git` from a bundle of every ref, with `HEAD` at the worktree's commit and the index at `HEAD`. Without `--git`, a `.git` that `rx` made is removed.
- **How it is tested:** against a small repository a test makes, standing for GitHub, with two pull requests as `refs/pull/N/head`: two that change different lines combine, and the check sees all three layers; two that change the same line stop at the second, naming it, its commit and the file, and the check is not run; a session in a linked worktree, whose `.git` is a file, is combined and its branch, head, refs, status, stashes and the list of worktrees are the same after; and a pushed branch is taken from the remote. Each test starts git about forty times: under 0.1 s on Linux, and seconds on a Windows runner, where they are ignored in the blocking checks and the nightly workflow's Windows job runs them (`cargo test -p xtask -- --ignored combine::tests::sys_`).
- **A clone kept with `--keep` reads the repository's objects in place** (`--shared`): a `git gc --prune` in the repository can take objects it needs. Look at it and remove it; do not keep it for long.

### The public API between two trees

A fix session is asked to list the public signatures it changed, for the step that comes after it, and wrote the list by hand. `cargo xtask api-diff [--against REF] [-p CRATE]… [--format text|markdown]` writes it (since the seventh tooling step): the public items added, removed and changed between a ref (`main` when not given; `origin/main` where there is no `main`, as in a checkout of a branch from the remote) and the working tree, by crate, each with its path and its signature before and after. `-p` is repeatable; without it every workspace crate that has a library is compared, those only one tree has included (the report says so).

```text
Public API, `main` (1f2e3d4c5b) against the working tree
cortex-base: 3 added, 1 removed, 1 changed
  + cortex_base::ResolvedPath::shown  fn shown(&self) -> String
  - cortex_base::ResolvedPath::display  fn display(&self) -> String
  ~ cortex_base::load
      was  fn load(path: &str) -> Config
      now  fn load(path: &str, strict: bool) -> Config
no public API changes: cortex-agent, cortex-config
```

- **How the API is read: rustdoc's JSON output** (`--output-format json`). It is exact: it has the re-exports, the items a macro or a derive makes, what a `cfg` leaves out, and every signature as the compiler understood it. The lighter way, reading the `pub` items with the lexer of `mutate`, was not taken because it misses exactly those (a re-export, a `pub(crate)` that is not public, an `impl` a derive writes, a macro's items) and would report them wrongly in both directions. The JSON needs `-Z unstable-options`, which the pinned stable toolchain accepts with `RUSTC_BOOTSTRAP=1`: no second toolchain to install, and the format is the pinned toolchain's own, where a nightly would write another. `cargo xtask fuzz` needs a nightly because the fuzzer does; this does not.
- **Only the format it was written against is read.** rustdoc's JSON has no stability promise: its field names move from one toolchain to the next. `api_diff/read.rs` reads **format 61**, the one toolchain 1.99.1 writes, and refuses any other number with both numbers named (`SUPPORTED_FORMATS`). **A toolchain bump that moves the number makes `api-diff` fail** until the new format has been looked at, the reader changed and the list extended: the ignored test `sys_the_real_rustdoc_…` of `xtask` runs the real rustdoc on two small crates and says at once (the nightly workflow runs it with the other `sys_the_real` tests). What the reader does not know within its format (a type, a bound or a predicate of a shape it has not seen) is written as the JSON itself, so a change in it still shows.
- **What is listed.** The walk goes from the crate root through public items only, and follows `pub use` (a glob too). An item that is reached by one path is an entry there, with its members: a struct's or union's fields, an enum's variants (each with its fields in its signature and its discriminant), a trait's items (a method with a default says `{ .. }`, a constant with one `= ..`), the methods of its inherent `impl`s (with the `impl`'s bounds when it has any), and `impl`s of traits for it, with the associated types they fix. An item reached by several paths is full at the first (where it is defined, else the shortest) and a `use` entry (`pub use <path>`) at each of the others, so a re-export that is added or removed shows. A struct says when it has private fields, `#[non_exhaustive]` and `#[repr(…)]` are part of the signature, and an `impl !Send` is listed where a type stops being `Send`. What rustdoc adds to every type (`Send`, `Sync`, `From<T> for T`) is left out. A private or `#[doc(hidden)]` item is not in rustdoc's JSON and not here.
- **What "changed" means:** a different kind of item, or a different signature: generics, bounds, arguments and return type, a struct's shape, a variant's fields, a trait's supertraits and items, an `impl`'s bounds. Not its documentation, not its body (a constant's value, a function's code), and not the name of an argument (it is shown, and a rename is no change: a caller does not see it).
- **The `impl`s of a type that was added in the same change are left out of the report** (and those of a type that was removed): a new type with its derives would be a dozen lines of `impl Clone for …` beside it. Its fields, variants and methods are listed.
- **The output is sorted by path and the same each run.** One line for an addition or a removal and three for a change, short enough to paste; `--format markdown` is a table for each crate, for a report. Progress goes to the standard error, the report to the standard output.
- **Nothing of the session's own is touched.** As `combine` does, the other tree is a clone under the build directory (`target/api-diff/base`) made with `git clone --shared`, which reads the repository and writes nothing to it: no branch, no ref, no worktree entry. It is checked out at the ref and reused by the next run, which moves it. A clone that is damaged is made again, never checked out in: git would look in the folders above it and find the session's own repository. The working tree is documented where it is, uncommitted changes and new files included. Each tree has a build directory of its own (`target/api-diff/head-target` and `base-target`), kept between runs, so that the next run documents only what changed; they are apart from the ordinary build, so that a build with `RUSTC_BOOTSTRAP=1` (which build scripts may read) never disturbs the ordinary one. One run at a time (a lock). A copy without a `.git`, as `rx` makes, is refused: `rx --git -- cargo xtask api-diff …` gives the copy one.
- **The API is that of the host system with the crate's default features** (and `cortex-sandbox`'s `backends` on Linux, as `test -p` turns it on): an item behind `cfg(windows)` is in the report of a Windows run only.
- **What it costs** (the desktop, a debug build of `xtask`, the tree with 22 crates; the first run builds each tree's third-party crates in its own build directory):

  | Run | Time |
  |---|---|
  | One crate (`cortex-base`), build directories empty | 10.5 s: 5.1 s to document each tree |
  | The same, nothing changed | 0.7 s |
  | The 19 crates that have a library, third-party crates built once before for one crate only | 21.8 s: 9.6 s and 9.5 s to document the two trees, the rest the clone, `cargo metadata` and reading 19 JSON files twice |
  | The same, nothing changed | 2.6 s: 0.8 s of cargo for each tree, the rest the reading |

  A laptop (8 threads) took 43 s for the first run on one crate, third-party crates included. A run is dominated by the first build of each tree's third-party crates in its own build directory, which is why they are kept; after it, a change in a crate costs what rustdoc takes to document that crate and those built on it. Under two minutes cold was the bar, and it is met by a wide margin, so the exact way was taken.

- **How it is tested:** `api_diff/read/tests.rs` reads a rustdoc JSON file recorded from the real rustdoc (`xtask/fixtures/api-diff/toy.json`, the crate in `toy.rs.txt` beside it, with what the reader does not use taken out) and holds the whole listing it gives (every kind of item and type, the re-exports of a private module, a glob, derives, a trait with defaults, `extern "C"` with a variadic argument), and JSON written for the purpose for the rules one at a time: the format that is refused, private items, what is not public, argument names, auto-trait impls and `impl !Send`, two methods of one name in two `impl`s, the path an item is given, and which type an `impl` belongs to. `api_diff/diff/tests.rs` holds the comparison and both outputs. No test runs a toolchain except one, `sys_the_real_rustdoc_reports_what_was_added_removed_and_changed`: a repository made for it with a crate at a commit and, in the working tree, a signature changed, a field, a default method and a derive added, a function removed and a crate that was not there. It documents two trees with the real rustdoc, so it is ignored in the blocking checks (0.3 s on the desktop once built, a few seconds from cold) and the nightly workflow runs it. Two tests start git and are ignored on Windows, as `combine`'s are (the ref's default and fallback; the clone that moves between commits and leaves the repository as it was).

### Where the five minutes go

Everything in this section was measured on GitHub-hosted runners on 2026-11-12, in step 2. Both runner types report 4 cores. Times are from the job and step timestamps the API reports, to the second, and from timers in the measurement scripts.

**Hosted runners vary.** The same clean build took 27, 29, 42 and 45 s on four Linux runners and 60, 75, 77 and 82 s on four Windows runners on the same afternoon. Read every number here as "about", and compare two settings only when they were measured in the same job on the same machine, which is how the comparisons below were made unless they say otherwise.

#### The skeleton, as merged in step 2

The workspace has 21 crates with no code to speak of, 22 test binaries and five small third-party crates. Wall time per OS is the slower of that OS's two jobs.

| Case | Linux | Windows |
|---|---|---|
| Cold cache: the pull request's own runs, which have no cache to read | 20 to 29 s | 37 to 39 s. Before cargo's and rustup's files were moved off `C:` (below): 47 to 59 s, and 74 s once |
| Warm cache: a scratch branch running the same jobs with cache writing on, second run | 20 s | 42 s, measured before that move |
| Documentation-only pull request | 16 s | 14 s |

All four cases are far inside 5 minutes, and cold and warm are the same within noise, because there is almost nothing to cache yet. The warm case can only be measured on the real workflow once the main branch has written its first caches, which happens when step 2 is merged; the first pull request after that is the check.

The job breakdown, for the last cold run of step 2's pull request:

| Phase | `lint-linux` | `test-linux` | `lint-windows` | `test-windows` |
|---|---|---|---|---|
| Start the job, check out, ask what changed | 2 s | 4 s | 9 s | 9 s |

#### After each later step

#### The planned third-party set

The skeleton cannot show what a cold cache will cost once the dependencies arrive, which is the risk this page was written around. So step 2 also built a throwaway program that depends on the whole third-party set planned for the first release (the async runtime, the HTTP and TLS stack, serde, the terminal library, the search libraries, the MCP SDK, the highlighter, the script engine, the test-kit libraries, and the Windows-only and Linux-only crates: 283 packages in its lockfile) on both runners. The program was on a scratch branch and is not in the repository. It uses each library enough to link it.

| Measurement | Linux | Windows |
|---|---|---|
| Fetch the sources (download and unpack) | 2 to 3 s | 26 to 37 s |
| Clean build, dependencies at `opt-level = 1` (the `dev` profile) | 129 s | 259 s |
| Clean build, dependencies at `opt-level = 0` (the `ci` profile) | 27 to 45 s | 60 to 82 s |
| Relink the one binary after touching its source | 0.4 to 0.5 s | 1.2 to 1.9 s |
| Build directory | 0.5 to 0.6 GB | 0.65 to 0.72 GB |
| The cache `rust-cache` stores for it | 209 MB | 220 MB |
| Restore that cache | 3 to 4 s | 26 s |
| Unpack the sources again after a restore (the cache holds the `.crate` files, not the unpacked trees) | 2 s | 18 s |
| Build after a restore | under 1 s | 5 s |

What follows from it:

- **Optimised dependencies do not fit a cold Windows run.** With the `dev` profile's `opt-level = 1`, Windows spends about 290 s fetching and building dependencies before it compiles a line of ours. Unoptimised, it spends about 110 s. That is why the test jobs build in a profile of their own, `ci`. The `dev` profile is unchanged, because at a desk the dependencies are built once and kept.
- **Line tables are nearly free.** In one job per OS, with dependencies unoptimised: no debug info anywhere, 29 to 30 s on Linux and 75 to 82 s on Windows; line tables for the top crate only, 29 s and 75 s; line tables for every crate, which is more than `ci` asks for, 32 s and 83 s. Relink times did not change. So `ci` keeps line tables for our own crates.
- **The faster linker does not pay on Windows.** With `rust-lld` in place of the default linker, in the same job: a clean build took 274 s against 259 s, and a relink 1.3 s against 1.5 to 1.7 s. For the skeleton's 22 test binaries, 2.9 s against 3.8 s. Linking is not where the time goes, so the default linker stays. (Mitigation 7 below is closed.)
- **The script engine builds on Windows.** QuickJS compiled with the MSVC toolchain on the hosted runner and ran a script. Step 28 still confirms it in the real crate.
- **A warm Windows run paid about 45 s before it built anything of ours:** 26 s to restore the cache and 18 s to unpack the sources. The second figure is what the next section cuts to 9 s.

#### Where cargo's files live on a Windows runner

A hosted Windows runner has two disks. The workspace is checked out on `D:`, and cargo's home directory, where crate sources are downloaded and unpacked, is on `C:` by default. Unpacking a few hundred crates is tens of thousands of small files, and that is slow on `C:`. Measured in one job, two rounds each, with the planned set (283 packages):

| Where `CARGO_HOME` is | Download and unpack | Unpack only (what a warm run does) | Set-up cost |
|---|---|---|---|
| `C:`, the default | 26 to 30 s | 23 to 27 s | none |
| `C:`, in a folder excluded from antivirus scanning | 24 to 25 s | 24 to 33 s | 0.1 s |
| The workspace's disk, `D:` | 10 s | 9 s | none |
| A Dev Drive (a ReFS volume in a virtual disk on `D:`, trusted) | 8 to 9 s | 7 to 8 s | 9 s to create, and 1.5 s to copy the checkout onto it |

- **The Windows jobs set `CARGO_HOME` and `RUSTUP_HOME` to a folder on the workspace's disk.** It costs nothing and saves 15 to 20 s on every Windows run that has dependencies to unpack, warm or cold.
- **A Dev Drive is not used.** The owner asked for it to be measured, with the workspace, `CARGO_HOME` and the build directory on it. In one job, alternating the default disks and the Dev Drive twice: a clean build of the planned set took 75 and 76 s on the default disks and 76 and 77 s on the Dev Drive; a relink 1.6 to 1.7 s on both; the skeleton's 22 test binaries 7.9 and 8.0 s against 8.0 and 9.2 s; restoring a cache archive 3.1 and 3.0 s against 2.7 and 3.0 s. Compiling and linking are not held back by the file system here. The one thing the Dev Drive speeds up is unpacking sources, and the plain `D:` disk gets all but about 2 s of that without the 10 s of set-up. Net, the Dev Drive is slower.
- Real-time antivirus scanning is already off on the hosted image (`RealTimeProtectionEnabled: False`), which is why excluding a folder changes nothing and why a Dev Drive's "performance mode" has little to give.

#### After a lockfile change: `rust-cache` alone, or with `sccache`

The owner asked whether a per-crate compile cache (`sccache` with the GitHub Actions cache as its store) would shorten the run after a lockfile change. The premise was that a lockfile change throws the dependency cache away. It does not: `rust-cache` restores the newest cache for the previous lockfile, and cargo rebuilds the crates that changed and the crates that depend on them. The measurement, with the planned set in the `ci` profile, each cell one job (so different machines; differences of a few seconds are noise):

| Run | Linux, `rust-cache` | Linux, with `sccache` | Windows, `rust-cache` | Windows, with `sccache` |
|---|---|---|---|---|
| Everything cold | 45 s | 61 s | 88 s | 88 s |
| One small crate added that nothing else depends on: first push | 1.8 s | 2.2 s | 18.2 s | 19.8 s |
| The same: second push | 1.8 s | 1.9 s | 18.0 s | 19.2 s |
| A patch bump of `bytes`, which 19 crates of the set are rebuilt for: first push | 14.9 s | 17.3 s | 39.4 s | 40.1 s |
| The same: second push | 11.2 s | 8.0 s | 36.3 s | 28.4 s |

The times are the build step, which on Windows includes about 18 s of unpacking sources on `C:` (these runs were made before `CARGO_HOME` was moved). "First push" is the first run of a pull request that changes the lockfile; it reads the main branch's cache and, like every pull request, cannot write it. "Second push" is a later run of the same pull request.

- **`sccache` is not used.** On the first push after a lockfile change it has nothing to offer: the crates that must be rebuilt have new inputs, so its cache has never seen them. It was 0.4 to 2.4 s slower there. It helps only from the second push of a pull request that bumps a crate much of the graph depends on, by about 3 s on Linux and 8 s on Windows.
- What it would cost: a third-party action in the blocking workflow, a network request per compiled crate, cache entries written from pull requests (against the rule that only the main branch writes caches), and a slower cold build on the Linux runner that measured it.
- The warm case was not slowed by it: with every dependency fresh, cargo starts no compiler and the wrapper is not called.

**The risk is still the cold-cache Windows run,** and it is now a rare one: a toolchain bump, or expired caches. The mitigations, in the order they are applied, with what step 2 found:

1. Keep the dependency tree small. This is why every dependency has a measured cost and an owner crate.
2. Only the main branch writes the cache, and a scheduled job on the main branch keeps it warm. A pull request that does not touch the lockfile never builds dependencies. **In place.**
3. A lockfile change restores the previous lockfile's cache and rebuilds only what changed. **In place** (it is how `rust-cache` works), and measured above.
4. Build dependencies unoptimised in CI. **In place:** the `ci` profile. It is the largest single saving found.

### Not blocking

`main` and `nightly` exist in their first form since step 3 of the [build plan](build-plan.md), with the checks that need no product code. Later steps add their tiers to them. `release` and `live` arrive with the steps that need them. The blocking workflow also runs on every push to the main branch and twice a week on a schedule: those runs are what write the caches and keep them from expiring.

| Workflow | When | What it runs now | What later steps add |
|---|---|---|---|
| `main` (`.github/workflows/main.yml`) | After each merge to the main branch, and by hand | `cargo xtask size --check` for Linux x86-64 and Windows x86-64: a build of the published profile (`dist`, with the build machine's folders taken out of its paths and the binary then read for any path under a home folder, since step 33's size fix: decision [0036](decisions/0036-the-shipped-binary-is-optimised-for-size.md)), the binary's size checked against its budget ([performance-budgets.md](performance-budgets.md)), and the number of crates in the build. | `release` | On a version tag | Not built yet. | Builds, checks and publishes binaries with checksums. |
| `live` | By hand | Not built yet. | Tier 5 and fixture recording. Uses a protected environment for secrets. |

- **The jobs call `cargo xtask`,** like the blocking ones, so the same commands run at a desk.
- **Fuzzing is two things.** The first is the nightly property run. Step 5 built the first decoder, the SSE parser, and fuzzes it with a property: the pieces of the format in any order, with bytes that are not text among them, cut at random, must never panic and must give the same events however they are cut. Pull requests run 400 such inputs and the nightly run 20,000. Step 14 added the same for the Anthropic decoder, from the pieces of real streams with some of them damaged. That is random testing: it does not follow coverage.
- **The second, since step 14, is coverage-guided fuzzing,** in the `fuzz` job of the nightly workflow.
  - **The targets** are a package of their own, `fuzz/`, outside the workspace, with its own lockfile: the fuzzer needs a nightly compiler and a C++ compiler for its runtime, and neither belongs in the blocking checks or in what ships. There is one target for the SSE parser and one for each protocol's decoder: `anthropic_decoder` and, since step 31, `openai_chat_decoder`, whose first input byte chooses the kind of server (reasoning under a named member, reasoning in tags inside the text, a model that is asked for a speed tier or one that is not). Since the fixes of the independent review of step 18, `extractors` runs every outline extractor of `cortex-index` on the input as a file, decoded as a pass decodes one: no input panics or passes a cap (entries, a name's, a head's or a doc's length).
  - **What a target checks** is written as an ordinary function (`fuzz/src/lib.rs`), which a test on the stable toolchain also calls. The first two bytes of an input decide where the rest is cut, so the fuzzer explores the cuts as well as the content. For both targets: no input panics, and the same bytes give the same result however they are cut. For the decoder also: a response ends at most once and nothing follows its end; a block ends only after it started; and every block the decoder stores is one JSON object, so that it can be sent back.
  - **The corpus** each run starts from is the recorded fixtures, each once whole and once in small pieces; the extractors' is their sample files (`crates/cortex-index/fixtures/outlines`), each once. Nothing the fuzzer finds is kept between runs yet.
  - **Running it.** `cargo xtask fuzz [--seconds N] [TARGET…]`, which needs a nightly toolchain and `cargo-fuzz`. An input that fails is kept under `fuzz/artifacts/`, and as an artifact of the nightly run, and `cargo +nightly fuzz run <target> <file>` runs it again.
  - **The nightly compiler is pinned to a date,** in `fuzz/rust-toolchain.toml` and nowhere else, so that a new nightly cannot break the job without a change here. `cargo xtask fuzz` and the workflow both run inside `fuzz/`, where that file decides the toolchain. **To move it forward:** change the date in that file to a recent nightly, start the nightly workflow by hand on the branch (`gh workflow run nightly.yml --ref <branch>`), and merge when its `fuzz` job passes. Do it when cargo-fuzz or the fuzzer's runtime is updated, or every few months: the sanitizer and the coverage instrumentation are part of the compiler, and an old nightly gets none of their fixes.
  - **The package's lockfile is its own,** and the nightly advisory check, which reads the workspace's lockfile, does not see it. What it adds to the workspace's packages is the fuzzer's runtime and the few crates that brings.
- **No build cache.** Nobody waits for these runs, and the blocking workflow's caches keep the repository's whole 10 GB.
- **One Windows job each.** Hosted Windows runners queue when a repository starts many of them ("What grows the time", above).

**A failure opens or updates an issue.** It does not block merging, and it is not ignored. Each workflow ends with a `report` job that runs only when another job failed, **in a run on the main branch** (scheduled, or dispatched there): a session's own run of the workflow on its branch reports nothing, so that it cannot add to the main branch's issue (since the third tooling step, whose dispatched nightly runs added two comments to #40). The nightly's `partial-landlock` job is not among the jobs it reports until the fixes to step 26 make a test of the protected-paths watch pass on Ubuntu 22.04 (the comment on the `report` job names it). It looks for an open issue titled "The `<workflow>` workflow failed", with the label `ci-failure`. If there is none it opens one; if there is one it adds a comment. Either way the text names the run, the jobs that did not succeed, the trigger and the commit. A person closes the issue when the cause is fixed, and the next failure opens a new one. The steps are in `.github/actions/report-failure`.

**Only the `report` job can write, and only issues.** Every workflow's token is read-only at the top level. A workflow that runs on pull requests can write nothing and uses no secret. In a workflow that does not, the job named `report` may have `issues: write`, and nothing else may have any write permission: the job that holds a token that can write runs no code from the build, and the jobs that build and run code hold a token that cannot write. `cargo xtask rules` checks all of it.

**Testing the report.** Both workflows take a `force_failure` input when started by hand, which makes the first job fail at once. Since the report is for runs on the main branch only, `gh workflow run nightly.yml --ref main -f force_failure=true` exercises the whole path without waiting for a real failure; on a branch the forced failure shows the job failing and reports nothing. Close the issue it opens. Step 3 did this for both workflows from a scratch branch, before the report was held to the main branch: each forced run opened its issue within seconds of failing, and a second failure of `nightly` was added to the open issue as a comment.

## Lints and formatting

- `rustfmt` with a small checked-in configuration.
- Clippy with warnings as errors, a workspace lint table, and three project-specific rules through `clippy.toml`:
  - blocking calls (`std::fs`, `std::process`, `std::thread::sleep`) are disallowed. The lists are on in every crate. Code that is meant to block, because it runs on the blocking pool or the whole crate is synchronous, opts out for a module or the crate with an `allow` that gives the reason;
  - `unwrap` and `expect` are disallowed outside tests, except where an attribute gives the invariant;
  - `println!` and `eprintln!` are disallowed outside `cortex-cli` and `xtask`, so nothing can write to standard output by accident.
- An `allow` or `expect` attribute must carry a `reason`. `todo!`, `unimplemented!`, `dbg!` and `std::process::exit` are warnings, and so errors in CI.
- `unsafe` is denied by default and allowed per module in `cortex-sandbox` and `cortex-term`, where the OS interfaces need it, and in one Windows-only module of `cortex-base`, `private::windows`, which creates files with an access list of their own and reads a file's reparse tag ([decision 0029](decisions/0029-owner-only-files-on-windows.md)). Every block has a safety comment. A new place needs a decision record.
- Public items are documented (`missing_docs`).
- Clippy runs on Linux and on Windows, so that code compiled only for Windows is linted.

**The repo rules** are the checks no off-the-shelf tool does. `cargo xtask rules` runs them, and a test runs them again on both OSes:

- no file contains an absolute home-directory path (every file is scanned, binary files included);
- the crate dependency rules of [architecture/01-workspace.md](architecture/01-workspace.md), read from `cargo metadata`, and the manifest conventions (the `cortex-` prefix, `publish = false`, shared lints, no doc tests, one integration-test binary);
- `cortex-protocol` depends on serde and serde_json and nothing else, and on schemars only as an optional dependency behind its `schema` feature;
- `docs/dependencies.md` agrees with the manifests;
- workflow actions are pinned by commit hash; every workflow's token is read-only; a workflow that runs on pull requests uses no secret and can write nothing; and the only write permission anywhere is `issues: write` on the `report` job of a workflow that does not run on pull requests ("Not blocking", above); and no `run:` script has a workflow input or a part of the event (`${{ inputs.… }}`, `${{ github.event.… }}`, `${{ github.head_ref }}`) pasted into its text: those reach a script through `env:`; and no unquoted value holds `: ` or ends with `:`, which YAML reads as a mapping, so that GitHub reads the whole file as no workflow (the third tooling step's `run: … --ignored combine::` did that to the nightly workflow, and only its dispatch showed it);
- **a wrapped trait has no default bodies** (since the third tooling step): `Tool`, `Launcher`, `Policy` and, since the fourth, `ModelClient`, which tests wrap to check what a request builds to: the traits listed in `WRAPPED` (`xtask/src/rules/rust_source.rs`). Each is wrapped by a type that holds another implementation and forwards to it, and a method added later with a default body is silently not forwarded by a wrapper written before it: the default runs in its place. Step 26's wrapper of `Tool` did that with `Tool::preview`, which a parallel pull request added, and a clean rebase hid it. With no defaults, adding a method fails to build until every implementation writes it; the rule keeps a default from coming back. A trait that is not where the list says is an error, not a pass. A trait that gains a wrapper joins the list;
- **a program is not started by a bare name** outside tests (since the third tooling step): `Command::new("git")`, and the same through the project's own starters (`CommandLine::new`, `Shell::new`, `brief::run`, `Pty::spawn`), whatever follows the first argument. The name is a literal, borrowed or made into a `String`, an `OsStr` or a path (`"git".to_owned()`, `String::from("git")`, `OsStr::new("git")`), or a constant or a `let` of the same file that holds one. A name that comes from another module, or is built at run time, is not seen. A bare name is looked for in the `PATH`'s relative entries, and on Windows in the working directory, so a file of that name in the workspace would run in its place (step 13a's review, R4). The harness finds a program with `cortex_base::program` and starts it by the path found. Code under `#[cfg(test)]` (a module, or a module in a file of its own) and `#[test]`, files under a `tests` folder, `xtask` (the developer's own tools, as cargo finds them) and the test kit are not checked. One call is allowed with a comment on its line or the line before: `// program by name: <the reason>`. When the rule was written, nothing on the main branch broke it. Only the files whose text calls a starter are lexed for it, and only those that may declare a test module in a file of its own for that: the rules step took 0.6 s on the desktop with the two rules of the Rust source and without them;
- a crate's `test-hooks` feature (`cortex-tools`, `cortex-stats`, and since the seventh tooling step `cortex-base`, whose points are in [A point the library stops at](#a-point-the-library-stops-at)) is turned on by a dev-dependency and in no other way: not by a normal or build dependency, not by `default` or another feature of the crate that has it, and not by a feature of another crate that passes it on ("A seeded order of events", above). The test kit turns on `cortex-base`'s, and a crate's dev-dependency on itself, which asks for its own feature for its own tests, is no edge of the crate table;
- **every link inside the repository leads somewhere:** a relative link in a Markdown file names a file or a directory that is there; a link with a `#fragment` names a heading the page has, by the name GitHub gives it (the text in lower case, without punctuation, a `-` for each space, and `-1`, `-2` for a second and third heading of the same name); and a `docs/….md` path written in prose, in configuration or in a comment of the code names a file that is there. In Rust source only what follows `//` on a line is read, on a line of its own or after code: a string there is as likely to be a test's made-up file. Links to other sites are not followed;
- **the step records and the open items are where the others expect them** ([steps/README.md](steps/README.md), [outstanding/README.md](outstanding/README.md)): a folder of `docs/steps/` is a step's number in two digits with its letter, or a name in lower-case words joined by hyphens; it holds `answered.md` and `ci.md` and nothing else; each begins with the heading its kind has, naming the step the folder is for; and a file of `docs/outstanding/` is named in hyphenated words and holds the table's header and one row; and **the index in `docs/outstanding/README.md` lists every open item exactly once** (since the fifth tooling step), as a link to its file under the crate or area it is about, so that a review can see whether a finding is known without reading every file.

**The rules read the files git tracks** (since the third tooling step): what a pull request holds. A scratch folder in a worktree, with a build of its own full of absolute paths, once failed them with 3,963 findings. A new file is read once it is added, and a link may lead to one before. In a copy of the tree with no `.git` (the one `rx` builds in), every file is read except those under `.git` and any `target` directory.

`cargo xtask links` runs the last two alone. They read text files and ask cargo nothing, so they answer at once: under a tenth of a second for the 137 pages there are.

`cargo xtask check` also has a `generated` step: the protocol's JSON Schema and TypeScript declarations in `docs/protocol/` must be what the types in `cortex-protocol` generate. A test makes the same comparison on both OSes. `cargo xtask schema` regenerates them.

**The configuration's generated files** are `docs/configuration/schema.json` and `docs/configuration/reference.md`, generated from the settings declared in `cortex-config`. They are checked by a test in that crate, on both OSes, and not by the `generated` step: `xtask` is built before every CI job does anything, and checking them there would make it build the configuration crate and its TOML parser each time. `cargo xtask gen` writes them, by running that test in its writing mode.

### Rebuilding the generated files

`cargo xtask regen` (since the sixth tooling step) is for after a rebase that met another branch's changes to a generated file, where a merge of the text is not the file the merged sources produce (step 18 settled such conflicts by hand in the snapshots, the screens and the schema). Settle the sources, take either side of each generated file, run it. One step for each generator, all of them run even when one fails, each timed:

| Step | Writes | By |
|---|---|---|
| `protocol` | `docs/protocol/` | `schema`'s writer |
| `configuration` | `docs/configuration/` | the test of `cortex-config` that checks them, with `CORTEX_UPDATE_GENERATED=1` |
| `screens` | the reference screens and their text copies in `docs/architecture/tui-look/` | `tui-screens --write` (before the snapshots: one of their tests holds the text copies to the screens, and since the sixth tooling step `--write` also puts a text copy right that is out of step with its screen alone, as a merge that took one side of each file leaves it) |
| `snapshots` | the snapshots of `cortex-tui`, `cortex-llm`, `cortex-index` and `cortex-config`, and the requests of the hand-written provider fixtures | the tiers 1 and 2 tests of those four crates, with `CORTEX_UPDATE_SNAPSHOTS=1` |

It then lists the files that differ from `HEAD` in those places (a change to a snapshot is a change in what users see: it is read like code), and runs `links`, which writes nothing and checks what `regen` cannot write. **Left out, with `regen --list` saying so:** the tables of `docs/steps/<step>/ci.md`, which are a CI run's measurements (`ci-times RUN --write`, which needs `gh` and a run id); the index of `docs/outstanding/README.md`, whose lines are prose that an item's file does not hold (the area, the sentence, the owner), so there is nothing to generate it from, and `links` fails on an item left out or listed twice; the toolbox and the recorded provider fixtures, which are a paid API's answers (`record`); the golden transcript, which is not edited to make a test pass; and `Cargo.lock` and the break lists. **A test holds the lists to the code:** every `CORTEX_UPDATE_*` variable found in the code is run by one step or named as left to another command, and every place a step writes is a place the repository has, so a writing mode added later cannot be forgotten. On a tree that is right it changes nothing: measured at the desk, 46 s, of which the snapshots are 24 s, the screens 15 s and the configuration 6 s.

### The copy of `xtask` that still runs

In the middle of a change to `xtask` itself `cargo xtask replace` cannot run, because cargo builds `xtask` first and the build fails: the command that would edit the code that does not build is the one that cannot be used. Every `xtask` command that ends well keeps the binary that ran it in `target/xtask-last-good/xtask` (`xtask.exe`), beside `xtask.stamp`: the binary's size and modification time (which say whether it is the one already kept, so a run that changes nothing copies nothing), when it was copied, and the commit with a note when `xtask/` held changes that were not committed. A runner keeps none (`GITHUB_ACTIONS` is set): nobody uses its build again.

- **`./x replace …` and `./x links` build first, and run the copy when the build fails.** A cargo that is not there is not a failed build: that is reported as it is. On Windows `cargo xtask` cannot fall back; run `target\xtask-last-good\xtask.exe replace …`.
- **The copy says it is old,** on standard error, on every run: when it was built, how long ago, from which commit, and which files of `xtask/` are newer than it (or that none are, and the build is broken for another reason).
- **It offers `replace` and `links` only.** Every other command is a check or a run whose answer depends on the code as it is, and a copy would answer for the code as it was.
- **It never overwrites the copy in place:** a new one is written beside it and renamed over it, and where the system will not replace a program that is running (Windows) the old one is moved aside first, which it does allow. The copy does not refresh itself.

## Dependency hygiene

- **Licences.** `cargo deny` allows: MIT, Apache-2.0 (with or without the LLVM exception), BSD-2-Clause, BSD-3-Clause, ISC, Zlib, 0BSD, BSL-1.0, CC0-1.0, Unlicense, Unicode-3.0, Unicode-DFS-2016, and CDLA-Permissive-2.0 (the certificate data). Everything else fails the check. The planned dependency set was checked against this list when these docs were written: all of it passes. The one copyleft licence seen anywhere in the candidates (MPL-2.0, through one of the scripting engines that was not chosen) is not in the planned set.
- **Sources.** crates.io only. No git dependencies.
- **Bans.** OpenSSL bindings, native-TLS, and anything that needs CMake or NASM. Duplicate versions of the same crate are warnings that the weekly update pull request is expected to clear.
- **Advisories.** Checked nightly and on every lockfile change. A new advisory against an unchanged lockfile must not block unrelated pull requests, so it is not in the blocking set.
- **Unused dependencies.** Checked nightly, with cargo-machete. It reads the sources and needs no build, so it is a heuristic: a dependency used only in a way it cannot see is declared in the manifest, under `[package.metadata.cargo-machete]`, with the reason. **For now it looks at third-party crates only.** The skeleton declares the edges between workspace crates before the code that uses them exists, so the workspace's own crates are on an ignore list in the root `Cargo.toml`. A name comes off the list when the crates that depend on it have code, and the list goes once the first release's crates are built.
- **The dependency list.** `docs/dependencies.md` names every direct dependency, its owner crate, its purpose and its measured cost. A tier 0 check fails when it and the manifests disagree.
- **Crate count.** The number of crates in a release build is recorded on the main branch by the `main` workflow (every crate cargo compiles for the binary, ours included, with build dependencies and without development ones). An increase of more than five in one change needs a line in the pull request saying why.
- **Updates.** One grouped pull request a week.
- **The lockfile is committed.**

## Local development loop

The same budgets apply at a desk.

| Action | Budget | How | Measured for the skeleton, step 2 |
|---|---|---|---|
| `cargo check` after an edit in a leaf crate | Under 2 s | Small crates; heavy dependencies in leaf crates. | 0.04 s |
| Rebuild and relink the binary after an edit | Under 5 s | A tiny binary crate. Measured floor for relinking the full dependency set: 0.4 s on the desktop, 0.5 s on a Linux runner, 1.2 to 1.9 s on a Windows runner. | 0.1 s |
| No-op build | Under 0.5 s | | 0.03 s |
| Tiers 1 and 2 | Under 30 s | `cargo xtask test --profile fast`. | 0.2 s |
| The static checks | | `cargo xtask check`. | 0.3 s |
| Everything that blocks a pull request | Under 3 min | `cargo xtask ci` runs exactly what CI runs. | 0.7 s warm; 3.6 s from an empty build directory on 4 cores |

The measurements are from the desktop the earlier spikes used, with warm build directories unless it says otherwise. The crates are empty, so these are floors: what the tooling itself costs before there is any code.

The commands, all through `cargo xtask` (or `./x`):

| Command | Runs |
|---|---|
| `check` | The static checks: `fmt`, `rules`, `breaks`, `generated`, `clippy`, `deny`. All of them run even when one fails, and the time of each is printed. |
| `test` | All tests. Arguments go to nextest: `--profile fast` for tiers 1 and 2, `-p cortex-agent` for one crate, and then only that crate is built and run. `--dependents -p CRATE` adds every workspace crate whose tests can see a change to it: built on it through normal and build dependencies, to any depth, or using such a crate as a dev-dependency (a dev-dependency is not passed on). Run it after a change of behaviour. |
| `ci` | What the blocking jobs run: `check`, then the tests in the `ci` profiles, then the tier budgets. |
| `ci --tiers` | The tests as CI builds them, and each tier's time and slowest tests ("A CI run's test times"); `--like-runner` estimates what a hosted runner would say ("What a runner would say, from a desk"). |
| `ci --tiers --compare` | Two runs' tiers side by side ("A CI run's test times"). |
| `ci-times` | A run's job and tier tables, for a step's `ci.md`, written into it with `--write`; `--ab` for a `try` A/B run's, and the pull request's CI section. |
| `corpus` | The pinned corpus of real code that `perf_` tests measure: `fetch` it, `check` or print its `path`, `pin` a new one ("A tree of real code to measure"). |
| `try` | What the `try` workflow runs ("A run on the runners without a pull request", "Running an experiment on the runners"). |
| `ab` | Two trees' tests run in turn on one machine and compared ("Two trees on one runner"). |
| `combine` | This branch on top of open pull requests, checked by `ci` in a clone ("This branch on top of others"). |
| `stress` | The tests of the crates named, many times over, each time under the next seed, optionally squeezed onto a few cores beside busy loops ("Running the tests many times over"). |
| `mutate` | The breaks of `mutations/*.breaks`, on copies of the tree, two or `--jobs N` at a time ("Breaking the code on purpose"). |
| `replace` | An edit of Rust code found by its tokens, or with `--text` of any file by its exact text; `--script FILE` makes many edits across many files, all of them or none ([CONTRIBUTING.md](../CONTRIBUTING.md), "Editing from a script"). When `xtask` does not build, `./x replace` and `./x links` run the last binary that ran a command to its end, kept in `target/xtask-last-good/` ("The copy of `xtask` that still runs", below). |
| `scratch-test` | One throwaway test file run against a crate's integration tests, in a copy of the tree; in a cargo profile of its own and with its ignored tests, for a measurement ("A throwaway test"). |
| `api-diff` | The public items added, removed and changed between a ref and the working tree, with their signatures ("The public API between two trees"). |
| `owner-guard` | The owner guard: CI's form, `--pre-push` for the git hook, `--unpushed` by hand ("The owner guard"). |
| `decide` | The permission engine's decision on a command line ("Asking the permission engine"). |
| `links` | The part of `rules` that is about the docs: links inside the repository, and where the step records are. |
| `schema` | Regenerates the protocol's JSON Schema and TypeScript declarations in `docs/protocol/`. `schema --check` only compares. |
| `gen` | Regenerates every generated file: what `schema` writes, and the configuration schema and reference in `docs/configuration/`. |
| `regen` | Rebuilds every generated file the tree can rebuild, with no network and no key: what `gen` writes, the reference screens and every snapshot; then lists what differs from `HEAD` and runs `links` ("Rebuilding the generated files", above). `--list` says what it covers and what it leaves out. |
| `size`, `unused`, `advisories` | What the non-blocking workflows run: the `dist` build with its size and crate count (`--check` fails over the budget, `--target` names the target), cargo-machete, and `cargo deny check advisories`. |
