# Security notes

What can go wrong when a model drives tools on a developer's machine, and what Cineris does about each threat. The mechanisms are specified in [architecture/06-permissions-and-sandbox.md](architecture/06-permissions-and-sandbox.md); this page is the threat-by-threat view.

## Position

- The model is not trusted. Its output is treated like input from the network: it may be wrong, and it may be steered by text an attacker placed where the model would read it.
- The user is trusted. So is the user-level configuration.
- A repository is not trusted until the user says so, and then only for the specific definitions they saw.
- **Only the OS sandbox is a boundary.** Permission rules and approval prompts reduce risk and catch mistakes. They do not stop a determined attack, and the docs and the UI never suggest they do.
- Limits are stated where they exist. A weaker platform (Windows in the first release) shows its state in the hint row and falls back to asking.

## 1. Model-driven shell commands

**Threat.** The model runs a command that destroys data, changes the system, installs something, or sends data out. It may do so by mistake or because injected text told it to.

| Mitigation | Covers | Limits |
|---|---|---|
| Sandbox for every shell command where enforcing (Linux, Landlock 3 or newer, built in step 26): writes only inside the workspace, a private temporary directory and `sandbox.write`; no socket that reaches beyond the command's own processes, loopback and Unix sockets included (so no D-Bus, SSH agent or Docker socket), and with the network on only the internet's sockets and netlink's route one; no `io_uring`, no new user namespace, no keyrings; no leaving the command's session, so nothing it starts outlives it ([decision 0032](decisions/0032-what-the-linux-sandbox-needs.md)). A failure to apply it fails the call. A write root that holds the harness's own files or its program is not confined, and says so. | Damage outside the workspace. Data leaving the machine. A way out through a local daemon. | Reads are unrestricted by default, so secrets can be read (but not sent while the network is off); what a command prints reaches the model. Not available on Windows in the first release. On Landlock 3 to 5 a command can signal the user's other processes, and the status says so. A program that ignores `TMPDIR` and writes `/tmp` fails. |
| Protected paths inside the workspace (git's hooks and configuration, `.cineris/`, shell start-up files, CI configuration, registry and build settings, and the same names at any depth in the workspace) are looked at before and after each sandboxed command that may write (step 26). A change is named in the result, stops the turn at that command (nothing the model wrote after it runs, and the model is not asked again: the turn ends `denied`, since the owner's decision of 2026-11-21), and is kept in the round's checkpoint, so undoing the turn puts it back. | Planting code that runs later outside the sandbox, by a route the command analysis cannot see (`python3 fix.py`, a link made by another program, a pattern misread). | Detection, not prevention, with the default Linux backend. The look is bounded (20,000 directories, a quarter of a second); past it the result warns and a change further down is not seen. A file over 256 KiB, a link, a special file or a change of mode is found and must be put back by hand; undo never writes through a link. Not looked at: a command the user let leave the sandbox. Not on the list: files that git's configuration names in the workspace (`core.hooksPath`), which are left open. Each look costs about 24 ms in a repository of 3,000 directories. |
| Approval before any command leaves the sandbox, and before every unlisted command where there is no sandbox. The prompt shows the full command and directory with control characters made visible. Leaving the sandbox (`sandbox: false`) is asked about at every level but `unrestricted`, each time: only "allow once" and "deny" are offered, so no answer outlives the call (step 26). | Unintended escalation. A model that learns one approval and reuses it. | People approve without reading. |
| **The project's checks run only in a project the user trusts, and only commands the user wrote or accepted** (step 19, [architecture/15-efficiency.md](architecture/15-efficiency.md), "Automatic verification"). A check is the user's own `verify.commands` (which a project's file may not set) or a test or check command of the profile that the user accepted, or wrote; never one that became active by observation alone, never a shared entry the user has not accepted at its present hash. Each is decided by the engine just before it runs, and a `deny` or a stop wins; an entry of the profile runs only where the engine allows it unasked, the user's own line where the engine allows it or asks by no `ask` rule of the managed configuration (since the owner's decision of 2026-11-16: an administrator's `ask` binds the user's check as a managed `deny` does), and a check never asks. It runs through the session's own shell: the same sandbox, environment and looks at protected paths as the model's commands, and a check that changes a protected path stops the turn. Nothing runs at `read-only`. | A cloned repository, or a model that wrote a file, cannot choose a command that runs unasked at the end of every turn: its shared profile's entries are proposals, its configuration's `verify.commands` is ignored, and nothing runs before the user trusts it. | **A trade-off the owner decided on 2026-11-16, as built** (step 19): where nothing confines commands (Windows, a kernel without Landlock, `sandbox.enabled = false`, `unrestricted`), the user's own `verify.commands` line runs unconfined where the engine would ask, in a project the user trusts: the user listed it, and trusted the repository whose code it runs. The user is told once a session that the checks run outside any sandbox. Requiring the sandbox as well would make checks on Windows need an allow rule. |
| The command that runs is the command that was shown. It reaches the shell as it was written, by each shell's own rules, and one that cannot (a NUL character, a line break for `cmd.exe`, a command too long to pass) is refused before anyone is asked ([architecture/05-tools.md](architecture/05-tools.md), "`shell`"). | A command whose text is cut, or split into a second command, on its way to the shell. | What the shell then makes of the text is the shell's. |
| Command analysis that fails closed: anything it cannot model is "ask", never "allow". Read-only status only for commands with fully enumerated safe flags. Built in step 12 as allow-list tokenizers, compared with real bash, dash and PowerShell on generated lines ([decision 0031](decisions/0031-command-analysis-by-allow-list.md)). | Allow-rules being used to smuggle a different command. A command made to look read-only. A quoted text that Windows PowerShell, or `cmd.exe` behind a `.cmd` program, passes on as other words than the parser read: refused, and a test on the Windows runner compares what a program receives with what the analysis gave. | Convenience layer. Not a boundary. `cmd.exe` and shells the analysis does not know are not analysed: every command of theirs asks. A `deny` on the raw line of a command the analysis does not model matches through quotes, escapes and line breaks after them, and can still be dodged by a name the line makes as it runs (`$(echo git) push`) or a pattern the shell expands to the program (`/usr/bin/gi? push`); at `autonomous` and `unrestricted` such a line runs. zsh's `EXTENDED_GLOB`, if a `.zshenv` turns it on, makes a `~` inside a word (`HEAD~1`) a pattern the analysis takes as text. |
| What a command names is checked as a read. A command on the read-only table that names a file outside the workspace, a file that looks like a secret or a path a rule protects is asked about; so is any other analysed command that names a path a rule holds back, an option's attached value included (`cp -t.git/hooks`), and a pattern the shell expands, judged by what it matches in the directory as it is, through links, or by its text where the line may have made names the listing cannot see (`cp evil .gi?/hooks/pre-commit`, `rm *.lock` under `deny write **/*.lock`). A line the analysis does not model has its words checked the same way. One that names one of the harness's own files is refused. Every option the table reads as taking a value was checked against the real program, so that no option hides behind it (`git log --pretty --output=f`), and a `git` line with `--out` in a word is never on the table. | The read-only table as a way round the read rules: `cat ~/.ssh/id_rsa`. | Only what the command line names. A program can read whatever it likes once it runs; where the sandbox enforces, reads are still unrestricted by default. A directory can change between the listing of a pattern and the run. The directory above a protected path, and a link that leads nowhere yet, are not protected. |
| No search that reads the content of a whole tree is on the read-only table: not `grep -r`, not `rg` (what it leaves out, the workspace can change: a `.ignore` with `!.env`, or `rg -t sh`, whose type names `.env`), and not `git grep --untracked`, `git grep --no-index`, `git diff --no-index`, or `git diff a b`, which outside a repository is `--no-index`. The `search` tool makes the search with every file put to the read rules. The `git` commands that print what tracked files hold are asked about where a `deny` or `ask` rule on reading can match something in the repository. | `grep -r KEY .` or `rg -t sh KEY` printing every `.env` in the workspace unasked. A search that reads a file a rule protects without naming it. | **Tracked content** that `git diff`, `git show`, `git log -p` and `git grep` print, a file that looks like a secret included, is read unasked. A rule on reading closes it (`deny read **/*.pem`): the command is then asked about. Through the shell, `rg` and `grep -r` are ordinary commands: asked about at `supervised`, run at `autonomous`, where the sandbox confines them and reads are unrestricted by default. Commands that print names (`ls -R`, `find`) show the names of protected files. |
| **Sensitive paths go to the user by every route,** at every level below `unrestricted`: git's hooks and configuration (anything in a `.git` directory, at any depth), `.cineris/`, shell start-up files, CI configuration, registry and build settings (cargo's, npm's and yarn's at any depth, since they are read from the directory a build starts in and upward), files that look like secrets, and `sandbox.protect`. The routes are the `write` and `edit` tools, a redirection, a command that names the path (`cp x .git/hooks/pre-commit`), and `git config`. An allow rule that names the path lifts the question; a project's allow only after trust. At `read-only` the write is refused. | Planting code that runs later, by a route the level would otherwise let run unasked: at `autonomous` a command runs without a question, and one that names a sensitive path still asks. | A program that writes one without the command line naming it (`python3 fix.py`): asked about as a command at `supervised`, and at `autonomous` held only by the sandbox (the row above, which detects). At `unrestricted` nothing is asked; the user's `deny` and `ask` rules and the protection of the harness's own files still hold there. |
| The `git` forms on the read-only table (`git status`, `git diff`, …) are there only in a trusted project, and nothing writes git's configuration unasked (the row above). | A model that writes `core.fsmonitor`, a pager, `diff.external` or a filter driver into a repository's configuration, in the workspace's repository or a nested one, and then runs `git status` unasked to run it. | The forms on the table are as safe as `.git/config` is: a program that runs unasked at `autonomous` and writes it without naming it is held only by the sandbox. From step 13 every shell command runs with the file-system monitor turned off in its environment. |
| A `cd` in a command line is followed only where its effect is certain: not after `\|\|`, not in a pipeline, only when everything after it is joined by `&&`, and only when its target says where it starts (`./`, `../`, `/`, `~`, past `--` and `-L`), so that no `CDPATH` can send it elsewhere. `..` is taken logically, as the shells take it. After a `cd` that is not followed, what a part could reach from anywhere is still checked: protected paths, secrets, `git config`. A command run after a followed `cd` is judged where it runs. A redirection on a `cd` is a write like any other. | `true \|\| cd sub && cat ../../x`: the analysis taking a file outside the workspace for one inside it, because it followed a `cd` the shell never ran. `cd link/../.. && …` through a link in the workspace, which the file system would take one way and the shell the other. `cd sub && git config …` with `sub` sent elsewhere by a `cdpath` in `.zshenv`. | After a `cd` that is not followed, the level decides the line: at `autonomous` it runs, confined by the sandbox. |
| The harness's own files are closed to every tool at every level, by protection no rule can lift: the configuration directory (credentials), the state directory (trust, stored approvals) and other projects' session logs. A redirection into one is refused. | A model that reads the provider key from its file, or grants itself trust or an approval by writing the file that records it. | A command that reaches them without naming them. With the sandbox enforcing, the state directory is outside the writable roots. |
| Process-tree control: process groups and Job Objects, staged kill, and clean-up when the call ends, when the harness exits and when it crashes. On Linux a guard process kills what a dead harness left ([decision 0030](decisions/0030-process-tree-control-in-cineris-sandbox.md)). A command's whole tree is killed when its call ends: nothing is left running in the background. | Runaway and orphaned processes. | A process that leaves the group on Linux can outlive it: one that starts a session of its own is not signalled. The result says so when such a process still holds the command's output. Nothing leaves a Job Object on Windows. |
| On Windows every command is given `NoDefaultCurrentDirectoryInExePath`, so `cmd.exe`, and every `cmd.exe` a command starts, looks for a program only in `PATH` ([architecture/05-tools.md](architecture/05-tools.md), "`shell`"). | A workspace file named like a command (`git.bat`) running in its place: `cmd.exe` looks in the directory a command runs in before `PATH`. | A file named by its path (`.\build.cmd`) runs, as it is meant to. A program that does its own search for what it starts may still look in that directory: the variable is what `cmd.exe` reads, and another program's search is its own. |
| Timeouts, output bounds, and the loop guards (request limit, repetition guard, cost limit). | Runaway loops and resource exhaustion. | |
| Credentials are removed from the environment given to commands: the key variable of every provider the harness knows or is configured with, and any variable a provider's header reads. A variable that becomes a key at a reload is withheld from the next command; one that stops being a key stays withheld for the rest of the session ([architecture/05-tools.md](architecture/05-tools.md), "`shell`", "Environment"). | A command reading the provider key from its environment. | The user's other secrets in the environment are passed through unless listed (`shell.env_remove`). Every program the harness starts for itself is kept from the same keys: its git, and the shell asked its version (section 12). Where nothing confines commands this is defence in depth, not a boundary: a command running as the user can read the harness's own environment (`/proc/<pid>/environ` on Linux); inside the sandbox it cannot. |
| A command's `PATH` names only absolute directories. On Unix it is never empty and never missing: with no absolute entry left, the command is given `PATH=/usr/bin:/bin`, the system's own directories, and the model is told so (since the shell environment's fixes). | A file the model wrote in the workspace, named like a command (`ls`), running in place of that command, which the engine had passed as `ls`: an empty or relative entry, an empty `PATH`, and a shell's own default (upstream bash's ends with `.`) all look in the directory the command runs in. | An absolute entry inside the workspace (an activated `.venv/bin`) is kept on purpose: commands find the project's tools there. The shell itself and the harness's git are never taken from one (section 12). bash's `source name` and `. name` read `./name` when the `PATH` has none; the command analysis never passes either unasked. |
| File tools checkpoint before writing, with the bytes they read, and do not change a file whose earlier content cannot be kept: one over 16 MiB, or when the store fails. They never write text that was read lossily: a file that is not UTF-8 is refused by both `write` and `edit`. A file the model has not read in the session, or that changed since, is not changed (the staleness guard). | Recovering from a bad edit. A model overwriting work it has not seen. | Shell-made changes are not checkpointed. |

**Residual risk.** Inside the workspace, a sandboxed command can delete or corrupt anything. Version control is the recovery path. On Windows in the first release, an approved command has the user's full rights.

## 2. Prompt injection through files and web content

**Threat.** Text the model reads (a source file, a README, a tool result, a web page, an MCP tool description, an instruction file in a cloned repository) contains instructions. The model follows them: it runs commands, edits files, or sends data out.

No harness can make a model immune to this. The design limits what a successful injection can do.

| Mitigation | Effect |
|---|---|
| The sandbox and approvals above. | An injected instruction to run something harmful meets the same wall as any other command. With the network off, it cannot send data anywhere. |
| **No silent path from untrusted text to the network.** Network access from tools is "ask" by default. Fetching a URL (when that tool exists) is checked per host. | The usual injection goal, sending secrets or code to an attacker, needs a visible approval. |
| Tool results are data. They are delimited in the request as tool output through the provider's tool-result structure, never placed in the system prompt or presented as a user message. | The model can tell where text came from. This helps and is not a guarantee. |
| Third-party text is labelled: MCP tool descriptions and results, extension-provided content and fetched pages carry their source. | The same. |
| **The repository's shared profile is proposals** (since step 17). Every entry of `.cineris/profile.toml` is a proposal to each user until that user accepts it, and the acceptance is of what the entry said: a changed entry is a proposal again. The file cannot give its own entries a status, a date or an acceptance, and is read only as a regular file in a `.cineris` that is a directory of the workspace. Every piece of an entry is escaped where the profile is rendered into the system prompt, so an entry is one list line. | A cloned repository, or a model that wrote the file, cannot put text into the system prompt, a command into verification, or a command onto the safe list. An accepted command still waits for the project's trust. A user who accepts an entry without reading it has accepted it. |
| **An observed command reaches the prompt as plain words, and grants nothing** (since step 17). The command observer is the one path by which text reaches the system prompt with no person reviewing it: a command the model ran twice with success becomes an active entry. So a line is observed only when it is made of letters, digits and `_ . / : = @ % + , -`, at most 160 characters, and a table classes it as a build, a test run or a check; the directory it ran in, which is shown beside it and which a model can name as it likes, is held to the same characters; both are rendered in a code span, escaped. Becoming active is not being accepted: the command still asks before it runs, and is not offered to verification, until the user accepts it. A line that holds what looks like a credential is not observed. | A model, or text that steers it, cannot write a sentence into the system prompt by running a command twice, and cannot put a command on the safe list at all. **What is left:** the words of an observed line are the model's. A model that can make a line succeed twice (by writing a script or a `package.json`) can have up to 160 characters of its own choosing, joined by `-`, `.`, `,` or `:`, listed under "Commands" in every later session of the project until the entry expires (90 days, renewed while the command goes on succeeding). It reads as a command in a code span, not as a sentence of the prompt; the user is told the line in full when it becomes active, with the command that takes it out; and `project.learn = false` turns the observer off. |
| Instruction files cannot grant anything. A project's permission rules, hooks, extensions and MCP servers need trust. The engine sets a project's `allow` rules aside itself when the project is not trusted, whatever the configuration loader passed on; a project's `deny` and `ask` rules apply at once. | A cloned repository cannot configure its way to running code. An instruction file can still mislead the model, within the sandbox. |
| **Instruction-file text sent as a notice carries a user message's authority** (a changed file, or a file under a directory a tool touched; [decision 0034](decisions/0034-notices-in-the-users-role.md)). That is the same as the system prompt's project section, which holds the same files at the start of an epoch: both are text the model reads, and neither grants anything. Every notice begins by saying it is the harness's, not the user's. | A file a command changed mid-session reaches the model no more strongly than it would at the next epoch. |
| **An instruction file is read as the agent would read it** (since step 15): a link is followed only where it stays inside the workspace, and a file the permission engine would not let the agent read unasked (a rule denies it, or it looks like a secret) is not read. The user's own file in the configuration directory is read as it is, a link there followed to its file. A workspace file that links outside the workspace is not read, and the user is told which (since the review of step 15). | A repository cannot ship a `CLAUDE.md` that links to a private key and have the key sent to the provider with every request. |
| **A skill reaches the model as one line** (since step 28): a project's skills need no trust, as its instruction files need none, and each one's name and description reach section 6 of the system prompt one line each, a name cut to 64 bytes and a description to 300, with every control and format character taken out (the bidirectional controls, the zero-width characters), and its path escaped where it acts unseen; the index is 8 KiB at most and lists 100 skills. A skill's folder reached through a link out of its root, or a project's root that leads out of the workspace, is left out. | A repository's skill can name itself and say what it is for, in a line; it cannot write the harness's words, hide text, or point the model at a file outside the workspace. What a skill's file then says is read as any file the model reads is. Asked whether a project's text for the model should wait for trust, the owner kept it as it is ([steps/28/answered.md](steps/28/answered.md), "The owner's answers"). |
| **A user's own skill folders may be read unasked, if the user chooses** (since step 28; `permissions.read_skill_folders`, the user's own setting, off by default, which a project cannot set): while it is on, each skill found in the home directory's roots, its folder apart from the workspace and not the home directory or above it, gives the session `allow read` on its folder, a session approval the user can revoke. A project's skills give none. | Reading a skill the user installed is not asked about, and the workspace's reads, its look for secrets included, are as they were. Off, nothing changes. On, **a file that looks like a secret inside the user's own skill folder** (a `.env` or `credentials.json` its scripts use) **is read without a question, found by searches, and sent to the model's provider**: the reason it is off unless the user turns it on ([06-permissions-and-sandbox.md](architecture/06-permissions-and-sandbox.md), "A user's own skill folder may be read unasked"). |
| **The repository map is a notice, and names only what the read gate lets through** (since step 18). It is made from the repository's own file names and definitions, which a repository can word as it likes, so it is sent as the harness's notice in the user's role ([decision 0034](decisions/0034-notices-in-the-users-role.md)), never inside the user's message and never in the system prompt. Only files the agent could read unasked are indexed (the permission engine's gate, the ignore rules `search` honours, no link followed), and the `outline` tool reads only inside the workspace, through the same gate for a directory. | A file named to read like an instruction reaches the model as text the harness quoted, not as the user's words, and a file a rule protects is never named. |
| **What a check printed reaches the model marked as the command's** (step 19). A failed check's output is sent in a notice in the user's role ([decision 0034](decisions/0034-notices-in-the-users-role.md)), the one place a command's output is not a tool result. So every line of it passes `cineris_base::visible` and begins with `| `, under a sentence that says it is the command's output, within a bound of 16 KiB. | A test that prints the harness's own notice lead-in, a heading or a fake instruction cannot begin a line of the notice: it reads as a line of output. It is still text the model reads. |
| The harness's own questions to git run nothing of the repository's that the user has not accepted, and nothing with the user's own rights once commands are confined. Git is asked what a command changed only in a trusted project, and then with the file-system monitor a repository's configuration can name turned off (`core.fsmonitor`), no hooks directory, no optional locks, and no lazy fetch. A project that is not trusted is looked at by modification times, without git: a filter named in a repository's configuration is a program git runs on `git status`, and nothing turns every filter off. And because a confined command may rewrite a trusted project's configuration mid-session, the harness runs its own git **inside the sandbox** (read-only, no network) while commands are confined, so a program the configuration names runs confined, as the command did (decision 0032). | A repository that arrives with a `.git` directory of its own (an archive, a copied folder) cannot have code run by the harness looking at it, and a confined command cannot plant a filter that the harness's git then runs with the user's rights. A git command the model runs is a shell command like any other, confined by the sandbox. In a trusted project the forms that only read (`git status`, `git diff`, …) run unasked, which is why git's configuration is a protected path (section 1). |
| Nothing fetches automatically. Opening a session does not retrieve URLs, install packages or start project-defined processes without trust. | No injection before the user has done anything. |
| The base state of a session in an untrusted repository reads only the commit and the branch. A diff or a listing of untracked files can run a clean filter the repository's own `.git/config` names, so they wait for trust; every git command the harness runs turns the file-system monitor off (`core.fsmonitor=false`) and writes nothing to the repository (`--no-optional-locks`). Once the project is trusted, the harness's git runs inside the sandbox while commands are confined, so even a filter the repository names runs with no write root and no network. | Opening a session in a repository someone handed over does not run its configured programs. After the user trusts the project, a filter git runs for the harness runs confined, not with the user's rights, so a confined command cannot turn the harness's own git into a way out of the sandbox. |
| Approval prompts show exactly what will run. Hidden and look-alike characters are made visible. | An injection cannot hide part of a command from the person approving it. |
| For the future fetch tool: block loopback, link-local, private and metadata addresses after name resolution, cap response size, strip markup to text, and never send credentials. | Server-side request forgery and oversized or active content. |
| **An extension's fetch reaches the host that was checked, and none of the addresses known to be outside the internet** (since step 28). A script's `cineris.http.fetch` is checked by the manifest's `net` patterns and decided by the permission engine as a `network` effect on the URL's host, and the host they judged is the host the connection goes to. A URL the URL standard would read as another host is refused before anyone is asked: one that does not begin with `https://` or `http://` (the standard skips the slashes after a scheme, so `https:good.com://evil.com/` is `good.com`), one with a control character, a space or a `\` anywhere (dropped, trimmed, or read as `/`), a user part, a host with a `%` (decoded) or written as an address in another form (`0x7f.1`, `2130706433`, `127.1` are `127.0.0.1`), and an IPv4-mapped IPv6 address. The client, given the host that was checked, refuses a URL it reads as another before its lookup. The name is looked up once, every address it has is checked, and the client is given only those addresses, so nothing under it looks the name up again; the connection's peer must be one of them. An address in one of the ranges of `cineris_base::address::RANGES` (the one list, which later clients take too: what IANA's special-purpose registries mark as not reachable on the internet, the machine's loopback, the private and link-local networks, and the metadata services of most clouds, AWS's on IPv6, Azure's and Oracle's), or an IPv6 form of one (IPv4-mapped, translated, IPv4-compatible, NAT64's well-known prefix, 6to4), is refused unless the manifest names that very host literally as an address, or as `localhost` for this machine's loopback, never through a pattern and never because another of its entries names one. Only `https`, or `http` to such an address. A server's certificate is checked by rustls against the system's own roots, read once in a process, with nothing fetched: a server a script chose cannot have the machine fetch the issuer or the revocation lists its certificate names, as the platform's verifier on Windows did, from any address (step 28's review; a Windows runner showed the connection). What that gives up: no revocation is checked (none was on Linux before), a server that leaves its chain incomplete fails, and on Windows a root the system has not yet downloaded is not known and its `Disallowed` store is not read. No redirect is followed (a 3xx is returned, and a fetch of its location is checked again), no proxy is used, no cookie is kept, and the headers that steer a request (`Host`, the hop-by-hop ones, `Content-Length`, `Expect`, any `Proxy-` header) are refused. What the client would refuse before its lookup (a URL over 8 KiB, more than 64 headers or 64 KiB of them, a body over 1 MiB, the scheme) is refused before anyone is asked. The question shows the URL up to its query, cut at 200 bytes (its path is shown, and a path can itself be a credential, such as a webhook's: the person sees where the request goes), and names what the fetch sends besides: the sizes of its query and its body, and its headers' count, size and names, never a value. A failure to connect reads the same whatever its cause. The response is cut at 4 MiB and says so, and a fetch takes 30 s at most, less if the script asks for less or its call has less left. **What is not refused:** an address of the internet that is the machine's own or its network's (a dual-stack network's IPv6 addresses, an intranet on public addresses), which nothing here knows, and an address under a network's own NAT64 prefix or ISATAP's. A name a pattern of the manifest allows can be pointed at one, and the fetch connects to it; over `https`, a service there answers only with a certificate for that name, which most local services do not have, but a script can try the ports, and tell an open one from a closed one by how long a failure takes ([an open item](outstanding/a-fetch-reaches-the-machines-own-and-its-networks-public-addresses.md)). | An extension cannot be steered, or steer itself, into the machine's loopback, its private and link-local networks or a cloud's metadata service: by a name that resolves there, a name that resolves elsewhere the second time, a redirect, a certificate that names an address, or a host written so that the check and the connection read it differently. What a wildcard in `net` reaches beyond the manifest's own hosts, the machine's and its network's public addresses included, the manifest is the bound of. |

**Residual risk.** A model that has been steered can still make bad edits inside the workspace and can waste money. A user who approves a network request can still be tricked. Review of diffs and the cost limits are the backstops.

## 3. Malicious or compromised extensions and MCP servers

**Threat.** An extension script, a hook command or an MCP server is malicious from the start, is replaced by a malicious version, or is defined by a repository the user cloned. A special case: the harness itself writes an extension at the user's request, and injected text steers what it writes.

| Mitigation | Effect |
|---|---|
| **Extension scripts run in an embedded script runtime with no access of their own.** A script cannot open a file, start a process or reach the network. It can only call host functions, and each call is checked against the extension's manifest and then against the session's permission rules. | A malicious or badly written script is confined on every OS, including Windows, where no OS sandbox is available in the first release. It cannot read the harness's credentials: no host function returns them. |
| Each script runtime has a memory limit, a time limit per call and an instruction interrupt. | A runaway script is stopped. It cannot stall the agent. A few of the engine's native functions loop without looking at the interrupt (`Array.prototype.reverse` over an object whose length is huge), and cannot be stopped: since step 28 such a thread is left running and said so, its extension is not started again in the process (until a restart or a new approval), and past four such threads no extension starts at all. |
| **What a script hands the harness is bounded where it crosses** (since step 28): each kind of host call's arguments by size before they are taken, at most sixteen calls a script awaits waiting at once, and counts of notices, questions and lines of the log in each call. A question's answer is one of its choices, and what a script shows passes through the same escaping as a workspace's names. A refusal names the path as the script gave it, and nothing is resolved where the manifest grants nothing. | A script cannot fill the harness's memory, which its runtime's limit does not count, nor flood the front ends, nor draw what the harness draws, nor learn where a path outside its manifest leads. |
| **The script's code never runs while the harness holds the runtime's state** (since step 28): a definition is read whole first, an error is made after it is let go, and `Error.prepareStackTrace` cannot be set. | A getter, `toJSON` or a stack-trace hook calling back into the engine cannot take the process down, before approval or after. |
| A manifest lists what an extension may ask the host to do: which programs it may run, which paths it may read or write, which hosts it may contact. | The user approves a short, readable list, and the runtime enforces it. |
| **A script never writes a protected path** (since the fix of step 28's protected writes): `cineris.fs.write` of git's configuration or hooks, a CI file, a build or registry setting, a shell's start-up file or `.cineris`, at any depth where the table of protected paths says so, is refused at every level, `unrestricted` included, before the permission engine is asked. It is judged by where the path leads (through `..`, a link, another case or separator on Windows), and the refusal names the path. | A script cannot plant a hook or a filter through `fs.write` for the harness's own git to run unconfined where the sandbox does not enforce, or for the model's `git status` at `unrestricted`, though nothing looks at a host write afterwards. Its programs are confined at every level only where the sandbox enforces: on Windows today a program it runs can still write one (the next row). |
| Programs an extension asks the host to run go through a sandbox launcher of the extension's own where the sandbox enforces, at every level, `unrestricted` included (since step 28): the session's reads; as writes, only the manifest's write roots, each handed over unresolved so that a link on the way is refused, and the session's temporary directory; the network only with `exec_network`, which the engine decides as reaching any host. Nothing is found where a program could have been planted, by the harness's search or by the program's own `PATH`. Where nothing confines programs (Windows in the first release, a machine without the sandbox), a manifest's `write` and `exec_network = false` do not bind them, and the approval says the program runs outside the sandbox. **The engine judges a program's line, its arguments, not its input** (since the fixes to step 28's process starts): a question about a program given input says how long the input is and shows how it begins, at most three lines and 200 bytes, escaped: what follows is not shown, and a script can put what matters past it, so the length is the warning. | The same OS confinement as shell commands, where the OS has it, and narrower: what the manifest lists, not the session's grant. |
| **Self-written extensions are reviewed before they load.** The harness shows the manifest and the full source, checked for syntax, and loads nothing until the user approves. The approval is pinned to a hash. | Injected text can at most produce a proposal that the user sees in full. What it could do if approved is bounded by the manifest shown beside it. |
| MCP servers and hook commands are separate processes, started in the sandbox with a narrow default: read the workspace, no writes, no network. More must be declared and approved. | A malicious server is confined where the sandbox is enforcing. A crash cannot hurt the harness. |
| Project-defined hooks, extensions and MCP servers need project trust, including MCP servers found in another tool's configuration file in the repository. Since step 28 a session of a project that is not trusted does not look in its `.cineris/extensions/`; the trust question lists each extension in words from its manifest, its author's description last, labelled and quoted, and the manifest refuses a backtick in what is shown as code; a yes pins each extension as the question read it. | Cloning a repository runs nothing, and an author's text cannot pose as what the harness says it may do. |
| Trust is pinned to a hash of the definition (script and manifest; command and arguments; for MCP, each tool definition). A change disables it until approved again. The store and the hashes are built in step 12 (`cineris-policy`, `trust`), and a project's rules are pinned the same way, all of them: a project that drops one of its `deny` rules has changed, and its allow rules wait for the user. Since step 28 an extension's hash is of its folder read whole: the user's own are pinned in `pins.toml` beside `trust.toml`, and a project's extension never takes a name a folder of the user's has. A session checks each pin when it finds its extensions, and again at a turn's start when what they were found in changed, withdrawing one that no longer stands approved; and the runtime checks the hash once more at the extension's first call, so a change between those looks is never run. Step 30 computes the hashes of what it loads. | The "approved once, changed later" attack. |
| **Git is trusted only once it was shown** (since the follow-ups of step 23). Trust pins whether git was in what the person was shown, as it pins the rules (`trust.toml` version 2): a folder trusted before it was a repository, or under a store of version 1, has git asked about when it is one, and until then the harness's git does not read the repository's configuration, nor are git's forms on the read-only table. A person asked about what is new in a trusted project can keep trusting it without it, which keeps what was trusted before; never is not offered there. An older build refuses a version 2 store whole and trusts nothing. | A folder trusted before `git init`, or before an archive with a `.git` was unpacked into it, cannot have git run a program its configuration names without the person having seen git in the list. Declining new rules does not take away the trust given before. |
| Their tools go through the same permission check as built-in tools, and ask by default. | A tool cannot act without the policy's say. |
| Their output passes the same truncation and is labelled as third-party. | Flooding and some injection. |
| **An extension's text in the system prompt is the approved text, fenced, and leaves when the user takes it back** (since step 28): section 7 holds each enabled extension's `prompt` file as the registration cache holds it for the approved hash, under the harness's line naming it, every line quoted after `> `, between a lead line and an end line, 4 KiB a text and 16 KiB in all, the user told of what the cap leaves out. An extension removed, disabled or changed has its text withdrawn by a notice naming it before the model's next request, a session read again begins a new epoch without it, and a summary is asked to leave its text out. | An extension's author speaks with the system prompt's authority only in the text the user approved, and cannot forge another extension's part, the harness's lines or the user's appended text; the authority goes when the user takes it back. A change on disk is seen at the next turn's start, so one made during a headless run is seen after it. |
| The provider credentials are never passed to them. Environment variables given to MCP servers and hook commands are an explicit list. | Credential theft. |
| Hook decisions are typed and bounded: allow, deny, ask, or a rewritten argument that is shown to the user and re-checked by policy. Hooks have deadlines. | A hook cannot silently widen a command or stall the agent. |
| No installation at start-up. The harness never downloads or installs extension code on its own. | Supply-chain surprises at launch. |

**Residual risk.**
- The script engine is a C library. A memory-safety bug in it could let a script escape the runtime. Scripts are code the user approved, the engine is kept current, and it is the one C dependency in the binary; this risk is the price of an engine that authors and models already know. See [decision 0005](decisions/0005-extension-mechanism.md).
- The engine's own asserts are kept on (since step 28): one that fails ends the process, the safer failure than going on with the engine's state broken. A script that could reach one would end the session; the review of step 28 found one way (fixed) and no other.
- A file a call was allowed to read or write is opened by its path after the decision, which may wait on a person; something running beside it that can place a link in the workspace could swap a folder above it. An extension's read checks its path again after the decision. Open: [a-file-is-opened-by-name-after-its-decision](outstanding/a-file-is-opened-by-name-after-its-decision.md).
- On Windows in the first release, MCP servers and hook commands are not confined by the OS.
- A trusted project's own `sandbox.write` that names a folder holding the harness's files (`~/.cargo` with `cineris` in `~/.cargo/bin`) turns the sandbox off for the project's sessions, its extensions' programs and the shell's commands both. The trust question says so before the yes, and so does `cineris permissions trust` (since step 28); leaving that root out and keeping the sandbox on is step 32's ([outstanding/a-projects-write-root-holding-the-harness-files-turns-the-sandbox-off.md](outstanding/a-projects-write-root-holding-the-harness-files-turns-the-sandbox-off.md)).
- An extension the user approved with network access to a host can send that host whatever its manifest lets it read. This is stated at approval time.

The reference harnesses load extensions into the agent process with the user's full rights. See [reference-notes.md](reference-notes.md).

## 4. Secrets in logs and session files

**Threat.** Credentials or other secrets end up on disk in logs, session files, artifacts, crash reports or exports, and leak from there.

| Mitigation | Effect |
|---|---|
| Credentials are a `Secret` type. It prints as `[redacted]`, and it cannot be serialised. | The harness's own keys cannot reach a log or session by accident. Tests check it where a key is handled: no `Debug` or `Display` form of a secret, of a credential, of a store or of a store's error contains the test key, and an error about a malformed credentials file names a line number and never the line. `cineris-testkit`'s `assert_never_printed` makes the check one call: `cineris-config` runs it over every public type that can hold a key or the environment (the environment itself, the load options, the live configuration, a loaded configuration and its views, a credential lookup), with a made-up key put in the environment, a provider's literal header, the command line and the store. The environment prints its variables' names only, and a provider's literal header, which a gateway can use for its key, prints as `[redacted]`. So does, until its step declares it, a value in a reserved section under a key whose name looks like a secret's (an MCP server's `env`, an `api_key`), and the user part of any web address (`http://user:password@proxy`) ([architecture/08-configuration.md](architecture/08-configuration.md), "Credentials"). A check of the whole test suite's output for the test key is planned, and is not built yet. |
| Request logging prints an allow-list of headers. Bodies are logged only at debug level, truncated and filtered. | Keys in headers are never logged. |
| Credentials are stored in the OS keychain or an owner-only file, never in the configuration file, and are not readable by child processes through the environment. | The file, its lock and the folder that holds them are closed to the agent's tools at every level, by the built-in protection: on Linux the configuration directory, and on Windows a folder of their own in the local application data folder, so that a temporary file left by a write that was killed, which holds every key, is closed too ([architecture/08-configuration.md](architecture/08-configuration.md), "Where each system keeps the harness's files"). |
| Reading or writing a file that looks like a secret asks first, at every level short of `unrestricted`: `.env` and `.env.*` (not the templates, such as `.env.example`), `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, the SSH private key names, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `.envrc` ([architecture/06-permissions-and-sandbox.md](architecture/06-permissions-and-sandbox.md), "Files that look like secrets"). It is the default for such files, not a rule: a user's `allow` lifts it, a project's `allow` lifts it only after trust, and a `deny` closes the file. | A model reading a key file, or a walk returning one, without anybody having said it may. A name is all there is to go on: a secret in a file with an ordinary name is not caught. |
| The base state of a session stores only what the read rules would let the agent read without asking, trusted project or not and whatever the level; the rest is listed as omitted ([architecture/07-sessions-and-context.md](architecture/07-sessions-and-context.md), "The base state"). The session store has no list of names of its own: it asks a gate the core fills from the permission engine (step 12). | An untracked `.env` does not end up in the checkpoint store, and neither does a file a rule protects. |
| A file that looks like a secret and that an edit tool changed **is** kept in the checkpoint store. The edit happened only after the user approved it or wrote a rule for it, undo needs the old bytes, and the store is owner-only. | Undo of an approved edit to `.env` works. The old content of a file the user chose to let the agent edit is in the session directory until the session is deleted. |
| Session logs, artifacts, checkpoints and log files are created owner-only: mode `0600` on Linux, and on Windows an access list with the user alone and inheritance off, given to the call that creates the file ([decision 0029](decisions/0029-owner-only-files-on-windows.md)). | Other local users cannot read them. Not on a file system that keeps no permissions, such as FAT: there the harness reports that the file is not private. |
| A redaction filter runs when session entries and artifacts are written: the harness's own credentials by value, and strings in well-known key formats. Step 8 built the hook (`cineris-session`'s `Redactor`), applied to every string of an entry and to text artifacts line by line; step 13 builds the filter. | Catches common accidents, such as a command that prints its environment. Best-effort, and described as such. **Not redacted:** the provider's own blocks (`raw` fields: reasoning signatures, encrypted content), because a changed byte makes the provider refuse them on replay, and the file contents kept for undo, which must be put back exactly. **Settled in step 13a:** a raw block in which the filter finds a secret is never written. The whole message is stored as its neutral projection and marked; the running session still replays it; and after a resume the reasoning from the first altered entry onwards is not sent back, because the provider would refuse it against a history that has changed ([architecture/07-sessions-and-context.md](architecture/07-sessions-and-context.md), "Secrets in sessions"). |
| The filter itself (`cineris_base::SecretFilter`, step 13a) masks the harness's own keys wherever their exact text appears, and tokens in the formats of well-known services: Anthropic, OpenAI and the services that copied its `sk-`, GitHub, GitLab, AWS access key ids, Google API keys, Slack, Stripe, npm, Hugging Face and PyPI; a private key in PEM form; a JSON web token; a bearer token; and the password of a web address. Every key the core finds for a provider is given to it, whenever it is found, and to the log's own filter; so is what a provider's header reads from the environment. A header written out in the configuration file is not: it is in a file already, and is as often a version or a date as a token, which masking by value would take out of every session. Text inside JSON, or printed for debugging, has its line breaks written out (`\n`), and a key that follows one is found. | **Best-effort, and narrow on purpose.** What it masks in a log is what a resumed session then shows the model, so a filter that masked ordinary source text would damage the conversation. **It does not catch:** a secret with no recognisable shape (a database password); one that is encoded (base64, URL escapes) or split across two pieces of text; a key shorter than 8 characters, by value; the body of a private key in an artifact, where the filter sees one line at a time and only the first line says what it is. **It does not see:** the checkpoint store, which holds the earlier content of files a tool changed and the content of files `read` showed, exactly. |
| No sharing or upload feature. Export reads the session masked by the core, and writes nothing unless the core says it masked it; the client then masks every string and every object key again with the same formats, drops every provider block again, masks the Markdown's text once more as it is shown, and says how many values the file holds masked, in one count (since step 25; [architecture/09-tui.md](architecture/09-tui.md), "Exporting a session"). | Sessions leave the machine only by a deliberate act. **Not caught:** what the filter does not catch anywhere (above). The count is not given by kind: a mask the log wrote says nothing of what it took the place of. |
| No telemetry and no automatic network requests. | Nothing leaves by default. |
| Crash reports contain a backtrace and versions. They contain no prompt, file or environment content. | |

**Residual risk.** A secret that a tool reads from a file and that does not look like a key is stored in the session like any other text. Sessions should be treated as sensitive. Retention is configurable.

**What goes to a client is not filtered, by design.** The filter is for what is written to disk. Events (a tool's output, the deltas, items as they complete), approval requests (a command line in full) and `session/read`'s items in progress reach a front end as the model saw them, so headless `--output jsonl` redirected to a file holds in clear what the session log masks. The owner chose to keep it so in step 27 ([steps/27/answered.md](steps/27/answered.md), "The owner's answers"): a client is the user's own program, admitted over a socket only as the same user and never as one of the server's own commands, and it is sent what the person at the terminal sees; a filtered command line would ask a person to approve what they cannot see. What a client does with what it is sent, such as a file it writes, is outside the harness.

## 5. The RPC surface

**Threat.** Another local user, another program, or a web page in the user's browser connects to the RPC server and drives the agent, which can run commands as the user.

| Mitigation | Effect |
|---|---|
| The default transport is standard I/O, reachable only by the parent process. | No exposure. |
| Local sockets are owner-only, in the per-user runtime directory, with a check that the peer is the same user, and `cineris attach` reaches a server only once it is shown to be the user's: the socket and its folder the user's, and the process at the other end the user's (on Windows, the pipe owned by the user and labelled medium or above). Named pipes on Windows admit only the current user, at the server's integrity or above, with a check of each connection's own token (step 27). | Other local users cannot connect, and nor can a lower-integrity process of the same user on Windows. |
| The server refuses its own commands: on Linux a peer whose line of parents reaches the server's process, on Windows a client in the Job Object the server puts itself in at the start, which every process it starts inherits and cannot leave (step 27). | A command the user approved for one purpose cannot simply connect back as a client to answer its own session's approvals or raise its level. A thin check on Windows (the residual risk below). |
| Network listening is off by default, absent from the first release, loopback-only unless explicitly widened, and always requires a per-launch random token. No unauthenticated mode exists. | Other machines and unauthenticated local programs cannot connect. |
| `Origin` checking on the WebSocket transport. | A web page cannot use the browser to reach a local server. |
| Remote use goes through SSH or a TLS proxy. The server does not implement TLS. | No home-grown transport security. |
| Clients cannot weaken policy. A client may have `unrestricted` only of a server started at it (`--permission-mode unrestricted`, or the user's configuration). Otherwise the core refuses it at one gate, on the level the configuration comes to however it is asked for: a session's settings or an override of `permissions.mode` however spelled (`session/new`), a stored session opened again, a fork (refused before it is written), a raise by `session/set`, and `config/reload` with a profile or after the user's file changed, explicit or at a turn's start, which leaves the level out and applies the rest (step 27). A supervisor's grant covers no question about a path, and a command only where the session's enforcing sandbox confines it in the session's own scope; the session is told, when the supervisor opens it, what of the grant does not apply and why (step 27). Trust is a question put to the person's own front end, a `user` client that declared `trust`, as the terminal UI is asked; a client that did not declare it trusts nothing without `--trust-project`, as a headless run does. Approvals are requested from clients, never assumed. | A client is not more powerful than the user at the terminal. |
| Input is size-limited and schema-checked. Malformed messages get an error and never crash the server. Outbound queues are bounded. | Denial of service by a client. The protocol decoder is fuzzed. |

**Residual risk.** Any program already running as the user can start its own `cineris` or read the user's files. The RPC server does not change that. The refusal of the server's own commands is defence in depth: on Linux a command that detaches itself from its parents escapes it, and the enforcing sandbox, which keeps a confined command from every Unix socket, is the wall; a peer whose process is gone when the server looks, or in another pid namespace, is refused, but one whose process id was taken by another process in between could pass, and so could one with a parent `/proc` hides from the server (a process of the user's that ran a set-user-id program, or made itself not dumpable), since a hidden parent is taken for another user's. On Windows, which has no sandbox in the first release, the check is thin: a process of the user at the same integrity may open any other such process with full rights by default, so a command can take an admitted connection from a client outside the job (the user's terminal, `cineris attach`), act from inside the server's own process, or make an instance of the pipe's name for a new client to reach, and a service that starts processes for it (the task scheduler, WMI) puts one outside the job. There the person approving the command is the wall.

## 6. Supply chain

**Threat.** A dependency is compromised, or a build is tampered with.

| Mitigation | Effect |
|---|---|
| A small dependency tree, with every direct dependency justified and listed. | Less to audit. |
| `cargo-deny` on every pull request: advisories, licences, banned crates, sources limited to crates.io. | Known-bad versions and unexpected sources are blocked. |
| `Cargo.lock` is committed. CI builds with `--locked`. | Reproducible dependency versions. |
| No build script downloads anything. The model catalog is a checked-in file. | Builds are offline and reviewable. |
| GitHub Actions are pinned by commit hash and run with minimal token permissions. Pull-request jobs have no secrets. | A malicious pull request cannot reach credentials. |
| Release binaries are built by CI from a tag and published with checksums. | Users can verify what they run. |

## 7. Terminal and local environment

| Threat | Mitigation |
|---|---|
| Control sequences in model output, file content or tool output change the terminal's state, title or clipboard, or forge UI. | The renderer writes only text it has sanitised. Control characters other than newline and tab are stripped or shown as visible symbols. Only the harness emits control sequences. Characters that act unseen without being controls (the bidirectional overrides, the characters of no width, the tag characters) are written as escapes, `\u{202e}`, so that text cannot read as something else ([architecture/09-tui.md](architecture/09-tui.md), "Sanitising"), including the character a markdown entity stands for. |
| An answer copied with `/copy` and pasted into a terminal types what it holds: an escape ends bracketed paste early, and the rest runs as keys. | `/copy` drops every control character but the line feed and the tab, and writes what acts unseen as its escape, before the text leaves for the clipboard (since the review of step 23). |
| A link in a model's answer hides its address behind its text (a terminal hyperlink, OSC 8): a click opens a local file with whatever the system runs it with, or, for a share (`file://server/share/x`), makes Windows send the account's credentials to that server. | Only a web address (`http://` or `https://`, in printable ASCII) is written as a hyperlink. Any other link is drawn as its text followed by its address, which can be read before it is used (since the review of step 23). |
| Symbolic links lead a tool outside the workspace. | Paths are resolved before the permission check, and the check applies to the target. Windows junctions are resolved the same way. The harness follows links itself, one at a time, and checks each target before it goes there. A link to something that does not exist is refused. |
| A protected file is reached under another spelling, which a rule written for its name does not match. On Windows: another case, a short name (`SECRET~1.ENV`), a trailing dot or space, an alternate data stream (`secret.env::$DATA`), a device or extended-length path. | The check is made on the resolved path, in which case and short names are already the file system's own. The other spellings are refused outright, each with its own error ([architecture/05-tools.md](architecture/05-tools.md), "Paths"). |
| On Windows a directory can be marked case-sensitive, and there `App` and `app` are two folders. An allow rule, a lease's scope or a project's trust given for one would reach the other if names were compared without regard to case. | What grants compares names exactly, against the resolved path in its stored case: the scope, an allow rule, a writable root in `narrow`. The project key is made from the stored case, so the two folders are two projects, each with its own trust and approvals. Tested on the Windows runner in a real case-sensitive directory. |
| A path on a network share makes Windows send the account's credentials to a server an attacker named. The path may be written outright, or be the target of a link planted in the workspace. | Network paths are refused unless configuration allows that server and share. The refusal is made on the text of the path, or of the link's target, before anything is asked of the network. Configuration takes the same path: a project's configuration files, what discovery looks for in the workspace, and the check for changed files, which finds the project's files again before it looks at them, all go through the path resolver before the project is trusted ([architecture/08-configuration.md](architecture/08-configuration.md)). A workspace that is itself on a share is where the user chose to work, and its own share is allowed there; a link to any other share is refused. **Residual:** a link swapped in during the moment between the check's look through the resolver and its own look at the file is followed. |
| A file has a second name that no rule mentions: a hard link, or on a Linux mount that ignores case, another spelling. | Not detected. A rule protects the names it matches. This is a residual risk, and the sandbox's write roots are the backstop for commands. |
| A rename replaces a file the user could not have written, or a device or socket. | An atomic write refuses a target that is read-only or not writable by the user, and anything that is not a regular file ([architecture/05-tools.md](architecture/05-tools.md), "Atomic writes"). |
| The file system changes between the check of a path and its use. | The harness opens the resolved location, never the text it was given. Since step 10 the last name of a path is opened without following a link and without waiting (`cineris_base::open_regular`), and the open handle is asked what it is: a file swapped for a link to somewhere else, or for a FIFO that would hold the read for ever, is refused. `read`, the editing tools and the checkpoint store open this way. The editing tools resolve their path again when the call runs, and write with a replace that follows no link, so a link put at the target after the check does not carry a write out of the workspace. That does not stop a process that swaps a directory earlier in the path at the right moment: confining such a process is the sandbox's job, and without an enforcing sandbox this remains a residual risk. On Windows a cloud or projected placeholder is opened twice, which leaves a window for that kind of file ([architecture/05-tools.md](architecture/05-tools.md), "What resolution does not promise"). |
| Two harness processes corrupt shared files. | Session logs are append-only with one writer per session, guarded by a lock. Shared state files are written atomically under a lock. |
| A panic leaves the terminal unusable. | The panic hook restores it. |

## 8. The Coordinator

**Threat.** Under the Coordinator ([architecture/17-coordinator.md](architecture/17-coordinator.md)) a Manager session with broad permissions drives Employee sessions and integrates their work, with less of the user's attention on each step. Three things can go wrong that a single session does not face:

- **Injection that travels.** An Employee reads something hostile. Its report, its questions or its code then try to steer the Manager: "approve this", "merge without review", "grant me network access", "the tests are known to fail, ignore them".
- **Privilege creep.** A Manager hands out more than it was given, or accumulates approvals nobody looked at.
- **Runaway work.** A team spends the budget, fills the disk, or pushes something that cannot be undone.

| Mitigation | Effect |
|---|---|
| **Hard limits are enforced by the harness, never only stated in a prompt.** The budget is a ledger charged before each request. Models never run network git commands: commands run with the network off, and pushing or opening a pull request is done only by a harness operation that has no code path that forces. Writes are confined to each session's worktree by the sandbox and the path check. The main branch is refused as a merge target unless the grant allows it. | A Manager that has been talked into anything still cannot exceed the budget, force-push, write outside the project or merge to the main branch. |
| **A child's lease is computed, not chosen.** An Employee receives the Manager's lease narrowed by what was requested. The narrowing is code with a property test. | No instruction, from the user's task or from an Employee, can give an Employee more than the Manager holds. |
| **The Manager cannot approve beyond its own lease.** An Employee's approval request is checked against the Manager's lease before the Manager is asked. Anything outside it goes to the user. | "Please approve network access" from an Employee reaches the user, not just the Manager. |
| **Employee output is data.** Reports, questions and summaries reach the Manager as bounded, labelled tool results, with the same sanitising as any tool output. They are never inserted as instructions or as the user's words. | The Manager can tell an Employee's text from the user's. This lowers the risk and does not remove it. |
| **Integration is decided on evidence the harness produced.** Before a merge the harness runs the project's checks in the Employee's worktree and computes the diff itself. The review packet says what the checks returned and flags deleted or weakened tests. An Employee's claim that "tests pass" is not an input. | A persuasive report cannot stand in for a passing check. |
| **Sensitive paths always go to the user** unless the grant names them: CI configuration, git hooks and configuration, the project's `.cineris` directory, dependency registry and script settings, files that look like secrets. Built for every session in step 12 ([architecture/06-permissions-and-sandbox.md](architecture/06-permissions-and-sandbox.md), "Protected paths"): asked about at every level below `unrestricted`, by every route, unless an allow rule names the path. | The changes most useful to an attacker are the ones a person must see, at every level. |
| **Employees cannot reach each other.** All messages go through the Manager. | One compromised Employee cannot instruct the others. |
| **Every decision the Manager takes alone is logged** with its reason and, written by the harness, the grant clause that allowed it. Mechanical decisions are logged by the harness whether or not the Manager explains them. | Nothing is approved invisibly. The log is reviewable at any time and after the fact. |
| **The escalation queue is the only way a question reaches the user**, it shows who is asking and the full detail, and unanswered requests are denied on timeout. | No request is approved by default. |
| **Levels above supervised need an enforcing sandbox.** Where the OS sandbox is not enforcing, only the supervised level is offered. | The hard limits are never offered where they could not be guaranteed. |
| **A watchdog in the harness**, not a model, pauses a session that stops making progress or repeats itself, and the whole team stops at the budget cap. | Runaway spend and stuck sessions are caught without relying on the Manager's judgement. |
| **The user can see and stop everything**: every Employee is listed, any can be attached to, and one action stops the team. | |
| The team lease is shown in full, in plain language, before the team starts. It is the same lease type and the same levels a single session uses (section 9). | The user knows what they are delegating, in terms they already know. |

**Residual risk.**
- Choices about design, security and scope depend on the Manager recognising them as such. The harness cannot detect them mechanically. At the guided and autonomous levels a steered Manager could make a poor design choice inside its grant; the decision log and review of the integration branch are the backstops, and the main branch stays out of reach.
- Code written by a steered Employee can still be subtly wrong while passing the checks. The same is true of any agent, and review before merging to the main branch remains the user's.

## 9. Task leases

**Threat.** A task lease ([architecture/06-permissions-and-sandbox.md](architecture/06-permissions-and-sandbox.md)) lets the agent work without asking inside agreed terms. The risks are terms that are wider than the user understood, terms that widen themselves, and work that carries on after the user stopped watching.

| Mitigation | Effect |
|---|---|
| **Only a person grants, extends or revokes a lease.** It is a protocol operation open to the `user` role alone. A model can draft terms; a draft is text. | Injected text cannot give the agent more autonomy. |
| **The terms confirmed are the terms enforced.** The confirmation screen is rendered from the lease value itself: scope, level, budget, time, stop conditions. | No gap between what was read and what runs. |
| **Every term is enforced by the harness**: scope by the permission engine and the sandbox, budget by the ledger, time by the supervisor, stop conditions as data. | None of it depends on the model's good behaviour. |
| **`guided` and `autonomous` need an enforcing sandbox.** | Autonomy is never offered where confinement could not be guaranteed. |
| **At the edge the agent stops and reports**, and the session falls back to its standing lease. | No drift into a stream of prompts that train the user to approve without reading. |
| **A lease cannot exceed managed or user configuration, and a project cannot grant one.** | A repository cannot make itself trusted. |
| **A child's lease is always a subset** (`narrow`, with property tests). | Runs, attempts and Employees cannot hold more than their parent. |
| The level and what remains of the lease are always in the hint row. | The user can see at a glance that the agent is working unasked, and for how much longer. |

**Residual risk.** Inside its scope a lease permits everything it says. A lease that allows running the project's tests allows whatever the tests do, inside the sandbox. This is the same trust the user already places in the project's own build.

## 10. Reading other tools' usage records

**Threat.** The usage view can read files written by other coding agents ([architecture/18-usage.md](architecture/18-usage.md)). Those files hold conversations as well as numbers, are in formats that change without notice, and could be crafted by anything that can write to the user's home directory.

| Mitigation | Effect |
|---|---|
| **Opt-in per source, user-only.** Nothing is opened until the user enables a source. A project cannot enable one. | No surprise reading of another tool's data. |
| **Read-only.** Nothing is created, changed or locked in another tool's directory. | The other tool cannot be damaged. |
| **Only numbers are kept.** Adapters extract times, model names, token counts, costs, project paths and record ids. A test asserts that no text field from the input reaches the output or the cache. | Conversations are not copied into our state. |
| **No network by default.** The view and the indexer make no connection. Tested with the network denied. The one exception is the opt-in refresh of limits: off by default, per provider, user-only, made only when the user asks, and sent only to that provider's documented usage endpoint with the user's own key. It carries no usage data, and a test asserts that. **What the endpoint answers is read and dropped**: one provider's answer holds a shortened form of the key, so nothing but the figures is kept, shown or logged (built in step 31 for the first three such endpoints, [architecture/04-providers.md](architecture/04-providers.md), "The `openai-chat` protocol"). | Nothing read from another tool can be sent anywhere. |
| **Untrusted input.** Size and line-length limits, no following of links out of the tool's directory, fuzzing of every adapter. A bad file is skipped and named. | A crafted file cannot crash the harness or make it read elsewhere. |
| **Unknown versions are refused, not guessed.** | Wrong numbers are not shown as facts. |
| **Every figure is labelled** with its source and cost basis. Estimates are never merged silently into metered totals. | The user is not misled about what was billed. |
| The cache is owner-only and can be deleted per source. | |

**Residual risk.** Project paths from other tools are shown in the view and stored in the cache. They stay on the machine.

## 11. What git and cargo execute, and what is neutralised

Git and cargo run programs that a repository names, not only the one a command line names. A workspace is the model's to write, so whatever it can make git or cargo run is a way to run code, or to reach a secret, without a question. This is the list, with what the harness's own git (`cineris_base::git`, [architecture/06-permissions-and-sandbox.md](architecture/06-permissions-and-sandbox.md), "The harness's own git") and the sandbox do about each. "Protected" means a protected path ([06](architecture/06-permissions-and-sandbox.md), "Protected paths"): writing it goes to the user at every level, and a confined command that writes it anyway is found by the look before and after the command, which stops the turn.

| Mechanism | What runs it | The harness's own git | A command the model runs |
|---|---|---|---|
| **Hooks** (`.git/hooks/*`, or the folder `core.hooksPath` names) | `git commit`, `checkout`, `merge`, `push`, `am`, `rebase` | `core.hooksPath` is `/dev/null` (`NUL` on Windows): no hook runs | `.git` is protected. A hook a confined command wrote is found and stops the turn; one that is there runs inside the sandbox with the command that starts git |
| **The file-system monitor** (`core.fsmonitor`) | Nearly every git command that reads the index, `status` and `diff` among them | `core.fsmonitor=false` | Every shell command is given `core.fsmonitor=false` in `GIT_CONFIG_KEY_<n>`, after any of the caller's, and at the end of `GIT_CONFIG_PARAMETERS`: a command's own git runs no monitor either |
| **Filters** (`filter.<name>.clean`, `smudge`, `process`, chosen by `.gitattributes`) | `status`, `diff`, `add`, `checkout` | **Nothing turns them off.** Git's content is asked for only in a project the user trusts; in a session that confines commands git runs inside the sandbox, reading only, with no network. A filter is given git's environment, which has no provider key and a `PATH` of absolute directories only, so a filter named by a bare name is never a workspace file (section 12) | The configuration is protected; `.gitattributes` is not, so a filter the configuration already names can be pointed at more files. Inside the sandbox it runs confined |
| **Text converters and external diff** (`diff.<driver>.textconv`, `diff.external`, `GIT_EXTERNAL_DIFF`) | `diff`, `log -p`, `show` | The base state's diffs pass `--no-ext-diff` and `--no-textconv`; the list of changed files `--no-ext-diff` | Runs confined |
| **The pager** (`core.pager`, `pager.<cmd>`, `GIT_PAGER`, `PAGER`) | Any command whose output is a terminal | The output is a pipe: no pager | `GIT_PAGER` and `PAGER` are `cat`; a `-c core.pager=…` on the command line is something the command analysis asks about |
| **Aliases** (`alias.<name> = !program`) | `git <name>` | Runs built-in commands only, which an alias cannot replace | An alias is a program the command names, and runs confined; the configuration that defines it is protected |
| **Transports, credential helpers, `core.sshCommand`, a partial clone's lazy fetch** | `fetch`, `push`, `clone`, and any command that meets a missing object | `GIT_NO_LAZY_FETCH=1`, `GIT_TERMINAL_PROMPT=0`; no network inside the sandbox | `push`, `fetch`, `pull` and `clone` are never approved with further words; no network inside the sandbox |
| **Included configuration** (`include.path`, `includeIf`) | Every git command | Read like the rest: what it names is the list above | The repository's configuration is protected; a file it includes from outside the workspace is the user's |
| **`.cargo/config.toml`** (`build.rustc-wrapper`, `target.<triple>.runner`, `[alias]`, `[env]`, registries and their tokens) | `cargo build`, `test`, `run`, `check` from that folder or below | The harness runs no cargo | Protected at any depth, as are `.npmrc`, `.yarnrc` and `.yarnrc.yml`. A cargo the model starts runs confined |
| **Build scripts and procedural macros** (`build.rs`, a `proc-macro` crate) | `cargo build`, `check`, `test`, `clippy`, and an editor's language server | The harness runs no cargo | Ordinary workspace files, and a command's to write: they run confined, inside the write roots, with no network. A user who runs cargo outside the harness afterwards runs them unconfined |
| **`rust-toolchain.toml`** | Any `cargo` or `rustc` through rustup, which installs the toolchain it names | The harness runs no cargo | Not protected. Inside the sandbox a toolchain that is not installed cannot be fetched; outside it, rustup installs from the official channel only ([outstanding](outstanding/rust-toolchain-is-not-a-protected-path.md)) |

**What is not neutralised:** a filter, a text converter or a build script is a program the repository may run whenever git or cargo is run outside the harness: by the user, by an editor, by CI. The harness keeps a command it runs from planting one unseen (protected paths, the look before and after) and from running one outside the sandbox, not the user's own tools from running what the repository holds. [06](architecture/06-permissions-and-sandbox.md), "Invariants to test", lists what a review should try to break here.

## 12. Every process the harness starts

**Threat.** A process the harness starts for itself, unasked, runs a program the workspace chose, or hands it a secret: a key variable reaches a filter that a repository's configuration names, a `bash` a command wrote becomes the shell, or a bare name is found in the workspace through an empty or relative `PATH` entry. The shell's commands had all three settled (section 1); two of the harness's own starts had not, until the harness's own processes' fixes ([steps/harness-process-fixes/answered.md](steps/harness-process-fixes/answered.md)).

**The rule.** A process the harness starts for itself never sees more than a command sees. It is given no provider key variable: the keys of the providers it knows, the key variable of every one it is configured with, and those a provider's header reads, from one list a reload sets. It searches only the absolute directories of `PATH` (on Unix `/usr/bin:/bin` when none is left), and on Windows `cmd.exe` is told not to look where it runs. Everything else passes as it came: `HOME`, `XDG_CONFIG_HOME`, the user's `GIT_*`, the locale, `SystemRoot`, `USERPROFILE`, through which git reads the user's own configuration. The shell, and the harness's git, are never a program found on `PATH` inside the workspace, whether commands are confined or not, nor inside a write root while they are, and nothing on the way to one (a link, a link's target) is inside either; such a program's own `PATH` leaves those directories out. What the user named is taken as named: a configured absolute `shell.program` (refused inside a write root while commands are confined), and on Windows `%ComSpec%` and the shells under `%SystemRoot%`. One builder makes that environment for every such start (`cineris_base::child_env`), and the shell's commands' environment is built on the same pieces.

**`shell.env_remove` is for commands, and git does not take it.** It is the user's list of what the model's commands may not see. The harness's git is the user's own tool reading the user's own configuration, and a pattern on that list (`GIT_*`, `HOME`) would change what it reads. The keys are the harness's own secret, which it withholds from everything it starts. A filter a trusted repository names therefore sees the user's other variables, as it would under the user's own `git status`; while commands are confined, and in the look after a program an extension's own launcher confined at any level, it runs inside the sandbox, reading only, with no network.

**The table** is every place in the product that starts a process. `cargo xtask rules` checks it against the code: a file outside the tests that calls `Command::new`, `brief::run` or `CreateProcessW` must be named here, and every file named here must still start one. The test kit and `xtask` are not the product and are not listed.
