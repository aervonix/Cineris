A variable that one reload made a provider's key, and a later reload made no longer one, is given to commands and to the harness's git again.

- Area: cineris-core
- Owner: the maintainers

| Item | Who | When |
|---|---|---|
| **"Withheld for the rest of the session" holds only for the keys the session started with.** Found by the early review of the harness's own processes' fixes ([../steps/harness-process-fixes/answered.md](../steps/harness-process-fixes/answered.md)). The key variables reach the shell's commands, and the harness's git, by two paths. One is the list the session started with: the shell's removal list is seeded from it, and `SessionGit` keeps a copy. The other is the list as it is now (`child_env::Withheld`), which a reload replaces. A variable that stops being a key at a reload is still withheld if it was one at the start, by the first path. If it became a key at an earlier reload, nothing holds it any longer, and the next command and the next git are given it. [05-tools.md](../architecture/05-tools.md) says a variable that stops being a key "is still withheld for the rest of the session, which is the safe way to be wrong", which is true only of the start's. **Why it is low:** it needs a variable that held a key and that the user's configuration then stopped naming, while the variable is still set in the harness's environment. **Recommendation:** have a reload add to what is withheld and never take away, and keep the test that pins each path alone (`sys_a_reload_withholds_a_new_key_variable_and_still_the_old_one`) able to tell the two apart: for example, a list of what reloads added, kept beside the current one. Not changed in the fixes: the shell behaves the same, and the fixes made git match it. | The maintainers | Before the first release |
