When no inherited `PATH` entry is absolute, the shell tool gives a command an empty `PATH`, and an empty `PATH` makes Unix shells look in the current directory.

- Area: cineris-tools
- Owner: the coordinator

| Item | Who | When |
|---|---|---|
| **An empty `PATH` is the workspace.** `crates/cineris-tools/src/shell/env.rs`, `absolute_entries` (around lines 148 to 185, its filter at 171 to 184, called from `build` at 137), drops every entry that is not absolute and passes `PATH` on empty when none is; the unit test `path_keeps_only_its_absolute_directories` pins it ("the variable stays, empty", around lines 388 to 391). Reproduced by the lead on a Linux laptop in step 25: in a folder holding an executable file named `ls`, `env PATH= bash --noprofile --norc -c ls` and `env PATH= sh -c ls` both ran the folder's `ls`; with `PATH` unset, bash used its own default and ran the real `ls`. So a harness started with no absolute entry in its `PATH` (say `PATH=.`) runs a file of the workspace named like a command as that command, which is what dropping the relative entries is there to stop ([05-tools.md](../architecture/05-tools.md), "`shell`", "Environment"). Unsetting it is no fix either: bash's built-in default path may end with `.` (from the reviewer's knowledge, not checked). On Windows `cmd.exe` looks in the current directory first whatever `PATH` holds, unless `NoDefaultCurrentDirectoryInExePath` is in the environment ([cmd-searches-the-current-directory.md](cmd-searches-the-current-directory.md)); what an empty `PATH` does there needs a look of its own, measured on a runner. **Recommendation** (the reviewer's): on Unix, give a fixed absolute default (such as `/usr/bin:/bin`) in place of an empty or unset `PATH`; look at Windows on its own. | A small security fix session, with [a-provider-key-break-no-longer-bites.md](a-provider-key-break-no-longer-bites.md), since both are in the shell's environment | Before the first release |
