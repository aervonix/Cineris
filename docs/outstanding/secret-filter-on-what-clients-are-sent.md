Events, approval requests and in-progress items sent to clients skip the secret filter applied to disk writes.

- Area: cortex-core
- Owner: the owner; before step 27

| Item | Who | When |
|---|---|---|
| **Whether what goes to a client passes the secret filter.** The filter masks the harness's own keys, and well-known key formats, in what is written to disk: the session log, artifacts, the log file ([../security.md](../security.md), section 4; [../architecture/07-sessions-and-context.md](../architecture/07-sessions-and-context.md), "Secrets in sessions"). What goes to a client does not pass it: events (a tool's output, a delta, an item as it completes), approval requests (a command line in full) and `session/read`'s items in progress. So headless `--output jsonl` redirected to a file holds in clear what the session log masks, and an RPC client that writes what it is sent to a file does the same. **Today this is meant:** the docs promise filtering for what goes to disk, and a client is the user's own program, sent what the model saw. Filtering events would also change a tool's output between the client and the log, and a key the user pastes into a prompt would come back masked in their own front end. The choice is the owner's: leave it, filter what is sent in a format meant for files (`jsonl`), or filter every event (and then whether an approval's command line is filtered too, since the person approving must see what would run). Found by the independent review of step 13a.  **What an RPC client of the same user is sent** (step 27, for the owner's choice): exactly what the terminal UI's own interface is sent in process, through the same queue: a tool's output and a command line in full, a delta as the model wrote it, and `session/read`'s items in progress. A client over the socket is admitted only when it is the same user (and, from the second pull request, not one of the server's own commands), so it sees nothing the person at the terminal does not; what it does with it (a file it writes) is outside the harness. The coordinator's recommendation stands: leave it, and say so in security.md. | The owner (a security trade-off, sent on by the coordinator in step 27) | Before the first release |
