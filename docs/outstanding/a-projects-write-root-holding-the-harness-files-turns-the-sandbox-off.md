A trusted project's own `sandbox.write` entry that holds the harness's files turns the sandbox off for the project's next sessions, the shell's commands and extensions' programs both, where leaving that one root out would keep it on.

- Area: cineris-core
- Owner: step 32 (hardening pass)

| **What happens today.** At a session's start, when the sandbox would enforce and any write root holds the harness's configuration, state or data directory, the user's configuration file or the launcher, the whole session is `NotEnforcing(HarnessFilesWritable)` (`assemble.rs`, the session's sandbox; [decision 0032](../decisions/0032-what-the-linux-sandbox-needs.md) where it names that case). A write root is the workspace, its temporary folder, or an entry of `sandbox.write`, and a project's entry applies once the project is trusted (`sandbox.write` widens access). Then the shell's commands run unconfined (`autonomous` is refused, `sandbox_required`, and the status says why), and an extension's programs, whose launcher confines only where the session enforces, run unconfined too. A reload that would add such a root while the sandbox enforces is refused (`harness_files_writable`) and keeps the sandbox as it was, so a project turns enforcement off only at the next session's start. Step 28's review of 2a-1 found it while judging what an extension's approval may say of its programs (the question now says they are not confined, from the load a yes puts in force). **So a project's own file, once trusted, can switch the sandbox off for its sessions** by naming a root such as `~/.cargo` with the harness in `~/.cargo/bin`. **Recommendation:** leave out a `sandbox.write` entry that holds the harness's files (a project's surely, the user's too unless that decision says otherwise), with a notice naming it under `~`, and keep enforcing; keep `NotEnforcing` only for the workspace and its temporary folder, which cannot be left out. That changes the session's assembly, step 26's tested behaviour (`sandbox::a_workspace_that_holds_the_harness_files_is_not_confined`) and decision 0032's text, so it is a step of its own. Until then, the trust question says so: where the sandbox would otherwise enforce, it lists first, of each such root of the project's own that a yes would add, "This project's configuration asks to write in `~/.cargo`, which holds Cineris's own files. If you trust it, its sessions run without the sandbox."
