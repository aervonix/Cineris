`cineris ext remove` deletes an extension's folder by its path, and a folder above it swapped for a link before the delete is followed. Security.

- Area: cineris-core
- Owner: step 32 (hardening pass)

| Item | Who | When |
|---|---|---|
| **What is open.** `cineris ext remove <name>` (since step 28's third pull request; [12-extensions.md](../architecture/12-extensions.md), "As built in step 28: managing extensions") deletes its target, one name directly in the user's folder of extensions, by its path (the names' rules, `ext::manage::folder_name_refused`, keep it one name; a check that the target's folder, resolved, was the user's folder of extensions, resolved, compared the folder with itself, since the target is always built from such a name, and was taken out by the fixes of the full review of step 28, its finding 18): a link at the name is unlinked, and a folder goes with everything in it through the standard library's `remove_dir_all`. **What the standard library guarantees:** since Rust 1.58.1 (the fix of CVE-2022-21658), `remove_dir_all` on Unix walks with `openat` and `unlinkat` and `O_NOFOLLOW`, so a link inside the folder is removed and never followed, and a link at the top is removed itself; on Windows it opens through handles with `FILE_FLAG_OPEN_REPARSE_POINT`, so a junction or a symbolic link, inside the folder or at its top, is removed as a link and never walked. **What it does not cover:** the path's ancestors are resolved by name at the call, so `<config dir>/extensions` itself swapped for a link before the call has the delete take the folder of that name inside the link's target. Where `<config dir>/extensions` is a link already, the delete goes where it leads: by design for a link the user made. That needs write access to the configuration folder, which a command with the user's rights has wherever nothing confines commands. **Tests not built with it** (the early review's L7): Windows tests of a junction and of a symbolic link met by `cineris ext add`, by `cineris ext remove` and by a write over a link, at the name and inside the folder; the breaks for `O_NONBLOCK` and for a handle that shares deletion are there. Found by the early review of step 28's `cineris ext add` (its L6), and left for step 32 by the maintainers, beside [a-file-is-opened-by-name-after-its-decision](a-file-is-opened-by-name-after-its-decision.md). **Recommendation:** delete relative to a held handle of the user's folder of extensions, opened once: on Linux from the folder's descriptor with `openat` and `unlinkat` (`AT_REMOVEDIR` for a folder), walking below it with `O_NOFOLLOW`; on Windows with `NtOpenFile` relative to the folder's handle and `FileDispositionInfoEx`, as `cineris_sandbox::unfollowed` opens names. | Step 32 (hardening pass) | Before the first release |
