| **A filter a confined program plants runs unconfined later.** A confined write is a sandbox escape when what it writes is later run unconfined. At `unrestricted` an extension's program with a write root covering the repository (`write = ["**"]`), or a confined shell command at `supervised` before the user moves the session to `unrestricted`, can write a `clean` filter into `.git/config` and a matching `.gitattributes`. The program's own look catches it: `.git/config` is a protected path, the turn stops and names it, and the harness's git after that program runs confined (since step 28). But nothing puts it back: in the next turn, the look after any unconfined shell command runs the session's git as it is at `unrestricted`, which runs the filter with the user's rights and the network, and so does the model's own `git status`. Found by the review of step 28's fixes; the same family as [the-harness-git-reads-the-repository-git-names-in-the-environment](the-harness-git-reads-the-repository-git-names-in-the-environment.md), the harness's git trusting what the repository says. **The options:** (1) put a protected change back before anything else runs, from the round's exact record of it, telling the user what was undone; (2) refuse write roots that cover the repository's git folder, for extensions and the session's confined commands alike, which would refuse `write = ["**"]`; (3) have the harness's own git refuse what a repository configures to run (filters, `fsmonitor`, hooks it would call), with overrides on its own command line (`-c filter.<name>.clean=` for each configured filter, `-c core.fsmonitor=false`), so that its looks never run a repository's program, whoever planted it. **Recommendation (must fix before release):** (3) for the harness's own git, which closes the harness's part whatever wrote the configuration, with (1) for a protected change found after a confined start, so that a command the user runs next does not meet it either. | Step 32 (hardening pass) | Before the first release |
