The provider transport checks a server's certificate with the platform's verifier, which on Windows fetches what the certificate names, its issuer and its revocation status, from any address and on the thread that polls the request.

| **What the platform's verifier does on Windows.** `reqwest` with no roots of its own checks a certificate with `rustls-platform-verifier`, which on Windows calls `CertGetCertificateChain` with revocation checking of the end certificate and a URL retrieval timeout of 10 s. Windows then fetches, through its own HTTP stack, with the system's resolver and proxy and to any address, the issuer a certificate's AIA names when its chain is incomplete and the OCSP responder and revocation list it names. Step 28's review of extensions' fetch found it there: a server a script chose could have the user's machine send requests to its loopback, its network or a cloud's metadata service, and a Windows runner showed the connection. The fetch client now checks with rustls against the system's roots (`tls_certs_only`, `rustls-native-certs`), fetching nothing; the provider transport keeps the platform's verifier, as the maintainers settled. **Who can choose the server.** Only the user: a provider's `base_url` is `[UserOnly]` (a project's value is ignored, with a warning), the import reads other clients' MCP servers and never a provider, no environment variable sets it, and no RPC method does; `cineris setup` writes it with the user. So no script or project can choose a certificate this verifier reads; someone who can answer for the provider's host on the network can, and then has the machine fetch what that certificate names, blind. **The second effect:** the retrieval runs inside rustls on the thread that polls the request, which in the core is the session's current-thread runtime, so for up to the 10 s it waits no interrupt, time limit or cancel of that thread lands; a provider's real certificate, whose revocation is fetched from its CA, may take part of that on any request that makes a connection. **Recommendation:** give the provider transport the fetch client's check (rustls against the system's roots), with the cost the fetch client took: no revocation, as on Linux already, and a provider that sends an incomplete chain fails, which none of the built-in ones does. Or keep the platform's verifier for its revocation checking and run the transport's connections on a thread of their own, so that a retrieval holds only them. | Step 32 (hardening pass) | Before the first release |
