| **No mouse through a pseudo-console.** Measured in step 25 on a hosted runner's pseudo-console (its own ConPTY, not the one Windows Terminal ships), with the terminal demo's `mouse` option: with modes 1000 and 1006 written by the program, ConPTY passed them on to the terminal, and the terminal's wheel report reached the program as typed text (`[<64;10;5M`); with the console's mouse input on and QuickEdit off, ConPTY asked the terminal itself for modes 1003 and 1006 in one sequence (try run 44370064135), any motion reported, which would reach the program the same way. So nothing asks for the mouse on Windows (`Capabilities::vt_mouse`) or wherever the win32 input mode is on (a Linux build under WSL or over ssh in Windows Terminal), and the keys do what the mouse does. **The likely mechanism** (read from the decoder, a reviewer's inference, not measured): the report comes as win32 input records with no virtual key, one per character, and the decoder drops the record whose character is the Escape and types the rest; the same would explain `function-keys-through-conpty`. **The wheel:** with no mouse mode, Windows Terminal's alternate scroll (mode 1007) is likely to send the wheel to the full screen as `Up` and `Down`, which reach the input's history and cursor, not the transcript (not measured). **The rule's other side** (inferred): it is the win32 input mode that decides, so a Linux build behind a pseudo-console with the mode not turned on would still ask for the mouse, and a terminal that knows the mode itself with no pseudo-console between (WezTerm by default, if it answers the query; not checked) loses the mouse it could have had. **At exit** (older than step 25): the input mode found at the start is put back, and where QuickEdit is off in the console's defaults that mode has the mouse flag on, so by the request measured the pseudo-console would ask the terminal for the mouse for the shell after the program leaves. **A first frame's window** (the review of step 25, by reading): the full screen asks for the mouse (`crates/cineris-term/src/terminal.rs`, lines 640-647 at the review's commit, `77ffbbcc`) before the win32 input mode's reply has come (lines 971-984), so a Linux build behind a pseudo-console can get one round trip of mouse reports as typed keys before the reply turns the request off. **The old console host,** with no pseudo-console, would give the program its mouse records, but no test has run there and nothing now asks it. **Recommendation:** first, have the decoder put win32 records with no virtual key back into the byte stream they stand for, which if the mechanism is right brings the mouse, the function keys' plain sequences and alternate scroll's arrows back as what they are; it can be shown on a hosted runner, which reproduces the typed reports; take care with pasted control characters. Then ask for the mouse again where a test shows the wheel arriving as a wheel, never as typed keys, and decide what the wheel does in the full screen when no mouse is asked for (turning 1007 off needs its state put back).
