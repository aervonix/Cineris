An extension's program is refused an argument with one of a list of characters a Windows code page's best fit turns into `"`, `\` or `-`; an argument is not converted as Windows converts it, so a character the list does not name gets through.

- Area: cineris-core
- Owner: step 32 (hardening pass)

| Item | Who | When |
|---|---|---|
| **An exec argument is checked against a list, not against the code page's best fit.** A program that reads its command line in the system's code page (an "ANSI" program) is given it converted from UTF-16 with a "best fit" for a character the code page lacks, which can make a `"` that ends the quoting, a `\` that escapes one, or a leading `-` that makes a word an option, where the permission engine was shown something else. Since step 28 `cineris.exec` refuses, on every system, an argument with one of the characters known to do so (`programs::LOOKALIKES`: U+FF02, U+02BA, U+FF3C, U+2216, U+00A5, U+20A9, U+00AD and U+FF0D, the last four added by the review of step 28's process starts), naming the argument and the character ([architecture/12-extensions.md](../architecture/12-extensions.md), "Windows"). The tables differ by code page and are not all published, so a list cannot be shown to be whole. **What a full check needs:** on Windows, convert each argument with `WideCharToMultiByte(CP_ACP, …)` with best fit on, as the program's C runtime will, and refuse one whose result gains an ASCII `"` or `\`, or begins with `-` where the argument did not; that needs Windows' own functions through FFI, which `cineris-core` does not have: `unsafe` code is allowed only in the modules [architecture/01-workspace.md](../architecture/01-workspace.md) names, none of them the core's. The list stays as the check on every system, where no conversion can be made. Found by the review of step 28's process starts. | Step 32 (hardening pass) | Before extensions run programs on Windows by default |
