A `cargo build` at the workspace's root builds `cineris` with the test hooks on, one of which shortens the dialogs' quiet time when a variable says so.

| **What a build of the whole workspace gives.** The test kit is a member of the workspace and asks for `cineris-base`'s `test-hooks` feature, and cargo builds one set of features for a build, so `cargo build` (or `cargo build --release`) at the root, with no `-p`, builds a `cineris` that carries the hooks ([testing-and-ci.md](../testing-and-ci.md), "A build of the whole workspace has the hooks"). In that binary: `CINERIS_TEST_READY_DIVISOR` divides a dialog's and the first run's readiness times by up to 100 (its quiet second, which keeps typed-ahead keys from answering a trust or an approval dialog, becomes 10 ms), and the process-start hook stops a process started under a test runner's `NEXTEST_TEST_NAME` that is not a `sys_` or `perf_` test's (since CI budgets II, [steps/ci-budgets-2/answered.md](../steps/ci-budgets-2/answered.md)); and, since step 28's third pull request, `CINERIS_TEST_MARK_FAILS` makes the harness's mark of its sessions' commands fail, which holds its sessions at `supervised` and so only narrows; and, since the step 25 fixes, `CINERIS_TEST_HOLD_CORE` makes a subcommand wait, up to 60 s, just before its core starts, until a file `go` appears in the folder it names, which only delays (a set variable makes such a binary seem to hang for that long). The switches of the Windows approving check's own tests, which could weaken it, are not hooks: they are read only under `#[cfg(test)]` in `cineris-sandbox`, so such a binary holds none of them. Each needs a variable in the binary's environment, and nothing in a user's environment sets either. **Where people are told to build:** the README's "Building from source" runs `cargo build` ("the workspace") and then `cargo xtask alias`, which builds `cineris` by its package and so replaces it with a binary without the hooks; a reader who stops after the first line runs one with them. No page says `cargo install`. Every build that is shipped or measured as shipped names its package (`cargo xtask size`, `startup`, `alias`, and step 34's `dist`), and `cargo xtask size` refuses a binary that holds the hooks. **Recommendation:** in step 34, build the binary to run from source by its package (`cargo build -p cineris-cli`, or `cargo xtask alias` alone) in the README and the installation instructions, and weigh a `default-members` that leaves the test kit and `xtask` out, which also changes what a bare `cargo test` at the root runs. | Step 34, its release built through `xtask` | With step 34's installation instructions |
