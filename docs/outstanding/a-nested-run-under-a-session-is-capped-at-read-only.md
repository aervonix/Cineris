A headless run of Cineris started by one of a session's commands runs at `read-only`, whatever it asks for, because it cannot know its parent session's level; a nested sub-task that needs to write cannot run until the parent's level reaches it in a form the model cannot raise.

| **What is open.** Since step 28's third pull request, Cineris's subcommands look at their own process tree, and one that runs under a session's command (Linux by its line of parents, Windows by the harness's job) refuses to approve or trust anything, and a headless run (`cineris -p`) there is capped at `read-only`: it says so on its output and in its result, naming this item. The cap is the narrowest, since the run cannot read its parent's level: an environment variable or an argument would be written by the model's own line, and the permission engine already refuses a line that runs Cineris with a `CINERIS_` variable set or a widening flag ([security.md](../security.md), section 3). So a nested sub-task that needs to write, or to run a command at `supervised`, does not run as it would. Under a session's command the run also refuses, or ignores, what would let it take more than a level: a project's trust (`--trust-project`), settings given on its line (`-c`, `--profile`), and configuration or state locations moved by the environment (`CINERIS_CONFIG`, `CINERIS_DATA_DIR`, `XDG_*`, `HOME`, `APPDATA`, `LOCALAPPDATA`, `USERPROFILE`), since a user's own hook runs where the engine would ask and a moved state directory would bring stores the model wrote. **What would close it** (the design step 28's review of the refusal proposed): the nested run takes the lower of the level it asks for and its parent's, and the parent's comes from the parent harness itself, never from the environment or a file, which the model controls where commands are not confined. The harness answers on a local channel only to a peer the kernel identifies (`SO_PEERCRED` and a pidfd on Linux; `GetNamedPipeClientProcessId` and a process handle on Windows), and only for a process its own records place in one of its sessions' command trees (a job per harness or per session on Windows; a cgroup, or a tree held as a subreaper, on Linux), not by the parent chain. Its answer is that session's current level and its configuration and state locations, which the child must match; an environment variable may only lower the level; with no answer the run is `read-only` and takes none of the trusting or configuration inputs. On Linux without confinement a process of the same user can still leave any tree (`systemd-run --user`, `ssh localhost`), so this stays a backstop beside the confinement.
