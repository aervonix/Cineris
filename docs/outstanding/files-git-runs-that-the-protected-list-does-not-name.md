| **Files that decide what runs later and that the protected list does not name.** The list is by name ([architecture/06-permissions-and-sandbox.md](../architecture/06-permissions-and-sandbox.md), "Protected paths"), so neither the engine nor the look after a sandboxed command protects a file that git's own configuration points to inside the workspace: a program named by `core.fsmonitor`, `diff.external`, `core.pager`, `core.sshCommand`, `credential.helper`, `core.editor`, `gpg.program` or a filter, or a file an `include.path` or `includeIf` reads. A confined command can rewrite such a file unseen, and it would run outside the sandbox at the user's next git command. The same holds for protected names inside a `sandbox.write` root outside the workspace, which the walk does not visit. **Narrowed by the fixes of step 26:** a main repository's `.git/commondir` and a `.cargo` made as a link are watched now (findings 3 and 4), and the harness's own git runs inside the sandbox, so a program the configuration names runs confined, not with the user's rights (finding 1). **Narrowed by the third security fix** ([../steps/security-fix-3/answered.md](../steps/security-fix-3/answered.md)): what the repository's configuration names for git to run or read (the folder `core.hooksPath` names, every configuration file it includes, every path a key that names a program gives) is read with one command of the harness's own git before and after every confined start and watched with the protected paths, by place, where it lies inside a write root, and what a confined start changes there is put back at once; the harness's own git runs inside the sandbox at every level where it enforces, so a program a file of this kind names runs confined for the harness. **What remains:** a program a key names by a bare word, found on the `PATH` of whichever git runs it (an activated `.venv/bin` in the workspace, which the harness's git keeps out of but a command's does not); what a protected link to a folder leads to (`.git/hooks` made a link to `hooks`), which `ext::protected` judges where it leads and the look reports as the link alone, not looking through it; and protected names inside a `sandbox.write` root outside the workspace, which the walk does not visit. Found by the independent reviews of step 26. **Recommendation:** read the repository's configuration (as git would, without running it) when a session starts and after a change to it, and add what it names inside the workspace to the watched list and to the engine's protected paths; walk the `sandbox.write` roots as the workspace is walked. **A partial clone's lazy fetch, from the git a command starts** (found at step 28's close, by the `release` example): git fetches an object a partial clone lacks from its promisor remote on its own, and a promisor remote's configuration can name the program that fetches, so that a plain read (`git log` of a missing commit) starts a program the repository chose. The harness's own git never does it: every git the harness starts itself (the base state's capture, the changes, the looks at the protected paths) is given `GIT_NO_LAZY_FETCH=1` (`cineris_base::git::GIT_ENV`). The model's shell and `cineris.exec` are not: both take their environment from `cineris_tools::shell::command_env`, whose fixed variables are `PAGER`, `GIT_PAGER`, `NO_COLOR`, `TERM` and `GIT_TERMINAL_PROMPT`, with `core.fsmonitor` turned off beside them, and not `GIT_NO_LAZY_FETCH`; the option `--no-lazy-fetch` needs git 2.44, newer than some systems ship, which is why the `release` example names it in its README's caveat rather than pass it. **What would close it:** `GIT_NO_LAZY_FETCH=1` among `command_env`'s fixed variables, which git before 2.44 ignores, so that no command's git fetches on its own, with a test that a command's environment holds it. | Step 32 (hardening pass) | Before the first release |
