| **The hold on a project's hooks for an unreadable trust store, as built in the fixes to step 28.** While the store cannot be read, none of a trusted project's hooks runs and each of its approved gating hooks fails ([12-extensions.md](../architecture/12-extensions.md), [security.md](../security.md) §3). Three things the second round of the fixes' pre-push review found, past its cap, so recorded and not built: (1) **The way back waits for the file to change.** A turn's look reads the store again only when its file's stamp changed; on Windows a stamp has no identity, so a store made readable again by a change of its permissions alone, with its time and size as they were, is not read again, and every gated call and prompt of the project is refused until the file changes or the session's configuration is reloaded whole. A store written by a newer build stays unreadable for the session, which fails closed as meant, and the notice does not name the reload. To settle: have a look read the store again while the project is held, or name the reload in the notice. (2) **Not held by a test:** the hold's branch of `prompt_gate_held`, and the second look at a project's trust once a queued hook has its place (`HookCommands::run`); both are behind the failing gate the loop is given, so a break of either alone lets nothing through. (3) **The test of an observer held back from a secret file** (`hook_trust::sys_a_users_hook_is_handed_a_secret_file_only_after_the_yes`) looks for the observer's file only after the session's close, which lets observers go: on a loaded machine its break could survive. To settle: wait for the observer's process to end before the close. | Step 32 (the hardening pass), found by the fixes to step 28 ([steps/step-28-fixes/answered.md](../steps/step-28-fixes/answered.md)) | Before the first release |
