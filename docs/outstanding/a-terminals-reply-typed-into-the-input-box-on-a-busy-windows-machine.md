On a busy Windows machine a reply from the terminal can come slower than the 500 ms the decoder waits for it, and then `[?0u` is typed into the input box as if the user had typed it; one CI flake, and a product bug.

- Area: cineris-term
- Owner: step 32
- Flaky: `cineris-cli::system tui::sys_a_session_is_resumed_with_its_history_drawn`
- Flaky: `cineris-cli::system tui::sys_a_turn_with_tools_runs_in_the_interface_and_the_terminal_is_put_back`

| Item | Who | When |
|---|---|---|
| **What happens.** At its start the program asks the terminal questions (its keyboard protocol, its device attributes), and the replies come back through ConPTY as input, about a key at a time. A reply's ESC that comes alone is held while the replies are due, for `REPLY_ESCAPE_WAIT` (500 ms, `cineris-term`'s `terminal.rs`) and within 3 s of the queries, so that the rest of the sequence can join it ([conpty.md](../conpty.md), "Wait for the rest of a reply"; the CI-budgets fix found the first case, a 50 ms wait, in `cineris-cli`'s trust-dialog test). **It came back:** in step 28's `try` run 44895882087, on a loaded Windows runner, `tui::sys_a_session_is_resumed_with_its_history_drawn` failed once in five rounds with `[?0u` typed into the input box: the rest of the reply came more than 500 ms after its ESC, which was then taken as the Escape key. **Why it is a product bug, not only a flaky test:** a user of Windows Terminal on a busy machine can have the same reply typed into their prompt, and send it. It is the same family as the decoder's corners step 32 already owes ([input-decoder-corners](input-decoder-corners.md)). **Recommendation:** make the decision depend on what came, not only on how long it took: while the replies are due, hold a lone ESC until the device attributes' reply, the last, has come or the 3 s after the queries have passed; and never type into the input a sequence that reads as a reply to a query the program sent (`CSI ? … u`, `CSI ? … c`) while the replies are due, wherever its ESC was taken. A test drives a reply whose ESC comes 1 s before the rest, on the fake clock. **Seen again** in `try` 45682764323 (step 28's script hooks, the Windows A/B, a hosted runner at 5 ms a process start), on `main`'s side, in round 1 of 5: `tui::sys_a_turn_with_tools_runs_in_the_interface_and_the_terminal_is_put_back` waited 30 s for the key's echo (`crates/cineris-testkit/src/pty.rs`, line 259), the prompt holding `[?0uw`, the reply typed before the key; this item took in the one opened for it then, `a-late-keyboard-reply-is-typed-into-the-prompt-on-windows`. | Step 32 | Before the first release |
