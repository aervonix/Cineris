Where nothing confines commands, anything that runs with the user's rights can write the stores that approve extensions and trust projects; only approvals signed with a key that needs a person present would keep the model from approving for itself there.

- Area: cineris-policy
- Owner: a step before step 34, the maintainers

| Item | Who | When |
|---|---|---|
| **What is open.** An extension is approved, and a project trusted, by what is written in the user's state directory (`pins.toml`, `trust.toml`) and configuration directory (`<config dir>/extensions/<name>`). Step 28's early review of `cineris ext add` found that wherever the model's code runs unconfined (on Windows, on Linux without Landlock, in a workspace that holds Cineris's own files, and at `unrestricted` on every system), a process with the user's rights can write those stores: a program that does not name them, the user's own checks and configured hooks running code the model wrote, an approved extension's programs. Step 28 narrows the plain routes: the permission engine refuses, at every level and whatever the rules, a command line that runs Cineris's approving subcommands; those subcommands refuse to approve when they run under a session's command; and scripted approval binds to the hash shown ([security.md](../security.md), sections 1 and 3). A wrapper script, a copied binary, or a direct write by unconfined code still gets past them. **The owner wants this closed before the first release.** **What would close it:** pins and trust signed with a key that needs a person present (Windows Hello's consent, a TPM-held key behind a PIN, or a prompt for the user's password where neither exists), every session trusting no unsigned entry; the trust question and `cineris ext add` sign at the person's yes. **What it costs:** scripted and headless approval stop working without a person, set-up needs the key made once, and a store written by an older build is unsigned and asks again. | A step before step 34, the maintainers | Before the first release |
