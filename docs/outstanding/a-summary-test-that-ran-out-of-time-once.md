| **A summary test that ran out of time once.** `cineris-agent`'s `context::a_summary_that_failed_in_the_background_is_asked_of_the_main_model_at_the_trigger` was reported slow at 2 s and then timed out at 18 s (its limit is 10 s) in one run of `cargo xtask ci --tiers` on the reference machine, otherwise idle. It has not been seen on CI. It printed nothing for itself: it used none of the test kit's waits, so the watch never started. **What was ruled out.** The test runs on the agent rig: one single-threaded runtime on the test's thread, the scripted provider, the fake clock, and every piece of blocking work run inline at moments the seed decides (`cineris_tools::InlineBlocking`); `ci` runs it under seed 0. On its path the loop has no timer and no real-time wait (no `tokio::time`, no sleep, no `recv_timeout`, no `Instant` compared with a deadline), the `fast` role's scripted failure ends its stream at once, and the compaction's retries are bounded (the background summary's failure is asked once more, of the main model). On the reference machine it passed 1,000 times under seeds 0 to 999 on two cores beside six busy loops (`cargo xtask stress -p cineris-agent --count 1000 --cores 2 --load 6`, about 23 ms a run), 3,000 times under seed 0 in CI's build profile (`cargo nextest run --cargo-profile ci`, 4 to 5 ms a run), and once under seed 0 in each of 161 scratch directories of different lengths (the workspace's path is in the prompt, so its length moves every estimate the loop makes from bytes). So with one seed the order is fixed, and a run of a few milliseconds that passed 10 s points at the process being held up rather than at the test. **What changed:** the agent rig's `World::run` now names itself to the test kit's watch (`cineris_testkit::watch::doing`), so a test of the rig still running at 8 s writes the report: what it was running, its seed, and each thread's state and wait channel on Linux, which tells a lost wake-up (the test's thread parked in the runtime) from a spin (running) and from a process the system held up (in the kernel, on the disk). **To settle:** at the next occurrence, read that report; if it shows the runtime parked or spinning, replay the seed it names with `CINERIS_TEST_SEED` and fix the race; if it shows the process held up by the system, or nothing recurs over the following steps, delete this item. | The maintainers | At the next occurrence, or after a few steps without one |
