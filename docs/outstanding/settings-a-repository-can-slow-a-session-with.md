| **Settings a repository can slow or stall a session with.** A key of the class `preference` applies from a project's file whatever the project is trusted with ([08-configuration.md](../architecture/08-configuration.md), "Trust and what a project may set"). The independent review of step 18 found `index.map_wait` among them, with no range, so a repository's file could make every epoch's first request wait for a whole pass; it is the user's alone now, at most a second. A search of the schema for the same mechanism found these, each a preference with no range: **`retry.backoff_base`** and **`retry.backoff_cap`** (a project can make the wait before each retry an hour), **`retry.max_wait`** (it can accept a provider's request to wait a day), **`retry.idle_timeout`** and **`retry.first_event_timeout`** (it can keep a session waiting on a silent stream for a day, or, set to a millisecond, fail every request), **`model.speed_wait`** (a request waits that long for a speed tier the user chose before falling back), **`model.speed_cooldown`** and **`model.speed_cooldown_min`** (how long a session stays at `standard` after a fallback, which slows it without stalling it), and **`context.background`** (off, a compaction waits for its summary at the trigger instead of having it ready). `shell.timeout` is bounded by `shell.max_timeout`, which is tighten-only. **Recommendation:** each a range of what a person would set, and the retry and timeout keys tighten-only or user-only, as `index.map_wait` now is; `context.background` user-only. Each is a change of what a repository may do, which the owner decides key by key. | The owner, with the next step on `cortex-config`, or step 32 | Before the first usable release |
