| **F5 sent through ConPTY did not act.** Step 24's hot reload system test (`cineris-cli::system tui::sys_a_look_and_a_binding_changed_in_the_file_reach_the_next_key`) bound `editor.submit` to `f5` and wrote F5 as its xterm sequence, `ESC [ 1 5 ~` (`\x1b[15~`), into the pseudo-console's input pipe with `cineris_testkit::pty::Session::send`. On Linux the application submitted the prompt; on a hosted Windows runner (try run 43995124400, every round) it never did: the test waited 30 s for the answer the submit would bring. What the application received is not known: no trace of its input was kept. The test now binds `ctrl+s`, one control character, and passes on Windows (try run 43997741947). **Most likely the harness, not the product:** [conpty.md](../conpty.md) records that a pseudo-console asks the terminal for win32 input records (Windows Terminal's win32 input mode, `CSI Vk ; Sc ; Uc ; Kd ; Cs ; Rc _`, which `cineris-term`'s decoder reads), that plain sequences after an escape are misread by ConPTY, and that Windows Terminal never sends them to one. A real Windows Terminal would send F5 as a win32 record (virtual key 116), which the decoder takes as F5; the test kit sent the xterm sequence instead. But no test has sent a function key as a win32 record through ConPTY, so the product's path for function keys on Windows is untested. **Recommendation:** the test kit's driver writes a named key as the win32 record a Windows Terminal would send (`Session::send_key`, on Windows only; the sequence elsewhere), and a system test sends F1 to F12 and the arrows that way and checks each reaches the application as itself; step 25 runs the Windows Terminal checklist's function-key line by hand, and keeps the input of a failed key in memory to say what arrived. | Step 25, which re-runs the Windows Terminal checklist and owns terminal quirks | Before the interactive alpha |
