| **What is open.** Since step 28's third pull request the application, like `cineris serve` and `cineris attach`, refuses to start under a session's command, and marks its own sessions' commands before it starts any process ([06-permissions-and-sandbox.md](../architecture/06-permissions-and-sandbox.md), "The harness's own approving commands"). A headless run does both on a thread of its own beside the rest of its start, its core waiting for them; the application does them inline, before its first frame. Measured with both trees on one hosted runner (`perf_start_to_first_frame_under_both_names`, a release build, three rounds of 30 runs), its first frame on Linux took 3.00 to 3.01 ms against `main`'s 2.81 to 2.87 ms, about 0.15 ms (5%) more, the ranges apart: the check and the mark, and the reads of the roots of skills and extensions through handles held open where they were resolved to. It is far under the first frame's budget ([performance-budgets.md](../performance-budgets.md), "Start-up"), and the maintainers kept it inline for that part rather than add a thread to a security path late in it. On Windows the same test's figures fell on the system timer's 15.6 ms steps on both trees, and showed nothing either way. **What would close it:** the application asks and marks on a thread of its own, as a headless run does, and draws its first frame meanwhile, starting no session, core or process until both are known, and refusing then if it runs under a session's command; with a review of that ordering, since it is the approving commands' guard. | Step 33 | Before the first release |
