On Windows an edit by `write` or `edit` gives a file the person made private its folder's access rules, so other users the folder admits can read it. Security, Windows only.

| **The editing tools write a private file open, on Windows.** The editing tools replace a file with `write_atomic` and its default options. On Linux that keeps the file's mode, so a private file stays private. On Windows the new file takes its folder's access rules, and rules set on the old file itself are not carried over: that is `write_atomic`'s documented behaviour, which a caller that writes a private file meets with `owner_only` (`cineris-base`'s `atomic`, and its test `an_owner_only_write_gives_the_file_the_list_new_or_existing`). So a file the person cut off from its folder and kept to themselves (`icacls … /inheritance:r`) is, after an edit, as open as its folder. The project profile's write (`cineris-knowledge`'s `project`) replaces a file the same way. Found by the step 25 fixes, which made a file a rewind creates again keep its mode, on Windows owner-only when the person had made it private ([../architecture/07-sessions-and-context.md](../architecture/07-sessions-and-context.md), "Snapshots and undo"), and left this, which is not a put-back, as it was. **Recommendation:** the editing tools pass `write_atomic` the mode they now read for the checkpoint (`AtomicWriteOptions::mode`, from `Existing::mode` in `cineris-tools`' `change.rs`): on Linux it changes nothing (the mode put back is the file's own), and on Windows a private file stays owner-only. One line, and a Windows test beside `a_private_file_made_again_on_windows_is_owner_only`. Changing `write_atomic`'s own default instead would change a documented behaviour every caller relies on. | Step 32 (hardening pass) | Before the first release |
