| **The terminal layer's waits start their timeout again.** The waits in `sys::unix::wait` and `sys::windows::wait` start their timeout again after an interrupted call, a stale wake or a key release, so a wait can run longer than asked. The escape's own wait, and since step 21 the wait for the rest of a paste, are bounded by `Terminal::next`, which counts from the last input. Since small fixes II a lone ESC held while the terminal's replies to its queries are due is bounded the same way, by `Terminal::next`'s own deadline: it is held until the replies end, and at the latest 3 s after the queries ([conpty.md](../conpty.md), "Wait for the rest of a reply", which also says what that costs a person's keys in those 3 s). **Left open by small fixes II:** a reply with a person's key typed inside it (`ESC [ ? 0`, then a key 50 ms or more later, then `u`) is still typed, since the key ends the sequence; replies that come as win32 input records, which a pseudo-console may give once the program has turned the win32 input mode on (inferred, not measured: [conpty.md](../conpty.md), "Mouse reports come as typed keys"), are keys from records and pass beside the check of raw `[` and `]`; and after the replies, a sequence split after its ESC by more than `ESCAPE_WAIT` (a mouse report over a slow link, while the mouse is on) is still the Escape key and typed text, as it always was: the Escape is a dialog's deny. Holding an ESC longer outside the start would make every Escape late, so that one is for a decision, not a fix. The two other corners step 20's review found (an over-long sequence that arrives split, and a paste whose end never comes) were settled in step 21 ([steps/21/answered.md](../steps/21/answered.md)). | Step 32 (hardening) | Before the first release |
