# Performance budgets

Numbers the product and the tooling must meet, how each is measured, and where each is checked automatically. They exist because "fast" is the first goal of the project and the second pillar of the [vision](vision.md), and a goal without a number erodes one reasonable-looking change at a time.

## How to read the budgets

- **Reference machines.** "Desktop" is the owner's desktop class of machine (a current 8-performance-core x86-64 CPU, Linux). "Runner" is a GitHub-hosted 4-core runner. Budgets are given for both where the difference matters, because the desktop number is what users feel and the runner number is what CI can check.
- **Measured basis.** Each budget lists what the throwaway prototypes measured, so it is clear how much room the real product has. The prototypes do far less than the product will. The budget is the limit, not the target.
- **Checks.** "PR" means a blocking pull-request check. "Main" means the non-blocking performance tier that runs after every merge and nightly, compares with stored baselines, and opens an issue on a miss. Hosted runners are noisy, so runner checks use generous limits and medians of several runs; they catch regressions of tens of percent, not single percents. `cargo xtask perf` runs the same measurements locally for exact work.
- **A miss is a bug.** A change that breaks a budget is fixed or reverted, or the budget is changed in this file with a reason, in the same pull request. Budgets are not loosened quietly.

**How.** A pseudo-terminal harness records the time from spawning the process to the first frame that shows the input box and hint row. Thirty runs, median and 95th percentile. The alias `cx` is the same file under a second name ([decisions/0013-naming.md](decisions/0013-naming.md)), so it has the same budget; the measurement is taken under both names.

**Rules that protect it.**

- Nothing on the start-up path reads the network, the session index, the statistics, the repository index or the model catalog's optional overlays.
- The HTTP client, the script engine, MCP servers and the repository index start in the background after the first frame. Since step 18 a session's index is made touching no file, and its first pass starts once the session's loop runs; `cortex-core`'s `index::the_index_is_not_touched_until_the_session_is_open` holds a gated index closed while the session opens (`cortex_testkit::Untouched`), and fails if the path that opens it used the index, or started a pass it did not wait for: the core says when the session's loop runs and when a pass starts, on the thread that starts it (since the fixes of the independent review of step 18, which started a pass while the session was put together and found the check passing). A general trace of what start-up opens is [outstanding](outstanding/what-start-up-opens-traced.md).
- Terminal capability queries never block the first frame.
- No file outside an allow-list is opened before the first frame. No test traces it yet: the check is [outstanding](outstanding/what-start-up-opens-traced.md), and only the index's part is held (above).

**Checked.** A coarse PR check: the system tier fails if the real binary's first frame takes more than five times the runner's budget (250 ms on Linux, 600 ms on Windows, in an unoptimised build: `crates/cortex-cli/tests/system/tui.rs`, every test that starts the application). Each of those tests starts a binary the runner has started before: its shell runs `cortex --version` first, so a cold runner's first start of an executable (an antivirus scan, its pages read from disk) is not counted; the cold start itself is the `startup` measurement's below, whose first run is not counted either. Main (both OSes) times `--version` and the headless run with `cargo xtask startup`; it does not time the interface's first frame, which is measured by hand or through `try` (below). The review of step 23 found this line claiming more (finding 12e).

**Measured in step 13b** with `cargo xtask startup BINARY --budget COLUMN`, which times `--version` under both names and a trivial headless run (`cortex -p hi`) from the start of the process to its request reaching a listener on the loopback interface, 30 runs each. The `main` workflow runs it on the `dist` binary of each OS after every merge and puts the table in the job's summary. Desktop, release build: `--version` 0.56 ms (`cx` 0.54 ms), the headless run 12.8 ms under either name, of 15 ms. The runners' numbers are in [steps/13b/ci.md](steps/13b/ci.md). The first measurement on a hosted Windows runner missed the headless budget, 212 ms against 100 ms, and showed why: about 180 ms was the session asking PowerShell 7 its version before its first request. The version is now kept in the state directory and asked off the start-up path ([architecture/05-tools.md](architecture/05-tools.md), "`shell`"); the numbers after are in the same record. `cargo xtask startup` keeps three rows that show where a headless run's time goes: without a session log, with a shell that starts fast, and with both. **A release build on hosted runners,** measured by the `try` workflow on the main branch at `c8753f4` (`-f command=startup -f profile=dist`, run 43512041506, 2026-11-13), median / 95th percentile of 30 runs: on Windows `--version` 7.02 / 7.63 ms of 50 (`cx` 7.05 / 7.58) and the headless run 17.32 / 20.33 ms of 100 (`cx` 16.68 / 17.69), 12.95 ms of it without a session log; on Linux `--version` 1.09 / 1.14 ms of 15 and the headless run 7.31 / 7.52 ms of 40. The overhead of starting a command in a release build on Windows is still not measured ([outstanding](outstanding/windows-start-overhead-in-release.md)).

**Measured in step 23** with the real application (`perf_start_to_first_frame_under_both_names` in `crates/cortex-cli/tests/system/tui.rs`, ignored, a release build through the pseudo-terminal, 30 runs under each name; `gh workflow run try --ref BRANCH -f os=both -f command="perf -p cortex-cli"` runs it on the runners): from the shell starting the binary to its first frame, median and 95th percentile, as `cortex` and as `cx`: on the desktop 1.80 / 2.21 ms and 1.95 / 2.07 ms; on a Linux runner 2.48 / 2.53 ms and 2.45 / 2.51 ms; on a Windows runner 10.2 / 21.8 ms and 10.0 / 21.7 ms. The harness's own git, run inside the sandbox while commands are confined, starts through the launcher: 0.78 ms added per git call (measured, step 26), two or three git calls a typical command (two `status`, a `diff` when `HEAD` moved), so about 1.6 to 2.3 ms a command, far under the 500 ms the look caps git at. |

One edit in the middle of a file of 10 KiB: 0.15 ms; of 1 MiB: 3.2 ms; of 16 MiB, the limit: 49 ms. That is the whole call: open, read, hash, match, hand the bytes to the checkpoint store, write the new file beside the old and rename it, hash what was left. **The flush to disk is on top,** and for a small file it is nearly all of the call: about 15 ms a write on the desktop's disk, so 15.6 ms, 22 ms and 113 ms for the three sizes. ## What is deliberately not budgeted

- **Model latency and tokens per second.** They belong to the provider. The harness shows them.
- **Verification time.** It is the project's own build and test time. It has limits the user sets ([architecture/15-efficiency.md](architecture/15-efficiency.md)), not a budget here. Speculative verification spends CPU early to save waiting: one run at a time, off until local statistics show it pays.
- **Parallel attempts and Coordinator teams.** They multiply the project's build cost by design, and run only on request with an estimate first. What the harness controls is how many commands run at once (by default no more than half the machine's cores) and the spend ([architecture/16-run-engine.md](architecture/16-run-engine.md), [architecture/17-coordinator.md](architecture/17-coordinator.md)).
