# ConPTY: facts a session needs before it tests a terminal on Windows

On Windows, a pseudo-terminal is a pseudo-console (ConPTY): the console host without its window, with pipes for its two ends. The test kit's driver (`cineris_testkit::pty::Session`, whose system half is `cineris_term::pty`) runs a program in one, and the terminal layer's system tests and `cargo xtask perf` run the demo there. Step 20 learned each fact below one CI round trip at a time. They are gathered here from its records ([steps/20/](steps/20/)), the terminal layer as built ([architecture/09-tui.md](architecture/09-tui.md), "The terminal layer as built (step 20)"), the open item on key latency ([outstanding/key-latency-over-conpty.md](outstanding/key-latency-over-conpty.md)) and the driver's code. The Windows facts that are not about terminals are in [AGENTS.md](../AGENTS.md).

## What the test's side sees

- **ConPTY re-renders.** The bytes the program writes do not reach the other end as written: ConPTY keeps a console buffer, and writes its own rendering of it to the output pipe. A frame may arrive split across reads, or two as one, and a synchronized update's brackets are not passed on (`cargo xtask perf` says "the terminal passed on no brackets (ConPTY re-renders)"). So a virtual terminal on the test's side checks what the screen shows, never the program's bytes. What speaks for the program on Windows is what it can be asked about itself: the terminal layer's system tests run a small shell that records the console's two modes and two code pages before and after, and says whether they match.
- **ConPTY asks the terminal for modes of its own.** It turns on focus events and Windows Terminal's win32 input mode for the console it runs, and draws with automatic wrap as it likes. On Windows those modes, read from the test's virtual terminal, say nothing about the program: the system tests check them on Linux only.
- **Input comes as win32 input records,** because ConPTY asked for them. Plain sequences that follow an Escape (`ESC x` for `Alt+x`, `ESC [1;5A`) are misread by ConPTY, and Windows Terminal never sends them to one as keys (a mouse report sent in answer to a mode passed on is one, and is typed: below): on Windows they are checked only in the decoder's unit tests, by sequence. A key outside the Basic Multilingual Plane arrives as two records, one for each half of its surrogate pair, and the decoder joins them.
- **Mouse reports come as typed keys.** Measured in step 25 with the terminal demo's `mouse` option: with modes 1000 and 1006 written by the program, ConPTY passes them on to the terminal, and the terminal's wheel report reached the program as typed text, `[<64;10;5M`, its last key `M` (try run 44357459502). With the console's mouse input on and QuickEdit off, ConPTY asks the terminal itself for modes 1003 and 1006, in one sequence, `ESC [ ? 1003 ; 1006 h` (try run 44370064135; the reports themselves were not sent). A test that looks for `?1003h` misses that request: read every parameter of every mode set (`cineris_testkit::vterm::modes_set`). Inferred, not measured: that the report comes as win32 input records with no virtual key, one per character, the Escape dropped, and that a function key sent as a plain sequence came the same way (`function-keys-through-conpty`). So nothing asks for the mouse on Windows, nor wherever the win32 input mode is on ([the-mouse-under-windows-terminal](outstanding/the-mouse-under-windows-terminal.md)). Windows Terminal sends keys as win32 records, and the test kit's `Session::send_key` does too.

## What the program must do

- **Turn virtual-terminal processing on.** A pseudo-console starts with `ENABLE_VIRTUAL_TERMINAL_PROCESSING` off, as the old console host has it. Without it the program's escape sequences are text, and the first frame never shows: that is what failed all three system tests when the break was made by hand ([steps/20/ci.md](steps/20/ci.md)). The system tests turn it off before they start the demo, on purpose.
- **Wait for the rest of a reply.** The terminal's replies to the queries the program sends at its start come back through the console as input, about a key at a time, and on a loaded runner a reply's ESC came more than the 50 ms the decoder gives a lone ESC before its `[`: the ESC was taken as the Escape key and `[?0u` typed into the input box (`cineris-cli`'s trust-dialog test, try run 44623384932). While the replies are due (the device attributes, the last of them, have not come, and for an ESC within 3 s of the queries), a lone ESC waits 500 ms for the rest of a sequence (`REPLY_ESCAPE_WAIT` in `cineris-term`; [steps/ci-budgets/answered.md](steps/ci-budgets/answered.md)).
- **Put the console back on every way out,** both modes and both code pages. When the input half was not put back, the shell child saw input mode `1f7` before and `3e8` after, on a normal exit, a panic and a Ctrl+Break event alike.

## What the driver must do

- **Give the child invalid standard handles.** The test runner has redirected the test process's own; a child that inherits them writes there and not to the console. The driver starts it with `STARTF_USESTDHANDLES` and `INVALID_HANDLE_VALUE` for all three, which makes it use the console, and inherits no handle.
- **A child takes its environment from the test process.** The driver refuses an environment of its own for a program in a pseudo-console (on Unix it adds one). Set what the child needs in its arguments.
- **The output ends when the console is closed, not when the program exits.** The reading thread sees `ERROR_BROKEN_PIPE` (109) once `ClosePseudoConsole` has run. Dropping the session closes the console and does not wait for the reader: waiting first would wait for ever.
- **A Ctrl+Break event goes to every process on the console,** the parent's too when it shares one. The process that sends it to a child it shares a console with ignores control events first (`cineris_term::pty::ignore_control_events`), or it is stopped with the child.

- **Closing the console is what a closed tab does.** `cineris_testkit::pty::Session::close_console` calls `ClosePseudoConsole` while the program runs: the console host sends every process on the console `CTRL_CLOSE_EVENT` and ends it when its handler returns, or after its own time. The call may wait for the handler, so the driver makes it on a thread of its own. The screen is gone with the console, so what the program says in its handler, and a shell of the test's that would say how the program ended, are never read: the shell is on the console too, and is ended by the event. A test of the application reads what it leaves outside the terminal (a request dropped, a command gone). The Unix twin is a hang-up (SIGHUP, then SIGCONT, to the program's process group), and a shell that should outlive it asks `ModeShell::surviving_hangup()`.

## Time

- **A key takes about 16 ms to show through ConPTY on a hosted runner,** at the median and 23 ms at the 99th percentile when the program is idle, against a budget of 2 ms. The program's own share, from reading the key to writing the frame, is 0.06 to 0.22 ms. The rest fits ConPTY passing output on at its own pace of about one frame in 16 ms. In Windows Terminal 1.24 on the reference machine's Windows host the prototype's idle echo took 0.19 ms, so this is the runner's older ConPTY. Until the owner decides ([the open item](outstanding/key-latency-over-conpty.md)), a test holds a key's echo under ConPTY to a coarse limit (250 ms for the terminal layer's demo, 500 ms for the real binary, which is built without optimisation in the blocking tiers), and `cargo xtask perf` reports the program's share beside the whole; the real application's share is `cineris-tui`'s `perf_a_keys_frame_through_the_loop`.
- **Frames are paced by the system's timer.** The demo's frames, written 60 times a second while streaming, came 18.2 ms apart at the 99th percentile against a limit of 18 ms, with none dropped: the wait for the next frame is the timer's, which the terminal layer does not set finer.
- **Every wait on the screen has a deadline** (`Session::wait_for`), long enough for a slow runner: Windows runners differ in speed by a factor of two ([AGENTS.md](../AGENTS.md), "Windows facts every session needs").
