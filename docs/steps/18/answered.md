# Answered in step 18, on 2026-11-15

Step 18 built the repository map: `cortex-index` (fifteen languages' extractors and an indentation fallback, the on-disk cache, passes under caps, ranking and the map), the map in a context epoch (`cortex-agent`), the `outline` tool (`cortex-tools`), and a session's index (`cortex-core`). These are the points its prompt asked it to settle, the four questions it put to the coordinator, who speaks for the owner, and the choices it made on the way.

## The six points

The coordinator approved all six as proposed on 2026-11-15.

| Point | Settled | Recorded in |

Two writers: the last replace wins, both valid. | The same; `cortex_index::cache` |

A pass cut short while listing writes nothing; one stopped while reading writes what it has. | 15-efficiency, "As built in step 18" |
| **6. ## Choices made on the way

| Choice | Why | Recorded in |
|---|---|---|
| **A pass holds one window of 512 listed files' outlines at a time**, writing each window's records out before the next is read, and the cache's summary line comes after its records. | The first version held every outline of a cold pass until the cache was written: a cold pass of 20,000 files peaked at 33.5 MB resident and left 24 MB with the allocator. With windows: 13.1 MB at the peak and 7.1 MB after, which later passes reuse. | [performance-budgets.md](../../performance-budgets.md), "Memory"; `cortex_index::pass` |
| **The memory check is the process's resident memory, on Linux,** not a count of the heap. | Counting the heap byte for byte needs an allocator of the test's own, which is `unsafe` code, and the workspace allows that in three named modules only. Twenty more passes and maps must not grow the resident memory after a warm-up. | `cortex-index`'s `memory::passes_and_maps_leave_nothing_behind` |
| **`[index]` is declared:** `map`, `map_tokens`, `map_wait`, `max_files`, `max_file_bytes`, `pass_time`. The budget and the caps are tighten-only; the caps take effect at a restart. | The section was reserved for this step. The map's budget was planned under `[adapt]`; it sits with the map. | [architecture/08-configuration.md](../../architecture/08-configuration.md); [configuration/reference.md](../../configuration/reference.md) |
| **The core's test rig has no index unless a test asks** (`CoreOptions::repo_index`). | A late map arrives at a boundary of its own timing, which tests of exact requests do not want. The real binary's system tests run with the index on. | `crates/cortex-core/tests/it/main.rs` |
| **A directory's outline gives each file at most 30 definitions.** | One large file in path order would otherwise take the whole result and leave the directory's other files out. | 05, "`outline`" |
| **The toolbox the binary sends now has `outline`**, and its recorded fixtures do not. | A recording is a paid call; the sixth tooling step recorded them again ([answered](../tooling-6/answered.md)). The system test that compares them warns and does not fail. | — |

**Raised (rule 11): the warm map on hosted Windows runners.** The budget is 150 ms for a warm repository map. On the desktop a warm pass over 20,000 files and the map take 57 ms; on hosted Windows runners they took 149.5, 157.5 and 182.8 ms in three runs ([ci.md](ci.md)). The listing is most of it there, and a third of the whole is looking for `.gitignore` and `.ignore` in each directory, which the ignore rules need (the same rules as `search` and `list`). With `index.map_wait` at 150 ms, the first prompt of a Windows session in a tree that size would often go without the map, which then comes at the turn's next boundary. Recommendation, in order: (1) **list on several threads** (the `ignore` crate's parallel walker), sorting the listing after as now, and falling back to the one-thread walk in name order when the listing reaches its cap, so that a cut listing stays the same on every machine: no change to what the map says, and the looks for ignore files, a third of the time, spread over four threads; (2) or **answer the first prompt's map from the pass that ran when the session opened**, if no turn has run since, and start a pass after it for the next epoch: the map at once, but a change made outside the session between opening it and the first prompt is not in the first epoch's map (`outline` and `read` always see the file as it is); (3) or a Windows figure for the budget, which is the owner's to set. Step 18 can make (1) or (2) before it merges.

**The coordinator chose (1)**, with (2) only if (1) was not enough; at most four threads and never more than half the cores; a test that the two listings are equal with nested ignore files on both systems, one of the cut at the cap, and one that a pass on several threads still gives way; breaks of the listing left unsorted, of the cap not made again on one thread and of a nested ignore file missed; stress at two tests at a time; a focused review of the change alone; and measurements again on hosted Windows. **Done:** the listing runs with the walker `search` and `list` use, on the pass's threads (one included), and is sorted after; one that meets its cap is made again on one thread in name order, and a workspace whose cache says its last listing met the cap is listed in name order at once; the path order compares bytes with `/` as the least, which needs no split of the paths. Tests: `index::the_listing_on_several_threads_is_the_listing_on_one` (on 1, 2 and 4 threads, byte for byte, passed on Windows in `try` run 43704770339), `index::a_listing_at_its_cap_is_cut_in_name_order_on_any_number_of_threads`, `index::a_listing_on_several_threads_gives_way_at_each_threads_next_entry`, the time-limit test on 1 and 4 threads, and `tree_order::property_the_path_order_is_the_order_name_by_name`. Seven breaks more, and six moved to the code as it is now, all caught; `cortex-index` passed 200 stress repeats at two tests at a time. **The focused review** of the change found no wrong cache, and these, each fixed: on a file system that does not tell case apart the walk on one thread honoured a `.GITIGNORE` that the walk on threads (and `search` and `list`) passes over, so the listing depended on the cores (the walker of threads is now used on one thread too, and the walk in name order only at the cap, where the difference is written down; `index::an_ignore_file_is_known_by_its_exact_name_on_any_number_of_threads`, and `walk::tests::the_walk_in_name_order_lists_what_the_walk_on_threads_lists` for the two walkers below the cap); the knowledge that a listing meets its cap was held in memory, so each session's first pass walked twice (it is read from the cache; the cap test counts the gate's questions on the second pass); a thread asks the gate about a directory's subdirectories between two looks at whether to give way (written down); the break of a nested ignore file did not break one (it turns `.gitignore` off on the walk on threads now); the test tree was made in name order, which a file system could give back (it is made out of order); the comment of a test that relied on the order of the walk. **The warm map on hosted Windows runners is now 84.6 to 112.6 ms** (three runs), and 37.6 ms on the desktop, so (2) was not made.

**Raised (rule 11): memory after indexing.** The done criterion says memory after indexing returns to the idle level. Measured by the process's resident memory, it does not quite: a cold pass of 20,000 files takes a process from 3.9 MB to 13.1 MB and leaves 7.1 MB, which the allocator keeps for later passes (twenty more passes and maps grow it by nothing). The index itself holds nothing; what stays is glibc's free memory. Recommendation: hold the index to "no growth over repeated use", which the test checks, and leave returning the allocator's memory to the system (`malloc_trim`, which needs `unsafe` and `libc` in `cortex-index`) to step 33's memory pass if the idle budget needs it.
