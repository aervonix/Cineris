# Answered in the stop-ends-turn step, on 2026-11-21

A small step of its own outside the numbered steps, which the owner approved on 2026-11-21: a change to the agent loop that closes the open item `a-stopped-host-call-does-not-end-the-turn`. The build plan's "Must not change: the loop" was step 28's constraint, not a rule for every step, so the build plan is unchanged. The design is in [03-agent-loop.md](../../architecture/03-agent-loop.md), "Tool rounds", "A stop from a call's run".

## What was open

The item's text, as it stood:

> **A turn stopped during a call's run ends only at its next call.** Since step 28, an extension's host call answered with a stop ends the script's call at once and stops its turn (`EnginePolicy::stop_turn`, as a confined command that changed protected paths does): every call of the turn not yet started is answered with the stop, no call with side effects runs after it, and when one follows the turn ends `denied` without the model being asked again. But in the loop only the policy's decision of a round's own call ends a round with a stop, never a tool's result: when the stopped call was the last of its response, **the model is asked once more** (one more paid request), and a reply of text alone ends the turn `completed`, **the streamed `turn.completed` saying so**. The headless result is held to the denial (since step 28, settled by the maintainers): with `--fail-on-denial` and a denial recorded, a turn that completed is reported `denied` and the run exits 6. The shell's stop after protected paths changed has the same gap, and records no denial, so its turn is reported as it ended. **What would close it:** the round honouring a tool result marked as a stop as it honours the policy's (a `ToolResult` mark in `cineris-tools`, kept through the output bounding and the wrappers; `Round::finished` setting the round's stop and marking later calls not run), which closes both stops.

## What was built

- **The mark.** `ToolResult::stopping_turn(reason)` marks a result as one whose run stopped its turn, and `ToolResult::turn_stop()` reads it. It is a field of the result, so everything that adds to a result (`with_part`, `with_payload`, `with_artifact`) and the output policy (`bounded_with`) keep it, whatever the outcome: a command that changed a protected path may itself have succeeded. No wrapper builds a new result from an old one: `StopsWithTurn`, `RecordingShell`, the registry's `tool_call` (whose `execute_produced` bounds the inner result, which the outer `execute` then returns as it is) and the extension tool all hand the result on.
- **The round.** `Round::finished` reads the mark before the result becomes an item, and ends the round at that call through `Round::stop_at`, the tail of `Round::stop`, which both now share: what the model wrote after it does not start, and the open question is withdrawn. The call keeps its own result. `Round::adopt` does the same for a run kept from a response that was thrown away, when the response sent again uses it. The loop is unchanged: it already ends a round whose `Round::stopped` is set with the outcome `denied`, the error `permission_denied`, and no further request, and `turn.completed` carries that.
- **What a later call is told.** Before, after a run-stop, the policy decided every call not yet started again and answered it with the stop, so a later call got "This call was not allowed to run, and the turn was stopped. Reason: …" as a denial. The round's own tail would have told it the policy's stop text, "did not run" as an interruption, whenever the run's report reached the round before the next decision. So the round remembers which kind of stop came first (`Stopped::by_a_run`), and after a run-stop gives a later call that same denial (`Round::kept_from_running`). The first call after the stopped one is told what it was told before this step, in either order. When the mark comes first, the calls after that one are told the same denial; before, they were told the policy's stop text, "did not run", which is still what they are told when the policy's decision again reaches a later call first (found by the reviews).
- **Both stops set the mark.** The shell (`RecordingShell::run_by`): a confined command that changed protected paths, or whose look stopped short; a command that left a process the kill could not clear; and the command refused because a protected path changed from outside since the last look (`RecordingShell::continuity`). The extension tool (`LoadedExtension::call_tool`): every `CallError::Stopped`, which is every host call's stop, `CallHost::decide`'s `Verdict::Stop` among them, and the stops of an extension's program (`ext::exec`), which end the script's call the same way.

The functions of the round that changed: `Round::stop` (its tail moved to `Round::stop_at`), `Round::stop_at` and `Round::kept_from_running` (new), `Round::finished`, `Round::adopt`, `Round::planned` and `Round::ask_next` (each gives a call the stop keeps from running its result through `kept_from_running`).

## The headless stopgap

Step 28's stopgap (`report::held_to_its_denial`) reports a turn that completed as `denied`, with exit 6, when `--fail-on-denial` is set and a denial was recorded. It stays, because one path is left where it matters: a call refused under `--fail-on-denial` in a response that then fails part-way and is sent again. The stop goes with that response (`Round::void`; [03-agent-loop.md](../../architecture/03-agent-loop.md), "Tool rounds"), the policy is shown the call again only if the next response makes it, and a next response of text alone completes the turn, with the denial recorded. The agent test `run_stops::a_stop_over_a_call_of_a_response_sent_again_goes_with_that_response` shows the loop's side of that path. The stopgap's comments, its test's and [10-headless.md](../../architecture/10-headless.md) now name it, in place of the host call. Closing that path too would change what a stop over a thrown-away response does, which is outside this step.

## Tests

In the agent rig (`crates/cineris-agent/tests/it/run_stops.rs`), whose fake tools mark a result with a `stop` argument:

- the stopped call last in its response: one request, `remaining` 1, the turn and the streamed `turn.completed` `denied` with the stop's reason, the call's own result kept, and the next prompt answered with a whole history;
- a stop in the middle of a response: the read before it runs, the write and the command after it do not, each gets the denial, no request follows;
- a stop from a call that changes nothing (a command found to only read is still looked around for protected paths): a write waiting for it does not run. After a call that may have changed the file system the round decides every later call again anyway, which hid the round's own stop from the first test of a stop in the middle (found by `mutate`);
- an ordinary failing result, in the middle and last: the calls after it run, and the model is asked again;
- a kept run with the mark, used by the response sent again: the turn ends `denied`;
- the stopgap's path above.

In the core: `extensions::a_host_call_nobody_can_answer_as_the_last_call_ends_the_turn_without_asking_again` (the extension's stop as the last call: `denied`, the response after it left unasked); `sandbox::sys_a_protected_path_a_command_changes_stops_the_turn_and_undo_puts_it_back` and `sandbox::sys_a_change_between_two_commands_is_found_and_stops_the_turn` now count the responses left (the shell's two stops as the last call, on Linux where the sandbox enforces); `adversary::sys_an_adversarial_command_reaches_only_what_it_may` had held the gap as the truth, a completed turn after a command that made a git hook, and now holds `denied`. In the binary: `runs::sys_exit_6_when_an_extensions_host_call_stops_the_last_call_under_fail_on_denial`, a headless run whose extension's host call nobody can answer: exit 6, `outcome` `denied`, one request. In `cineris-tools`, a unit test that the mark survives what adds to a result and the bounding.

Each fails with the change taken out: the breaks are in `mutations/stop-ends-turn.breaks`. Older breaks moved with the code:

- step 7's `call-after-the-stop-is-planned-and-runs`: the line it changes was rewritten;
- step 26's `a-protected-change-does-not-stop-the-turn`: its test no longer sees the policy's stop alone, since the command's mark now ends the round too. The policy's stop still matters for a project's check, which the verifier runs outside any round and which reads it, so the break is now caught by `verify::sys_a_check_that_changes_a_protected_path_stops_the_turn_and_undo_puts_it_back`;
- five breaks of the policy's side of a stop are marked `expect: survives`, each naming the mark as the guard that now covers it (found by the review, by running them): step 28's `a-stopped-host-call-leaves-the-turn-going` and `exec-protected-change-does-not-stop-the-turn`, step 12's `a-stop-of-the-turn-moves-no-count`, and step 26's `a-stopped-turn-goes-on` and `a-stopped-turn-runs-another-command`. The first four were caught because the model was asked again and its next call was stopped, which no longer happens; the guards stay as a second line. The fifth, `StopsWithTurn`'s refusal, was already caught by no test before this step: the test it named passed with it made (found by the second review, by running it at the branch's base). It is the only guard of a call already started when another call's run stops the turn, and a test of it can be written now, with `cineris_agent::BEFORE_A_CALL_RUNS`. For an extension's tool, which runs alone, nothing can start between the stop and the round's taking of the result. For a command found to only read, which runs beside other calls that only read, a call could start in that window. No test holds a command there without a point to wait at inside `RecordingShell`, which security fix 3 is rewriting: open as [the-policys-guards-of-a-stop-from-a-run-have-no-test](../../outstanding/the-policys-guards-of-a-stop-from-a-run-have-no-test.md).

The command that left a process the kill could not clear has no test that can make one, and so no break of its mark.

## Left as they are

From the review, each low and reasoned rather than shown:

- **The turn's error says "A tool call was not allowed"** for a stop from a call's run too, where the call was allowed and ran. The loop's message is the policy's stop's, unchanged: the outcome is what the spec asked to match, and the loop's code is step 28's next part's to change.
- **A task that panics after its run stopped the turn** reports an error with no mark, and the turn goes on to another request, as before this step. It needs a bug in a tool.
- **A kept run whose stop the next response does not use** loses it with the response (`Round::void`). Only a run of a call with no side effects (one that may start while a response streams) is kept, and neither stop comes from one today; the code says so where it drops the stop.
