# Answered in CI budgets II, on 2026-11-26

A fix outside the numbered steps, given by the maintainers: on a slow hosted Windows runner `main`'s own tests were close to failing pull requests that did not cause it. On a runner at 8 ms a process start `main` at `42c90dcc` read Windows' integration tier at 55.2 s of its 40 (a failure past 60) and the system tier at 91.6 s of its 90 (`try` 45695681459), and on a usual runner (6 ms) `main`'s own CI read the integration tier at 43.8 s (run 45721643017). This record says where a Windows session's time goes, what was changed at its cause, and what that did to the tiers and to the test job. The CI times are in [ci.md](ci.md).

## Where a Windows session's time goes

**How it was measured.** Timing points along the core's path (a session's open, its turns, the log's birth, the rig's world), on an experiment branch that is not merged, read by an ignored test that runs a child process forty times over, as every test of CI is a process of its own: each child times a world, a core, a session's open, two turns, the close and the drops, then the same in a second world of the same process, then a second session of that world's core, and says each stretch between two points. The table gives medians of the forty, on a hosted runner of each system, in a release build (`try` 45725495734; the same run's CI build is `try` 45725475934). The parent test, with the points, was also run on Linux under `strace -f` with each point marked by a failing look at `/zz-lap/<name>`, which counts the system calls of each stretch. The cost of each call on its own was measured by a throwaway test that times each one 400 times in a directory as deep as a core test's workspace (`try` 45726487886, release). Everything compared below is one system against the other, each from its own runner; a claim that a change saved time rests on a one-runner A/B, in the next sections.

**The cause is the path resolver's walk.** A session's open walks 29 paths ([cineris-base's `PathResolver`](../../../crates/cineris-base/src/path/resolve.rs)): the workspace and the home folder in each place, each project file of each load of the configuration, and each folder the engine's parts resolve. A walk looks at every name of a path from the drive's root, without following it, so that no link is followed that the rules have not seen ([security.md](../../security.md), section 7), and then asks the system for the path's own spelling (`canonicalize`). On a hosted runner a test's workspace is nine names deep (`D:\a\_temp\tmp\cineris-core-it-N\<test>\work\app`), and each name was a `symlink_metadata`, which on Windows opens a handle, reads two of the file's records and closes it. Timed in place, on a Windows runner in a release build (`try` 45727050579), the 29 walks of an open took **2.67 ms in their names and 1.02 ms in their `canonicalize`: 3.69 ms of an open of 5.97 ms** on that runner, against about 0.2 ms on Linux. The configuration's loads, the trust look, the engine's parts and each turn's look at the files are each mostly walks; the rest of the difference is CPU (the tools, about 2.5 times slower there) and private files (below).

**What else was checked, and is not the cause.** The candidates the maintainers named, each against the numbers above:

- **Thread or runtime start-up per session:** the open starts three threads (three `clone3` in the trace: two as the agent's store opens, one at the assembly's end), and no runtime: the session's loop is a task on the core's. The store's opening took 0.05 ms on Windows against 0.02 ms on Linux, and the assembly's last stretch 0.43 against 0.05 ms, most of it a walk: not the cause.
- **The state directory's locks:** none is taken in the open; the log's lock is taken at its birth, in the first turn (0.14 ms of the birth on Windows).
- **The registry and the environment:** the open reads neither; the environment was read when the core started.
- **The extensions' finding with no extension:** off the path that opens the session (step 28), and step 28 measured it at 4.6 to 10.4 µs on the reference machine.
- **Defender scanning a new file:** the open writes no file; it makes one folder, the session's temporary one (0.38 ms, 1.79 ms for a process's first, which includes the first look-up of the user's security identifier). The first turn writes the log and the index, the birth's 3.04 ms on Windows against 1.02 ms on Linux, which is what an owner-only file costs there (the table above).
- **A process:** the open starts none (the rig hands its core a shell; the product asks its version off the open path).

## What was changed

1. **The walk looks at a name by its attributes on Windows** (`cineris-base`'s `path::is_link` and the resolver's `is_dir`; `private::attributes` and `private::on_a_fixed_disk`, the two new `unsafe` calls, in [decision 0029](../../decisions/0029-owner-only-files-on-windows.md)'s module, amended for them). `GetFileAttributesW` opens nothing and does not follow a link at the end of the path. **Only on a fixed disk:** on a share or a mapped network drive the attributes may be the network client's from an earlier look (an SMB client keeps them up to ten seconds), so there, and on any drive Windows does not report as a fixed disk, the name is opened as before (`GetDriveTypeW`, once a drive letter; the early review's finding). A name whose attributes show no reparse point is no link, which is `symlink_metadata`'s answer for it; a name that is not there is not there to both, with an error of the same kind; a reparse point, and a name whose attributes cannot be read for any other reason, are looked at by `symlink_metadata` as before, so that a link is still told by its tag and a junction, a symbolic link or a placeholder of a cloud file system is what it was. The walk's order, its share checks before anything is asked of the file system, its `canonicalize` and every refusal are as they were. **A user's session open, in a release build, both trees on one Windows runner** (`try` 45728026037, the median of three rounds of forty processes each): **a steady open 8.78 to 5.97 ms (−32%)**, a process's first open 11.46 to 8.82 ms, the walks' looks at their names 4.24 to 1.46 ms an open; each turn about 0.5 ms less. On Linux nothing changes: the look is `symlink_metadata` there.
2. **The same look for the other walks of a path's names** that ask each name whether it is a link: the program search's (`program::places_on_the_way`, each program the harness starts itself), the checkpoints' (`reached_through_a_link`, each file a tool writes), the protected paths' look (`first_link_on_the_way`, `through_a_link`) and the snapshots' (`snapshot::through_a_link`); and `private::create_dir_all`'s look at the folders that exist, several times a turn. The other look-ups found by the same search ask something else (whether a `.git` or a `.cineris` is there, whose a folder is, what a file is) and are listed in [the item](../../outstanding/a-sessions-open-walks-the-same-paths-again.md) as follow-ups.
3. **The core and server rigs find Windows PowerShell where Windows keeps it** (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, one look) before they search `PATH`, which looked in each of a hosted runner's dozens of folders: 1.9 ms of every core test's process on a Windows runner. On a runner both find the same program; elsewhere the search is as before.
4. **A test's directories are left in the test job's own runs on a GitHub-hosted runner** (`cineris_testkit::scratch::leaves_directories`: `CINERIS_TESTKIT_KEEP_DIRECTORIES=1`, which the blocking test job sets and `cargo xtask try` sets for its runs of the tests and its A/Bs, and the runner's own `RUNNER_ENVIRONMENT=github-hosted`): its disk goes with the job, and removing a core world's directories took 2.7 ms of every core test on Windows (1.3 ms on Linux). A `Scratch` and the core rig's world leave them there; what an earlier run there left under the same name is moved aside in one rename, so that an A/B's later rounds pay no more than its first. On a desk, on a self-hosted runner, and in a run that repeats the tests (`stress`, `mutate`, which would fill the runner's disk; the full review's finding) they are removed as before. **What the removal caught:** nothing. Both removals ignored their errors (`let _ = remove_dir_all(…)`, and `Scratch`'s `remove_all`), so a handle the product leaked, which makes a delete fail on Windows, failed no test before; no check is lost, and none is moved elsewhere.

**The tiers, both trees on one Windows runner** (`try` 45730634759, the median of three rounds, at 5 to 6 ms a process start; [ci.md](ci.md)): tier 1 12.7 to 11.6 s, **tier 2 36.7 to 31.2 s (−5.6 s, `cineris-core` −3.14 s)**, tier 3 62.5 to 62.8 s. The first change alone, on another runner at 6 ms (`try` 45728496329): tier 2 44.6 to 43.5 s.
