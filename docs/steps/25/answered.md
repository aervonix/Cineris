### 2. The full-screen presenter

**What it keeps.** Today the application keeps every committed part as rendered lines for the viewer (`App`'s kept `Committed` parts, step 23), in both presenters. That changes to **the finished blocks themselves**: a new `transcript::Kept`, an append-only list of the blocks `Transcript::commit_parts` has finished with (each block as it was drawn, with whether a blank row stood before it, the turn it belongs to, and for a round whether it is open in this view), and nothing rendered. Both the viewer and the full-screen presenter draw from it:

- **Rendered lines are kept only around the viewport** (09-tui, "Rendering cost control"): a cache of each block's rows at the current width, for the blocks within two screens of what is shown, dropped for the rest after each frame, and dropped whole on a change of width, theme or glyphs. A frame costs the rows on the screen, not the session's length.
- **A finished answer keeps its markdown source** (`Markdown` gains a mode that keeps it; the inline presenter does not use it) and the colours its code lines were committed with, by code block and line. It is drawn again with `Markdown::render` at the new width, which takes those colours ("Re-wrapping", below).
- **A finished round keeps what it shows**, with one bound: a command's output kept for a closed box is its last 16 KiB; opening a box whose output was cut asks the core for the whole of it (`session/artifact`, a read), and shows `reading…` in the box until it comes, as the review panel's check output does. Without the bound a session of commands that each print 64 KiB (what a running command keeps) holds 38 MB after 200 turns in its rounds alone, before anything is drawn. **The 16 KiB is to confirm by measurement**, against the 200-turn budgets.
- **The inline presenter is unchanged:** it still commits the lines `commit_parts` gives at the width of the time, and draws its live region as now. Only what is kept beside it changes, from lines to blocks, which is less memory, not more.
- **The budget:** 80 MB resident after 200 turns, 40 MB inline. A turn's blocks are a few kilobytes of text (the prompt, the reasoning summary, the answer's source, the round's call lines, diffs and the kept output); 200 turns of a realistic mix is estimated at 4 to 10 MB kept, the render cache at under 1 MB. **To confirm by measurement:** the long-session test (point 2, "Memory") measures both presenters on the shipped musl `dist` build in a workspace of the real-code corpus, as step 23 asked.

**How a frame is drawn.** A new presenter in `cortex-term`, `Full` (beside `Inline`), draws a whole screen of rows on the alternate screen: one write, inside a synchronized update; only the rows that differ from the last frame, each placed with a cursor move and followed by an erase to the line's end; the cursor placed at the editor's insertion point last, or hidden. A resize, `Ctrl+L` and a resumption draw every row. It holds no state but the rows on the screen, and never clears and then redraws. The viewer moves onto it from `Terminal::draw_screen`, which writes every row every frame; `draw_screen` is then removed (a change to `cortex-term`'s public API, recorded). The layout, top to bottom:

1. **The transcript area:** the kept blocks and the transcript's live rows (the streaming tail, the reasoning rows, the running round's box) as one column of rows, of which a window is shown.
2. **The panels' block,** when panels are open and the window is narrower than the width at which they move beside the transcript (below): exactly as inline, with step 24's limit.
3. **The bottom:** the input box with its hint row or menu, or a dialog, exactly as inline.

The bottom and the panels are made by the same code as inline (`App::frame` is split so that both presenters call one function for them), so they look the same in both.

**Scrolling while an answer streams.** The view **follows the end** while the transcript's last row is shown, which it is from the start and after each prompt is sent. **Any move up stops following** (`PageUp`, `Shift+Up`, the wheel, a search's jump): what streams then grows below without moving the view, and the transcript area's last row says so, dim: `↓ 24 new rows · pgdn goes to the end`. Following starts again when the view reaches the end (`PageDown` or the wheel down to it), when a prompt is sent, and when a dialog opens (it asks about what just happened, at the end). The view is held by its first row's block and the row inside it, not by a row number, so a block that changes above it (a round's box committed in place of its live rows) does not move it.

**Re-wrapping on resize.** A change of width drops the render cache; the next frame draws the blocks around the view at the new width, keeping the same block and row at the top (a row inside a block that now wraps differently is kept by its share of the block). Nothing is drawn at the old width again. **Code is highlighted again at the new width** ([highlighted-code-drawn-again](../../outstanding/highlighted-code-drawn-again.md)): a finished answer keeps the colours its code was committed with, which are byte ranges of each source line and so do not depend on the width; `Markdown::render` is given them. A code line that was committed plain (its colours were late) is handed to the highlighter as a whole block, by its language and text, when it is first drawn again; it is drawn plain until the worker's answer comes, whose waker asks for a frame. `Markdown::render` never waits for the worker. The same holds in the viewer, which re-wraps too from now on.

**Search** (screen F6). `Ctrl+F` opens a search row in the hint row's place: what is typed after `search`, laid out through `editor::cluster::width` and `drawn`, then the count (`2 of 3`) and the keys. It searches as it is typed, from the bottom of the view upward (newest first), ignoring case, in the text of the rows as they are drawn at the current width; every match on the screen is drawn reversed, the current one in the accent. `Enter` or `Up` goes to the next older match, `Down` to the newer, `Esc` ends the search and leaves the view where it is (not following). **A match inside a closed box:** the search looks in every box's whole detail, as the box draws it open; when the current match is inside a closed box, that box is drawn open while the match is current, its bottom border saying `opened by the search · enter keeps it open`, and closes again when the search moves on or ends, unless `Enter` was pressed on it. A paste goes to the search row while it is open, on one line. **The cost** of the first query of a long session is drawing every block once at the width (each kept in the cache only while near the view): **to confirm by measurement** on the 200-turn session; if it passes a frame's 16 ms it is done in slices across frames, with `searching…` shown.

**Panels beside the transcript** (screen F5). From **140 columns** the panels sit in a column of their own on the right, 40 columns wide (a third of the width past 140, up to 56), two columns from the transcript, from the top of the transcript area to its bottom; the transcript keeps the rest (prose at `tui.prose_width`, code and boxes to the column's edge). Below 140 columns they are stacked above the input box as inline. The column has its own height limit (the transcript area's), with step 24's rules inside it (the focused panel scrolled, the oldest collapsed, the fold row); focus, keys and readiness are unchanged. The 140 is a constant of the layout, not a setting, chosen so the transcript keeps at least 100 columns; **the coordinator judges it from F5.**

**The keys,** in a new key-map context `screen` (looked up after the editor and before `global`, while the full-screen presenter is shown): `screen.page_up` and `screen.page_down` (`PageUp`, `PageDown`; 09-tui's table has them), `screen.line_up` and `screen.line_down` (`Shift+Up`, `Shift+Down`), `screen.search` (`Ctrl+F`, free today), and the mouse's (point 3). The search row's keys are the `search` context's, as `Ctrl+R`'s are.

**Leaving the screen,** on every way out, each with a test that reads the terminal's modes after it (the test kit's virtual terminal learns modes 1000 and 1006):

| Way out | What happens |
|---|---|
| `/quit`, `Ctrl+C` twice, `Ctrl+D` | The loop leaves the alternate screen and turns mouse reporting off before anything else; the main screen comes back as it was before the program started. Nothing of the session is printed on it. |
| SIGHUP, SIGTERM, SIGINT, SIGQUIT, the terminal going away under a read (EOF, EIO), Windows' close and `Ctrl+Break` | The emergency restore: each of its sequences for a state with the alternate screen on also turns modes 1000 and 1006 off (four of `sys::RESTORE`'s eight), and on Windows the console's input mode is put back as it was found, which turns its mouse input off. The terminal layer's existing hand-off then ends the program. |
| A panic on the interface's thread | The same restore, from the terminal layer's panic hook. |
| The external editor (`Ctrl+G`) and `global.suspend` | The terminal is left as now, which leaves the alternate screen and turns mouse reporting off; after the editor, or on `fg`, the terminal is entered again, the alternate screen and mouse reporting are turned on again (`Terminal::resume` already does the screen), and `Full` draws every row. |

**The inline presenter's output does not change.** `Inline` is not touched, and `App::frame`'s output is held to what it is: every existing snapshot and golden screen passes unchanged. **The same view snapshots render under both presenters:** a test drives one scripted session (the turn of screen 1, with reasoning, an answer with code, a round with a diff and a failure, a notice and the plan panel) through the inline presenter into the virtual terminal and through `Full` at the same width in a window tall enough to show it all, and compares the rows: the inline terminal's scrollback and screen from the session's first row against the full screen's rows, cell by cell, styles included. A second test does it at 60 columns. The viewer's screens 8a and 8b stay as they are.

**Memory.** The long-session test (`perf_two_hundred_turns_in_each_presenter`, ignored, in `cortex-cli`'s system tests, run by `try`'s `perf` and by hand on the musl `dist` build): a workspace of 20,000 files of the real-code corpus, a scripted provider playing 200 turns of a realistic mix (reasoning, an answer of about 40 lines with a code block, a round of a read, an edit with a diff and a command with 200 lines of output), once inline and once with `--fullscreen`, scrolled to the top and back, resized twice, and searched once; the binary's `VmRSS` and its peak read once it is idle. Budgets 40 and 80 MB. A cheap test in `cortex-tui`'s own tier holds the bound per turn of what `Kept` holds.

**Choosing it:** `--fullscreen` on the command line, or `tui.presenter = "fullscreen"` (`inline` by default; user-only, takes effect at the next start). Headless is unaffected.

### 3. The mouse

- **The decoder** (`cortex-term`'s `input`): mode 1006's reports (`CSI < b ; x ; y M` or `m`), and mode 1000's own form (`CSI M` and three bytes) for a terminal that turns 1000 on and does not know 1006, so that its reports never become typed text. A new `Event::Mouse(Mouse)`, with `Mouse { kind, col, row, mods }` and `MouseKind::{Press(Button), Release(Button), Drag(Button), Wheel(Up | Down | Left | Right), Moved}`, the cell counted from 0. **A change to `cortex-term`'s public API, recorded** (the decoder's new event and types, `Terminal::set_mouse`, `Full`, and `draw_screen` removed); `Event` is matched exhaustively in a few places, which are updated. About 150 lines with its tests, as 09-tui estimated; its tests include every split of every report, as the decoder's other tests do.
- **On only while the viewer or the full-screen presenter is shown.** The terminal turns modes 1000 and 1006 on with the alternate screen and off with it (`Terminal::alternate`), when the application has asked for the mouse (`Terminal::set_mouse(true)`, from the setting `terminal.mouse`, on by default). The inline screen never has it: 09-tui's reasons stand. On every way out (the table above) it is off.
- **On Windows,** the console's mouse input (`ENABLE_MOUSE_INPUT`) is turned on while the alternate screen is shown with the mouse wanted, and off with it; the input mode the program found is what every restore puts back. With virtual-terminal input a console passes the terminal's mouse reports as text, which the one decoder reads; a mouse event that arrives as a console record instead is written into the same form before it is decoded. **Which of the two Windows Terminal sends through ConPTY is to confirm by measurement**, on the runner (a system test) and in the checklist.
- **What it does.** In the viewer and the full-screen presenter, a click (a press and a release of the left button on the same cell) on a box's row opens or closes the box, and selects it in the viewer; the wheel scrolls three rows a notch, and in the full-screen presenter stops following as any move up does. Other buttons, drags and moves do nothing. **`Shift` and a drag stay the terminal's own selection:** terminals keep shift-drag for themselves while a program reports the mouse (xterm, VTE, Windows Terminal, kitty, iTerm2), so the program never sees it; the viewer's key row and `/help` say `shift+drag selects text`.
- **The actions are in `ACTIONS`.** The viewer's keys move from the code (today they are tested for in `state/viewer.rs`) into a `viewer` context with the same default keys, and the mouse's actions are added to it and to `screen`: `viewer.toggle` (`enter`, `click`), `viewer.scroll_up` and `scroll_down` (`wheel_up`, `wheel_down`), `screen.toggle` (`click`), `screen.scroll_up` and `scroll_down`. `[keys]` reads three new binding names, `click`, `wheel_up` and `wheel_down`, which only those two contexts take (anywhere else the entry is refused, as a binding that cannot be used is). The key map holds a binding as a key or one of those gestures; `keys::parse` keeps its signature for keys, and `keys::parse_binding` reads either.

### 4. Rewind, undo and fork in the interface

**`/rewind`** opens a picker over the session's earlier points, newest first: each prompt of the active branch, as `turn 12  14:32  fix the lexer so digit separators…  3 files changed since`, its text sanitised and cut at the row. The points are read with `session/read` (a read, beside the lane), not kept: the application holds no ids of a long history. The first prompt is not a point (rewinding before it is `/new`).

- **Choosing a point asks, in the input box's place,** as the undo's question does: `? Rewind to before turn 12?`, the prompt's first line under it, then `1 Rewind it and put back the files changed since (3)`, `2 Rewind the conversation only; the files stay as they are`, by their digits; `Esc` cancels and nothing is sent. No answer is preselected and `Enter` chooses nothing. The dialog's rule of keys holds (readiness, no repeat, no paste). The count of files is what the turns since changed through their file tools and the commands' changes their results record; the files themselves are listed under the question when there are at most eight.
- **What is restored:** with `1`, `session/rewind` with `restore_files: true`; with `2`, `false`. A file edited since the harness left it is then the core's question (built in step 23, screen 2d's dialog), which keeps the files unless the person says to put them back. **Nothing is restored that the person did not choose:** a test for each answer, `Esc` included, checks the operation sent, or that none was.
- **After it:** the prompt of the turn rewound to goes back into the editor, to change and send again. Inline, the scrollback cannot be taken back: a notice says `· Rewound to before turn 12. The conversation goes on from there; what is above this line is no longer part of it.` The viewer's and the full-screen presenter's transcript is read again from the active branch (`session/read`) and drawn from it, so the turns undone are gone there.
- **`/undo`** stays as built in step 23 (the last turn, files and conversation, after the question about files edited since), and its result is drawn the same way as a rewind's.

**Fork.** In the `/rewind` picker, `Tab` forks from the point instead (`tab - fork from here` on the picker's last row, as `/effort`'s toggle row reads): `session/fork` with `at` the item before that prompt, which opens the new session and leaves this one as it was. In the `/sessions` picker, `Tab` forks the selected session at its end. A new picker action, `picker.fork` (`tab`), in a context of its own for the pickers that have it, as `toggle` is for `/effort`'s.

**A fork's place in `/sessions`:** in the list's order (the one used last first), with its note saying whose fork it is: `fork of "fix the lexer…"` (the parent's title, sanitised) or, when the parent is not in the list, `fork of s_4f2a…`. `session/list`'s `parent` already carries it.

**Over `cortex attach`:** each of these is an operation through the `Link` (`session/read`, `session/rewind`, `session/fork`, `session/undo`, `session/list`), and the question about files is the core's `question/ask` to the session's `user` clients that answer questions, which an attached interface is. Nothing of it is in-process. A test runs the rewind through the scripted `Link`, which is what step 27's second link is held to.

### 5. The first run

**What starts it:** an interactive start (`cortex` with no `-p`, at a terminal) when **the user's configuration file does not exist**: no `config.toml` in the configuration directory, and no `CORTEX_CONFIG` naming a file. Narrower than "no configuration at all" in one way: a stored key, an environment variable or a managed file does not stop it, since none of them says the person has set the harness up; the provider step then offers what it found. **It ends by writing the configuration file** (with the mode, and a comment for each step that was skipped, saying the command that does it later), so it never starts again by itself. **A later run when the person skipped it:** it does not ask again; `cortex setup` runs the flow again on request, and `/status` says how a provider with no key gets one. `Ctrl+C` (twice, as anywhere) leaves the flow and the program with nothing written but what a finished step wrote (a stored key), and the flow starts again next time. **Headless never runs it:** with no key it says what is missing and how to give it (`cortex auth login`), as it does now.

**Where it lives.** The steps that write the person's own files (the key, the configuration, an imported server) cannot be operations of the core's protocol without letting any client write them, so they go through a trait the program gives the application, `app::Setup`, as it gives `Restyle` (step 24): the providers and where each one's key would come from, storing a key, discovery, reading one file the person picked, writing the configuration. `cortex attach` gives none, and never runs the flow: the server it attaches to has its configuration. The steps that are a session's (the trust question, the profile's entries, the mode for this session) are operations through the `Link`, as any client's are.

**The key** (screens F1a, F1b):
- The providers the core knows, each with where its key comes from now. **A key found in the environment is offered by the variable's name** (`its key from ANTHROPIC_API_KEY`), never its value: the flow is told which variables are set, not what they hold. Choosing it stores nothing.
- Otherwise the key is typed or pasted into an input of its own: **read without echo, never drawn** (the row shows only how many characters it holds), held as a `cortex_base::Secret` from the first character (each key and paste appended to the secret, nothing in a `String` that outlives the read), **never in the prompt history, the undo of any editor, the log, a crash report or the transcript**; `Enter` stores it in the credential store (`Setup::store_key`, the store `cortex auth login` uses) and drops it. A paste of more than a key's 64 KiB is refused. Tests: the key's text is in no frame written to the virtual terminal, no log line, no history file, no notice, and the crash report of a panic raised while it is held (the report's text is checked); the `Secret`'s `Debug` prints nothing of it.
- **`cortex auth login` at a terminal** ([reading-a-key-at-a-terminal](../../outstanding/reading-a-key-at-a-terminal.md)) uses the same input, through a function `cortex-tui` gives `cortex-cli` (`cortex_tui::secret::read_key`), which enters the terminal inline, draws the one row and the hint row, and puts the terminal back whatever happens. Standard input that is not a terminal is read as now.

**Imports** (screens F2a, F2b). The list is `cortex-config`'s discovery, which opens nothing. **Nothing found is started, trusted or put in the prompt without a yes**, and what each yes does is said on its row:
- **The project's instruction files** (`AGENTS.md`, `CLAUDE.md`) are read as its instructions today, by `compat.instructions` (on by default; [07-sessions-and-context.md](../../architecture/07-sessions-and-context.md) loads them without trust, as text for the model). The row says so and starts picked; unpicking it writes `compat.instructions = false`, for every project. **A question:** this row starts picked, unlike the others, because it is today's default for everyone who never runs the flow; starting it unpicked would make the flow's default differ from a hand-written configuration's.
- **Skills folders** are listed, unpicked. Skills are read from step 28; a pick writes `compat.skills = true`, no pick `compat.skills = false`, so step 28 starts with the person's answer.
- **MCP servers in other clients' files of the user** (`~/.claude.json`, Cursor's, Codex's, Claude Desktop's) are listed by file, unpicked, and **a file is read only when the person asks to see inside it** (`space`): reading it is the import 08 says the user asks for. Its servers are then listed with **each command in full**, arguments and all (a remote server's address), wrapped and never cut, sanitised. A server picked is written to the user's configuration as an `[mcp.servers.<name>]` table in 13-mcp's form; a value of its environment or headers that is a literal in the other tool's file is brought in as a reference to the variable of the same name (`{ env = "GITHUB_TOKEN" }`), the value never copied, and the row says so. Nothing starts before step 30's client exists, and then by its rules (the sandbox, approval per tool). The project's `.mcp.json` is not imported: 13-mcp has it offered live, after trust, as proposed servers; its row says that and has no box to pick.
- `s` skips the step: nothing is brought in, and the instruction files keep today's default.

**The project** (screen 2c, then F3). The trust question is the session's own, asked as the session opens (`trust/request`, golden screen 2c), with what trusting turns on, so the first run adds no second way to trust. Then, for a trusted project with no commands in its profile, **the commands found** are listed: from the project's own files (`Cargo.toml`, `package.json`'s scripts, `Makefile` targets named `build`, `test`, `check` or `lint`, `go.mod`, `pyproject.toml`), each **shown in full**, unpicked or picked by how sure the finding is (a `Cargo.toml` workspace's `cargo build`, `test` and `clippy` picked; a script whose body is not shown, not). `e` edits one before it is kept. The picked ones enter the profile **as entries the person wrote**, through `project/update`'s `add` (`NewEntry` of kind `command`, active at once, step 17's rules for a user's entry): no command is learned, proposed or run by the flow. An untrusted project is not offered the step. Detection reads only those files of the workspace, through the session's path resolver and the engine's read gate, on the blocking pool; **it is a function of `cortex-knowledge`'s, reached by a new read operation `project/detect`** (in `reads()`), so that a client over the wire has it.

**The mode** (screen F4): a picker of the levels the session can hold, `supervised` preselected, with two lines each for what it means (supervised: `reads and edits files in this project without asking; asks before a command that is not known to be safe`); `autonomous` is shown only where the sandbox enforces, as 06 has it, and `unrestricted` says it confines nothing. The choice is `session/set` for this session and is written to the configuration file as `permissions.mode`. `s` keeps `supervised`.

**Every step can be skipped and has a default:** the provider (no key; the first prompt then says how to give one), the imports (nothing brought in), the project (not trusted now, as `n` in 2c; no commands), the mode (`supervised`). A pseudo-terminal test runs the flow in an empty home directory to a working session against a local scripted server and a fake credential store, and one test per step skips it.

### 6. `/export`

- **`/export`** writes the session as Markdown; `/export json` as JSON; `/export <path>` takes the format from the path's ending (`.md`, `.json`). The default file is `cortex-session-<date>-<the session's first eight characters>.md` in the folder the person started in.
- **What it holds:** the session's items of the active branch, read from the log through `session/read` in pages (a read, beside the lane). An item still in progress is left out, and a line says a turn was running. Markdown: a heading with the session's title, its workspace, when it began and its model; then each turn's prompt, reasoning summary, answer (as the model wrote it) and tool calls (each call's line, then its output or diff in a fenced block). JSON: `{ "protocol_version", "session": <SessionSummary>, "items": [<Item>…] }`, the protocol's own types.
- **The redaction.** The log holds what the core's secret filter left when each entry was written: the harness's credentials masked by value, and anything in a well-known key format ([security.md](../../security.md), section 4). The export is made from the log, so it holds no more than that; and the whole text of the file passes through `cortex_base::SecretFilter`'s key formats again before it is written, so that nothing the log might hold unmasked from an older build reaches the file. **The test:** a session whose prompt holds a key stored in the fake credential store (masked by value), a token in a well-known format in a command's output, and a value the log holds masked, exported as both formats: none of the three is in either file, and the mask is.
- **The file:** written private to the user (`cortex_base::private`: mode `0600`, or an access list with the user alone on Windows), **created new, never over a file that exists**: `/export` names the file that is there and writes nothing. Where it went is said with its path. The writing is a function the program gives the application (`Start::export`), as `Restyle` is, so `cortex-tui` touches no file; `cortex attach` gives the same function.

### 7. Terminal quirks

Each detected, each with an override in `[terminal]` (user-only, at the next start), each with a test of the decoder or the terminal and a break:

| Quirk | Detection | Override | Test |
|---|---|---|---|
| **Backspace sent as `^H`** ([backspace-sent-as-ctrl-h](../../outstanding/backspace-sent-as-ctrl-h.md)) | On Unix, the terminal's erase character as the program starts (`termios`' `VERASE`): `^H` there means byte 0x08 is Backspace. On Windows, never (Windows Terminal sends DEL for Backspace, and win32 input mode tells them apart). | `terminal.backspace = "auto"`, `"del"` or `"ctrl+h"` | 0x08 is `Backspace` with the override and with an erase character of `^H`, and `Ctrl+Backspace` otherwise; win32 records are unaffected. |
| **Pastes without bracketed paste** ([pastes-without-bracketed-paste](../../outstanding/pastes-without-bracketed-paste.md)) | Where reads happen (`Terminal::next`): keys that come in one read, none with `Ctrl` or `Alt` and none a sequence's key (text, `Enter`, `Tab`), at least eight of them with an `Enter` that is not the last, or more than 64 of them, are given as one `Event::Paste` of their text. A person cannot type that fast; a loop held up for a moment can gather a few keys, never eight with a line break inside. **The eight and the 64 are to confirm by measurement** (the fastest typing a read can gather, from the key-latency tests' recordings). | `terminal.bracketed_paste`: unset, it is asked for and pastes outside it are rate-detected; `false`, it is not asked for and pastes are rate-detected; `true`, no rate detection. | A read of keys as each kind of terminal sends a paste (bytes alone, with `\r` and `\n`) is one paste; typing, a burst a held loop gathers, and keys with modifiers are keys. |
| **A paste that stalls** ([a-paste-that-stalls](../../outstanding/a-paste-that-stalls.md)) | After a bracketed paste is given up on (no input for the wait), the keys that follow without a pause of 500 ms are the paste's too, given as further pieces of it (`Event::Paste`, which the editor appends), an `Enter` among them as a line break, until such a pause or the end marker, which is dropped. | `terminal.paste_wait` (2 s by default, the time a paste may pause before it is given up on) | A paste cut by a pause past the wait, then its rest with line breaks, then the end marker: one paste's text, no `Enter`, nothing sent; a key after the pause of 500 ms is a key. Paused time, the device's clock. |
| **Function keys through ConPTY** ([function-keys-through-conpty](../../outstanding/function-keys-through-conpty.md)) | Not a detection: the test kit sends a named key as the win32 input record Windows Terminal would (`pty::Session::send_key`, on Windows; the sequence elsewhere), and a system test sends `F1` to `F12` and the arrows that way, each bound to a test action, and checks each reaches the application as itself. A key that does not is reported with what the application read, kept in memory and printed only on failure. The checklist's function-key line is run by hand. | — | The system test, on both systems. |

`/copy` gets the same treatment ([copy-where-the-clipboard-sequence-is-not-taken](../../outstanding/copy-where-the-clipboard-sequence-is-not-taken.md)): where the terminal is known not to take the clipboard sequence (the old console host, tmux whose `set-clipboard` default does not pass a program's sequence on, GNU screen), `/copy` sends it and also opens the viewer on the text, saying to select it with `shift` and a drag; `terminal.clipboard = true | false` overrides the guess.
