### 2. The full-screen presenter

**What it keeps.** Today the application keeps every committed part as rendered lines for the viewer (`App`'s kept `Committed` parts, step 23), in both presenters. That changes to **the finished blocks themselves**: a new `transcript::Kept`, an append-only list of the blocks the transcript has finished with (`Transcript::take_finished`: each block with whether a blank row stood before and after it), and nothing rendered. Both the viewer and the full-screen presenter draw from it:

- **Rendered lines are kept only around the viewport** (09-tui, "Rendering cost control"): each block's rows at the current width are made when the window first reaches them, kept for the blocks within two windows of what is shown, dropped for the rest after each frame, and dropped whole on a change of width, theme or glyphs (a `tui.*` reload). A frame costs the rows near the screen, not the session's length.
- **A finished answer keeps its markdown source** (`Markdown::keeping`, which the inline presenter's stream does not need) and the colours its code lines were committed with, by code block and line (`markdown::Source`). It is drawn again with `Markdown::render_source` at the new width, which takes those colours. A test holds that every kind of block, kept and drawn again at the width it committed at, gives the committed lines exactly, styles and blank rows included, and at another width what a transcript committed there gives.
- **A finished round keeps what it shows, bounded:** a command's output to its last 16 KiB and a diff to its first 2,000 lines, from a line's start. Opening such a box in the viewer reads the whole of it: the call's result item (`session/read` with `item_id`, a read), which holds up to the tool's 32 KiB, and past that its artifact (`session/artifact`); the box says `reading…` until it comes. Search looks in what is kept, and a box that was cut says so when a search goes through it. Without the bound, 200 turns of commands that each print 64 KiB (what a running command keeps) hold 38 MB in their rounds alone. **The 16 KiB and the 2,000 lines are to confirm by measurement** against the 200-turn budgets.
- **An answer still streaming** commits rows while it is open, before it is finished and kept. In the full-screen presenter those rows are kept as lines beside the open block, at the width they were made at, and drawn between the kept blocks and the live rows; when the block finishes they are dropped and the kept block takes their place. **On a change of width while it streams,** its stream is made again from its source so far at the new width (`Markdown::render_source` does not finish it: a fresh stream fed the same text, which the commit rule makes give the same rows a stream at that width gives), and its rows replace the old, so that a resize in the middle of an answer re-wraps it too. The inline presenter never does this: its scrollback cannot be taken back. A test feeds an answer token by token and checks every frame of the full-screen presenter against the inline presenter's scrollback and live rows at the same width, and again across a resize.
- **The inline presenter is unchanged:** it still commits the lines `commit_parts` gives at the width of the time, and draws its live region as now. Only what is kept beside it changes, from lines to blocks, which is less memory, not more.
- **The budget:** 80 MB resident after 200 turns, 40 MB inline. A turn's blocks are a few kilobytes of text; 200 turns of a realistic mix is estimated at 4 to 10 MB kept and the cache at under 1 MB. **To confirm by measurement** (point 2, "Memory").

**How a frame is drawn.** A new presenter in `cineris-term`, `Full` (beside `Inline`), draws a whole screen of rows on the alternate screen: one write, inside a synchronized update; only the rows that differ from the last frame, each placed with a cursor move and followed by an erase to the line's end; the cursor placed at the editor's insertion point last, or hidden. A resize, `Ctrl+L`, a resumption and the alternate screen entered again draw every row. It never clears and then redraws, and says nothing to the emergency restore about rows above the cursor (the main screen holds none of its rows; the inline region, when the viewer was opened over it, is what the restore must still erase there). **While the view follows the end, every transcript row moves up with each committed row,** which as rows that differ is the whole area each frame (more than 4 KiB at 120 by 40, and ConPTY passes no synchronized-update brackets): when the transcript area's rows are the last frame's moved up by `k`, `Full` scrolls that area by `k` inside a scroll region (`CSI top;bottom r`, `CSI k S`, the region reset) and writes the `k` new rows. **To confirm by measurement**, bytes and time a frame with and without it, here and under ConPTY; kept only if it pays. The viewer moves onto `Full` from `Terminal::draw_screen`, which writes every row every frame; `draw_screen` is then removed (a change to `cineris-term`'s public API, recorded). The layout, top to bottom:

1. **The transcript area:** the kept blocks, the open blocks' committed rows, and the transcript's live rows (the streaming tail, the reasoning rows, the running round's box) as one column of rows, of which a window is shown. A transcript shorter than the area is drawn from its top, and the bottom stays at the window's foot.
2. **The panels' block,** when panels are open and the window is narrower than the width at which they move beside the transcript (below): exactly as inline, with step 24's limit.
3. **The bottom:** the input box with its hint row or menu, or a dialog, exactly as inline.

The bottom and the panels are made by the same code as inline (`App::frame` is split so that both presenters call one function for them), so they look the same in both.

**Scrolling while an answer streams.** The view **follows the end** while the transcript's last row is shown, which it is from the start and after each prompt is sent. **Any move up stops following** (`PageUp`, `Shift+Up`, the wheel, a search's jump): what streams then grows below without moving the view, and the transcript area's last row says so, dim: `↓ more below · pgdn goes to the end`. Following starts again when the view reaches the end (`PageDown` or the wheel down to it), when a prompt is sent, and when a dialog opens (it asks about what just happened, at the end). The view is held by its first row's block and the row inside it, not by a row number, so a block that changes above it does not move it.

**Re-wrapping on resize.** A change of width drops the rows made; the next frame draws the blocks around the view at the new width, keeping the same block at the top and the nearest row inside it. **Code is highlighted again at the new width** (`highlighted-code-drawn-again`, closed by the first pull request): a finished answer keeps the colours its code was committed with, which are byte ranges of each source line and do not depend on the width. A code line committed plain because its colours were late is recorded as late (`Source::late`); when such a block is first drawn again, it is handed to the highlighter whole, by its language and lines, and drawn plain until the worker's answer comes, which is put into the kept source and wakes the loop for a frame. `Markdown::render_source` never waits for the worker. The viewer re-wraps the same way from now on.

**Search** (screen F6). `Ctrl+F` opens a search row in the hint row's place, in the form of the history search's (`ctrl+f`, what is typed, then the count, `2 of 3`, and the keys), the query laid out through `editor::cluster::width` and `drawn`; its keys are the `search` context's, as `Ctrl+R`'s are, `Up` and `Enter` for the next older match and `Down` for the newer. **It runs off the interface's thread:** each kept block's text, as it reads (an answer's source, a round's call lines and its kept detail, every other block's text), is handed once, as it is kept, to a worker of its own, which matches the query (ignoring case) and answers with the blocks that hold it and how often, for the latest query only, as the `@` worker does (`app::files`); a key's frame draws what the worker last gave. Only the block of the current match is then drawn, to find the match's row and bring it into view. Every match on the screen is drawn reversed, and the current one reversed and bold: no colour is needed, so it holds at 16 colours and none. `Esc` ends the search and leaves the view where it is (not following). **A match inside a closed box:** the worker looks in each box's whole kept detail; when the current match is inside a closed box, that box is drawn open while the match is current, its bottom border saying `opened by the search`, and closes again when the search moves to another match; when the search ends on it, it stays open. A paste goes to the search row while it is open, on one line. A match the markdown's marks split as drawn (`**fo**o`) brings its block into view without a row marked.

**Panels beside the transcript** (screen F5). From **140 columns** the panels sit in a column of their own on the right: 40 columns wide, plus one for each two columns past 140, up to 56; two columns from the transcript, which keeps the rest, at least 98 columns (prose still at `tui.prose_width`, code and boxes to the column's edge); from the top of the transcript area to its bottom. Below 140 columns they are stacked above the input box as inline. Step 24's rules hold inside the column (a panel without the focus is drawn collapsed and the focused one whole, the focused one scrolled, the oldest collapsed, the fold row), with the column's height as the limit; focus, keys and readiness are unchanged. The 140 is a constant of the layout, not a setting; **the coordinator judges it from F5.**

**The keys,** in a new key-map context `screen` (looked up after the editor and before `global`, while the full-screen presenter is shown): `screen.page_up` and `screen.page_down` (`PageUp`, `PageDown`, which 09-tui's table already gives the full-screen presenter), `screen.line_up` and `screen.line_down` (`Shift+Up`, `Shift+Down`), `screen.search` (`Ctrl+F`, free today), and the mouse's (point 3). **A committed box is opened by keys through the viewer** (`Ctrl+O`, then `Up`, `Down` and `Enter`), as inline; in the full-screen presenter the viewer is a state of the same alternate screen, and `Esc` from it returns to the full-screen view without leaving the alternate screen. A box's border says what it says inline (`ctrl+o expands`), so that the same rows are drawn under both presenters.

**Leaving the screen,** on every way out. Each is tested on a scripted `Device` (the terminal layer's own tests and the application's), which reads every byte written; the pseudo-terminal tests are kept to one for each presenter (point 2, "The system tests"):

| Way out | What happens |
|---|---|
| `/quit`, `Ctrl+C` twice, `Ctrl+D`, the core gone (`Exit::Gone`) | The loop turns mouse reporting off and leaves the alternate screen before anything else; the main screen comes back as it was before the program started. Nothing of the session is printed on it. |
| SIGHUP, SIGTERM, SIGINT, SIGQUIT, the terminal going away under a read (EOF, EIO), a write to it that fails, Windows' close and `Ctrl+Break` | The emergency restore: each of its sequences for a state with the alternate screen on also turns modes 1006 and 1000 off (four of `sys::RESTORE`'s eight), and on Windows the console's input mode is put back as it was found, whatever that was. The terminal layer's existing hand-off then ends the program. |

| `global.suspend`, then `fg` | Left as for the editor; `Terminal::resume` turns the alternate screen on again, and the mouse with it when it was asked for. |

Mouse moves that come as console records with no button down are dropped where they are read, so they cost no wake.

It runs at 60, 80 and 120 columns, and once with the answer streamed token by token, every frame compared. The viewer's screens 8a and 8b stay as they are.

**Resize tests for both:** inline as step 20's presenter tests have them; for the full-screen presenter, every width from 40 to 160 and back, mid-stream and idle, checking that no row is wider than the window allows, that the top block stays the top block, and that every frame is one write with no clear (the virtual terminal's frame report, as for `Inline`).

### 3. The mouse

- **The decoder** (`cineris-term`'s `input`): mode 1006's reports (`CSI < b ; x ; y M` or `m`), and, while the mouse is on, mode 1000's own form (`CSI M` and three bytes) for a terminal that turns 1000 on and does not know 1006, so that its reports never become typed text; with the mouse off, `CSI M` is dropped alone as before, so `Alt+[` and `M` never take the keys after them. A new `Event::Mouse(Mouse)`, with `Mouse { kind, col, row, mods }` and `MouseKind::{Press(Button), Release(Option<Button>), Drag(Button), Moved, Wheel(Wheel)}`, the cell counted from 0. **A change to `cineris-term`'s public API, recorded** (the decoder's new event and types, `Decoder::set_mouse`, `Terminal::set_mouse` and `mouse`, `Full` and `Screen`, and `draw_screen` removed). Its tests include every split of every report.
- **On only while the viewer or the full-screen presenter is shown.** The terminal turns modes 1000 and 1006 on with the alternate screen and off before it (`Terminal::alternate`), when the application has asked for the mouse (`Terminal::set_mouse(true)`, from the setting `terminal.mouse`, on unless set to `false`). The inline screen never has it: 09-tui's reasons stand. On every way out (the table above) it is off.
- **On Windows,** the console's mouse input (`ENABLE_MOUSE_INPUT`) is turned on while the alternate screen is shown with the mouse wanted, and off with it; every restore puts back the input mode the program found. With virtual-terminal input a console may pass the terminal's mouse reports as text, which the one decoder reads, or give a mouse event as a console record, which is written into the same form before it is decoded. **Which of the two Windows Terminal sends through ConPTY is to confirm by measurement**, on the runner (the full-screen system test sends a click) and in the checklist.
- **What it does.** In the viewer and the full-screen presenter, a click (a press and a release of the left button on the same cell) on a box's row opens or closes the box, and selects it in the viewer; the wheel scrolls three rows a notch, and in the full-screen presenter stops following as any move up does. A click is input as a key is: it counts for a dialog's and a panel's readiness (step 23's rule), and a click on a box under an open dialog does nothing. Other buttons, drags and moves do nothing. **`Shift` and a drag stay the terminal's own selection:** terminals keep shift-drag for themselves while a program reports the mouse (xterm, VTE, Windows Terminal, kitty, iTerm2), so the program never sees it; `/help` says `shift+drag selects text` (the viewer's key row stays as screens 8a and 8b draw it).
- **The actions are in `ACTIONS`.** The viewer's keys move from the code (today they are tested for in `state/viewer.rs`) into a `viewer` context with the same default keys, and the mouse's actions are added to it and to `screen`: `viewer.toggle` (`enter`, `click`), `viewer.scroll_up` and `scroll_down` (`wheel_up`, `wheel_down`), `screen.toggle` (`click`), `screen.scroll_up` and `scroll_down`. `[keys]` reads three new binding names, `click`, `wheel_up` and `wheel_down`, which only those two contexts take (anywhere else the entry is refused, as a binding that cannot be used is). The key map holds a binding as a key or one of those gestures; `keys::parse` keeps its signature for keys, and `keys::parse_binding` reads either.

### 4. Rewind, undo and fork in the interface

**`/rewind`** opens a picker over the session's earlier points, newest first: each prompt of the active branch, as `turn 12  14:32  fix the lexer so digit separators…`, its text sanitised and cut at the row. The points are read with `session/read` (a read, beside the lane), not kept: the application holds no ids of a long history. The first prompt is not a point (rewinding before it is `/new`). While a turn runs, `/rewind` says to wait for it or stop it, as the core refuses a rewind then.

- **Choosing a point asks for the core's own plan** before anything is offered: a new read, `session/rewind_plan` (`SessionRewindParams` less `restore_files`, an addition to the protocol, in the lane's `reads()`), whose result is the plan the core would carry out (07, "A rewind is planned first"): each file with what it would go back to (its earlier content, removed, or nothing it can do: unknown, too large, a checkpoint it cannot read), and whether it was edited since the harness left it.
- **The question, in the input box's place,** as the undo's is: `? Rewind to before turn 12?`, the prompt's first line under it, the plan's files listed (each with what happens to it), then `1 Rewind it and put back the files listed`, `2 Rewind the conversation only; the files stay as they are`, by their digits; `Esc` cancels and nothing is sent. **`1` is offered only once every file of the plan was drawn whole,** in the dialog or in the viewer (`ctrl+o shows it whole`), by the approval dialog's rule for a lasting answer. No answer is preselected, `Enter` chooses nothing, and the dialog's rule of keys holds (readiness, no repeat, no paste).
- **What is restored:** with `1`, `session/rewind` with `restore_files: true`, which the core carries out from its plan made again; with `2`, `false`. A file edited since the harness left it is then the core's own question (built in step 23, screen 2d's dialog), which keeps it unless the person says to put it back. **Nothing is restored that the person did not choose:** a test for each answer, `Esc` included, checks the operation sent, or that none was, and a plan that moved between the question and the answer is the core's to refuse.
- **After it:** the prompt of the turn rewound to goes back into the editor, after what was being written there, to change and send again. Inline, the scrollback cannot be taken back: a notice says `· Rewound to before turn 12. The conversation goes on from there; what is above this line is no longer part of it.` The viewer's and the full-screen presenter's transcript is read again from the active branch (`session/read`) and drawn from it, so the turns undone are gone there.
- **`/undo`** stays as built in step 23 (the last turn, files and conversation, after the question about files edited since), and its result is drawn the same way as a rewind's.

**Fork.** In the `/rewind` picker, `Tab` forks from the point instead (`tab - fork from here` on the picker's last row, as `/effort`'s toggle row reads): `session/fork` with `at` the item before that prompt, which opens the new session and leaves this one as it was. In the `/sessions` picker, `Tab` forks the selected session at its end. A new picker action, `picker.fork` (`tab`), in a context of its own for the pickers that have it, as `toggle` is for `/effort`'s.

**A fork's place in `/sessions`:** in the list's order (the one used last first), with its note saying whose fork it is: `fork of "fix the lexer…"` (the parent's title, sanitised) or, when the parent is not in the list, `fork of s_4f2a…`. `session/list`'s `parent` already carries it.

**The viewer opens a reasoning summary and a compaction summary** (09-tui, "The viewer", left to this step by step 23): `Up` and `Down` move between boxes and these too; `Enter` on a reasoning block opens its whole summary (shown even when `tui.reasoning = "duration"` keeps only its first line in the transcript), and on a compaction notice reads the summary item (`session/read` with `item_id`) and opens its text.

**Over `cineris attach`:** each of these is an operation through the `Link` (`session/read`, `session/rewind_plan`, `session/rewind`, `session/fork`, `session/undo`, `session/list`), and the question about files is the core's `question/ask` to the session's `user` clients that answer questions, which an attached interface is. Nothing of it is in-process. A test runs the rewind through the scripted `Link`, which is what step 27's second link is held to. Every new listing (the rewind picker's rows, the plan's file names, the fork's note) has a hostile-text test (`testing::problems`).

### 5. The first run

**What starts it:** an interactive start (`cineris` with no `-p`, at a terminal) when **the user's configuration file does not exist**: the file `CINERIS_CONFIG` names, or `config.toml` in the configuration directory. A stored key, an environment variable or a managed file does not stop it, since none of them says the person has set the harness up; the provider step then offers what it found. **It ends by writing that file** (with what the steps chose, and a comment for each step skipped saying the command that does it later: `cineris auth login`, `/mode`, `/project`, `cineris permissions trust`), so it never starts again by itself. **A later run when the person skipped it** does not ask again; there is no command that runs the flow over a configuration that exists, since the flow writes only a file that does not (the writer never edits one). `x` on any step skips the whole set-up: what the steps before it did stays done (a stored key), and the rest take their defaults. `Ctrl+C` (twice, as anywhere) leaves the flow and the program with nothing written but what a finished step wrote, and the flow starts again next time. **Headless never runs it:** with no key it says what is missing and how to give it (`cineris auth login`), as it does now.

**The order:** the provider, the imports, the mode, then the project. 08 lists the mode last; it moves before the project because the configuration file must be written before the first session opens, so that the session is made with what was chosen (the `compat.*` keys take effect in sessions opened from then on), and the project's trust question is that session's own. After the mode the file is written, the core reads it again (`config/reload`), and the session opens. 08's "First run" is changed to say so.

**Every step holds the dialog's rule of keys** (`app::ready::Readiness`, step 23): it takes no key until 300 ms after its rows were first drawn, and only a second after input it did not take; keys read together, a repeat and a paste never answer it. A prompt typed at the first frame, or an `Enter` held from the step before, changes nothing and stores nothing (a test). Typing into the key's input and a step's text field (`e` on a command) is typing, not an answer.

**Where it lives.** The steps that write the person's own files (the key, the configuration, an imported server) cannot be operations of the core's protocol without letting any client write them, so they go through a trait the program gives the application, `app::Setup`, as it gives `Restyle` (step 24): the providers and where each one's key would come from, storing a key, discovery, reading one file the person picked, writing the configuration. **None of it runs on the interface's thread:** `Setup`'s calls go to a worker of its own that wakes the loop with the terminal's waker when it answers, as the history and the `@` files do; a step shows `reading…` until its answer comes. `cineris attach` gives no `Setup`, and never runs the flow: the server it attaches to has its configuration. The steps that are a session's (the trust question, the profile's entries, the mode for this session) are operations through the `Link`, as any client's are.

**The key** (screens F1a, F1b):
- The providers the core knows, each with where its key comes from now. **A key found in the environment is offered by the variable's name** (`its key from ANTHROPIC_API_KEY`), never its value: the flow is told which variables are set, not what they hold. Choosing it stores nothing. Where the key would be stored is said for the system at hand: the owner-only file on Linux, Windows Credential Manager on Windows.
- Otherwise the key is typed or pasted into an input of its own, **not the prompt's editor**: it has no undo, no kill slot, no history, no completion and no hand-off, and answers only typing, a paste, `Backspace`, `Ctrl+U` (which empties it), `Enter` and `Esc`; `Ctrl+G`, `Ctrl+O`, `Ctrl+Y` and the rest do nothing there. **It is read without echo and never drawn:** the row shows only how many characters it holds. It is held in a buffer of fixed capacity (64 KiB, a key's limit, so it never moves), which is written over with zeros when it is dropped, a `cineris_base::SecretBuf` (new: `cineris-base` changes too), and given to the store as a `Secret`. A paste that holds a line break, or more than the capacity, is refused with a sentence and nothing of it kept; the key is trimmed as `auth login` trims it, and on Windows one that is not printable ASCII is refused before Credential Manager is asked (08, "Windows Credential Manager"). `Enter` stores it in the credential store (`Setup::store_key`, the store `cineris auth login` uses) and drops it.
- **What is not wiped:** a key typed or pasted passes through the terminal layer's read buffer and the decoder's, and a paste through `Event::Paste`'s string, before it reaches the buffer; those are cleared, not written over. They are the process's own memory, short-lived, and never written anywhere. Said in 08's "Credentials".
- **The tests:** the key's text is in none of the bytes written to the pseudo-terminal (read raw, not only as frames), no log line, no history file, no notice, no transcript block, and not in the crash report of a panic raised while it is held (the report's text is checked); the buffer is zero after it is dropped; `Debug` prints nothing of it.
- **`cineris auth login` at a terminal** ([reading-a-key-at-a-terminal](../../outstanding/reading-a-key-at-a-terminal.md)) uses the same input, through a function `cineris-tui` gives `cineris-cli` (`cineris_tui::secret::read_key`), which enters the terminal inline, draws the one row and the hint row, and puts the terminal back whatever happens. Standard input that is not a terminal is read as now.

**Imports** (screens F2a, F2b). The list is `cineris-config`'s discovery, which opens nothing (so it gives no counts). **Nothing found is started, trusted or put in the prompt without a yes,** and what each yes does is said on its row:
- **Instruction files** (`AGENTS.md`, `CLAUDE.md`): one row, unpicked; picked, `compat.instructions = true`, which reads them in every project; not picked, or the step skipped, `compat.instructions = false`. **A question for the coordinator:** this follows "nothing put in the prompt without a yes" to the letter, so a person who skips the step has no project's `AGENTS.md` read, where a person who writes the configuration by hand has it read by default (07 reads them without trust, as text for the model). The other way, the row starts picked and says so.
- **Skills folders:** one row for `compat.skills`, which covers the user's and each project's, unpicked, the same way. Skills are not read by this version; the row says the choice holds once they are.
- **MCP servers in other clients' files of the user** (`~/.claude.json`, Cursor's, Codex's, Claude Desktop's) are listed by file. **A file is read only when the person asks to see inside it** (`space` on its row opens it, as a tree): reading it is the import 08 says the user asks for. `Setup` reads and parses it on its worker and gives the application each server's entries with **every literal value already dropped**: the environment's and the headers' values are not given, only their names. Its servers are then listed under it, **each command in full**, arguments and all (a remote server's address), wrapped and never cut, sanitised. **Every argument and the address go through the secret filter's formats and the address's user-part rule** (08, "Credentials"); a part that matches is drawn `[masked]`, and that server **cannot be imported**, its row saying it holds a credential, as step 17 refuses an entry that holds one. A command with a control character or a character that acts unseen is refused the same way. A server picked is written to the user's configuration as an `[mcp.servers.<name>]` table in 13-mcp's form, through the TOML writer (never text put together, so a name from the other tool's file cannot escape its table), and the file is read back strictly before it is kept: its environment and headers as references to variables (`{ env = "NAME" }`), an environment variable's own name for an `env` entry and, for a header, a variable named on the row (`TRACKER_AUTH`, the server's name and the header's in capitals), which the person sets; `network` and `expose` are never written, so 13-mcp's defaults hold (no network, behind search). Nothing starts until this version runs MCP servers, and then by 13-mcp's rules. **A project's own MCP files** (`.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`) are not imported: 13-mcp has them offered live, after trust, as proposed servers; their row says that and has no box to pick.
- `s` skips the step: nothing is brought in.

**The mode** (screen F3): the levels the session can hold in the ladder's order, `supervised` preselected, with two lines each for what it means (supervised: `reads and edits files in this project without asking; asks before a command that is not known to be safe`; read-only: `reads, and runs only commands known to read; asks before any other, and never writes`, as 06's table has it); `autonomous` only where the sandbox enforces, as 06 has it. **`unrestricted` is not offered:** 06 has it chosen explicitly, and a first run's one key would write it for every project; `/mode` and the configuration still reach it. The choice is written as `permissions.mode`. `s` keeps `supervised`.

**The project** (screen 2c, then F4). The session opens, and asks its own trust question when the project has something to trust (`trust/request`, golden screen 2c), with what trusting turns on, so the first run adds no second way to trust. Then **the commands found** are listed: from the project's own files (`Cargo.toml`, `package.json`'s scripts, `Makefile` targets named `build`, `test`, `check` or `lint`, `go.mod`, `pyproject.toml`), each **shown in full**: the command that would run (`npm run test`) and, for a script, what the script runs (`jest --coverage`), sanitised; **every row unpicked**. A name taken from a file (a script's, a target's) must be plain words by step 17's rules (`classify`), or it is not offered. `e` edits one before it is kept. The picked ones enter the profile **as entries the person wrote**, through `project/update`'s `add` (`NewEntry` of kind `command`, active at once, step 17's rules for a user's entry), their text saying where they were found (`found in Cargo.toml by the set-up`): no command is learned, proposed or run by the flow. For a project not trusted (nothing to trust, or `n` in 2c), the step is offered all the same, and its sentence says that a command still asks until the project is trusted, as 14 has it. Detection reads only those files of the workspace, through the session's path resolver and the engine's read gate, on the blocking pool; **it is `cineris-knowledge`'s, reached by a new read operation `project/detect`** (`{ session_id }`, a `user` or `observer` client, in the lane's `reads()` in `cineris-rpc`'s `lane.rs`), so that a client over the wire has it.

**Every step can be skipped and has a default:** the provider (no key; the first prompt then says how to give one), the imports (nothing brought in), the mode (`supervised`), the project (not trusted now, as `n` in 2c; no commands). A pseudo-terminal test runs the flow in an empty home directory to a working session against a local scripted server and a fake credential store, a second sends a prompt at the first frame and checks nothing was chosen, and one test per step (on the scripted `Link`, not a pseudo-terminal) skips it. Every listing the flow shows (provider names, paths found, servers and their commands, detected commands) has a hostile-text test.

### 6. `/export`

- **`/export`** writes the session as Markdown; `/export json` as JSON; `/export <path>` takes the format from the path's ending (`.md`, `.json`). The default file is `cineris-session-<date>-<the session's first eight characters>.md` in the folder the person started in, and a second export the same day adds `-2`, `-3` and so on.
- **The core masks what an export reads.** `session/read` gains `redacted: true` (an addition): the core then applies its own secret filter to each item's text as the log's encoder does (the harness's credentials by value, which the core alone holds and which a client over the wire never has, and every well-known key format), **drops every provider block (`raw`)**, which the log keeps unmasked by design, and does this for a session kept in memory (`--no-session`, whose items were never masked) as for a logged one. An item in progress is left out, and the export says a turn was running.
- **Then the client's stricter pass** (security.md, section 4: "export applies a stricter filter and lists what it masked"): every string of every item, before it is serialised, through `cineris_base::SecretFilter`'s formats again and the address's user-part rule, and the title with them; what was masked, by either pass, is counted (the core's result says how many it masked), and `/export` says where the file went and how many values were masked, by kind (`2 keys, 1 web address's password`). Masking each string before serialising, not the file after, means a key cut by JSON's escapes (a PEM key's line breaks) is still found.
- **Markdown is made safe to read:** control characters made visible and what acts unseen escaped, as `/copy` does; a code block fenced with more backticks than any run in its content.
- **The tests:** an ephemeral session; a key stored in the fake credential store after its entry was logged (the core's by-value pass finds it); a PEM key and a token in a well-known format in a command's output, in both formats; a `raw` block holding a key; a title holding a key. None reaches either file, the masks do, and the count is said.
- **The file:** written private to the user (`cineris_base::private`: mode `0600`, or an access list with the user alone on Windows), **created new, never over a file that exists**: `/export` names the file that is there and writes nothing; a write that fails part-way removes what it wrote. The writing is a function the program gives the application (`Start::export`), run on a worker as `Setup`'s are, so `cineris-tui` touches no file and the interface's thread never waits on the disk; `cineris attach` gives the same function.

### 7. Terminal quirks

Each detected, each with an override in `[terminal]` (user-only, at the next start), each with a test of the decoder or the terminal and a break:

| Quirk | Detection | Override | Test |
|---|---|---|---|
| **Backspace sent as `^H`** ([backspace-sent-as-ctrl-h](../../outstanding/backspace-sent-as-ctrl-h.md)) | On Unix, the terminal's erase character as the program starts (`termios`' `VERASE`): `^H` there means byte 0x08 is Backspace. On Windows, never (Windows Terminal sends DEL for Backspace, and win32 input mode tells them apart). | `terminal.backspace = "auto"`, `"del"` or `"ctrl+h"` | 0x08 is `Backspace` with the override and with an erase character of `^H`, and `Ctrl+Backspace` otherwise; win32 records are unaffected. |
| **Pastes without bracketed paste** ([pastes-without-bracketed-paste](../../outstanding/pastes-without-bracketed-paste.md)) | **Only where the terminal has not confirmed bracketed paste:** the capability queries ask for mode 2004's state (`CSI ? 2004 $ p`), and a terminal that answers that it knows the mode is trusted to bracket its pastes. Elsewhere (no answer, or "not known"), where reads happen (`Terminal::next`): the keys one read gives, none with `Ctrl` or `Alt` and none a sequence's key (text, `Enter`, `Tab`), when there are at least eight of them with an `Enter` that is not the last, or when the read filled the reader's buffer, are one `Event::Paste` of their text; and for 50 ms after such a paste, the keys that follow are its rest, so that a paste's last read (a few keys and its `Enter`) does not send it. **The eight and the 50 ms are to confirm by measurement** (the most keys typing puts in one read, from the key-latency tests' recordings, under load). | `terminal.bracketed_paste`: unset, as above; `true`, no rate detection; `false`, bracketed paste is not asked for and every terminal is rate-detected. | A paste as each kind of terminal sends it (bytes alone, with `\r` and `\n`, in one read and cut across reads) is one paste; typing, a burst a held loop gathers, and keys with modifiers are keys; a confirmed terminal is never rate-detected (the pseudo-terminal tests, which send text and `Enter` in one write, run with a terminal that confirms). |
| **A paste that stalls** ([a-paste-that-stalls](../../outstanding/a-paste-that-stalls.md)) | After a bracketed paste is given up on (no input for the wait), the decoder stays in the paste's tail: the text and line breaks that arrive are kept, and given as the paste's next piece (`Event::Paste`, which the editor appends) when the end marker comes, which is dropped. The tail ends, and what it kept is given as a paste, at the end marker, after a second wait with no input, or at a read that is one key alone: a lone `Enter` or `Ctrl+C` after the give-up is a key. | `terminal.paste_wait` (2 s by default, the time a paste may pause before it is given up on) | A paste cut by a pause past the wait, then its rest with line breaks, then the end marker: one paste's text, no `Enter`, nothing sent; a lone `Ctrl+C` after the give-up is `Ctrl+C`. Paused time, the device's clock. |
| **Function keys through ConPTY** ([function-keys-through-conpty](../../outstanding/function-keys-through-conpty.md)) | Not a detection: the test kit sends a named key as the win32 input record Windows Terminal would (`pty::Session::send_key`, on Windows; the sequence elsewhere), and one system test sends `F1` to `F12` and the arrows that way, each bound to a test action, and checks each reaches the application as itself. A key that does not is reported with what the application read, kept in memory and printed only on failure. The checklist's function-key line is run by hand. | — | The system test, on both systems. |

`/copy` gets the same treatment ([copy-where-the-clipboard-sequence-is-not-taken](../../outstanding/copy-where-the-clipboard-sequence-is-not-taken.md)): where the terminal is known not to take the clipboard sequence (the old console host, tmux, whose `set-clipboard` default does not pass a program's sequence on, GNU screen), `/copy` sends it and also opens the viewer on the text, **with mouse reporting off** there so that a plain drag selects, saying so; `terminal.clipboard = true | false` overrides the guess.
