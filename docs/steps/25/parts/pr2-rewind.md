## Departures from the design, and the choices made

- **The plan's mark.** "A plan that moved between the question and the answer is the core's to refuse" needs the core to know which plan was shown: the plan read gives a `mark`, and `session/rewind` takes it back as `plan`, refused with a new code, `plan_changed`. Both are additions under answer (f). Statuses, not contents, are in the mark: a file edited again after it was shown as edited since does not refuse the rewind, since the person saw it was edited and the core asks about it before it is put back.
- **The plan read refuses what the rewind refuses**, `turn_running` included: a plan under a turn would be stale when it is answered. No test runs a plan under a turn (the core's test rig has no turn to hold open cheaply); since the full review below the check is the rewind's own (`SessionHandle::may_change_history`, which the rewind's `change_history` shares), and its refusal of a change under way is tested.
- **The key is `fork.fork`, not `picker.fork`.** An action is named by its context, and the design gives the fork a context of its own (as `toggle.fast` is `/effort`'s): `[keys.fork] fork = ["tab"]`.
- **`cineris-session` changed**, which "What changes outside `cineris-tui`" did not foresee: the reasons a file cannot be put back were sentences only; `FileRestore::cannot` names them, so the protocol carries a value and the interface its own words.
- **The notice has two wordings.** Inline it is the design's (`… what is above this line is no longer part of it.`); in the transcript read again for the viewer and the full screen, where what is above is the active branch, it is `Rewound to before turn 12. The conversation goes on from there.`
- **What is read again replaces the whole kept transcript.** After a switch in `/sessions` the viewer showed the earlier sessions' blocks above the new header; after a rewind it shows the session's active branch alone, then what was kept since the rewind.
- **A prompt sent while the transcript is read again waits for the read,** so that its turn is not read once from the log and again from its events; `/new`, a switch, `/undo`, `/rewind` and a fork wait for it too, and say so, and a second `/undo` waits for the first (a switch during an undo stays allowed, as step 23's fixes have it). The read is milliseconds in process.
- **`/undo` is drawn as a rewind is** (its notice, the transcript read again); its prompt is not put back into the editor, which the design asks only of a rewind.
- **The question counts the plan's turns**, not the picker's: `The plan undoes 3 turns.` The mark holds the plan's turns, so a turn run since the points were read is counted where the person reads it (the review, below).
- **`/sessions`' `Tab` on another session** closes the one open and forks the other at its end by the `--fork` path (opened, forked, closed); on the session open it forks it directly.
- **A row holds at most 512 bytes of its prompt**, on one line, before the menu sanitises and cuts it; the whole prompt is read again (`session/read` of its item) when its point is chosen, for the editor.

## The tests that show each part

- **The plan and the mark, through the real core** (`cineris-core::it rewind_plan`): a plan read twice is the same and changes no file and no line of the log; a file edited since shows as edited and changes the mark, and a rewind by the old mark is refused with nothing changed; as the harness left it again, the rewind by the first mark puts back and removes what the plan said. A conversation-only rewind is refused when a turn ran since, and not when only a file changed. A session with no log has no plan.

## The full review of the second pull request

The full review of step 25's second pull request read rewind and fork again, the core's side and the interface's. What it found, and what was done; each fix has a test that failed on the code before it, and a break in `mutations/step-25.breaks`.

### The coordinator's decision: `before`

**Settled by the coordinator, with the reviewer's agreement.** `session/rewind`, `session/rewind_plan` and `session/fork` take `before`, an item, beside `to` (a fork's `at`). The core resolves it to the parent of that item's entry in the session's tree, so "before this prompt" is exactly the state before the prompt's entry, as `/undo` has it, and not everything after the item before it. A rewind and its plan name their point by exactly one of `to` and `before`, a fork by at most one of `at` and `before` (none still forks all of the session, which `--fork` and `/sessions` send); two, or none for a rewind, are refused `invalid_params`, as `project/list` refuses a project named two ways. The interface sends `before` the chosen prompt's item for the plan, the rewind and the fork. The mark covers the point. It is an addition ([11-rpc-protocol.md](../../../architecture/11-rpc-protocol.md)): `to` became optional; a core from before it refuses a rewind or a plan with `before` alone, for want of `to`, and forks all of a session for a fork with `before` alone. The open item `a-rewind-to-before-a-prompt-takes-what-followed-the-turn-before` is settled, and its file deleted.

- **What the old point took, shown before the fix.** `sys_a_rewind_before_a_prompt_keeps_what_the_checks_of_the_turn_before_changed` (Linux; a check starts a shell, and git says what it changed) was run first with the old point, `to` the item before the second prompt: the fork left out the first turn's last checkpoint, the plan counted both turns (`t_1`, `t_2`), the rewind removed `made.txt`, which the first turn's check had made, and the log recorded the first turn as rewound. With `before` the fork holds the checkpoint, the plan undoes the second turn alone and names no file, and the check's files stay.
- **The plan edited between the turns does not show the fault.** The review's second example, a plan the person edited between two turns, is not lost by the old point: the edit's notice to the model is an item of the next turn, written before its prompt, so the item before the prompt is that notice, which comes after the plan's entry. `a_fork_and_a_rewind_before_a_prompt_keep_the_plan_edited_before_it` passes with either point, and is kept as the guard of `before` (with `before` the notice, the next turn's first entry, stayed on the branch: the edit it tells of stands. Since the review of the fixes, below, the notice goes with its turn, as `/undo` takes it, and the edit still stands).

**The choice for finding 1.** The reviewer offered (a) `before` a prompt that starts a turn resolved to the parent of that turn's first entry, or (b) `plan_undo` skipping turns the log records as reverted. (a) was taken: it is the coordinator's decision read as "before this prompt's turn", which is what "as `/undo` has it" asks, and it leaves no entry of a turn recorded as rewound on the branch, where (b) would leave them there for good and have every later reader of the branch (the context, `session/read`, the next plan) see them. It changes nothing for an item that began no turn: a steering message, an answer or a tool's result goes back to just before its own entry, as before. What goes with the turn are entries the turn wrote as it began: the notice of a plan the person edited goes, and the edit stays, as with `/undo`. A prompt is a user message that is not steering; a queued one begins a turn of its own, and a turn of `/compact` has none, so steering that comes into one stays an item of its own.

**What was decided against.** For finding 2, a field on `SessionResult`, which `session/new`, `session/open`, `session/rewind`, `session/undo` and `session/set` answer too: it would mean nothing there, and change every one of their constructions; and giving back the entry the fork ends at, which is not on the wire, items are.
