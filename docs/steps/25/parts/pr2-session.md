### Departures from the design, after the review

- **The count is one number, not one for each kind** (point 6 of the design: `2 keys, 1 web address's password`). A mask the log wrote says nothing of what it took the place of, so a logged session's masks have no kind to give; the core's count crosses the protocol as one number; and a count by kind of only the client's own masks would mislead. 09-tui and security.md say so.
- **The count is of the masks the export holds,** each in a string or a key of its items and in its title, and in Markdown each the last pass adds: the count the core makes of its own items, made again by the client on what it writes, rather than the core's count with the client's added to it. A pass that changes nothing cannot add to it.
- **The client's filter is the core's formats** (`SecretFilter::new()`). What makes its pass stricter is the keys, the provider's blocks dropped again, and the Markdown's last pass; the design's "the address's user-part rule" is the filter's own.

### What is left

- No test sees on which thread the client's pass and the rendering run: moving them back would fail none.
- A file system with no hard links (FAT, some network shares) takes the file created new under its name and written there, as before the review; no test reaches that path.
- The two Windows breaks are run only on a Windows runner.

### Departures from the design

- **A long read ended by `Enter` is keys** (L1). The design took a read for a paste "when the read filled the reader's buffer"; the code had put "more than 64 keys" in its place. The rule now: a read with a line break that is not its last key, and at least eight keys, is a paste; a read of more than 64 keys with no line break at all is a paste (its rest may be in the next read); a read whose only line break is its last key is keys, however long. So a line typed through a stall, or sent by `tmux send-keys`, sends, as a single line pasted with its line break always has (a terminal without brackets gives no way to tell). The buffer's filling is not used: on Unix one read takes 4,096 bytes, which typing never fills, and a read that filled it with a line break inside is a burst already; reporting it would have changed `Device`, a public trait, and the one read it would decide otherwise is a line of 4,096 bytes or more ended by its line break, which is keys here.
- **A run of several unseen characters is one mark** (L4): the design drew a run of four or more *of one* escape as its escape and a count; a run of different ones is now one mark too, `\u{e0068}+11`. Still the prompt editor's row only: `sanitize`, the approvals, the transcript and `/copy` show every escape.
- **The eight keys and the 50 ms are not measured.** The design asked that both be confirmed from the key-latency tests' recordings under load; no such measurement was made, here or before. The 50 ms is now of time spent waiting for input, which is what a measurement of gaps between a paste's reads would give.

### What was decided against

- **"The read filled its buffer" on Windows** (M3c's second way): draining every waiting record into one read makes a Windows read what a Unix read is, and needs no change to `Device` or `Ready`.
- **Showing `/copy`'s text and a stored output with `\r` as its symbol** (L7's reach): they are a command's output and what is copied by hand, shown as a terminal would show them; only the two views the finding named, of text a model wrote, changed.
- **Clearing the reader's ids in `rewind.rs`** (L2): that file is the rewind part's, and its question is answered only by a key, which reaches a ready dialog after the ids are cleared.
