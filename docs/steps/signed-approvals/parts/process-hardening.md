# Signed approvals, part: the harness closes its own process

The owner's call 8 of the signed approvals' design: the harness closes its own process to the user's other programs, in this step. A session holds the person's checking key for its life, the key a password makes while a signature is made, and the password while it is typed; code the model runs with the user's rights, where nothing confines it, could otherwise open the harness and read them, or write the checking key so that the session accepts what it forged.

## What was built

- **`cineris_sandbox::harden`** ([harden.rs](../../../../crates/cineris-sandbox/src/harden.rs)), called first thing in `main`, in every process of the binary (the tree's guard and the sandbox launcher included), before anything is read. A failure is said once on standard error and does not stop the program; on Linux the call cannot fail.
  - **Linux:** `prctl(PR_SET_DUMPABLE, 0)`. A process of the same user without `CAP_SYS_PTRACE` cannot attach to the harness with `ptrace`, nor open its `/proc/<pid>/mem`, `environ`, `fd`, `maps` or `exe`, whatever Yama's `ptrace_scope` is; no core dump of it is written. Its `stat`, `status`, `comm`, `cmdline` and its `/proc/<pid>` folder's owner stay readable. A program it starts is dumpable again from its `execve`.
  - **Windows:** the process's list gives the user and `OWNER RIGHTS` (S-1-3-4) `SYNCHRONIZE`, `PROCESS_QUERY_LIMITED_INFORMATION` and `PROCESS_TERMINATE`; SYSTEM and Administrators every right. Each thread's list gives the user and `OWNER RIGHTS` `SYNCHRONIZE` and `THREAD_QUERY_LIMITED_INFORMATION`. The threads that run at the call are found in a list of the system's threads (`CreateToolhelp32Snapshot`) and given their list; a thread made later gives itself its list as it starts, from a TLS callback (in `.CRT$XLY`, as the standard library's own is in `.CRT$XLB`), which does nothing until the call has made the list, and calls only `SetKernelObjectSecurity` on its own pseudo-handle, safe under the loader's lock.
  - **Windows, the standard handles** (the OS-layer review, after the design's review): `SetHandleInformation(GetStdHandle(…), HANDLE_FLAG_INHERIT, 0)` on the input, output and error handles, first in the call. A shell starts Cineris with inheritable console handles, and `serve --stdio` with the protocol's pipes; every `CreateProcessW` with handles inherited (the standard library's `Command::spawn` in `tree::windows`, `cineris_base::git::start`, `process::brief::run`) handed them on at the same values, so a command could find the console's input among its handle values and peek at or read the password, or write keys, even with no console of its own. A child given the standard handles on purpose (the external editor: `Command::spawn` with the default `Stdio::inherit`) still gets them: the standard library duplicates each as an inheritable copy for that child, under its own lock around `CreateProcessW`, and closes the copy after; it never passed the handle itself. The pty driver's `CreateProcessW` inherits nothing and gives its child invalid standard handles already.
  - **`harden::traced()`**, for the password prompt to refuse at: Linux `TracerPid` in `/proc/self/status` other than 0 (a status that cannot be read counts as traced); Windows the debug port, as `NtQueryInformationProcess(ProcessDebugPort)` gives it, which is what `CheckRemoteDebuggerPresent` asks (with the crate's existing `windows-sys` features: no feature added). **`harden::hardened()`** says whether the call took.
- **The harness's word, on Linux** (`cineris_sandbox::session::channel`, [channel.rs](../../../../crates/cineris-sandbox/src/session/channel.rs)). A closed harness's `environ` and `exe` are root's to read, which the nested run's moved-stores check and guard B's "the very file" rule read. So `session::mark`, which every harness calls before it starts a process and which did nothing on Linux, now makes a pair of `SOCK_SEQPACKET` Unix sockets, writes one record into the end it keeps (a tag, its start time from `/proc/self/stat`, and `NAME=value` for each of `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME`, `CINERIS_CONFIG`, `CINERIS_DATA_DIR` that it has), closes the other end, and clears close-on-exec on the kept end so that everything it starts inherits it. A process reads, of every descriptor it holds, each `SOCK_SEQPACKET` Unix socket whose `SO_PEERCRED` is a process of its own user, and looks at the record with `MSG_PEEK`. The peer's credentials are those of the process that made the pair, set by the kernel then; the record cannot be changed or added to, as its writing end is closed and what is sent into the kept end goes there. A command can close it or take the record out (then a nested run refuses: failing closed), never hold one that names its harness and says something else. Cineris makes no other sequenced-packet socket and connects to none.
  - **The nested run's stores** are compared with the word of the harness its line of parents reaches, started when the word says (`/proc/<pid>/stat`'s 22nd field). No such word held, or two that say different things, refuses, naming "the stores the session gave what it starts, which this process does not hold".
  - **Guard B** takes a process of the line for a harness also when this process holds its word, whatever its name, and a process `/proc` does not show when it holds its word.
  - **The sandbox launcher**, which marks every descriptor above the standard three close-on-exec before it becomes the command, finds the words it holds before it confines itself and lets them pass.
- **A process of this user that `/proc` does not show** (the independent review of the design, point 1). Where `/proc` is mounted with `hidepid`, a process that is not dumpable is hidden from the other processes of its user, so a closed harness is hidden from its own commands, and the line of parents read past it as "another user's" before. Now a process `/proc` does not show is asked with a signal of nothing (`kill(pid, 0)`): there and of this user is `Seen::Hidden`, which is not known and refuses wherever on the line it is; another user's (`EPERM`) or gone (`ESRCH`) ends the line, as before; and one whose word this process holds is a harness.

## The independent review's four points

1. **`hidepid`:** handled as above. A process of this user hidden on the line refuses, unless the harness's word names it. Tested with a simulated hidden entry (`a_process_of_this_user_that_proc_hides_is_not_known`) and with the real look (`a_process_proc_does_not_show_is_told_by_whose_it_is`, on this process's own id, which `kill(pid, 0)` finds). **Its cost, for the maintainers to decide:** an SSH login's own `sshd` process runs as the user and is not dumpable (it changed its user without an `execve`), so where `/proc` has `hidepid`, every line of parents in such a login meets a hidden process of the user: the approving subcommands, the application, `serve` and `attach` refuse there, and a headless run is held to `read-only`. Nothing short of a reading `hidepid` allows tells it from a closed harness. Recommendation: keep it failing closed, and say so in the refusal's words (it names `hidepid`); `PIDFD_GET_INFO` (Linux 6.13 and later) gives a hidden process's parent and user without `/proc`, but not its program, so it does not tell them apart either.
2. **A tracer attached before the call:** `harden::traced()` is built, for the prompt to call. What it cannot tell: a `/proc/<pid>/mem` (Linux) or a process handle (Windows) opened before the call, which keep working; neither system lists them for the process.
3. **Windows threads:** each thread gets its list, those running at the call and every later one, and `OWNER RIGHTS` is in both lists. **The token's default list (`TokenDefaultDacl`) is not changed, against the review's suggestion:** every process the harness starts copies its token, default list and all, so each command, and everything it starts, would be closed to the user's other programs too (against "a command started by a session is unaffected"), and the objects they make without a list of their own (a named semaphore `cargo` gives `rustc` for its jobs) could no longer be opened by their own children with the rights they need. A thread gives itself its list in a TLS callback instead. What that leaves: a thread made without the loader's notice of a new thread, and one opened in the moment between its making and its first instruction.
4. **The creator's full handle:** stated in [security.md](../../../security.md), section 3, with the console host's.
5. **Inheritable standard handles** (the OS-layer review): built, above, with a test that a probe the closed process starts with no console of its own (`CREATE_NO_WINDOW`) finds the closed process's console input among none of its handle values, where it finds it under one that did not close itself. Its reach is narrower than it looks: a session's commands share the harness's console, and open its input by name (the table above).

## Measured

On the reference machine, a release build, not idle (other runs beside it), `perf_closing_a_process`: the call (`prctl`) **0.094 µs** a call, median of 50; `traced()` (a read of `/proc/self/status`) **4.6 µs**. Start-up does not move by a measurable amount on Linux. **Windows has not been measured:** its call makes two lists, sets one on the process and one on each thread, and takes a list of the system's threads (`CreateToolhelp32Snapshot`), which may cost a fraction of a millisecond; the same test on a runner (`gh workflow run try --ref <branch> -f os=windows -f command="perf -p cineris-sandbox"`) measures it, and `-f command=startup -f profile=dist -f against=main` its share of a start. The Linux nested run reads its word in place of `environ`: a listing of `/proc/self/fd` and a few calls a descriptor, once a check.

## Breaks

`mutations/signed-approvals-process-hardening.breaks`, six, each with the test named that catches it: the `prctl` skipped; a word counting for any process; the launcher dropping the word; a hidden process of the user ending the line; the Windows process list keeping `PROCESS_VM_READ`; a thread made later keeping the default list. The word not compared is step 28's `session-linux-moved-store-same`, moved to the code as it is now (the nested run's system test catches it), and step 28's `session-linux-name-alone` and `session-windows-moved-store-same` were moved to the code as it is too. `cargo xtask mutate --check --tests` passes on both lists. **No break was run:** the part ran no `mutate` locally, so the verdicts are for a run on the runners (`gh workflow run try --ref <branch> -f command="mutate signed-approvals-process-hardening"`, and `-f os=windows` for the two Windows breaks).

## For the reference machine's Windows session

Nothing below runs on a hosted runner, which has no person at a console:

- Start `cin` from Windows Terminal (PowerShell) and from `cmd`, and open the external editor with Ctrl+G: it opens, takes keys and gives its text back (the standard handles are given to it as copies).
- With the session open, from another PowerShell of the same user, not elevated: Process Explorer, or `Get-Process -Id <pid> | Select-Object -ExpandProperty Modules`, is refused the harness's memory and its threads' stacks; Task Manager still ends it.
- A command the session runs (`ping -t localhost`) can be opened from that PowerShell as before (its modules listed).
- Under the session, a command that opens `CONIN$` and peeks while a password is typed sees it (the shared console, left open above): to confirm, with the result in the step's record.

## Left open

- **Windows, the creator's full handle** and the console host's: closing them needs the harness made by a program that keeps no full handle of it (a first process that starts the real harness with its list given at `CreateProcess`, both process and first thread, and keeps only a limited handle). It costs a process's start on every run (several milliseconds on Windows), and is beyond this part: for the maintainers.
- **`hidepid` and SSH**, above.
- **Linux, what was opened before the call** (a `/proc/<pid>/mem` file): not told by `traced()`.
