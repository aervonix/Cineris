# Signed approvals, part: fixes to the harness's word

A focused review of the harness's word ([process-hardening.md](process-hardening.md), "The harness's word, on Linux") found five things, each Low, with failing tests. The maintainers' rule for this guard: **a word that is missing, or a line that cannot be known, means refuse.** This part fixes them in `cineris_sandbox::session` ([session.rs](../../../../crates/cineris-sandbox/src/session.rs), [channel.rs](../../../../crates/cineris-sandbox/src/session/channel.rs)) and the nested run's refusal in `cineris-cli`'s `nested_run`.

**Step 28's fixes merged into `main` while this part was built** (their part B: [guards.md](../../step-28-fixes/parts/guards.md)): they compare a nested run's stores with every harness of the line (`harnesses_on_the_line`, `moved_from`), refuse a store variable given twice, read process 1, and refuse a line that cannot be read; but they read each harness's `/proc/<pid>/environ`, which a harness that closed itself does not let its user read. The signed approvals' work was rebased onto them: **each harness's stores are read from its word, never its `environ`**, a harness of the line whose word is not held refuses, and the word is written as Cineris reads its own environment (`value_in`: the last entry of a name, an empty value as none, an entry that is not Unicode left out), so that `moved_from` compares what the harness used.

## Step 28's tests, with a closed harness

- `guards::sys_a_shell_named_cineris_on_the_line_does_not_pass_moved_stores`: a copy of `/bin/sh` named `cineris`, run with a moved `HOME` between the session and a nested run. Its `environ` was compared, and named `HOME`; it is a harness by its name and gave no word, so the run is now refused for that, and the test asserts it. The every-harness rule itself is held by the word tests above, which its break (`stores-compared-with-the-nearest-harness-alone`) now names.
- `guards::sys_a_nested_run_whose_line_cannot_be_read_is_refused_with_its_stores_moved`: asserts the reason now given.
- `guards::sys_a_harness_that_is_process_1_is_seen`: unchanged; the word gives the harness's id in the reader's namespace, and its start is read from that namespace's `/proc`.
- `nested::each_variable_that_moves_the_stores_refuses_a_nested_run` and `session::tests::a_nested_runs_stores_are_compared_as_cineris_reads_them`: unchanged; the words go through the same `moved_from`.
- `session::tests::the_harnesses_of_a_line_are_every_one_to_process_0`: `Ok`/`Err` where it had `Some`/`None`.
- `tests/it/session.rs` is Windows's, which reads no other process's environment: unchanged.

## What it costs, and what the maintainers may want to decide

- **Where `/proc` is mounted with `hidepid`, every nested headless run refuses**, since a harness is hidden from its commands and the line past it cannot be read; so does every headless run over SSH there (as step 28's fixes already had it: the login's hidden `sshd` leaves the line unread). That follows the rule, and the refusal names `hidepid` and what to do. **Recommendation:** keep it. `PIDFD_GET_INFO` (Linux 6.13 and later) gives a hidden process's parent and user without `/proc`, which would let the line be read past a hidden harness; it does not tell what the process is, so it would not lift the SSH case. It is left for later.
- **A closed harness run under another name than Cineris's** is not seen by the RPC socket's check of a peer (step 28's `under_a_session_of`), which reads the peer's line with the server's own words, not the peer's: the same residual as B's, stated in security.md.
- **Guard B, where its line reaches no harness, now lists this process's descriptors** (`/proc/self/fd`) for words, and reads the `stat` of each word's maker. Not measured: a few dozen system calls once a run, beside a start that is milliseconds.
- **`cineris_sandbox::session::moved_stores` changed its type** (`Option<String>` to `Option<Moved>`), for the CLI's two sentences; its one caller outside the crate is `nested_run`. Windows's gives `Moved::NotKnown` where `CINERIS_SESSION_STORES` is not set, with words of its own, and is otherwise unchanged. Step 28's `stores-not-compared-without-a-harness` and `nested-run-moved-stores-passed` breaks were moved to the code as it is.
- **Under Landlock's scoped signals** (the residual the maintainers accepted on 2026-11-27), a confined command's `kill(pid, 0)` of a harness outside its sandbox is `EPERM`, read as another user's: where `/proc` also hides the harness, a word held by a confined command that detached itself reads as its maker gone. Without `hidepid` the maker's `stat` is read and its start compared, and the word counts.

## Breaks

`mutations/signed-approvals-word-fixes.breaks`, one for each rule this part adds, each naming the tests that catch it. Moved to the code as it is now: step 28's `session-line-passes-a-harness` (the hidden harness's arm) and `nested-run-moved-stores-passed` (`nested_run`'s `match`); step 28's fixes' `stores-not-compared-without-a-harness`, `a-peers-line-is-not-read`, and `stores-compared-with-the-nearest-harness-alone` (now caught by the word tests: the shell named `cineris` gave no word, which refuses with the break made too); the process hardening's `a-hidden-process-of-this-user-ends-the-line` (`Whose::Ours`).

## What ran

On the reference machine (Linux), after the rebase onto step 28's fixes:

- `cargo xtask clippy -p cineris-sandbox` and `-p cineris-cli`, and Windows's lint from Linux (`cargo xwin clippy --target x86_64-pc-windows-msvc --workspace --all-targets --locked -- -D warnings`): clean.
- `cargo xtask test -p cineris-sandbox`: 167 passed (4 ignored `perf_` tests skipped).
- `cargo xtask test -p cineris-cli -E 'test(nested) | test(guards) | test(hardened)'`: 15 passed, `guards::sys_a_harness_that_is_process_1_is_seen` among them (user namespaces are open there).
- `cargo xtask test -p cineris-rpc`: 52 passed, 1 failed, `conformance::every_scenario_is_the_same_in_process_and_over_the_wire`: its scripted trust question is answered with a bare yes, which the signed approvals' core now refuses (`invalid_answer`: a yes needs the person's signature). It is for the front end's part, not this one.
- **The review's own tests** (`cargo xtask scratch-test cineris-sandbox review_word.rs`): the line not known passes; the closed harness under another name without its word fails, as W3's residual says; **the word a command makes fails too, by the same residual:** its harness runs as the test binary, under a name that is not Cineris's, and the program between it and the nested run is `python3`, whose `subprocess` closes every inherited descriptor (`close_fds`), the harness's word with them, so that harness is not seen at all. Where the harness is known by its name (a copy named `cin`), the same attack refuses: `harden::sys_a_word_a_command_makes_does_not_stand_for_its_session`.
- `cargo xtask mutate --check` and `cargo xtask outstanding --check`: clean. **No break was run:** no `mutate` on the reference machine; the verdicts are for a run on the runners (`gh workflow run try --ref <branch> -f command="mutate signed-approvals-word-fixes"`).
- Windows ran no test: nothing of this part's code runs there but `moved_stores`'s type.
