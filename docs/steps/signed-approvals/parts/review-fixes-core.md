# Signed approvals, part: fixes from the permission path's review

An independent review of the first pull request's permission path ([core-wiring.md](core-wiring.md)) found what lapses or blocks without the person's key; a review of the system's layer found two more in the reset. Each finding below, its fix in the core, and the test that failed before the fix. The breaks are in [mutations/signed-approvals-review-fixes-core.breaks](../../../../mutations/signed-approvals-review-fixes-core.breaks).

## The findings

**1. Medium: under `--trust-project` with no key, a pinned hook's or extension's gate lapsed.** `assemble::trust` returned `ForTheRun` without reading the store, so no `Uncounted` was built; the hooks' store was read with no key, and `ext::hooks::in_session`'s trusted branch found the hook untrusted and held nothing; the pipeline judged the extension untrusted, and `not_found` looked only at signed pins. The maintainers' answer to call 4 keeps every gate in a headless run.
- **Fix:** `--trust-project` reads the project's entry with the session's key, and the session says once that what the entry approved does not count and holds its gates (`assemble::for_the_run_uncounted`). `Uncounted` is built whenever the entry is there and does not count, the project trusted for the run or not. In `in_session`'s trusted branch a hook named in `held(Hook)` of an entry that does not count is on its event, failing; in the pipeline a found project extension named there is not loaded, says why, and holds its gates at the hash pinned, unless it stands approved (`uncounted_found`, and the uncounted loop's skip of what stands approved). A build without the script engine holds them through `without_engine::in_session`'s `uncounted_gates`.
- **Tests:** `cineris-core::it signed::under_trust_project_without_the_key_a_pinned_hooks_gate_holds` and `under_trust_project_without_the_key_a_pinned_extensions_gate_holds` (the review's two), the control `under_trust_project_with_the_key_the_pinned_hook_runs`, `ext::hooks::tests::under_trust_project_a_hook_an_entry_that_does_not_count_pins_holds_its_event`, and `ext::without_engine::tests::a_session_without_the_engine_holds_what_an_uncounted_entry_pins`.

**2. Low-medium: the reset could be blocked by another program.** `Core::reset_approvals_at` stopped at a `pins.toml` it did not understand, at a folder or link at a store's name, at a folder at a lock's name, and at a lock held by a process left running (refused after `LOCK_WAIT`, its stores half-done).
- **Fix:** a store whose read or write fails is left as it is and said in `ResetReport::left`: what it holds counts for nothing under the new key, and it is never moved aside, which would lift its gates. A folder or link at a lock's name is moved aside. Each store's lock is tried for the reset's wait (`LOCK_WAIT` for a person's reset) and, held past it, the store is left and said; the key file's lock held past it stops the reset before anything changes. `reset_approvals_within` takes the wait, for tests that hold a lock.
- **Tests:** `signed::a_store_not_understood_does_not_block_a_reset` (the review's, with a folder at `trust.toml` too), `signed::a_folder_at_a_locks_name_does_not_block_a_reset`, `signed::a_held_lock_is_waited_for_no_longer_than_the_wait`.

**2b. The system layer's review, F3, low: a read-only key file stopped a reset after it had stripped every store.** The atomic writer refuses a read-only file, and only something that was not a regular file was moved aside.
- **Fix, in this order:** the new key file is written first under a new name beside the key file's (`approval-key.toml.new-` and sixteen random hexadecimal digits), which shows it can be, and nothing changes when it cannot; then the stores are stripped; then whatever stands at the key file's name, regular files included, is moved aside to a name of its own (`.aside-` and sixteen random digits, never the process's id, which a folder planted at the next ids' names would block); then the new file is renamed into place. The key file's lock is held throughout.
- **Tests:** `signed::what_stands_at_the_key_files_name_is_moved_aside_at_a_reset` (a read-only key file of the model's, a folder, and a link to a file elsewhere; the new password opens, and what was there is aside, a link's target untouched).

**2c. F6.3: tests of the reset's standard cost and of what is moved aside.** `Core::reset_cost` is the cost a person's reset writes, apart so that a test sees it without making a key at it (Argon2 at the standard cost takes seconds in the `ci` build, whose third-party crates are unoptimised): `signed::a_reset_writes_the_standard_cost`. A folder and a link at the key file's name: the test above.

**3. Low: while the user's pins did not count, a pinned extension that is gone held nothing.** `not_found` and the pipeline's lookup of a pinned hash used `list` and `get`, which give nothing when the pins do not count.
- **Fix:** while they do not count, the pipeline keeps what they hold (`PinsUnused::held`), and a gone or left-out extension they pin holds its gates at the hash pinned, as it does while they count; a build without the engine the same (`Judging::pins_held`, `without_engine::pin_of`). Deleting `pins.toml` whole stays the stated residual, now said beside the existing sentence in [12-extensions.md](../../../architecture/12-extensions.md) and in `docs/security.md`.
- **Tests:** `signed::a_pinned_users_extension_gone_holds_its_gates_without_the_key`, `ext::without_engine::tests::a_pinned_extension_gone_holds_its_gates_while_the_pins_do_not_count`; the residual, `signed::the_pin_store_deleted_whole_holds_nothing`.

**3b. Found by the front-end part: `cineris ext disable` let a gating extension go unasked.** `Core::extension_gates` found the pin through the listing, which reads the pins with the core's key; a subcommand's core never has the approvals open, so the pin did not count, and the extension "held no gates": it was turned off with no question, and with no `--hash` where there is no terminal (step 28's M1 asks first).
- **Fix:** the pin is looked for among every pin the store holds, signed or not (`pins(None).held()`, as `extension_removal` and `disable_extension` look), and what it registered is taken from the cache at that pin's hash. A pin store that cannot be read leaves what the extension holds not known, which asks.
- **Test:** `signed::the_gates_a_disable_lets_go_are_found_without_the_key`; the front-end part's `commands::sys_ext_add_disable_and_remove_act_only_on_what_is_shown` holds it end to end once both are merged.

**4. Low: the core's signing methods took any key and wrote before checking it.** `trust_project_with`, `add_extension` and `remove_extension` proposed, signed and committed with the key given, and only then did `open_approvals` refuse.
- **Fix:** each first asks `Core::signing_key_refusal`: no key file (`NoKey`), a key that does not open it (`NotThePassword`), or one that is not the open key (`NotTheOpenKey`) is refused with the refusal's words (`key_refused`), and nothing is evaluated, written or pinned. No signature changed.
- **Tests:** `signed::a_key_that_may_not_sign_writes_nothing`, `signed::an_extension_is_neither_added_nor_removed_with_a_key_that_may_not_sign`.
- **For the CLI part:** the core now reads `approval-key.toml` from the state directory before it signs, so a test that signs with a key made in memory must write its key file there (`KeyFile::write`). The core's `World::core` and the RPC tests' probe world do; `crates/cineris-cli/src/ext/tests.rs`'s world does not yet.

**5. Low: a question shaped by one reading was proposed from a second, and the ask-again loop had no bound.** An older signed entry put back between `look`'s reading and `TrustStore::propose`'s would be signed again, at a new revision, by a yes to what is new.
- **Fix:** `TrustProposal::is_against` (`cineris-policy`, read-only) says whether a proposal was worked out against the entry a reading holds; `look` puts no question when it was not, and the session opens with the trust as it stands. `trust_for` puts the question three times at most (`TRUST_ASKED_AT_MOST`), then opens with the trust as it stands and says why (`assemble::moved_each_time`).
- **Tests:** `signed::a_question_is_put_only_with_a_proposal_from_its_own_reading`, `signed::the_question_is_put_three_times_at_most_when_the_entry_moves_under_each_yes`, and `cineris-policy trust::tests::a_proposal_is_against_the_entry_it_was_worked_out_from`.

**6. Tests the review found missing.** The core's key refusals with a key file the test writes (`World::set_up_key`): `signed::the_cores_key_refusals` (`person_key`'s `NoKey`, `NotThePassword` and `NotTheOpenKey`; `open_approvals`'s `NotTheOpenKey`; `set_up_approvals`'s `KeyExists`); and `without_engine::uncounted_gates` with an entry that does not count (above).

**7. The protocol and the docs.**
- `clients::trust_answer_problem` takes a yes only over a proposal that is the `project` unit of the asking session's project (`Clients::ask_trust` keeps the project's key with the open question): never another project's, nor the user's pins. Test: `clients::tests::a_trust_yes_is_taken_only_over_the_asking_projects_trust`.
- `TrustRequest.proposal`'s documentation said a yes without one held for the session; it trusts nothing, and the core never asks without one. The schema and declarations are regenerated.
- `docs/security.md` section 3 and [core-wiring.md](core-wiring.md) say what the first pull request closes and what stays unsigned until the second: stored approvals, the accepted entries of what was learned, and the registration cache, whose entry can drop an approved extension's gate. `06-permissions-and-sandbox.md`'s "As built in the signed approvals step" says the fixes above, by the maintainers' leave.

## What ran

On the reference machine, its disk stalling for much of each run:

- `cargo xtask test -p cineris-core`: 754 run, every one passed but three that failed under the stall (`harness_git::sys_a_filter_the_harness_git_runs_is_not_found_in_the_workspace` and `sys_a_folder_a_reload_makes_writable_is_kept_out_of_the_harness_gits_path`, "git did not answer within the time one look may take"; `extensions_reload::with_the_examples_approved_no_engine_starts_until_one_is_used`, out of time), each of which passed run again alone.
- `cargo xtask test --dependents -p cineris-policy` (`cineris-policy`, `cineris-core`, `cineris-ext`, `cineris-cli`, `cineris-rpc`): 1,453 run, 1,435 passed, 15 failed, 3 out of time. The three out of time passed run again alone. Of the 15:
  - eleven are the ones [core-wiring.md](core-wiring.md) lists as failing until the parts after it land: `cineris-cli`'s system tests of `ext add`, `ext remove`, `permissions trust`, the examples, the runs and the signal that add an extension or trust a project through the command line's stub, the interactive application's trust dialog, `serve --stdio`'s conformance, and `cineris-rpc`'s conformance test (an unsigned yes);
  - four are `cineris-cli`'s unit tests in `src/ext/tests.rs` (`an_extension_is_added_listed_turned_off_and_removed`, `the_place_is_looked_at_again_at_the_yes_and_leftovers_are_cleared`, `a_folder_set_aside_that_cannot_be_removed_does_not_fail_the_write`, `what_cannot_be_added_or_removed_is_refused_first`), refused `key_refused` by finding 4's fix: their world signs with a key whose file is not in the state directory. Its world writing the key file (`KeyFile::write` to `Core::approval_key_file`) is the CLI part's.
- `cargo xtask schema` (the protocol's schema and declarations regenerated), `cargo xtask fmt`, `cargo xtask clippy -p cineris-core`, and `cargo xtask check` (formatting, rules, the workspace's clippy, the build without the script engine, the generated files and the licences; the break lists after the fixes below), and `cargo xtask mutate --check --tests`.
- One of step 28's breaks (`trust-for-the-run-reads-no-pin-of-a-hook`) named the read of the trust store under `--trust-project` that finding 1 moved into `assemble::trust`: it names that read now.
- Not run: `cargo xtask mutate` (no long run on the shared machine; the breaks were checked to apply and their `caught-by` names to exist), `stress`, and CI, Windows among it.
