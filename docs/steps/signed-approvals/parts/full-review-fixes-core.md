# Signed approvals, part: fixes from the full review (stores and core)

The full independent review of the first pull request found ways a gate lapses, or a person is kept from what they approved, through the stores and the core. Each finding below, its fix, the test that holds it, and its break. The breaks are in [mutations/signed-approvals-full-review-core.breaks](../../../../mutations/signed-approvals-full-review-core.breaks). The command line's, the application's and the hardening's findings are a part of their own, made beside this one; the contract between the two is the summary of item 1.

## The findings

**1. A signed change dropped, unseen, a pin it did not show** (both reviewers; the front ends' finding 1, the core's L2). `PinStore::propose` started from an empty set when the pins did not count, and `TrustStore::propose(Trust)` rebuilt an entry that did not count from what was approved alone. So after a reset, an upgrade, or one write by the model, the person's next unrelated yes (`ext add` of another extension, a "no" to `permissions trust`'s extensions question) signed a set without the pins that held gates, and the gates lapsed.

- **Fix: pins that do not count are carried forward as restrictions, never signed and never dropped by a signed change** (the design the session settled). `pins.toml` (version 2) has `[[held]]` beside its signed `[[pin]]`s, and each `trust.toml` entry (version 3) `[[project.held]]` beside its `[[project.pinned]]`: what earlier pins named, kept only for their gates. Both versions are this step's own and unreleased.
  - A proposal over a set or an entry that does not count moves its pins into the held list. A pin approved again moves from held to signed; a signed `Unpin` or `Drop` of a name takes it out of both. A name both signed and held, or held twice, refuses the whole file, as two pins of one name do.
  - `UserPins::held` and `ProjectTrust::held` give the signed pins and the held list: what restricts. `UserPins::unsigned`, `unsigned_of` and `ProjectTrust::unsigned` give what holds gates and approves nothing (the held list beside a set that counts; everything beside one that does not). `standing`, `get`, `list`, `pinned_of` and `registration` count the signed pins alone, as before; the statement signs them alone.
  - The session holds a held entry's gates as one approved and not loaded: the user's found or gone, at the hash held (the pipeline's `Unstood::Held`, `Stand::Held`; `ExtensionStanding::Held` in a listing and a build without the engine); a project's through the generalised `ext::found::Uncounted`, which an entry that counts and holds extensions unsigned now builds too; a project hook held unsigned beside a signed entry is on its event, failing (`ext::hooks::in_session`).
  - A proposal's `summary()` names each pin carried as held ("the extension `probe`: approved earlier but not signed by your key; kept, holding its gates, approving nothing"), and a signed change of a signed entry by `Trust` names each pin it takes away. The core's signing methods return it: `Added.summary`, `Removed.summary` (`Removed` is no longer `Copy`), `Trusted.summary`, for the front ends to print.
- **The maintainers' two requirements, added while this part was under way.** Nothing reads the held list as a grant, on any path: no standing, no prompt text (section 7), never shown as approved before (`ApprovalsHeld::project_pins` gives the entry's own pins only, `ProjectTrust::named`); a held pin's hash keeps the registration cache's entry for its gates (`pinned_hashes`, the pin store's `held()`), and never makes a registration count. And a planted held entry can only deny: `docs/security.md` section 3 says so beside the deletion residual.
- **Tests:** the reviewer's scratch test, both cases, as `cineris-core::it signed::an_unrelated_yes_keeps_the_gate_of_a_pin_it_did_not_show`; `signed::a_trust_that_leaves_an_extension_out_keeps_the_gate_an_unsigned_entry_pinned` (`permissions trust`'s "no" over an unsigned entry); `signed::a_held_entry_alone_approves_loads_and_adds_prompt_text_for_nothing` (the user's and a project's, at the very hash found, cached with prompt text); `ext::without_engine::tests::a_held_pin_and_a_name_the_users_key_does_not_own_hold_their_gates`; in `cineris-policy`, `trust::pins::tests::a_held_pin_is_approved_again_or_let_go_only_by_the_persons_yes`, `a_held_entry_written_by_another_program_only_holds_a_gate`, `a_held_list_is_read_strictly`, `trust::tests::an_entry_that_does_not_count_is_carried_as_held_by_the_next_trust`, `a_held_entry_written_by_another_program_only_holds_a_gate`, and `a_pin_not_signed_by_the_person_is_never_signed_with_their_next_pin` changed to the held form.

**2. After a reset or an upgrade the application never asked again** (the core's M1). `assemble::look` kept the trust question from an entry that did not count whenever the approvals were closed, an unsigned one included; after a reset nothing carries a signature, so `ApprovalsHeld::to_use` was false, the password was not asked for, and the core stayed closed.

- **Fix:** the question is kept back only for `Checked::NoKey` (a signature, and no key to check it). An unsigned entry gets the no-key `Trust` proposal, and the front end sets up or opens the approvals at the yes. `to_use` is true when the key file cannot be read and something carries a signature, so that the unlock's refusal names the key file and the reset. The session's words (`person::uncounted`, `project_uncounted`, `script_hooks::way_out`'s `Uncounted`) say "asked again" and "the project's trust question asks when a session opens", which now holds.
- **Tests:** the reviewer's scratch test as `signed::a_project_whose_signature_a_reset_took_off_is_asked_about_again`; `signed::what_carries_a_signature_is_counted_and_nothing_is_opened` (an unreadable key file with a signature beside it).

**3. A held key-file lock blocked the reset** (the core's M2). `reset_approvals_within` failed after the wait, every time, while another program held `approval-key.toml.lock`.

- **Fix:** a key lock still held after the wait is treated as a folder at its name is: moved aside (to a random aside name) and a fresh one locked. The reset first makes its state directory owner-writable (`0700` on Unix). The Windows residual is said in `person.rs`'s documentation and `docs/security.md` section 3: a program that holds the key file or its lock open without `FILE_SHARE_DELETE` blocks the rename until it exits. The module documentation's "Nor can another program keep the person from a reset" now says what holds.
- **Tests:** `signed::a_held_lock_is_waited_for_no_longer_than_the_wait` (the key lock held: the reset goes on, the lock aside), `signed::a_state_directory_without_its_write_does_not_block_a_reset` (Unix).

**4. Gates lapsed through what the user's folder of extensions names** (the core's M3, two of its three ways).

- **Fix:** a folder of the user's that takes a project extension's name lets the project's gates go only when the user's own extension of the name is pinned with a signature that counts (`UserNames::owns`; the pipeline's `released`, its uncounted loop, and the listing). Otherwise the project's extension is not used, and holds its gates as an approved one not loaded does (`Unstood::Taken`, `Stand::Taken`; in a build without the engine, `NotUsed` held by its pin). With more than `MAX_PLACES_PER_ROOT` places the cut takes every name from loading, and none from its gates.
- **The third way,** `[extensions.<name>] enabled = false` in the user's configuration, is the user configuration's, which the third pull request pins: said in [12-extensions.md](../../../architecture/12-extensions.md), `docs/security.md` section 3, and [the open item](../../../outstanding/approvals-signed-with-a-key-that-needs-a-person.md) (the `[extensions]` table among what is pinned).
- **Tests:** `signed::a_folder_of_the_users_that_takes_a_projects_name_releases_no_gate`; `ext::found::tests::the_users_names_are_taken_within_the_bound_on_places_the_session_watches` (the cut, and pins that do not count); the without-engine test of item 1.

**5. The trust store and the stored approvals wrote through a link** (L8). `TrustStore::write` and `ApprovalStore::write` set `follow_links: false`, as the pin store does. **Tests:** `cineris-policy trust::tests::a_link_put_at_the_stores_name_after_its_read_is_not_written_through` and `approvals::tests::…` of the same name: a link put at the store's name after its read, before its write.

**6. A password that is not UTF-8 was copied unwiped** (L10). `KeyFile::make` and the reset count characters where the password lies (`signed::password_chars`), with no copy; one that is not UTF-8 is refused as not text (`KeyError::PasswordNotText`), which the prompt never makes. `signed/key.rs`'s documentation says that `ring`'s HKDF `Prk` is not wiped either, and that nothing is locked in memory, so swap can hold a secret: the residual under the memory protection (`docs/security.md` section 3 too). **Tests:** `cineris-policy signed::key::tests::a_password_shorter_than_twelve_characters_is_refused`, `signed::a_reset_writes_the_standard_cost`.

**7. Breaks.** L3: `unsigned-pins-are-listed` (`signed-approvals-policy.breaks`) names `a_registration_or_a_revision_changed_by_hand_counts_for_nothing`, which now asserts `list()` empty and `New`, and `cineris-policy::it pins::pins_count_only_with_the_key_they_are_signed_by`. L4: `a-moved-yes-is-not-asked-again` (`signed-approvals-core-wiring.breaks`) boxes its answer, and compiles. Moved by this part's changes: `an-uncounted-entry-holds-no-extension-gate`, `an-uncounted-entry-holds-no-hook-gate`, `an-unopened-entry-is-asked-about` (core wiring), `trust-project-hook-of-an-uncounted-entry-runs-or-lapses` (the review's core fixes), `a-short-password-is-taken` and `unsigned-pins-are-laundered`'s rule (policy), and `step-28-close`'s `a-changed-extension-gates-by-its-manifest-as-found-without-the-engine` (`occurrence: 2`). Every list applies (`cargo xtask mutate --check`).

**8. Docs that claimed more than the code** (L9, this part's).

- `docs/security.md` section 3's signed-stores row says exactly what holds: an entry that does not count holds the gates of each extension it names, found, changed or gone, and of each project hook it names that the configuration still has; a pin taken out of a set or an entry lifts no gate, a whole store or entry taken away does (the residual).
- The rollback's narrowing by a reset holds only while the old key file stays gone: putting the old key file and stores back, with the old password typed, brings the old approvals back.
- [answered.md](../answered.md)'s review table: finding 8 (the registration hash) is the second pull request's.
- `cineris-config`'s `managed.rs` and [managed-config.md](managed-config.md): rootless containers (`podman exec -u 0`, `flatpak-spawn --host` from a toolbox) and the `docker` group are elevation without the person.
- [06-permissions-and-sandbox.md](../../../architecture/06-permissions-and-sandbox.md)'s "As built in the signed approvals step" says that an unsigned entry is asked about again without the key, and that a trust carries what it does not approve again as held (rule 6: the doc that described the old behaviour changes with it).

## What ran

On the reference machine:

- `cargo xtask test --dependents -p cineris-policy` (`cineris-policy`, `cineris-core`, `cineris-ext`, `cineris-cli`, `cineris-rpc`): 1,489 run, 1,489 passed, 26 skipped. No test of the command line depends on the summaries yet: printing them is the sibling part's.
- `cargo xtask check` (formatting, rules, the break lists, the generated files, the workspace's clippy, the build without the script engine, the licences): clean. `cargo xtask clippy -p cineris-core -p cineris-policy`, `cargo xtask mutate --check` (every break of `mutations/` applies), `cargo xtask links` and `cargo xtask outstanding --check`: clean.
- **Each break made by hand, one at a time,** its `caught-by` tests run and the code put back: the 25 of this part's list, and seven of the other lists that the review named (L3, L4) or this part moved. Every one is caught, every test its `caught-by` names failing (about two and a half minutes, on the desk's second copy). `cargo xtask mutate` itself did not run: no long run on the shared machine; it belongs on the runners once the branch is pushed.
- Not run: `stress`, and CI, Windows among it. The tests that make a link skip where a link cannot be made, and fail on a CI runner that cannot; the state directory's test is Unix's.
