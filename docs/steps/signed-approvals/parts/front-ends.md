# Signed approvals, part: the person signs at the yes

The part of the first pull request ([answered.md](../answered.md), "The pull requests") that puts the person's password in front of every approval the harness keeps: the command line's `cineris approvals setup`, `reset` and `status`; `ext add`, `ext remove` of a pinned extension and `permissions trust` signing at a terminal; a headless run asking at a terminal before its session opens (moved here from the second pull request by the maintainers: under the password anchor a run with no terminal never has approvals); and the application asking when a session opens with approvals to use, and signing the trust question's yes. Guards A and B refuse the new subcommands that set the password. The description as built is in [06-permissions-and-sandbox.md](../../../architecture/06-permissions-and-sandbox.md) ("As built in the signed approvals step: where the person types the password"; the guards), [09-tui.md](../../../architecture/09-tui.md) ("The approvals password"), [10-headless.md](../../../architecture/10-headless.md) ("The person's approvals") and [security.md](../../../security.md), sections 1 and 3.

## What was built

- **`cineris approvals setup | reset | status`** (`cineris-cli`'s `approvals`).
  - `setup` chooses the password at the terminal, typed twice, at least 12 characters, written at the standard cost; refused when a key is set up. `reset` warns that every approval asks again and that what it let run stays held back, chooses a new password the same way, and says how many pins and projects' entries it took the signature off (`ResetReport`). Both take the terminal before the core starts, and need standard input and output to be terminals.
  - `status` only reads (`Core::approvals_held`, below): the key's fingerprint and when it was made, and how many entries of `pins.toml` and `trust.toml` carry a signature, "not checked".
  - The help says the password is the text as typed, with no normalisation (a composed and a decomposed letter are two passwords).
- **Signing at a terminal** (`approvals::key_at_terminal`, `approvals::Taken`). The stub `commands::person_key` is gone.
  - `ext add`, `ext remove` and `permissions trust` take the terminal (raw, echo off) **before anything slow**: before the core starts and before the key file is read. What they show meanwhile is written as raw mode needs (`print_out`, `print_err`). `permissions trust`'s question about the project's extensions, and `ext remove`'s of a folder nothing pins, are no secret: asked in the terminal's own line mode, the terminal taken again before the key file or the password is read (`Taken::confirm`).
  - Once what is approved is shown, the password is asked with *sign* and lines that name it: `Enter` is the yes, `Esc` the no; one that is not the person's asks again, three times in all. With no key set up, the yes sets one up first (*choose*, typed twice). The key is made, the core called, and the key dropped when the command's arm ends.
  - **With no terminal there is no approval:** `--hash`, `--extension NAME=HASH` and `--hook NAME=HASH` check what is shown and approve nothing on their own; the refusal names the command to run at a terminal. `ext disable` and `ext remove` of a folder nothing pins are unsigned, and act on the hash with no terminal as before.
  - `permissions list` says "its trust carries your signature, not checked here" of a project whose entry carries one, where it said "not trusted".
  - `permissions trust` checks no signature before the password, so a project's extension or hook its entry approved already is shown, and asked about, again; a no keeps its pin. Each one a held pin names at its hash says so: "Approved before at this hash; your password confirms it again." (The maintainers' choice: hiding what an unchecked pin names would put an unchecked file in charge of what the person sees.)
- **A headless run at a terminal** (`headless::taken_for_the_password`, `approvals::open_at_start`). With standard input and output both terminals, the run takes the terminal before anything slow (`PasswordTerminal::enter_leaving_signals`, which leaves the signals to the run's own watch); once its core has started, and when something carries a signature to use, it asks with *unlock* before the session opens, and opens the approvals with the key. `Esc` goes on without them, said once on standard error. With no terminal nothing is asked, and a run that had approvals to use says once: "no terminal to ask your approvals' password at: your extensions and this project's trust are not used in this run". The main thread watches for signals only once the terminal is put back, so that the terminal's handlers never outlive it. A run under a session's command asks nothing.
- **The application** (`cineris-tui`'s `app::approvals`, `app::state::approvals`; `cineris-cli`'s `interactive::CoreApprovals`).
  - `Approvals` is the trait the program gives (`to_use`, `state`, `unlock`, `set_up`, `sign`), since this crate sees neither the policy nor the core; `cineris attach` gives none.
  - After the first frame, `to_use` is asked once; when it says so, the session's open is held while the password is asked with *unlock* (asked once the frame's own bookkeeping is done, so that the frame that did not show it starts no grace). The person's opens the approvals, then the session; one that is not theirs asks again; `Esc` opens the session without them, and says so.
  - At the trust question's yes, for a question with a `proposal`, the answer waits: the password is asked with *sign* and the question's `summary` (or *choose* with no key set up), `sign` rebuilds the statement with `statement_of`, makes the key, opens the approvals if they are not, signs, drops the key, and the answer is the yes with the signature. A wrong password asks again; `Esc` is not now; a question with no proposal is answered as before; with no `Approvals`, such a yes is not now, and the transcript names `cineris permissions trust`.
  - Each call runs on a thread of its own, the password moved into it and dropped there, and wakes the loop with its answer; a call that panics answers with a failure.
  - The full screen's search row no longer draws over the password dialog's row of keys (`state/screen.rs`).
- **`Core::approvals_held`** (`cineris-core`'s `person`, added with the maintainers' leave): one read of the key file and the two stores, with no key, which counts what **carries** a signature (`Checked::NoKey` read with no key) and says whether the project's entry carries one; `ApprovalsHeld::to_use` decides only whether to ask. It opens nothing, holds no secret and no `Verifier`.
- **Guards.** A: `approvals setup` and `reset` are refused in the CLI's grammar (`nested::standing`) and in the engine's fallback (`approving::APPROVING`, with `CASES` rows); `approvals status` reads. B: both refuse under a session's command.
- **The debugger check** is `cineris_sandbox::harden::traced` (the process hardening part), asked first by every prompt for the password (`approvals::traced`): the subcommands, the headless run and the application's calls refuse while it is true, saying why.
- **The conformance test signs** (`cineris-testkit`'s `conformance::run` takes a `Signer`; `cineris-rpc`'s cores have their approvals open with the test's key and sign with it). The real binary's `serve --stdio` leaves out the two scenarios whose yes must be signed (`Scenario::signs`), on both of its carriers: `serve` has no way yet to open the approvals.
- **From the OS layer's review:** the application's exclusive mode, every paste's wipe (counted through the one function every paste goes through, `secret::password::forget`, by a thread-local counter in tests), and the exclusive mode across a stop and a continue (a pty test in `cineris-term`), each with a test and a break.

## Left open

- **Ask for the password before showing,** in `permissions trust` (and `ext add`), once the command line's flow allows it: what the entry approves could then be checked, and an extension approved already not asked about again.
- **`ext disable` sees no gate while the approvals are closed** (every subcommand's core): `Core::extension_gates` takes the pin from a listing judged with the core's key, so a gate-holding extension is turned off unasked. Passed to the core review-fixes part; `commands::sys_ext_add_disable_and_remove_act_only_on_what_is_shown` keeps asserting the rule, and fails until that lands.

- **The Windows variant of the signals test of an extension's command** (`signals::sys_ctrl_break_stops_a_running_extension_command`) now runs `-p` at a pseudo-console and sends the Ctrl-Break from inside its console by the binary's guard program, to the binary started in a process group of its own (`Machine::tui_grouped`). It has not run on Windows yet.
- **Argon2 at the standard cost in the unoptimised CI build:** two system tests pay it (`setup`, and `reset`, which always writes the standard cost). `[profile.ci.package.argon2]` and `blake2` at `opt-level = 2` would make it cheap; the root `Cargo.toml` is not this part's.
- **What the log's standard-error sink writes while a headless run holds the terminal raw** (its core's start) steps down without returning; nothing else writes then.
