# Signed approvals, part: fixes from the full review (front ends)

The full independent review of the signed approvals' work found what the front ends (the command line's subcommands, a headless run, the application) show, sign and ask wrongly. Each finding below, its fix, the test that fails before it, and its break. The stores' and the core's findings are [full-review-fixes-core.md](full-review-fixes-core.md)'s, built beside this part; this one rebased onto it. The breaks are in [mutations/signed-approvals-full-review-fronts.breaks](../../../../mutations/signed-approvals-full-review-fronts.breaks).

## The findings

**1. Show what a signed change does.** The core's `Added.summary`, `Removed.summary` and `Trusted.summary` (the core part's: the proposal's lines, the pins carried as held among them, which are never dropped now) were not printed.
- **Fix:** `ext add`, `ext remove` of a pinned extension and `permissions trust` print them once the change is written, under "What your password signed:" (`approvals::signed_text`). In the application the trust question's yes shows the request's `summary` before the password, every line of it, a held line among them.
- **Tests:** `cineris-cli::bin/cineris approvals::tests::a_signed_changes_lines_are_said_each_on_a_line_of_its_own`, `commands::tests::a_trust_says_what_it_signed`, `ext::tests::an_extension_is_added_listed_turned_off_and_removed` (an add and a pinned removal say what they signed, an unpinned removal says nothing of it); `cineris-tui app::state::approvals::tests::the_yes_shows_every_line_of_the_summary_held_carries_among_them`.
- **Breaks:** `a-signed-change-says-nothing-of-what-it-signed`, `ext-add-says-nothing-it-signed`, `ext-remove-says-nothing-it-signed`, `permissions-trust-says-nothing-it-signed`, `the-yes-shows-the-first-summary-line-alone`.

**2. "Approved before at this hash" came from an unchecked entry** (both reviewers). `permissions trust` said it of every pin the trust store names, signed or not.
- **Fix:** "The trust store names it at this hash; this is not checked here: if you do not remember approving it, answer no." `permissions list` says an entry "carries a signature, not checked here", not "your signature".
- **Tests:** `cineris-cli::system commands::sys_permissions_trust_approves_a_projects_extensions_on_a_signed_yes` and `commands::sys_a_project_trusted_with_permissions_trust_is_trusted_on_the_next_start`.
- **Breaks:** `the-store-named-it-is-said-approved`, `the-list-says-your-signature`.

**3. `permissions trust` signed rules and settings it showed only afterwards.** The password named "its permission rules and settings as they are now"; the core read and pinned them after the password, and the command printed them after the commit.
- **Fix, in the core with the maintainers' leave** (`manage.rs` and its tests): `Core::trust_reading` reads the rules as trust pins them and the settings trust turns on, once; `trust_project_with` takes that reading, pins its rules as read, and refuses with `rules_moved`, writing nothing, when the project's files hold other rules or settings by the yes; `trust_project` reads and passes its own. The command prints the reading before the password, whose line says "as shown above", and after the commit says only what it trusted and what it signed.
- **Tests:** `cineris-core::it trusting::a_trust_is_refused_when_the_rules_changed_after_they_were_shown` (a rule widened between the reading and the yes, then a setting changed: each refused, nothing written; read again, pinned as shown); `cineris-cli::system commands::sys_a_project_trusted_with_permissions_trust_is_trusted_on_the_next_start` (the rules and settings on the screen before the password's prompt; a rule added while it is asked refuses the trust).
- **Breaks:** `the-rules-are-shown-after-the-password`, `a-reading-the-files-no-longer-hold-is-pinned`; step 13b's `trust-pins-only-the-allow-rules` follows the pin into `trust_reading`.

**4. `Ctrl+C` at `-p`'s unlock went on without the approvals,** as `Esc` does.
- **Fix:** the terminal's prompt tells the two apart (`PasswordTerminal::interrupted`, from `read_password_answered`); `approvals::open_at_start` answers `AtStart::Interrupted`, and the run ends as interrupted (130, outcome `interrupted`), its session never opened and nothing sent. `Esc` still goes on without them. A subcommand's `Ctrl+C` stays its no.
- **Tests:** `cineris-cli::system approvals::sys_a_headless_run_with_no_terminal_asks_nothing_and_says_why` (at a terminal, `Esc` goes on without them and `Ctrl+C` ends with 130, no session record and no request); `cineris-tui secret::password::tests::at_a_terminal_esc_and_ctrl_c_give_nothing`.
- **Breaks:** `ctrl-c-at-a-runs-password-goes-on-without`, `the-prompt-does-not-tell-ctrl-c-from-esc`.

**5. The debugger check** (both reviewers).
- **Before the dialog:** the application asked `traced()` only in the call made after its dialog had read the password. `Approvals::why_not_asked` is asked before the dialog opens, at the session's start (`App::ask_unlock`: the session opens without the approvals, saying why) and at the trust question's yes (`App::ask_to_sign`: not now, saying why); `unlock`, `set_up` and `sign` ask again, for one attached while the dialog was open.
- **One check, in one place:** `approvals::may_ask`, which every prompt asks first: `key_at_terminal`, `open_at_start`, `choose` (`approvals setup` and `reset`), and `CoreApprovals::{why_not_asked, unlock, set_up, sign}`.
- **On Windows, a process that could not close itself asks nothing** (`!harden::hardened()`): its threads then keep the user's default access list, so any program of the user's could read the password, or the key it makes, from the memory of the thread holding it. Said in `approvals::NOT_CLOSED`.
- **Found while testing it: `traced()` saw only the first thread on Linux.** It read `/proc/self/status`, which is the first thread's; a tracer attaches to a thread, and one attached to any thread reads and writes the whole process. The real traced child of the new test was told it was not traced, its tracer attached to the test harness's thread. It now reads every thread's status (`/proc/self/task/<tid>/status`); a thread that ended meanwhile is passed over, any other unreadable status fails closed.
- **The test override:** `cineris-sandbox`'s new `test-hooks` feature, turned on only by `cineris-cli`'s dev-dependency, makes `traced()` true while the file `CINERIS_TEST_TRACED` names exists (it can never say false); `cargo xtask size` refuses a shipped binary that holds the name (`xtask/src/shipped.rs`, with the maintainers' leave), and the sandbox's own test holds the constant to that name.
- **Tests:** `cineris-cli::system approvals::sys_no_password_is_asked_at_a_subcommand_or_a_run_while_a_debugger_is_attached` (`approvals setup`, `permissions trust` at a terminal, a headless run at a terminal); `approvals::sys_the_application_asks_no_password_while_a_debugger_is_attached` (before the open; attached while the dialog is up at the open, at a yes, and at a yes that sets the password up, which writes no key file); `cineris-tui app::state::approvals::tests::a_debugger_attached_before_the_open_asks_nothing_and_opens_without`, `a_debugger_attached_before_the_yes_asks_nothing_and_is_not_now`; `cineris-cli::bin/cineris approvals::tests::no_password_is_asked_while_a_debugger_is_attached` (on Windows it asserts the real check refuses in the test's process, which never closed itself); **a real tracer:** `cineris-sandbox::it harden::sys_a_process_with_a_tracer_is_told_it_is_traced` (Linux: the role asks its parent to trace its thread, `PTRACE_TRACEME`, and the test is its tracer, reaping the traced thread with `__WALL`; Windows: the role is started under the test as its debugger, `DEBUG_ONLY_THIS_PROCESS`, the test servicing its events; Yama at 2 or more is said and passed over).
- **Breaks:** `traced-always-false`, `traced-reads-the-first-thread-alone`, `key-at-terminal-asks-while-traced`, `open-at-start-asks-while-traced`, `setup-asks-while-traced`, `windows-asks-where-the-process-is-open`, `the-application-opens-its-dialog-while-traced`, `the-applications-yes-opens-its-dialog-while-traced`, `the-program-says-no-debugger-before-the-dialog`, `unlock-asks-while-traced`, `set-up-asks-while-traced`, `sign-asks-while-traced`.

**6. The application started its core before taking the terminal,** so a password typed early was echoed by the terminal's line mode.
- **Fix:** `interactive::run` takes the terminal (`cineris_tui::app::TakenTerminal`) before the core starts and hands it to `app::interactive_taken`; a core that fails to start puts it back before saying why; a signal while it is held puts it back and ends the program as the signal does. What is typed meanwhile reaches the password's dialog, which drops it.
- **Test:** `cineris-cli::system approvals::sys_a_password_typed_before_a_subcommand_or_a_run_asks_is_never_echoed`, its third part: the application held before its core (`HOLD_CORE`, now asked there too), the password and `Enter` typed, nothing echoed, the field empty, and nothing sent.
- **Break:** `the-application-takes-the-terminal-after-its-core`.

**7. On Windows the shipped binary's access lists were tested only in the sandbox's test binary.** `hardened.rs` now builds on Windows too.
- **Test:** `cineris-cli::system hardened::sys_the_binary_closes_its_own_process_and_every_thread`: the real `cineris serve --stdio`, probed as an ordinary process of the user (a restricted token impersonated, as the sandbox's probe does), denies its memory, threads, handles, changes, suspension and lists, keeps waiting, the limited questions and ending; each of its threads (two at least, those made after `main` began among them, which only the loader's callback closes) denies its context, suspension, changes and list. It needs `windows-sys` as a Windows dev-dependency of `cineris-cli` (the dependencies' row amended, the lockfile with it).
- **Break:** `the-binary-does-not-close-itself` (its Linux test catches it too).

**8. The y/N before the password** (`Taken::confirm`).
- **Fix:** what was typed while the terminal was taken is read and thrown away before the question (`PasswordTerminal::drain`): a `y` and `Enter` typed early, then `Enter` at the question, was a yes, since the line mode took the raw bytes as the start of the line. The line read is judged in place and written over (`approvals::yes_of`, `cineris_base::secret_buf::wipe_string`).
- **Tests:** `cineris-cli::system approvals::sys_a_yes_typed_before_the_question_does_not_answer_it` (Unix); `cineris-cli::bin/cineris approvals::tests::a_yes_or_no_line_is_judged_and_written_over`.
- **Breaks:** `the-question-takes-what-was-typed-before-it`, `the-yes-line-is-not-wiped`.

**9. The docs** (rule 6). `answered.md`'s "The password prompt" is amended to what is built, saying so: standard input and output when both are terminals, never the controlling terminal opened by name; type-ahead read and thrown away, not flushed. [security.md](../../../security.md), section 3, and [10-headless.md](../../../architecture/10-headless.md): a `-p` run whose output is piped or redirected never asks, so never uses approvals; `Ctrl+C` at its password ends it. [06](../../../architecture/06-permissions-and-sandbox.md) and `TrustRequest.proposal`'s documentation (the protocol's schema and declarations regenerated): checking that a proposal holds what the front end shows is the second pull request's work, with `attach`. `RESET_WARNING`, and what a reset says it did, now say that what each approval pinned keeps its gates until it is approved again (`approvals::tests::the_resets_warning_says_what_keeps_its_gates`, break `the-resets-warning-leaves-the-gates-out`). [09-tui.md](../../../architecture/09-tui.md) describes the check before the dialog and the terminal taken early; the open item [permissions-trust-offers-approved-extensions-again](../../../outstanding/permissions-trust-offers-approved-extensions-again.md) quotes the new words.

## What ran

- `cargo xtask clippy -p cineris-cli -p cineris-tui -p cineris-sandbox -p cineris-core`: clean. `cargo xwin clippy --target x86_64-pc-windows-msvc --workspace --all-targets --locked -- -D warnings`: clean (before the rebase; the Windows code did not change after it).
- `cargo xtask test --dependents -p cineris-policy -p cineris-tui -p cineris-sandbox` (with `cineris-agent`, `cineris-cli`, `cineris-core`, `cineris-ext`, `cineris-mcp`, `cineris-rpc` and `cineris-tools`): 3,415 passed.
- The new system tests' times there: the application's debugger test 0.9 s, the subcommands' 0.2 s, the y/N typed early 0.3 s, the headless run's (two runs more) 1.1 s, the trust test 1.7 s, the real tracer 3 ms.
- `cargo xtask mutate --check` and `cargo xtask check`: see the report.
- **Not run:** Windows (every Windows test here, the access lists of the real binary and the debugger's events among them, runs on the runners); `stress` and `mutate` (no long run on the shared machine): the breaks' verdicts are for a run on the runners (`gh workflow run try --ref <branch> -f command="mutate signed-approvals-full-review-fronts"`, and `-f os=windows` for `windows-asks-where-the-process-is-open` and the Windows test of the binary).
