## The design, before building

The seven points the step's prompt asked to settle, and the open items that name step 27, written against `main` at `0458c35` and revised after an independent review (its findings are at the end, with what each changed). Every choice is **reversible** unless it says otherwise; a choice that hangs on a number says **to confirm by measurement**, and the number is measured before the pull request that ships it.

### What already exists, and what this step adds

The core already does most of what the protocol page asks of a server, in process: `Core::connect` with a role and capabilities, `Core::handle` for every operation, one `EventQueue` per client that merges deltas, drops them with one `item.resync`, never drops a whole event and keeps a fence at a read's `seq`, and `Core::respond` with the first-answer-wins rule. `cortex-protocol` has the wire tables (`Op::from_wire`, `OpResult::from_wire`, `ServerRequest`, `ServerResponse`, `ServerNotification`) and `cortex-base` has the line framing (`FrameDecoder`). `cortex-rpc` is an empty crate.

So the server adds **transport and order, and no behaviour of its own** (11-rpc-protocol, "One contract, two carriers"): reading lines into operations, running them in the lane, writing results, events and requests as lines, and the rules only a wire has (the stall rule, the inbound bounds, peer checks, the end of a connection). Where the protocol needs a behaviour the core does not have yet, it is a change to `cortex-core`, which this step's "Must not change" covers: **each such change is in the table at the end of this note and asked for by name.** None is merged before the coordinator says yes; each is built on a commit of its own, so it can be dropped whole.

### 1. Who may connect

**Unix.**

- **The default path** is `$XDG_RUNTIME_DIR/cortex-harness/rpc.sock`. Where `XDG_RUNTIME_DIR` is not set, `/tmp/cortex-harness-<uid>/rpc.sock`. The state directory is not used: a socket path is limited to 107 bytes, which a long home path would pass. `serve --socket PATH` and `attach --socket PATH` take another.
- **The folder is secured before the socket exists.** A missing folder is created with mode `0700` (`cortex-base`'s owner-only directory). An existing one is looked at without following a link: a directory, owned by the user, with no permission for group or others; anything else refuses the start and says why. For a `PATH` the user gives, its folder must be owned by the user with no write for group or others, or owned by root with the sticky bit (as `/tmp` is, where another user can create names but not remove or replace ours).
- **The socket is `0600`.** Linux creates it with the mode the umask leaves, so it is set right after `bind`. The window between the two is covered twice: in the default folder nobody else can reach the socket at all, and every connection is checked before a byte is read.
- **The peer check.** Each accepted connection's credentials (`SO_PEERCRED`, through `tokio::net::UnixStream::peer_cred`, which hold the identity at `connect` time) must name the server's own effective uid. Otherwise the connection is closed with nothing read or written, and the log says the peer's uid and pid.
- **A stale socket.** A lock file beside the socket (`rpc.sock.lock`), opened without following a link, owned by the user and owner-only, locked with the standard library's `File::try_lock` for the server's whole life. A lock that is held means another server runs: the start is refused, naming the path. A lock taken means a socket at the path is probably stale; it is removed only if a `connect` to it is refused (so a lock file that a cleaner of `/tmp` removed under a live server cannot lead a second server to remove the live socket). Anything at the path that is not a socket is never removed, and refuses the start. A clean end removes the socket before it lets the lock go.
- **The client checks the server too.** `attach` reads the server's credentials from its side of the connection and refuses a server of another uid, so a socket another user put in a folder `attach` was pointed at cannot collect a person's approvals.
- **Accepted, and said:** another user can stop a server starting by creating its predictable names first (`/tmp/cortex-harness-<uid>` before the user's first start, a pipe name on Windows). That is a refusal to start with a message, never a connection.

**Windows.**

- **The default name** is `\\.\pipe\cortex-harness-<the user's SID>`; `serve --socket NAME` and `attach --socket NAME` take `\\.\pipe\NAME`.
- **The security descriptor is given at creation,** so there is no window: owned by the user, a protected access list with one entry allowing the user alone, and a mandatory label at the server's own integrity level, written in Windows's own description language as `cortex-base`'s owner-only files are ([decision 0029](../../decisions/0029-owner-only-files-on-windows.md)). The label keeps a process of lower integrity out: without it a medium process could drive a server that UAC elevated, and its commands would run elevated. Every instance is created with it; the first with `FILE_FLAG_FIRST_PIPE_INSTANCE`, so a name that exists already refuses the start rather than joining it; all with `PIPE_REJECT_REMOTE_CLIENTS`. **The next instance is created before a connected one is handed on,** so the name never lapses for another process to take.
- **The connection's identity is checked as well.** The server takes the connection's own token (`ImpersonateNamedPipeClient`, then `OpenThreadToken` with `OpenAsSelf`, then `RevertToSelf`) and admits it only if the token's user is the server's own, its integrity level is at least the server's, it is not restricted (`IsTokenRestricted`) and not an AppContainer. The connection's token, not the process's: a thread impersonating another user connects as that user, and a process id can be reused. A client that allows only anonymous impersonation is refused. The impersonation runs on a short thread of its own, never the core thread, and a `RevertToSelf` that fails ends the process. Whether the client must have written first (`ERROR_CANNOT_IMPERSONATE`) is checked on a runner before the design relies on it; if it must, the check runs on the first line, before the line is read.
- **`attach` checks the server** from its own handle: the pipe's owner must be the user's SID and its label at least medium (`GetSecurityInfo`), and a failed query refuses. Another user cannot make the user's SID the owner of their pipe, and a lower-integrity process of the same user cannot give its pipe a medium label.
- **Where it lives:** `cortex-rpc`'s `transport/windows.rs`, a module that may use `unsafe` with a reason, as `cortex-term`'s and `cortex-sandbox`'s Windows modules do. `cortex-base` makes public the one function it has that `cortex-rpc` needs, the user's SID as text. `cortex-rpc` gains `windows-sys` (on Windows only, in the build already) with the API families it calls, and a row in `dependencies.md`.

**What the runners showed, and what the building changed** (pull request 2):

- **The client must have written first.** Before the server has read anything, `ImpersonateNamedPipeClient` fails with `ERROR_CANNOT_IMPERSONATE` (try run 43936070154). And the token it gives is that of the client's thread that wrote what was read, not of the one that opened the pipe. So each connection is read, in a task of its own, until its first data, which is held; the client is checked and only an admitted one is handed on, with that data first. A client that writes nothing holds up no other; past 16 of them, the longest waiting is closed.
- **The label is `NWNR`, not `NW` alone:** since a client is checked only once it has written, a lower process that could open the pipe to read and never write could hold connections it could never be refused on.
- **The module is `socket/windows.rs`,** beside the Unix half, and makes its instances with `CreateNamedPipeW` rather than tokio's `ServerOptions`, which needs a runtime to make one. The new place for `unsafe` has [decision 0037](../../decisions/0037-the-named-pipe-is-served-from-cortex-rpc-in-one-windows-only-module-that-may-use-unsafe.md).

**The harness's own commands.** A command the agent runs is a process of the user. Inside the enforcing Linux sandbox it cannot reach a Unix socket; outside it (Windows, or a sandbox that does not enforce) a command a person approved for one purpose could connect as a `user` client, answer its own session's approvals and raise its level. **Recommendation: refuse a connection from one of the server's own commands:** on Windows, a process in a Job Object of the server's commands (`IsProcessInJob`), which a command cannot leave since breakaway is not allowed; on Linux, a process whose ancestry reaches the server (`/proc/<pid>/stat`), which a command that detaches itself escapes, so it is defence in depth there and the sandbox is the wall. It is said in security.md's residual risk either way. **The owner's call;** built in pull request 2 as recommended meanwhile.

**A test that another user is refused, on each OS** (tier 3, both blocking):

- **Linux:** a hosted runner has a second user (`nobody`) and `sudo` with no password. `sys_another_user_cannot_connect` runs `sudo -n -u nobody python3 -c …` (Python is on every hosted image). The test's folder is made traversable, and two positive controls come first: `nobody` can reach that folder, and the same Python helper run as the test's own user is answered `initialize`. Then: against the server's own layout, `connect` fails at the folder; against a socket the test itself makes `0777` in the traversable folder, `connect` succeeds and the server closes the connection with no answer to `initialize` (the peer check alone).
- **Windows:** the test creates a local user with a random password (`net user … /add`, which the runner's administrator may), logs it on (`LogonUserW`), and opens the pipe from a thread of the test: first as the test's own user (the positive control, answered), then impersonating the second user (`ImpersonateLoggedOnUser`), which fails with access denied. For the token check alone, a **runtime option** that exists only with `cortex-rpc`'s `test-hooks` feature (`ServeOptions::widen_access_for_tests`, off by default) adds `Everyone` to the access list of that server only: the open then succeeds and the server closes the connection unanswered. A compile-time switch would widen every pipe in the test build, the binary the system tests start included. The user is deleted at the end.
- **Where a second user cannot exist** (a desk without `sudo -n`, a run without administrator rights), each test says it was not run and passes, **unless `CI` is set,** where it must run: a runner that cannot make the second user fails the test.

### 2. Roles and routing

**What each role may send** is the core's table, unchanged: an `observer` watches (it opens a running session, reads it and closes its own view; everything that starts, changes or ends something is refused `role_not_allowed`); a `supervisor` drives as a `user` does, but may not raise the level, may not use `usage/refresh`, never reaches `Engine::record`, and is not put trust or rewind questions; only a `user` answers those. The server adds two rules: **every request before `initialize` is refused `not_initialized`,** and a second `initialize` `already_initialized`. The server builds the client's `ClientInfo` from `initialize`'s role and capabilities, connects it to the core, and then has the core answer `initialize` (the version and the role's validity); when the core refuses it, that client is disconnected again and the connection stays open and uninitialized, so a later `initialize` may succeed.

**Supervisor routing** is a change to the core, and a conflict in the build plan: step 13's "What later steps inherit" gives it to step 37 ("today is asked nothing and may answer nothing"), and this step's "Done when" asks for it ("approvals route to it first, it cannot answer beyond a test lease, and a user client's answer wins"). **Recommendation: build it now, as an addition that does nothing until a supervisor has a grant,** so that the core's behaviour for every client that exists today is unchanged. It follows 17-coordinator's "Approval routing":

- `ClientInfo` gains `grant: Option<Lease>`: what a supervisor may approve. **Nothing on the wire sets it** in this step: `serve` gives every supervisor connection the grant in its `ServeOptions`, which the binary leaves empty; a test gives its "test lease" there. Steps 37 to 40 decide where a real grant comes from, and protocol version 1 does not change.
- **A session has at most one supervisor:** a second one's `session/new`, `session/open` or `session/fork` is refused `supervisor_present`, the code the protocol already lists.
- **Every approval goes to the session's supervisor,** when it declared `approvals`, and to every `user` client that answers approvals, at once: the supervisor's orchestration layer decides what it hands its Manager and what it escalates (17-coordinator, steps 1 to 3), and a user attached to the session always sees the request and can answer it.
- **The grant is enforced on the supervisor's answer,** whatever the layer did. The grant is the session's own standing lease narrowed by it (`standing.narrow(grant)`: a grant never widens what the session holds, and `unrestricted` is never handed on); an engine built from the session's engine template with that lease decides the call, and only `allow` is within. A `deny` is always taken. An allow within the grant is taken as `allow_once` (a supervisor's `allow_session` or `allow_project` included, which is logged), allows that call without `Engine::record`, and settles the request. **An allow beyond the grant is not taken:** the request stays open for the users, which is how the supervisor passes it up. A JSON-RPC response gets no reply, so the supervisor learns its answer was taken from `request.resolved`, and that a user answered from `request.resolved` on a request it did not settle: no new field.
- **"A user's answer always wins"** (17-coordinator, step 4) is read as: a user may answer at any moment until the request is settled, and the first answer taken settles it. A supervisor that answers within milliseconds therefore settles a request before a person reads it; a person who wants to decide answers the escalated ones, which are exactly those beyond the grant. **The coordinator confirms this reading;** a test covers both orders, and 11-rpc-protocol (line 206), 06-permissions (the paragraphs on whose answer counts and on supervised sessions), the header of `clients.rs` and the build plan's step 13 bullet are amended in the same change.

**The alternative** is to leave the routing to step 37, as step 13's record says, and meet this "Done when" item in part: a supervisor is asked nothing and a user's answer is final.

**When the asked client disconnects mid-request** (unchanged in the core): an approval stays open for the clients still asked, is put to a `user` client that opens the session later (`Clients::join`), and is denied at the time limit or withdrawn when the turn is interrupted; a trust or rewind question ends with its askers, as no answer. A supervisor that leaves does not answer for itself. The server calls `Core::disconnect` first when a connection ends, before it waits for the lane, as the in-process link does, so a question the client never answered cannot hold its lane.

**A JSON-RPC error in answer to a server request** means the client declines it: the request stays open for the others asked and for its time limit, as if that client had not answered.

**Only a `user` reaches `Engine::record`:** a test for each of `observer`, `supervisor` and a `user` that was not asked, over the wire.

**Raising the level and trust over RPC.** security.md section 5 says `unrestricted` and trust decisions "need the same explicit flags as on the command line"; since step 23 the core puts the trust question to a `user` client, and lets a `user` client raise the level to anything the configuration allows, so a `user` client over the socket can do both, as the terminal UI can. **Recommendation:** the server refuses `unrestricted` (`session/new`, `session/set`) unless it was started with `--permission-mode unrestricted`, so that a client never holds more than the server's own command line gave; trust stays a question to the person's front end, and security.md's line and 06's "RPC modes cannot ask" (stale since step 23) are corrected. **The owner's call.**

### 3. Several clients and backpressure

The core's queue does the merging, the dropping with `item.resync` and the fence at a read; the server must not undo it. So **the server holds no queue of events of its own:**

- **One writer task a connection** takes the next thing from the client's `EventQueue` only once the line before it has gone, so a client that reads slowly leaves its backlog in the core's queue, where deltas merge and then drop. The writer holds one encoded line at a time, and the transport one more.
- **Results go out after the events queued before them.** A result that is ready is written after the events the queue held when it became ready, and no others: the in-process link's rule (`take` in `cortex-cli`), so a `session/read`'s result never overtakes the events it holds, and a stream that goes on does not hold the result back. The rule moves into `cortex-rpc` (`order`), and both links use it.
- **A queue bounded by bytes as well as count.** A delta is merged into the one before it whatever its size, so a reader that stops during one long item never fills the queue by count: a command's output streams at up to 64 KiB every 16 ms, about 4 MB a second, into one merged delta. **A core change:** the queue also counts the bytes of the deltas it holds, and is full past **8 MiB** (to confirm by measurement) as it is past its count, so the item's deltas drop with one `item.resync` as they would. Whole events are not counted by it and are never dropped.
- **The rule that closes a connection** (02-runtime: "closing a connection that cannot take them in time is the RPC server's rule"): while a line waits to be written, the writer looks at the client's queue at most once a second (only then: an idle connection sets no timer, and the queue wakes nobody when it grows), and closes the connection when whole events wait past the queue's capacity and the client has taken no line for **30 s**, or at once when **4 × the capacity** wait. Nothing more is written to it, the log says why, and `Core::disconnect` follows; the session and its turn go on (in `--stdio` the server then ends, as when standard input ends: its one client is gone). Both numbers, and the bytes whole events hold meanwhile, **to confirm by measurement** under a fast scripted turn with a reader that stops; if whole events can reach hundreds of megabytes inside the time, the queue counts their bytes too.
- **Inbound is bounded, and reading never stops for it:** an answer to a question an operation waits on comes in on the same stream, so a server that stopped reading could wait for good. Instead a request counts against the connection's budget, at most **256** and **64 MiB of lines**, from when it is read until its result is written; a request past either is answered at once with an error of kind `limit` (`overloaded`) and not run. Those refusals count too, and a client that has more than as many of them unread is both flooding and not reading: its connection is closed. A line is at most 32 MiB (the framing's limit), and one of more than 1 MiB is read on the blocking pool so that the core thread is not held for it (to confirm by measurement: the time to read and to write a line of 1, 8 and 32 MiB).
- **The model's stream never waits on a client:** the loop's events go into `EventQueue::push`, which never waits, and only the writer task waits on the client. The test: one client stops reading altogether while a second takes everything; a scripted turn of many deltas completes, the second client gets `turn.completed` with no virtual time passing, the first's queue holds at most its capacity (and its bytes) of deltas and one `item.resync` an item, and once the fake clock passes 30 s the first is closed and the session goes on.
- **Merged and dropped deltas over the wire:** a client whose writer is held reads fewer, larger deltas; past the capacity it reads `item.resync` with the `seq` of the first delta dropped, and `session/read` gives the item so far; every `seq` it reads increases.
- **Connections** (socket mode): at most 64 at once, and one that has not said `initialize` within 10 s is closed.

### 4. Lifetimes

- **`serve --stdio`** has one client, its parent. **When standard input ends,** the server stops reading, disconnects the client (which withdraws its questions and ends its sessions: their turns are interrupted and their logs closed), waits for the lane's operation at most 1 s, shuts the core down, waits for the requests still running at most 2 s, writes what is already queued (at most 2 s, since standard output may not be read any more), and exits 0. A `shutdown` request does the same and is answered `{}` before the exit. **The whole end is bounded:** standard input and output are served by threads that are not joined (output through a one-line hand-off, never `tokio::io::stdout`, whose blocking task would hold the runtime's drop), and the main thread gives the core thread at most 5 s from the end's start, as the interactive mode's `CoreThread::end` does, since `Core::shutdown` waits for each session's close. No system test waits on these bounds: each is tested on the fake clock in `cortex-rpc`, and the binary's own tests end it by its input, `shutdown` or a signal.
- **Standard output carries only the protocol:** the log's standard-error sink is at `warn`, as in headless mode, and a system test reads every line the real binary writes as a JSON-RPC message. Moving the real standard output to a private handle and pointing descriptor 1 elsewhere would also stop a stray print, but needs `unsafe` in a crate that has none; the test is what 11-rpc-protocol asks for, and the move is offered, not built.
- **`serve --socket` keeps sessions for clients to come back to.** A session whose last client disconnects goes on running, and its turn with it; another connection's `session/open` joins it. This is a core change (step 13's record foresaw it: "a server that keeps sessions for clients to come back to changes that in `Core::end`'s callers"): `CoreOptions::keep_sessions`, off by default, so headless, the TUI and `--stdio` behave as today. With it on, a disconnect ends no session, and **an approval in a session with no client at all waits for a `user` client to open it,** up to the approval time limit, as one whose askers have all gone already does; a session whose clients are there and answer no approvals still gets the default at once (11-rpc-protocol, "Server → client requests"). A session put together for a client that left meanwhile is still ended (11-rpc-protocol, the step 13a bullet on it). A session ends when a client that may drive it closes it and no other client has it open, or when the server ends. **A kept session costs memory and, while its turn runs, money with nobody watching:** nothing ends one by time in this step, and an item in `docs/outstanding/` (`sessions-kept-with-no-client`) is opened with this pull request, with the measured cost of one held.
- **How `serve --socket` ends:** a `shutdown` request from a `user` or `supervisor` client, SIGINT or SIGTERM (Ctrl-C, Ctrl-Break or the console's close on Windows). It stops accepting, shuts the core down (every session's turn is interrupted and its log closed, every open question ends as no answer), waits for the requests under way at most 2 s (so a session put together meanwhile ends itself in the core and is not cut off by the exit: the open item `shutdown-and-a-session-being-put-together`), closes every connection, removes the socket and exits 0, or 130 or 143 for a signal, within the same 5 s bound. **A second signal ends the process at once;** the guard and the Job Object end its commands. This is headless mode's table with its second step (interrupt with `now`) left out, since a server has no one turn to interrupt: `signals::watch` is used as it is, and the server's driver ends the process on the second signal it is told.
- **A connection's end** in either mode: `Core::disconnect` first, then the lane's operation, at most 1 s, as `interactive.rs` does.
- **The command line.** `cortex serve (--stdio | --socket [PATH])` takes the flags of a run that set up the core rather than one run: `--profile`, `-c KEY=VALUE`, `--model`, `--effort`, `--speed`, `--permission-mode`, `--allow`, `--deny`, `--trust-project`, `--system-append`, `--log-level`, `-q`, `-v`; a run's own (`-p`, a prompt, `--output`, `--continue`, `--resume`, `--fork`, `--no-session`, `--fail-on-denial`, the `--max-*` limits) are refused by name. The core is made as the interactive mode makes it, with `answers_may_stop` on: any client may interrupt a turn while a question is open, as the TUI's dialog can.

### 5. `cortex attach`

`cortex attach [--socket PATH] [--continue | --resume ID] [PROMPT]` connects to a running `serve --socket`, says `initialize` as a `user` client with every capability, and runs the same application as `cortex` does, through `cortex_tui::app::interactive`, with a second `Link`. It has no core of its own: it reads the user's configuration only for `[tui]`, `[keys]`, `[terminal]` and the log, and keeps the prompt history locally, as the interactive mode does.

**What crosses the wire that the in-process link does in memory:**

| In process (`cortex-cli`'s `InProcess`) | Over RPC (`attach`) |
|---|---|
| `send`: the op on a channel to the core thread's lane | a JSON-RPC request; the server's lane for the connection orders it the same way |
| `Done(ticket, result)` from the lane's queue | the response, matched to the ticket by its request id |
| events and requests from the client's `EventQueue` with `try_next` | `session/event` notifications and server requests, which the link's I/O thread puts into an `EventQueue` of its own (the core's type), so that merging and `item.resync` work for an interface that is behind (an external editor open while a turn streams), as in process, and the server's stall rule never meets an `attach` whose person is in the editor |
| a result held until the events queued before it are taken | the same rule: the I/O thread queues each result in wire order, and the link takes it in `Order` |
| `respond`: `Core::respond` on the interface's thread | a JSON-RPC response to the server's request; a refused answer is dropped by the server, as the in-process link drops it |
| `Gone` when the core thread ends | `Gone` when the connection closes or reading fails |

The link's I/O runs on a thread of its own with a current-thread runtime (a named pipe needs overlapped I/O, so blocking reads and writes on two threads would serialise on one handle), and wakes the terminal's waker once a burst. `attach` going away is a disconnect: the server keeps the session.

**The paste rule and the quiet rule** are the application's, in `cortex-tui` (`app::dialog`), not the link's, so `attach` has them as they are; a pseudo-terminal test shows typing through an approval does not answer it over `attach`.

**Prompts at a turn's edges** (the open item, which `attach` meets on every attach to a running turn): (1) the prompts held while the session opens are sent one at a time, each once the one before it was answered, and a refused one gives back the rest with it, so their order holds; (3) the first is sent with `delivery: steer` when the open says a turn is running, as `Enter` steers a running turn. For (2), a prompt refused `turn_running` in the gap between two queued turns, **the recommendation is to send it again once with `queue`,** so it runs after the turn that took the gap; the owner's call, built that way meanwhile.

### 6. The conformance test

- **A scenario is data:** a name, the scripted model's responses, the workspace's files, and a list of steps (send an operation, answer the next request of a kind, wait for an event). They are in one module, `cortex-rpc`'s `conformance`, behind its `test-hooks` feature, so that `cortex-cli`'s system tests run the same list: **a later step adds a scenario in one place** and it runs on every carrier.
- **Carriers:** in process (`Core::connect`, `handle`, the queue), over the wire in process (the very connection code `--stdio` runs, over the transport's in-memory ends, tier 2), and the real binary's `cortex serve --stdio` (tier 3, compared with the in-process run against the same scripted SSE server).
- **Each scenario has a workspace and a state directory of its own,** and in the binary's run a server of its own, so the core's memory of a project (the "not now" trust answers, stored approvals, `session/list`) never carries from one to the next. Background work whose events come when they like (the repository index, the base state's capture, the context probe) is off in the scenarios' options, and a scenario's bursts stay under a queue's capacity, so no delta is dropped by load.
- **What is compared:** each client's events in order, with ids numbered by first appearance, times and durations taken out, and **runs of deltas of one item and kind joined into one**: merging depends on how fast a reader is, so the sequence a client could be sent differs in where deltas are cut, and nothing else may differ. `seq` is checked to increase on each carrier, and every result is compared after the same normalising. **The order of results among events is checked too:** a `session/read`'s result comes after every event at or below its `seq` that the client was sent.
- **The first scenarios:** a turn with text and reasoning; a tool call approved; a call denied with a note; an interrupt mid-stream; steering and a queued prompt; `session/compact` idle and during a turn; a rewind; two clients on one session; every method of the table once.

### The `[rpc]` settings

The reserved `[rpc]` section gets two keys, **the user's alone** (a project's file cannot set them: they are read once, by the server, which loads no workspace):

| Key | Default | What it is |
|---|---|---|
| `rpc.approval_timeout` | `"10m"` | How long an approval waits for an answer before it is a denial (`CoreOptions::approval_timeout`, which `serve` sets; the TUI keeps none). `"0s"` is no limit, which only the user can choose. The open item `approval-time-limit-setting`. |
| `rpc.stalled_client` | `"30s"` | How long a client may take no line while whole events wait past its queue's capacity before its connection is closed. |

Ten minutes is long enough for a person to read a diff and short enough that an editor that crashed with a dialog open does not hold a turn for good; **the owner's call.**

### The review of this note

An independent reviewer read the first draft against the spec and the code. What it found, and what each changed:

| Finding | Changed |
|---|---|
| Past its inbound bound the server stopped reading, so a trust answer behind 256 queued requests was never read and the open waited for good; results waiting to be written were not bounded | Reading never stops for the bound: a request past it is refused (`limit`, `overloaded`), a request counts until its result is written, and a client that floods and does not read is closed |
