## Windows' unit tier at 25 s

The owner's decision of 2026-11-20: Windows' unit tier is held to 25 s above the start of its tests' processes, and Linux's stays at 20 s, as the system tier is 90 s on Windows and 60 s on Linux. On Windows that is a warning past 25 s and a failure past 37.5 s. The measurement behind it is in [../ci-budgets/answered.md](../ci-budgets/answered.md), "Left for the owner": on an 8 ms runner the tier read 20.2 to 21.0 s, 8.8 s more than in wave 12, which is 680 new tests. `cargo xtask ci --tiers` judges each system's run against its own budget (`Tier::budget` in `xtask/src/tiers.rs`). It is one commit, "Hold Windows' unit tier to 25 s, Linux's to 20 s", the CI-budgets fix's proposal as it was built then, with the pages that state the budget brought along. No other budget changed.

## Seven breaks that did not do what their lists said

Step 25's first-run part found four breaks that no test caught ([../25/parts/pr3-first-run.md](../25/parts/pr3-first-run.md), "Open"); two more had tested nothing since step 24; one was caught and marked to survive. Each is now caught by a test it names.

**The configuration directory, closed whole** (`step-13a/configuration-directory-not-closed` and `step-13a/protected-directory-unresolved`, `crates/cineris-core/src/assemble.rs`). Both rules hold, and the second is a security rule. What hid them: on Linux the stored keys' folder *is* the configuration directory, and the core closes that folder too, resolved. So with the directory's own closing taken out, or given the path through a link, the keys' closing still closed the real directory, and every test passed. The tests now keep the keys apart, in the data directory, as Windows keeps them:

- `start::the_configuration_directory_is_closed_whole_to_every_tool` (new, every system): at `unrestricted`, with a user there who would say yes, a read of a file of the directory that nothing else closes (what a killed write of the configuration file leaves) and a write of a new file there are both refused, and nobody is asked.
- `start::a_configuration_directory_behind_a_link_is_protected_where_it_really_is` (Unix): it read `config.toml` by its real path, which is closed by name and where it leads whatever becomes of the directory. It now reads a file that nothing else closes.

**The shell's trust** (`step-13a/repository-trust-not-given-to-the-shell` and `step-13a/shell-given-rules-trust`). Since step 24 the shell tool reads the repository's trust from the session's `ShellLive`, which a reload sets again, and reads `ShellConfig`'s field only when it has no `ShellLive`. The core always gives it one, so breaking the field changed nothing. Both breaks now break the value `ShellLive` starts with (`ShellLive::sharing(…)` in `assemble.rs`), and the tests they named still catch them: the first by nine tests of `harness_git`, `shell` and `trust`, the second by `trust::sys_a_project_trusted_in_the_store_is_trusted_while_its_rules_are_the_ones_the_user_saw` and `trust::sys_a_repository_whose_git_was_not_shown_gets_nothing_of_git`. The reload's own setting of it is step 24's to break. A comment at the field now says it is not the one read.

**A failed open, and an update of another session** (`step-23/a-failed-open-shows-anothers-events` and `step-23/an-update-of-another-session-taken`, `crates/cineris-tui/src/app/state.rs`). Both rules hold; the breaks no longer changed behaviour. `App::event` drops every event but a notice when no session is open, and a session is only ever opened with none open (the first start, and `/new` after it closes the one there). So `open_failed`'s own filter of the held events, and the update arm's check that a session is open, could decide nothing. Both were taken out, which changes no behaviour, and the gate at the head of `App::event` is the one check, with a comment that says so. The breaks now break the gate, each its own way: one lets every event through, the other lets an update through. `app::tests::a_fork_that_fails_closes_its_original_and_takes_nothing_of_it` catches both, and the first is caught by `app::tests::sessions::with_no_session_open_only_notices_of_the_one_closed_are_shown` too.

**The engine told every project is trusted** (`step-13a/engine-told-every-projects-rules-are-approved`). It was marked `expect: survives`: configuration holds the project's own rules back before the engine sees them. The engine's half is now relied on. Since step 19 the project's accepted commands reach the engine directly, as learned rules, and only the engine's trust holds them back in a project that is not trusted (a learned allow needs trust). Told every project is trusted, the engine lets an accepted command run unasked there, and `knowledge::an_accepted_command_waits_for_the_projects_trust` fails. The expectation is now `caught-by` that test.

## A git cap of zero that git could still beat

**What was open:** `cineris-tools`' `changes::sys_git_that_does_not_answer_in_time_is_not_waited_for` gave the change detector a git time cap of zero and expected git's answer not to be used. It failed once in CI with `Method::Git`. `process::brief::answer` reads git's output on a thread and waits for it with the cap, so a git that has already answered when the wait is asked is taken. The test depended on the order the machine ran two threads in; the product was right either way.

**The fix**, in the test alone. It starts the test binary in git's place, through the detector's git confinement (`ChangeDetector::with_git`): a child of the test kit that reports to the test and stays until it is killed, writing no answer. "Does not answer in time" is now made, not hoped for. The test asserts that the look gave up on git for its time (`GitTooSlow`, no files, `Method::None`) and started git once. A look that waited for this git would never return, and the test would run out of time. The product is unchanged: a cap of zero still starts git and takes an answer that is already there, which is not a wait.

**What it no longer checks.** A cap swapped for another finite one (500 ms) would pass after that time; telling zero from 500 ms needs a clock, and the old test told them apart only through the race that made it flaky.

**Measured.** On the reference machine the test passed 200 times out of 200 under `cargo xtask stress --strict`, and 300 out of 300 on two cores under load (`--cores 2 --load 6`). Two breaks show that it bites: a brief answer waited for with no limit, and the look's cap not passed to git's wait. Both are caught, by the test running out of time.

**The same mechanism elsewhere.** Searched the workspace for tests with a zero or tiny limit that race a thread or a child, `recv_timeout`, and the callers of `brief::answer`. None is this race. `changes::a_look_that_runs_out_of_time_says_it_is_not_complete` gives the walk by modification times a cap of zero; it relies on the monotonic clock moving while a few dozen entries are walked, which it does in practice, and is listed rather than changed. `cineris-base`'s log tests of `flush_within(ZERO)` hold the writer with a `Hold`; the core's index tests with no wait for the map gate the index or do not depend on which side wins; the agent's map test runs on a fake timer.

## A test of the sandbox's watch that depended on real time

**What was open:** `cineris-sandbox`'s `protect::tests::a_cargo_made_as_a_link_is_found` failed once in CI on `assert!(before.is_complete())`. The look at protected paths stops after `Limits::time`, a quarter of a second of real time by default, and says it is incomplete.

**How far it went.** Every test of `protect`, and every `cineris-core` test of a confined command, inherited that default, so a loaded runner could cut a look short. With the default time made zero, 22 of them failed on the reference machine: 12 in `cineris-sandbox` and 10 in `cineris-core`.

**The fix.** The tests now give the watch the standard limits with a time of an hour: `unhurried()` in the sandbox's tests, and `protect_limits()` in the core's test rig, which every core it makes now has. With the default time made zero, all 536 tests of the two crates pass, which shows that none of them reads it. The time bound itself has a test of its own, `past_its_time_a_look_says_it_is_incomplete`, with a time of zero. For that the check became "at or past the time" rather than "past it", so that zero stops a look at its first check on any machine, whatever its clock's resolution (settled by the maintainers: a limit of zero that always stops a look widens nothing). The product's default, and what it does with it, are unchanged. Two breaks, a look that ignores its time and one that stops without saying it is incomplete, are caught by the new test.

**Measured.** On the reference machine the `protect` tests ran 200 times each under `stress --strict` and passed every time, on an otherwise unloaded run and with `--cores 2 --load 6`.

**Left as they are:** `cineris-cli`'s system tests that run a confined command through the real binary (in `signals.rs` and `tui.rs`) still take the product's default time, because the binary has no setting for it. None of them asserts on the look.

## A summary test that ran out of time once, on the reference machine

`cineris-agent`'s `context::a_summary_that_failed_in_the_background_is_asked_of_the_main_model_at_the_trigger` was reported slow at 2 s and then timed out at 18 s in one run of `cargo xtask ci --tiers` on the reference machine, otherwise idle. It has not been seen on CI. No cause could be pinned. The agent rig runs on one single-threaded runtime with a fake clock, and its blocking work runs inline in the order the seed decides, so under seed 0, as CI runs it, the order is fixed. On the test's path the loop has no timer and no real-time wait, and the compaction's retries are bounded. On the reference machine the test passed 1,000 times under seeds 0 to 999 on two cores beside six busy loops, 3,000 times under seed 0 in CI's build profile (4 to 5 ms a run), and under seed 0 in 161 scratch directories of different lengths.

The test had printed nothing for itself, because it used none of the test kit's waits. The agent rig's `World::run` now names itself to the test kit's watch, so a test of the rig still running at 8 s reports its seed and each thread's state and wait channel before nextest stops it. Only the agent rig had that gap: the core's rig already names its waits, and the other crates' process and server tests start the watch through the kit. The test is a known flake in [`a-summary-test-that-ran-out-of-time-once`](../../outstanding/a-summary-test-that-ran-out-of-time-once.md) until that report shows the cause.
