# Step 28 fixes: the engine, fetch and the manifest

The review of step 28's close, its findings 9, 10, 13 and 19 (the fetch's user part and the waiting host calls' bytes), and the engine's notes of lower confidence. Breaks in [mutations/step-28-fixes-engine.breaks](../../../../mutations/step-28-fixes.breaks).

## 9. The cap of four threads left running was not a cap

**Outcome: fixed, with the bound it now has stated.**

- **What it was.** The cap (`cineris_ext::engine::MAX_ABANDONED`) was looked at only as a runtime started; a live runtime's call looked only at whether its extension was disabled, and an extension was disabled only once its thread's 2 s grace was over. So a runtime started in another's grace (a hook of a call planned meanwhile, since the core makes a fresh runtime whenever the slot's is not alive), and a call of another session's runtime made in that grace, were each let in and each could leave one more thread; and a runtime alive before the cap was reached took calls past it.
- **The fix.** A thread is counted from when it is **told to stop**, not when its grace ends: every place that stops a thread (a call's time up, cancelled or given up, a start's time up or given up, a runtime dropped) goes through one method that marks the thread (`Watched::tell`); the thread itself says when it ends; and a thread told to stop that has not ended within the grace is left running, counted once and its extension disabled, whoever looks first (its own call, or the next start or call of its extension). A start or a call of an extension **waits** while a thread of that extension is being stopped, or while threads being stopped would with those left running reach the cap, and once its look is over is refused if that thread was left (`Disabled`) or the cap is reached (`TooManyAbandoned`, a new `CallError` for a call). A call's wait is within a hook's time and ends at the call's cancel, and nothing is sent before it. A start's wait is bounded by a grace after the last thread it sees told (each thread it sees gets a grace of its own, from when it first sees it); a tool's start also ends at the call's cancel, and a command's at its cancel or its time; a hook's start runs on a task of its own, which the hook's run gives up at its cancel and nothing awaits, so it is bounded by that grace and its evaluation time, not by the hook's time. Waiting, not refusing, keeps "the next use makes a new runtime" true when the thread comes back within its grace.
- **Twins it closed.** A call whose future was given up in a native loop, a start given up there, and a runtime dropped while its call ran, each set the stop flag and nothing else: the thread ran on, counted by nothing, and its extension started again. They now count from the telling, and the next start or call judges them.
- **The real bound,** now in the module's doc, [12-extensions.md](../../../architecture/12-extensions.md) ("Limits" and "Threading") and [security.md](../../../security.md) §3, said the same way in each: four threads left running in a process, plus the calls and starts already running when the count reached four, which nothing can stop; and one an extension, plus one for each of its other runtimes, in the process's other sessions, whose call was already running, or whose start was already evaluating, when the first was told to stop. The review's first case with all five calls spinning together still leaves five; that residue is in [threads-left-running-past-the-cap-by-calls-already-running](../../../outstanding/threads-left-running-past-the-cap-by-calls-already-running.md) (step 32). **Step 28's answered.md, its Threads budget row ("at most four left running in a process before no extension starts"), is corrected here;** step 28's own record is left as it is.
- **Tests** (`cineris-ext::it left_running`, each thread that will not stop held at `A_CALL_IS_STARTED` or `A_DEFINITION_IS_REGISTERED`, never racing a native loop; time is the fake timer's): a runtime started in another's grace waits and is refused when that one is left; one that waits goes on once that thread comes back; four other sessions' calls made in a grace are refused once that thread is left (one thread, not five); past the cap a runtime alive before it takes no call; a thread whose call was given up, and one whose start was given up, are judged by the next start.
- **On `main`** (the tests alone, at `main`, on the reference machine): five of the six fail. "a runtime of the extension started in the first one's grace, before it was judged: Ok(ScriptRuntime { name: \"probe\", alive: true, .. })"; "assertion `left == right` failed: a call made in another runtime's grace was let in, left: Ok(Number(1))" (its held calls let in, which went on when the hold's bound passed); "a call was let in past the cap of threads left running: Pending"; "the extension started again while its thread that would not stop ran on: Ok(…)", for the given-up call and the given-up start. The sixth, a start that goes on once the thread comes back, passes there, as it should: it guards against a fix that refuses rather than waits.
- **Breaks:** `a-thread-being-stopped-is-not-waited-for` (4 tests), `a-thread-told-to-stop-is-not-counted` (6), `a-start-given-up-is-not-counted` (1), `the-cap-is-not-looked-at-for-a-call` (1): all caught (`cargo xtask mutate step-28-fixes-engine`, 9 of 9). Seven breaks of `mutations/step-28.breaks` named the code this changed and were moved to it (`a-thread-waiting-for-an-answer-is-not-woken`, `a-thread-left-running-is-not-counted`, `a-main-module-that-will-not-stop-is-not-counted`, `a-call-given-up-leaves-its-script-running`, `a-glob-may-hold-a-backslash`, `a-thread-left-running-disables-nothing`, `a-dropped-start-leaves-its-thread-running`): all seven caught again at the moved code. Stress: `cargo xtask stress -p cineris-ext --count 100`, every test passed every time (seeds 0 to 99). The tests of `cineris-ext` and of every crate that depends on it (`test --dependents`, 1,142 tests) pass.

## 10. A fetch's lookup outlived it and could fill the blocking pool

**Outcome: fixed, with a process-wide count of system lookups.**

- **The fix.** `cineris_llm::SystemResolver` holds each lookup to one of `LOOKUPS_LIMIT` (8) places in the process, taken before the lookup is sent to the blocking pool and moved into the blocking closure, so it is given back when `getaddrinfo` returns, not when the fetch's future is dropped at its time or its cancel. A lookup past them waits for a place holding no thread, within its fetch's own time and cancel. No floor on a fetch's `timeout` was added: with the count, a script's loop of `timeout: 0` fetches of names that never answer holds at most eight threads.
- **Why a process-wide count, not one in flight per runtime.** Only the resolver knows when the blocking lookup returns; a count per runtime would need the runtime carried through the core's host into the fetch client, would not bound the process (each session's runtime would have its own), and would not cover step 30's HTTP MCP client, which will use this fetch client and has no runtime. **Who shares it:** every client of `Fetcher` with the system resolver (extensions' fetches now, step 30's MCP client later). **The provider transports do not:** they look their hosts up through their HTTP client's own resolver, so a provider's request is never held by the count. **What it costs:** while one extension's lookups that never answer hold all eight places, other fetches' lookups wait, up to their own time, for one to return (the system resolver's own timeout, tens of seconds); that slows fetches only, never the session's other blocking work. Every place is the process's: N runtimes that each keep one lookup of a name that never answers queued can make another client's lookup wait about N/8 of the resolver's timeouts, and a fetch waits within its own time, so it fails as out of time; [system-lookups-wait-in-turn-behind-names-that-never-answer](../../../outstanding/system-lookups-wait-in-turn-behind-names-that-never-answer.md) (step 30) has it, with a share of the places for each client as the way to close it.
- **Test:** `cineris-llm fetch::tests::a_lookup_given_up_holds_its_place_until_the_lookup_returns`, over the new seam `on_the_pool` with a resolver that blocks until the test lets it go (no name looked up, no network): two lookups given up still hold their places, a third waits and is not sent to the pool, and runs once one has returned.
- **On `main`:** confirmed by reading only, as the review was: `main` had no place to hold, and the test is of the new seam. The break that restores giving the place back as the future goes (`let _place = place;` to `drop(place);`) is caught.
- **Breaks:** `a-lookup-given-up-frees-its-place`: caught.

## 13. A brace glob with an absolute path passed the manifest's check

**Outcome: fixed.**

- **The fix.** `manifest::check_glob` looks at **every alternative** the glob's braces give, read as the glob's compiler reads them (`cineris_policy::glob::brace_alternatives`, a new public function over the compiler's own `expand_braces`, so there is one reading of braces), nested braces included: each must not be empty, start at a root (`/`, `//server`), at `~` or at a drive (`C:`), or name `.` or `..`. A `\` (so `\\?\` and `\\server`) and a control character are refused in the whole text, as before. A glob whose braces the compiler cannot read (one not closed, too many alternatives) is left to the compiler to refuse, as before: it never compiles, so nothing of it is matched (a core test holds an extension whose capabilities do not compile that way). Stricter in one more case: an alternative that is wholly empty (`{,src/**}`, which compiled to every file of the workspace) is refused.
- **Tests:** `cineris-ext::it manifest::no_alternative_of_a_globs_braces_leaves_the_workspace` (`{/etc/**,src/**}`, nested, `{.,/}etc`, `{..}`, `{~,x}/`, `{C:/x/**,src/**}`, `{src,c:x}`, `//server/share` in braces, an empty alternative; and brace globs that stay inside still read); `cineris-ext::it capability::a_glob_whose_braces_name_a_path_outside_reads_nothing_there`, which compiles such a glob past the manifest's check and reads the folder beside the workspace through it, by its absolute path and through `..`.
- **On `main`:** both fail: the manifest read `{/etc/**,src/**}` ("called `Result::unwrap_err()` on an `Ok` value: Manifest { … read: [\"{/etc/**,src/**}\"] … }"), and the capability test's manifest took the glob naming the folder beside the workspace. That the read through such a glob is refused was held on `main` by `let inside = …` alone, which the review's break showed no test caught.
- **Breaks:** `a-glob-is-looked-at-whole-not-by-its-alternatives` (2 tests) and the review's `a-path-outside-the-workspace-matches-a-glob` (`let inside = true;`, caught by the capability test): both caught.

## The pre-push review of the third pull request

The maintainers' review of the third pull request, before its push, found these in this part; each has a test that fails without its fix and a break in a fresh [mutations/step-28-fixes-engine.breaks](../../../../mutations/step-28-fixes.breaks) (the first list was merged into the step's own).

1. **A wait could wait without bound** (medium-low). `settle` began a fresh grace at every wake, so a thread with no judge of its own (a call given up in a native loop, a dropped runtime) was left running only by a whole round with no other thread ending in it: a process where some thread ended every 2 s kept a start waiting, holding its session's runtime slot. **Fix:** each thread being stopped gets a grace of its own from when the wait first sees it, which no wake begins again; the wait leaves every thread whose grace has passed and sleeps until the next one's. The engine's timer has no clock, and a runtime dropped has no timer to read one from, so the grace runs from when the wait first sees the thread, never before it was told, rather than from an instant recorded at the telling. **Every wait is bounded:** a call's is within its time (a hook's) and ends at its cancel; a tool's start ends at the call's cancel, and a command's at its cancel or its time (both new in the core's `ext::tools`, and either drop lets go of the slot); a hook's start runs on a task of its own, given up at the hook's cancel, bounded by a grace after the last thread it sees told and its evaluation time, not by the hook's time. **Test:** `left_running::a_wait_woken_by_another_thread_ending_keeps_its_grace` (another extension's runtime dropped, its thread ending a second into the wait: the waiting start is refused 2 s after it first saw the stuck thread). **Break:** `a-wait-begins-its-grace-again-at-every-wake`.
2. **A start evaluated as its time ran out gave a stopped runtime** (low-medium): its thread idled in `serve()`, told to stop and never shut down, and the next use left it running, disabling the extension with nothing spinning. **Fix:** such a start is `Err(Limit(Time))`, and its inbox, dropped, ends the thread. A point, `A_MAIN_MODULE_IS_EVALUATED`, after the evaluation and before the start is told, lets the test hold it there. **Test:** `left_running::a_start_evaluated_as_its_time_runs_out_leaves_no_thread`. **Break:** `a-start-out-of-time-gives-its-runtime`.
3. **The cap's branch of the wait had no test.** **Test:** `left_running::a_call_waits_while_threads_being_stopped_would_reach_the_cap` (three left, a fourth extension's in its grace, a fifth's call waits and is refused `TooManyAbandoned`). **Break:** `threads-being-stopped-do-not-count-toward-the-cap`.
4. **Braces a glob cannot read let its text through unchecked** (low): `["/etc/**}"]` and `["../x/}"]` passed the manifest. **Fix:** such braces are refused when the manifest is read, as the compiler refuses them. The core's test of an extension whose capabilities do not compile now uses an unclosed set (`src/[a`), which the manifest takes and the compiler refuses. **Test:** the three cases added to `manifest::no_alternative_of_a_globs_braces_leaves_the_workspace`. **Break:** `braces-a-glob-cannot-read-are-let-through`.
5. **`Atomics.wait`** is dropped from the open item: `can_block` is false and `rquickjs` never sets it, so it throws.
6. **The bound is said the same way everywhere** (the module's doc, 12-extensions, security.md §3, this record), with another session's start that was already evaluating among the threads it allows.
7. **Nothing held the resolver's eight places.** **Test:** `cineris-llm fetch::tests::the_systems_lookups_take_the_processs_places` (with seven places taken, a lookup of `localhost` takes the eighth, and the next waits). **Breaks:** `the-systems-lookups-have-more-places`, `the-systems-lookups-take-no-place`. The cost to other clients is in finding 10, above.

**Verdicts:** `cargo xtask mutate step-28-fixes-engine`, 6 of 6 caught. The tests of `cineris-ext` (201) and of every crate that depends on it (1,145) pass, and `cargo xtask stress -p cineris-ext --count 100` passed every time on a hosted Linux runner (run 45956204037).

## A Windows stress run of the third pull request

A stress run of the third pull request on Windows (`stress -p cineris-core -p cineris-agent -p cineris-ext --count 50`, try 45968251959) failed once in 50: `cineris-core::it commands::an_interrupt_stops_a_running_command_and_its_questions_are_its_own`, seed 46, "The extension `probe` is not started in this process: a thread of it did not stop when its time was up". Linux passed all 50.

- **The cause.** A thread told to stop counted toward the cap until it had **ended**, and a start of its extension waited for that end with a grace on the session's timer. In that test an interrupted command's thread had already come back (its call's end told, the call over) and was ending, which takes real time, longest on a loaded Windows runner. The next command's start waited for it, and the test then moved its clock 30 s for that command's own time (the start's own sleep for the command's time, new in the pre-push fixes, is one the test's `sleeping_for(30 s)` can find first): the start's grace passed with the thread not yet ended, and it was left running, the extension disabled. So both of the questions asked: the grace is the session's fake timer, which a test moves while a thread's end takes real time; and the thread had a judge, its own call, which had already seen it come back.
- **The fix.** A thread that comes back within its grace (its call's end told, or its start's) is released from the cap at once, not when it has ended (`Watched::came_back`, a state of its own): it stopped as told, and ends at the shutdown it was sent or as its inbox closes. Nothing waits for its real end any more. What still waits on the session's timer is only a thread that has not come back, which is what the grace is for; a test that moves its clock past a grace while such a thread runs on means it.
- **Test:** `cineris-ext::it left_running::a_thread_that_came_back_counts_no_more_while_it_ends`: a call cancelled in a loop the interrupt reaches, its thread held at `AFTER_A_CALLS_END_IS_TOLD` (its end told, the thread not ended), counts nothing, and a start of its extension with the clock moved a grace meanwhile starts. Before the fix it counted one, and the start was refused `Disabled`.
- **Break:** `a-thread-that-came-back-still-counts`, in a fresh [mutations/step-28-fixes-engine.breaks](../../../../mutations/step-28-fixes-engine.breaks): caught. The tests of `cineris-ext` (210) and of every crate that depends on it (1,182) pass on the reference machine; the Windows stress run is in the maintainers' report.

## Mechanisms looked for elsewhere

- **A limit looked at only at a start:** the starts let go (`LET_GO`) were counted while a start ran and released when its future was dropped, though a module in a native loop runs on: closed by the same telling. Nothing else found that counts what can still grow after its start.
- **Blocking work whose future is dropped at a limit while its thread runs on:** `cineris_tools::run_blocking` returns at its cancel and leaves the work running, by design (the work is handed the token). A script's host calls through it are served one at a time a runtime, so a script holds at most one such thread a runtime, not a pool's worth. The provider transports' HTTP client looks names up on the blocking pool the same way, but only for the session's own requests, which no script chooses. Not changed.
- **A path or glob check that looks only at a string's start:** the command analysis refuses brace expansion outright, the permission rules' globs go through the compiler, which reads each alternative, and a knowledge entry's paths are literal paths, not globs. None found.
