# Step 28 fixes: hooks and their trust

The part of the fixes to step 28 that takes the review's findings 4, 5 and 14 (the review of step 28 at `5eda6204`, its hooks and pins areas), and its lower-confidence notes on hooks. Branch `worktree-step-28-fixes-hooks`; breaks `mutations/step-28-fixes.breaks` (merged from its part list).

## 4. An approved project gate lapsed when its entry changed, went, or was turned off

- **Outcome:** fixed, with the way out the maintainers settled: the gate is held, and the trust question and `cineris permissions trust` list each approved item with no entry as removed, whose yes drops its pin.
- **What it was on `main`:** `ext::hooks::in_session` built a changed hook's held gate from the *changed* entry (its event, `observe` and tools), so `observe = true`, another event or other tools moved the gate off the calls it gated. `Configured::of` dropped an `enabled = false` entry before its standing was judged (`enabled` is not hashed), nothing looked for a pinned hook with no entry, and a pinned entry that no longer compiled was put on no event. The review's runs 45938975731 and 45938633973 showed `read` running in each of those cases (the review's `review_hooks.rs` and `review_pins.rs`).
- **The fix:** a trusted project's hook that was approved (pinned, or approved for the session) and has no entry that runs as approved now (changed, taken out, turned off, or no longer compiling) holds a failing gate on `tool.before` for every call and one on `prompt.submit` (`ext::hooks::held_gates`). The pin keeps only the hash, so what the hook gated is not known; the rule is the one an extension whose approved registration is known nowhere follows. One whose name one of the user's own hooks takes holds nothing: that is the user's word, as for a project's extension whose name a folder of the user's takes. The session says so once, naming the hook, what happened to it and the way out (`held_way_out`, kept apart from the gates). The gate's failure says the same, and never "correct its entry, or turn it off", which would be no way out.
- **How the person lifts it:**
  - A changed hook: approving it as it is now. The trust question lists it as changed when a session opens; `cineris permissions trust` shows it; a yes pins the new hash, and the session opened after the yes runs it. The same session's held gate stays: the hooks are settled as the session opens.
  - One with no entry that runs: the trust question (`ext::hooks::asked`) and `cineris permissions trust` (`Core::project_removed`) list it as removed, kind `hook`, "Removed: the project's hook `gate`, which you approved, is no longer in the project's file. What it gated is not known (only its hash was kept), so it holds every tool call and every prompt until its approval is taken away. A yes takes its approval away." A yes drops its pin (`TrustStore::drop_pins`, new and small: each pin of the kind and name only while it is still at the hash listed, no format change, its doc saying a drop is an approval change that signed approvals will need the person's signature for). At a terminal `cineris permissions trust` asks "Take these approvals away? [y/N]"; without one it drops nothing and says how many it left.
  - Either: taking the project's trust away (`cineris permissions untrust`), which lifts them at once in a running session (finding 5).
- **The twin, a removed project extension:** `cineris permissions trust` on a trusted project only added pins (`approve`), so the documented way out of a removed project extension's held gates, "trust the project again without it", kept its pin and lifted nothing. The same listing now covers it: a pinned project extension that is not in the project's folder of extensions (and nothing of the folder was left out unread, so missing is told from unread) is listed as removed, with the gating events the registration cache keeps for its pinned hash, or "What it gated is not known", and a yes drops its pin (`ext::found::removed`).
- **Tests:**
  - `cineris-core ext::hooks::tests::an_approved_projects_hook_holds_both_gates_once_not_as_approved`: each case the review ran (`observe`, its event, its tools, its time alone, taken out, turned off, broken) holds both gates on every call and says so with the way out; as approved, untrusted, and a name the user's takes hold none.
  - `cineris-core ext::hooks::tests::the_trust_question_lists_an_approved_hook_that_is_gone_as_removed`.
  - `cineris-core::it hook_trust::an_approved_projects_gate_holds_whatever_its_file_does_to_it`: the review's scratch test made real; each case refuses the prompt, the gate named with the way out, told once; a yes to the changed entry lets the read run; a yes to the question that lists a removed one takes its pin away, and the next session is not asked.
  - `cineris-core::it hook_trust::trusting_a_project_again_takes_away_the_approvals_shown_as_removed`: `project_removed` lists a turned-off hook and a gone extension, and `trust_project_dropping` drops both and leaves the rest.
  - `cineris-policy trust::tests::a_drop_takes_away_only_the_approvals_listed_as_they_were_read`.
- **Left open:** the precise alternative, a cache of each approved hook's event, tools and `observe` keyed by its hash (no `trust.toml` change), so that only the gate it held is held: [an-approved-hooks-gate-is-held-on-every-call](../../../outstanding/an-approved-hooks-gate-is-held-on-every-call.md), step 32. A yes the trust store cannot keep drops nothing, so a removed hook's gate then holds for that session.

## 5. A project's hook commands outlived its trust

- **Outcome:** fixed.
- **What it was on `main`:** `assemble` built `SessionHooks` once as the session opened, and `reload` never touched it; after `cineris permissions untrust` and a reload the session was `Untrusted` and `run_hook_command("lint")` still started the program (the review's run 45938633973).
- **The fix, and why a live flag:** `HookCommands` holds a token for the project's trust, fired once by `withdraw_project` and never set again in the session. `reload_session` fires it whenever the store's judgement, or the load's judgement again, reads the store and gives a standing under which a session runs none of a project's hooks (`Untrusted`, `Never`), before anything else of the reload is applied, so a broken file or a failed build cannot keep it back (`withdraw_untrusted`). The loop's points read it (`on_now`, through `HookCommands::project`), as do the session's own events, a script command's held-gate check and the test seam; each project run is under a child of the token, so the runs still going stop. A flag fits the code: the loop is handed `PointHooks` once, built from `SessionHooks` as the session opens, so taking entries out of `SessionHooks` would not reach it without rebuilding the loop's hooks. The user is told once ("This project is no longer trusted, so its hooks no longer run in this session, and the gates its changed or removed hooks held are lifted."). Trust given again in the session takes effect at the next session, as any change of the hook commands does.
- **A project's held gates leave with its trust:** an untrusted project's hooks are nothing to its session (the review of the second pull request, H1), and the held gate exists so that the model cannot lift a gate by editing the project's file. Taking trust away is the person's act, which a session's command cannot do (guard B covers `permissions untrust`), so it lifts them, as a project's extension's held gates go when its trust is taken away (12-extensions, "Hot-reload"). This is the documented rule for extensions, applied to hook commands; no feature changed beyond the finding.
- **Tests:** `cineris-core::it hook_trust::sys_a_projects_hook_command_stops_with_its_trust` (the review's test made real) and `hook_trust::a_projects_held_gates_leave_with_its_trust` (a held gate refuses the prompt; the trust taken away from outside and a reload, the prompt goes through, said once).
- **Twins:** in a build without the script engine, the gates a project's extension holds are settled as the session opens and kept after untrust; that only narrows and is documented ("What is held is settled as the session opens"). A project's `session.start` observer started before the trust went runs to its own time.

## 14. `{path}` handed a user's hook a secret file before the call's question

- **Outcome:** fixed as the owner chose: held back until the person's yes, with the hook run after it, before the call.
- **What it was on `main`:** `tool.before` runs before the call's question, and `HookCommands::run` filled `{path}` with every file within the workspace, so `read .env` handed `/work/.env` to a user's `["scanner", "{path}"]` before the person answered.
- **The fix:**
  - **Held back** (`cineris-policy`'s `Engine::holds_back_from_hooks`, one query that changes no rule and asks what `judge_path` does): a read or write the engine asks about or refuses for what the file is: a secret's look, a protected path written, or a path rule that asks or denies. Not an ordinary edit asked about at `supervised`, a file a rule allows, or one `unrestricted` lets through unasked.
  - **Deferred** (`ext::hook_command`): a waited-for `tool.before` hook command that uses `{path}` while the call names such a file does not run, and answers `HookOutcome::AfterAnswer`. An observer of `tool.before` does not run for such a call.
  - **Run after the yes** (`cineris-agent`'s round, the smallest phase that would do): such hooks are no opinion as the call is decided and are kept with the call (`Call::deferred`). In the task that puts the question, after a yes and before `Answered` is reported, they are run again with `HookInput::answered` set, so the core fills `{path}`. Their refusal or failure refuses the call; so do an ask and a replacement there, since the call is not asked about twice and the yes was to the call as shown (`hooks::after_the_answer`). A no or a stop runs none of them; where nobody can be asked the call is denied and none runs. Where the rules allow the call and nobody is asked, they run at once, before it. With a replacement they are shown the call as it will run. The call's question stays open while they run, so no other question is put meanwhile, within their own times.
- **Tests:** `cineris-agent::it hooks::a_hook_that_waits_for_the_answer_runs_after_the_yes_and_before_the_call` (deterministic, the question held at a gate: not run again while asked; run after the yes, then the call; a deny, an ask or a replacement after the yes refuses it; a no runs it no more; with nobody asked it runs at once and may refuse); `cineris-agent hooks::tests::after_the_answer_only_a_pass_lets_the_call_run`; `cineris-policy::it files::a_hook_is_held_back_from_the_files_asked_about_for_what_they_are`; `cineris-core::it hook_trust::sys_a_users_hook_is_handed_a_secret_file_only_after_the_yes` (the hook's report is not there when the question is put, is there with `.env` after the yes; a no runs nothing; a failing hook after the yes refuses the read; a plain file is handed to it at once).
- **What it is not:** a hook command is given the event's JSON on standard input, the call's arguments with it, so the file's name reaches every hook, and a user's own hook runs with the user's rights and can read what the user can. The deferral keeps `{path}` from pointing a program at the file before the yes, and is not a boundary of confidentiality. The maintainers kept it at that, and 12-extensions and security.md (§3, §12) say so.

## After the pre-push review of the third pull request

The pre-push review of the pull request that carries this part found seven more things in it, each fixed with a test that fails without it and a break (`mutations/step-28-fixes-hooks.breaks`, a fresh list; the first one was merged into `mutations/step-28-fixes.breaks`):

1. **An unreadable trust store withdrew the project's hooks for the session.** The store's judgement read as untrusted when the store could not be read (a newer build's file, its permissions, a read on Windows while another process replaces `trust.toml`), and the withdrawal never came back, every held gate with it. The judgement now says when it could not read the store (`assemble::Judged::store_unread`), and such a look only holds the project's hooks back (`HookCommands::project`, `ProjectHooks::Unread`): none runs, each of its gates fails, refusing what it gates (an approved gate through its failing twin, `OnEvent::while_unread`; a held gate as it was), and a script command is refused by a project's `prompt.submit` gate. A look that reads the store again and finds it trusts the project puts them back; only one that reads it and finds it does not withdraws them. Each change is told once. Test: `hook_trust::sys_an_unreadable_trust_store_holds_a_projects_gates_until_it_is_read`. Breaks: `unreadable-store-withdraws`, `unread-project-gate-lapses`, `store-read-again-keeps-hooks-back`, and `in-force-ignores-the-projects-trust` in place of `step-28-fixes/withdrawn-project-hook-runs-by-name`, whose code changed.
2. **A replacement's note carried selectors to the model** (the twin of finding 6): `replaced_note` used `visible`, which keeps one variation selector after a character. It uses `visible_to_the_model` (from the selectors part, brought here as it is). Test: `cineris-agent hooks::tests::a_replacements_note_carries_no_selector_to_the_model`. Break: `replaced-note-keeps-selectors`.
3. **A hook the managed file locks read as removed.** The configuration leaves out a project's hook whose name the managed file locks, so an approved one read as gone, held every call and prompt, and was listed as "no longer in the project's file". The names left out so are now in `Loaded::project_hooks_locked`, and are the administrator's word, as a name one of the user's own hooks takes is the user's: they hold nothing and are not listed as removed. And a name the user's hook takes is judged before `enabled`, so one turned off as well holds nothing either. Tests: `ext::hooks::tests::an_approved_projects_hook_holds_both_gates_once_not_as_approved` (new cases), `cineris-config::it hooks::a_lock_keeps_a_projects_hook_of_its_name_out`. 4. **No test stopped a project's run going on when its trust went.** Test: `hook_trust::sys_a_projects_hook_run_going_on_stops_when_its_trust_is_taken_away` (a project gate's program held running, its time on the session's clock; the trust taken away and a reload; it stops, its process gone, and the read is refused). Break: `running-project-run-not-stopped`.
5. **No test held an observer back from a secret file.** `sys_a_users_hook_is_handed_a_secret_file_only_after_the_yes` now has an observer that takes `{path}`: it writes nothing for the `.env` reads, the close having waited for every run, and is handed the plain file. 6. **The docs said more of the deferral than it does:** 12-extensions and security.md (§3, §12) now say that it keeps `{path}` from pointing a program at the file before the yes, that the file's name still reaches every hook on its standard input, and that a user's own hooks can read what the user can.
7. **The withdrawal's notice** had stray spaces from a lost line continuation, and named only changed hooks; it names changed or removed ones. A test's doc that the new agent test had been put under is back on its test.
