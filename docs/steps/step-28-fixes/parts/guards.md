## 1. `cineris project`'s changes had no guard B

- **Outcome:** fixed. `project add`, `accept`, `edit`, `promote`, `disable` and `delete` call `not_under_a_session` before the core starts; `project list` and `path` only read.

- **Test:** `cineris-cli::system nested::sys_cineris_run_by_a_sessions_command_is_held_or_refused`, rule `an_approving_subcommand_refuses_under_a_sessions_command`: the session's script now also runs `project add fact`, `project add command … --purpose check --command 'touch review-ran.txt'`, `project accept k_1`, `project accept --shared`, `project edit`, `promote`, `disable`, `delete`, `auth login anthropic`, `auth logout anthropic` and `stats reset`; each must say it was refused, and `project list --all --json` must then list no entry.

- **Breaks:** `project-change-not-under-a-session`, `project-add-not-under-a-session`, `auth-login-not-under-a-session`, `stats-reset-not-under-a-session`. Verdicts: below.

## Stated, from the early review of these fixes

- **Windows: `CINERIS_SESSION_STORES` is the command's own environment.** A script that sets it (`set CINERIS_SESSION_STORES=APPDATA=C:\evil|…`) and the variable it names passes a nested run's check, and `ProgramData` with it. A reads the line that sets it; a script file is the residual's. Reading the harness's own environment block (its process's parameters, read with `PROCESS_VM_READ`) would close it, but needs the harness's process found for every way B tells it (a job names its process; a service's start does not), and was not built here: it is in 06's residual and the guards' item.
- **Windows: a peer in another logon session.** The socket's check resolves the harnesses' jobs through `Local\`, the server's own logon session's namespace; a command of a harness in another logon session (an SSH session's, which is session 0, or a second desktop session's) whose line of parents no longer reaches its harness stays in that harness's job, which is not found, and is admitted. Resolving the jobs in the peer's own session (`ProcessIdToSessionId`, `\Sessions\<n>\BaseNamedObjects`) was not built here: it is stated in security.md section 5 and the guards' item.
- **WSL crossings.** A Windows session's script that runs `wsl.exe -e cineris ext add …` reaches the Linux installation, whose check sees WSL's `/init` and no harness; a WSL session's command that runs `cineris.exe` through interop reaches the Windows installation, with no harness on its line or job of it.
