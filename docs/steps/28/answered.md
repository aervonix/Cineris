## The design, before building

Settled with the maintainers before any product code, so that each pull request is reviewed against rules written first.

### 1. Who controls what

| Who | Controls | Can make the harness do | Held by |
|---|---|---|---|
| **The user** | Their configuration (`[hooks.<name>]`, `[extensions.<name>]`), `<config dir>/extensions/`, `<config dir>/commands/`, the skill folders in their home; every approval; `cineris ext add` | What they approve | Their own configuration is taken as written, as their rules are: no tool can write it. Script extensions are pinned all the same (point 5). **No project file can name, change or turn off the user's hooks or extensions** (point 4). |
| **A repository's files** | `.cineris/config.toml`'s hooks, `.cineris/extensions/`, `.cineris/commands/`, `.cineris/skills/`, `.agents/skills/`, `.claude/skills/`; and every file a hook's program reads (a formatter's configuration, `package.json`'s scripts) | Commands and skills: text for the model, as `AGENTS.md` is, with no trust. Hooks and extensions: **nothing** until the project is trusted and each definition is approved as it is now. What a hook's program reads, the model can write unasked at `supervised`: each start is decided by the permission engine (point 3). | Project trust and a pin per definition. `.cineris/` is a protected path, so the model's writes there are asked about. |
| **An extension's author** | Its script and manifest | Register tools, commands, a prompt section, and hooks **only on the events its manifest lists**; call host functions | The manifest the user approved, then the permission engine, then the sandbox for programs; the runtime's limits. |
| **The model, through tool calls** | The arguments of extension tools; which calls a hook sees; files it may write | Call an extension's tool (asked by default); feed a hook's placeholders (resolved paths only, point 3); write a skill or a command file (text) | The permission engine. It cannot approve anything, cannot write the configuration or state directories (closed to every tool), and cannot add an extension in this step. |
| **What a hook or an extension returns** | Text | Reach the model as a labelled notice, a note on a result or a tool's result | Caps (8 KiB a hook's context; the output policy for results), a label naming the source. |

**The invariants the reviews test against.**

1. **Nothing runs unapproved.** The engine evaluates only bytes whose hash is the pinned one (point 5), and a hook command starts only from a definition that is approved as it is now (a project's) or that is in the user's own configuration.
2. **No ambient access.** A script reaches files, programs, the network, the user and storage only through the host functions below. Every host call is checked against the manifest first, refused there with the capability named, then decided by the permission engine as the same effect a built-in tool would declare, and a program it starts is confined by the sandbox where the sandbox enforces. No host function returns a credential or the session's content, changes configuration or grants a permission. What a hook is given (prompts, a call's arguments, its result) is the session's content, so a script's hooks are a capability of their own: the manifest lists the events, and the approval says in words what each lets the extension see ("every prompt you send").
3. **A hook only narrows.** It can refuse, or turn an allowed call into a question; nothing a hook answers runs anything unasked that the policy alone would not have run.
4. **Extensions cost start-up nothing.** The engine is not initialised until something of an extension's is used; what extensions register is read from the registration cache.
5. **A limit stops one runtime, never the session.**
6. **Windows behaves the same,** with script shims escaped or refused (point 3).

**A residual risk, stated:** QuickJS is C. A memory-safety bug in it could let a script out of the runtime; a script that breaks one of the engine's own invariants trips an assert, which **ends the whole process**: the assert's line (expression, file, line) on standard error, the process gone with the signal of an abort. On Linux the terminal is put back by the handler step 23 installed for `SIGABRT`; on Windows the console may be left in the harness's modes. The session log is flushed at item boundaries, so the session resumes with `--resume`, without the call that was running.

### 2. The host functions

The whole surface. Registration happens only while an extension's main module is first evaluated; a call to register later is refused, and so is any other host call during that evaluation (a top-level `await` of one): it belongs to no call, so it would have no deadline, no checkpoint and nobody to ask.

| Function | Manifest | The permission engine decides it as | Limits |
|---|---|---|---|
| `cineris.tool(def)`, `cineris.command(def)`, `cineris.on(event, filter, fn)` | `api`; for `on`, the event in `hooks` | (registration) | Names by the registry's rules (ASCII letters, digits, `_`, `-`, `.`); 64 tools, 32 commands, 32 hooks; a description 2 KiB, a schema 16 KiB; the seven events only, and only those the manifest lists |
| `cineris.exec(program, args, {cwd, stdin, timeout})` | `exec`: the program exactly as listed | `exec`: the arguments quoted in the session shell's syntax, so the command analysis reads the same words; `cwd` resolved as the shell tool resolves it, inside the workspace; and `network` (any host) beside it when `exec_network = true` | 30 s by default, never past the call's own time; 256 arguments of 32 KiB; input 1 MiB; standard output and error 1 MiB each, cut with a flag |
| `cineris.fs.read(path, {offset, limit})` | `read` globs | `read`, through the `read` tool's own code (the read gate, files that look like secrets) | 1 MiB of text a call; a binary file refused |
| `cineris.fs.write(path, text)` | `write` globs | `write`, through the `write` tool's code: the round's checkpoint (so undo covers it). A protected path is refused before the engine is asked, at every level (since the fix of the protected writes, [parts/protected-writes.md](parts/protected-writes.md)) | 1 MiB; refused inside a hook (no round to record it in) |
| `cineris.fs.list(path, {glob})`, `cineris.fs.search(pattern, {path, glob})` | `read` globs, on the root **and on each entry** | `read` and `read_tree`, through the `list` and `search` tools' walk, which follows no link | Those tools' own caps |
| `cineris.http.fetch(url, {method, headers, body})` | `net` host patterns | `network`, the host | `https` only, or `http` to an address the manifest names literally. **The name is resolved once, and a loopback, link-local, private, unique-local or metadata address is refused** unless the manifest names that literal address or `localhost` (never through a `*`), as [security.md](../../security.md) section 2 says of fetching; the connection is made to the address that was checked. No redirect followed (a 3xx is returned, and the next fetch is checked again); a script may not set `Host`, `Connection`, `Transfer-Encoding`, `Content-Length` or a `Proxy-` header; request body 1 MiB, response 4 MiB, 30 s; no cookies, and no header the host adds |
| `cineris.ask(question, choices)` | none | (a question to the user, `question/ask` with the extension's name) | In tools and commands only, never in a hook; one open at a time for an extension, five a call; `null` where nobody can be asked |
| `cineris.notify(text)`, `cineris.progress(text)` | none | (to the front ends, not the model) | 1 KiB and 10 a call; progress 200 characters, the latest kept |
| `cineris.state.get(key, {scope})`, `cineris.state.set(key, value, {scope})` | none | (none) | JSON values. `session` (the default) is kept in the log's `ext` records, so a resume has it as the session left it and a fork as it was at its point, and a rewind leaves it, since a record belongs to the session and not to a branch (settled by the maintainers during the build); `project` in the state directory, one file an extension and project (`{"version": 1, "values": {…}}`, read strictly, written owner-only and atomically), and a file this build did not write refuses the call and is left as it is, not set aside (settled by the maintainers during the build). 64 KiB an extension a scope; a key 1 to 256 bytes; at most a hundred `set` calls in one call of the extension, and 16 MiB of `session` records an extension a session (settled by the maintainers during the build): [decision 0041](../../decisions/0041-an-extension-s-state-is-kept-in-the-session-s-records-and-a-project-file-read-strictly-within-fixed-bounds.md) |
| `cineris.log(...)`, and `console.log`, `warn`, `error` as its names | none | (the harness's own log) | 4 KiB a line, 100 lines a call |

- **Paths are checked as the built-in tools check them.** A path given to `fs.*` is resolved by the session's path resolver first (`~`, a relative path, `..`, a link followed to where it leads, case on Windows), and the manifest's globs are matched against the **resolved** path relative to the workspace. A path that resolves outside the workspace is outside every manifest glob in this step. Tests give every check non-canonical input: `~`, relative, `..`, a link inside the workspace leading out, a link outside leading in.
- **Under which name, and which default.** A host call is decided as a call of the extension's tool that made it (`tracker/find_issue`; a hook's as `tracker/hook.tool.before`, a command's as `tracker/command.deploy`), with the default of the built-in tools (allow, where nothing else decides), its own effects, and an `ext` effect of that name beside them: so a `deny ext tracker/*` refuses every host call of the extension, and nothing else about the decision differs from a built-in tool's.
- **A question a host call puts offers only "allow once" and "deny",** as leaving the sandbox does. A rule kept from it ("for the session", "in this project") would reach far past the extension: an `exec_network` call names no host, so its rule would be `network *`, and every later fetch of the model, an MCP server or another extension would go unasked.
- **Inside a hook,** a host call the engine would ask about is refused, with the rule that would allow it named: a hook decides by its answer, not by putting questions.
- **Where the calls run.** A host call is made on the core's side, inside the future of the tool call, hook or command that the script serves, with that call's context: a write lands in that round's checkpoint, and a question names the tool that asked. A command runs outside any round: in it, as in a hook, `fs.write` is refused.

### 3. The processes: `cineris.exec` and hook commands

Both start through the shell tool's process runner (`cineris-tools`' `process::Runner`), so the process tree, the staged kill, the Job Object's limits and the guard are the shell's.

| | `cineris.exec` | A hook command |
|---|---|---|
| **The program** | A name in `exec`: a bare name found in `PATH`'s absolute directories outside the workspace and the write roots (`cineris_base::program::find_outside`); an absolute path as named, refused inside a write root while commands are confined. A relative path is refused. | `command[0]`, by the same rules. |
| **Its arguments** | As the script gives them, each one argument. | Placeholders are whole arguments, never part of one: `{path}` (each file a `read` or `write` effect of the call's plan names, **resolved**, in the system's plain form (never `\\?\`), one argument each, at most 64, so a model's `--flag` cannot become an option; a call with none, such as a shell command, does not run the entry (since the maintainers settled it, so that `find {path} -delete` cannot become `find -delete`; a folder, or a file outside the workspace, never fills it)), `{tool}`, `{workspace}`, `{event}`. `--file={path}` is refused when the entry is read. 256 arguments at most. |
| **Decided by the permission engine** | Yes, as an `exec` of the extension's tool (point 2), and asked about where the engine asks. | **Yes, every start**, as an `exec` of the expanded line in the workspace, as the project's checks are ([architecture/15-efficiency.md](../../architecture/15-efficiency.md)): a `deny` or a stop refuses it. Where the engine would ask, a hook of the user's own configuration runs (it is the user's word), and a project's does not, nor any hook where a managed `ask` rule is among the reasons. A hook never puts a question; one that does not run has failed (point 6). |
| **Its environment** | What a shell command is given (`env::build`): no provider key, no `shell.env_remove` variable, an absolute `PATH`, `NoDefaultCurrentDirectoryInExePath` on Windows; the session's private `TMPDIR` when confined. | The same. The event's input is on standard input; its standard output is read up to 1 MiB, of which the answer is at most 64 KiB. |
| **The sandbox, where it enforces** | A launcher of its own (`cineris_sandbox::launch`), at every level, `unrestricted` included: network only with `exec_network = true`, and write roots **made from the manifest's `write` globs**: each glob's directory before its first wildcard (`out/**` gives `out/`; `**/*.rs` gives the workspace), so a program can write no wider than the manifest's directories, though inside them not only the files its globs name. | A launcher of its own: reads, no write root, no network, unless the entry says `write = true` (the workspace) or `network = true` (for a project's hook, part of what is pinned). |
| **The look at protected paths** | Before and after every start that has a write root, as for a confined shell command (step 26), with its stop. | The same. |
| **Where it does not** (Windows, no Landlock, sandbox off) | Started as it is, as the shell's commands are; the permission engine has decided it. **The manifest's `write = []` then binds the script's `fs.write` and not its programs,** and the approval says so on such a system. | The same: started as it is, after the engine's decision. |
| **What reaches the model** | Nothing directly: the script gets the exit code and the bounded output. | The hook's answer (point 6). |

**What a hook's program reads is the workspace's.** A formatter reads its configuration, `npm run lint` runs `package.json`'s scripts, and the model can write those unasked at `supervised`. That is what an allowed `npm test` or a project's check does today, and [security.md](../../security.md) section 11 gets hooks as one more such path; where commands are confined the hook reads everything and writes nothing unless its entry says so, and where they are not, a hook runs with the user's rights. The engine's decision of every start is what keeps a project's hook from running a line the user would have been asked about.

**Windows.** The program is looked for in each absolute directory of `PATH` in turn, as `name.exe`, `name.cmd`, `name.bat` there before the next directory; a name that already has an extension is taken only if it is one of these three (compared without regard to case), and nothing else of `PATHEXT` (`.ps1`, `.vbs`, `.js`) is ever run. A `.exe` is started directly, **each argument in double quotes by the C runtime's rules** (since the maintainers settled the arguments on Windows: the standard quoting leaves `*` bare, and a Cygwin-family program, such as Git for Windows' `usr\bin`, expands it). A `.cmd` or `.bat` is started as `%SystemRoot%\System32\cmd.exe /d /e:on /v:off /s /c ""<script>" "<argument>" …"`: the whole line in an outer pair of quotes, which `/s` takes off, and the script's path and each argument in double quotes of their own, inside which `^ & | < > ( )` are plain characters to `cmd.exe`. Command extensions stay on, since the shims package managers write use them (`%~dp0`, `call :label`). **A run of backslashes before a closing quote is doubled,** so the program the script starts reads the argument as it was given; **an argument, or the path, holding `"`, `%`, `!`, `& | < > ^ ( )`, a carriage return, a line feed or a NUL is refused,** naming the argument and the character (`& | < > ^ ( )` since the same settlement: a script that takes the quotes off and reads an argument again, `set A=%~1` and then `echo %A%`, acts on them, and an npm shim's `--x=(a)` is refused with them). **On every system an argument holding `＂` (U+FF02), `＼` (U+FF3C), `¥` (U+00A5) or `₩` (U+20A9) is refused,** naming it and the character: a program that reads its command line in a Windows code page is given them as `"` or `\` by the code page's best fit. Tested on a Windows runner: every refused character, a script that reads an argument again given an `&`, a trailing backslash, a path with spaces, a real package manager's shim, and Git for Windows' MSYS2 `echo.exe` given `*` in a folder of files.

**The socket refuses them** (step 27): they are the server's own commands, by their line of parents on Linux and by the job the server joins on Windows, and a test of each starts one that tries.

**Two rows in [security.md](../../security.md), section 12,** one for each, naming `crates/cineris-tools/src/process/mod.rs` called from the core's modules for them, as the row for the shell's version does.

### 4. The manifest and the registration cache

Both are files users keep, and both carry a version from the first one.

```toml
# <config dir>/extensions/tracker/extension.toml, or .cineris/extensions/tracker/
api = 1                     # the version of this file's format and of the host functions
name = "tracker"            # the registry's name rules; the folder's name
version = "0.1.0"           # the author's, shown
description = "Issue tracker tools"
main = "main.js"            # a module in the folder
prompt = "prompt.md"        # optional: section 7 of the system prompt, 4 KiB

[capabilities]              # each empty unless given
exec = ["gh"]               # programs: bare names or absolute paths
exec_network = false        # whether those programs may reach the network
read = ["**"]               # workspace path globs (the permission rules' glob)
write = []
net = ["api.github.com"]    # hosts for cineris.http.fetch (`*.example.com` allowed, `*` alone is any host)
hooks = ["tool.before"]     # the events its script may hook, each shown in words ("sees every call's arguments")

[limits]                    # optional, never above the hard caps
memory = 32                 # MiB, at most 64
time = 120                  # seconds a tool call, at most 600
```

- **Read strictly:** an unknown key, a wrong type, or an `api` this build does not know refuses the extension with the reason. The capabilities are values the harness enforces, so they fail closed ([decision 0028](../../decisions/0028-enforced-values-fail-closed.md)).
- **The folder** holds only regular files and directories: a link of any kind (a symbolic link, a junction) anywhere in it refuses the extension. At most 256 files, 1 MiB each and 4 MiB in all. Imports resolve only to files in it.
- **The configuration it adds.** `[hooks.<name>]` with `event`, `tools` (tool events only: names, or `source/*`; a `tool_call` is matched by `tool_call` and by the `source/tool` it names), `command`, `observe`, `timeout`, `write`, `network` and `enabled`; and `[extensions.<name>]` with `enabled` alone, which `cineris ext disable` writes. **The user's and a project's are kept apart, not merged by name:** `[extensions]` is the user's alone; a project's hooks are its own, each waiting for trust and pinned, and a project's hook with the name of one of the user's is refused and shown, so no project file can change or turn off a hook or an extension of the user's. `[skills]` stays reserved.
- **The registration cache** is `<state dir>/extensions/registered.json`, in the state directory that every tool is closed to: `{"version": 1, "entries": {"<content hash>": {"name", "api", "tools": […], "commands": […], "hooks": […], "prompt": "…"}}}`. It is keyed by the extension's content hash, written when an extension is approved (the script is evaluated once in a throwaway runtime whose host functions are stubbed and record what it registers), and pruned of hashes no pin names. A session reads it and knows every approved extension's tools, commands, hooks and prompt text without starting the engine.
- **The live registration must be the cached one.** A script can tell the stubbed runtime from a live one, so each live runtime compares what its evaluation registered with the cache's entry, and an extension that registers anything else is disabled, named, and its gating hooks fail (point 6).
- **A missing entry fails closed.** A missing cache is empty, and an unreadable or newer one is set aside (moved to `registered.json.set-aside`, and read as empty); an approved extension missing from it is registered when the session opens, off the start-up path, and the first turn waits for it, so a gate it holds is never skipped.
- **`state`'s files are keyed by where the extension comes from** (the user's or this project's) and its name, so a project's `tracker` never reads the user's `tracker`'s values.

### 5. Trust pinning

- **What is hashed.** An extension: every file of its folder, sorted by its path with `/`, each as its path, its length and its bytes (SHA-256, `cineris_base`'s content hash), the manifest among them. A project's hook: its whole entry in a canonical form (event, filter, command and arguments, `observe`, `timeout`, `write`, `network`).
- **Where the pin lives.**
  - A project's hooks and extensions: in the project's entry of `trust.toml` (step 12's store, kinds `hook` and `extension`), approved through the trust question, which lists them, or `cineris permissions trust`, which shows them as the question does and pins them on a yes at a terminal, where `--with-extensions` is ignored, or, where there is no terminal to ask at, with `--with-extensions` (settled by the maintainers during the build).
    A yes the trust store could not keep approves the extensions it listed, by the hashes shown, for that session alone; *Keep trusting it, without what is new* leaves them unapproved for the process alone, with no record in `trust.toml`, so the next start asks again (settled by the maintainers during the build).
  - The user's own extensions: in a new store beside it, `<state dir>/pins.toml` (`version = 1`, one `[[pin]]` of kind, name, hash and time each), owned by `cineris-policy`'s `trust` module, written owner-only and atomically under a lock and read strictly, as `trust.toml` is. A new file, rather than a version 3 of `trust.toml`, so that an older build does not refuse every project's trust. Step 30 keeps the user's MCP servers' per-tool pins there.
  - The user's own hooks: not pinned. They are the user's configuration, which no tool can write, as the user's rules are.
- **What a change does.** The extension is disabled: no runtime, its tools leave the registry, its commands are not listed, and the session says so with the command that approves it. **Its gating hooks do not lapse:** an extension whose approved registration holds a `prompt.submit` or `tool.before` hook, and which is changed, unreadable or failing, has those events counted as a failed hook (so they deny, with the reason and the command that approves or disables it), until the user approves it again or disables it. (As built in step 28's script hooks: the gates are made from the registration the pin names, as the registration cache keeps it, or the session's own knowledge of it; an extension whose first registration failed holds one on each gating event its manifest lists, and a changed one whose approved registration is known nowhere holds both, its manifest being the change's; a store of approvals that cannot be read keeps the gates of what the session loaded, and of a user's extension never loaded those its manifest lists, but none of a project's never loaded. The refusal names the extension, why, and the way out, and the user is told once a session.) The engine **never** evaluates a changed file: a runtime is made from a snapshot of the folder read whole, whose hash is compared with the pin, and modules are served from that snapshot, never from the disk. A file changed after the snapshot was taken is not seen until the next runtime, which checks again. So a file's time of change, which a command can set, decides nothing; it only tells hot-reload when to look.
- **Approving** is `cineris ext add <path>` for the user's own (it reads the folder once into a snapshot, shows that snapshot's manifest in words and every file, asks, and then writes, pins and registers **that snapshot**, never a second read of the source, which may be a folder the model can write), and the trust question for a project's, which pins the definitions it showed, as it does the rules. A project's extension of the same name as the user's is not used: the name is the user's, and `ext list` says so. Within one source, extensions whose names differ only in case are all refused, on every system, since on Windows they are one name and would share what an extension keeps (settled by the maintainers during the build).

### 6. Hooks in the loop

The loop gets **one seam, `cineris_agent::Hooks`**, a trait the core implements with `cineris-ext`, beside `Policy`. With no hook whose filter matches, every point is passed at once: the loop's behaviour, and every existing test of it, are unchanged.

| Event | Where | A hook may | Waits for it |
|---|---|---|---|
| `session.start` | The core, when a session opens (new, open, fork), after trust is settled | Add context: a notice before the first prompt | Its hooks, up to their time, before the first turn starts |
| `prompt.submit` | The loop, as a prompt is taken to start a turn, or as a steering message is delivered | `deny`: the prompt is not recorded and never reaches the model, and the front end is given the text back with the hook's reason; a prompt that would start a turn ends it `denied`, and a steering message is dropped while the running turn goes on. Add context: a notice after the prompt | Yes |
| `tool.before` | The round, after `Policy::decide` said allow, allow read-only or ask, before a question is put or the call starts | `deny`, `ask`, `allow`, or replacement arguments | Yes; the call counts as one whose plan is not known yet, so nothing that could conflict with it starts |
| `tool.after` | The round, after the call ran, before its result is recorded | Add a note to the result, labelled with the hook's name | Yes |
| `turn.end` | The loop, as a turn ends, whatever its outcome | Add a notice for the next turn | No: delivered at the next turn's start if it is in by then, else at the next safe boundary |
| `compaction.before` | The loop, before a summary is requested (by hand, at the threshold, in the background) | Add instructions for the summary | Yes |
| `session.end` | The core, as a session closes | Observe | No; given up to 5 s while the process ends |

- **`tool.before`, decided.** Hooks on one event run together, and their answers combine as `deny` over `ask` over `allow`, so order never matters. **A hook only narrows:** `ask` turns the policy's allow into a question (the question shows each hook's reason), and `allow` never lifts the policy's question. A call the policy denied or stopped is not shown to hooks.
- **Replacement arguments,** from exactly one hook: checked against the tool's schema, planned by the tool, and decided by the policy again; a denial or a stop stands. **Then the user is always asked** (only "allow once" and "deny"), with the hook's name and both sets of arguments, whatever the policy would have answered, and where nobody can be asked the call is denied. Otherwise a hook could turn an allowed `cargo test` into another command at `autonomous`, or a write into another file at `supervised`, where neither is asked about: a replacement is new work nobody chose, and only a person can choose it. The hooks are not run on the replacement; it is scheduled by its own new decision; for `tool_call` it may not name another tool (that denies). The call's item is updated for the front ends, and its result tells the model which hook changed the arguments to what. **Two hooks that both replace the arguments deny the call** (the page's "apply only if exactly one" stays true, and the call does not run with arguments neither hook accepted).
- **A call decided again** (the re-decide step) is shown to its hooks again with its new plan and the model's own arguments; what they said before is dropped.
- **Failure.** A hook that fails, times out, or answers with something that is not the contract (an unknown field or decision: the answer is enforced, so it is read strictly) counts as `deny` on `prompt.submit` and `tool.before`, with the failure named; on the other events it is shown to the user and adds nothing. An `observe = true` hook is never waited for, its answer is not read, and its failure is logged.
- **Times:** 5 s by default for a hook that is waited for, 60 s for an observer, at most 60 s and 10 minutes. A script hook's time is the engine's interrupt and the host's deadline, both on the session's clock, so the tests use the fake clock.
- **A hook command's start** is decided by the permission engine every time (point 3); one that is refused has failed; where the engine would ask, a hook of the user's own configuration runs and a project's does not, nor any hook where a managed `ask` rule is among the reasons (point 3, as the owner confirmed: "The owner's answers").
- **A hook's writes** (a `write = true` command such as a formatter) are not recorded in the round's checkpoint, and the model's view of a file a hook rewrote is stale until it reads it again; stated in the page. The look at protected paths runs around it (point 3). A script hook's program has no write root (since step 28's script hooks), and what it writes where the sandbox does not enforce is not recorded either.
- **`compaction.before`'s text** goes into the summary's instructions under a line naming the hook; the summary the model writes from them carries no label of its own, so an extension the user approved can steer what a summary keeps. Stated in [security.md](../../security.md) section 3 as a residual risk of approving one.
- **The outstanding items that wait for this step** (`a-tool-that-makes-links-beside-other-calls`, `a-kept-run-adopted-after-its-call-moved`) are closed for extensions by one rule: **an extension's tool is always scheduled as exclusive,** whatever its definition says (`readOnly` is shown to the user and decides nothing). So no later call starts beside it, it counts as a call that may change the file system, and it is never started before its response ends. Each item stays open for MCP's tools, handed to step 30, which must follow the same rule or close them otherwise.

### 7. Sections 6 and 7 of the system prompt

- **Section 6, the index:** the skills (name cut to 64 bytes and description to 300, each on one line with control characters and Unicode's format characters, the bidirectional overrides among them, taken out; and the path to `SKILL.md`, relative to the workspace or under `~`), at most 100, the rest counted; then each source of dynamic tools (`name/`, its tool count and its description's first line), with one line on `tool_search`. 8 KiB in all. Custom commands are not listed: they are for the user to type, and the model cannot run one.
- **Section 7:** the `prompt` file of each enabled extension, ordered by name, each under a line that names the extension and says the text is its author's, 4 KiB each and 16 KiB in all, taken from the registration cache (so it is the approved text).
- **The epoch rule.** Both are built when an epoch begins and are fixed for it. **Section 6 is outside the epoch's `base` hash,** as sections 4 and 5 are, so a skill added between two processes does not make a resume a new epoch; a change to it during an epoch is told at the next turn's start in one notice of a new source, `extensions`, that gives the section whole, as the profile's notice does. **Section 7 is inside `base`:** it is text with the system prompt's authority that the user may have taken back, so a resume whose section 7 would differ (an extension removed, disabled or changed) begins a new epoch, and during an epoch a removed, disabled or changed extension's text is withdrawn by a notice that names it and says to disregard it. The declared tool list never changes: extensions' tools are reached through `tool_search` and `tool_call`. Declaring an extension's tool directly (`expose = "direct"`) is left to step 30, which needs the same for MCP; the manifest has no such key until then.
- **Reading a skill (the owner's call; settled by the owner, 2026-11-21: only while the user turns on `permissions.read_skill_folders`, off by default, and asked at the first run; narrowed by the maintainers to the user's own folders apart from the workspace, "The owner's answers" above).** The folders of the skills actually found, the user's own and those of a trusted project, are given to the session as an allowed read (a session rule, source `session`), so that reading a skill in the user's home is not asked about; reads only, a `deny` still wins, and a folder found through a link that resolves outside it gets no rule. ### 8. The runtime

- **One runtime an extension, on a thread of its own,** made the first time something of the extension's is used and kept while the session is open. The page said one thread for all; a thread each means a script that computes until its time is up never holds up another extension's hook. Host functions are promises answered from the core.
- **One call at a time in a runtime.** The engine's interrupt check belongs to the runtime and cannot tell which call a piece of work is for, so a runtime runs one call (a tool's, a hook's, a command's) to its end, its awaits included, before it starts the next. **A call's time starts when it starts running, a hook's when it is asked:** a hook that waits for its turn behind the extension's tool or another of its hooks spends its own time waiting, and one still waiting when its time is up is withdrawn before it starts, the call the runtime serves going on. So a gating hook of an extension whose tool is running can fail for the wait alone, and its gate then refuses the call it is about, as any hook that runs out of time does: an extension whose tools run long gives its gating hooks the time they take, or keeps its tools short. A host call never fires a hook (hooks are on the model's calls), so a runtime cannot wait on itself.
- **Limits.** Memory 32 MiB by default, 64 at most; the stack 256 KiB; a tool call's time 2 minutes by default, a hook's its own. The time is enforced inside the engine by its interrupt check against the running call's deadline, and outside it by the host, which stops waiting. **A thread that does not come back** (stuck inside the engine past its deadline and a grace) is abandoned: the runtime counts as torn down, a new one gets a new thread, and the old thread's memory is held to its runtime's limit until it ends. A tool's result is at most 1 MiB of JSON before the output policy, which then applies as to any tool, and the result is labelled as the extension's.
- **A limit hit, or the engine's out-of-memory,** tears the runtime down: every call of that extension still running fails with the limit named, and the next use makes a new runtime from a fresh snapshot. An exception is an error result for that call only.
- **Start-up.** Opening a session reads nothing of an extension's but what the trust question needs, for a client that answers it: a project's extension folders, each held only as its hash, manifest, shown text and prompt file (no other bytes), none read once 16 MiB of a root have been read (every byte read counts, of a folder left out after its read too, and a file over its cap is refused by its length, unread) and no more than a session watches (4,096 places within a root's extensions), the rest left out and counted, and, only when the project has an extension, the user's folder for its names, with the places within its extensions looked at (`read_dir` and `lstat`, up to 4,096, as the session's finding counts them) and none of their files read. A task that runs once the session's loop runs, off the path that opens it, reads the user's folders whole, the pins, the trust store and the registration cache, and reads a project's folder again only to register it at the approved hash; the first turn waits for the extensions' tools, not for the cache's write (settled by the maintainers during the build). Measured on the reference machine, on an otherwise idle machine, a release build, medians of 30, with three extensions of about 4 KiB: an open costs 0.70 ms with three of the user's and 0.69 ms with none; the trust question, answered not now, 0.93 ms with three of the project's and 0.79 ms with none; the first turn 9.7 to 11.7 ms in every case, three registrations of a cache miss included ([parts/pr2a1-found.md](parts/pr2a1-found.md)). A process-wide count of runtimes made (`cineris_ext::engine::runtimes_made`) lets the start-up test assert that none was, and no thread is started for an extension until it is used. The step's budget table gives the threads a session with extensions has: one a runtime in use.

## What must not change

**The permission engine's rules.** The step made one change to them, and the owner lifted the rule for it: **A**, the engine's built-in refusal of a session's command line that runs one of the harness's approving subcommands, at every level and whatever the rules (`cineris_policy::approving`), the one protection the owner took the engine's "must not change" off for ([parts/pr3b-manage.md](parts/pr3b-manage.md), "Settled during the build", point 4); the narrow re-check of its fixes found the rule held otherwise. Everything else the step checks stands outside the engine's rules: the manifest's gate, asked before the engine (point 2); the extension host's refusal of a protected write at every level, which "changes none of the engine's rules" ([parts/protected-writes.md](parts/protected-writes.md)); the skill folders' read rule, made and taken back as "allow for this session" is, with no new kind of rule ([parts/pr2a2-skills.md](parts/pr2a2-skills.md)); a host call's question offering only "allow once" and "deny", and a question in a hook turned into a refusal; and what PowerShell and `cmd` call read-only asked about rather than allowed, for an extension's program (`HostQuestion::read_only_asks`). What would need the rules to change is left to step 32: [an-extensions-program-is-judged-by-the-sessions-shell](../../outstanding/an-extensions-program-is-judged-by-the-sessions-shell.md) and [a-hook-cannot-run-a-line-read-as-only-reading-where-another-program-may-run](../../outstanding/a-hook-cannot-run-a-line-read-as-only-reading-where-another-program-may-run.md).

**The loop, except through its hook points.** The loop has one seam, `cineris_agent::Hooks`, beside `Policy`, at its points (`prompt.submit`, `tool.before`, `tool.after`, `turn.end` and `compaction.before`; the core runs `session.start` and `session.end`). With no hook whose filter matches, every point is passed on one synchronous check, and every existing test of the loop is unchanged (`cineris-agent::it hooks::with_no_hook_that_matches_every_point_is_passed_and_nothing_changes`). A prompt's ticket, by which a prompt a hook refuses goes back whole to the client that sent it, is `prompt.submit`'s ([parts/pr2b1-hooks.md](parts/pr2b1-hooks.md), point 4). **Outside the hook points, one change of data and none of behaviour, accepted by the maintainers:** a command's origin, carried through the loop as the ticket is (`SessionHandle::prompt_from`, `Prompt`, `Pending::Steer`, to `UserMessageItem.command`), which no branch of the loop reads ([parts/pr3a-commands.md](parts/pr3a-commands.md), point 3). Sections 6 and 7 of the system prompt and their epoch rule are the context's, which the build plan gives step 28 ("What later steps inherit from step 15"). The change to the loop the step found it needed, a stop in a tool's result ending the round, was not made in it: the owner approved it as a small step of its own after step 28 ([its record](../stop-ends-turn/answered.md)).

## What later steps inherit

A, the permission engine's built-in refusal of Cineris's approving subcommands, is defence in depth; B, those subcommands' own check under a session's command (Linux by the line of parents; Windows by a harness on the line of parents, by its job, and by a service's start made after a harness began), is the guard; C, approval by the hash shown, replaces every bare yes.
