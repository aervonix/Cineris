# Step 28, its parts: script hooks

The second part of step 28's hooks ([answered.md](../answered.md), "The design, before building", points 5, 6 and 8): an extension's registered hooks, functions of its script, on the seam the first part built ([pr2b1-hooks.md](pr2b1-hooks.md)), beside the hook commands.

## What was built

- **Script hooks on the seam** (the core's `ext::script_hooks`, read by `ext::hook_points` beside the hook commands): each hook a loaded extension registered with `cineris.on`, on an event its manifest lists, named `<ext>/hook.<event>[.N]`, from when the extension is loaded until it is withdrawn; a project's only while the project is trusted and the extension pinned as it is ([12-extensions.md](../../../architecture/12-extensions.md), "As built in step 28: script hooks").
- **A run is a call of the extension's runtime** (`LoadedExtension::call_hook`, `Target::Hook`), one of its queue, its time from when it is asked (`cineris-ext`'s `CallContext::asked`): queued past its time it is withdrawn before it starts, running past it it is stopped. A run is a task the session keeps, under a token of its extension's, and its future stops it when dropped, polled or not.
- **In a hook, a question is a refusal** (`CallHost`'s `Phase::Hook`, `for_a_hook`): a host call the engine would ask about is refused, naming the rule that would allow it, so a hook runs only what the engine allows outright; `cineris.ask` and `cineris.fs.write` are refused, and a hook's program has no write root.
- **Its gates fail closed:** a changed, unreadable, removed or unloadable extension that stands approved keeps its `tool.before` and `prompt.submit` gates on their events, failing, from the registration approved; one never registered holds one on each gating event its manifest lists.
- **A session whose finding died starts no turn:** `turn/start` and `session/compact` are refused with `extensions_not_settled` ([11-rpc-protocol.md](../../../architecture/11-rpc-protocol.md)).
- **The breaks:** the part's list (`step-28-scripthooks`) is put together in the step's, [mutations/step-28.breaks](../../../../mutations/step-28.breaks).

**Settled during the build:**

1. **A stopped turn's script hooks do not start,** the maintainers' rule for hook commands ([pr2b1-hooks.md](pr2b1-hooks.md), point 11) carried over; a hook's host call in a stopped turn is refused with the stop and is no stop of its own.
2. **A hook's time starts when it is asked** (`CallContext::asked`, an addition to the engine; a tool's call passes none and is unchanged). Point 8's "costs nothing in practice" no longer holds: a gating hook queued behind its extension's long tool can fail for the wait alone, and its gate then refuses the call; point 8 says so.
3. **No write root in a hook** (the maintainers, after the early review): `serve` gives the manifest's write roots to a tool's call, and to a command's as before (point 13), never to a hook's, pinned at `supervised` and at `read-only`; a hook that needs to write is a hook command with `write = true`.
4. **Gates never lapse** (the early review's merge-blocking finding, point 5): an extension's hooks leave their events only when the user turns it off, the project's trust goes, its pin is taken away, or, for a project's, a folder of the user's takes its name. Where no registration was ever known (a first registration failed), a failing gate on each gating event the manifest lists (the maintainers); where a changed extension's approved registration is known nowhere (not cached, the cache set aside, never loaded in the session), both gates, since the manifest found is the change's (the maintainers, after the full review confirmed a change dropping `capabilities.hooks` left none). A pinned extension deleted from disk keeps gating, since a deletion may be an unconfined program's, and says so: "its folder is gone; if you removed it, turn it off with `[extensions.<name>] enabled = false` (or, from the next release, `cineris ext remove <name>`)" (the maintainers' words, the table named after the re-check, pinned by `a_removed_extensions_gates_hold_until_it_is_turned_off`). Each refusal names the extension, why, and the way out, written in one place (`script_hooks::way_out`) for the third pull request's `cineris ext` to change; the user is told once a session; the core's own operations are no hook points, so turning the extension off stays open, pinned by `a_changed_extensions_gates_hold_and_the_way_out_stays_open`.
5. **`session.start` and `session.end` script hooks** are built in this part, as the hook commands' are.
6. **A finding that dies fails the session's turns** (`extensions_not_settled`), rather than letting a first turn wait for ever or start without a gate.
7. **A hook's `cineris.state` is its extension's,** keyed by its source and name, as its tool's is (the independent review's "`state` keyed by name alone", answered for hooks too).
8. **`hook.` and `command.` names are the harness's:** no tool or command of an extension may take one.
9. **A store of approvals that cannot be read keeps the gates of what the session loaded** (the maintainers, and the owner for a project's): where `pins.toml` or `trust.toml` cannot be read, an extension the session loaded keeps what it registered, by its source and name, whatever it is found as now or if it is gone; of the user's, one never loaded holds the gating hooks of the cache's entries of its name beside its manifest's gating events as found (the cache names no source, so it only ever adds: the fourth look found a project's same-named entry with no hooks lifting a gate where the cache stood in alone); an extension approved that could not be loaded, or never registered, is known by what it registered or its approved manifest's gating events; what the session knows of each is the latest, by source and name, and one unpinned or no longer trusted is forgotten; **of a project's, one never loaded holds nothing, since no repository gates a session by itself** (the owner's answer after the re-check, as the first part's point 10 settled for a project's hook entries); where a pin stands and only the registration is unknown (a changed extension), both gates are held. The user is told once, naming the file under `~` and the fix. A project not trusted as the session opened has nothing of it looked at, and its store is not read (a read of an untrusted project's folder, which the decisions round had added, is taken out again). Pinned by `an_unreadable_pin_store_holds_the_gates_of_the_users_extensions`, `an_unreadable_trust_store_holds_the_gates_of_a_projects_extensions`, `an_unreadable_trust_store_gates_nothing_of_a_project_the_session_never_loaded` (an untrusted project, and one trusted for the run, whose manifests list `prompt.submit`: the prompt goes through) and `an_extension_approved_for_the_run_keeps_its_gates_while_the_store_is_unread`, each with the way out working while gated.
10. **The loop's own stop is a stop for a turn's hooks** (the maintainers): a call nobody can be asked about, under `fail_on_denial`, ends the turn without the policy's `stop_turn`, so a hook of it still running had its host calls allowed. Recording it with `stop_turn` would also decide again, and stop, the round's earlier allowed calls, against the round's rule that a call written before the refused one, and allowed, still starts; so it is recorded for hooks alone (`EnginePolicy::stopped_for_hooks`), read by a script hook's start, a hook's host calls and a hook command's start. Pinned by `a_turn_the_loops_own_stop_ends_refuses_its_hooks`.
11. **A hook cannot run a line read as only reading where another program may run** (the maintainers, after the full review): on Windows, and in a PowerShell or `cmd` session, the refusal says so and names no rule, since none would help, and says that a hook command can; the engine's part is [an item for step 32](../../../outstanding/a-hook-cannot-run-a-line-read-as-only-reading-where-another-program-may-run.md), beside its sibling.
12. **`session.end` hooks are of no turn** (the maintainers, fixing the first part's forward): a `session.start` hook's stop refuses none of them.
13. **An extension's commands keep the manifest's write roots,** as before: the maintainers' call was for hooks, and the commands' are for the part that wires them.
14. **A runtime start that a run let go runs on, unawaited, to its own evaluation time** (the maintainers, after the third re-check, on the reviewer's agreement): a close that ended it past a 2 s grace counted it as abandoned and refused its hash for the process, so a `/new` during a slow module's start disabled the extension in every later session. Now nothing waits for it, not the close nor the core's shutdown, and it is abandoned only past its own time and grace, as any start is: the first part's "no run outlives its session" has this one bounded exception, stated in the page. The reviewer agreed on two conditions, both built: a start whose future is dropped tells its thread to stop, as a call's does (every place that awaits a script thread from a future was checked: calls, hooks and host calls through `ScriptRuntime::call`, already guarded; starts and the cache's registrations through `ScriptRuntime::start`, guarded now); and a start let go counts toward the cap of four while it evaluates, so that closing and opening sessions cannot stack starts, a gate whose start the cap refuses holding, failing, with the user told once that it clears within the evaluation time (`starts_let_go_count_toward_the_cap_and_a_gate_holds_meanwhile`). Each of the maintainers' four conditions has a test: such a start answers no host call after the close (`fs.write`, `exec`, `fetch`, `ask`, `state.set`, `notify` and `log` refused, nothing kept); the core's shutdown ends while it runs on; a later session in the same process runs the hook on a runtime of its own, the count of threads left running unmoved; past its time and grace it counts once.

**The engine's flaky test is settled** (its item, `an-engine-test-that-advances-its-clock-before-the-script-spins`, is deleted): the test moves its clock only once the module has registered its tool, just before the loop that never looks at the interrupt. It counts the engine thread's arrivals at the point `A_DEFINITION_IS_REGISTERED`, which a test can stop at and this one never holds. The item's recommendation, a host call just before the loop, could not be the signal, because no host call can be answered during a first evaluation.

## The early review

**The script hooks' permission path** (a fresh reviewer, of the first round): no high. A script hook could put no question to anyone and get none of its own host calls decided as a tool's. **Medium:** a gating hook vanished at the next turn when its extension changed on disk, became unreadable or failed to load (one byte appended to `main.js` dropped a `tool.before` guard), now held failing (point 4); and a hook's programs were given the manifest's write roots, unrecorded (point 3). **Lows,** each fixed with a test and a break: a hook's settled promises ran in the next tool call's phase; a call's leftover host calls could stop the runtime and end the extension's next call; the test of a hook that finds its turn stopped by another call; `asked` tested where the loop's own wait does not cover it; the close's `session.end` runs stopped together, and a runtime's start raced against the run's cancel; withdrawal stopping the runs going; the policy keeping the latest sixteen stopped turns, not one; the reserved names; a test that held one wording of two that fire at once; Windows' refusal of a program read as only reading.

**The full review** (a fresh reviewer, of the whole part after the early review's fixes): no high. **Medium:** a changed extension whose approved registration was not known took its gates from the changed manifest, so a change that dropped `capabilities.hooks` left none (now both events are gated); and on Windows, or in a PowerShell or `cmd` session, a hook can never run a line the engine reads as only reading, while its refusal named a rule that could not change that (now it names none, and the engine's part is [an item for step 32](../../../outstanding/a-hook-cannot-run-a-line-read-as-only-reading-where-another-program-may-run.md)). **Lows:** a store of pins or of trust that cannot be read dropped a loaded extension's gates; the loop's own stop under `fail_on_denial` was not a stop for hooks; the bound of sixteen stopped turns had no test that bit; the way out was not valid TOML for a dotted name (`[extensions.acme.lint]` names another table); a disabled runtime's way out could not work as worded; the finding read the stores with no extension; a runtime's start outlived its session; a `session.start` hook's stop refused every `session.end` hook, since both were of turn 0 (the first part's, fixed here); the commands' write roots had gone with the hooks' (put back: the maintainers' call was for hooks); a test that did not pin the cached filter. It confirmed that no gate lapses on any other way an extension stops standing approved, that the way out stays open, that no lock is taken in two orders, and that every change to the step's breaks follows the code.

**The re-check** (the same reviewer, of the fixes and the decisions round): no high. **Medium:** while a store of approvals could not be read, a loaded extension that was also changed or removed lost its gates, since they were made at the hash found, from the manifest found. **Lows:** what the session saw an extension register was kept as a mark, not as its hooks; while the trust store could not be read, an untrusted project's manifests chose what was gated (the owner's answer: no repository gates a session by itself); the way out of an extension the engine refuses for the rest of the process covered one of its three causes; the close waited for a runtime's start with no bound of its own; one break caught only through a stale result; a way out that named `enabled = false` without its table. It confirmed that the stop kept for hooks alone is read on the three hook paths and no other, that `NO_TURN` opens no hole, and that the read of an untrusted project's folder while the trust store is broken keeps every bound of the finding's (each root's 16 MiB, its 64 folders, the places' 4,096, no link followed out of the workspace or within an extension's folder), with nothing of it evaluated or registered.

**The third re-check** (the same reviewer, of those fixes): no high or medium. **Lows:** a project's extension approved but never registered, and one a session that opened with the store of pins unreadable never loaded, could still take its gates from a changed manifest (now from what was approved: the registration at the approved hash, or the registration cache standing in for the pins); a close that let go a runtime's start past its grace counted it as abandoned, which disabled the extension for the rest of the process (now the start runs on to its own time: point 14); the session's record of what each extension registered grew with every hash loaded (now the latest of each); two breaks caught by a hang rather than an assertion (gone with the close's ending of a start). It confirmed that nothing of a project the session never loaded is read or gates while the trust store is broken, and that taking out the read of an untrusted project's folder reopened nothing.

**The fourth look** (the same reviewer, of the start that runs on and the third re-check's fixes): no high or medium. It agreed with the maintainers' settling of the start that runs on, on two conditions, both built (point 14): a start whose future is dropped stops its thread, and starts let go count toward the cap. **Low:** the registration cache standing in for an unreadable store of pins could lift a gate, a project's same-named entry with no hooks taking the place of the user's manifest (now it only adds).

**The fifth look** (of those): no high. **Medium:** a start let go before it began, waiting on its runtime's lock or the look at the names on the way, was counted and never released, so that four such could stop every extension of the process from starting while the user was told it would clear (now the count is held only while a start runs, by the guard that releases it on every way out). **Low:** gates held from the cache for an extension the session never loaded lapsed if a store then became unreadable (now they are known as the rest are). It confirmed that every place a script thread is awaited from a future stops the thread when dropped.
