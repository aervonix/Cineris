# Step 28, its parts: the fetch

The second of step 28's pull requests: `cineris.http.fetch`, an extension's HTTP request made by the host. The maintainers settled that it comes in a pull request of its own after the engine's, and that its bar is the resolver: no second lookup, the refused ranges with their IPv6 forms and the written forms of an address, no redirect, and the headers that steer a request.

## What was built

- **The fetch client, in `cineris-llm`** behind `http`, since only that crate links the HTTP stack: `Fetcher`, given a resolver and a timer. A request's body and headers are checked before anything is looked up; the URL is read by the URL standard (`reqwest`'s `Url`), so every written form of an IPv4 address is the address it means; the name is looked up once and every address it has is checked; the HTTP client is made for that one fetch with a resolver that answers the request's host with the checked addresses and refuses every other name, no proxy, no redirect, no retry and no referrer, and TLS checked by rustls against the system's own roots with nothing fetched; and the connection's peer must be one of the checked addresses. What the client refuses before its lookup (the body, the headers, at most 64 of 64 KiB, the scheme and the host) is `fetch::check`, which the core calls before anyone is asked. The ranges refused unless the host is named literally are one list in `cineris-base`, `address::RANGES`, for later clients to take: what IANA's special-purpose registries mark as not reachable on the internet, the machine's own addresses, the local networks', and the metadata services of most clouds, AWS on IPv6, Azure and Oracle, each in its IPv6 forms too (IPv4-mapped, translated, IPv4-compatible, NAT64's well-known prefix, 6to4). `http` goes only to a literal address the caller allows, or to `localhost` when loopback is allowed, which is this machine's loopback alone.
- **The host that was checked is the host connected to.** The extension side reads the URL's host for the manifest's `net` patterns and the permission decision, and refuses a URL the URL standard would read as another host: one that does not begin with `https://` or `http://`, a control character, a space or a `\` anywhere, a user part, a `%` in the host, a host that ends in a number unless it is four decimal numbers (`0x7f.1`, `2130706433`, `127.1`, `0177.0.0.1`), and an IPv6 address with anything but hex digits, colons and dots, or an IPv4-mapped one. An IPv6 host is judged in its shortest form, the form the manifest keeps its address entries in. The client is given the host its caller checked, and refuses a URL it reads as another before the lookup. Found while the client was carried onto the first part's code: before it, a manifest allowing `*.example.com` let `https://evil.com\.example.com/` reach `evil.com`.
- **The wiring:** `cineris.http.fetch` in the engine's prelude and `host::serve` (the manifest's hosts; the host itself as the client's allowance when the manifest names it literally, and nothing for a name a pattern matched; 30 s at most, less if the script asks or its call has less left), and the core's host (the client's check, then a `network` effect on the host, decided as every host call is, its question showing the URL without its query and naming the headers sent without their values, then the client).

## The full review

One reviewer, who had not seen the author's reasoning, read the whole diff against the maintainers' bar (no second lookup, the refused ranges with their IPv6 forms and an address's written forms, no redirect, the steering headers) and the dependencies' own code. Each finding was fixed with a test and a break.

| Finding | Fixed by |
|---|---|
| **High, on Windows only.** `reqwest`'s default verifier is the platform's, and on Windows `CertGetCertificateChain` fetches what a server's certificate names, the issuer and the revocation lists, from any address, through Windows' own HTTP stack and on the thread that polls the fetch: a server a script chose could have the machine send requests to its loopback, its network or a cloud's metadata service, and hold the session's thread for up to 10 s. A Windows runner showed the connection. | The client checks with rustls against the system's roots (`tls_certs_only`, `rustls-native-certs`), fetching nothing; a fetch checks no revocation, as on Linux, and a server with an incomplete chain fails (the maintainers settled the trade-off). The provider transport keeps the platform's verifier: [its own item](../../../outstanding/the-provider-transports-tls-check-on-windows-fetches-what-a-certificate-names.md). |
| `url_host` read `https:good.com://evil.com/` as `evil.com` and the URL standard as `good.com`: the client's check refused it, but after the user had been asked about `evil.com`, and nothing tested that the core passed the client the checked host. | `url_host` takes only a URL that begins with `https://` or `http://` and has no control character, space or `\`; the core's passing of the host is tested. |
| Every literal entry of the manifest went with every fetch, so `net = ["*", "localhost"]` let a name a `*` matched reach loopback. | Only the host itself, and only when the manifest names it literally. |
| 24,577 headers panicked in `http`'s `HeaderMap::with_capacity`. | At most 64 headers of 64 KiB, counted before anything is made of them. |
| NAT64's local-use prefix, `64:ff9b:1::/48`, was read as the internet. | It is refused whole, with the rest of what IANA marks not reachable, 6to4 by the address it carries, and Azure's and Oracle's metadata addresses: one list, `cineris_base::address::RANGES`, as the maintainers asked, for later clients to take. |
| `localhost` allowed IPv6 forms of `127.0.0.1` that leave the machine (`::127.0.0.1`, `64:ff9b::7f00:1`). | This machine's loopback alone: `127.0.0.0/8` and `::1`. |
| An IPv6 host was judged by its text, so `[::ffff:127.0.0.1]` missed a rule written for `127.0.0.1`. | An IPv4-mapped host is refused, and an IPv6 host and the manifest's address entries are kept in one form. |
| The client's own refusals came after the question. | `fetch::check` before the question. |
| The question showed the raw URL, its query too, and nothing of what the fetch sends. | The URL without its query or fragment, through `visible`, and a reason naming the body's size and the headers' names. |
| The extension side's `Debug` printed header values. | `FetchCall` and `FetchRequest` print names, sizes and the URL without its query. |
| The docs and the code disagreed on the time, and claimed more than held. | 30 s at most, less if the script asks or its call has less left, and the docs say what holds now. |

The reviewer also found holding: one lookup, the pinned resolver, no proxy, no redirect, the header checks, the response's cap, cancellation and the time limit, and no URL in any error. Two breaks the reviewer found missing were added: the client's pinned resolver, and the core's passing of the checked host.
