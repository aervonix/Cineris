# Step 28, its parts: the step's close

The third part of step 28's third pull request ([answered.md](../answered.md), "The design, before building", point 10, item 3, "3c"): the three examples under [examples/](../../../../examples/) and their test, the conformance scenario, the start-up test with the examples approved, a build of the binary without the script engine made possible again, checked and failing closed, the step's break lists put together, and the step's report ([answered.md](../answered.md), "The step's report, at its close").

## What was built

- **Three examples** (`examples/`), each with a README that says what it shows, what its manifest asks for and why, and how to install it ([12-extensions.md](../../../architecture/12-extensions.md), "As built in step 28: the examples"):
  - `md-outline`: a tool, `md-outline/outline`, that gives a Markdown file's headings with their levels and lines, leaving out what is inside fenced code. It reads through `cineris.fs.read`, and its manifest asks for `read = ["**/*.md"]` alone.
  - `shell-gate`: a `tool.before` hook on the shell tool's calls alone (`hooks = ["tool.before"]`), which reads a line's words as a POSIX shell splits them, and the line given to `sh -c`, `bash -c` and `eval` again, and refuses `rm` given a recursive and a forced option (shortened long options and any case included) and `git push` with `--force`, `--mirror`, `-f`, a `+` refspec or a `+` `push` refspec set with `-c`, past git's own options that take a value, letting `--force-with-lease` through; its README says it is an illustration of a hook, not a safety boundary (after the full review).
  - `release`, laid out as the configuration directory is: a command file, `/release-notes <version> [audience]`, beside an extension's command, `/changelog:draft [since]`, which reads `git log --oneline --no-decorate` through `exec = ["git"]`, refuses a revision that begins with `-`, and returns the prompt to send.
- **Their test,** `cineris-cli`'s `examples::sys_the_examples_run_as_their_readmes_say`, one world and seven rules, each judged by its own name. The three are added with `cineris ext add`, once for the hash it shows and again with `--hash`; the command file is copied into the user's `commands/`; the workspace is a git repository with a tag and two later commits, made in one `git fast-import` (the test kit's new `scratch::git_with_input`). One release follows in two headless runs against the scripted model: `/changelog:draft v0.1.0` under `--allow 'exec:git log *'`, and `/release-notes 0.2.0` under `--allow 'ext:md-outline/*'`, in which the model outlines `CHANGELOG.md`, is refused `src/main.rs`, and sends five shell calls: `rm -rf`, `--force`, a `+main` refspec, the lease and `echo`. The lease passes the gate and is refused by the permission engine for its own reason, nobody being there to ask; `echo` passes and runs. No test reaches the network: the repository has no remote.
- **The conformance scenario** "a project's commands and extensions" (`cineris_testkit::conformance`), from the `release` example's files put in the project's `.cineris/` with `include_str!`: the trust question listing the extension, answered yes; a `turn/start` that names the command file; then, after the turn, so that the session's extensions are settled on every carrier, `commands/list` and `extensions/status`. It runs in process and over the wire (`cineris-rpc`'s `conformance::every_scenario_is_the_same_in_process_and_over_the_wire`) and through the binary (`cineris-cli`'s `serve::sys_serve_stdio_conforms_to_the_core_in_process`). The script command is listed, not run, since the scenarios start no process. No golden file and no generated file changed.
- **The start-up test with the examples approved,** `cineris-core`'s `extensions_reload::with_the_examples_approved_no_engine_starts_until_one_is_used`: with the three pinned and cached, opening a session, a turn whose call none of their hooks is on (`list`), and `commands/list` make no runtime, and the first call of `md-outline/outline` makes one (`cineris_ext::engine::runtimes_made`). The tests before it held a session with no extension (`extensions_reload::with_no_extension_a_session_looks_once_a_folder_and_reads_nothing`) and a user's extension of one tool (`extensions_found::a_users_extension_stands_by_its_pin`), neither with a hook on a tool that is never called, nor with commands listed.
- **A build of the binary without the script engine, possible again and checked** ([decision 0005](../../../decisions/0005-extension-mechanism.md), "A build without the engine, held since step 28's close"). With `cineris-core`'s `scripts` off the binary no longer compiled: `cineris ext add` called the core's evaluation and approval of an extension, which exist only with the engine.
  - `cineris-cli` passes the engine through as its own `scripts` feature, on by default, and the workspace takes `cineris-core` with its default features off, so that no crate between the binary and the core turns the engine on for it: the CLI names `mcp` and `sandbox`, `cineris-rpc` names none, and its tests' dev-dependency names all three.
  - Without the feature, `cineris ext add` says the build has no script engine and exits with 2, before the extension's folder is read.
  - `cargo xtask check` gains a `no-scripts` step: it asks `cargo tree` whether the binary with `scripts` off and its other default features on still reaches `rquickjs`, for every target, fails naming the cause if it does, and then lints that build with warnings denied (`cargo clippy … -- -D warnings`, after the full review; `cargo check` before it) ([testing-and-ci.md](../../../testing-and-ci.md), "Lints and formatting"; [01-workspace.md](../../../architecture/01-workspace.md), "Cargo features").
- **Hook commands without the engine, and approved extensions' gates held** ([12-extensions.md](../../../architecture/12-extensions.md), "A build without the script engine"). Such a build had given the loop no hooks at all: the user's own `[hooks.<name>]` and a trusted project's approved hooks, which are processes and need no engine, never ran, and a gate on `tool.before` or `prompt.submit` let through what it would refuse.
  - The seam is not built on the engine's types, and is built in both builds now: `HostParts` moved to `ext::host` and the hooks' naming to `ext::hooks`, and only the script hooks' part is behind the feature. Hook commands run in a build without the engine as in the shipped one, `session.start` and `session.end` included.
  - An extension that stands approved holds its gating hooks there, failing, as the shipped build holds those of one it cannot load (`ext::without_engine`): those the registration cache keeps at its pin's hash, else a gate on each gating event its approved manifest lists, else both gates. While the pins cannot be read, the user's extensions hold what the cache keeps of their names and their manifests' gating events; while the trust store cannot be read, a project's hold nothing. The refusal says the build has no script engine, and gives the way out.
  - `extensions/status` and `cineris ext list` give such an extension as `failed`, "approved, and not loaded: this build of Cineris has no script engine, which runs it", never `ready`; the protocol is unchanged. `manage::status`'s reading of the stores, the folders and the cache is `manage::judge` now, which the build without the engine judges a session's extensions with as it opens.
  - The decision is built in every build, so that its tests run in the ordinary test run.
- **The pins writers' test made deterministic** (`cineris-policy`). `pins::two_writers_at_once_both_keep_their_pins` caught a lock let go too early only when four writers' turns happened to overlap: alone it missed `pins-lock-let-go-before-the-write` now and then, and on a loaded machine both breaks of the lock went uncaught. `PinStore::update` marks a point between its change and its write (`cineris_policy::trust::BEFORE_THE_PINS_ARE_WRITTEN`, nothing in a build without the test hooks), and `pins::a_writer_between_anothers_read_and_write_waits_and_both_keep_their_pins` holds the first writer there, after its read, brings the second in, and reads from the lock file itself whether it is held, so that nothing waits on a clock or on a thread in the system's lock ([testing-and-ci.md](../../../testing-and-ci.md), "A point the library stops at").

## The reviews

**The full review** (a fresh reviewer, of the close from `69090915` to `c474f72b`, the deterministic pins test included): two highs, both in the examples' READMEs. In the code the build without the engine fails closed but in one narrow race (L1), and the shipped build is otherwise unchanged.

- **High, H1: `release`'s README offered a rule that widens what the model's shell may run, in every project, untrusted ones included.** It said that `git log` is asked about in an untrusted project, since a repository's own configuration can name programs that git starts, and offered the user's rule `allow exec git log *`. That rule covers every `git log` line with any options, the model's own shell calls among them: `cargo xtask decide --untrusted --rule 'user allow exec git log *' -- git log -1 --format=%B --output=build.rs main` answers allow where it would ask, so a model led by a repository's text could write a commit message into `build.rs` unasked, for the next build to run; and `git log --output=src/lib.rs -p` is allowed the same way, `-p` running the repository's own diff and text-conversion programs, the very risk the README names. The reviewer's fix: `--end-of-options` before the range in `main.js`, a rule that matches only the extension's own line, and the README saying that an `exec` rule covers the model's shell in every project, or recommending "allow once".
- **High, H2: `shell-gate`'s README promised more than the hook gives.** It said `rm` given `-r` and `-f` is refused "in any form". Run apart from the harness with a stub of `cineris.on`, the hook let through: `rm --rec --for build` and `rm -r --f build` (GNU `rm` takes abbreviated long options, and deletes the tree); `rm -{r,f} build`; `rm -r\` and a line break before `f build`; `sh -c 'rm -rf build'`, `bash -c "rm -rf build"` and `eval 'rm -rf build'`, where its comment says `$(rm -rf .)` is read as the command it runs; `git --git-dir .git push --force origin main`, and the same with `--work-tree .` or `--namespace x` (it skipped a separate value only after `-C` and `-c`); `git -c remote.origin.push=+refs/heads/main:refs/heads/main push origin`, a forced refspec given as configuration; `git push --mirror origin`, which force-updates every ref; and, where the session's shell is PowerShell, `rm -Recurse -Force build` and `rm -r -Force build`, force being told by a lower-case `f` alone. The hook only narrows, and short of `autonomous` the engine still asks about each; the gate matters most where nothing else asks. The reviewer's fix: prefixes of `--recursive` and `--force`, `f` in either case, the argument of `sh -c`, `bash -c` and `eval` read again, the values of `--git-dir`, `--work-tree` and `--namespace` skipped, `--mirror` and a configured `push=+` taken as forced, and "in these forms" in place of "in any form", the rest listed under what it does not do.
- **Medium, M1: nothing tests the session's wiring of the build without the engine,** which the page said the tests cover in both builds. The held gates in `assemble.rs`, `PointHooks::of`'s loop in that build, the status's `not_loaded` and the hooks given to the loop are compiled only in the build `no-scripts` checks, which runs no test, and `cineris-core`'s integration tests do not compile there (21 errors). The reviewer confirmed in a copy of its own that the wiring works today (a cached `tool.before` gate on `list` refuses `list` and lets `read` through; the user is told once; the status says `failed`, with the gate; the user's own hook command on `tool.before` refuses the call), and proposed compiling the held list in both builds and testing `PointHooks` with a held gate in the ordinary build, which costs CI nothing, or running a few of the core's tests in that build, the page's sentence reworded either way.
- **Medium, M2: the close's records and its budget check were missing:** no record of this part, no step's report or budget table, no record of the whole break list's run, the stress or the close's CI times, while Windows' tier 3 was already over its budget at the eighth pull request (93.8 s against 90 on a runner at 8 ms, [ci.md](../ci.md)). This record and the step's report answer it, their figures still to come marked.
- **Lows:**
  - L1: in the build without the engine, a project's extension approved for the session by a yes the trust store could not keep is not judged once the store cannot be read, and then holds no gate, where the shipped pipeline loads it from the session's approval. It cannot happen as the session opens (a store unreadable then makes the project untrusted, and nothing is asked); it needs the store to become unreadable between the answer and the judging. The fix proposed: look at the session's approval before the store's error in `judged`, which corrects the shipped `extensions/status` too, where such an extension reads as not judged.
  - L2: `no-scripts` resolves the graph for the host's target alone, so that a dependency of Windows alone that turned the core's `scripts` on would pass (`--target all` would see it); and the page said the same build is checked on Windows with `cargo xwin check`, which no CI job runs (the reviewer ran it: it passes, with the same 7 warnings).
  - L3: the build without the engine is never linted; its 7 dead-code warnings are printed and passed.
  - L4: the new conformance scenario asserts nothing of its own, and is only compared between carriers, so a regression that broke every carrier alike would pass. Its transcript, printed, is right: the trust question lists `changelog`, the command file's body is sent, `commands/list` has both commands, and `extensions/status` says `ready`.
  - L5: a change to `examples/release/commands/release-notes.md` alone would skip CI's Rust build and tests, since CI's filter of changed paths counts every `*.md` as documentation, while the test kit and the system test read that file. Outside the step (`.github/actions/changes`): a recommendation.
  - L6: claims of the READMEs with no test: `release`'s refusal of a revision that begins with `-`, with no break either (without it, `/changelog:draft --output=x` has git write the log to a file, allowed under H1's rule); and `shell-gate`'s `-f`, `-uf`, `-fr`, `-r -f`, `--recursive --force` and the forms after `sudo`, `xargs` and `;`.
  - L7: `md-outline`'s README said a call is asked about unless a rule allows it, which does not hold at `unrestricted`, where an extension's tool runs unasked.
  - And a slip of arithmetic in decision 0039's outlook, 1.65 × 1.6 written as 2.7, since written as 2.6.

**What it checked and found sound:** the shipped binary's features (`cargo tree -p cineris-cli -e normal,build --target all` at `69090915` and at the head differ only in `default` no longer named for the core, which keeps `mcp`, `sandbox` and `scripts`); the refactors, which keep the shipped code the same (`manage::judge` reads the stores in the order `status` did, `projects_looked_in` is the same expression, the moves of `HostParts` and of the naming are structural); the held gates, which match "Its gates fail closed" for an extension approved, changed, gone, unreadable or missed by the cache, and for unreadable stores, leaving observers and the events that only add out; each refusal and its way out, under `--trust-project` too; `no-scripts`, about 12 s in a fresh copy, and the Windows check by hand; the break lists (`mutate step-28-close` 18 of 18 caught, and `mutate --check` finds every one of the repository's 4,809 breaks applies); the pins change (its point nothing without the test hooks, the test deterministic under its lock checks and passing 100 runs of `stress`, its three breaks of the lock caught); the tests (a Windows `try` run at `c474f72b` passing both new ones, no network, no real waiting, the `sys_` names right, the start-up test starting no process); and the pages and the items (`outstanding --check` and `links` clean, the page's words on `%` matching `reaches_a_program_whole`, `md-outline`'s manifest check made on the resolved path before the policy is asked).
