# Step 28, its parts: managing extensions

The second part of step 28's third pull request ([answered.md](../answered.md), "The design, before building", point 10, item 3): managing extensions (`cineris ext list|inspect|add|disable|remove`, `extensions/status`); the guards that keep a session's commands from approving an extension or trusting a project for the model; the RPC server's refusal of its own commands, shown for hooks and extensions' programs; and the first run's question on reading skill folders ([12-extensions.md](../../../architecture/12-extensions.md), "As built in step 28: managing extensions"; [06-permissions-and-sandbox.md](../../../architecture/06-permissions-and-sandbox.md), "The harness's own approving commands").

## What was built

- **A folder read through handles that follow no link** (`cineris_sandbox::unfollowed`): on Linux `openat` with `O_NOFOLLOW` relative to the folder's descriptor, a folder listed through a descriptor of its own; on Windows `NtCreateFile` relative to the folder's handle with `FILE_OPEN_REPARSE_POINT`, every handle held without sharing deletion, a placeholder opened again and checked to be the same file. `cineris_ext::folder::Snapshot::read_unfollowed` reads an extension with it, the caps moved into the read of an opened file that both reads share; `cineris ext add` reads with it, and discovery, the trust question and a runtime's start read below the folder with it (`Snapshot::read`). A name Windows cannot hold is refused on every system, and a folder's listing is taken to one name past its bound.
- **The management** (`cineris-core`'s `ext::manage`; `cineris-cli`'s `ext`): `list` and `inspect`, each standing judged from the stores a session reads; `add`, evaluated before its question, shown, written whole into the user's folder of extensions, pinned and cached; `disable`, the user's file edited in place (`cineris-config`'s `write::extension`); `remove`, unpinned and deleted on one yes, never through a link. `extensions/status` is filled (`ExtensionsStatusParams`'s `session_id`, `ComponentStatus`'s seven new fields, the result's `problems`), with one value appended to the protocol's golden values. The way out of a held gate names the commands (`script_hooks::way_out`).
- **The guards of the harness's own approvals** ([06](../../../architecture/06-permissions-and-sandbox.md), "The harness's own approving commands"):
  - **A, the engine's built-in refusal** (`cineris_policy::approving`, its table `CASES`), the CLI's grammar handed to it (`cineris-cli`'s `nested`, through `CoreOptions::own_commands`);
  - **B, the subcommands' own check** (`cineris_sandbox::session`): on Linux the line of parents, on Windows the harness's own job and a line of parents that reaches a service's host; the application, `serve` and `attach` refuse there; a nested `-p` refuses trusting flags and moved stores, and is otherwise held to `read-only` (the headless result's `capped`, an addition pinned in the golden values); a harness whose mark fails holds its sessions at `supervised` (`CoreOptions::level_at_most`, the core refusing a `session/set` past it);
  - **C, approval by the hash shown:** `ext add|remove|disable --hash H` and `permissions trust --extension NAME=HASH --hook NAME=HASH`, in place of the first round's `--yes` and the second pull request's `--with-extensions`;
  - **E, the residual stated:** the opening notice of a session whose commands are not confined (`SANDBOX_OFF_TOO`), and [security.md](../../../security.md), sections 1 and 3.
- **The stores' locks** wait ten seconds at most (`cineris_base::private::LOCK_WAIT`, `hold_lock_within`), for every caller of `hold_lock`.
- **The RPC server's refusal of its own commands** is shown, on both systems, by three probes: a hook command, an extension's `cineris.exec`, and a program the model's shell runs, standing for a hand-written client of `serve --socket` (`cineris-rpc`'s socket and pipe tests).
- **The first run's skill-folders step,** 3 of 5, and `cineris setup skill-folders on|off` (`cineris-config`'s `write::setting`), from the owner's answer of 2026-11-21 ([08-configuration.md](../../../architecture/08-configuration.md), "First run").
- **The engine's two items left by the first part** ([pr1a-engine.md](pr1a-engine.md)): `ext add` calls `forget_abandoned` before it evaluates, so that an extension refused for a thread left running starts again on a new approval; and an extension's folder is read through handles. Besides, a call stopped as its runtime's thread takes it runs nothing and says so (`CallError::NotRun`), and the core takes a tool's call once more to a fresh runtime.
- **The breaks:** the part's list, `step-28-manage`, 153 breaks, 11 of them for Windows alone ([mutations/step-28-manage.breaks](../../../../mutations/step-28-manage.breaks)); 8 of the step's own breaks and one of step 25's were pointed at the code as it now is.

## The reviews

**The early review of `ext add`** (a fresh reviewer, of the first round, both systems' halves of the new `unsafe` code read): the approval sound, one snapshot shown and written; the `unsafe` sound on both systems; decision 0030 the right home. **High:** where nothing confines a session's commands, the model could approve an extension or trust a project for itself: `cineris ext add --yes`, `cineris permissions trust --with-extensions`, a write of the stores. The reviewer set out five ways to meet it (A, B, C, D and E above), and the owner chose (points 3 and 4). **Medium:** `remove` and `disable` let a gate go with no yes (M1: `remove` now asks one question that names the unpin and the delete, and `disable` asks first of one that holds gates); the text an extension adds to the system prompt was not shown (M2: the script is now evaluated before the question, and its tools', commands' and prompt's text shown); a user's extension was said confined as the workspace confines it, though it loads in every workspace (M3: now said to hold only where the sandbox is on). **Lows,** fixed: a trailing separator at the folder's name; a folder of a great many names listed whole; the destination not looked at again at the yes; what an interrupted write left beside it; names Windows cannot hold; `~` left unexpanded where PowerShell and `cmd` pass it on. **Left:** the delete relative to a held handle (point 8; the exact name is now preferred over another case of it), and Windows tests of a link for `add`, `remove` and a write over a link, with breaks for `O_NONBLOCK` and for sharing without deletion, which were not built.

**The early review of A** (a fresh reviewer, of A as first built): a line could still run an approving subcommand. **High:** a name glued into a word that an allowing rule lifted (`git -c alias.x='!cineris …'`, `env -S`, `cargo run --bin=cin`); approving subcommands missing from the list (`project accept|add|edit|promote|disable|delete`, `auth login|logout`, `stats reset`); a nested headless run that trusts or widens for itself (`--trust-project`, `--permission-mode`, `--allow`, `-c`, `--profile`, `--continue`, `--resume`, `--fork`, a variable that moves its stores). **Medium:** the CLI's real grammar should decide (M3); a line that cannot be modelled failing open in places; interactive runners, and flags' values. **Low:** false refusals (12 of 33 realistic lines, `git commit -m`, `grep`, `--help`); the cost, 492 µs on a long line; tests and breaks; wording; the binary's name. Settled in points 5 and 6.

**Its re-look** (the same reviewer): the first review's ways round closed, and two new highs. **High:** the narrowing had dropped the reading of any word, so that about fifty lines the first build refused passed (unlisted wrappers, options with values before `-c`, a name as an argument); and words the grammar could not read, a parse error or the help, were taken as safe (patterns, comments, redirections, braces). **Medium:** `parallel` and `find -exec`; `c$'i'neris`, `c$()ineris`, a pattern before the name. **Low:** a cluster of short flags; `env -uHOME`, `source` and `eval`, `cd` and `env -C`; `-p -- "$TASK"`; tests that the engine asks the grammar, that each front end gives it, and that a grammar that panics refuses. The reviewer's 370 lines went into `CASES`. On B: the cap is sound as a cap, and not enough alone (point 7). Settled in point 7.

**The full review** (a fresh reviewer, of the whole part, A, B and C together): **High, Windows:** a start through WMI or the task scheduler (`Win32_Process.Create`, `wmic`, `schtasks`, `New-ScheduledTaskAction`) passed A, and was outside the harness's job, so that B did not see it. **High, Linux, end to end:** `echo 'setsid -f sh -c "…cineris ext add…"' | sh` was approved and pinned at `unrestricted`: A did not read what a pipe feeds a shell, and B did not see a command that detached itself. **Medium:** A's reading recursed without bound, so that a line of 6 KB (`nohup` a thousand times; PowerShell's `start` five thousand times) overflowed the core thread's stack and aborted the harness, and some forms were quadratic. **Names held ahead:** Windows's one shared job could be made ahead with breakaway allowed or with an access list that denied the harness, which then ran unmarked, and an error opening another process's job read as no job; a store's lock held by a command waited for ever. **Lows:** B took a user's own `cin` wrapper for Cineris; A refused reads of `$env:`, `command -v cineris`, `HOME=… cin --version` and `if ($?) { … }`; `ext remove` could take another case of a name; look-alike letters; the dependency rows and decision 0030's amendment. What only signed approvals close, the reviewer named: direct writes; a script, a copied binary or a name the shell builds run by a daemon already running; keys typed into the user's terminal; a job tampered with; and the hash, which is public. Settled in points 9 to 11.

**Its fixes,** in two rounds (the part's author, then a fresh one): every call into A's reader checks its depth and a budget of work, and a line over 32 KiB that names Cineris is refused; A gained the general rules of [06](../../../architecture/06-permissions-and-sandbox.md) ("Where Cineris is found"): what a pipe or a substitution feeds a program that runs it, the runners that reach a daemon or a service, the keys a terminal is told to type, a flag's one-word line, `git`'s configuration values that are lines, a `sed` script with `e`, interpreters by their versions and clusters, the missing shells, PowerShell's arrays and casts, continuations, look-alike letters, hidden braces, every form that sets a store's variable; the review's 384 probe lines, and 7 rows the breaks need, went into `CASES`; a lone help or version is safe however the line was read. B on Windows sees a service's start through command interpreters (a first version that followed the whole line refused every test on a hosted runner, `try` 45762816067); the job is named for the harness's process instance, made with a descriptor that lets its user and owner only ask, and its mark fails closed, holding the harness at `supervised`; an error opening another harness's job is not known, and refuses. B on Linux takes a process for Cineris only when it runs the same file, or when its name and its file's name are both Cineris's. The stores' locks wait ten seconds. The subreaper was not begun (point 10).

**The narrow re-check** (the full reviewer, of the fixes): fixed, A's side of the first high, B's walk up the line of parents, the job's hardening, Linux's false refusal, the help and the version; the engine's "must not change" held. **Medium, left:** the join of line continuations recursed before the bound on a line's length (3,000 backslashes and line breaks, 6 KB naming nothing, abort a thread of 2 MiB; 2,000 pairs take 223 ms), and the scans of braces were quadratic (`cin ` and 32,000 `{`, over 10 s); and on Windows a start through WMI or the scheduler of `python -c` whose code runs `["cin","ext","add",…]` (and `pythonw`, `perl -e`, `node -e`, `ruby -e`) passed A in PowerShell and B, whose walk ended at the interpreter of a language. **Lows:** the credentials' lock (`auth login`) and the session index's lock wait with no bound; two false refusals on Windows (a terminal a logon task opened; a service host counted when the service manager cannot be asked, under `runas`); the level cap's message says the harness could not mark its commands for a nested run's cap too; a planted job that denies its opening forces a refusal. The lines A misses that B catches, and those only the residual reaches, went into the step-32 item. Settled in point 13.
